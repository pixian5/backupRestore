## 6. 配置类功能的核查纪律（2026-10-17 实机确立，两个真实缺陷换来）

> 触发场景：产品里任何"`设置窗口/ini/env` 里写了一个值 → 某处代码读它"的功能。
> 本节来自 v2.6.10 独立复核查出的**两个**静默失效缺陷（`20261017-0116`）。

- **「写进去了」不等于「读出来了」——必须沿取值函数反查写入方。** 验收配置项时，
  先找到**消费它的那个函数**（这里是 `dism_timeout::wait_ms()` / `recovery_progress::pause_total_timeout()`），
  再问"谁给它赋的值"。只验 ini 内容正确 = 弱信号，会放过整类缺陷 —— 20261017-0116 [✅]
- **两个缺陷的共同形状**：写入方存在、读取方存在，但**不是同一个键**或**不是同一个进程**：
  - 键不一致：读取方写裸字符串 `"BACKUPRESTORE_PAUSE_TIMEOUT_SECS"`，全仓**零写入方** → 恒为默认值；
  - 进程不一致：`wait_ms()` 只读进程环境变量，而唯一赋值点在 `recover_env`（恢复环境专用），
    于是**在线还原**与 **图形用户界面安装预安装环境** 两条路径永远读不到用户在设置里配的值 —— 20261017-0116 [✅]
- **规则：任何跨模块传递的键名一律提为单一来源常量**（`PAUSE_TIMEOUT_ENV_VAR`）。
  裸字符串各写各的时，"只有读取方、没有写入方"这件事编译器不会提醒你 —— 20261017-0116 [✅]
- **「默认 0 = 不限制」类开关的验收必须做三组对照，缺一不算通过**：
  ① 不配置 → 应为默认（零回归）；② 配置 → 应为配置值；③ 同时有显式 env 与 ini →
  **显式必须赢**（否则会破坏"任务级值优先"的无人值守契约）—— 20261017-0116 [✅ 实机三组]
- **优先找"调用前就写日志"的取证点**：`online_operation::dism` 在**调用 DISM 之前**就把等待上限
  写进 `Online.log`，所以哪怕 DISM 必然失败（用 310 MB 的 `S:` 卷做源、退出码 32），
  这一行也能直接证明"配置是否被读到"——**失败不影响取证**，零风险拿到强信号 —— 20261017-0116 [✅]
- **`cfg` 门控要跟着模块走**：`mod dism_timeout` 是 `cfg(any(windows, test))`，在 `main()` 里裸调用它，
  macOS 的非测试构建立即编译失败。新增调用点前先看模块声明的 cfg —— 20261017-0116 [✅]
- **给只被 Windows 路径调用的函数/常量加 `#[cfg_attr(not(windows), allow(dead_code))]`**，
  否则 macOS 构建多出 `dead_code` 告警，破坏"clippy 零新增"的对照基线 —— 20261017-0116 [✅]

### 12.2 「码没追到出口」会以「同一类失败两种待遇」的形式复发（v2.6.69 实机）

- **★ 一条只读拒绝用例就能逼出产品缺陷**：`secondary_menu_repair_rejections` 断言
  「拒绝路径的失败必须带码」，第一次跑就红——`bcdedit.exe failed with exit code: 1` **无码**。
  查下来是**四条同类路径一条有码三条没码**：
  `run_logged` 用 `BR-APL-009`，而 `capture_logged` / `run_command` /
  `windows_prepare::run_bcdedit_quiet` 都用无码 `err()` → `--json` 的 `errorCode` 恒 `null`。
  **凡「外部命令非零退出」，四条出口都要问一遍「码去哪了」**，别只查主链。
- **★ 断言「有码」不够，要钉死具体码**：`error.code().is_some()` 只能证明有码。
  改 `assert_eq!(error.code(), Some("BR-APL-009"))` 后，换码也会红。
- **★ 模板有槽就得给值**：`BR-PE-039` 的模板是 `{0} 失败：{1}\n{2}`，直通通道没有输出可传，
  塞空串会让文案与 `--json` 尾部多一个**裸换行**（实机 `od -c`：`3` 后直接是 `"` 才算干净）。
  与其塞空串，不如加一个无槽的码（`BR-APL-010` `ProgramExitNonZero`），并跑
  `tools/gen-error-codes.py` 重生成 `docs/ERROR-CODES.md`（pre-push 第 3 步会校验同步）。
- **★ 内存字符串截尾要自己保 UTF-8 边界**：`&text[len - max..]` 会在多字节字符中间切开而 **panic**。
  纯函数 `text_parsing::tail_of_text` 从候选起点往后挪到最近的 char 边界（代价最多 3 字节），
  单测覆盖 `max = 1..=len` 全区间。
- **★ 插入新测试时锚点必须包含它自己的全部属性**：用「`#[ignore] fn X` 到函数体」当锚点插入新用例，

- **★ 升版本必须刷 `Cargo.lock`**：改完两处 `Cargo.toml` 直接进 VM，`--locked` 报

- **★ 能跨平台的判据优先**：`run_command` 的回归测试用 `sh -c 'exit 3'`，
  在 mac 上也跑——`#[cfg(windows)]` 里的测试在 mac 上是零信息，这条不改。

### 13.3 判据的**输入**也是判据的一部分（2026-10-27 实机）

同一个毛病到今天已出现三种形态，共同点都是「报告通过，而实际什么都没验」：

| 形态 | 表现 | 修法 |
| --- | --- | --- |
| **空集通过** | 断言依赖某种数据状态，机器上恰好没有 → 既不会真红也不会真绿 | 判据**自带夹具**（T2/T3） |
| **用例不存在** | 用例丢了 `#[test]`，门禁在「环境缺失」那步 SKIP 掩盖 | 门禁核对 `--ignored --list` |
| **输入缺失静默通过** | 判据读外部文件，文件不在就 `return`（测试通过） | 夹具入库 + **缺失即 panic** + 规模闸 |

- **★ 大日志用小夹具，不要整份入库**：82 MB / 224 万行的真实恢复日志，
  按 `\r`/`\n` 切、按 apply 段分组、每阶段「首尾 + 均匀 30 条」，得
  **9 KB / 180 条**；再配 `parsed >= 100` 的**规模闸**（否则抽稀到 3 条也全绿）。
  抽取脚本 `tools/test/extract-wimlib-fixture.py` 全程按 `bytes` 处理，**不 decode-rencode**，
  否则会改掉 `\r` 与编码细节。★ 只抽「能解析出百分比」的片段，才与真实日志等价。
- **★ 两份输入必须共用同一套断言**：把三条断言收成 `assert_replay()`，常态版（夹具）与
  取证版（全量日志）都调它——否则两处各写一遍，改一处漏一处。
- **★ `*.log` 会把夹具吃掉**：本机能跑只是因为文件恰好在盘上，CI 上直接 panic。
  加 `!path/tests/fixtures/*.log`。判据用 **`git add --dry-run`**；
  `git check-ignore -v` 对**否定规则也会输出**（行首是 `!`），容易读成「被忽略」。
- **★ 改判据的路径解析方式 = 改判据语义**：把 cwd 相对路径换成
  `env!("CARGO_MANIFEST_DIR")` 看起来更「健壮」，实际是**编译期**路径——
  门禁在 Windows 上从别的 cwd 起跑、交叉编译又在 `X:`，拼出来必然不存在（实测立刻 FAIL）。
  稳妥做法：显式环境变量 → cwd 相对（保持旧语义）→ 源码树兜底，并把候选路径打进 panic 信息。
- **★ `prlctl exec` 里别用 `(...) &` 跑短任务**：exec 返回时会把子进程一起带走，
  写出的文件常是空的或半截，表现为「取不到 `--ignored --list`」而单独手跑同一条却成功
  （典型竞争）。秒级任务**同步执行**；只有跑 DISM 的长用例才异步，且必须配轮询兜底。
  —— 20261027-2210 [✅ cli 307 + core 57；门禁 pass=5 skip=5；CI 40516744674 / 40518002710 双绿]
- **★★ `prlctl exec` 约 1/8 的调用「根本没执行」命令**（不是失败，是没跑）：症状是
  **结果/日志文件连创建都没有**，而脚本会白等到超时，再把「仪器没工作」判成 FAIL。
  本机实测两次分别落在 `secondary_mapping_rejections` 与 `secondary_menu_repair` 上，
  而同一条用例手工重跑都是 0.01s / 1.8s 全绿。**重启后几十秒内（VM 忙）比例明显更高**。
  判据纪律：凡「发出命令 → 等它产出文件」的步骤，一律走
  `vm_launch_verified <通道> <命令> <探测命令>`（发 → 探测是否生效 → 最多重发 3 次），
  而不是「发一次然后死等」。★ 注意这仍是**仪器层**补救：判据还是那一行 `test result`，
  绝不允许把失败改判成通过。 —— 20261028-0835 [✅ 单条用例 6.01s PASS]
- **★★ 「清完就好了」是错的，要问「它靠什么复发」**：把可见的残留（注册表/文件/进程）清掉
  只解决当前实例。判断修没修好，必须找出**复发载体**——本次的载体是 Windows 的
  「登录时还原上次打开的文件夹窗口」（`HKCU\...\Explorer\Advanced\PersistBrowsers`，
