## 2. 版本与部署

- 版本规则：每次修改 **+0.0.1、每一位满十进一**；**仅源码轮升**（纯文档/验证轮不升）；三处同步 = `VERSION` + `crates/backuprestore-cli/Cargo.toml` + `crates/backuprestore-core/Cargo.toml`（漏同步让构建脚本版本断言失败；`PROGRAM_VERSION` 取 `CARGO_PKG_VERSION`，图形用户界面「关于」与镜像元数据都显示它）；当前 **2.6.25**（2026-10-22；wimlib 覆盖式还原通道集成轮）—— 20261014-2107/20261015-0725 [✅]
- **版本号是标签不是文档 ID**：同一个版本号可能挂多篇文档（2.2.2 同时挂数据卷+系统卷两份），判定覆盖范围必须列全该号下所有文档再合并 —— 20261011-2350 [✅]
- 部署判据只有一条：**包目录 `BackupRestore.exe`+`Recovery.exe` 与 H:\brwork 两份，四个文件的 SHA-256 与刚构建的成品逐个相等**；曾踩"只更新包目录、运行目录 Recovery.exe 还是旧件"（唯一症状是镜像元数据 programVersion 偏低，静态检查看不出来）—— 20260819-2245 [✅]
- **wimlib 通道的部署核对 = 六个哈希**（v2.6.25 起）：`windows/wimlib-aarch64/` 两个二进制（`wimlib-imagex.exe` 125,440 B sha256 `fddb8c21…f908`、`libwim-15.dll` 432,640 B sha256 `b34549c6…c992`）随构建脚本拷到**包目录 + H:\brwork 两处共四个副本**，两个构建脚本（macOS `build-win.sh` / 虚拟机 `build-windows.ps1`，**后者的 wimlib 部署块是 2026-10-22 端到端轮补的**——此前只改 macOS 侧，虚拟机路径会漏部署 wimlib，端到端必倒在 apply 步）逐一与仓库基线比对；恢复环境内则由 `OPTIONAL_RUNTIME_FILES` 经 `inject_winre_payload` 注入恢复环境的 `Windows\System32`（缺失容错不阻断，用到时 `locate_wimlib` 明确报错，**绝不静默回退 DISM**）。恢复环境内定位规则 = `current_exe().parent()`（恢复环境里 exe 就在 System32）—— 20261022-1719/2030 [✅]
- **实机部署一律走虚拟机内 `build-windows.ps1 -Deploy`**（2026-10-15 拍板：虚拟机内构建是唯一发布路径）。macOS 侧 `build-win.sh --deploy` 确实存在且已含 wimlib 八联校验，但它部署的是**交叉编译产物**（`1423beba…091d`），只配做本地类型检查——别被旧文档「`./build-win.sh --deploy`」的部署指引带偏（20261022-1719 待办文档已勘误）。端到端轮虚拟机部署件 = **`87ad04d6…bfc03`**（包目录 + H:\brwork 两处一致）—— 20261022-2030 [✅]
- 部署前先 `Stop-Process`/taskkill 两个 exe 并等 500ms 释放句柄；copy 撞"另一个程序正在使用"时脚本仍可能打印 DEPLOYED —— 20260819-2245/20260913-0505 [✅]
- **图形用户界面以提权状态运行时，未提权会话的 `Stop-Process` 静默失败**（不报错但进程还在，copy 撞占用）→ 走 **SYSTEM 通道 `taskkill /f /im BackupRestore.exe`** 再部署 —— 20261022-2030 [✅]

## 6. CI 与工具链固定（2026-10-27 恢复 CI 时确立）

- **★ 一个长期红的 CI 比没有 CI 更坏**：上一版 CI（`9b96f52` 引入）跑
  `audit-runtime-boundaries.sh`（`fmt --check` + cli 的 clippy `-D warnings` + 交叉编译），
  连续红了 5 次后被整个删掉（`8dcfe88`）。它红的原因全是**本机门禁刻意不做的事**：
  仓库从未 fmt-clean、cli 那 40 条告警几乎都是 `cfg(windows)` 假阳性、交叉编译要 Windows SDK libs。
  → 重建 CI 时只搬「本机能验、云端也验得了」的 4 步，**第一轮就必须全绿**。
- **★ 工具链必须固定**：`rust-toolchain.toml` 写 `channel = "1.98.1"` +
  `components = ["clippy"]` + `targets = ["aarch64-pc-windows-msvc"]`，CI 显式装同版本
  并断言 `rustc --version` 与文件一致（漂移即红）。第一次跑 CI 就吃了不固定的亏：
  runner 已到 1.99，新增 clippy `single_element_loop` 把 core 里一处**故意的单元素循环**
  判成 error，而本机 1.98 不认识这条 lint → 「本机绿、CI 红」。
  ★ 固定工具链等于新装一份：**忘了 `targets` 的症状是 `can't find crate for 'core'`**，
  与代码无关，极易误判成代码坏了。
- **★ 断言要看 `--list` 真值，别信「没报错」**（同 §5 的口径）：CI 恢复后
  Windows 侧真跑出 **341 passed / 10 ignored**，而 mac 上这一半是零信息。
- **★ 用例若依赖具体硬件布局，就是 CI 的定时炸弹**：`recovery_object_accepts_only_the_registered_partition`
  硬编码 `harddisk0\partition6`（只有开发机有独立恢复分区），runner 上直接红。
  正确做法是**用本机真实卷构造规格**（`volume_identity` 取盘号/分区号 + `dos_device_of` 取
  NT 设备路径），既能任何机器通过，又比常量断言更强（验的是「真设备 → 真分区号」链路）。
  —— 20261027-2145 [✅ 两个 job 全绿：gate 306+56、windows 341/0/10]
