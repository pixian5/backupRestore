# 02 虚拟机操作与传输纪律

> 本节全部来自多轮实机踩坑，可信度以标注为准。坐标/分辨率/空闲**每轮重新实测**。

## 1. prlctl 通道三态

- `prlctl exec "<VM名>" cmd /c "命令"`（**多参数姿势**，不加 `--`）= **SYSTEM+管理员**；把整个 `cmd /c ...` 当一个引号串会静默失败(被当程序名) —— 20260927-0016 [✅]
- `--current-user` = Session 1 中等完整性令牌：图形用户界面会话可见，但跨完整性读控件/UIPI 拦键鼠；**冷启无登录会话时返回固定占位 `p8b6\x`，不是通道坏**，判活看 SYSTEM 模式 `whoami` 是否干净 —— 20260927-0016 [✅]
- 全功能恢复环境内 `prlctl exec` **可用**（刚进恢复环境瞬时报 `Unable to open new session`，稍后重试即恢复，别据此断定没代理）；裸 WinPE 内不可用 —— 20261013-2115 [✅]
- **虚拟机名必须带空格完整形式或用 UUID**；间歇抖动（`Invalid argument`/打不开会话）等 3-5s 重试即可，不是客体故障 —— 20261014-1216 [✅]
- `prlctl restart` 对无 Tools 的预安装环境无效，需 `stop --kill` + `start`；卡锁屏时 `stop --force` + 8s + `start`（约 16s 就绪）—— 20260911-0102/20261013-2115 [✅]
- 长 `-EncodedCommand` 会整体超时；**复合长脚本过 prlctl 会神秘挂起且 0 字节输出——拆单步逐个验证** —— 20261014-1216/2107 [✅]

## 2. 会话隔离与键鼠注入

- `prlctl exec` 跑在 Session 0 服务窗口站，图形用户界面在 Session 1：**SYSTEM 通道结构性 EnumWindows 不到主窗口**（GetLastError 1400 类）→ 图形用户界面操作用计划任务 `Interactive+Highest`（`restart-gui-plain.ps1`/`restart-gui-h.ps1`）或虚拟机内 TCP agent —— 20260927-0016/20261014-1315 [✅]
- **唯一可靠键鼠路线 = 虚拟机内 TCP agent**（`tools/win-clicker/br-agent-tcp.sh` → 提权+Session1+高完整性，真实 `SetCursorPos`/`mouse_event`/`SendInput`） —— 20261014-0126 [✅]
- **⚠️ 2026-10-17 修正「Win32 消息级不可行」**：消息级并非绝对不可行，**UIPI 只拦「完整性级别更低」的发送方**。用 `tools/launch-as-gui-token.ps1`（SYSTEM 通道 `OpenProcessToken`+`DuplicateTokenEx`+`CreateProcessAsUser` 借 **图形用户界面自己的提权令牌**）起子进程后，子进程与图形用户界面 **同会话/同 IL/同桌面**，`PostMessage(BM_CLICK)` 与 `SendMessage(WM_SETTEXT)` 均**完整生效**（设置窗口四输入项端到端全绿，见 `20261017-0100`）[✅ 2026-10-17 实机]。但需同 IL；跨 IL 时仍被静默丢弃（返回 0、不报错）。
- 端口 9124；虚拟机 IP 段 10.211.55.x；空闲 900s 自退；agent 的 exec 与 agent 同进程，脚本里写 `exit N` 会把 agent 一起杀掉——一律用 `return` —— 20260927-0016/20261014-0126 [✅]
- 判注入是否生效**只信 `GetLastInputInfo` tick 前后对比**，不信退出码 —— 20260927-0016 [✅]
- F 键/组合键用 `prlctl send-key-event --scancode`（`--key enter` 是无效键名、退出码 255 且静默无效；Enter=28 Tab=15 Insert 等需 scancode）—— 多篇一致 [✅]
- 键盘注入半瘫根因：`keybd_event` 扫描码传 0 且不置扩展键标志 → Home/End/Insert/Delete/PageUp/方向键被标准 EDIT 忽略（Backspace 不是扩展键所以一直正常）。修法 `MapVirtualKeyW` 取真扫描码 + 扩展键表置 `KEYEVENTF_EXTENDEDKEY` —— 20261014-0126 §4 [✅]
- 标准 EDIT **本身不支持 Ctrl+A**（RichEdit 特性）；可靠全选 = `End(0x23)`→`Shift+Home` —— 20261014-0126 [✅]
- ⚠️ `tools/win-clicker/vmkey.sh space` 疑有键码 bug：路由门按数值区间 59-88 走 scancode，`space`(-k 65) 落入该区间被发成 scancode 65=F7；09-30 的"修复"只改了 f7 数值没动路由门，F7/F8/F9/F10 映射疑均错位。**用 f7-f10 前先现场打条短命令截图核对** —— 代理静态核验 [🔸 未实证]
- SmartMouse 卡死（连宿主光标都动不了）按 Ctrl+Alt 释放；根治关 SmartMouse 但 `MouseSync`/`MouseVtdSync` 必须保持 1 —— 20260927-0016 [✅]
- **prlctl 无鼠标注入接口**；macOS AX/computer-use 合成鼠标事件不转发进 guest —— 20260913-1408/20260916-0759 [✅]

## 3. 编码链（踩过 N 次的元凶）

- `prlctl exec` stdout 是 **GBK**：宿主侧 `iconv -f GBK -t UTF-8` 或 python `decode('gbk')` —— 20260927-0016 [✅]
- **中文 cmd 管道会静默漏字段行**：`bcdedit /enum {bootmgr} /v | findstr /R default displayorder resumeobject` 只命中 default——字段名本身是英文，是 GBK 字节流与模式不匹配；**根治 = 管道前 `chcp 437`** —— 20261015-0708 实测 [✅]
- 写进客体的 `.ps1` 必须纯 ASCII 或 UTF-8 带 BOM（PS5.1 按 GBK 读 UTF-8 here-string，C# 段里任何中文注释都会吞行致 Add-Type 失败）—— 20260916-0759 [✅]
- DISM/BCDBoot 原生输出按系统代码页；产品用 `decode_windows_bytes` 按字节嗅探（UTF-8 失败则 MultiByteToWideChar CP_OEMCP/CP_ACP）—— 20260819-implementation-notes/20260930-1530 [✅]
- **二进制内含新代码核对**：Rust 字符串字面量在 exe 里是 **UTF-8**（不是 UTF-16）——`[Text.Encoding]::UTF8.GetString(ReadAllBytes)` 后 `Contains`；`findstr` 查中文/二进制不可靠 —— 20261014-1216/0126 [✅]
- GBK 陷阱：`read_to_string` 读 GBK 控制台输出解码失败会被当成"无输出"；快照/`cmd >` 重定向文件读用 `GetEncoding(936)` —— 20261005-1050/20261015-0021 [✅]
- zsh `echo` 把 `\c` 当抑制输出——写 batch 一律 `printf '%s\n'` —— 20261015-0010 [✅]
- PowerShell 5.1：`ConvertFrom-Json` 处理不了仅大小写不同的键→验收用 python 标准 JSON；`$_`/`\` 会被 exec 吃掉→复杂参数走 `-File` 或 base64 —— 20260930-2130/20260927-0016 [✅]

## 4. 共享盘与 UNC

- `X:` = 共享目录，**只在虚拟机交互会话可见**；SYSTEM 会话用 UNC `\\Mac\backupRestore`（prlctl exec 传 UNC 要双反斜杠转义）—— 20261013-1725/20261015-0105 [✅]
- `powershell -File` **不吃 UNC 路径**——先 copy 进虚拟机再跑 —— 20261015-0105 [✅]
- 共享盘"坏"的真因是 Tools 降级+无交互登录会话（prl_fs 只有 console 登录才建通道）；`net view` 报 1702 是假警报，判好坏直接 `dir \\Mac\backupRestore\VERSION`；`if exist \\Mac\...\NUL` **恒假** —— 20260928-0658/20261013-1725 [✅]
- 共享目录**不同步 `.` 开头隐藏文件**（计划任务静默不执行）；共享不同步同名文件覆盖有 >12s 缓存（用唯一文件名）—— 20260927-0016 [✅]
- 共享盘重启后必掉：`net use X: \\Mac\backupRestore /persistent:no` 是唯一解，`--shf-host off/on` 无效 —— 20261012-1510 [✅]
- ★★ **宿主侧已存在的「只读」文件（`-r-xr-xr-x`，无 `w` 位）在 SMB 侧不可覆盖**：`copy /y` 退出码 **0**、加 `&& echo OK` 也会打印 OK，但原始输出是 `拒绝访问。` + `已复制 0 个文件。`（GBK 乱码，`cat -v` 才看清）—— 判据必须是**产物大小/SHA-256**，绝不是退出码。先 `dir` 确认宿主侧权限；解**法两条**：① 宿主 `chmod u+w <file>` 后重试；② **更稳**：拷成**新文件名**（`pe-boot.new.wim`，新文件不带继承的只读位）→ 宿主侧 `mv` 顶替。★ 本机 `pe-assets/pe-boot.wim`/`pe-boot.sdi` 就是 09-13 留下的只读件，坑了整整一轮「重出镜像」 —— 20261029-0020 [✅ 实测]

## 6. 宿主空间（CoW 模型，2026-10-15 用户纠正）

- **快照走 CoW：只记相对父快照的增量，不会整份复制磁盘**。层数多的真正代价 = 各快照增量各自累积、**删除前不释放**；10-12 吃满怀因 = 多轮大量写入的旧块增量累积。估算按「写入量 × 保留层数」，**不按「磁盘大小 × 层数」** —— AGENTS.md/20261015-0710 [✅ 用户拍板]
- 纪律不变：改启动配置数据/默认项/一次性启动/恢复环境注册/预安装环境部署**不拍整机快照**（用启动配置数据文件级备份）；确需回滚才拍且**全程最多 1 个**；跑 87GB 级还原前宿主空闲 ≥ 镜像 × 2.5；跑完立刻 `df -h /System/Volumes/Data`；有快照时 `prl_disk_tool compact` 无效（先删层）—— AGENTS.md [✅]
- **删快照必须由旧到新**（Parallels 删快照 X 是把子快照增量合并进 X；反向删会让小文件吸收大增量，仅剩 646MB 时极可能 ENOSPC）；zsh 不做单词切分，`for id in $LIST` 要写 `LIST=(...)` + `"${LIST[@]}"` —— 20260929-1948 [✅]
- `tools/vm-snapshot.sh` 用 `set -euo pipefail` 且输出重定向进记录文件→**快照创建失败时一声不出**；排查读 `.test-artifacts/snapshots/<stamp>-<label>.txt` 的 `VERIFIED_SNAPSHOT=` —— 20260929-2040 [✅]
- `\Mac disk` 是磁盘气球：宿主越满越写大气球的正反馈死循环，停 Tools Service 瞬间消失（禁用服务期间 exec 通道也断，失败分支必须 `net start` 拉回）；它必须进 Capture 排除表（始终被独占，/Apply-Image 撞 0x80070020）—— 20260928-2215/2247 [✅]
- 一天积累 39 个快照约 180GB；清理后宿主 646MB→186GB。实验快照设上限，先建一个明确命名的干净基线长期保留 —— 20260929-1948 [✅]
- 快照对 suspended 虚拟机必失败：先 `resume; sleep 8; stop --kill` 再建；`PRL_ERR_REVERT_IMPERSONATE_FAILED` 常伪装成权限问题，真因是 Mounter 占锁（kill pid + umount /Volumes/.PEVolumes/*）—— 20260925-0424 [✅]
- **薄配 `.hds` 删文件不还宿主空间**：客体内 `format`/`del` 只标记空闲，宿主 `.hds` 不缩；唯一有效手段 = **虚拟机优雅停机（触发客体 TRIM 回收）**。2026-10-22 端到端前实测：宿主仅剩 70GiB 而镜像展开需 68GiB → 停虚拟机后 harddisk1 从 102GiB 缩到 68.8GiB，空闲 70→112GiB。overlay 覆盖写只碰既有块，还原过程宿主零增长（端到端全程实证）—— 20261022-2030 [✅]

## 7. 其它会咬人的小坑

- 停 Tools 前的 vssadmin/DISM 在线命令只输出版权信息 → 用 `schtasks /create /tr ... /ru SYSTEM /rl HIGHEST /f` + `/run`，用完删任务 —— 20260913-0021 [✅]
- `schtasks /it` 不启动 PowerShell；沙箱策略会拦 `schtasks /delete /f` 与 `del`（判为不可逆删除）→ 用同名 `/f` 覆盖创建、用 `>` 覆盖写输出 —— 20260913-0021/20260925-1940 [🔸]
- 客体删大文件别用 cmd `del /f /q`（会谎报"找不到"而文件仍在），用 `Remove-Item -LiteralPath -Force`；全盘 `Get-ChildItem -Recurse` 遇单个目录拒绝访问会整体中止，改分目录 `cmd dir /s /b` —— 20261013-2348/0020 [✅]
- 目录含保留设备名文件 `nul`（历史脚本 `copy nul` 忘加 `>` 真创建了 0 字节文件）会让删目录报"不是空的"—— `[System.IO.Directory]::Delete("\\?\path",$true)` 绕过 —— 20260913-0021 [✅]
- 提权会话看不到共享盘 X: 但看得到 UNC；提权进程 `GetFolderPath('Desktop')` 可能返回 `C:\Mac\Home\Desktop`（Parallels 重定向）—— 20260925-0424/20260911-0102 [⚠️]
- `--pause-idle off`：虚拟机窗口非活跃+无窗口程序会被自动暂停，exec 报 `Unable to open new session`（是睡了，`resume` 而非重启）；用完虚拟机最稳是 `prlctl suspend` —— 20261009-0830 [✅]
- 测试期温控：`prl_vm_app` 92-104% CPU + ~6.8GiB 时 WindowServer ~60%、无 thermal warning —— 20260819-impl-notes [🔸]
- PD27 vs PD26.4.2：ramdisk 引导在 PD27.x EFI 固件崩溃触发虚拟机复位（~6.4s 必现、静默复位非 0xc00000xx），PD26.4.2 同虚拟机同镜像成功——故障与固件版本绑定，与文件系统/镜像大小无关；ISO 引导成败也与 PD 版本绑定。宿主当前版本以实际为准 —— 20260925-0025/0424 [⚠️ 时点敏感]

## 8. 图形用户界面消息级自动化纪律（2026-10-17 实机确立）

> 前提：先按 `tools/launch-as-gui-token.ps1` 借 **图形用户界面自身提权令牌** 起子进程（同会话 1 / 同 IL / `winsta0\default`）。
> 借令牌子进程**没有控制台**，一切输出必须**落文件**；成功与否只看 `launch.log` 的 `launch_result=True`。

- **`SendMessage` 必须写 `[DllImport(..., CharSet=CharSet.Unicode)]`**：不写时默认 Ansi → 走 `SendMessageA`，跨进程按 **ANSI** 编组 `WM_SETTEXT` 的 UTF-16 指针 → 第 2 字节即 NUL，**只传过去首字符**（注入 `1200` 存成 `1`、`600` 存成 `6`）。**单字符测试值会漏掉这个 bug**，多位数必须带 readback —— 20261017-0100 [✅]
- **点按钮/单选一律用 `PostMessage`（异步），不要用同步 `SendMessage(BM_CLICK)`**：图形用户界面线程处理 `BM_CLICK` 时会进入**嵌套模态消息循环**，跨线程 `SendMessage` 的等待被拖到模态窗口关闭才返回 → 脚本静默卡死（症状：transcript 停在最后一行、窗口其实已弹出）—— 20261017-0100 [✅]
- **借令牌的子进程看不到 `X:`**（每用户网络驱动器映射不随复制令牌走）→ `Start-Transcript -Path X:\…` 抛错使**全部输出丢失**，表现为「脚本没跑」。日志与 marker 一律写**本地路径**（`<exe>\logs\`），宿主再用 SYSTEM 通道读回共享盘 —— 20261017-0100 [✅]
- **跨进程读 EDIT 要用 `WM_GETTEXT`，不能用 `GetWindowText`**（后者对其他进程窗口不发送该消息，返回空 → 误判「值没写进去」）。`GetDlgItem` 属纯查询不受 UIPI 限制，能拿到句柄；受限制的只有「要求目标执行」的消息 —— 20261017-0100 [✅]
- **SYSTEM 会话枚举不到会话 1 的窗口**（`EnumWindows` 只看调用进程所在窗口站/桌面）：在 SYSTEM 通道找设置窗口必报「找不到」，而窗口明明开着。**分工：SYSTEM 通道管文件/注册表/进程/事件日志，借令牌通道管一切界面操作** —— 20261017-0100 [✅]
- **设置文件写在「运行中 exe 所在目录」**，不是固定包目录：`H:\brwork` 与 `C:\Users\Public\backupRestore-package` 各有一份 exe，哪份在跑就写哪份的目录。冒烟脚本硬编码检查包目录 → 会误报「settings.ini 未生成」而实际保存成功。判据要用 `Get-Process BackupRestore | % Path` 动态定位；**遇到「功能判据失败」先分清是产品缺陷还是判据写错** —— 20261017-0100 [✅]
- 冒烟成功判据（五项缺一不算通过）：窗口句柄非零 **且** 窗口矩形落在屏幕内且 `visible=True` **且** 各输入控件 readback 与注入值一致 **且** 保存后的 ini 等于注入值 **且** 保存后模态窗口句柄归零（主窗口 `EnableWindow` 已还原）—— 20261017-0100 [✅]

## 13. 安全启动：直接开必停机，**先删固件存储重建**就成功（2026-10-29 实测）

- **开关一条命令**：`prlctl set "Windows 11" --efi-secure-boot on|off|reset`
  （图形界面在「配置 → 硬件 → 启动顺序 → 高级设置 → EFI 安全启动」）。**必须在关机状态改**。
- **★★ 直接 `on` 会起不来，且不弹窗不报错**：现象是「启动约 45 秒后状态变 stopped」。
  真因在 `Windows 11.pvm/parallels.log`：`Sending warning PRL_ERR_SECURE_BOOT_VIOLATION`，
  伴随 `Error allocating memory for new data to SetVariable KEK / db / dbx`，
  而 `PK/KEK/DB/DBX` 的哈希全是 `e3b0c442…`（**空数据的 SHA-256**）。
  安全启动是**白名单**机制：白名单空 = 一切引导程序都被拒，**微软签名也照拒**
  （当次 ESP 上三个 EFI 全是 Valid + CN=Microsoft Windows，一点用都没有）。
  `--efi-secure-boot reset` 也救不了（`PK=ok KEK=lost DB=lost DBX=lost`）。
- **★ 正确做法（实测成功，02:20）**：关机 → `--efi-secure-boot on` → **删掉
  `NVRAM.dat` 与 `NVRAM.tnvs`**（这两个就是「固件存储」，删掉由固件按默认值重建）→ 启动。
  这次的日志里 `Create PK/KEK/db/dbx var` **一条 allocate 失败都没有**，系统直接进，
  客体 `Confirm-SecureBootUEFI=True`、注册表 `UEFISecureBootEnabled=1`、
  白名单 `db` 里含 `Microsoft Windows Production PCA 2011` 与 `Windows UEFI CA 2023`；
  再重启一次仍为 `True`（不是碰巧）。
- **★ 「删固件存储会丢引导项」这条老经验不成立**（至少本机）：重建后固件自己扫出
  `Windows Boot Manager`（`path \EFI\Microsoft\Boot\bootmgfw.efi`、`device partition=S:`），
  系统直接进来。9-13 那次要新建虚拟机，原因在别处。
- **白名单不含 `Microsoft UEFI CA 2011`** ⇒ 能启 Windows 与微软签名的 PE，**拒绝非微软签名的引导器**。
  这正是我们要模拟的「真机安全启动」环境。
- **回退**：`--efi-secure-boot off` + 启动即可；要回到「重建前原状」，关机后把
  `/Users/x/Parallels/brvm-backup-20261029/` 的 `NVRAM.dat`、`NVRAM.tnvs`（及 `config.pvs`）拷回虚拟机目录。
- **磁盘未加密时才没有恢复密钥风险**：开之前先查 BitLocker（本次四个卷全为 0=未加密）。
- **后续可选（2026-10-29 04:00 修订）**：①新建一台一次性虚拟机开安全启动、挂 PE 镜像启动（不碰工作机）；
  ②删 `NVRAM.dat`+`NVRAM.tnvs` 让 Parallels 重建固件存储——**本条已实测为正解**（见上，

## 14. 共享目录回传会「假成功」，且 `-EncodedCommand` 必须 UTF-16LE（2026-10-29 实测）

- **★ SMB 回传间歇性假成功**：客体 `copy` 报「已复制 1 个文件」，宿主侧**根本没有**
  （客体自己再 `dir` 也看不到）。本轮复现多次；VM 重启回 Windows 后，`X:`/`Y:` 盘符映射
  会处于「不可用」而 UNC（`\\Mac\backupRestore\…`）可能仍可用——**盘符状态不是通道状态的判据**。
  对策：**回传后必须换通道核对**。小文件一律 `certutil -encode` + 宿主 `base64 -d` 取内容；
  大文件（镜像）传完核对大小 + SHA-256。`net use X: /delete` + 重连有时能恢复，但别依赖。
- **★ `prlctl exec` 传 `powershell -EncodedCommand` 必须给 UTF-16LE 字节的 Base64**
  （`iconv -f UTF-8 -t UTF-16LE file | base64`）。直接 base64 UTF-8 原文，PowerShell 解出的
  是乱码：**换行全丢、整段被当成一个命令名**（`CommandNotFoundException`）。曾据此误判为
  「长参数被截断」——最短 8 字节也一样坏，与长度无关。
- 共享目录仍**看不见点开头的文件/目录**（见 §12），回传中转名别带点。

## 15. 清理磁盘与删分区时的两条硬规矩（2026-10-29 实测）

### 15.1 ★ `C:\Mac` 是宿主共享目录入口，按体积排序会伪装成本地大目录

- 这台虚拟机里 `C:\Mac` 的 `Get-ChildItem -Recurse` 报 **2.7 GB / 46 项**，看起来像一大坨本地残留；
  实际它是 Parallels 共享文件夹入口：`C:\Mac\backupRestore` 就是**宿主机的仓库目录**，
  另有 `Home`、`ReadMe.url`、`desktop.ini`。
- **在客体里删它 = 删宿主仓库里的文件。** 清理清单里凡出现 `C:\Mac`（或任何共享挂载路径），
  一律先 `Get-Item | fl LinkType,Target` 确认是不是挂载点，再看体积。
- 同类坑：`\\Mac\backupRestore` 映射出来的盘符也一样，别拿体积判断归属。

### 15.2 ★ Windows 的「扩展卷」只能向右长，删掉前面的分区并进去是不可能的

- 场景：磁盘上 `[MSR][T: 8 GB][56 GB 空洞][H: 192 GB]`，删掉 `T:` 后要求「并进 H:」。
- 结果：`Get-PartitionSupportedSize -DriveLetter H` 的 `SizeMax` 只比当前大 **1 MB**；
  `Resize-Partition` 报 `Size Not Supported / the size of the extent is less than the minimum of 1MB`；
  `Update-HostStorageCache` 刷缓存无效；`diskpart` 的 `select volume H` + `extend` 同样失败。
- **原因**：释放出来的 68.6 GB 全部位于 H: 的**前面**。Windows 只把「卷尾之后」的连续未分配空间
  并入卷，**不支持向左合并**（要向左并只能靠第三方工具移动分区）。
- **正确预期**：只有「删除的卷在目标卷之后」时扩展才成立。前面有空洞时，只能
  ①留着不分配，②在那块空间新建一个分区（会多一个盘符，会出现在产品的备份目标卷列表里），
  或③删卷重建整盘分区（要先把数据搬走）。
- 顺带：`Remove-Partition` 删掉带盘符的卷后，记得查 `HKLM\SYSTEM\MountedDevices` 有没有
  `DosDevices\<盘符>:` 幽灵项（本次干净，没有残留）。
