## 二、根因（已证实）

**bootmgr 只能解析「系统卷（C:）」的盘符；数据卷（H: 盘1 / F: 盘2 / T: 盘0数据分区 / P: / E:）的盘符
在 bootmgr 阶段解析不了。** 新启动通道把载荷暂存在**镜像卷**（数据卷）并用该盘符写 BCD
`device/osdevice = ramdisk=[X:]\BackupRestoreRE\<id>\Winre.wim` → winload 找不到 ramdisk →
bootmgr 丢弃一次性启动 → 回落默认项 C:。

Kernel-Boot 签名（每次失败一致）：Id 18「从 0x2 启动选项启动」、Id 27「启动类型 0x0」、
无 WinRE 引导事件、MeasuredBoot 只有一次（winload 从未为我们的条目运行）。

**关键排除项**（都试过，均无效）：
- 刷新竞态：手动武装后等 60 秒、回读仍在、暂存完好，照样回落；
- displayorder 僵尸引用（{80a463f9}/{a269ee4f} 已失效）：清理后照样回落；
- bootmgr `device=S:` vs `\Device\HarddiskVolume2`（10-11 的设备路径）：C: 手动条目在今天
  `device=S:` 状态下照样能进 WinRE，证明此项不是阻塞点；
- `\\?\Volume{GUID}` 形式：**bcdedit 拒绝**（「不支持该格式」），GUID 不能直接写 device 元素。

## 四、修复方向（已验证可行）

**把载荷暂存到系统卷（C:）**，BCD 条目自然写 `ramdisk=[C:]\...`——已手动证实能进 WinRE。
产品改动点（`windows_prepare.rs`）：

```rust
let re_staging = ReStaging {
    volume: image_volume.clone(),   // ← 现状：镜像卷（数据卷）→ bootmgr 解析不了
    ...
};
```

改为**系统卷**（`%SystemDrive%` 对应的 VolumeIdentity）。注意：
- 镜像仍在原数据卷（闸门「镜像不能位于承载 WinRE 的分区」不受影响——它管镜像，不管暂存）；
- 暂存目录建议 `C:\BackupRestoreRE\<id>\`（与注册位 `C:\Recovery\WindowsRE\` 不同目录，不冲突）；
- C: 需 ≥1GB 空闲（当前 181GB）；
- SDI 源本来就是 `C:\Recovery\WindowsRE\boot.sdi`（系统卷）——与暂存同卷后
  `ramdisksdidevice partition=C:` 也能解析（虽然实测 winload 缺 SDI 也能兜住）。

**备选方案**（未验证）：把 `ramdisk=` 写成 `\Device\HarddiskVolumeN` 设备路径形式
（需先拿到镜像卷的 HarddiskVolumeN；GUID 形式已被 bcdedit 拒绝）。

## 五、顺带澄清：「RE 硬盘版」的形态问题

即便启动通道修好，`create-secondary` 对 WinRE 镜像走的是 **apply 到 P: + bcdboot**，
产出的是一个「把 WinRE 当常规系统启动」的菜单项。而 WinRE 有「启动 ramdisk 路径 ==
ReAgent 注册位置」自校验（09-27 PoC 四路证伪、09-29 部分修正），装到 P: 的那个启动项
**大概率起不来**。真正的「RE 硬盘版」形态是 **ramdisk 启动项**（boot.sdi + wim 留在
数据卷 + 菜单项），不是把 WinRE 应用成系统卷。这一点可在通道修好后实测验证。
