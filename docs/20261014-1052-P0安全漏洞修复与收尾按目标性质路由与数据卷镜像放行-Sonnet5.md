## 二、P0：create-secondary 可格式化当前活动系统（安全漏洞）

### 漏洞复现（修复前）

`prepare --operation create-secondary --source-drive T --target-drive C --allow-destructive`
**会被接受**，重启进 RE 后 diskpart 格式化正在运行的系统盘。

三道防线全部漏过：
- GUI 智能分流 `native_gui.rs:4984` 的条件是 `matches!(operation.as_str(), "backup" | "restore-existing")`，
  **create-secondary 不在内** → 不过 `%SystemDrive%` 检查；
- prepare 侧 `assert_environment` 只查 **source** 的 SYSTEM hive，target 只查 `is_reserved_partition`；
- 唯一挡着的 `source != target`（`core/lib.rs:804`）**把源选成 T: 即绕过**。

### 修法

`windows_prepare.rs` 的 `RestoreExisting | CreateSecondary` 分支加：

```rust
let target_is_active = target.same_partition(&active_system_volume_identity()?);
if options.operation == Operation::CreateSecondary && target_is_active {
    return Err(err("create-secondary target must not be the active Windows volume"));
}
```

**按卷身份（disk/partition GUID）比对，不用盘符字面量**——盘符会重排，系统盘也不一定是 C:。

新增 helper `windows_prepare::active_system_volume_identity()`，取 `%SystemDrive%` 的 `volume_identity`。

⚠️ **restore-existing 不加这条**：它的目标就是当前系统卷，属合法场景（重建唯一系统，GUI 弹窗走 PE/RE 离线链）。

### 实机验证（通过）

```
> BackupRestore.exe prepare --operation create-secondary --source-drive T --target-drive C \
    --image-path H:\BRImages\gui-backup.wim --boot-menu-name P0Test --allow-destructive --no-reboot
error: invalid task: create-secondary target must not be the active Windows volume
退出码: 1
```

校验位置在 BCD 导出之前，所以被拒时**不动盘、不改引导**。

## 三、P1：收尾按「目标性质」路由，不按「操作类型」

### 现象与根因

离线把完整 Windows 镜像还原到 C 以外的 Windows 卷时，格式化 + BCDBoot 都做了（观感 = 装好第二系统），
但收尾缺三样 → **抢走主系统默认启动项** + **第二系统盘符绑定错乱** + **WinRE 注册不对**，
产出「能启动但会崩、且主系统每次开机被劫持」的半成品。

根因：STEP 3/4 的进入条件是「目标卷有 SYSTEM hive」（`main.rs:2645`，与 role 无关），
但里面 5 处收尾全部卡在 `target.role == TargetRole::NewWindows`（= 只有 create-secondary 才做）。

**对照**：在线路径 `online_operation.rs:302` 用 `target_is_windows_volume()` 按目标性质路由
→ 两条通道自相矛盾，**在线那套才是对的**。

### 走过的弯路：为什么不能靠重解释 `role`

`role` 全项目只有一个生产设置点（`windows_prepare.rs:802`，按操作类型写死），
一度以为只改这一处就能让 RE 侧 5 处判据自动正确。**不成立**——`role` 与 `boot_plan.mode` 是耦合的一对：

- `core/lib.rs:793`：RestoreExisting 要求 `role == ExistingWindows`
- `core/lib.rs:798`：RestoreExisting 要求 `boot_plan.mode == ReturnExisting`
- `main.rs:2513`：`role == NewWindows` 要求 `boot_plan.mode == AddSecondary`

后两条直接冲突。结论：`role` 承载的是**操作语义**（重启后回哪里），不是目标性质，
必须另加一个字段把「目标性质」解耦出来——即交接文档 §P1 原本的方案。

### 修法

`TargetSpec` 新增 `is_active_system: bool`，准备阶段落盘，RE 内读取：

```rust
is_active_system: target.same_partition(&active_system_volume_identity()?),
```

RE 内 4 处收尾判据改为 `let target_is_secondary = !target.is_active_system;`：
`secondary_registry::repair` + BCD 快照（2684）、`/d /addlast` + `/description`（2698）、
`repair_secondary` vs `repair`（2751）、`set_secondary_boot_menu` + `preserve_primary_boot_manager`（2756）。
`main.rs:2513` 的 role/boot_plan 一致性校验**保持用 role**（它校验任务自洽性，不是目标性质）。

### 为什么这个判断只能在准备阶段做

**RE 里 `%SystemDrive%` 是恢复环境自己的 RAM 盘 `X:`**（`main.rs:1702` 注释写明），
离线侧重新探测只会得到 RAM 盘，探测不到用户的系统卷。所以结论必须在联机准备时落盘带进 RE。

### 配套：`set_secondary_boot_menu` 的 menu_name 改 `Option<&str>`

restore-existing 没有用户指定的菜单名（`boot_menu_name` 只对 create-secondary 要求），
原代码 `ok_or_else(|| err("secondary target has no boot menu name"))?` 会直接报错。
改为 `None` 时只定位 loader 标识符、不改描述，但 **`preserve_primary_boot_manager` 两种情况都跑**
——保住主系统的默认启动项与菜单顺序是安全行为，不依赖菜单名。

### ⚠️ 未实机验证

需要「非活动的 Windows 卷（E: 或 P:）+ 完整 Windows 镜像」，而现有镜像全是 16MB 的 T: 数据卷备份。
造一个完整 Windows 镜像需备份 C:（已用 72.8GB）。验证三项：
**BCD `default` 没变** + 新系统能正常进桌面 + 菜单项名正确。**别用 C: 做这个验证。**

## 四、P2：数据卷镜像被硬拒

### 修法

判据用**目标卷**当前有无 SYSTEM hive，与恢复期分叉 BCDBoot 的判据完全一致：

```rust
let target_is_windows = target_is_active
    || crate::pe_safety::target_is_windows_volume(&PathBuf::from(format!("{}:\\", letter)))?;
if options.operation == Operation::CreateSecondary || target_is_windows {
    wim_full_windows_probe(path, options.wim_index)?;
}
```

- 目标不是 Windows 卷 → 这次只铺数据、不碰引导，镜像缺 Windows 标记属正常 → 放行
- **create-secondary 不在放行范围内**：装第二系统必须是完整 Windows

### 【重要坑】活动系统卷绝不能做文件探测

`pe_safety::probe_file` 会 `File::open` 目标文件（`pe_safety.rs:185`），
而**活动系统卷的 `C:\Windows\System32\config\SYSTEM` 被系统独占锁定**。
实测（PowerShell，两种共享模式都失败）：

```
[IO.File]::Open("C:\Windows\System32\config\SYSTEM", 'Open','Read','None')      → 失败：另一个程序正在使用
[IO.File]::Open("C:\Windows\System32\config\SYSTEM", 'Open','Read','ReadWrite') → 失败：另一个程序正在使用
```

共享违例（os error 32）**不是 NotFound**，会走 `probe_file_inner` 的 `Err(error) => return Err(...)`
→ **把整个准备阶段弄失败 → A 入口（还原系统到 C 盘）直接坏掉**。

所以代码里用 `target_is_active ||` 短路：活动系统卷必然是 Windows 卷，无需探测。
写代码时就发现了这个坑，没等到实机炸。

### 本机验证不了真实拒绝路径

本机 DISM `/Mount-Wim` 在有 VHD 附加时一律报 87，`wim_full_windows_probe` 走
`Err(_)` → 镜像名启发式 → 数据卷镜像名不含 "windows pe"/"winpe" → `HeuristicPass` 放行。
所以**本机 probe 形同虚设**，区分不了「probe 被跳过」和「probe 被调用但放行」。
真实拒绝路径需换一台 DISM 挂载可用的机器验证。

### 在线通道不受影响（已核实）

在线侧的 probe 在 `restore_to_windows_volume` 内部，而它只在 `target_is_windows_volume(&root)?`
为真时才被调用（`online_operation.rs:302`）。**数据卷在线还原根本不走这个 probe**，
走的是「数据卷在线覆盖，不格式化、不修复引导」分支。所以 B 入口的在线主通道本来就没有这个问题，
P2 只需改离线侧。

## 五、配套修复：加必填字段会把新版本整个卡死

### 实测踩到

P1 给 `TargetSpec` 加了必填字段（**故意不给 `#[serde(default)]`**：缺字段时默认 `false`
会让「重建唯一系统」误走第二系统收尾、去改写当前运行系统的盘符绑定，显式失败才安全）。

部署 2.4.9 后第一次跑 prepare 直接失败：

```
error: invalid task: cannot inspect existing task 559d28bd-… :
       JSON error: missing field `isActiveSystem` at line 67 column 3
```

2.4.8 留下的 **5 个终态任务**（4 success + 1 failed）缺新字段，
让 2.4.9 完全无法创建任何新任务。**这不是「安全失败」，这是拒绝服务。**

### 根因

`core/lib.rs` 的 `incomplete_tasks()` 对**所有**任务目录先
`read_json(task.json)` + `validate()` + 一致性比对，**最后**才判 `is_incomplete()`。
于是已完成的历史记录也能把新任务挡住。

### 修法

先读 `status.json` 定性，终态直接 `continue`，不去反序列化 `task.json`：

```rust
let status: StatusRecord = read_json(path.join("status.json"))?;
if !status.stage.is_incomplete() { continue; }
let task: Task = read_json(path.join("task.json"))?;   // 非终态才读
```

- 终态任务只是历史记录，读不懂也不影响「现在能不能创建新任务」
- **非终态任务仍然全程 fail-closed**（设计意图保留：被中断的任务其启动项/载荷/目标可能还等着恢复，
  读不懂必须报错给用户，不能静默跳过——`lib.rs:1276-1279` 的原注释）

这条修复让「Task 结构新增必填字段」从此不再是破坏性变更。

### 测试任务的清理（用程序自带路径，不手删）

```

```

## 七、给接手方的提醒

1. **P1 还没实机验证**，而它改的是 BCD 写入路径。做之前先造完整 Windows 镜像，**用 E: 或 P:，别用 C:**。
2. **本机 probe 形同虚设**（DISM 挂载报 87），任何依赖 `wim_full_windows_probe` 真实拒绝的验证都要换机器。
3. **活动系统卷不要做文件探测**（共享违例），要判它是不是 Windows 卷就直接定论。
4. `abandon-task` 是清理 prepared 任务的正确路径，别手删任务目录（会留悬空 BCD 条目和载荷）。
5. prepare 的 stdout 被 GUI 按行解析（`TASK_ID=` / `TASK_ROOT=`），**别随便往里加日志行**。
6. 控制台是 GBK，`prlctl exec` 的中文输出会乱码且 `ConvertFrom-Json` 可能截断含中文的字段——
   看文件真实内容要用 UTF-8 解码，别被乱码误判成「文件坏了」。
7. `prlctl exec` 会间歇性报 `Unable to open new session`（Parallels 通道抖动），重试即可，不是客体故障。
