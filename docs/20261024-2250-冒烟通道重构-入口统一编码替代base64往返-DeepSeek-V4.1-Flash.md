# 冒烟通道重构：入口统一编码，废掉 base64 往返

- 基线 commit：`3b7a74e`（v2.6.37）之后的工作树
- 撰写时间：2026-10-24 22:50
- 撰写模型：DeepSeek-V4.1-Flash
- 涉及文件：`tools/smoke/br-smoke.sh`、`tools/smoke/br-smoke-helper-seed.ps1`、`tools/smoke/br-smoke-helper-collect.ps1`

## 一、起因

用户的质疑（原话）：

> 你为什么总是只能拼接 Base64 呢？你为什么不想到直接在开始的时候就直接调整 CMD 或者 PowerShell 里面的编码，这样你不就能避免 GPK 或者 UTF-8 的问题了吗？

这个质疑是对的。`br-smoke.sh` 之前有约 90 行专门做 base64 搬运（分块 `echo` 写 `.b64`、全量长度校验、3 次重来、回读时 `grep` 拼接多段），
而这些复杂度里有**一大半不是通道限制造成的，是我自己制造出来的**：

1. 遇到中文输出乱码 → 没有在入口统一输出编码，而是把结果写成文件再 base64 编码回读；
2. base64 的大段输出被 CLIXML（PowerShell progress 流的序列化）包装行切碎 → 我误判成「prlctl 单次输出有 ~2.5KB 上限」；
3. 于是为了绕这个"上限"又加了多段拼接、`head -1`、长度校验、重试……问题越绕越多，最后变成了一个自洽但完全不必要的小系统。

## 二、实测：三条决定性结论

全部在 `prlctl exec "Windows 11"` 通道上实测（mac 宿主 / Windows 11 / PowerShell 5.1）。

### 结论 1：标准输出是字节透传，没有长度上限

```bash
# VM 内造 30000 字节 ASCII 与 6000 字节（2000 个"中"）UTF-8 文件后回读
prlctl exec "Windows 11" cmd /d /c 'type H:\brwork\smoke-big-ascii.txt' | wc -c   # → 30000
prlctl exec "Windows 11" cmd /d /c 'type H:\brwork\smoke-big-cn.txt'    | wc -c   # → 6000
```

6000 字节经 Python 校验 `utf8_ok=True`，首字符就是 `中中中中中中`。

**推论**：回读 VM 内文件只需要 `cmd /c type`，一个 `type` 就够，既不用 base64 也不需要分段。
之前所谓"上限"是 base64 文本被 CLIXML 行污染后 `grep -oE '[A-Za-z0-9+/=]{16,}'` 拼接失败造成的假象。

### 结论 2：中文输出必须显式设 `[Console]::OutputEncoding`

```bash
# 不设：输出 GBK 字节
prlctl exec "Windows 11" cmd /d /c 'echo 中文测试'            # → d6d0 cec4 ...（GBK）
# 设了：输出 UTF-8 字节
powershell -NoProfile -Command '[Console]::OutputEncoding=[Text.Encoding]::UTF8;
  [Console]::WriteLine([char]0x4E2D + [char]0x6587 + [char]0x6D4B)'
                                                              # → e4b8ad e69687 e6b58b ✓
```

注意 **`chcp 65001` 单独不够**：

```bash
prlctl exec "Windows 11" cmd /d /c 'chcp 65001 >nul & echo 中文'   # → d6d0 cec4（仍是 GBK）
```

因为 `chcp` 只改**控制台代码页**，不改**进程 ANSI 代码页**；`echo` 这类内建命令按进程 ANSI(936) 落字节。

### 结论 3：命令行参数里不能带中文，但脚本本体可以完全不经过命令行

```bash
prlctl exec "Windows 11" cmd /d /c 'if exist \\Mac\Home\code\backupRestore\tools\smoke\br-smoke.sh (echo OK)'
# → MAC_HOME_OK（\\psf\Home 同样可用）
prlctl exec "Windows 11" cmd /d /c 'powershell -NoProfile -Command "...Get-Content -Raw -Encoding UTF8 \\Mac\Home\...md..."
# → 中文完整
```

VM 能直读宿主共享目录 → **脚本根本不需要"传输"**，`Get-Content -Raw -Encoding UTF8` + `iex` 即可。
这一条顺带把「命令行 ~3.4KB 上限」也一起绕开了，所以"分块部署 helper"整套都不必要。

## 三、结论：base64 的正当边界

| 用途 | 判断 |
|---|---|
| 回读 VM 内文件内容 | **不需要**。`cmd /c type` 字节透传，无长度问题 |
| 把脚本传到 VM | **不需要**。VM 直读 `\\Mac\Home`，零传输 |
| `-EncodedCommand` 传短命令 | **保留**。它解决的是「引号/换行/`$` 被 cmd 解释」+ 让中文安全通过参数，**不是**编码转换手段 |

`-EncodedCommand` 必须留着，因为 prlctl 传参是 UTF-8 字节、VM 侧 cmd 按 936 解码，
任何含中文的参数直接拼进 `-Command` 都会乱码；走 UTF-16LE base64 就没有这个问题。

## 四、改造清单

`tools/smoke/br-smoke.sh` 通道层重写（净减约 60 行）：

- 新增 `PS_PRE='$ProgressPreference="SilentlyContinue"; [Console]::OutputEncoding=[Text.Encoding]::UTF8;'`，
  所有 PowerShell 调用统一带这个前缀 —— **编码只在一处定，调用处不再各自打补丁**。
  `$ProgressPreference` 是压 CLIXML 的关键：冒出来的 `#< CLIXML ...` 是 progress 流序列化，不是编码问题，
  压掉后 `grep -av '^<'` 只作兜底。
- `vm_read_file`：从「base64 编码 → 传参 → 多段 grep 拼接 → 解码」缩到 `cmd /c type` 一行（保留空结果重试，见下）。
- 删除 `vm_put_file` 的主路径地位 → 降级为**共享目录不可用时的 fallback**；正常路径零传输。
- 新增 `detect_share`：从脚本自身路径反推 `\\Mac\Home\...`，探测失败自动回落 `\\psf\Home`。
- `vm_run_helper`：改为共享目录直读 + `iex`，仍以 helper 自写的 `DONE` 标记判成功（通道偶发丢命令，重试 3 次）。
- 任务状态探针：原来「VM 写 `smoke-status.txt` + 宿主回读」两步，改成 PowerShell 直接打到 stdout（通道已通，省一次往返）。
- 还原日志：原来在 VM 端截尾 80 行再回读，改成整份回读（实测 2.2KB），超 512KB 才截尾 400 行。
- 两个 helper 落盘全部改成 **无 BOM**（`[IO.File]::WriteAllText` / `UTF8Encoding($false)`）：
  PS 5.1 的 `Out-File -Encoding UTF8` 会写 BOM，BOM 在宿主侧表现为行首 U+FEFF，会让字段比较直接失配。

## 五、改造过程中暴露的四个真 bug（都不是编码问题）

1. **C3 判据变量被覆盖**（最隐蔽）：判据 python 里先算出
   `log = 任务日志 if 日志存在 else stdout`，紧接着又有一行 `log = open(restore_out)` 把它冲掉 ——
   于是 C3 永远只看见 CLI 的 2 行 stdout，报「任务日志仅到 STEP <无>」。
   之前三轮一直以为是通道截断，其实是判据自己写错了。已删并加注释留痕。
2. **`vm_read_file` 的重试被我删掉了**：重构时只留 `type`，结果同一文件连续两次调用会一次空一次满
   （run18 就有 2224B 的日志回读出 0 字节）。空结果必须重试，否则「通道抽风」被当成「文件为空」。
3. **`grep` 在 UTF-8 locale 下会整行跳过 GBK 字节流**：`format.out` 里明明有 `100 百分比`，
   `grep -c "100"` 返回 0。必须 `LC_ALL=C grep`。
4. **`fsutil volume diskfree` 的输出是本地化 GBK**：原脚本用中文 grep 取可用空间，一直取到空字符串，
   日志里长期显示 `T: （空）`。改成走 PowerShell `Get-Volume` 格式化数字（经 `-EncodedCommand`，中文安全）。

## 七、纪律固化（写给下一个会话）

1. **编码在入口统一设**：任何 `prlctl exec` 出来的 PowerShell 都带
   `$ProgressPreference='SilentlyContinue'; [Console]::OutputEncoding=[Text.Encoding]::UTF8;`。
   出现乱码先查这个前缀，不要立刻上 base64。
2. **参数里不放中文**。要中文就走 `-EncodedCommand` 或从文件读。
3. **文件回读用 `type`**，别转 base64。`type` 前不要加 `chcp`，`chcp` 解决不了进程 ANSI 问题。
4. **脚本不进命令行**：VM 直读 `\\Mac\Home`（fallback `\\psf\Home`），彻底免掉长度限制。
5. **grep 处理 GBK 字节流一律 `LC_ALL=C`**。
6. **通道偶发返回空是真的**：读文件/读状态必须有重试。

## 八、编码方案总表（2026-10-24 22:52 补测：用户追问「现在如何解决」）

### 8.1 PowerShell：四件套，缺一不可

PowerShell 5.1 在 prlctl 管道下的三个编码变量**默认值全是错的**（实测）：

```powershell
"OutputEncoding=" + $OutputEncoding.WebName              # → us-ascii
"[Console]::OutputEncoding=" + [Console]::OutputEncoding.WebName   # → gb2312
"[Console]::InputEncoding="  + [Console]::InputEncoding.WebName    # → gb2312
```

| 变量 | 默认 | 管什么 | 不设的后果 |
|---|---|---|---|
| `[Console]::OutputEncoding` | `gb2312` | PS 写 stdout 的编码 | 中文按 GBK 落字节，宿主看到乱码 —— **乱码的根源** |
| `[Console]::InputEncoding` | `gb2312` | 读 stdin / 管道输入 | 从管道读入的中文被按 GBK 解 |
| `$OutputEncoding` | `us-ascii` | 向**外部程序**喂管道数据 | 中文直接变 `?`（PS 5.1 的老坑） |
| `$ProgressPreference` | `Continue` | 是否序列化 progress 流 | 输出混进 `#< CLIXML ...`，不是编码问题但同样污染 |

统一成一句（脚本里就是 `PS_PRE`）：

```powershell
$ProgressPreference="SilentlyContinue";
[Console]::OutputEncoding=[Text.Encoding]::UTF8;
[Console]::InputEncoding=[Text.Encoding]::UTF8;
$OutputEncoding=[Text.Encoding]::UTF8;
```

### 8.2 CMD：三条实测把「调编码」的路全否了

| 尝试 | 结果 |
|---|---|
| 默认（936）`dir /b T:\`（目录名含中文） | `d6d0 cec4 c4bf c2bc b2e2 cad4`（GBK） |
| `chcp 65001 & dir /b T:\` | **逐字节相同**（`d6d0 cec4 …`，仍是 GBK） |
| `cmd /u /c "dir /b T:\"` | **输出直接丢失**（空），不可用 |

关键点：`chcp 65001` 其实生效了（`chcp` 回显 `Active code page: 65001`），但 `dir` 的输出没变。
原因是 prlctl 的 stdout 是**管道**，cmd 内建命令对管道按**系统 ANSI(936)** 落字节，`chcp` 只改控制台代码页、管不到这条路。

所以 CMD 侧的正解不是"调编码"，而是**不依赖它**：

- `cmd /c type <file>` —— 字节透传，不受任何代码页影响 → 这是回读文件的正确通道；
- 需要读数据（卷信息、目录列表、文件长度）→ 一律换 PowerShell 的 .NET 等价物（`Get-Volume` / `Get-ChildItem` / `(Get-Item).Length`）；
- 必须解析 cmd 外部程序的输出时（如 `diskpart`）→ 只认**跨语言稳定的 ASCII 特征**（进度数字 `100`），且 `grep` 必须 `LC_ALL=C`。

### 8.3 落盘与读盘

| 动作 | 错误写法 | 正确写法 |
|---|---|---|
| 写文本文件 | `Out-File -Encoding UTF8`（写 BOM） | `[IO.File]::WriteAllText($p,$s,(New-Object Text.UTF8Encoding $false))` |
| 读文本文件 | `Get-Content $p -Raw`（按 ANSI 解） | `Get-Content $p -Raw -Encoding UTF8` |
| 写 JSON | `ConvertTo-Json \| Set-Content -Encoding UTF8` | 同上 WriteAllText（无 BOM） |
| 宿主回读 | base64 编码往返 | `prlctl exec … cmd /d /c "type <file>"` |

### 8.4 一句话记住

> **PowerShell 的编码在入口一次设全（四件套）；CMD 的编码改不了，只用来搬字节和看 ASCII；中文数据一律走 PowerShell + 显式 UTF-8 文件 I/O。**

本节方案已并入 `tools/smoke/br-smoke.sh` 的 `PS_PRE` 与通道注释，补测后全链冒烟仍 **7/7 PASS**（run21）。
