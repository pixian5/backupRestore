按重要性排三个问题：

   哪些能在现有环境复验、哪些被环境卡住？
3. 台账里的旧结论，哪些可以继续引用、哪些必须作废？

**不在本轮范围**：物理机（另见 [`20261103-1510` 物理机清单](20261103-1510-ARM64物理机实机引导与部署验证Checklist-Gemini.md)，拿到机器后另订计划）；

## 四、判据与记录纪律

台账 §三「验收判据总纲」全部适用（判据优先级、两个卷级铁证、变异验证、六个判据坑）。本计划再钉六条：

1. **每个破坏性步骤都要有两条来自不同代码路径的证据**：一条是产品自陈（`status.json`、`--json` 字段、日志行），
   一条是外部物理事实（哨兵文件、卷序列号、独立算出的哈希、`bcdedit` 回读）。
2. **结果四态**：`PASS` / `FAIL` / `SKIP`（必须写明缺什么）/ `NA`（本轮不适用，写明原因）。
   「读不到」一律记 `SKIP instrument`，不记 `FAIL`——通道时好时坏是这台机器的常态。
3. **每项开始前记下部署件哈希的前 8 位。** 哈希一变，之前与受影响模块有关的实机结果作废。
4. **产品缺陷一旦确认，停止后面依赖它的测试项；修复后从 B1 重来**（二进制变了，旧证据不能续用）。
5. **哨兵必须在备份之后、还原之前放**（先放会被打进镜像，还原后「回来」，判据自相矛盾）；
   负向证据（哨兵消失、序列号变化）必须配一条正向证据（备份前放进系统盘的标记文件，还原后内容原样回来）。
6. **本机 `tr` 处理客体输出必须加 `LC_ALL=C`**；客体回显的结尾哨兵可能按双字节编码，
   按单字节去找会误判成「没跑完」——本文制定时就栽过这两下，白跑了六次。

记录方式：每个测试项在实测文档里占一行——编号、结果、部署件哈希前 8 位、证据路径、一句话说明。

## 六、分阶段执行步骤

### 6.1 阶段 A：准入（不破坏任何东西）

**A1 宿主空间达标**

- 操作：按 §三 选走法并清理。空间只看 `df -h /System/Volumes/Data`（`df /` 是只读快照卷，读数会误大一倍）。
- 判据：可用空间 ≥ 150G（走法甲）或 ≥ 50G（走法乙）。

**A2 开工前静态门禁**

- 操作：`cargo test --workspace`；`gh run list --limit 1`；`git status --short`；`git log -1 --format=%h`。
- 判据：单元测试 0 失败；HEAD 的持续集成为 success；工作区干净；把 HEAD 记进本轮记录。

**A3 环境基线与残留检查**

- 操作：`tools/vm/baseline.sh check`；`tools/vm/postflight.sh`。
- 判据：3 个注册表项与「启动分区上有引导存储」共 4 项为 pass；两个夹具项预期是 `fail remanual=1`（只有 G4 需要，本轮记下即可）；
  `POSTFLIGHT=clean`。

**A4 重启复验启动菜单**

11-05 改过启动配置（C: 加入显示顺序、删掉 F: 两条）之后，这台机器还没有完整重启过。

- 操作：`prlctl exec "Windows 11" cmd /d /c "shutdown /r /t 0"`；然后每 15 秒发一次 `prlctl exec "Windows 11" cmd /d /c "echo ALIVE"`，
  直到带回显（上限 6 分钟）。**不要用固定睡眠等待。**
- 判据：① 回到 Windows；② `bcdedit /enum {bootmgr}` 的 `default` / `displayorder` / `timeout` / `resumeobject` 与重启前逐字一致；
  ③ 没有 `bootsequence`；④ 图形界面自启进程 ≥ 1；⑤ `tools/task-audit.ps1` 仍是 4 个终态任务。
- 失败处置：进不了系统 → 停，转 §八 第 1 条。

**A5 映射共享盘**

- 操作：用户会话里先查 `net use`；没有 `X:` 就执行
  `prlctl exec "Windows 11" --current-user cmd /d /c "net use X: \\Mac\backupRestore"`。
- 判据：用户会话里 `dir /b X:\windows\build-windows.ps1` 回显文件名。
- 注意：Parallels 自动映射的是 `Y:` 和 `Z:`，不要拿它们当 `X:` 用；**以后每次重启后、每次要在虚拟机内编译之前都重查**。

**A6 采集基线**

- 操作：`bcdedit /export H:\brwork\bcd-baseline-<本轮标签>.bak`；记录 C、F、H 三个卷的序列号；
  把 `tools/bcd-audit.ps1` 与 `tools/task-audit.ps1` 的输出、一次 `df` 存进 `.test-artifacts/baseline-<本轮标签>/`。
- 判据：导出文件非空，且 `bcdedit /store <文件> /enum {bootmgr}` 能读出关键项（**不看字节数**）。

### 6.2 阶段 B：构建、部署、冒烟

**B1 虚拟机内构建并部署**

- 操作：先 `prlctl exec "Windows 11" cmd /d /c "taskkill /im BackupRestore.exe /f"`，再

  输出存进 `.test-artifacts/`。
- 判据：脚本末尾四个文件的 SHA-256 核对通过；产物目录里出现与 `VERSION` 对应的版本目录，
  其 `build-manifest.json` 的 `version` 与 `VERSION` 一致。
- 这是 11-04 之后第一次在虚拟机内构建，**最近两个版本的代码是第一次被真正编译成二进制**。

**B2 产物三项核对**

- 操作：`tools/vm/preflight.sh`；在运行目录里独立算一次哈希；在宿主解析产物的导入表。
- 判据：① `PREFLIGHT=pass`（部署不过期、含当前版本串）；② 运行目录里的哈希 == 构建清单里的 `binarySha256`；
  ③ 导入表只依赖系统动态库，不含任何 C 运行库（`VCRUNTIME` / `ucrtbase` / `api-ms-win-crt`）——漏了静态链接会进不了恢复环境。

**B3 图形界面快速判据**

**B4 全链冒烟**

### 6.3 阶段 C：核心链回归（本轮的重点）

**C1 系统盘备份——重启进恢复环境**

验证的是：准备 → 暂存恢复环境载荷 → 建启动条目 → 重启进入恢复环境 → 离线捕获 → 回写副档 → 清理 → 回到 Windows。

- 操作：
  1. 在 `C:\` 放一个标记文件 `BR-MARKER-<本轮标签>.txt`，内容已知（C2 的正向证据）。
  2. `H:\brwork\BackupRestore.exe prepare --operation backup --source-drive C --image-path H:\BRImages\c-<本轮标签>.wim --json`，
     记下返回的 `task_id`。程序会自行重启。
  3. 每 20 秒轮询 `H:\brwork\BackupRestore.exe status H:\brwork <task_id>` 直到终态（上限 25 分钟）；
     期间用 `prlctl capture` 抓一两帧恢复环境的进度窗留证。
- 判据（产品自陈 + 外部事实成对）：
  - `status.json` 为 `stage=success`、`progress=100`；
  - 镜像文件存在、大小 20G 以上；副档 `.index-1.metadata.json` 含 SHA-256；
  - 客体里 `certutil -hashfile` 独立算出的哈希与副档一致；
  - 恢复环境主日志（**在镜像旁的 `H:\BRImages\Recovery.log`，不在任务目录**）里 `CAPTURE_HEARTBEAT` 至少 1 行；
  - 回到 Windows；启动配置回到 A6 的基线：没有 `bootsequence`、任务建的两个启动对象已删、`bcd-audit` 没有新增孤儿条目；
  - `H:\BackupRestoreRE` 已清空；F: 与 H: 的序列号不变。
- 失败处置：任务停在非终态时**不要手动删任务目录**，先看 `status.json` 与 `Recovery.log` 尾部，
  用 `H:\brwork\BackupRestore.exe resume H:\brwork <task_id>` 收口后再分析。

**C2 系统盘还原——图形界面三道确认 → 恢复环境 → 回 Windows**

这是 98 个提交以来第一次在恢复环境里执行还原，也是拆分后的图形界面任务调度第一次真跑破坏性流程。

- 回滚准备：走法甲 → `tools/vm-snapshot.sh before-c-restore`，拿到 `VERIFIED_SNAPSHOT=` 才继续；
  走法乙 → 确认 §八 第 1 条的救援材料就绪（启动配置基线、救援光盘镜像）才继续。
- 操作：
  1. `tools/restore/sentinel.sh arm --drive C`（必须在 C1 之后）。
  2. 确认 `C:\br-test.json` 不存在（它会自动点「是」，验真实确认链必须跑纯净界面）；
     用 `restart-gui-h.ps1` 从 `H:\brwork` 起纯净图形界面。
  3. 切到「还原系统到 C 盘」页，填镜像路径，点创建任务；**三道确认框逐个先枚举再点「是」**
     （枚举用 `br-enum-dlg.ps1`，点击用 `tools/gui-check/ps/click.ps1` 的提权通道）；确认重启。
  4. 轮询任务终态（上限 30 分钟）。
- 判据：
  - `tools/restore/sentinel.sh verify --drive C` 给出 `VERDICT=PASS`（哨兵消失 + 序列号变化）；
  - 标记文件 `BR-MARKER-<本轮标签>.txt` 内容原样回来（证明写进去的是镜像内容）；
  - `status.json` 为 success/100；`Recovery.log` 里有 `RESTORE_SELFCHECK target=C` 且 `ntoskrnl=true`；
  - `{current}` 的设备与系统设备都是 `partition=C:`、`recoverysequence` 指向恢复环境加载器、`recoveryenabled Yes`；
  - `reagentc /info` 为已启用；没有 `bootsequence`；任务建的两个启动对象已删；
  - 应用错误事件零新增、WerFault 进程不超过 1 个；
  - 自启的图形界面是 H: 里的新版本；H: 序列号与部署件哈希不变；
  - `gui.log` 里三道确认各有一行 `GUI action:` 审计记录。
- 图形界面驱动受阻时：先证明读数侧（窗口在不在、点击有没有送达——比较点击前后可见控件编号集合）；
  确属仪器问题就改走命令行通道完成还原
  （`prepare --operation restore-existing --source-drive C --target-drive C --image-path <镜像> --wim-index 1 --allow-destructive --json`），
  图形界面那一项记 `SKIP instrument`。
- 通过后：**立刻删快照回收空间**（`prlctl snapshot-list "Windows 11"` 取编号 → `prlctl snapshot-delete "Windows 11" --id <编号>`），
  再看一次 `df`。

**C3 第二轮还原并按 B 回退**

- 操作：重新布哨兵，按 C2 的命令行通道再还原一次；在恢复环境里镜像应用进行到 20%–60% 时发 `tools/win-clicker/vmkey.sh b`。
- 判据：镜像应用**不被打断**、跑到 100%；日志里出现回退动作（关键行以实际日志为准，10-23 的实测记录见台账 §4.4）；
  任务按设计以「回退后续跑链校验失败」结束，且对话框说明这是预期后果；
  系统回到 Windows，哨兵消失、序列号变化；启动配置等于准备期基线。
- 说明：这一轮会破坏 C2 的「干净成功」现场，所以必须排在 C2 之后单独做。

**C4 系统还原到非 C 盘（在线）**

- 空间前提：宿主可用 ≥ 80G，否则跳过并记 `NA space`。
- 操作：`H:\brwork\BackupRestore.exe online --operation create-secondary --source-drive C --target-drive F --image-path H:\BRImages\c-<本轮标签>.wim --index 1 --image-name BR-<本轮标签> --format-target --json`（约 22 分钟）。
- 判据：`success=true`；F: 序列号变化；`F:\Windows\System32\ntoskrnl.exe` 存在；
  启动菜单新增加载器且排在显示顺序末尾；默认项仍是 `{current}`；`resumeobject` 不变；
  C: 与 H: 的序列号不变；全程没有重启（开机时间连续）。
- 之后：F: 留给阶段 G 用；不用时格式化 F:，停机后空间由 Parallels 自动收回。

**C5 数据还原到非 C 盘三段**

用一个带 100MB 已知哈希载荷的小数据镜像，在 F: 上做三段（台账 §4.3 上一次实测在 10-14，版本 2.3.x）：

| 段 | 操作 | 判据 |
| --- | --- | --- |
| 在线、不格式化 | 先放哨兵和一个镜像里没有的文件，再 `online --operation restore-existing --source-drive F --target-drive F --image-path <数据镜像> --index 1 --json` | 哨兵**存活**、多余文件**存活**、序列号**不变**、镜像内文件回来 |
| 在线、格式化 | 同上加 `--format-target` | 哨兵**消失**、序列号**变化**、100MB 载荷字节级一致 |
| 离线、不格式化 | 图形界面「还原数据到非 C 盘」把通道选成离线，弹窗里选「进入恢复环境」并确认。等价的命令行形式是 `prepare --operation restore-existing --source-drive F --target-drive F --image-path <数据镜像> --wim-index 1 --allow-destructive --json` | 走得通时：哨兵**存活**、恢复环境日志里没有格式化动作、任务 success/100 |

★ **第三段是读代码发现的「预判缺陷」，实测前先看这里**（以下是读源码和提交记录得出的，**没有实测**）：

- 图形界面这条路径（`native_gui/task_executor.rs`，10-14 写入）在用户确认「进入恢复环境」之后，
  下发的是 `prepare --operation restore-existing`，目标是数据卷；
- 准备期有一道 10-18 加入的安全闸（`prepare_validation.rs`，提交 `08ec341`）：
  **「还原到原卷」的目标必须是当前活动系统卷**，否则拒绝——目的是防止「源和目标都选成数据盘」一路通到格式化；
- 两者互相矛盾：按代码推断，用户选了「进入恢复环境」并确认之后，任务会被准备期一句
  `restore-existing target must be the active Windows volume` 拒掉；
- 这条路径上一次实机验证是 **10-14**，安全闸是 **10-18** 加的，**此后再没有人跑过**。

所以第三段有两种结果，处置不同：

| 结果 | 定性 | 处置 |
| --- | --- | --- |
| 走得通，三条判据满足 | 读错了代码，记 PASS | 无 |
| 确认之后被准备期拒绝 | **产品缺陷**：界面提供了一条走不通的路 | 记 FAIL。修法有两个方向，需要你裁定——要么让准备期接受「图形界面离线数据还原」这一种数据卷目标，要么界面对数据卷不再提供「进入恢复环境」选项 |
| 卡在中间（比如任务建了但没进恢复环境） | 产品缺陷 | 保留现场，记 FAIL |

## 八、回滚与救援手册

原则：**破坏性步骤之前，快照或启动配置基线导出必须已就绪，否则不开工**；
卡住时先截屏读屏再动手；恢复环境卡住时不要反复强制停机。

1. **重启后进不了 Windows**：先 `prlctl capture` 看屏幕。
   - 停在恢复环境的「需要处理」对话框 → 读任务目录的 `status.json` 与 `Recovery.log`，决定继续还是回退；
   - 引导坏了 → 关机 → 把虚拟机的光盘指向 `artifacts/BaseWinPE.iso` 并把光盘设为第一启动项 → 进预安装环境 →
     `bcdedit /import <A6 导出的基线>`，或 `Recovery.exe recover H:\brwork <task_id>` 手工续跑（10-19 实测可用）。
     预安装环境里没有 Parallels 工具，只能用 `vmkey.sh` 注入按键。
   - 有快照 → `prlctl snapshot-switch "Windows 11" --id <快照编号>` 一键回到快照。
2. **任务停在非终态**：`H:\brwork\BackupRestore.exe resume H:\brwork <task_id>` 续跑或清理；
   确认要放弃再用 `abandon-task H:\brwork <task_id>`（第一参数是工作区根，不是任务目录）。
3. **快照空间**：快照在时压缩无效；验证通过后**立刻删快照**；虚拟机停机时 Parallels 会自动回收空间，不需要手动压缩。
4. **共享盘丢失**：构建或编译报找不到 `X:\` 时按 A5 重新映射，不要去改脚本。
