# 这台虚拟机能不能开安全启动：实测结论是「开关能开，但开了起不来」

> 时间：2026-10-29 02:15　模型：deepseek-4.1-flash　版本：**不升版本**（纯虚拟机固件实验，零代码改动）
>
> 一句话：`prlctl set "Windows 11" --efi-secure-boot on` **执行成功**，但虚拟机重启后被固件判定「安全启动违规」**直接停机**；
> 根因是这台虚拟机的固件**写不进安全启动的白名单证书库**，白名单是空的，于是任何引导程序都不被信任。
> 现场已回退到「安全启动关、系统正常运行」，备份留了两份。

## 二 根因：白名单写不进去，所以白名单是空的

固件启动时的日志（`Windows 11.pvm/parallels.log`）把原因写得很清楚（以下为原文摘录，两次尝试分别对应
「直接开」与「重置后开」）：

```
第一次（02:07:58）
[SecureBoot] Initializing: PK=ok(clear) KEK=ok(clear) DB=ok(clear) DBX=ok(clear)
[SecureBoot] PK =e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855
[SecureBoot] KEK=e3b0c442…（同上，空）  DB=e3b0c442…  DBX=e3b0c442…
[SecureBoot] Create PK var
[SecureBoot] Create KEK var
[SecureBoot] Error allocating memory for new data to SetVariable KEK
[SecureBoot] Create db var
[SecureBoot] Error allocating memory for new data to SetVariable db
[SecureBoot] Create dbx var
[SecureBoot] Error allocating memory for new data to SetVariable dbx
02:07:59  Sending warning PRL_ERR_SECURE_BOOT_VIOLATION   → 虚拟机停机
```

`e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855` 是**空数据**的 SHA-256。
也就是说：**主密钥、密钥交换密钥、允许清单（db）、禁止清单（dbx）全都是空的**。
安全启动的规矩是「只放行清单里的签名」，清单空 = 谁都不放行 = 微软签名的 `bootmgfw.efi` 也被拒。
Parallels 检测到这个违规后不是报错弹窗，而是**直接把虚拟机停机**（所以看到的现象是「启动 45 秒后自己关了」）。

`reset` 那次有一点进展：

```
第二次（02:09:15）
[SecureBoot] Resetting: PK=ok KEK=lost DB=lost DBX=lost
[SecureBoot] PK =485aca0cb5f875572c905e6f19ec0a249cf438b005a3e27257ac4bd3f56777bd
              （主密钥这次有内容了，其余三项仍是空值）
[SecureBoot] Error allocating memory for new data to SetVariable KEK / db / dbx
02:09:16  Sending warning PRL_ERR_SECURE_BOOT_VIOLATION   → 虚拟机停机
```

说明**不是「没有证书」，而是「写证书那一步分配内存失败」**，这是固件/虚拟机管理程序侧的缺陷，
不是我们哪里配错了。

### 补充证据：这台虚拟机从来没有过白名单

虚拟机目录里留着四个历史固件存储副本（含 9-13 那次「只剩 UEFI Shell」事故前后的备份），
逐个按字节查微软证书名（`Microsoft Windows Production PCA 2011` 等），**五个文件全部没有**。
所以 9-13 之前配置里那个「安全启动=开」，很可能从来没真正生效过 —— 这也是当时引导菜单里只剩
「UEFI Shell」的一个合理解释。

### 开之前我以为能过，但那三条都不管用

| 我核过的事 | 结论 | 为什么没能救场 |
| --- | --- | --- |
| ESP 上三个引导文件签名 | 全部「有效 · 微软签名」 | 白名单空着，签名再正规也没人认 |
| 虚拟 TPM | 在（类型 crb） | TPM 管的是密钥与度量，不是放行名单 |
| 磁盘加密 | 四个卷全未加密 | 只影响「会不会要恢复密钥」 |

Parallels 官方文档确实写了 Apple 芯片上的 Windows 11 虚拟机支持安全启动，官方知识库也记录了
「安全启动阻止操作系统启动」这个故障（该问题号称在 26.3.3 / 20.4.2 修好，本机是 27.1.0，属于更新的版本，
症状却以另一种形态出现）。所以**不能把它当成「Parallels 不支持」一句话结论**，准确说法是：
**这台虚拟机当前的固件存储（NVRAM）无法建立安全启动白名单**。

## 四 三条后续路线（按代价从低到高）

1. **换一台一次性虚拟机验 PE**（推荐）：新建一台空虚拟机、开安全启动、挂我们的 PE 镜像启动。
   不碰这台工作机的固件存储；能直接回答「我们的 PE 在安全启动下会不会被挡」这个真问题。
   代价：要先用 ADK 工具把 PE 目录打成 ISO（十几分钟）。
   注意：如果新虚拟机也是白名单写不进去，那就等于证明**本版本 Parallels 无法提供安全启动环境**，
   这本身也是有效结论（真机验证时这条未知项要继续挂着）。
2. **重建这台虚拟机的固件存储**：关机 → 删掉 `NVRAM.dat` 与 `NVRAM.tnvs`（让 Parallels 重建，
   社区里对这个故障的常用解法）→ 开安全启动启动。风险是**引导项可能丢**（9-13 那次就是这么丢的，
   修复要新建虚拟机挂旧盘）；但已备份，拷回即可回到现在的状态。
3. **不再动**：把「本机无法构成安全启动环境」记档，真机验证时把这条当作未验项。

## 五 一句话给以后的自己

**「签名有效」≠「会被放行」**。安全启动是**白名单**机制：白名单为空时，微软签名的引导程序一样被拒。
判断能不能开，先看固件信任库（日志里 `PK/KEK/DB/DBX` 的哈希是不是 `e3b0c442…` 那个空值），
而不是先查文件签名。
