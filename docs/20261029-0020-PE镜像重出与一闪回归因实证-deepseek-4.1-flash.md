## 二、镜像重出：字节级证据

### 2.1 旧件（`pe-assets/pe-boot.wim`，2026-09-13 12:19，367,395,379 B）

从仓库旧件直接提取壳（宿主侧 `wimlib-imagex`，不是 VM 里的副本）：

```
$ wimlib-imagex extract pe-boot.old-20260913-badshell.wim 1 /Windows/System32/winpeshl.ini --dest-dir=...
Extracting file data: 89 bytes of 89 bytes (100%) done
```

内容（**LF，89 B，双入口**）：

```
[LaunchApps]
%SYSTEMROOT%\System32\RecoveryLauncher.cmd
%SYSTEMROOT%\System32\recenv.exe
```

同镜像 `System32` 清单里：`Recovery.exe` **在**、`RecoveryLauncher.cmd` **在**、`recenv.exe` **完全不存在**。

### 2.2 新件（`pe-assets/pe-boot.wim`，412,902,223 B）

```
$ wimlib-imagex extract pe-boot.wim 1 /Windows/System32/winpeshl.ini --dest-dir=...
Extracting file data: 61 bytes of 61 bytes (100%) done
```

内容（**61 B，单入口，与 `poc/build-backuprestore-pe.ps1:87-91` 的 `$expectedPeShell` 逐字相同**）：

```
[LaunchApps]
%SYSTEMROOT%\System32\Recovery.exe,--pe-desktop
```

`System32` 清单：只有 `Recovery.exe`，`RecoveryLauncher.cmd` / `recenv.exe` **都为 0** —— 说明新镜像干净，没有旧 POC 启动器残留。

| 项 | 旧件 | 新件 |
| --- | --- | --- |
| 大小 | 367,395,379 B | **412,902,223 B** |
| SHA-256 | `d5f1515acc2a5bf5d244048b9b9b1975f88433c18b4e13c15f3177393c3d17cc` | **`c0bd17eaa23c7ddfaac9d75f4294b41da786952543fb33f0211e8ea91d476d27`** |
| 壳大小 | 89 B（双入口，LF） | **61 B**（单入口） |
| `RecoveryLauncher.cmd` | 在（750 B 旧 POC） | **不在** |
| `recenv.exe` | **不在** | 不在 |

旧件**改名留档**为 `pe-assets/pe-boot.old-20260913-badshell.wim`：它是「壳能启动第一个入口、但整条链必失败」的**真实负样本**，将来给 §「输入 WIM 壳契约校验」做变异验收（判据必须能把它判红）正好用得上。

### 2.3 ★ 回写踩到的「假成功」（值得单独记）

第一次回写用的是覆盖式 `copy`，**退出码 0、`&& echo COPY_OK` 也打印了 OK**，但宿主侧文件仍是 367,395,379 B / 09-13。单独跑一次看原始输出才露真容：

```
prlctl exec "Windows 11" cmd /d /c 'copy /y C:\BackupRestorePE\BackupRestorePE.wim \\Mac\backupRestore\pe-assets\pe-boot.wim'
→ 拒绝访问。
  已复制         0 个文件。
```

（GBK 乱码，要 `cat -v` 才能看清。）根因：宿主侧 `pe-assets/pe-boot.wim` 与 `pe-boot.sdi` 都是 `-r-xr-xr-x`（**无 `w` 位**，09-13 留下的），SMB 上不可覆盖。

**解法**（已写进 `经验/02 §4`）：拷成**新文件名** → 宿主侧 `mv` 顶替 → `chmod u+w` 掉继承的只读位。判据只认**大小 + SHA-256**，不认退出码。这条坑与「空输出分不清真没有与没跑」是同一族：**退出码不是判据，副作用才是**。

## 三、重测闭环（#143）：一闪回 vs 稳定驻留

### 3.1 旧镜像的失败现场（`C:\pe-old-evidence`，抢救留存）

`winpeshl.log` 共 **9 轮**，每轮都以 `recenv.exe` 失败收尾：

```
2026-10-28 21:54:35.426, Info      Windows PE Shell beginning execution
2026-10-28 21:54:35.432, Info      Winpeshl.ini detected.
2026-10-28 21:54:35.432, Info      [LaunchApps]: Launching [%SYSTEMROOT%\System32\RecoveryLauncher.cmd]
2026-10-28 21:54:35.432, Info      Succeeded launching application (null) [command line: X:\Windows\System32\RecoveryLauncher.cmd]
2026-10-28 21:54:35.467, Info      [LaunchApps]: Launching [%SYSTEMROOT%\System32\recenv.exe]
2026-10-28 21:54:35.467, Warning   Failed to launch application (null) [command line: X:\Windows\System32\recenv.exe] [0x80070002]
```

9 轮起始时刻：`21:54:35 / 21:58:09 / 22:00:06 / 22:00:25 / 22:00:45 / 22:01:04 / 22:01:24 / 22:01:43 / 22:05:13`，**相邻间隔 ≈19 s**。

`Recovery-launcher-early.log`（旧 POC 启动器自己写的）：

```
RecoveryLauncher.cmd entered
RecoveryTask.env missing
```

**机制链**（完整闭合）：

1. 第一个入口 `RecoveryLauncher.cmd` **真的能启动**（log 记 `Succeeded launching`），但要读 `RecoveryTask.env`，缺则 `exit /b 87` → **立刻退出**；
2. 第二个入口 `recenv.exe` 在镜像里**不存在** → `0x80070002`；
3. `[LaunchApps]` 列表跑完、无前台进程 → WinPE 自己重启 → 回到 Windows（用户看到的「黑一下又回来」）→ 循环（19 s 一轮，正是「重启 + 重新加载 PE」的时间）。

### 3.2 新镜像的通过现场

安装（9 条 `bcdedit` 全部 `-> 0`），新 BCD 项 `{831787dd-d2e1-11f1-89db-f371a71018a0}`；装后核对目标卷 `T:\…\winpeshl.ini` = **61 B 正确件**、`Recovery.exe` 在、旧 POC 残留 `OLD=NO`。

`bcdedit /set {bootmgr} default {831787dd…}` → `prlctl restart` → 45 s 截图即 **「BackupRestore 恢复桌面 v2.6.74」**，底栏 `BackupRestore v2.6.74 | WinPE`。

**稳定性**：00:04:36 / 00:05:56 / 00:08:10 / 00:08:33 四张截图桌面全程未变 —— **4 分半无自重启**（旧件此时已跳 9 次）。

新 `winpeshl.log` **只有一轮**：

```
2026-10-29 00:04:05.655, Info      Windows PE Shell beginning execution
2026-10-29 00:04:05.655, Info      Winpeshl.ini detected.
2026-10-29 00:04:05.655, Info      [LaunchApps]: Launching [%SYSTEMROOT%\System32\Recovery.exe] with argument(s) [--pe-desktop]
2026-10-29 00:04:05.655, Info      Succeeded launching application (null) [command line: X:\Windows\System32\Recovery.exe --pe-desktop]
```

**判 PE 起没起，看条数，不看画面**（已入 `经验/04` 与 `经验/10`）：一条 = 驻留成功；多条 + ≈19 s 间隔 = 死循环。

## 四、顺带查出的产品侧真缺陷：`default` 被写成悬空 GUID

「返回 Windows」之后：

```
bcdedit /enum {bootmgr} /v   →  default  {a8bafbae-af1a-11f1-a77c-9813bbfbbd66}
```

而真实 Windows 项是 `{a6273652-d15f-11f1-aa4b-ff70ff0b7794}`。

**判「不存在」不能用 `bcdedit /enum {guid}`**（本机返回空，但 `bcdedit` 对不存在对象也可能给「本地化空文案 + 退出码 0」，这是老坑）。改用全文搜：

```
bcdedit /enum all > all.txt ; grep -n "a8bafbae" all.txt
→ 只有第 23 行的 default 那一处，全文没有任何对象以它为 identifier
```

**悬空成立**。机器还能进 Windows，靠的是 bootmgr 回落到 `displayorder` 第一项 —— **是运气，不是设计**。

**真因**：`exit_pe_to_windows`（`native_gui.rs:7967`）从 ESP 读 `S:\pe-exit-guid.txt` 当目标 GUID，而这个文件**是测试/部署时一次性写下的，之后没有任何机制刷新它**。本机那份写于 **2026-09-26 09:21**（`.test-artifacts/v173-20260926/prepare-gui-re.ps1:86` 的产物），早已过期。

**现场已修**：

- `bcdedit /set {bootmgr} default {a6273652-…}`；
- 用真实 GUID 重写 `S:\pe-exit-guid.txt`（复核 `GUID_FILE={a6273652-…}`）；
- 复核 `default {current}`、`displayorder` 三条。

**这是产品缺陷，不只是现场问题**（`经验/03 §6` 已落档）：根因是「信任一个永不校验的外部标记文件」，与「注入件哈希陈旧」是同一类病。**是否改成「从 BCD 现查当前 Windows 项」尚未拍板。**

## 五、`windows_prepare.rs:1228` 死代码 → 断言（#144）

上一轮已证：`ensure_workspace_capacity`（`:1094`）在租约点**之前**就硬要求恢复卷有盘符，所以走到 `:1227` 时 `lease_recovery` 必然是「复用既有盘符」的空租约，`hold_for_process()` 恒空转。

按用户裁决改成断言，而不是删代码：

```rust
pub(crate) fn owns_no_letter(&self) -> bool {
    self.letter.is_none()
}
...
debug_assert!(
    lease_recovery.owns_no_letter(),
    "recovery lease unexpectedly owns {recovery_letter}: the recovery volume lost its \
     drive letter between the workspace capacity check and the lease point"
);
lease_recovery.hold_for_process();
```

★ **当场踩到的坑**：给访问器加 `#[cfg(debug_assertions)]` 会 `E0599 method not found` —— `debug_assert!` 展开成 `if cfg!(debug_assertions) { assert!(…) }`，**条件表达式在 release 下照样要过类型检查**。已写进代码注释防复发。

`cargo check --release --target aarch64-pc-windows-msvc -p backuprestore-cli` → **Finished，无警告**。

注意边界：本轮**只加断言、不改行为**。`20261028-2315 §4.4` 明确写着「**不要在没观测到之前改 1228**」，那条观测闭环（100–250 ms 采样器 + `identity_from_diskpart` 前后日志）**仍未做**。
