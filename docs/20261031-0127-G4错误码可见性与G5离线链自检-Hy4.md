## 二、四个测量陷阱（每个都曾直接产出过错误结论）

### ★★★ 陷阱 1：跨进程 `GetWindowTextW` 读到的是"控件出生时的文本"

**现象**：点刷新后日志明明白白写着 `lines=8 code=BR-PE-039`，但读状态框（EDIT，id 1300）  
永远返回 31 个字符——正好等于它创建时的中文占位提示语长度。连续三轮都判成  
"界面藏了错误码"，差点去改产品代码。

**根因**：`GetWindowTextW` 读**别的进程**的窗口时，取的是窗口管理器缓存的那份文本，  
这份缓存只有 `DefWindowProc` 处理 `WM_SETTEXT` 时才会更新。  
**EDIT 控件自己处理 `WM_SETTEXT`、不会去走 `DefWindowProc`**，于是缓存永远是创建时的值。

**修法**：显式发 `WM_GETTEXT`（配合 `WM_GETTEXTLENGTH` 取长度 + `SendMessageTimeout` 防卡死），  
判据里的 `GetTextLive()`。`STATUS_CACHED_len=31` 那行被**故意保留**在输出里，  
用来持续暴露这个陷阱——下次有人图省事改回 `GetWindowTextW`，两个数字立刻打架。

**影响面排查**：`dlg-fit.ps1` 也读文本，但它只量 `Static` 和 `Button`  
（这两类的缓存会被 `DefWindowProc` 更新，实测读到的就是切语言后的英文），**不受影响**。  
规则：**要读 EDIT 类控件，必须发 `WM_GETTEXT`**。

### ★★ 陷阱 2：点「刷新任务状态」会弹出手工模态窗口，把主窗口禁掉

源码 `native_gui.rs:8404`：`ID_REFRESH_TASK => { refresh_task_status(state); show_task_admin(...); }`  
——点一下这个按钮，**先刷新状态框，再立刻打开「任务与证据」窗口**。  
那个窗口是手工模态的：`EnableWindow(main, 0)` + 自己的 `PeekMessage` 循环，  
关掉前主窗口一直是**禁用**状态（实测 `MAIN_ENABLED=False`）。

后果：第一次点击成功（日志有记录），之后**每一次点击都石沉大海**。  
我一度以为是"程序卡了"，其实是自己把它点进了模态。

**修法**：判据开头先把遗留的模态窗口全部 `WM_CLOSE`，点完再读，读完再关，  
并且把 `MAIN_ENABLED=` 打进输出——**主窗口如果是 False，后面所有判据都不可信**。

### ★★ 陷阱 3：`SendMessage(BM_CLICK)` 会长时间阻塞 → 改用 `PostMessage` + 轮询日志

程序主线程一旦在嵌套模态循环里，`SendMessage` 就一直不返回；实测卡满 40 秒后  
判据脚本被外层超时砍掉，输出停在 `BTN_RECT=...` 就没了——**看起来像"程序没反应"，  
其实是判据自己挂了**。改成 `PostMessage` 投递 + 轮询日志文件里新增的记录，  
程序忙只是**延后**结论，不会**销毁**结论（`REFRESH_TRIGGERED=1`）。

顺带一条：判断"刷新到底发生没有"不能只看日志最后一行——日志是跨进程追加的，  
最后一行可能是几分钟前的。**必须比对点击前后的条数**（`REFRESH_RECORDS_BEFORE/AFTER`），  
新增了才算这次真的触发了。

### ★ 陷阱 4：`runas.ps1` 用固定输出文件名 → 上一轮卡住的进程锁着文件，下一轮读到旧内容

上一轮的提权进程卡住没退，重定向句柄没释放，`Remove-Item` 静默失败，  
于是新的一轮读到**上一轮的旧输出**，还当成新结果报出来。  
改成每次带时间戳的唯一文件名。

### 两个次要坑（也记一下，都会浪费半小时）

- **屏幕尺寸要在 DPI-aware 状态下量**：未提权的 `Screen.PrimaryScreen.Bounds` 报 1175×969，  
  真实是 **2350×1938**（正好 2 倍）。我据此误判"按钮在屏幕外点不到"，写了错误注释又改回来。
- **PowerShell 里 `Rd` 是 `Remove-Item` 的别名**：自定义函数 `function Rd($h)` 会被别名顶掉，  
  调用时实际在跑删除命令，报错信息指向 `Remove-Item` 让人一头雾水。

## 三、G5：离线（恢复环境 / PE）链路的自检清单

读代码核对的结果——**离线链路是有自检的，而且比预想的严**：

### 捕获侧（`crates/backuprestore-cli/src/main.rs`）

| 位置                   | 自检内容                                                | 失败行为                                                       |
| -------------------- | --------------------------------------------------- | ---------------------------------------------------------- |
| `4984 wim_indexes()` | `dism /English /Get-WimInfo` → 解析索引；**空索引或含 0 即报错** | `DISM returned invalid WIM indexes`                        |
| `3939` 首次捕获后         | 索引必须**恰好等于 `[1]`**                                  | `first backup capture did not produce WIM index 1`         |
| `3904` 追加捕获后         | 索引数必须**恰好 +1**                                      | 删掉候选文件 + `WIM append did not create exactly one new index` |
| `4046` 保留策略裁剪后       | 每删一个就**回读索引列表**比对 `1..remaining`                    | `WIM retention index read-back mismatch`                   |
| 捕获前                  | 先算 `previous_hash`（sha256）与旧索引，再捕获                  | —                                                          |

另外 `capture_heartbeat::Heartbeat` 在"DISM 静默期"持续往日志写心跳——  
**"还在扫盘"和"真的卡死"在日志里可区分**（只观测，不干预）。

### 还原侧（`crates/backuprestore-cli/src/pe_operation.rs:512-565`）

1. 打开镜像时 `share_mode(1)`（拒绝写入/删除），**句柄持有到任务结束**——  
   防止"预检通过后镜像被替换"。
2. 计算镜像 **sha256**。
3. `dism /Get-WimInfo /Index:N` 读展开后大小，读不到 → `ImageExpandedSizeUnknown`。
4. 读该索引的 **sidecar 元数据**，若 `wim_index` 或 **`image_sha256`** 与实测不符 → `SidecarMismatch`。

> ★ 这条订正了一条旧印象：项目记忆里写着"镜像哈希**不强制校验**（仅比大小）"。  
> 准确说法是：**还原前的预检是会校验 sha256 的**（`pe_operation.rs:558`），  
> 记忆里那条指的是别处（备份完成后的元数据记录环节）。两件事别混。
