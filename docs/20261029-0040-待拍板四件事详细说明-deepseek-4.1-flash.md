## 第一件：要不要在「安装 PE」之前，先检查你给的那个镜像文件配得对不对

### 现在是什么情况（先把机制讲清）

「安装 PE」这件事，产品干的活是：把你指定的一个 `.wim` 镜像文件**原样铺到**硬盘上某个分区或内存盘里，
然后再在系统启动菜单里加一条指向它的启动项。**产品一个字节都不改这个镜像里的内容**，它就是个搬运工。

那 PE 启动起来以后，为什么能自动弹出「BackupRestore 恢复桌面」而不是停在一个黑命令行窗口？
靠的是镜像里自带的一个很小的配置文件，叫 `winpeshl.ini`，位置在镜像的 `Windows\System32\` 目录下。
它的作用是告诉 Windows 的 PE 启动器：「启动完成后，请你运行下面这一个程序」。

产品期望这个文件只有两行：

```
[LaunchApps]
%SYSTEMROOT%\System32\Recovery.exe,--pe-desktop
```

意思是「运行 Recovery.exe，并带上 `--pe-desktop` 这个参数」——`Recovery.exe` 就是我们自己的程序，
带上这个参数它就知道「以 PE 桌面模式启动」（画那 7 张卡片）。

**如果这个文件里写的是别的东西**，那就出事了。今天实测到的真实情况是：仓库里旧的那个镜像文件，
这两行写成了：

```
[LaunchApps]
%SYSTEMROOT%\System32\RecoveryLauncher.cmd
%SYSTEMROOT%\System32\recenv.exe
```

- 第一行是一个旧版测试用的批处理脚本，它确实能被启动起来（日志里明确记了「启动成功」），
  但它需要读一个叫 `RecoveryTask.env` 的文件才能继续，那个文件在没有任务上下文时根本不存在，
  于是它立刻以错误码 87 退出；
- 第二行的 `recenv.exe`，**这个镜像里压根没有这个文件**（我把镜像里 4384 个文件列了一遍，确认不存在），
  于是启动失败，日志记 `0x80070002`（找不到文件）；
- 两行都跑完、都退出了，PE 里就没有任何窗口程序在前台了。Windows 的 PE 启动器这时候会认为
  「活干完了」，于是**自己重启**。

重启就回到 Windows 桌面。用户看到的就是：**选了 PE，屏幕黑一下，又回到 Windows**。
而且这个过程会自动循环——因为下次再进 PE 还是同样的结局。日志实测：**19 秒一轮，连跳 9 次**。

**这不是产品装错了。产品是搬运工，你给它一个配错的文件，它原样铺进去，装完必然是坏的。**
上一轮我已经用正确的模板重新生成了镜像（文件大小 412,902,223 字节），装到同一个分区，重启后
稳定停在恢复桌面，4 分半钟四张截图没有任何变化，日志里只有一条「启动成功」、没有循环。

### 不改会怎样

**任何人（包括以后的我）拿一份旧的、配错的镜像去装 PE，都会重演「黑一下又回 Windows、19 秒一轮」，
而且看不出为什么。** 更糟的是，这种失败**看起来像产品坏了**——上一轮我自己就差点这么判。
排查要花掉整轮时间：要进 PE 分区读 `T:\Windows\System32\winpeshl.log`，数里面有几条记录、
看相邻记录的时间间隔是不是约 19 秒，还要从镜像里把那个配置文件抠出来比对字节数
（对的 61 字节，坏的是 89 字节或别的）。

也就是说：**这道检查机器一秒钟能做，现在却要人花几个小时去追。**

### 三个选项

**选项甲：加这道检查（我推荐）**
装之前，先把镜像里那个 `winpeshl.ini` 抠出来看三件事：
1. 这个文件存在吗？（连文件都没有的裸镜像，装完会停在一个黑命令行窗口）
2. 内容是不是**逐字等于**产品期望的那两行？（注意必须是「逐字等于」，不能是「里面提到 Recovery.exe 就行」——
   宽松判断在别的坏法上会漏，见下面「为什么要这么严」）
3. 它指向的 `Recovery.exe` 在这份镜像里真的存在吗？（防止「配置写对了但程序没打进去」的半成品镜像）

三条有任何一条不过，就**在动硬盘之前**拒绝安装，弹一个能把话说明白的提示，并写一条日志。

- 代价：大约 60–100 行代码；属于行为变更（新增一条「拒绝安装」的路径），按项目规矩版本号 +0.0.1；
  需要配三个测试样本（正确的、今天这个坏的、连配置文件都没有的）。
- 好处：坏镜像装不上，错误在**开始装之前**就暴露，不用等重启完再回头查几个小时。

**选项乙：不加检查，维持现状**
谁给的镜像坏了谁自己承担，坏了再按上一轮那份证据文档去查。
- 代价：零代码。但每次踩到这个坑都要重复一遍几小时的排查。
- 适合：你认为镜像来源可控（就这几台机器、就这个脚本生成），不值得为它加代码。

**选项丙：只提醒，不拦**
检查照做，但发现不对时只弹一个警告框，你点「继续」它还是照装。
- 代价：和甲差不多（代码量一样），但拦不住误操作——警告框被人点掉过太多次了。
- 适合：你既想有提示，又不想让程序替你决定。

### 为什么判据必须「逐字等于」而不是「里面有 Recovery.exe 就行」

今天这个坏件**恰好不含** `Recovery.exe` 这个字符串，所以「包含 `Recovery.exe`」这种偷懒写法
**碰巧**也能拦住它。但那是运气，不是判据对。真正的漏洞在别的偷懒写法上：

- 「至少有一个启动项能起来就行」——坏件**满足**（第一行真的起来了）；
- 「里面提到 Recovery 就行」——坏件**满足**（`RecoveryLauncher.cmd` 里有 Recovery 字样）；
- 「里有 `[LaunchApps]` 这个小标题就行」——谁都满足。

这几种写法都会放过今天这个坏件，而它装完就是 19 秒一轮自重启。
要表达的真正意思是「**PE 启动后唯一在前台跑的程序，必须是我们自己的那个**」，
只有「整份文件跟我期望的那一份一模一样」能表达这件事。

（顺带说明：另外那条「安装恢复环境」的老链路里早就是这么干的——它也是「不相等就拒」，
两边口径一致，不会出现「一个链路严、一个链路松」。）

### 还有一个需要你知道的副作用

期望值会变成**两个地方**要维护：一个是生成镜像的脚本，一个是产品代码里的这道检查。
将来如果改了启动方式（比如参数从 `--pe-desktop` 换成别的），**两处都要改**，
否则会出现「产品拒绝自己刚生成的新镜像」这种自锁。这一点必须在代码注释里写死。

## 第二件：要不要花一轮时间，去亲眼看「那个盘符到底是谁分配的、什么时候分配的」

### 现在是什么情况

产品在准备恢复环境（WinRE）的时候，需要往某个分区里写东西，所以要给那个分区**临时分配一个盘符**
（比如 `R:`）。项目里有一条安全规矩：**谁临时分配的盘符，谁负责收回去**，不能留在系统里。
留着的后果是：那个分区以后会莫名其妙多出一个盘符，用户重装系统或删分区之后，还会弹「找不到磁盘」的报错框，
而且用 `fsutil`、`GetLogicalDrives` 这类命令**看不见**它，只能去注册表里翻——排查极其痛苦（项目里专门记过这个坑）。

负责「收回」这段逻辑在 `crates/backuprestore-cli/src/windows_prepare.rs` 第 1228 行附近。
上一轮实测发现：在这台机器上，走到这行代码的时候，那个盘符**早就已经分配好了**——
因为在更早的步骤（第 1094 行那个「检查工作区空间够不够」的函数）里，就已经**硬性要求**
恢复环境那个分区必须有盘符，没盘符直接报错退出。

所以推论是：**「临时分配 → 用完了收回」这条路，实际上一辈子走不到**，那段收回代码在空转。

这次按你的裁决，我**没有删**它，而是加了一句「断言」（`debug_assert!`）：
意思是「我认定走到这里时不可能有临时盘符；如果哪天居然有了，请在调试版里立刻炸给我看」。
这行不影响正式版的行为，也不会让程序崩。

### 还没做的那件事

**我们从来没亲眼见过那个盘符是哪一步分配的。**

所有关于「分配」的推断，都是读代码读出来的（第 979 行的身份识别函数会调用 Windows 的磁盘分区命令去分配盘符）。
但读代码不等于看见。项目里有一份文档明确写着：**「在没有观测到之前，不要动这段代码」**。

要「看见」，需要两件事：
1. 在分配盘符的前后各写一条日志（记下：哪个盘符、分配前是什么状态、分配后是什么状态）；
2. 在准备恢复环境的那几十秒里，每 100–250 毫秒采样一次「当前系统里有哪些盘符」，
   把整条时间线录下来，看盘符是什么时候冒出来、什么时候消失的。

然后跑一次真实的恢复环境准备，看日志。

### 不改会怎样

这段代码会一直处于「看着像死代码、但没人敢删」的状态。不会立刻出事，但：
- 以后任何一次重构到这里，都要重新怀疑一遍、重新查一遍；
- 如果哪天在**别的机器、别的分区布局**下，这条路其实真的会走到，那么现在的处理是**不收回**，
  就会留下幽灵盘符（就是上面说的那种查不出来的报错框来源）。

### 三个选项

**选项甲：做观测，把事实钉死（我推荐）**
- 做什么：加临时日志 + 高频采样器，跑一次真实的恢复环境准备，把时间线录下来；看完结论后再决定这段代码去留，
  观测用的临时代码随后删掉。
- 代价：一轮实机测试（要真的跑一次准备恢复环境的流程，可能格式化某个分区，所以要挑测试盘）；
  少量临时观测代码。
- 得到：确定「谁分配的、什么时候分配的、有没有被收回」，这段代码从此有定论。

**选项乙：不做，就保持现在这句断言**
- 代价：零。断言已经能在「万一真走到」时报警（仅调试版）。
- 风险：永远不知道真相；正式版里那句话等于没有。

**选项丙：直接把那段「收回」代码删掉**
- 依据：它反正走不到。
- 风险：如果它其实走得到（只是我们这台机器走不到），删了就没有兜底，可能留下幽灵盘符。
  **在没有观测证据之前删，正是项目文档明令禁止的做法。**

## 第三件：PE 桌面那个「返回 Windows」按钮，现在会把启动默认项指到一个不存在的对象上

### 现在是什么情况

PE 桌面上有 7 张卡片，第 5 张是「返回 Windows」。点它，程序要做的事是：
告诉 Windows 的启动管理器「下次默认启动这一项」，然后重启。

问题是：它怎么知道「Windows 那一项」是哪个？它的做法是——去 EFI 系统分区上读一个文本文件
`S:\pe-exit-guid.txt`，里面存着一串编号（GUID，可以理解为「启动项的身分证号」），
然后把这个编号写进启动配置的「默认项」。

**这个文件是怎么来的？** 是当初部署/测试的时候，用脚本写了一次。**之后没有任何代码会更新它。**

本机这份文件写于 **2026-09-26 09:21**，里面的编号是 `{a8bafbae-…}`。
而系统里真实的 Windows 启动项，现在的编号是 `{a6273652-…}`。
两者的差别不重要，重要的是：**那个旧编号对应的启动项，早就不存在了。**

结果就是：点「返回 Windows」之后，「默认启动项」被设成了一个**指向空气**的值。

**机器为什么还能进 Windows？** 因为 Windows 的启动管理器有个保底行为：默认项找不到，
就退回启动菜单里的第一项。而这台机器的第一项恰好是 Windows。**所以它进去了——这是运气，不是设计。**
如果哪天第一项不是 Windows（比如多系统机器上第一项是另一个系统、或者第一项是 PE），
用户点完「返回 Windows」，重启后**进的是别的系统，甚至又回到 PE**。

我这次已经把现场修好了：把默认启动项改回真实的 Windows 项，并把那个文本文件的内容也改成真实编号。
但这只修了**这台机器现在这一份**，代码逻辑没改，下次部署到别的机器还会这样。

### 怎么判断「那个编号真的不存在」

顺手记一个坑：直接问「这个编号是哪一项」时，命令返回空。**返回空不能当「不存在」**——
本机的 `bcdedit` 对不存在的对象也可能给一段本地化的空文案加上「成功」的退出码。
可靠办法是把整份启动配置全部导出来，然后**全文搜这个编号**：
如果它只出现在「默认项」那一行、没有任何启动项以它作为自己的身分证号，才能判定「指向空气」。
我这次就是这么确认的（全文只有一处）。

### 不改会怎样

**下次在别的机器上装 PE、点「返回 Windows」，默认启动项又被指到空气。** 能不能进 Windows 全看那台机器的
启动菜单第一项是什么。多系统机器上，用户可能直接进错系统。

### 三个选项

**选项甲：改成「现查」，不再信赖那个文件（我推荐）**
点按钮的那一刻，直接问启动管理器「当前真正的 Windows 启动项是哪个」（靠「当前系统」这个特殊标记去查），
查到什么就设什么。这个文件以后可以完全不用。
- 代价：改一个函数（约 20–40 行）+ 一处测试；行为变更，版本号 +0.0.1。
- 好处：从根上不会再过期。文件写错、文件丢了、机器换了，都不影响。

**选项乙：保留读文件，但用之前先验一遍**
仍然读那个文件，但设默认项之前先确认「这个编号在启动配置里真的存在」。不存在就现查一个、或直接报错不设。
- 代价：比甲略多几行（两边都要写），但保留了「部署时想指定特定启动项」的灵活性。
- 适合：你确实有「一台机器上有多个 Windows，要指定回哪一个」的场景。

**选项丙：不改代码，靠部署时把文件写对**
- 代价：零代码。但这是一个**没有任何机制保证**的约定，本机就是这条约定失效的实例（文件停留在 09-26）。
- 风险：谁也不知道什么时候会再失效一次。

## 第四件：真实电脑上能不能进 PE，到现在没有任何证据

### 现在是什么情况

这一轮所有「PE 能起来」的结论，都来自一台 **Parallels 虚拟机**。

虚拟机有一个已知限制（上一轮也实测确认过）：产品在装 PE 时可以设置「**下一次启动临时切到 PE**」
（这个设置叫「一次性启动序列」）。这是 Windows 启动配置里的一个标准功能，真实电脑的固件一般会照做。
但 **Parallels 的固件不认这个设置**——上一轮的日志证明设置被成功写入了、命令也返回成功，
可重启后进的还是原来的 Windows，而且那个设置被自动清空了。所以那个「装完自动重启进 PE」的按钮在虚拟机上**无效**。

我这一轮之所以能让 PE 起来，用的是另一种办法：**直接把「默认启动项」改成 PE 那一项**，然后重启。
这个办法在真实电脑上也会生效，但它不是产品设计里那条路。

### 不改会怎样

「装完自动重启进 PE」这条产品主路径，**只在虚拟机上被证明「写进去了但固件不消费」**，
在真实电脑上**一次都没跑过**。可能出现的问题包括：
- 真实固件消费了那个设置，进 PE 正常（最理想）；
- 真实固件有安全启动（Secure Boot），拒绝启动我们这份没有签名的 PE（很可能）；
- 真实固件的其他行为（比如只认某些启动项格式）。

这不是代码能「拍板改」的事，是**要不要拿一台真机做验证**的事。

### 选项

**选项甲：先不测真机**
- 代价：零。
- 风险：上面那条产品主路径始终是「设计上应该有、实际没验过」。安全启动这一条尤其可能直接挡死。

**选项乙：找一台可以随便折腾的真机做一轮验证**
- 代价：需要一台机器（会被格式化一个分区、会改启动配置），要准备一个 U 盘或能进 PE 的手段做退路。
- 得到：真实固件能不能消费那个「一次性启动序列」、安全启动会不会挡、进 PE 后键鼠和磁盘是不是都正常。

**我的建议**：这件事不用现在决定，等前几件定了再说。但**安全启动**这一条值得提前查一下
（我们的 PE 有没有签名、目标机器的安全启动是不是开着）——如果确定会被挡，那么真机验证的前提要先解决。
