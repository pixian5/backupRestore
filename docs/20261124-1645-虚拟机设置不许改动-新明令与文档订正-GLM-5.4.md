## 一、规矩（2026-11-24 起）

针对本项目使用的测试虚拟机「Windows 11」：

1. **不执行任何 `prlctl set`**（改虚拟机设置的命令）。「临时关掉、用完再恢复」**也不做**。
2. **要用的时候**：关机状态就 `prlctl start`（开机）；已暂停或已休眠就 `prlctl resume`（恢复运行）。
3. **用完执行 `prlctl suspend`**（休眠），不留着空转。
4. **休眠前先跑 `tools/vm/user-idle.sh` 确认没人在用**，有人在用就不动。
   （2026-11-24 晚订正：原文写的是「读桌面会话的空闲时长（`quser`）」——实测 `quser` 对本地控制台会话恒显示 `none`，
   分不出「有人在用」和「没人碰过」，不能用。详见 `经验/02` §19。）
5. **任务因为「空闲自动暂停」被停住时**：只做恢复运行、接着跑，**不去关这个功能**。

**适用范围**：这台虚拟机的全部设置——空闲自动暂停、显示缩放、启动顺序、安全启动、设备增删等。
之前的文档把其中几项写成了「可以照做」的操作步骤，那是没有授权的，本文一并订正。

| 18:48–18:55 | 接手会话为读取一份未经过滤的恢复环境日志，唤醒虚拟机、原样拷出文件后再次休眠；期间没有执行任务，没有改设置 |

**两个容易误判的现象**：

1. **在「已暂停」的状态下休眠，下次唤醒后仍然是「已暂停」。** 17:10 那次休眠之前，虚拟机恰好被空闲自动暂停了；所以 18:48 执行 `prlctl resume`（从休眠恢复）之后，它回到的是保存时的样子——`paused`，命令通道仍然不通。**再执行一次 `prlctl resume` 才真正运行**。判据：唤醒后看 `prlctl list -a` 的状态是不是 `running`，不要只看命令的回显。
2. `suspend` / `resume` 这类状态操作会让 Parallels **重写一次配置文件**（`config.pvs` 的修改时间变成操作时刻），
但不会改任何设置项的值。所以「配置文件的修改时间变了」**不等于**「设置被改了」——要判断设置有没有变，
用 `prlctl list -i "Windows 11"` 读具体的值，不要看文件时间。

**问题的根源在项目自己的文档**：它们是写给「以后接手的 AI」照着做的，里面把「关掉空闲暂停」写成了标准步骤。
只要这几处不改，下一个接手的人照着做就会再关一次。

## 四、以后遇到「空闲自动暂停」怎么办

这台虚拟机开着「空闲自动暂停」（超时 1800 秒）：距最后一次键鼠注入满 30 分钟就会被 Parallels 暂停，
**通过 `prlctl exec` 执行的命令不算活动**。表现是所有命令排队不返回，看起来像通道挂死、助手卡死、脚本死循环。

| 步骤 | 做法 |
| --- | --- |
| 先看状态 | `prlctl list -a`，状态一栏显示 `paused` 就是它 |
| 恢复运行 | `prlctl resume "Windows 11"`（不是重启，不改设置；恢复后先探测通道 `echo ALIVE`） |
| 接着跑 | 原来的命令重发。**先确认上一步到底执行没有**：暂停可能发生在一条命令的中途 |
| 用完 | `prlctl suspend`；先跑 `tools/vm/user-idle.sh` 确认没人在用（不要用 `quser`，见规则 4 的订正） |

**不要做的**：`prlctl set "Windows 11" --pause-idle off`。

**写无人值守脚本时按这个前提设计**：每次调用前检查虚拟机状态，是暂停就先恢复；
轮询循环里也要检查，不要把「被暂停」误判成「任务卡住」。
