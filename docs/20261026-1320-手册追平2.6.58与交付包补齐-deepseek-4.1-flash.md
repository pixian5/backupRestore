# 手册追平 2.6.58 与交付包补齐（2026-10-26 13:20）

> 本轮起点是一句判断：「`dist/` 交付包未追上 2.6.58」。做完发现真正的问题不在打包，
> 而在**包里的手册描述的是 2.6.53 的行为**——差 5 个版本，其中两个版本（2.6.54/2.6.55）
> 加了用户可见的东西而手册一个字没写。打包只是最后一分钟的事。

## 1. 起点与顺序

上一轮收工时留下的待办是「交付包追上 2.6.58」，并留了一个未查明的疑点：`ls USER-GUIDE.md`
在仓库根目录报 No such file。本轮先查清再动手，顺序定为：

1. 定位手册真实路径、确认打包脚本是否已有（**不手搓第二套打包流程**）
2. **打包前先判断手册是否过期**（这一步是本轮重点，见 §3）
3. 补手册 → 提交 → 再打包（让包内 `README.txt` 的「对应提交」指向真正含新手册的提交）
4. 按判据验收 → 写文档 → 三处索引

## 3. 打包前的手册体检（本轮真正的问题）

先算版本差：`VERSION` = 2.6.58，手册版本头 = **v2.6.53**。逐版本看 2.6.53→2.6.58 改了什么：

| 版本 | 改动 | 用户可见？ | 手册写了吗 |
|---|---|---|---|
| 2.6.54 | 备份前空间预检（新错误码 `BR-IMG-008`）+ 终态自检行 `RESTORE_SELFCHECK` | **是** | 没写 |
| 2.6.55 | 捕获心跳观测（`CAPTURE_HEARTBEAT` / `CAPTURE_STALL` / `CAPTURE_SUMMARY`） | **是**（日志里多出几行，排障要用） | 没写 |
| 2.6.56 | 排除表补根级自引用联接点 | 否（内部） | — |
| 2.6.57 | unwrap 盘点、进度窗纯逻辑剥离 | 否 | — |
| 2.6.58 | 设置文件合并写不再误删他人注释（+ 四块 GUI 拆分） | 半是（设置文件被别的模块写坏过） | 有维护者注记，够用 |

也就是说：**如果当时直接打包，交付出去的包里会有一份「描述 2.6.53 行为」的手册**，
而它配的是 2.6.58 的 exe。用户按手册准备镜像卷，会在空间不足时撞上一个手册里查不到的
`BR-IMG-008`；备份卡在零字节时会以为卡死（2.6.55 就是为这个场景加的心跳行）。

顺手还查出一处旧错：中文 §1 写「它能做**四**件事」，下面表格一直是 **5** 行，英文版早就是
`five things`。这种数字与表格对不上的错误，读者会先怀疑表格。

## 4. 改了什么（中英同步五处）

| 位置 | 改动 |
|---|---|
| 版本头 | `v2.6.53` → `v2.6.58`；标题栏示例同步 |
| §1 | 「四件事」→「五件事」 |
| §3.4 备份 | 新增「空间预检」引用块：镜像卷可用 < 源已用÷20（至少 1 GiB）→ `BR-IMG-008` 拒绝、**一字节未写**；低于保守估计（`压缩` 70% / `不压缩` 105%）只记日志警告、**不拦截**，并写明理由 |
| §6 失败速查 | 新增 `BR-IMG-008` 一行 |
| §7.3（新节） | 「结构化判据行」：`RESTORE_SELFCHECK` / `CAPTURE_HEARTBEAT` / `CAPTURE_STALL` / `CAPTURE_SUMMARY` 四个纯 ASCII 前缀的用途，并强调 `CAPTURE_STALL ≠ 失败` |

写手册时按源码取值，不按记忆：

- `crates/backuprestore-core/src/lib.rs:993` `backup_space_floor()` = `(used / 20).max(1 GiB)`
- `estimate_backup_bytes()`：`none` → 105%、其余 → 70%，注释明确「只用于日志警告，永不用于拒绝」
- `crates/backuprestore-cli/src/windows_prepare.rs:3084` 硬闸抛 `ErrCode::BackupSpaceInsufficient`；
  低于估计值只 `append_log` 一条 `ol_backup_space_warn`
- `capture_heartbeat.rs`：`INTERVAL` 30 秒、`STALL_AFTER` 600 秒，模块头写明「只记录，不干预」

为什么把「为什么按估计值不拦」也写进用户手册：不写理由，用户看到「可用空间小于估计值」还继续
跑成功，会以为预检坏了。压缩比 13%~100% 这个区间是实测数字，写进去读者才能自己判断。

## 5. 打包与验收判据

产物 `dist/BackupRestore-2.6.58-windows-arm64.zip`：

| 判据 | 实测 |
|---|---|
| 包大小 | 3,204,034 字节（2.6.57 为 3,200,944） |
| 条目数 | 14（目录 + 13 文件） |
| 条目结构 vs 2.6.57 | `diff` 排序后**完全一致**（只换版本号） |
| `shasum -a 256 -c SHA256SUMS.txt` | **10/10 OK** |
| 包内 `VERSION` | `2.6.58` |
| 包内 exe SHA256 | `90729146739d93304b41033482e942bff1c8888e0530bed337a6508ea5865f51` |
| 与实机部署 `H:\brwork\BackupRestore.exe` | **同一个哈希**（`certutil -hashfile` 实测）⇒ 交付包就是正在实机跑的那份 |
| 与产物目录 `build-manifest.json` 的 `binarySha256` | 一致 |
| exe 内版本串 | `2.6.58`（`strings` 命中 2 次） |
| 包内手册与仓库同源 | `cmp` 两份均一致 |
| `README.txt` 对应提交 | `c836940`（含新手册的那次提交，不是上一轮的 `2f9424d`） |

**「包内 exe 哈希 == 实机部署 exe 哈希」是本轮的主判据**：它同时证明了「产物目录 → 包」和
「产物目录 → 部署」两条拷贝都没串，而不是只证明打包脚本自己算得对。

提交顺序上刻意先提交手册再打包：`pack-dist.sh` 会把 `git rev-parse --short HEAD` 写进
`README.txt`，如果先打包，包里会写着「对应提交 = 上一轮那个不含新手册的提交」——包内容与
自述不一致，事后按提交回查会拿到旧手册。

## 6. 可复用的钉子

1. **「交付包旧了」先查包里的文档旧不旧**，别只比版本号。包结构对、exe 哈希对，手册说的却是
   五个版本前的行为，这种包比「完全没包」更危险——它有权威感。
2. **手册版本头要跟着 VERSION 走**。它是读者判断「这文档对这个 exe 有效吗」的唯一线索，
   停在旧版本等于宣告文档不可信，即使内容 90% 仍然正确。
3. **新增用户可见行为时，同一提交里就要改手册**。本轮的三处缺口全部来自「代码提交时没想到手册」，
   而它们又都是**排障时才知道需要**的信息（错误码、日志判据行），事后补最容易被漏。
4. **数字与表格要对账**：「能做四件事」配 5 行表格，属于最低成本的信任损失。改手册时顺手数一遍。
5. **打包前先提交文档**，让包内 `README.txt` 的「对应提交」真的指向包里的那份文档。

## 8. 文档与实机的对账（写完手册后做的一次抽查）

手册 §7.3 承诺了四条判据行。写完不实机核对一遍，就等于把「代码里这么写的」当成了
「日志里真的这样」。实测（`H:\brwork` 与 `H:\BRImages` 全量 `findstr`）：

| 判据行 | 实机命中 | 结论 |
|---|---|---|
| `CAPTURE_HEARTBEAT` | **40 行** | 格式与手册一致：`CAPTURE_HEARTBEAT elapsed_secs=30 image_bytes=208 phase=pre_scan`（每 30 秒一行） |
| `CAPTURE_STALL` | **32 行** | 确实会在长时间无增长时写出；32 行说明那次捕获卡了很久（正是 F: 卷 I/O 阻塞那次） |
| `RESTORE_SELFCHECK` | **0 行** | 未观测过。2.6.54（07:36）之后没有跑过真实还原——其后的验收全是图形界面点击与探测任务 |
| `CAPTURE_SUMMARY` | **0 行** | 未观测过。它由 `Heartbeat::drop` 在主线程写，而 2.6.55 之后的捕获都是卡住后被 `taskkill` 强杀，Drop 没机会跑 |

后两条**不是没实现**：读代码确认 `append_restore_selfcheck`（`main.rs:2587`，成功路径
`complete_recovery_cleanup` 内调用）与 `impl Drop for Heartbeat`（写总账）都在。只是
「这一版还没被真实业务走到」。

★ **教训（新增一条）**：手册里写「日志会有这一行」时，要顺手 `findstr` 一次。文档描述的是
**代码意图**，实机验证的是**曾经发生过**；两者不同步时，读者按手册去 grep 会以为程序坏了。
本轮的写法是保留手册（它描述的是当前行为），但在本文档里如实记下「哪两条还没被走到」。
