- 产品逻辑基线：`9a283e4`；版本元数据提交：`83fe9a8`。本轮新增 RE（恢复环境）实测与文档，未修改产品执行逻辑。

## 一、与上一轮测试的区别

2.1.2 完成的是 PE（预安装环境）界面安全测试和 Windows 原生执行器测试，不能据此认定主 `prepare → recover-env` 链路通过。

本轮调用发布程序的正常 `prepare` 入口，由产品自行准备独立 WinRE 副本、注入同源 `Recovery.exe`、创建并武装临时 BCD（启动配置数据）条目、重启。进入 RE 后，产品执行实际 DISM（部署映像服务和管理）捕获/应用，清理自身启动对象后自动重启回 Windows。未手动替换捕获、格式化、应用或清理步骤。

测试由命令行触发，未覆盖正常 Windows 图形界面选择“进入 RE”的完整交互。

## 五、真实还原结果

备份后主动制造三个差异：修改 `restore-me.txt`、删除 `nested\random.bin`、新增 `must-disappear.txt`。保持原 `testdata` 不变，用其校验还原不会丢失已有测试数据。

```text
BackupRestore.exe prepare --operation restore-existing --source-drive T --target-drive T --image-path H:\BRRE-213-20261005\images\test.wim --wim-index 1 --verify-hash --allow-destructive
```

- 任务：`fbb78053-ada2-4aa6-8bfe-78ec125a99c1`，最终状态 `success`。
- 真实 RE 进度窗口截图显示 `diskpart.exe` 与还原阶段。
- 日志明确选择磁盘 0 分区 5，执行真实格式化，再执行 `/Apply-Image /Index:1 /ApplyDir:D:\`，两条命令均成功。
- NTFS 卷序列号从 `94B52928` 变为 `2E0FC364`，分区 GUID 不变，符合格式化后的稳定分区身份。
- 返回 Windows 后，6 个预期文件全部按相对路径、大小和 SHA-256 核验通过；被删除的文件恢复，被修改的文件恢复原内容，新哨兵消失。
- 原镜像摘要不变，临时载荷目录消失，临时启动条目清理且完整 BCD 文本与启用后的基线一致。
- 日志明确记录 `data-volume restore: target has no SYSTEM hive; skipping BCDBoot`。因此本轮**未执行系统引导修复，也未验证恢复后的 Windows 系统能够启动**。

## 六、测试环境回收与发现

测试开始时 WinRE 为 `Disabled`，`reagentc /info` 无恢复位置。当前准备流程依赖已注册位置，因此先在新快照下临时 `/enable`，位置为磁盘 0 分区 4 的 `Recovery\WindowsRE`。产品两次事务均只读此原恢复镜像，注入发生在独立副本。

恢复环境时发现：`reagentc /disable` 会删改恢复关联，并移走原恢复目录中的 WIM 与 `boot.sdi`。直接导入事前 BCD 导出可恢复配置，但本机实测会新增 6 个固件条目。新增 GUID 仅出现在导入后差异中，类型均为固件应用。再次建立快照后，仅删除这 6 个本次新增对象，并恢复事前保存的 `ReAgent.xml`；缺失的原恢复文件从事前副本补回，补回 SDI 前另建快照。最终完整 BCD 枚举、`reagentc /info` 与测试前文本逐字一致，原恢复镜像及 SDI（启动内存盘映像）摘要一致。

原 `C:\Recovery\WindowsRE\Winre.wim` SHA-256：

```text
1060a552be3b6f2f190e9e50f0ee5fe9b183f97ef62083f61b92b1a9b52b9dd5
```

脚手架经验：Windows 图形子系统程序由 PowerShell 直接调用并重定向文件时，本轮遇到进程仍执行但 `$LASTEXITCODE` 为空；首次备份包装脚本误报失败，实际产品已完成正常 RE 事务。最终判据采用持久任务、真实命令日志、镜像与还原文件回读。常规测试脚本改用 `System.Diagnostics.Process` 持有进程句柄、异步读取两路输出、等待退出并验证真实退出码；两组退出码均为 0。空退出码没有记为测试通过。
