## 一、补齐新载荷路径的验收覆盖

1. **系统镜像还原 + 引导修复（BCDBoot）**（优先级最高）：
   本轮用的是数据镜像还原到数据卷 T:，日志 `data-volume restore: target has no SYSTEM hive;
   skipping BCDBoot`，**引导修复这一步在新载荷路径下完全没跑过**。而「系统还原时修复引导」
   是产品核心链路。需用系统镜像在 C: 或第二系统分区做一次完整还原，核验 BCDBoot 执行、
   启动项修复与目标可启动性。

2. **两个未终结任务并存**（问题 9 的并发窗口）：
   准备任务 A 后不执行，再准备任务 B，核对 A 的载荷哈希不变、清理 B 不影响 A、
   第二次武装被 `allow_rearm` 拒绝。本机单测已覆盖清理隔离，实机未做。
3. **`acceptance:entry-fields:error` 失败补偿**（2.2.1 新增）：
   需 `BR_ACCEPTANCE_ROOT` 与 `BR_ACCEPTANCE_SNAPSHOT`，用
   `--ignored --exact boot_entry::fault_tests::missing_payload_conflict_and_cleanup_retry` 显式运行。
   核验建条目失败后残留簿记落盘、BCD 与镜像卷回到基线、`boot-entry.json` 未被污染。
4. **真实断电矩阵在新路径下重跑**：2.1.9 的 11 点取自旧的共用载荷路径。
   用 `acceptance:cleanup-matrix:hold` / `acceptance:boot-matrix:hold` 配合
   `run.py capture` → `cut` 执行。
5. **C: 系统卷与第二系统**在新载荷路径下的验收（本轮只用 T: 5GB 测试卷）。
6. **ESP 定位多候选场景**：多 ESP、ESP 无挂载点、隐藏恢复卷排在 ESP 前。

## 二、验收工具的两点改进建议

这两条本轮实际踩到，建议固化进工具而不是只写在文档里：

- **`run.py` 的 `--fault` 应先做白名单校验**。本轮传 `none` 直到客体 `prepare.err` 才报错，
  白白消耗一次快照与一轮重启。校验逻辑与 `windows_prepare.rs:436` 对齐即可。
- **持续型故障（`acceptance:*:error`）不应用于 `--boot` 用例**，或 `run.py` 应明确拒绝：
  WinRE 内没有 Parallels Tools，`prlctl exec` 不可用，无法写 `fault-released` 解除故障；
  `prlctl reset` 后一次性启动请求未被消费会再次进入 WinRE，只能靠 `snapshot-switch` 回退。
  `--boot` 用例应改用 `error-once`。

另：`tools/acceptance/` 里 `--run` 默认值仍是 `re219-reliability-20261009`、
`rootRelative` 仍硬编码 `BRRE-219-20261009`，建议随轮次参数化（`native.ps1` 已改过）。

## 三、仍然保留的既有边界

- BCDBoot 完成后断电目前支持进入系统并显式 `resume`；要完全自动需重新设计持久恢复入口，
  会改变当前仅用一次性启动请求的设计。
- 状态事务的三个内部文件边界由真实文件重放测试覆盖；要增加存储介质级证明需另做定点断电。
- 按用户要求不扩展平台（Windows 10、x64、实体设备均不在范围内）。
