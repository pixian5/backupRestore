# 手动 `recover` 通道 D1/D2/D3/D4 实机全通 + 两处代码页/大小写缺陷

## 1. 目的

在 PE 内**手动**跑 `BackupRestore.exe recover <workspace-root> <task-id>`（不依赖
`prepare` 武装的一次性 bootsequence），端到端验证 D1–D4 四个离线续跑修复：

- **D1**：`recover` 第一参是**工作区根**（内部拼 `tasks/<id>`）。
- **D2**：镜像卷按卷 GUID 重解析盘符（PE 里 `H:` 实测变 `E:`），不认记录盘符。
- **D3**：STEP 1 前自动解析/挂载 ESP（不要求调用方传 `--efi-root`）。
- **D4**：WinRE 在**独立恢复分区**（本机 disk0/partition6）时校验载荷齐备后按独立分区重接。

## 2. 结论（一句话）

**手动 `recover` 全链实机通过**：`DONE_EXIT=0`，任务 `success`，目标卷被真实重写
（序列号变化 + 哨兵法），WinRE 仍 Enabled @ partition6 且 recoverysequence 完好，
重启进 Windows 正常、无崩溃。

但通过前连栽两处缺陷，均已修复并补 macOS 可跑的单测：

| # | 缺陷 | 现场表现 | 根因 | 修复 |
|---|------|---------|------|------|
| A | 设备路径大小写 | run1 失败：`设备路径形态无法识别：\device\harddiskvolume6` | `field()` 把 BCD 值统一小写化，旧 `partition_of_device_path` 只认大写 `\Device\` 前缀 | `text_parsing::device_path_volume_name` 大小写无关；`verify_partition_token` 路由同步无关化 |
| B | 菜单名回读在非 CJK 代码页误判 | run2 失败：`引导菜单名称回读不一致` | PE 的 ANSI 代码页非 CJK，`bcdedit /enum` 把每个汉字回读成 `?`；BCD 内存的是正确 UTF-16，写入没失败 | `boot_menu::menu_name_matches` 容忍有损回读（见 §4） |

### run2 失败点的实机形态（`recovery.log` 原文）

```
[2026-10-19T18:45:55.638+00:00] 引导菜单名称写入：（新建） -> 本次还原的 Windows
...
[2026-10-19T18:45:55.812+00:00] capturing bcdedit.exe /store Z:\EFI\Microsoft\Boot\BCD /enum {4d51a1b6-...} /v
description             ????? Windows
[2026-10-19T18:45:55.851+00:00] Recovery failed: invalid task: 引导菜单名称回读不一致
```

「本次还原的 Windows」= 5 个汉字 + “ Windows”；回读 `????? Windows` = 每字一个 `?`。
**这是有损回读，不是写入失败**——BCD 存的是 UTF-16，菜单实机显示正确。

## 4. 缺陷 B 的修复设计（`boot_menu.rs`）

旧实现（`apply` 内）：

```rust
if shown != Some(entry.display_name.as_str()) {
    return Err(crate::err("引导菜单名称回读不一致"));
}
```

新实现：

```rust
if !menu_name_matches(shown, &entry.display_name) {
    return Err(crate::err("引导菜单名称回读不一致"));
}
```

`menu_name_matches` / `ascii_skeleton`（平台无关，可 macOS 单测）：

- `shown == expected` → 通过（在线中文主机 CP936 正常路径）。
- **纯 ASCII 名字仍严格字面比对**，不一致判失败——真实校验不削弱。
- 非 ASCII 名字且严格失败 → 退化「ASCII 骨架」比对：两边剔除占位 `?` 与非 ASCII，
  剩余 ASCII 相同即认定一致（代码页本就无法逐字校验汉字，只能确认 ASCII 骨架没写错，
  例如误写成别的系统名会被拒）。

三个单测：
`menu_name_matches_tolerates_non_cjk_readback_of_cjk_name`、
`menu_name_matches_stays_strict_for_ascii_names`、
`menu_name_matches_rejects_genuinely_different_names`。

### 一个未改的既有设计（说明清楚，避免误判为新 bug）

`windows_prepare.rs:1164`：`boot_menu_name` 只在 `Operation::CreateSecondary` 时落盘；
`RestoreExisting`（A 入口）存 `None`，recover 走 `boot_menu.rs:891` 的硬编码
`"本次还原的 Windows"`。因此 `--boot-menu-name` 对 A 入口**按设计不生效**，本轮未改。

## 6. PE 操作新增经验（本轮踩坑，勿再犯）

1. **「Press any key」必须按住 ~200ms 再松**：背靠背 `press/release`（无间隔）会被固件
   键盘轮询整段漏掉，直接回落 Windows。连发 30 次、每次 `press→200ms→release→200ms`
   可稳定进 PE。
2. **PE 启动后桌面持焦点、cmd 不持焦点**；但上面那种 Enter 连发会落进 cmd 造成多行空
   提示，此时 cmd 反而**已持焦点**，可直接键入命令（本轮两次都靠这个直接跑 `rr.bat`）。
   若焦点不在 cmd，先 `Alt+Tab`（scancode 56+15）。
3. **PE 内 `bcdedit` 输出的中文必乱码**：按 ANSI 代码页转窄字符，非 CJK 页（WinPE 常见
   437/1252）每个汉字变 `?`。**不要在 PE 里 `type` 中文日志**，要回 Windows 后 copy 到
   `\\Mac\backupRestore` 当 UTF-8 读。PE 内 **UNC 共享文件夹不通**（Parallels tools 未加载）。
4. `Get-WinEvent -FilterHashtable @{...; StartTime=...}` 在刚还原的系统上可能**极慢**
   （实测 >7 分钟不返回）→ 用 `-MaxEvents 20` 有界查询 + 客户端按时间过滤。
5. `prlctl restart` 在 PE 内会 `canceled`；一律 `prlctl stop` + `prlctl start` 两步走。
6. 真机取 PE 日志链路：PE 内把日志留在 `H:\brwork\tasks\<id>\` → 回 Windows（bootorder
   `hdd0 …`）→ `br-ps.sh` 里 `Copy-Item` 到 `\\Mac\backupRestore\_pe-logs` → 宿主 UTF-8 读。
