## 当前 GUI 选择故障

此前实机日志出现按钮点击记录 `choice=2`，但对话框结果返回 `0`，导致程序按取消处理。源码已修改为通过局部结果盒读取选择，不再在窗口销毁后访问 HWND；同时增加按钮选择、返回值、确认结果及 ShellExecute 返回码日志，并将 prepare 控制台设为显示。

源码现有版本在 1.8.11 落地并构建部署（2026-09-30 08:27）：

| 项 | 结果 |
|---|---|
| 根因 | `ask_system_drive_handler` 在 `DestroyWindow` **之后**仍用 `GetWindowLongPtrW(dialog, …)` 取结果盒 → 窗口已销毁，属未定义行为，实机稳定返回 0 → 用户选的 `choice=2` 被吞，程序按取消处理 |
| 修复 | 结果盒裸指针留在局部变量里，循环退出后直接解引用读取，不再经过窗口句柄 |
| 可观测性 | 新增按钮点击、choice 返回值、确认框结果、`ShellExecuteW` 返回码四行日志；选择结果也写 `logs/gui.log` |
| 控制台 | prepare 由 `SW_HIDE` 改 `SW_SHOWNORMAL` —— 用户「点了没反应」的另一半原因是隐藏运行，约 35 秒内桌面无任何反馈 |
| 文案 | 确认框不再写死「备份」，按 operation 区分备份/还原/新增第二系统，标题统一为「进入恢复环境」 |
| 本机验证 | `cargo test --workspace` 95 passed / 0 failed（cli 72 + core 23） |
| 构建部署 | 1,815,552 B，SHA-256 `7a2183b70161aa66f4a825b524abf4eca6504c19acbf490e2b14e430b7b423f2`；客体 `C:\Users\Public\backupRestore-package\{BackupRestore,Recovery}.exe` 与 `H:\brwork\BackupRestore.exe` 三处哈希均一致 |

仍标记为**代码已修、实机复验待完成**：`--test-hook` 直接设置 choice，会绕过选择对话框，不能当作按钮修复验收。下一次复验必须用真实按钮点击或等效消息注入，且需先建快照。
