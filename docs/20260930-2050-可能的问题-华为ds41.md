## 0. 结论摘要

- **防御性设计整体扎实**：卷 GUID 身份、载荷四件套哈希、原子写、失败不伪造成功、破坏性阶段顺序在核心路径保持良好；`cargo test` 全绿、依赖全锁定、无机密入库。
- **风险集中在四处**：
  1. **构建/交付链路分叉**（潜在阻断：Windows 入口动态 CRT）；
  2. **错误与异常分支的安全网失效**（BCD 回滚、格式化回读、损坏 sidecar、双写撕裂）；
  3. **视图层与文本解析的崩溃/本地化盲区**（字节切片 panic、中文 `mountvol`）；
  4. **Windows-only 代码的测试盲区与文档治理失控**。
- 未发现「每次必现且必然损坏数据」的问题；有两项在特定组合下可视为条件阻断（B1、H2-危险组合）。

严重度分布（约 40 项）：阻断 1、高 ~12、中 ~14、低/技术债 ~13。

## 1. 阻断级

### B1. Windows 构建入口产出「动态 CRT」包，用于 WinRE/PE 可能直接起不来
- **证据**：`windows/build-windows.ps1:134` 只跑 `build --release --locked`，**无** `-C target-feature=+crt-static`；`:152-156` 仍从 `System32/SysWOW64` 拷贝 `VCRUNTIME140.dll`/`VCRUNTIME140_1.dll` 进包。而 `build-win.sh:29-38` 明确用 `+crt-static`，注释记录精简版 Windows/tiny11/WinRE 缺这些 DLL 时报 `0xC0000135 / STATUS_DLL_NOT_FOUND`。`winre_payload.rs:18` 的 `OPTIONAL_RUNTIME_FILES` 仍在搬运 VC 运行库兜底。
- **触发**：用 `build-windows.ps1` 产物（含 x64/arm64 与 `build-manifest.json`）部署到 WinRE/PE。
- **影响**：进程无法加载，且「已拷贝 DLL」会把它掩盖成假成功。该问题早在 `docs/开发方案/20260926-2342-阶段1-F4-统一Windows与Mac静态CRT构建.md` 被识别（F4，状态=待实施）。
- **建议**：实施 F4——ps1 加 `+crt-static`、新增 `.cargo/config.toml` 硬约束、去掉 VC DLL 拷贝、新增 EXE 导入表审计（无 `VCRUNTIME*/api-ms-win-crt-*`）作为发布门槛。
- 说明：若实际只用 `build-win.sh` 交叉编译发布，则影响面收窄，但仍属「入口不一致」的隐患。**建议确认主发布入口**。

1. **同一纪律未在所有入口落地**。项目已确立三条纪律——「不信外部命令退出码」「写完必须回读」「损坏≠缺失」。CLI/WinRE 路径贯彻良好，但 GUI PE 安装（M9）、准备层（H-PREP-1/H-PREP-4）、CLI 格式化（H-CORE-2）、sidecar（H-CORE-3）存在破例。
2. **异常/回滚分支是重灾区**。主路径稳，问题多集中在失败路径：回滚缺 `/store`（H-CORE-1）、失败不清理（H-PREP-4）、回滚吞错（Opus5 P2-2）、双写撕裂（H-CORE-4）。
3. **Windows-only 不可测**。约 3900 行 Windows-only 代码（含未提交 1600 行）本机零编译零测试，是最大回归面；H-GUI-1/2/3 都属此类。
4. **文档/交付治理滞后于代码速度**。119 份文档、双索引、版本三源、无 CI，人工维护不可持续。
