# 阶段 3 故障记录：RE 未自动执行任务 + C: 启动损坏（已快照回滚恢复）

> 模型：GLM-5｜发生时间 2026-10-14 14:44–15:20｜**VM 已完全恢复**（快照回滚），c-full 镜像完好。

## 故障经过（时间线）

1. 14:44 GUI（H:\brwork 实例）C 入口·离线·目标 F:·菜单名「第二系统-1014」→ 破坏性确认「是」→ 提权 prepare 启动，任务 `dd44a55a` 建立（参数正确：create-secondary / source C / target F / c-full 索引 1）
2. 14:46–14:52 prepare 校验+部署载荷（31.6GB 暂存复制 H:）
3. 14:52 VM 重启（bootsequence 已设）——**但进入的是 WinRE 手动恢复菜单（键盘布局选择界面），任务恢复程序没有自动执行**
4. prlctl ACPI 停机 → 开机**再次进 RE 菜单**（bootsequence 未被消费，Parallels 固件对一次性启动的消费行为异常）
5. 经 prlctl send-key-event 键盘操作：回车→高级选项→命令提示符，手工执行 `bcdedit /deletevalue {bootmgr} bootsequence`（成功）+ `wpeutil reboot`
6. 重启后 **C: 启动损坏**：「自动修复无法修复你的电脑」（多次非正常重启的次生灾害）
7. **回滚快照** `stage3-c-offline-p1-1014`（14:38 拍）→ 一键恢复

## 恢复后状态（已验证）

- VM 正常进 Windows；BCD default=`{12e3701c-…}` 基线值、无 bootsequence
- **c-full-20261014.wim 31.6GB 完好**（14:31 生成 < 快照点 14:38）
- 任务 dd44a55a 随回滚消失；T: 序列号 30D1-A4CA（1b 结果）保留
- 宿主空闲 246Gi

## 根因分析（证据随回滚丢失，以下为推理）

**直接问题**：bootsequence 触发的重启进入了「系统 WinRE 恢复菜单」而非「任务定制 RE 载荷（自动拉起 Recovery.exe）」。

**嫌疑排序**：
1. **Parallels 快照层与一次性启动（bootsequence）交互异常**——0200/0212 文档的 RE 往返（备份/还原 T:）在**无快照**状态下完全正常（同一套 boot_entry/载荷机制）；本次是首次「有快照 + bootsequence」。空间纪律「改 BCD 不拍快照」正是此类坑的先验。
2. 载荷 winpeshl 自动执行链失效——与 0200/0212 成功记录矛盾，次嫌疑。
3. bootsequence 指向写错——prepare 代码未变且 0212 成功过，可能性低。

**次生灾害教训**：RE 卡住时的正确动作是「选择一个选项→关机」后宿主侧诊断，不要反复重启。

## 下一步（不重启的诊断路径）

1. CLI `prepare … --no-reboot` 重建任务，检查 ESP 新 boot entry 的 ramdisk 指向与载荷 winpeshl.ini
2. **重跑阶段 3 不拍快照**（空间纪律原方案，BCD 三行抄录兜底）验证嫌疑；RE 键盘救援链已验证可用（prlctl send-key-event：回车→方向键→命令提示符→bcdedit→wpeutil）

## 救援工具沉淀

- **prlctl send-key-event**（-s 十进制 scancode，press/release 分发）可 RE 全阶段键盘注入；Shift 组合需 press→sleep→key→sleep→release 时序（右 Shift=54，{=Shift+26、}=Shift+27）
