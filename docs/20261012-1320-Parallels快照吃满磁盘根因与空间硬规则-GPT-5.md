# Parallels 快照吃满宿主磁盘：根因、账目与硬规则

日期：2026-10-12 13:20
版本背景：2.3.8（在线还原 STEP 4 引导验收期间）
模型：GPT-5

## 一句话结论

**Parallels 快照不是"备份"，而是把这台 VM 当前所有虚拟盘的**实际数据整份复制一份**。
本机挂载的第二系统盘 `BR217-secondary.hdd` 装着还原后的完整 Windows（约 87GB），
每拍一个快照就多占一份 87GB；三层快照叠加 = 约 265GB，直接把 250GB 空闲吃光。

## 空间账目（为什么"备份八次"的量级不够用）

| 项目 | 大小 | 说明 |
|---|---|---|
| 宿主总容量 | 926 GiB | macOS 数据卷 |
| C: 盘（harddisk.hdd） | 81G | 活动系统 |
| H: 盘（harddisk1.hdd） | 35G | 备份镜像库（36.96GB WIM） |
| E: 盘（harddisk2.hdd） | 1.5G | 数据卷 |
| **BR217-secondary.hdd** | **108G** | **还原目标盘（第二系统），装着一份完整 Windows** |
| 快照层 `BR217-secondary.hdd.0.{5fbaabe3}.hds` | 108G | **这是快照增量，不是"新增数据"** |

一次 C 盘备份 30 多G —— 但**还原**会在第二系统盘上写一份完整系统（87GB），
再拍快照就复制这 87GB。两轮快照叠加就超过 100GB，三层就是 250GB+。
这就是"备份八次的量"为什么不够：备份只写一次，还原 + 快照是乘法。

## 为什么之前几次也反复出现

同一个错在一天内犯了三次：
- 第一次：以为删文件能回收空间 → 实际虚拟盘是稀疏文件，删除数据不归还宿主
- 第二次：以为压缩能救 → 但压缩要在**无快照**状态下做，有快照时压缩无效
- 第三次：**把"拍快照"当成廉价保险** → 每拍一次就复制整个第二系统盘

## 硬规则（下次照做）

### R1　快照只在"真的要整机回滚"时拍，且最多 1 个
拍快照前先算：`第二系统盘当前大小 × 要拍的层数` 必须 ≤ 空闲空间的 1/3。
如果算下来超了，**不要拍**——改用**导出 BCD 文件 + 记录镜像哈希**作为回滚手段（几十 MB vs 100GB）。

### R2　改 BCD / WinRE 注册这类"可精确定位"的变更，用文件级备份代替整机快照
```cmd
bcdedit /store S:\EFI\Microsoft\Boot\BCD /export D:\bcd-backup\before.bcd
```
真正需要保护的是 BCD 这个文件（几 MB）和镜像哈希，不是整个 87GB 的磁盘。

### R3　跑还原前，先确认空闲空间 ≥ 镜像大小 × 2.5
87GB 镜像：至少要 220GB 空闲（镜像 + 快照 + apply 临时）。不够就先清理，不要硬跑。

### R4　每次跑完还原测试，立刻检查并压缩
```bash
df -h /System/Volumes/Data | tail -1          # 先看空间
prlctl list "Windows 11"                       # 确认 VM 已停
prlctl snapshot-list "Windows 11"              # 有快照先删旧层，再谈压缩
# 无快照时压缩三块主盘：
prl_disk_tool compact --hdd "…/Windows 11.pvm/harddisk.hdd"
```

### R5　Parallels 目录里的孤儿盘要么用要么删
`Win11temp.hdd`（5.4GB）从未被 VM 引用却一直占着空间——这类孤儿要定期清。
判断方法：`grep -oE "(harddisk[0-9]*\.hdd|[A-Za-z0-9-]+\.hdd)" config.pvs | sort -u`

## 关于构建产物的额外教训

编译产物放 `E:\br-target` 是错的——**E: 会被还原流程格式化**，每次跑还原产物都会消失，
必须重新编译。正确做法：编译输出放 `C:\br-target` 或宿主共享目录。
