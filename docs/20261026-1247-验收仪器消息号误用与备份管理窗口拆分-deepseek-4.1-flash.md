- 部署 SHA256：`f82d26852d3ce617446b17b1afe3b95537ceee807435172e8696ce98e59b78e0`（VM 内构建，`H:\brwork`）

## 0. 一句话结论

「探测入口选中态读回 9」看着像产品写错了勾选值，实际是**验收脚本把消息号写错了**：
0x00F2 是 `BM_GETSTATE`，`BM_GETCHECK` 才是 0x00F0。产品里那个常量一直是对的
（`native_gui.rs:199  const BM_GETCHECK: u32 = 0x00F0;`）。如果不是先量了三组数据，我会去「修」
一个本来就正确的判断，把它改成错的。**这是同一天里第二个「仪器缺陷伪装成产品缺陷」的案例**
（上午那个是 PS 5.1 的 GBK 解码吞换行）。

---

## 1. 起点：一条红判据

给 `tools/smoke/gui-clicks.sh` 加上「备份文件管理…」这一项后跑整条冒烟，新加的五条全绿，
反而是一直在里面的「探测」那一项红了：

```
-- 第六入口「探测」→ 选中且无关字段隐藏
   FAIL  [expected after: probe_checked=1]
         after: probe_checked=9
         after: backup_checked=0
         after: image_vis=0 target_vis=0 source_vis=0
         restored: backup_checked=9
```

`BM_GETCHECK` 的合法返回值只有 0/1/2（未选/选中/不确定），**9 不是任何合法勾选态**。
同一时刻 `backup_checked` 读到 0 是对的，说明跨进程通信没坏，坏的只是「刚被点过的那个按钮」的读数。

---

## 2. 先量，不猜：三组读数

| 读数 | 手段 | 结果 |
|---|---|---|
| 六个入口的勾选态（静止） | `_diag-checkstate.ps1` | 1101=1、其余=0 —— **全对** |
| 点「探测」后每 300 ms 连读 10 次 | `_diag-click-read.ps1` | 恒为 `check=9 state=0`，稳定不复原 |
| 同一控件用另一条 API 读 | `IsDlgButtonChecked` | 恒为 **1** |
| 「严格对比哈希」复选框（`BS_AUTOCHECKBOX`） | `_diag-checkbox-read.ps1` | 未点=0、勾选后=**9**、取消勾选后=**8** |

最后一行是关键：`8` 只可能是 `BST_FOCUS`。**`1|8 = 9`，`8` 单独出现，说明读回来的根本不是勾选态，
而是「勾选态 | 焦点位」** —— 那正是 `BM_GETSTATE` 的返回格式。

---

## 3. 真因

```
BM_GETCHECK = 0x00F0      <- 产品里就是写的这个，对的
BM_SETCHECK = 0x00F1
BM_GETSTATE = 0x00F2      <- 验收脚本误当成 BM_GETCHECK 用了
BM_SETSTATE = 0x00F3
```

`_t-probe-entry.ps1` 里写的是 `public const uint BM_GETCHECK = 0x00F2;`。
而同一目录下更早的脚本（`br-check-read.ps1`、`_t-gstate.ps1`、`br-gui-state.ps1`、
`br-combo-apply.ps1`）写的都是 **0x00F0** —— 只有今天新写的这一个写错了。
改这一个字节，`probe_checked` 立刻从 9 变成 1，冒烟 7/7 全绿。

**没有改任何产品代码，因为产品代码是对的。**

---

## 4. 如果当时直接去改产品，会改成什么

产品里唯一读勾选态的地方：

```rust
// native_gui.rs:6450（「严格对比哈希」是否启用）
SendMessageW(state.controls.verify_hash, BM_GETCHECK, 0, 0) == BST_CHECKED as isize
```

看到「读回来是 9、判断却写 `== 1`」，很自然的下一步是把它改成
`!= 0` 或 `& BST_CHECKED != 0` —— 那会让这段代码在真正的 `BM_GETCHECK` 下也能「容忍」9，
把一个正确的严格比较换成模糊比较，治好了不存在的病，还顺手降低了本来就对的判据强度。
**判据红的时候，先证明度量工具对，再证明被测对象错。**

对照检查：该复选框勾选后 `IsDlgButtonChecked` 返回 1、真实 `BM_GETCHECK`（0x00F0）也返回 1，
所以「严格对比哈希」这条功能路径一直是好的，不存在静默失效。

## 5. 「备份文件管理…」窗口拆分收尾

第 3 块结构搬迁，把 `native_gui.rs` 里的备份文件管理窗口整块搬到
`native_gui/image_admin_window.rs`（子模块，`use super::*`）：

| 项 | 值 |
|---|---|
| `native_gui.rs` | 10,659 → **9,986** 行（−673） |
| `native_gui/image_admin_window.rs` | **687** 行（新建） |
| 搬走的私有项 | 19 行（窗口类名、两个完成消息、BUSY 标志、三个结果槽、语言、目录） |
| 搬走的函数 | `open_image_admin` / `ask_image_admin_dialog` / `spawn_image_list_worker` / `image_admin_show_detail` / `image_admin_open_folder` / `image_admin_delete_flow` / `window_proc_image_admin` |
| 对外暴露 | 只有 `pub(super) unsafe fn open_image_admin(state: &mut State)` |
| 留在父模块 | `ID_IMAGE_ADMIN*` 常量（`CONTROL_NAMES` 审计表与主窗口 `WM_COMMAND` 还要用） |

逐字比对（脚本 `zip`，不靠肉眼）：**19 行常量块完全相同；656 行函数块只有 `pub(super)` 一处差异**。
交叉编译（`./build-win.sh`）3,186,176 字节，无代码告警；VM 内 release 构建 8.14 s，部署 SHA `f82d2685…`。

### 运行期验收（`_t-image-admin.ps1`，零副作用：只列清单 + 一次选中 + 关闭，绝不点删除）

```
IMAGE_ADMIN_WINDOW_FOUND hwnd=…
wim_files_on_disk=14  combo_count=14  combo_matches_disk=1
hint_nonempty=1
detail_len_before=0  detail_len_after=689  detail_filled=1

```

`combo_count == 磁盘 .wim 数` 是这一项的主判据：清单由 worker 线程写进 `IMAGE_ADMIN_LIST_RESULT`
再由搬走的模块填进 combo，**若静态量被复制成两份而不是搬走，这里会读成 0**。

## 7. 可复用的钉子

1. **判据红时的第一顺位不是读产品代码，是证明仪器对**：拿同一控件的第二条独立 API 对读
   （`IsDlgButtonChecked` vs `SendMessage`），两条都同意才算读数可信。
2. **「不合法值」是最强的线索**：`9` 不在 0/1/2 里，它必然带着别的位。把 9 拆成 `1|8`，
   再看 8 单独出现过（`_diag-checkbox-read` 的第三种状态），立刻指向「读的是 state 不是 check」。
3. **常量怀疑顺序：先怀疑新写的仪器，再怀疑老的，最后才是产品**。四个老脚本都写 0x00F0、
   只有今天新写的写 0x00F2 —— 这个分布本身就是证据。
4. **先把「读错」和「写错」分开**：本轮先用 `_diag-checkstate` 证明静止时读数全对（说明没写错），
   再用时间序列证明只在点过之后才变 9（说明是读的格式问题），两步就把范围从「整个产品」
   缩到「一次读取」。
5. **跑绿不等于对，跑红也不必改代码**：改完仪器后 7/7 全绿，但产品一个字节没动 ——
   这是这次唯一正确的收尾方式。
