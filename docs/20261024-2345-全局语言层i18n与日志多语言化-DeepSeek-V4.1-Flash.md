# 全局语言层 `i18n`：让界面之外的日志与 CLI 也能切英文

- 撰写：2026-10-24 23:45
- 模型：DeepSeek-V4.1-Flash
- 版本：**v2.6.39**（新增 `crates/backuprestore-cli/src/i18n.rs`）
- 触发：用户要求「其它地方适当的多语言化」

---

## 一、此前的问题：只有界面是多语言的

| 范围 | 改造前 |
|---|---|
| GUI 界面文案 | ✅ `Language{Chinese,English}` + `ui_text`/`tooltip_text` 双语表 |
| RE/PE 弹窗文案 | ✅ `MessageLanguage`，经 `prepare --ui-language` → `UI_LANGUAGE` → `RecoveryTask.env` → `ui_language()` 传递 |
| **日志文件** | ❌ `append_log(path, message)` **不带 language 参数**，258 个调用点全是中文硬编码 |
| **CLI stdout** | ❌ 同上（`online` 连 `--ui-language` 都没有） |

后果：英文用户排障只能看中文日志；自动化测试想让输出避开中文也做不到。上一轮文档里那句「切英文救不了判据」说的就是这个。

---

## 二、新增 `i18n.rs`：进程级语言状态 + 关键文案表

### 2.1 语言来源优先级

```
set()（GUI 切语言 / RE 读到 UI_LANGUAGE）
  > env BACKUPRESTORE_LANG（en* 判英文）
    > 默认中文（与改造前行为逐字一致）
```

### 2.2 文案表

`(key, 中文, 英文)` 三元组集中管理：

```rust
pub(crate) fn msg_in(language: MessageLanguage, key: &str) -> &'static str   // 纯函数
pub(crate) fn msg(key: &str) -> &'static str                                  // 读全局
```

- 缺失返回显眼哨兵 `<i18n:missing>`（不能返回 `key`——它是 `&str` 不是 `&'static str`）
- 单测 `every_key_has_both_languages` 防呆：不许缺一边、不许中英文一样（漏翻）、英文条目不许混 CJK

### 2.3 接入点

| 位置 | 作用 |
|---|---|
| `main()` | `init_from_env()` 读 `BACKUPRESTORE_LANG` |
| RE 侧（`ui_language(&values)` 之后） | `i18n::set(language)`——恢复环境日志跟着 `UI_LANGUAGE` 走 |
| GUI `apply_language()` | 界面切英文后**日志也跟着切**（此前切了界面日志还是中文） |
| `online_operation` | STEP 1 开场白、日志位置、收尾成功/失败结论 |

---

## 三、★ 「适当」的边界

只覆盖**结论性文案**：成功 / 失败 / 阶段 / 日志位置。深层错误细节仍是中文：

```
[ERROR] Online operation did not complete: invalid task: dism.exe 失败：退出码 2
        └── 已双语 ────────────────────┘   └── 未翻译（深层细节）──┘
```

**为什么不全量翻译**：`append_log` 有 **258 个调用点**，逐个加参数是灾难级改动，且绝大多数细节调试日志不值得翻译。改法不是改签名（那要动 258 处），而是**需要双语的点主动查表**。细节日志保持中文，按需逐步补。

---

## 四、★ 一个设计要点：查表要抽成纯函数

`msg_in(language, key)` 是纯函数，`msg(key)` 只是「读全局 + 调纯函数」的包装。

**原因**：Rust 单测并行执行。如果只有读全局的版本，测试里为了断言英文就得 `set(English)`，这会污染同时运行的其它用例——例如 `online_operation::step1_notice_splits_by_operation` 断言的是中文措辞（「不格式化」「只读取源卷」），会被误伤成 flaky。抽成纯函数后可逐个语言断言，完全不碰全局。

## 五、验收

| 项 | 结果 |
|---|---|
| 单测 | **235 通过**（含 i18n 新增 4 条） |
| 交叉编译 + 部署 | ✅ `SHA256=c85caaba…` |

| 日志英文 | `Log location: …\Online.log (unified log root, not lost when %TEMP% is cleaned)` |

| 全链冒烟 | **7/7 PASS**（run24，`.test-artifacts/smoke-20261024-233334`） |

中文对照是关键的**回归证据**：证明默认行为一字未改，不是"顺手把中文也改了"。

## 六、遗留

- **258 个 `append_log` 调用点里绝大多数仍是中文**。本轮只覆盖了 online 路径的结论性文案；`main.rs`（132 处）、`windows_prepare.rs`（40 处）、`boot_entry.rs`（26 处）等尚未接入。扩展方式明确：把文案搬进 `MESSAGES` 表，调用点改查表。
- `online` 仍没有 `--ui-language`（只有 `prepare` 有）——目前在线路径只能靠 `BACKUPRESTORE_LANG` 环境变量。
- 判据仍应优先用 `--json` 的结构化字段，不要依赖任何语言的文案（包括英文）——文案会随版本变，字段不会。
