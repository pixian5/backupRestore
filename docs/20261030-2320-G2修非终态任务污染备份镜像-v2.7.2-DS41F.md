## 1. 缺陷是什么（两段代码对照）

| 位置 | 原文 |
|---|---|
| `core::build_capture_exclusions` 注释 | 「同目录的 `tasks\`（任务证据）与 `logs\` **必须留在镜像里**（证据全留，2026-10-24 拍板）」 |
| `cli::find_pending_boot_task` | 只扫 `<exe目录>\tasks` 里的**阶段**（`BootRequested`…`ImageApplied`），**从不校验 BCD 里有没有该任务的一次性启动项** |

于是：备份时 `tasks\` 里若躺着一个**没跑完**的任务 → 它随镜像进 WIM → 还原到新系统后，
新系统上的程序看到它 → 弹「上次没跑完的还原任务」→ **点了必然失败**（启动项只在原系统的 BCD 里）。
用户看到一个"幽灵任务"。（2026-10-18 有截图实证，当时只修了死锁那半边。）

附带一条没人算过的账：每个任务目录里躺着 `original\Winre.wim`(679MB) + `stage\Winre.wim`(682MB)，
**每个非终态任务白占约 1.4GB 镜像体积**。

## 2. 治标（2.7.1）：续跑检测必须验证启动项存在

`main.rs::find_pending_boot_task`：读出任务的 `boot-entry.json`，确认其中的 `loaderGuid`
**此刻在 BCD 里真的存在**；不存在 → 跳过（记一行日志），不弹框。

新增 `boot_entry::bcd_object_present(object) -> bool`。

★ **判据不能用退出码**：实测 `bcdedit /enum {已删对象}` **退出码仍为 0**，
只输出本地化文案「没有匹配的对象或存储为空。」

## 3. 治标判据里踩的坑（2.7.2 修）：判据不能依赖本地化文案

第一版判据写的是「输出含 `identifier` 或 `标识符`，且含 `{`」。

**变异验证当场把它打红**：把夹具的启动项换成一个**真实存在**的 `{current}`，
按标准结果应该**弹框**（证明拦它的是判据），结果**没弹** —— 说明判据把存在的对象也判成不存在。

根因：`bcd()` 用 `String::from_utf8_lossy` 解码，而中文 Windows 的 `bcdedit` 输出是 **GBK**，
`text.contains("标识符")` **永远不匹配**；英文关键字在这个系统上也不出现。

**改为语言无关的结构判据**：`text.contains(object.trim())`
—— 找到时 `bcdedit` 一定在标识符行**回显请求的那个对象串**；找不到时只回一句空存储提示，不含请求串。

这条值得单独记：**判据里出现"本地化文案"就当红旗**，哪怕那文案是自己刚在屏幕上看到的。

## 4. 治本（2.7.2）：非终态任务目录不进镜像

`build_capture_exclusions` 在原来的「程序卷 == 源卷」块里，追加：

```rust
for name in pending_task_names(&exe_dir.join("tasks")) {
    lines.push(format!("\\{rel}\\tasks\\{name}"));
}
```

- **非终态**（`status.json` 的 stage 不是 success / failed）→ 排除；
- **终态**（success / failed）→ **保留**（那才是 2026-10-24 拍板要留的证据）；
- 读不到 / 解析失败 / 没有 `status.json` → **按非终态排除**（宁可少备份一条没跑完的记录）。

## 5. 验收

### 5.1 治标：端到端 + 变异（都在 VM 实跑）

夹具：复制一个真实任务目录，把 `status.json`/`task.json` 的阶段改成 `capturing`，
`boot-entry.json` 的 `loaderGuid` 改成一个**不存在的 GUID**。

| 场景 | 判据 | 结果 |
|---|---|---|
| 启动项**不存在** | `#32770` 对话框数 / 进程数 / 日志 | **0 个框** / 1 个进程 / 日志有 `Pending recovery skipped (boot entry no longer in BCD): ffffffff-…` |
| 启动项**存在**（`{current}`，变异态） | 同上 | **弹出** `#32770 待续跑的还原任务 / Unfinished recovery task` ✅ 证明拦它的就是新判据 |

★ 第一次跑变异态时结果不对（没弹框），正是靠它发现了 §3 的 GBK bug。

### 5.2 治本：单测 + 变异

`core::capture_exclusion_task_tests::pending_tasks_excluded_finished_kept`：

- 造 `done-1(success)` / `fail-1(failed)` / `busy-1(capturing)` / `broken-1(无 status.json)`；
- 断言 `pending_task_names` 只返回 `["broken-1", "busy-1"]`；
- **变异验证**：把 `task_stage_is_terminal` 改成恒 `true` → 测试 **FAILED**；改回 → **ok**。

★ 测试只测纯函数 `pending_task_names`，**不测整函数** `build_capture_exclusions`：
后者有「源卷 == 程序卷」的守卫，在 macOS 上恒为假，直接测整函数会得到空列表，
**把「逻辑错」伪装成「平台不同」**（第一版测试就是这么红的，一开始还以为是环境问题）。

### 5.3 全量回归

`cargo test -p backuprestore-core` → **58 passed**；`cargo test -p backuprestore-cli` → **329 passed / 1 ignored**。
