# 编码问题为何躲不开中文：ASCII 边界与判据纪律

- 撰写：2026-10-24 23:00
- 模型：DeepSeek-V4.1-Flash
- 版本：v2.6.37（**仅改测试脚本 `tools/smoke/`，产品代码零改动，故 VERSION 不动**）
- 触发：用户追问「你在编程的时候为什么还会涉及到 UTF-8 之类的字符啊？你编写 CMD 进行测试的时候你都使用 ASCII 码，是不是就能完全解决这个问题了？」

---

## 一、一句话答案

**用户说对了一半，而且是对的、该照做的那一半——但"全用 ASCII"消灭不了这个问题，因为中文不在我的代码里，在被测系统的回答里。**

- ✅ **能消灭的**：我写进 `prlctl` 命令行、批处理、PS 脚本的字符串，以及所有**判定逻辑**——已做到 **0 处非 ASCII**。
- ❌ **消灭不了的**：被测程序与 Windows 自身输出的中文。脚本一个中文都没有，`dir` 照样用 GBK 回你「找不到文件」。

所以真正的解法不是「不写中文」，而是：**让中文不参与任何逻辑判断**。

---

## 二、用户判断对在哪：已落地为 0 处

### 2.1 全脚本扫描结果

对 `tools/smoke/br-smoke.sh` 做精确扫描（`vm_cmd` / `vm_ps_raw` / `vm_ps_exec` 的第一个字符串参数，即真正进入 `prlctl` 命令行的部分）：

```
VM 命令体非 ASCII 位置数: 0
```

改前有 1 处（`'{0:N1} GiB 可用 / {1:N1} GiB'`，取卷容量时的格式化串）。改法：**VM 侧只输出两个数字**，中文由宿主终端拼：

```bash
free=$(vm_ps_raw "\$v = Get-Volume -DriveLetter ${DRIVE}; '{0:N1}|{1:N1}' -f (\$v.SizeRemaining/1GB), (\$v.Size/1GB)")
if [ -n "$free" ]; then
    free="${free%|*} GiB 可用 / ${free#*|} GiB 总容量"   # 中文只在宿主侧出现
fi
```

两个 helper（`br-smoke-helper-seed.ps1` / `br-smoke-helper-collect.ps1`）本来就是 **0 非 ASCII**。

### 2.2 纯 ASCII 批处理实测可行

造一个 225 字节、0 非 ASCII、CRLF 的 `.cmd` 放进 VM 执行：

```
PROBE_START
DIR_RC=1
DIR_BYTES=12
PROBE_END
```

执行干净、可解析、无任何编码干扰。**纯 ASCII 脚本这条路完全成立。**

### 2.3 判定逻辑已 100% ASCII 化

脚本里 6 项判据原先唯一的中文依赖是 C3：

| | 旧判据（中文，脆） | 新判据（ASCII，稳） |
|---|---|---|
| 还原是否走完 | `re.search(r'操作完成', log)` | `STEP 4/4` + `The operation completed successfully` |
| 还原命令是否返回 | `grep -aq "日志："` | `grep -aqE 'Online\.log'`（日志路径是 ASCII） |

其余判据本来就是结构化的：`stage=success` / `progress=100` / 文件字节数 / SHA256 / 卷序列号 / diskpart 的进度数字 `100`。

## 三、用户判断覆盖不到的那一半：系统会用中文回答你

### 3.1 四条实测（都是"脚本里 0 中文"的前提下发生的）

| 来源 | 输出编码 | 实测证据 |
|---|---|---|
| `dir /b T:\`（空卷） | **GBK** | `D5D2 B2BB B5BD CEC4 BCFE` = 「找不到文件」 |
| `diskpart` | **GBK** | `format.out` 开头 `b0e6 b1be` = 「版本」、`d4da bcc6 cbe3 bbfa` = 「在计算机」 |
| BackupRestore 主程序 stdout | **UTF-8** | `e6938d e4bd9c` = 「操作」，全文「操作完成：命令、回读和副档簿记均已通过」 |
| 主程序写的日志 | **UTF-8，且含中文** | `DISM 结果：退出码 0` |

**同一份冒烟脚本，要同时对付 GBK 和 UTF-8 两种输出源**。这不是脚本作者的疏忽，是被测环境的客观构成：Windows 是中文版、产品是中文产品。

### 3.2 决定性反证：我的脚本 0 中文，输出照样是中文

`probe.cmd` 全文只有 `@echo off`、`echo PROBE_START`、`dir /b T:\`、`echo DIR_RC=%ERRORLEVEL%` 这些 ASCII。运行结果里 `DIR_RC=1` 是对的，但 dir 的错误消息仍是 GBK「找不到文件」。

→ **编码问题是"数据"的属性，不是"代码"的属性。** 代码可以全 ASCII，数据不能。

### 3.3 能不能让上游工具也说英文？取决于上游

- **DISM 可以**：程序已经给它传了 `/English`（实测命令行里有 `"\/English"`），所以 DISM 输出恒为英文、`The operation completed successfully.` 跨语言稳定。
- **diskpart 不行**：没有语言开关。只能认跨语言稳定的数字 `100`（进度百分比）。
- **cmd 内建不行**：`chcp 65001` 生效但改不动管道输出（前一篇文档已实测），只能认 ASCII 或纯数字。

结论：**"能不能 ASCII 化"取决于上游工具是否提供语言开关**，不是脚本作者能单方面决定的。所以判据必须建立在"上游能保证英文或数字"的部分上。

## 四、编码问题的本质

> 不是「我的文件里有没有中文」，而是「字节流跨越进程边界时，两侧对同一串字节的解释是否一致」。

本项目的边界是 `prlctl exec` 的 stdin/stdout——本质是**管道**：

```
mac 宿主 (UTF-8 locale, bash)
   │  argv: prlctl 按字节透传
   ▼
Windows cmd (进程 ANSI 代码页 = 936/GBK)
   │  内建命令按 936 落字节；外置程序按自己的规则
   ▼
stdout 管道 → prlctl → mac 宿主
```

中文在这个边界上**必然出现**（因为被测系统是中文的）。所以可行的策略只有三条：

1. **不让中文进入命令行**（代码层 ASCII 化）——已做到
2. **不让中文参与判定**（判据层 ASCII 化）——已做到
3. **不转码，只透传**（传输层 `type` 字节搬运）——已做到

## 五、四层纪律（以后照这个写）

| 层 | 纪律 | 现状 |
|---|---|---|
| **代码层** | 进入 `prlctl` 命令行的字符串 100% ASCII；中文只在宿主侧拼 | ✅ 扫描 0 处 |
| **判定层** | 只认 ASCII 结构化特征（阶段标识 / 状态字段 / 数字 / 哈希 / 序列号），**绝不 grep 中文文案** | ✅ 0 处中文判据 |
| **传输层** | `cmd /c type` 字节透传，不做任何转码 | ✅ |
| **展示层** | 中文只在 mac 宿主终端出现（UTF-8 天然正确） | ✅ |

补充三条与编码无关但同源的经验：

- **`grep` 处理 GBK 字节流必须 `LC_ALL=C`**：UTF-8 locale 会因非法字节**整行跳过**（连 diskpart 的 `100` 都搜不到）。
- **`Out-File -Encoding UTF8` 在 PS5.1 会写 BOM** → JSON 首字段带 `U+FEFF`，比较直接失配。用 `[IO.File]::WriteAllText(..., (New-Object Text.UTF8Encoding $false))`。
- **通道偶发返回空**是独立问题（不是编码），读文件/读状态必须重试。

## 六、今天挖到的三个实锤（写下来防重犯）

### 6.1 `DISM  0` 是假象 —— 剥掉中文会骗自己

我在日志里用 `tr -d '\200-\377'` 剥掉非 ASCII 字节后看到：

```
[2026-10-24T14:52:53.278756+00:00] DISM  0
```

一度以为找到了纯 ASCII 的"退出码"判据（`DISM\s+(\d+)$`）。**实际字节是 `DISM 结果：退出码 0`**——中文。

> 教训：**用 ASCII 的眼睛看中文数据，看到的是残缺的假象。** 任何"我把它转成 ASCII 再看"的操作，都会掩盖真相。

### 6.2 `restore.out` 的 ASCII 骨架只剩一行

把主程序 stdout 剥掉非 ASCII 后：

```
H:\brwork\logs\BackupRestore-online-9976-1792853568355308300\Online.log
```

**其余全部是中文文案**。这意味着：想从 stdout 里取"还原成功"这个信息，就绕不开中文。所以判据必须换到**结构化源**——`STEP 4/4`（程序阶段标识）、`status.json` 的 `stage/progress`，而不是自然语言文案。

### 6.3 判据"名不副实"是隐患

C3 原来叫「任务 success/100」，判的却是日志里的 `STEP 4/4` + 中文「操作完成」，**从没读过 `status.json` 的 `stage`/`progress`**。名字承诺的是结构化字段，实现走的是文案匹配——文案一变就误判，而且给了"我已经判了结构化字段"的错觉。

改后：`STEP 4/4`（结构化）+ DISM 英文成功行（附加信息，降级路径无此行也不误判）。

## 八、遗留

- 中文文案仍会出现在**展示路径**（`log` 打印、`verdict` 详情），这是设计意图：人看的东西用人话，机器判的东西用 ASCII。
- `diskpart` 只能认数字 `100`；若将来要更细的成功证据，需要在程序里给 diskpart 结果做结构化输出（改产品代码，不在本次范围）。
- `restore.out` 全是中文文案，若能给 CLI 加 `--json` 输出，判据可进一步脱离日志文本。**记 backlog，非当前必做**。
