# 盘符观测：谁挂的、什么时候、有没有被收回（v2.6.76 实机）

- 撰写时刻：2026-10-29 01:38（世界时 10-28 17:38）
- 版本：**2.6.76**（行为变更：准备期新增盘符时间线落盘 + 可选采样线程）
- 起因：用户 2026-10-29 对「第二件：要不要花一轮看清那个临时盘符到底是谁、在哪一步分配的」裁决为
  **「要观测，把事实钉死」**（决策书见 `docs/20261029-0040-…`）
- 结论先说：**本机根本没有「临时盘符」这回事** —— 恢复环境的卷就是系统盘 C:，
  准备流程全程一个盘符都不挂。原先「恢复卷的盘符是 `identity_from_diskpart`
  提前用 `diskpart assign letter=` 分配的」这个推断，在本机布局下**不成立**。

---

## 〇 为什么这件事值得一轮

盘符是**持久**写入（`HKLM\SYSTEM\MountedDevices`）。用完了不撤，盘符会永久留在系统里；
等那个分区后来被删掉，记录还在，Windows 就会为一个不存在的卷反复弹
「X:\ 无法访问。设备未就绪。」。本项目 2026-10-27 一次性查出 6 个这样的幽灵盘符
（B/G/I/Q/V/Z），用户为此手动清理过多次。

准备流程里有一条**代码上没有任何租约覆盖**的挂载：`identity_from_diskpart()` 里的
`diskpart assign letter=`。它发生在 `recovery_identity()` 被调用的时候，比
`ensure_volume_mounted_leased()` 早；到后者执行时卷已经有盘符了，于是走「复用」分支、
租约是空的。也就是说：**如果准备流程在那之后失败/被杀，这个盘符不会被任何人撤掉。**

但这只是读代码得出的推断。上一轮已经吃过一次「推断很顺、实测打脸」的教训
（PE 装前自检那个 89 字节坏件，「包含 `Recovery.exe`」的宽松判据是**碰巧**拦住它的），
所以这一轮先造摄像机、再看事实。

## 一 仪器（v2.6.76 新增）

### 1.1 两类记录，缺一不可

| 记录类型 | 谁写 | 解决什么问题 |
|---|---|---|
| **有主的事件**（`ASSIGN` / `REUSE` / `LEASE` / `HOLD` / `RELEASE`） | 动手的那段代码自己写 | 「谁挂的」——采样器只能看见「R: 出现了」，说不出是谁让它出现的 |
| **采样**（只在设了环境变量时开） | 后台线程每 N 毫秒读一次 `GetLogicalDrives()` | 「有没有没人声明的变化」——别的进程挂的、Windows 自己收回的 |

两者合起来才是一份完整时间线；只有前者会漏掉意外，只有后者说不清归属。

### 1.2 落点与开关

- 文件：`H:\brwork\logs\drive-letter-trace.log`（`log_root::logs_dir()`，与其余日志同源）
- 格式：**追加**，每次准备先写一行分隔头
  `# drive letter trace: pid=… exe=… sample_ms=… started=<UTC>`
  —— 追加而不是覆盖，是因为盘符泄漏是「很久以后才发作」的问题，
  下一次准备就把上一次证据覆盖掉，等于在用户报障之前销毁证据。
- 采样开关：环境变量 `BACKUPRESTORE_LETTER_TRACE_MS=<毫秒>`，钳在 50–5000 ms。
  **不设就不启线程**，只记有主事件（每次准备十几行）。生产默认开销≈0。
- 输出**纯 ASCII**：这份文件要整段 `type` 回来看，混进非 ASCII 会在 `prlctl exec` 里变乱码。

### 1.3 代码落点

| 位置 | 内容 |
|---|---|
| `crates/backuprestore-cli/src/text_parsing.rs` | 两条纯判据：`letters_in_mask()`（位图 → `C..=Z`，A/B 软驱位不算）、`letter_delta_line()`（两次采样差异，**没变返回 `None`**）。4 条单测在 `mod drive_letter_timeline`，macOS 可跑 |
| `crates/backuprestore-cli/src/letter_trace.rs`（新） | 采样线程 + 落盘。`start()` 幂等；`note()` 在未开时**静默空转**（调用点不必判断）；`finish()` 写 `EXIT now=…` |
| `windows_prepare::prepare_task` 开头 | `letter_trace::start(...)` —— **必须早于任何身份探测**，晚一步就漏掉要观测的那一次 |
| `identity_from_diskpart` | 复用分支记 `REUSE`；assign 成功记 `ASSIGN … via=diskpart (persistent MountedDevices write; no lease covers it)` |
| `mount_volume_guid` / `release_mounted_letter` / `MountLease::new` / `hold_for_process` | 分别记 `ASSIGN via=mountvol` / `RELEASE` / `LEASE` / `HOLD` |
| `efi_identity` 的 `mountvol /S` + `/D` | 补 `ASSIGN via=mountvol /S (temporary ESP inspection)` / `RELEASE` —— 这是另一处**临时**盘符，原先时间线看不见 |
| `main.rs` 两处退出路径 | `release_process_leases()` 之后调 `letter_trace::finish()`：把「进程退出那一刻还剩哪些盘符」钉在文件里 |

单测：`cargo test -p backuprestore-cli` → **330 条，329 通过 / 1 ignored**。

## 二 实机观测

环境：Parallels「Windows 11」，填空题式 CLI（`prlctl exec` 走 SYSTEM，即 session 0），
二进制 `H:\brwork\BackupRestore.exe`（部署 SHA-256 `2bf7234f…`）。

### 2.1 时间线原文（四次运行，同一份文件）

```text

t+0ms START now=CDFHST
t+663ms REUSE C: disk 0 partition 4 (already mounted; no assignment)
t+33177ms EXIT now=CDFHST
# drive letter trace: pid=2440 ... started=2026-10-28T17:35:12.379823200+00:00
t+0ms START now=CDFHST
```

逐行含义：

| 运行 | 做了什么 | 读到什么 |
|---|---|---|
| pid 6700 | 一次**失败**准备（被上一轮遗留的未终结任务挡住，1.6 s 退出） | `REUSE C:` → 直接 `EXIT`，**没有挂任何盘符，因此也没有可泄漏的东西** |
| pid 2440 | 一次**成功**准备（备份准备 + `--no-reboot`，25.8 s） | 同上：零挂载、零撤销 |
| pid 1756 | 又被遗留任务挡住（1.3 s 就退） | `START` 快照里就带 `Y` —— 见 §三 的坑 3 |
| pid 3060 | 成功准备（31.7 s）＋**在它跑的时候注入一个 `subst Y:` 再撤掉** | `t+5142ms +Y` / `t+12260ms -Y` —— **采样器确实在按 200 ms 的粒度读真实状态并只写变化行** |

### 2.2 为什么恢复卷是 C:

- `reagentc /info`：`Windows RE 位置 = \\?\GLOBALROOT\device\harddisk0\partition4\Recovery\WindowsRE`
- 分区布局（`Get-Partition`）：

  | 磁盘 | 分区 | 盘符 | 类型 | 大小 |
  |---|---|---|---|---|
  | 0 | 1 | — | Recovery | 300 MB |
  | 0 | 2 | S | System（ESP） | 300 MB |
  | 0 | 3 | — | Reserved（MSR） | 128 MB |
  | 0 | 4 | **C** | Basic（系统盘） | 249.5 GB |
  | 0 | 5 | — | Recovery（label `WINRE`） | 840 MB |

  分区 4 就是 C:，WinRE 注册在它上面 → 恢复卷 = C: → `identity_from_diskpart` 在
  「复用已挂载分区」那一轮就命中 C:，`diskpart assign letter=` **一次都没执行**。

### 2.3 那能不能人为造出「无盘符的恢复分区」？——试了三次，Windows 不让

想要的是 OEM 常见布局：WinRE 落在**没有盘符**的专用恢复分区里。做法与结果：

| 步骤 | 结果 |
|---|---|
| 先把 Winre.wim 抄进分区 5（临时 `diskpart assign letter=R`，抄完 `remove letter=R`） | 成功（`robocopy /B`，两个文件 715,281,833 B） |
| `reagentc /setreimage /path R:\Recovery\WindowsRE` → `reagentc /enable` | `/setreimage` 打印「目录已设为 …\partition5\…」，但 `/enable` 之后 `/info` **仍是 partition4** |
| `reagentc /disable` → 删掉 `C:\Recovery\WindowsRE` 副本 → `/setreimage` → `/enable` | 仍然回落 partition4 |
| 清空分区 5（腾出 876 MB）后再来一遍 | 仍然回落 partition4 |

结论：**Win11 26100 的 `reagentc` 不接受这个 840 MB 的分区**，坚持把 WinRE 放回系统卷。
所以「在无盘符恢复分区上跑 assign」这件事，**在这台机器上造不出来**，也就无法用观测回答；
它只在 OEM 布局（RE 分区 ≥1 GB）上才会发生。

## 三 事实钉死（三条）

1. **本机准备流程不挂任何盘符。** 恢复卷 C:、工作卷 H:、镜像卷 H:、ESP S: 全都有盘符，
   没有任何一次 `diskpart assign letter=` / `mountvol` 发生。因此：
   - 「谁分配的」= 没人分配，用的是系统盘自己的盘符；
   - 「什么时候」= 不适用；
   - 「有没有被收回」= 没有东西可收回，退出时盘符集合与进入时完全一致（`CDFHST` → `CDFHST`）。
2. **`windows_prepare.rs` 里那段「租约为空」的注释，前提是错的。**
   原注释说那个盘符是 `identity_from_diskpart` 提前分配的；实测是**卷本来就有盘符**（C:）。
   断言本身仍然有效（它守的是「:979 到 :1226 之间恢复卷没丢盘符」这个环境前提），
   但注释已按实测订正，免得下一个读者照着错前提再推错一次。
3. **`identity_from_diskpart` 里那条 `diskpart assign letter=` 确实没有租约** ——
   这是**代码事实**，不是本机观测：它写的是持久记录，失败/被杀时没人撤。
   但它在本机走不到；要不要补租约，等有 OEM 布局机器再定。

### 顺带查出的四个坑（都已记进 `经验/`）

1. **`copy` 读不动 `C:\Recovery\WindowsRE\Winre.wim`**：`icacls` 只有 `BUILTIN\Administrators:(F)`，
   即便执行身份是 `nt authority\system` 也照样报「系统找不到指定的文件」（不是「拒绝访问」，
   极具误导性）。解法：`robocopy /B`（备份模式走 `SeBackupPrivilege`）。
2. **`reagentc /setreimage /path` 只在 RE 处于 Disabled 时才被采纳**，而且 `/enable` 之后
   仍会**重新判断**目标分区是否合格——它不认你指定的路径，只认它自己的标准。
3. **`prlctl exec` 全部落在 session 0，`subst` 映射跨调用可见**：所以第一次注入实验里
   进程一启动快照就带着 `Y`（上一分钟我在另一个 `prlctl exec` 里建的）。
   这也是注入实验能做的原因——注入与准备必须在**同一个会话**里。
4. **`start "" /b …` 的后台进程能活过 `prlctl exec`**（pid 2440 那次 25.8 s 全跑完了），
   但它创建的「未终结任务」会挡住下一次准备——`prepare` 的闸门在
   `recovery_identity()` **之后**、`ensure_workspace_capacity()` **之前**，
   所以被挡住的运行**压根没走到**租约那一段。

## 四 现场还原（务必遵守：改了机器就要还原并复核）

改装过程中对恢复环境注册做了 `disable` / `setreimage` / `enable` 的往返，还原后复核如下：

| 项 | 改前 | 改后（已复核） |
|---|---|---|
| `reagentc /info` 状态 | Enabled | **Enabled** |
| WinRE 位置 | `harddisk0\partition4\Recovery\WindowsRE` | **同左** |
| 恢复启动项 GUID | `{27468cac-d2da-11f1-89da-d3a2c441758f}` | **`{35457f54-d2f5-11f1-89de-dded4fd0121c}`**（`reagentc` 重新注册后换了 GUID，内容等价：`ramdisk=[C:]\Recovery\WindowsRE\Winre.wim`、`winpe Yes`、`path \windows\system32\winload.efi`） |
| `C:\Recovery\WindowsRE\Winre.wim` | 712,111,529 B（2026/09/27 20:13） | **同左**（`/disable`+`/enable` 是**搬运**不是复制，字节与时间戳都没变） |
| 分区 5 里的临时副本 | 无 | **已删**（分区 5 回到约 4 MB 占用） |
| `R:` 盘符 | 不存在 | **不存在**（`diskpart remove letter=R`） |
| `MountedDevices` 的 `\DosDevices\*` | C/D/F/H/S/T 共 6 条 | **C/D/F/H/S/T 共 6 条，无 R、无 Y 残留** |
| `subst` 映射 | 无 | **无** |
| 遗留任务 | 1 个未终结（`d26bd3d4`） | **全部 `abandon-task` 收口**（共 4 个：`d26bd3d4` / `1dffe939` / `42baa3c1` / `7fe6d377`） |

唯一实质变化是恢复启动项的 GUID。这是 `reagentc` 自己换的，不影响引导（同一份 wim、同一条
ramdisk 规格），但**记在这里**，免得下次对比 `bcdedit` 时以为是谁写坏了。

|---|---|---|
| OEM 布局（RE 在无盘符分区）下的 assign 观测 | 本机造不出来（§2.3），要改分区大小才有意义 | 有 OEM 机器时，把 `BACKUPRESTORE_LETTER_TRACE_MS=200` 一设、跑一次失败的准备，看 `ASSIGN … no lease covers it` 后面有没有对应的 `RELEASE` |
