## 1. PE 硬盘版安装（#139）：通过

**做法**：`diskpart` 在 disk1 上建 8 GiB 分区，盘符 `T:`，卷标 `BRPETEST`；然后用测试钩子驱动 GUI 走「硬盘版」分支。

钩子脚本 `tools/win-clicker/start-gui-hook-disk.ps1`（ASCII only，写后回读）：

```powershell
$json = '{"tab":"pe","mode":"disk","target_volume":"T","pe_name":"BR-PE-DISK","image":"H:\\BRImages\\pe-boot.wim","auto_install":true}'
[IO.File]::WriteAllText('C:\br-test.json', $json, (New-Object System.Text.UTF8Encoding($false)))
```

> 回读是必须的：钩子读不到字段会**静默回落默认值**，而默认值恰好是「内存版」，那样测的就不是硬盘版了。

**判据（只认副作用，不认界面文案）**：

1. **目标分区真的被格式化**：任务目录 `pe-format.log` 记录 `volume_serial 9814FA87 → EA53795F`，且 `verify_formatted_volume` 通过 —— 不是「退出码 0」就算，是序列号变了。
2. **WIM 真的展开到了分区根**：`T:\` 共 **15,457 文件 / 2,165,472,267 B**，`Program Files`、`Windows`、`Users`、`BackupRestorePE.txt`(216 B) 齐全，`T:\Windows\System32\winload.efi` 存在。
3. **BCD 新增条目**：`{17f55dc9-d292-11f1-89d2-badbd9f69e81}`，`description=BR-PE-DISK`、`device/osdevice partition=T:`、`path \Windows\system32\winload.efi`、`winpe Yes`；`displayorder` **追加在末尾**；`default` 与 `resumeobject` **逐字未变**（与界面「不改默认启动项」的自述一致）。

## 2. 已安装的 PE 能否真的启动（#140）：能

引导了三重证据，缺一不可：

- **内核加载日志**：`T:\Windows\ntbtlog.txt` 140 行，`ntoskrnl` / `hal` / `disk.sys` / `storvsc` 全部 `LOADED` —— 说明不只是 bootmgr 认了条目，内核确实起来了。
- **PE 壳的日志**：`T:\Windows\System32\winpeshl.log` 有内容（wpeinit 已跑）。
- **交互证据**：把镜像里的 `winpeshl.ini` 改名后重启，PE 停在
  `Administrator: X:\Windows\system32\cmd.exe  X:\Windows\System32>` —— 这是 PE 本体，不是 Windows。

> 教训：**「重启后又是启动菜单」不等于「PE 起不来」**。本次第一轮就误判过：重启后截图又是启动菜单，实际是 PE 已经把 `winpeshl.ini` 里的程序跑完、没有前台进程，自己重启回 Windows（见下节）。

## 3. 「选 PE 后一闪回 Windows」的真因

PE 镜像（`H:\BRImages\pe-boot.wim`）里 `\Windows\System32\winpeshl.ini` 的内容是：

```ini
[LaunchApps]
%SYSTEMROOT%\System32\RecoveryLauncher.cmd
%SYSTEMROOT%\System32\recenv.exe
```

- `RecoveryLauncher.cmd` 因为缺 `RecoveryTask.env` 直接 `exit /b 87`；
- `recenv.exe` **在这个镜像里根本不存在**，`winpeshl.log` 记 `Failed to launch application … [0x80070002]`；
- `[LaunchApps]` 列表跑完且没有前台进程 → **PE 自动重启**，外观就是「选了 PE，一闪又回到 Windows」。

**关键事实**：该 WIM 的自启动配置与仓库模板 `windows/winpe-winpeshl.ini` 不一致 —— 模板写的是

```ini
[LaunchApps]
%SYSTEMROOT%\System32\Recovery.exe,--pe-desktop
```

说明 `pe-boot.wim` 是 **WinRE 派生物**，它的 `winpeshl.ini` 没有被产品模板覆盖过。**「PE 起不来」和「PE 起来了但它的启动脚本指向不存在的程序」是两件事**，前者查引导，后者查镜像内容。

## 4. A 档「正常收尾释放 `hold_for_process` 盘符」（#138）：本机不可达 + 结构性死代码

### 4.1 为什么不能直接测

`ensure_volume_mounted_leased` 只在**亲手新分配**盘符时产生租约（`MountLease::new` 里 `created.then_some(letter)`），而 `hold_for_process` 只对「有字母」的租约生效。本机 WinRE 原本注册在 **C:**（本来就有盘符）→ 租约恒为空 → 函数空转。

要真正触发，必须让 WinRE 住在一个**无盘符卷**上。本机的 disk0 p5（840 MiB，GPT 类型 `de94bba4`、属性 `0x8000000000000001`）正好是一个合格的恢复分区，于是开始尝试把 WinRE 搬过去。

### 4.2 搬 WinRE 的六次尝试（前五次全部失败，值得记）

| # | 做法 | 结果 |
| --- | --- | --- |
| 1 | `reagentc /setreimage /path \\?\GLOBALROOT\…\partition5\Recovery\WindowsRE` | 返回 **183**「Windows RE 已经启用」；已启用时拒绝 |
| 2 | `/disable` → `/setreimage` → `/enable` | `setreimage` 成功、`enable` 成功，但 `/info` 仍报 **partition4** |
| 3 | 先搬文件，再 `/disable` + `/enable` | 同上，仍 partition4（`/enable` 把 wim 又铺回 C:） |
| 4 | 删 `C:\Recovery\WindowsRE\Winre.wim` + 删 `ReAgent.xml` 强制重新发现 | 仍 partition4 —— reagentc 认为「WinRE 就在 OS 卷上」 |
| 5 | 手改 `ReAgent.xml` 的 `WinreLocation offset` 指向 p5 | **无效**：`/info` 的位置不是从这个字段来的 |
| 6 | **改 BCD 恢复条目的 device**：`bcdedit /set {27468cac-…} device "ramdisk=[\Device\HarddiskVolume5]\Recovery\WindowsRE\Winre.wim,{devopt}"` | **成功**：`reagentc /info` 立刻报 `partition5` |

由此得到三条硬结论：

- **`reagentc /setreimage` 改的是「恢复映像」位置，不是 WinRE 本体位置**。`ReAgent.xml` 里 `ImageLocation` 会跟着变，`WinreLocation` 不变。
- **`reagentc /info` 的「位置」来自 BCD 恢复条目的 device**，不是 `ReAgent.xml` 的偏移（改偏移后 `/info` 纹丝不动）。
- **`bcdedit` 写 ramdisk 规格必须带方括号**：`ramdisk=[\Device\HarddiskVolumeN]\…`。不带方括号（写成 `ramdisk=\Device\HarddiskVolume5\…`）直接报「按规定设备无效」。产品代码 `boot_entry.rs:390` 用的正是带方括号的形式。

### 4.3 在 `/info = partition5` 的条件下实跑两次：零租约活动

环境：`reagentc /info` → `\\?\GLOBALROOT\device\harddisk0\partition5\Recovery\WindowsRE`（**p5 无盘符**）。

跑两次真实 prepare（`--operation backup --source-drive T --image-path H:\BRImages\_lease-r*.wim --compress fast --no-reboot`），各 ~30 s，均 `TASK_ID=…` 成功：

- `prepare.log` 里**没有** `drive letter R: held for the rest of this process`；
- **没有** `released temporary drive letter R:`；
- `C:\ProgramData\BackupRestore\logs\mount-leases.txt` **始终不存在**（说明 `register_lease` 从未被调用）；
- 前置 / 后置 `mountvol` 与 `HKLM\SYSTEM\MountedDevices` 的 `\DosDevices\*` **都是 6 条，完全一致**（C/D/H/F/T/S）——**没有留下也没有新增任何盘符**；
- 宿主侧每 2 s 轮询 `R:`，全程 `R_count=0`。

另外实测：`diskpart` 对该隐藏恢复分区 `assign letter=R` 被 VDS 拒绝（「指定的驱动器号对于分配不可用」），换 `assign letter=W` **成功** —— 所以不是「隐藏分区不能有盘符」，是 R 那个字母当时不可用。

### 4.4 结构性发现：`windows_prepare.rs:1228` 的 `hold_for_process()` 是死代码

顺读代码可以**证明**它不可能生效：

```
windows_prepare.rs:979   let recovery = recovery_identity()?;
windows_prepare.rs:1094  ensure_workspace_capacity(workspace, &recovery)?;   // ← 硬要求 recovery.drive_letter
windows_prepare.rs:3048      let recovery_letter = recovery.drive_letter
                                 .ok_or_else(|| err("Recovery volume has no drive letter"))?;
windows_prepare.rs:1227  let (recovery_letter, lease_recovery) = ensure_volume_mounted_leased(&recovery, 'R', …)?;
windows_prepare.rs:1228  lease_recovery.hold_for_process();
```

`ensure_workspace_capacity` 在**租约之前**执行，并且硬要求恢复卷**已经有盘符**（否则直接报错返回）。因此任何能走到 `:1227` 的运行，此刻恢复卷必有盘符 → `ensure_volume_mounted_leased` 走「复用既有盘符」分支 → `created=false` → `MountLease` 的 `letter` 为 `None` → `hold_for_process()` 空转。

也就是说：**这条路上不存在「字母逸出」，`hold_for_process` 是为一个到不了的状态准备的**。真正会逸出的分配在 `identity_from_diskpart`（`:3631` 的 `diskpart … assign letter=`）——那次分配**没有任何租约兜底**，这才是「送给」幽灵盘符的窗口。

### 4.5 仍未解的一环（如实记录，不装懂）

两次 prepare 都通过了 `ensure_workspace_capacity`（否则会以「Recovery volume has no drive letter」失败），说明恢复卷在那一刻**确实有盘符**；但宿主侧的 `mountvol` / `\DosDevices\*` 前后都没有任何新增字母，2 s 粒度的轮询也没抓到瞬时存在。三者对不上，说明**「哪个字母、什么时候分配的」还没有被观测到**。

下一步（新待办）：在 VM 内跑 100–250 ms 粒度采样器 + 在 `identity_from_diskpart` 前后加一次性日志，把「分配时刻 / 字母 / 是否被撤销」钉死。不要在没观测到之前改 1228。

## 5. 与 #141（2215 ramdisk 回落）的关系：只拿到一条硬事实

2215 的墓碑是「ramdisk 设备路径形式：原始件能进恢复环境、产品注入的三文件齐镜像必回落」。本轮**没有推进**这个未定因，但顺手钉了一条语法事实：`bcdedit` 的 ramdisk 规格**必须**写成 `ramdisk=[\Device\HarddiskVolumeN]\<路径>,{设备选项}`（方括号），否则报「按规定设备无效」；而 `/enum` **显示层会把设备路径规范化成 `[X:]`**（设备路径 `[\Device\HarddiskVolume5]` 显示成 `ramdisk=[R:]`）。**从回读分辨「盘符形式 vs 设备路径形式」是不可靠的** —— 这一点与 2215 的判定方法直接相关，下次查该案时必须换判据（查原始 BCD 元素，不看 `/enum` 文案）。

## 6. 本轮新增的环境事实（可复用）

1. **`prlctl exec "Windows 11" --starting-user Administrator …` 会静默返回空**（连试 3 次全空），去掉该参数立刻正常。空输出必须当「命令没跑」处理并换方式重试。
2. **本 VM 经 `prlctl exec` 读文件有可见性问题**：`Test-Path` 为真，但 `Get-Item` / `Copy-Item` 的后置校验报「找不到文件」；而 `dir` 与实际字节数证明文件已就位（709 MB / 712 MB 的 `Winre.wim` 都遇到过）。**判据要用 `dir` + 字节数/hash，不能用 cmdlet 的成败**。同源现象：往 FAT32 恢复分区拷 709 MB 文件「失败」，其实已经拷完。
3. **`reagentc /info` 的位置来自 BCD 恢复条目**（见 4.2），不是 `ReAgent.xml`。
4. **`bcdedit` 显示层会规范化设备路径**（见 §5）。
5. **PE 内存版 vs 硬盘版的 install 分支**由钩子字段 `mode` 决定；硬盘版会真的格式化目标分区，确认框由 `auto_install` 自动接受。测之前必须选一个**可以牺牲**的独立分区。

## 8. 教训

1. **「重启后看到启动菜单」不能作为「PE 没起来」的判据** —— 查 `ntbtlog.txt` 与 `winpeshl.log`。
2. **搬 WinRE 之前先读代码决定判据**：`reagentc` 的语义（setreimage ≠ 位置）不知道就会浪费 5 轮。
3. **结构上的矛盾要用代码证明，不要靠跑**：`ensure_workspace_capacity` 与 `:1227` 的先后顺序，读 10 行就能定论；而靠跑只得到「没日志」这种弱证据。
4. **删临时脚本前先 `git status`**：本轮用 `rm -f tools/win-clicker/_*.ps1` 误删了 **8 个已跟踪的历史脚本**，靠 `git checkout --` 才还原。仓库里 `_*.ps1` 既被 `.gitignore` 忽略、**也有历史文件是被跟踪的**，通配删除一定会踩。
