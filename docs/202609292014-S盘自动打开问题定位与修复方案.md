# S 盘反复自动打开且提示"不可访问"——问题定位与修复方案

## 一、结论摘要

codex 的**机制判断正确**（自动播放为临时盘符打开了文件夹窗口），但其引用的**注册表键名是错的**，且**没有找全挂载调用点**。

- codex 说：`StorageOnArrival=MSOpenFolder`
- 实机核对：`StorageOnArrival` 下只注册了 `MSStorageSense`；真正会开文件夹的是
  **`UnknownContentOnArrival → MSOpenFolder`**
- `MSOpenFolder` 处理器的定义：`InvokeProgID: Folder` / `InvokeVerb: open`
  —— 等价于"对新到达的卷执行 `Folder:open`"，这就是窗口的来源。
- codex 只引用了 [windows_prepare.rs:868](../crates/backuprestore-cli/src/windows_prepare.rs) 挂载、
  [:915](../crates/backuprestore-cli/src/windows_prepare.rs) 撤销这两处，并称"完成后撤销盘符"。
  实际上 Windows 侧还有 **[native_gui.rs:3976](../crates/backuprestore-cli/src/native_gui.rs) 和
  [:4689](../crates/backuprestore-cli/src/native_gui.rs) 两处 `mountvol S: /S` 挂载后从不卸载**。

## 二、实机测量证据（Windows 11 虚拟机，2026-09-29 20:00）

### 2.1 自动播放状态

| 注册表项 | 值 |
|---|---|
| `HKLM\...\AutoplayHandlers\EventHandlers\UnknownContentOnArrival` | **`MSOpenFolder=`** |
| `HKLM\...\AutoplayHandlers\EventHandlers\StorageOnArrival` | `MSStorageSense=`（codex 引用项，与本现象无关） |
| `HKLM\...\AutoplayHandlers\Handlers\MSOpenFolder` | `InvokeProgID=Folder`，`InvokeVerb=open` |
| `HKCU\...\Policies\Explorer\NoDriveTypeAutoRun` | `145`（0x91，默认值，仅禁用未知/远程/保留类型） |
| `HKLM\...\Policies\Explorer` | 不存在（无策略禁用自动播放） |

结论：**自动播放处于默认开启状态**，新到达卷会被判定为"未知内容"→ 打开文件夹窗口。
ESP 上只有 `EFI\` 和 `System Volume Information`，没有图片/音乐/视频，必然落到
`UnknownContentOnArrival`。ESP 上也没有 `autorun.inf`（已核对，38 个文件里没有），所以不是 AutoRun 路径。

### 2.2 进程会话差异（我的测量局限，须说明）

- `prlctl exec` 启动的进程运行在 **Session 0**（实测 `SessionId = 0`）
- 资源管理器 `explorer.exe` 运行在 **Session 1**

我在 Session 0 执行 `mountvol S: /S`，前后 `Get-Process explorer` 的 PID 与启动时间完全一致，
**没有新增 explorer 进程**。但这个阴性结果**不能否证**"程序运行时会弹窗"：
自动播放是交互会话内的 Shell 行为，会话 0 的进程触发的卷到达通知能否驱动 Session 1 的
Shell 属未验证项。真正运行时程序本身就在 Session 1（GUI 经 `ShellExecuteW` 提权启动），
所以用户看到的现象与注册表配置是一致的。

## 三、"不可访问"的成因

一次准备任务的时序：

1. 程序 `mountvol S: /S`（或 `mountvol Z: /S`）给 ESP 分配盘符
2. `UnknownContentOnArrival → MSOpenFolder` 弹出一个标题为 `S:\` 的文件夹窗口，内容正常（`EFI\`）
3. 程序用完立刻 `mountvol S: /D` **撤销盘符**
4. 那个已经打开的窗口此刻指向一个不存在的盘符 → 显示 **"S:\ 不可用 / 无法访问"**，且窗口不会自动关闭
5. 下一次准备任务又分配一次盘符 → 又弹一个窗口 → 又被卸载

"老是打开 S 盘 + 提示不可访问"完全由此解释。另外 GUI 侧 [native_gui.rs:3976](../crates/backuprestore-cli/src/native_gui.rs)、
[:4689](../crates/backuprestore-cli/src/native_gui.rs) 挂载后**不卸载**，所以那里弹窗后窗口内容一直是可读的，
直到重启或 `mountvol /R` 才变成"不可访问"——两种症状对应两条不同路径。

## 三·补、2026-09-29 21:0x 补测：`mountvol /S` 退出码不可信，"老是打开"的直接机制

在提权会话（计划任务 `/rl highest /it`，用户 `x`，SID 1000，High Mandatory Level）里逐盘符
实测 `mountvol`（证据 `.test-artifacts/elev-channel/mvwhy-result.txt`）：

| 盘符 | `/S` 退出码 | 紧随的 `/L` 回显 |
|---|---|---|
| `Z:` | **1（失败）** | `\\?\Volume{d08d796f-f082-4402-bdbb-a4a6a09ac53f}\` ← **其实挂上了** |
| `Y:` | 0（成功） | 同一个卷 `{d08d796f-…}` ← 已是挂载态，重复 `/S` 无事可做 |
| `X:` | 0 | 同一个卷 |
| `W:` | 0 | 同一个卷 |

结论：**`/S` 的退出码既出假阴性也出假阳性，完全不能用**。而旧代码
`efi_identity()` 正是信这个码：Z: 明明挂上了却因 `rc=1` 被判失败 → `continue` → 拿 Y:
再挂一次同一个卷 → 于是用户看到"又一次 S:/Z: 自动打开"。**这才是"老是打开"的直接机制**
（自动播放只负责"打开"，反复挂载负责"老是"）。

v1.8.0 已改：发起 `/S` 后不看退出码，改用 `/L` 是否回显卷路径来判定成功
（`mountvol_letter_shows_volume()`，配套单测
`mountvol_listing_reports_volume_presence_from_l_not_s_exit_code`）。

**同一轮实机跑通完整主路径**（不用 `--test-efi-drive`）：任务
`ddce302b-d1f1-4191-ad8b-1fae9cfd14d3` 日志第 2 行即
`capturing bcdedit.exe /store S:\EFI\Microsoft\Boot\BCD`，证明产品自己找到了 ESP 并成功
挂载/卸载；终态盘符只剩 `C D F H P T`（ESP 的临时盘符已正常卸掉），无残留。

> 附带的通道事实：`prlctl exec`（SYSTEM，Session 0）里 `mountvol /S` 会**挂起不返回**，
> 把 prlctl exec 通道堵死（只能 `prlctl reset` 恢复）；用户提权会话里同一命令正常。
> 后续凡要验 `mountvol` 或产品主路径，一律走计划任务提权通道。

## 五、关键技术前提的实测验证

### 5.1 已验证：`bcdedit` 接受卷 GUID 路径，无需盘符

实机命令（注意：Rust `Command::new` 不经 shell，无需任何转义）：

```
bcdedit.exe /store \\?\Volume{d08d796f-...}\EFI\Microsoft\Boot\BCD /enum {bootmgr}
```

输出正常，与 `mountvol S: /S` 后用 `/store S:\EFI\Microsoft\Boot\BCD` 的结果一致。
**"优先使用卷路径访问"这一修复方向在 bcdedit 上是成立的。**

### 5.2 必须验证的差异：`device` 字段的路径归一化

同一个 `{bootmgr}` 条目，两种打开方式显示不同：

| 打开方式 | `device` 显示 |
|---|---|
| 卷 GUID 路径 | `partition=\Device\HarddiskVolume2` |
| `S:` 盘符 | `partition=S:` |

实际存入的只能是一种，另一种必然是 bcdedit 的显示归一化。若写操作也做归一化，
卷路径方式可能把 ESP 的设备引用改写掉。**这是卷路径方案唯一的阻塞风险，必须先在
VM 里做写操作实验**（见第七节实验 E1）。

## 六、修复方案（分层，按优先级）

### 方案 A：卷 GUID 路径访问，彻底消除临时盘符（首选）

**目标：一次完整准备任务中，临时盘符挂载从 ≥3 次降到 0 次。**

改动点：

1. `snapshot_raw_bcd()`：路径从 `{letter}:\EFI\Microsoft\Boot\BCD` 改成
   `\\?\Volume{efi.volume_guid}\EFI\Microsoft\Boot\BCD`，删除整个
   `ensure_volume_mounted` + `mountvol /D` 块。Rust `std::fs::copy` /
   `sha256` 走 `CreateFileW`/`CopyFileExW`，均接受 verbatim 路径。
2. `rollback_boot_request()`：同上，`bcdedit /import` 与 `fs::copy` 都改用卷路径。
3. `efi_identity()`：不再用"分配盘符 → 读身份 → 卸盘符"来定位引导 ESP。
   改为：枚举 `FindFirstVolumeW` 卷 → 对每个 GUID 用 `QueryDosDeviceW(L"Volume{GUID}", ...)`
   反查设备路径 → 判断该卷是不是 ESP（partition type GUID `c12a7328-...` + FAT + 存在 `\EFI\Microsoft\Boot\BCD`），
   并用 `HKLM\SYSTEM\Setup\SystemPartition`（若存在）与 `bcdedit /enum firmware` 交叉校验。
   若系统里存在多个 ESP → 报错并要求 `--efi-drive`，绝不猜（保持现有代码的保守语义）。
4. `native_gui.rs:3976` / `4689`：把 `mountvol S: /S` + `std::fs::write("S:\pe-task.txt")`
   换成"先拿 ESP 卷 GUID，再用卷路径写文件"。GUI 需要一个 `esp_volume_path()` 辅助函数。
5. PE 侧 `7233 / 7640 / 7702`：同理，但 PE 里 `mountvol S: /S` 目前是最省事的入口，
   可放到第二阶段。

**收益**：不分配任何盘符 → 没有卷到达事件 → 没有自动播放 → 既不弹窗也不会"不可访问"，
同时省掉 `mountvol` 子进程、`volume_identity` 探测和 `PATH` 盘符漂移问题。

**残留盘符**：`main.rs` 给镜像卷（`R:` 等）分配的盘符由 `bcdedit` / `dism` 的路径语义决定，
也应当改写。但 `mount_volume_guid` / `identity_from_diskpart` / `verify_live_volume_identity`
这套校验链是为"盘符"设计的，改造量大，列为第二阶段（方案 A'）。

### 方案 B：目录挂载点代替盘符（A 的兜底）

用 `SetVolumeMountPointW(L"C:\\backuprestore-esp", L"\\\\?\\Volume{GUID}\\")` 把 ESP 挂到
NTFS 上的空目录，`bcdedit /store C:\backuprestore-esp\EFI\Microsoft\Boot\BCD`，
用完 `DeleteVolumeMountPointW`。

- 优点：不需要 5.2 验证通过，路径完全普通。
- 缺点：需要寄生在一个 NTFS 卷上并创建目录；进程崩溃会留下挂载点；PE 里没有可用 NTFS 目录；
  **目录挂载点是否触发自动播放未经验证**（不能假定不触发）。

### 方案 C：挂载期间临时抑制自动播放（B 的兜底，或与 A 并用）

挂载前把 `HKCU\...\AutoplayHandlers\EventHandlers\UnknownContentOnArrival` 的值改成
`MSTakeNoAction`，卸载后恢复原值 `MSOpenFolder`（并 `SendMessage(HWND_BROADCAST, WM_SETTINGCHANGE)`）。

- 缺点：改用户注册表；进程崩溃会留下"已禁用"状态；**改动是否对已经在运行的 Explorer 立即生效
  未经验证**。codex 说"关闭自动播放只能缓解现象"，这句是对的——它是兜底不是正解。

### 方案 D：让窗口内容不失效（治标）

把"用完立刻 `/D`"改成"进程退出前统一 `/D`"，并枚举 Shell 窗口（`IShellWindows`）关闭
指向该盘符的窗口。窗口内的内容始终有效，但每次仍会弹窗，只是不再显示"不可访问"。
**不推荐单独使用**，只作为已弹窗时的补偿动作。

### 建议组合

A（第五.1 节已验证可行）为主，把 5.2 作为 A 的前置门槛；
B/C/D 只在 A 的写路径被 5.2 否证后逐级启用。

## 八、顺带发现的其它问题（建议一并处理）

1. **ESP 已被开发日志污染**：`S:\` 根目录现有 **38 个 .txt/.log 文件共 93 KB**（`diag1-4.txt`、
   `bcd-*.txt`、`find-*.txt` 等，时间跨度 09-11 至 09-26）。ESP 是引导分区，且只有 100 MB 级，
   长期堆日志不合适。建议改为写到任务目录或卷路径下的 `BackupRestore\logs\` 而非 ESP 根。
2. **`exit_pe_to_windows()` 的盘符字符转换脆弱**：[native_gui.rs:5803](../crates/backuprestore-cli/src/native_gui.rs#L5803)
   `let bcd_path = format!("{}:\\EFI\\...", letter as u8 as char);` —— `letter` 是 `u16`，
   `as u8` 会静默截断（目前 `S..Z` 恰好 < 256，是偶然正确）。应改为 `char::from(letter)`。
3. **`native_gui.rs` 的 5 处 `mountvol S: /S` 从不卸载**：即便不做方案 A，也应至少在这几处
   用完 `mountvol S: /D`，这能立刻消掉"不可访问"那一半症状。
