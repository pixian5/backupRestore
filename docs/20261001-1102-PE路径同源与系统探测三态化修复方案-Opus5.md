## 一、摘要

本文解决一条**合成缺陷链**：PE（预安装环境）里"写一个探测文件、再读回来判断"这个模式有三层独立缺陷叠加，净效果是**系统卷格式化保护完全失效**、**还原后静默不修引导**、**自动点击验收通道整体失效**。

三层根因，分别由不同审计发现，必须合并修复：

| 层 | 根因 | 首次指出 |
|---|---|---|
| L1 | cmd 的 `>` 只绑定 `if/else` 的 else 分支，命中 `if exist` 时输出进 stdout 被丢弃，文件不生成 | [可能的问题claude5.md](可能的问题claude5.md) 第 1 条 |
| L2 | **写入路径与读回路径不是同一个路径**：命令里硬编码 `> S:\x.txt`（ESP 卷根），Rust 侧读 `esp_log_path(name)` → `S:\BackupRestore\logs\x.txt` | 本文（v1.8.1 回归） |
| L3 | `"NOSYS".contains("SYS")` 恒真，判据不具区分力；且探测失败与"非系统卷"没有分开 | [可能的问题GPT6.md](可能的问题GPT6.md) 第 14 项 A |

**修复顺序有硬约束**：单独修 L3 会把 `NOSYS` 判成系统卷，于是对**非系统卷执行 `bcdboot`**、改写本机真实 ESP 的 BCD（启动配置数据）——那是砖机方向，比现状更坏。必须 L1+L2 先行或同批。

另有一条在定决策时才浮现的事实（详见 WP2 的 2.2）：**现在"安装第二系统"可以格式化当前主系统卷**。该入口故意不带 `--allow-system` 来拒绝系统卷，但这个保护依赖上述失效的探测，因此等于不存在。修复时还必须把判据从"含 Windows hive"换成"是否 BCD `{default}` 卷"，否则会连带拒绝"重装第二系统到另一个 Windows 卷"这一合法场景。

### 2.1 回归来源

### 2.4 连带失效（本文独有）

**(a) `pe-click` 自动点击通道整体失效。** `pe-click.txt` / `pe-click.txt.done` 不在 `ESP_CONTROL_FILES` 白名单（该常量只有 3 个 `pe-task*`），而外部验收通道写的是 ESP 卷根（见 `20260913-1408-current-progress.md:314` 的 `prlctl ... echo main > S:\pe-click.txt`），程序读 `S:\BackupRestore\logs\pe-click.txt`（native_gui.rs:7304、7324，改名在 8052）。**自 v1.8.1 起所有"自动点击"验收不再触发**，PE 桌面照常显示，外部看不出异常。

影响评估：这使 `20260821-1528-verification-matrix.md` 里依赖 pe-click 的历史验收结论对 v1.8.1 之后的代码不再有效力。而 2.0.4 的实机闭环之所以仍然成功，是因为它走 `pe-task.txt` 通道——那个名字恰好在白名单里。

**(b) `AUTO` 盘符解析恒为空串。** `find-drive` / `find-system-drive` 读不到结果 → 写入 `pe-drive.txt` 的是空串（7517、7588、7681）→ `resolve_drive("AUTO")`（7249）返回空。后续：`format {空}` 被保护 1 的 `d_upper.is_empty()` 拦住（native_gui.rs:7688，这一条挡住了误格式化）；`restore {wim} {空}` 因参数数不足静默不匹配；`bcdboot {空} S` 退化成对 ESP 自身做检查。整条 AUTO 链**静默空转**，叠加"失败不阻断"（GPT6 第 4 项）后仍会弹"还原完成"并重启。

## 三、设计决策

**D1. 探测类动作改用 Rust 原生 API，不再经 cmd + 临时文件。**
这是本方案与前述两份审计建议的主要差别。claude5 已提到"直接别用 cmd 分支，在 Rust 里 `Path::is_file()` 判定"，本文把它确立为主方案：凡是"判断文件/目录是否存在、枚举盘符"的动作，一律在 Rust 里做。这一步同时消灭 L1、L2、L3 三层缺陷的产生条件，而不是逐层打补丁。受益动作：`format-check`、`bcdboot-check`、`find-drive`、`find-system`、`find-marker`、`verify-dir`、`dir-attached`。

**D2. 必须保留外部工具的动作（diskpart / dism / bcdedit / bcdboot），其输出文件落 PE 的 RAM 盘，不落 ESP。**
`rewrite_s_root` 在零盘符模式下会把 `> S:\x.txt` 改写成 `> \\?\Volume{GUID}\x.txt`，而 **cmd.exe 的重定向不解析 `\\?\` 前缀**——这是方案 A（v1.8.2 零盘符）在"命令输出重定向"这一类用法上的死角。方案 A 在 `bcdedit`/`dism`/Win32 API 上成立（有 v1.8.1 的实测证据），不能外推到 cmd 重定向。工具输出是会话内中间产物，无需跨重启留痕，放引导分区没有收益（v1.8.1 迁目录的动机正确，位置选错了）。代码已有三处先例：native_gui.rs:7498 `X:\attach-vhd.txt`、7710 `X:\pe-format.txt`、5801 `X:\exit-pe.log`。

**D3. 写一个文件再读回来时，路径必须由同一个函数产出。**
L2 的根因不是某条路径写错，而是写在命令字符串里、读在 Rust 里，两条代码路径各自演化。要让它结构上不可能再分叉。

**D4. 探测结果是三态：是 / 不是 / 探测未成功。**
未知态按调用方角色取安全默认——格式化取"拒绝"，引导修复取"跳过且记为失败"。

**D5. 跨环境、跨重启的控制通道与会话内输出分开治理。**
控制通道（`pe-task*`、`pe-click*`）要稳定、要两侧约定一致；会话内输出要就近、要可丢弃。两者混在 `esp_log_path` 一个函数里正是 L2 的温床。

## 四、工作包

### WP1：探测动作 Rust 化 + 输出文件同源（对应 L1、L2、第 15/16 项）

**可本机验证**（单测 + Windows ARM64 交叉构建）；PE 行为需实机确认。**必须先于 WP2。**

#### 1.1 新增探测函数（替代 cmd 分支）

```rust
/// 目标卷是否为 Windows 系统卷。三态：Rust 直接探文件，不经 cmd、不经中转文件。
/// NotSystem 要求父目录可访问；目录枚举失败（卷未就绪/权限/IO）必须报 Unknown，
/// 不能和"文件不存在"混为一谈——那正是保护失效的来源。
fn probe_system_volume(drive: char) -> SystemProbe   // System / NotSystem / Unknown
```

判据保持与现状一致，只是换实现：格式化检查看 `{d}:\Windows\System32\config\SYSTEM`；引导修复看该 hive **且** `{d}:\Windows\system32\winload.efi`（与 7734 的双条件一致）。

同步 Rust 化：`find-drive <marker>`（枚举 C..Z 找标记文件）、`find-system-drive`（枚举找 hive）、`find-marker`、`verify-dir` / `dir-attached`（`read_dir` 列目录）。每一步的枚举结果与失败原因都要进 `result` 文本，保持"PE 是离线环境、日志是唯一线索"的既有纪律。

#### 1.2 剩余命令输出统一落 RAM 盘

```rust
/// PE 会话内的命令输出目录（X: 是 PE 的 RAM 盘，恒存在可写）；
/// 非 PE 宿主退回 TEMP。返回纯盘符路径，调用方不得再对它做 rewrite_s_root。
fn pe_work_path(name: &str) -> String
```

适用：`format-out`、`bcdboot-out`、`bcdboot-def-before`、`bcdboot-after`、`bcdboot-restore`、`bcdboot-order`、`verify-bcd-enum`、`attach-vhd-out`、`pe-addsec-{create,set,order}`、`diag1~4`，以及本来同源的 `backup-out`、`restore-out`、`delete-out`、`verify-file-out`、`find-vhd`。

**注意**：`restore-out.txt` 同时是恢复进度窗口的数据源（native_gui.rs:7642 `recovery_progress::spawn`），迁移时两处必须同改，否则进度窗读不到 DISM 输出会停在 0%。

#### 1.3 `rewrite_s_root` 收窄

改完后它只用于命令里真正指向 ESP **内容**的路径（`S:\EFI\Microsoft\Boot\BCD`、`dir S:\`），调用点从 18 处降到 5 处左右。在其文档注释中写明"不得用于输出重定向目标"，把 D2 固化进代码。

#### 1.4 控制通道白名单补全

```rust
pub(crate) const ESP_CONTROL_FILES: [&str; 5] = [
    "pe-task.txt", "pe-task.txt.done", "pe-task-result.txt",
    "pe-click.txt", "pe-click.txt.done",   // ← 外部验收通道写 ESP 卷根

```

并把三处 `pe-click` 访问（7304、7324、8052）改为走 `pe_task_execute` 已在用的 ESP 卷根推导（7903-7920），而不是固定 `S:`。

#### 1.5 单元测试（macOS 可跑）

1. `probe_system_volume` 的三态：在临时目录造 `Windows/System32/config/SYSTEM` 与缺失两种结构（探测逻辑抽成接受根路径的纯函数以便测试）；父目录不可访问 → `Unknown`。
2. `esp_control_files_cover_every_cross_environment_channel`：5 个控制文件都返回根路径、不含 `logs`；用清单常量驱动，新增控制通道忘了加白名单就红。

4. `rewrite_s_root_must_not_touch_redirect_targets`：给一条含 `> X:\BackupRestore\format-check.txt` 的命令，断言改写后不变（把 D2 变成可执行约束）。

### WP2：系统卷判定三态化、判据升级与安全默认（对应 L3、GPT6 第 14 项 A）

**必须与 WP1 同批上线。**

#### 2.1 三态与安全默认

| 调用点 | `System` | `NotSystem` | `Unknown` |
|---|---|---|---|
| `format`（7700 一带） | 需 `--allow-system`，否则拒绝 | 放行 | **拒绝**，写明 `REFUSED: system probe inconclusive` |
| `bcdboot`（7739 一带） | 执行 | 跳过，记 `skipped: not a system volume` | **跳过并标记步骤失败**（交 WP3 阻断后续） |

`format` 的 `Unknown→拒绝` 比今天更严（今天读不到文件就放行），这是**有意收紧**。删除两处 `text.contains("SYS")`，留回归锁单测 `nosys_is_never_treated_as_system`，把 v2.0.5 的缺陷钉死。

#### 2.2 判据升级：`format` 的系统卷保护必须认"主系统卷"，不是"任何含 Windows 的卷"

这一条是定决策时发现的，**不加它，WP1+WP2 上线会引入功能回归**。

现状盘点——代码里 `format` 动作只有四个构造点：

| 构造点 | 场景 | 是否带 `--allow-system` |
|---|---|---|
| native_gui.rs:6804 / 6855 | `pe_restore_from_desktop`（还原系统，自动 + 交互） | **带** |
| native_gui.rs:6902 / 6954 | `pe_secondary_from_desktop`（安装第二系统，自动 + 交互） | **不带**（6953 注释写明"第二系统目标默认拒绝系统卷/ESP"） |

两个推论：

1. **今天这个保护等于不存在。** 探测恒 `false`（L1+L2），所以安装第二系统可以格式化任何卷，**包括当前主系统卷**——用户在 PE 桌面选错目标盘就会把主系统格式化掉，而流程还会继续 `restore` + `add-secondary-entry` 并报成功。这比本文第二节描述的影响更具体，是一条真实的数据丢失路径。
2. **直接修好探测会连带拒绝一个合法场景。** "把第二系统重装到另一个已有 Windows 的卷"（覆盖旧的第二系统）同样会读到 SYSTEM hive → 被判 `System` → 因不带 `--allow-system` 而拒绝。而这正是第二系统功能的常规用法。

根因是判据选错了：`secondary` 真正要拒绝的是**重启后会启动的那个卷**（主系统卷），而"含 Windows hive"对主系统卷和第二系统卷同样成立，不具区分力。

**方案**：`format` 判据分两层，`probe_system_volume` 的 hive 探测降级为日志信息，不再单独决定放行。

```rust
/// 目标卷是否就是 BCD {default} 指向的那个卷（即重启后会启动的卷）。
/// 读取失败/解析不出 partition= → Unknown，调用方按安全默认拒绝。
fn probe_boot_default_volume(drive: char) -> BootDefaultProbe  // Is / IsNot / Unknown
```

实现可直接复用现成代码：native_gui.rs:7747-7770 的 `bcdedit /store … /enum {default}` 调用与 `partition=X:` 解析（bcdboot 分支为了"修复前记录原默认卷"已经在做这件事），抽成函数两处共用。其输出文件按 WP1 的 D2 落 `pe_work_path`。

| 动作 | 目标 = BCD 默认卷 | 目标 ≠ BCD 默认卷 | 读取失败（Unknown） |
|---|---|---|---|
| `format … --allow-system`（还原系统） | 放行（语义就是要格式化它） | 放行 | 放行并告警（还原系统已有显式授权，不因 BCD 不可读而阻断续跑） |
| `format …`（第二系统，无授权） | **拒绝**：`REFUSED: target is the current boot default volume` | 放行（即使卷内有 Windows，支持重装第二系统） | **拒绝** |

`restore` 入口语义不变，继续显式带 `--allow-system`。保护 1（`X:` / `S:` / 空盘符一律拒绝，7688）保留。

#### 2.3 单测

除 2.1 的解析用例外，新增 `secondary_format_refuses_boot_default_volume_but_allows_other_windows_volume`：用注入的 `BootDefaultProbe` 覆盖三态 × 两种授权，锁住"主系统卷拒绝、另一个 Windows 卷放行"这组判定。

### WP3：PE 步骤结构化结果与失败阻断（对应 GPT6 第 4 项，利用第 5 项已有成果）

**可本机编译验证**；行为需实机。

不需要新造类型：`windows_command.rs:17` 的 `CmdOutcome` 已区分 `Exited / TimedOut / SpawnFailed / ExitCodeUnavailable / WaitFailed / ContainmentFailed / Skipped` 并带 `is_success()`，今天只是在 PE 捕获（7555）与应用（7648）两处被丢弃。

```rust
struct StepOutcome {
    action: String,              // 原始动作行
    command: Option<CmdOutcome>, // 真实命令结果；纯探测步骤为 None
    postcheck: PostCheck,        // Verified / Failed(原因) / NotApplicable
}
fn execute_pe_task_line(action: &str, result: &mut String, reboot: &mut bool) -> StepOutcome
```

- `format` 的后置检查不只看 diskpart 退出码：回读卷状态（NTFS、可访问、根目录为空）。退出码 0 但卷不可用 → `Failed`。
- `restore` 的后置检查：DISM 退出码 + 目标根存在 + 关键路径抽查。
- `TimedOut{terminated:false}` 与 `ContainmentFailed` 一律 `Failed`，且禁止后续任何写盘步骤（`windows_command` 已有 `CONTAINMENT_FAILED` 全局闸门，这里把它接到 PE 侧）。

三个调用方的阻断：

| 调用方 | 现状 | 改为 |
|---|---|---|
| `pe_restore_from_desktop` 交互分支（6855-6862） | 三步无条件连跑，之后必弹"还原完成" | 任一步失败即停，弹失败详情（失败步骤 + 原因），**不提供自动重启** |
| 同上自动点击分支（6803-6810） | 同上 + `exit_pe_to_windows` | 失败则留在 PE、结果落盘、不自动回 Windows |
| `pe_task_execute`（7928 循环） | 跑完全部行，失败也 `reboot`、也改名 `.done` | 首个失败即停；**不改名 `.done`**（保留现场可续跑）、不重启；结果写明第几行失败 |

`.done` 改名、"还原完成"弹窗、成功日志只能由一个统一成功判定函数产出，不许各分支自行判断。

**与第 5 项的衔接**：本包只做"结果被使用"。`600000` 毫秒上限本身属第 5 项，分两步走——先让超时可见且阻断（本包），再改等待策略（需大镜像长跑实测定值）。在那之前，十分钟超时至少不会被当成成功。

### WP4：任务通道写入对齐与失败不重启（对应第 19 项、第 10 项的一半）

**可本机编译验证**。本包几乎零设计风险——同一文件里已有正确范式。

`pe_reboot_to_pe`（native_gui.rs:4147）做对了两件事：用 `esp_volume_path_for_task()` 的 verbatim 卷路径写 `pe-task.txt`；且 `if code.is_success() && write_ok` 才重启。
`schedule_pe_task`（4947）两件都错：用 `esp_log_path("pe-task.txt")`（固定 `S:`，正常 Windows 下 S: 通常未挂载 → 写失败），且 `write_ok` 只进日志、照样 `bcdedit /set {bootmgr} bootsequence` 并重启。该函数 4959 一带的注释声称"用 verbatim 卷路径写，不挂 S:"，与实现不符——这类注释偏差本身就是缺陷来源。

```rust
/// 把 PE 任务写到 ESP 卷根（verbatim 卷路径，不挂盘符），写后回读比对内容。
/// 未确认写入成功时，调用方禁止武装 bootsequence、禁止重启。
fn write_pe_task_to_esp(task: &str) -> Result<PathBuf, String>
```

两个入口都调它；`schedule_pe_task` 改为写入失败即弹窗说明、不设 `bootsequence`、不重启。顺序固定为"先确认任务文件可读回，再武装"。

**并入第 10 项剩余一半**：`esp_volume_path_for_task`（windows_prepare.rs:1190）直接返回第一个无挂载点卷，不验 EFI 分区类型、不验 BCD 是否存在；而同文件的 `esp_identity_without_drive_letter` 两条判据都验。让前者复用后者的判据，多候选时报错而非取第一个。两函数的文档已声称"同一套判据"，现在只有后者真的在验。

### WP5：准备阶段排序与回滚（对应第 18 项，衔接第 7、11 项）

**需实机验证**；动启动项，按 AGENTS.md 每次变更前新建并核验快照，最多留最近 2 份。

#### 5.1 排序倒置（低成本、单向安全）

现状顺序 `arm_one_shot` → `write_transition(BootRequested)` → `write_status_env`，中间任一失败直接 `return Err` 且**不解除武装**（windows_prepare.rs:962-970）。两种中断后果不对称：

- 已写状态、未武装 → 下次开机不进 RE，用户重试即可（**安全**）
- 已武装、未写状态 → 下次开机进 RE，但 main.rs:811 的一致性检查只容忍 `task=Prepared` + `status=BootRequested` 这一个组合；撕裂成 `task=BootRequested` + `status=Prepared` 时被拒 → 反复进 RE 又被赶出来（**死局**）

故把持久化挪到武装之前。实施时须核实 `boot_entry::rearm` 的续跑判据不依赖"武装先于状态"（初判它比对载荷哈希，不依赖）。

#### 5.2 武装后失败一律回滚

把 `arm_one_shot` 之后的步骤包进作用域守卫：失败执行 `disarm` + `rollback_boot_request`，并把"回滚本身失败"持久化成可被下次准备识别的遗留事务记录。今天只有 `shutdown.exe` 失败那一条分支有回滚。

#### 5.3 结构方案（第 7 项，单独排期）

`write_transition`（backuprestore-core/src/lib.rs:1081）两次 `write_json_atomic`，无论怎么排序都有撕裂窗口。目标形态：**`task.json` 唯一权威，`status.json` 降为派生视图、不参与准入判断**；准入改为校验任务身份（task_id / operation / 载荷清单哈希）+ 阶段可达性，而不是比对两文件 stage 是否相等。此项完成后，第 8 项（恢复卷序列号硬依赖，main.rs:767 的 `mount_env_volume(..., "RECOVERY", 'R', ..., false)`）才有条件按"可信任务阶段"放行，否则只能继续用阶段白名单打补丁。

### WP6：目标身份单一来源（对应第 17 项，即第 1、2 项的执行层）

**需实机 + 测试盘**；唯一可能真正写错盘的一项，建议方案评审后再实施。

#### 6.1 问题的精确形式

- 格式化用**编号**选目标：`diskpart_format_script`（main.rs:2517）生成 `select disk N` / `select partition M`，编号来自任务持久化字段
- 复验用**盘符**读身份：`verify_partition_identity_after_format`（main.rs:2472）用 `volume_identity(letter)` 比 GUID
- 格式化前唯一的"解析"是 `resolve_volume_root`（main.rs:2462），它只是 `format!("{letter}:\\")`，**零核验**

结论：编号漂移导致 DiskPart 格错分区时，复验读的是盘符指向的（正确的）卷，GUID 比对通过——**误格式化检测不出来**。GPT6 第 1 项称"2.0.1 已补格式化前身份读取"，在核心还原链上不成立；claude5 第 4 条指出的 `verify_formatted_volume` 未接入核心链，与此处是同一片空白的两个侧面。

#### 6.2 编号必须是现场派生量

```rust
/// 以持久化的分区 GUID 为锚，现场反查磁盘号/分区号/盘符，三者必须自洽。
/// 任何一项不匹配、匹配到多个、或查询失败 → 拒绝；绝不回退到任务里的旧编号。
fn locate_target_now(expected: &VolumeIdentity, log: &Path) -> Result<ResolvedTarget, TaskError>
```

- 派生出本次的 `disk_number` / `partition_number` / `drive_letter`，再校验 `disk_guid`、`partition_type_guid`、`partition_offset`、`partition_size` 与任务记录一致。
- **格式化前**调用，用它派生的编号生成 DiskPart 脚本；**格式化后**复验用同一个 `ResolvedTarget`（而非重新按盘符查），并确认卷序列号已改变（证明格式化确实落在该分区）。
- 任务里的编号字段降级为诊断参考值，执行层不再信任。

#### 6.3 写盘前统一拒绝闸（第 1 项）

所有破坏性入口（核心链、PE 桌面、硬盘安装 PE）共用一次预检，先产出可审查的执行计划，确认后再执行，执行前再次核验身份：

| 检查 | 拒绝条件 |
|---|---|
| 镜像可用性 | 不存在 / DISM 不可读 / 指定索引不存在 |
| **镜像与目标同卷** | 镜像所在卷 == 目标卷（PE 桌面今天完全没查，会先把镜像和数据一起格式化） |
| 工作目录 / 载荷卷冲突 | 目标 == 当前 PE 载荷卷 / 任务工作卷 |
| ESP 冲突 | 目标分区类型为 EFI（按分区类型 GUID 判定，不看盘符是否 `S:`） |
| 容量 | 目标 < `max(required_target_size, source.partition_size)` |
| 身份 | 6.2 的现场定位失败 |

## 七、决策记录

原稿把三点留给用户，用户指示代为决定。以下为已定结论与依据，后续实施按此执行；若实机证据与依据冲突，回到本节重议而不是临场改判。

### 决策 1：采纳 `Unknown → 拒绝`，并同批做 2.2 的判据升级

**定：** `format` 探测未知时拒绝。**附加条件（不可拆）**：同批把第二系统入口的判据从"含 Windows hive"换成"是否 BCD `{default}` 卷"。

依据：

- 收紧的实际代价接近零。WP1 让探测改用 Rust 直接探文件后，`Unknown` 只在"卷根无法枚举"这类真异常时出现，那时本就不该写盘。
- 不收紧的代价是确定的数据丢失路径：现在安装第二系统能格式化主系统卷（见 2.2）。
- 但只收紧、不换判据，会把"重装第二系统到另一个 Windows 卷"一起拒掉。两件事必须同批，否则上线即回归。

### 决策 2：WP6 先只上 6.3 预检闸，6.2 单独排期

**定：** 本轮实施 6.3（写盘前统一拒绝闸），6.2（`locate_target_now`，以分区 GUID 为锚现场派生编号）另开轮次。

依据：

- 6.3 是纯增量检查，插在现有流程之前，不改 DiskPart 选择方式、不改任何既有成功路径的行为，可本机单测，实机风险低。
- 6.3 覆盖的是最可能真实发生的事故——"镜像在 `P:\backup.wim`，目标也选 `P:`"，PE 桌面今天完全没查，会先把镜像和数据一起格式化。这不需要盘符漂移这种罕见前提，是普通用户一次误选就能触发。
- 6.2 要改选目标的方式、依赖分区枚举查询，必须用测试盘覆盖盘符漂移/编号漂移/同标签不同 GUID 等场景才敢上，工程量与验证成本高一个量级。两者绑定会让更有价值的那半被拖住。
- **约束**：6.2 未落地期间，格式化前日志必须显式记录"磁盘号/分区号取自任务持久化字段，未经现场核验"，使事故可追溯；6.2 完成后删除该行。

### 决策 3：WP1 全面 Rust 化探测，不保留 cmd 探测

**定：** 探测动作（系统卷判定、盘符枚举、目录列举）全部改 Rust 原生 API。

依据：

- 双补丁方案要在 17 处字符串里逐个改对重定向与路径，每处都可能再错；且缺陷产生条件仍在——下一个人再写一条 cmd 探测，同样的坑会重现。本文第二节的回归正是这样产生的。
- Rust 化后不存在"中转文件"这个中间状态，L1/L2/L3 三层的产生条件一起消失，并且**能在 macOS 上写单测**。当前 PE 相关逻辑几乎无法本机测试，这是项目的结构性短板，本包顺带补一块。
- 唯一代价是"PE 里无法手工复现同一条 cmd"。用更好的方式替代：把探测结论连同判据路径写进 `result` 日志，例如 `probe C: -> System (found C:\Windows\System32\config\SYSTEM)`，比复现命令更直接。
- 判据本身不变（仍是同样的文件路径），不引入语义变化。

### 决策 4（附加）：第 0 步观测不单独占一次启动，并进 WP1 实机轮次

**定：** 取消独立的观测轮次。在 WP1 的同一次 PE 启动、同一个快照内，**先跑旧程序取"坏"的基线证据，再部署新程序验证**。

依据：静态证据已足够强（`git show 7613896` 能直接看到迁移只改读取侧），不值得为确认它再花一次启动与快照。但"修复前确实是坏的"这个对照有独立价值——否则修完无法证明修对了——所以把它放进同一轮次，用一次快照拿到前后两组证据。
