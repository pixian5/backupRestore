# G2 治本端到端实测：未完成任务真的不进镜像了（终态证据照样保留）

> 时间：2026-10-31 08:41（GMT+8） · 模型：Hy4 · 基线：v2.7.2 · 性质：**只做验证，未改任何代码**
> 结论：**治本生效**。非终态任务目录不进镜像；终态（success/failed）任务的证据照旧保留。
> 但先踩到一个更值得记的问题：**VM 里的部署件是"半成品"——有治标、没有治本。**

---

## 一、先说踩到的坑：部署件比修复提交早 4 分钟

第一次实测（用 VM 上现成的 `H:\brwork\BackupRestore.exe`）结果是**三个任务目录全进了镜像**，
包括两个本该被排除的非终态目录。差点判成"治本没生效"。

四份证据说明那不是产品问题，是**被测的二进制里根本没有这段代码**：

| 证据 | 实测值 |
|---|---|
| 部署件 mtime | `2026-10-30 22:36:43` |
| G2 提交时间（`a43387f`） | `2026-10-30 22:40:28` |
| 二进制里搜 G2 **治标**的日志文案 `boot entry no longer in BCD` | **有**（1 处） |
| 生成的排除表里有没有 `\brwork\tasks\...` 条目 | **没有**（只有 5 条自部署件排除） |

⇒ 结论：那个 exe 是"治标写完、已经部署；治本还没加"的中间态构建产物。
**用同一套夹具、换成带治本的新构建，行为立刻不同**（见下）。

★ 顺带一条工具经验：**在二进制里搜 Rust 的 `format!` 整串是搜不到的**——
`format!("\\{rel}\\tasks\\{name}")` 会被拆成 `"\\"` / `"\\tasks\\"` / `""` 三段常量存放。
我第一版搜 `tasks\{name}` 得到 0 命中，差点据此误判；要搜就该搜**片段**（`\tasks\`），
但片段会与别处的路径模板撞车（本次就搜到 2 处、其中之一属于任务目录路径拼接）。
**最可靠的版本判据还是 mtime 对照提交时间 + 一个该版本独有的子串。**

## 二、怎么测的（可复现）

| 环节 | 做法 |
|---|---|
| 源卷 | 2 GB **GPT** 动态 VHD（diskpart 建、NTFS、挂 `V:`）——排除逻辑只在**源卷 = 程序所在卷**时生效，而真实卷都是 80~250 GB |
| 程序 | 新构建的 `BackupRestore.exe` 放到 `V:\brwork\`（`exe_dir` 变成 `V:\brwork`，`rel` = `brwork`） |
| 夹具 | `V:\brwork\tasks\` 下三个目录，覆盖"没跑完"的三种形态 |
| 动作 | `V:\brwork\BackupRestore.exe online --operation backup --source-drive V --image-path H:\BRImages\g2-e2e.wim` |
| 判据 | ① 读本次真正传给 DISM 的排除表 `C:\Windows\SystemTemp\BackupRestore-exclusions.ini`；② `dism /Mount-Image /ReadOnly` 挂成品镜像，看目录与 CANARY 文件 |

三个夹具目录与预期：

| 目录 | `status.json` | 语义 | 预期 |
|---|---|---|---|
| `g2-running` | `{"stage":"capturing"}` | 明确非终态 | **排除** |
| `g2-finished` | `{"stage":"failed"}` | 终态（失败也是终态） | **保留**（证据） |
| `g2-nostatus` | 没有该文件 | 读不到 → 按非终态处理 | **排除** |

## 三、结果

排除表里（这两行就是判据的核心）：

```
INI \brwork\tasks\g2-nostatus
INI \brwork\tasks\g2-running
```

成品镜像（`/Index:3`，本轮是追加的第 3 个索引）挂载后的实际内容：

```
IN_IMAGE g2-finished
CANARY  \brwork\tasks\g2-finished\CANARY.txt
```

**四条都成立**：
1. 非终态 `g2-running` 不在镜像里 ✅
2. 无 `status.json` 的 `g2-nostatus` 不在镜像里 ✅
3. 终态 `g2-finished` **在**镜像里，连 CANARY 文件都在 ✅（"证据全留"没被破坏）
4. 同一套夹具换回"半成品"二进制时三个目录全在 —— 原缺陷可复现 ✅

> 附带观察：`g2-finished` 保留的代价是实打实的。真实任务目录里躺着
> `original\Winre.wim`(679 MB) + `stage\Winre.wim`(682 MB)，所以"少排一个非终态任务"
> ≈ 少进 1.4 GB 镜像体积——这就是治本省下来的东西。

## 四、这一轮又踩到的六个坑（都已记入 `经验/05`）

1. **PowerShell 5 的 `-Encoding UTF8` 会写 BOM**，而 `serde_json` 拒绝带 BOM 的 JSON →
   `task_stage_is_terminal` 读不到就当**非终态** → **连终态任务也被排除**。
   第一次跑出来的排除表是"三个目录全排"，我差点当成功。夹具要用
   `[System.IO.File]::WriteAllText($p,$t,(New-Object System.Text.UTF8Encoding($false)))`。
   ★ 顺带确认了产品的一个既有取舍：**读不到的 status.json 按非终态排除**（宁可少备份，
   也不把状态不明的东西烘进镜像）——这次正好把它测出来了。
2. **备份源卷必须是 GPT**：MBR 盘直接被拒，报 `selected disk is not GPT`（这条报错很清晰，值得表扬）。
   diskpart 新建盘默认是 MBR，要先 `convert gpt`。
3. **这台 VM 没有 Hyper-V 模块**（`New-VHD` 不存在），建 VHD 只能用 diskpart。
4. **`diskpart` 的 `assign letter=` 会留幽灵盘符**：`detach vdisk` 之后 `V:` 已经不存在，
   但注册表 `HKLM\SYSTEM\MountedDevices` 里 `\DosDevices\V:` 仍在（`reg query` 可见）。
   必须 `reg delete "HKLM\SYSTEM\MountedDevices" /v "\DosDevices\V:" /f` 清掉，否则以后会弹盘。
5. **只删 `.wim` 不删 sidecar 会让下一次运行静默失败**：剩下
   `g2-e2e.wim.index-N.metadata.json` 而镜像文件没了 → 下一次直接退出、**无任何输出、无日志目录**。
6. **"先 dism 卸载再跑备份"这个习惯本身会引入失败**：我两次在脚本开头无条件执行
   `dism /Unmount-Image /Discard`（当时并无挂载），随后的一次备份就以退出码 **50**
   （Win32 `ERROR_NOT_SUPPORTED`）**静默失败**；紧接着同一条命令、不做任何卸载，就成功了。
   未定位到根因，但形态很清楚：**静默退出 50 + 零输出 + 零日志**。
   ⇒ 判据/脚本里那句"清理挂载"应当改成**先 `/Get-MountedWimInfo` 确认真有挂载再卸**。
