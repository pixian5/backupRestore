## 二、本轮新发现的问题

严重度按「是否可能让用户以为成功、实际失败」或「是否可能损坏镜像」排序。

### P0-1 `run_cmd_to_file_timeout` 三重缺陷（`native_gui.rs:3127-3169`）

GUI 侧**所有**外部命令都走这个函数（diskpart、DISM、bcdedit）。

```rust
WaitForSingleObject(process.process, timeout_ms);   // 返回值被丢弃
let mut code: u32 = 0;
GetExitCodeProcess(process.process, &mut code);     // 返回值被丢弃
CloseHandle(process.thread);
CloseHandle(process.process);
code
```

1. **超时无法区分**：`WaitForSingleObject` 的返回值（`WAIT_OBJECT_0`=0 / `WAIT_TIMEOUT`=0x102 /
   `WAIT_FAILED`）被完全丢弃。超时时进程仍在运行，`GetExitCodeProcess` 返回
   `STILL_ACTIVE`(259)，于是「超时」被伪装成「进程退出码 259」。全项目无任何 259 处理。
2. **孤儿进程**：超时后不调用 `TerminateProcess` 就 `CloseHandle`。DISM/diskpart 继续在后台
   写目标卷，而 GUI 已经弹窗报失败。用户此时重试或删除镜像文件 = 两个写入者并发操作同一目标。
3. **`GetExitCodeProcess` 失败即伪报成功**：其返回值被丢弃，失败时 `code` 保持初始值 `0`，
   调用方一律按 `code == 0` 判成功。这与已修的 RE 清理缺陷是同一类。

对照：同文件 `native_gui.rs:4953` 的 `WaitForSingleObject` 就正确判了 `wait_result == 0`。

### P0-2 在线备份 10 分钟硬超时（`native_gui.rs:5200`）

```rust
let code = run_cmd_to_file_timeout(&command, Some(&out), 600000);
```

v1.8.19 实机记录：C: → F:\6.wim，32.47 GiB，**498 秒**。上限 600 秒，余量不到 20%。
再大一点的盘必然超时，叠加 P0-1 后的表现是：GUI 报失败 → DISM 仍在后台写 WIM → 用户看到
一个「失败」的、实际还在增长的镜像文件。

CLI 侧 `run_logged`（`main.rs:2673`）用 `child.wait()` 无超时等待，两条入口策略不一致。

### P0-3 在线备份/还原无防重入（`native_gui.rs:5248-5279`）

`run_online_operation` 只做 `std::thread::spawn`，不禁用按钮、无运行中标志
（全文件 `EnableWindow` 只用在模态对话框和另外两处，不覆盖此路径）。状态栏写
「已启动在线备份/还原（后台执行），完成后会弹出结果」，按钮仍可点。

- 重复点击 → 两个 DISM 并发写同一个 WIM 路径；`/Append-Image` 情形下是并发追加同一文件
- `*ONLINE_RESULT.lock().unwrap() = None` 会把第一个操作的结果直接丢掉

### P1-1 GUI 在线备份不维护 sidecar，破坏跨入口元数据契约（`native_gui.rs:5155-5240`）

CLI 备份路径对 `*.index-N.metadata.json`（sidecar）做了完整簿记：

- 追加后重写**全部**已有 sidecar 的 `image_sha256`/`image_size`（`main.rs:2177-2179`）
- `/Delete-Image` 后重编号 sidecar、重算 WIM 哈希并同步进所有 sidecar（`main.rs:2251-2293`），
  代码注释明写「否则后续 prepare 还原校验会报 hash mismatch」

GUI 的 `execute_online` 一处都不写（全文件无任何 metadata 写入）。后果：

| 场景 | 表现 |
|---|---|
| GUI 在线追加到 CLI 备份过的镜像 | 旧 sidecar 的 `image_size`/`sha256` 全部过期 |
| 之后从 GUI 还原 | 弹「备份档案与镜像不匹配（镜像可能被修改或损坏）」（`native_gui.rs:4643`）——**误报**，会训练用户习惯性点「仍要继续」 |
| 之后从 WinRE/CLI 还原 | 硬失败 `image hash does not match backup metadata`（`main.rs:1973`） |
| GUI 保留策略删过索引后 | sidecar 编号错位，`read_index_metadata` 的 `wim_index != index` 检查报错（`main.rs:561`） |

这条同时削弱了 v1.9.5 的「sidecar 毫秒级预览」：GUI 产出的镜像没有 sidecar，预览退化为全量哈希。

影响面不限于数据盘：在线路径的分流条件是「非当前活动系统」，**包含未运行的第二个 Windows 系统**
（`native_gui.rs:4833`）。也就是说用 GUI 在线备份第二系统，之后从 WinRE 还原它会因哈希校验
硬失败。且 GUI 只为 `wim-info`/`list-volumes`/`inspect-environment` 调用 CLI，备份从不走 CLI，
所以拿不到任何 sidecar 簿记。

### P1-2 在线备份缺回读校验（`native_gui.rs:5200`）

| 校验项 | CLI | GUI 在线 |
|---|---|---|
| 索引数核对 | 有（`WIM append did not create exactly one new index`, `main.rs:2111`） | 无 |
| SHA-256 | 有（`main.rs:2162`） | 无 |
| `/CheckIntegrity` | 有（`main.rs:2135`） | 无（capture 和 append 都没带） |

「备份成功」的唯一依据是 exit code，没有任何字节级证据。这与 `AGENTS.md` 里
「启动成功不等于备份还原成功」的原则相悖。

### P1-3 保留策略静默失效（`native_gui.rs:5213-5219`）

```rust
let count = rust_cli_output(&["wim-info", &params.image_path])
    .ok().and_then(|output| parse_wim_images(&output).ok())
    .map(|images| images.len())
    .unwrap_or(0);
if count <= keep as usize { break; }
```

`wim-info` 失败 ⇒ `count = 0` ⇒ `0 <= keep` ⇒ `break` ⇒ `removed = 0` ⇒ **不写任何告警**。
失败方向是安全的（不会误删），但用户以为「保留最近 N 个」生效了，实际没生效。

### P1-4 PE 硬盘安装的格式化无回读（`native_gui.rs:3885-3892`）

```rust
&format!("cmd /c diskpart /s \"{script_file}\" > NUL 2>&1"),
```

输出丢进 `NUL`，只判 `format_code != 0`，随后直接 `/Apply-Image` 到该分区。diskpart 脚本内
单条命令失败时进程退出码仍可能为 0，此时「格式化成功」没有任何证据，PE 会被展开到一个
未按预期格式化的分区上。

对照 CLI：格式化后有 `target_root.is_dir()` 检查 + `verify_partition_identity_after_format`
（`main.rs:2333-2337`）。项目已有「mountvol /S 退出码会说谎」（v1.8.0）的教训，以及
`classify_mountvol_output`（`text_parsing.rs:53`）这个「不信退出码、改看输出」的正确范例，
此处未套用。

### P2-1 在线操作全程无进度反馈（`native_gui.rs:5200`）

`text_parsing.rs:628`（`*const u8`, `c_int`）与 `native_gui.rs:378`（`*const i8`, `i32`）。

## 三、共性结论

P0/P1 全部集中在 **GUI 在线执行路径（`native_gui.rs` 的 `execute_online` 与
`run_cmd_to_file_timeout`）**。CLI/WinRE 路径的校验相当扎实——退出码之外还有索引数核对、
哈希、回读、分区身份复验、sidecar 簿记；GUI 在线路径基本只有 exit code 一道关，
且那道关本身因 P0-1 可能返回假 0。

这不是「又一个独立 bug」，而是**一整条入口没有套用项目已经确立的三条纪律**：

1. 不信外部命令退出码（已有 `classify_mountvol_output` 范例）
2. 写完必须回读（已有 `boot_cleanup::remove_staging` 范例）
3. 元数据簿记必须与镜像实际内容同步（已有 `main.rs:2251-2293` 范例）

## 四、建议修复顺序

1. **P0-1**：修 `run_cmd_to_file_timeout`——判 `WaitForSingleObject` 返回值、超时则
   `TerminateProcess`、`GetExitCodeProcess` 失败返回明确错误码而非 0。这一处修好，
   GUI 全部外部命令调用同时受益。
2. **P0-2 / P0-3**：在线备份改为无超时或按镜像大小估算；加运行中标志并禁用按钮。
3. **P1-1 / P1-2**：把 CLI 的 sidecar 簿记与回读校验抽到 core，GUI 在线路径复用，
   彻底消除「哪个入口备份的」差异。
4. **P1-3 / P1-4 / P2-1 / P2-2**：补告警、补格式化回读、接进度窗口、补 disarm 错误日志。
5. **P3-1**：合并 extern 声明。

建议第 3 步优先于第 4 步：跨入口元数据不一致会直接导致「GUI 备份的镜像在 WinRE 里还不了」，
这是功能性失效，不只是观测性问题。
