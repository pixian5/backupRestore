## 一、改造背景与目标

在方案二（B-2695）中，我们在 `recovery_progress.rs` 中引入了崩溃免疫互斥锁访问扩展 `SafeLock<T>`，消灭了该模块全部 42 处 Mutex unwrap。
为彻底消除系统级恢复工具在极端异常或锁毒化（PoisonError）场景下的级联 panic 风险，本轮对全仓代码进行了地毯式静态审计，目标：**生产代码（非 test / 非断言代码）`.unwrap()` 彻底清零，实现 100% 防御性容错与零 panic 免疫**。

## 三、修改明细

### 1. `native_gui/pe_desktop.rs`（8 处 Mutex unwrap 清零）
引入 `SafeLock`，在窗口过程 `window_proc_pe_dialog` 和对话框入口 `pe_dialog` 中，将所有：
- `PE_DLG_DEFAULTS.lock().unwrap()`
- `PE_DLG_VOLUMES.lock().unwrap()`
- `PE_DLG_OUT.lock().unwrap()`
全部替换为 `.safe_lock()`。当遭遇前置异常导致锁毒化时，自动解构恢复数据，保障 PE 环境下恢复界面绝对不崩溃。

### 2. `boot_menu.rs`（3 处 Mutex unwrap 清零）
引入 `SafeLock`，在引导方案会话 `BootMenuSession` 的关键方法中：
- `snapshot(&self)`：`self.state.safe_lock()`
- `edit(&self, ...)`：`self.state.safe_lock()`
- `freeze(&self)`：`self.state.safe_lock()`
即使先前的方案校验或原子写入遭遇不可预期的崩溃，状态提取与引导冻结操作依然可以安全执行，防止 BCD 回滚链路中断。

### 3. `pe_operation.rs`（1 处防御式解构）
在处理 `sidecar` 伴随元数据 NotFound 错误并尝试探测父目录时：
原代码：
```rust
fs::read_dir(sidecar.parent().unwrap())?;
```
优化后：
```rust
let parent = sidecar.parent().unwrap_or_else(|| Path::new("."));
fs::read_dir(parent)?;
```
消除了当 `sidecar` 为根目录或单个相对路径时 `parent()` 返回 `None` 导致的潜在 panic。

### 4. `online_operation.rs`（1 处盘符提取保护）
在解析盘符字符时：
原代码：
```rust
Ok(raw.chars().next().unwrap().to_ascii_uppercase())
```
优化后：
```rust
raw.chars()
    .next()
    .map(|c| c.to_ascii_uppercase())
    .ok_or_else(|| crate::err("invalid drive letter"))
```
避免依赖先验长度判断来假设 unwrap 成立，严格走标准 `Option::map` 与友好的错误抛出。
