# 修缺陷：「任务与证据」标签在 18 号字下被切（辅助窗口纳入矩阵后抓到的第一个真问题）

- 时间：2026-10-31 23:11
- 版本：**2.7.2 → 2.7.3**（改产品代码，按规矩 +0.0.1）
- 模型：Hy4

---

## 一、缺陷是怎么被发现的

同一天早些时候，我把四个辅助窗口（设置 / 备份文件管理 / 查看日志 / 任务与证据）接进了
`tools/gui-check` 的矩阵（见 `20261031-2227` 文档）。随后跑**完整矩阵**：

```
GUI_CHECK combos=40 clipped=0 overlaps=0 below=0 untipped=0 skipped=0 ...   ← 主窗口全绿
GUI_CHECK_AUX checked=16 clipped=1 overlaps=0 below=0 skipped=0            ← 第 13 项变红
RESULT=FAIL
```

唯一红的是：`aux font=18 lang=zh BackupRestoreTaskAdmin clipped=1`。

**这条缺陷在旧矩阵里永远不可能被发现** —— 旧矩阵只量主窗口 × 5 页签。
而它在菜单里一直点得到：把字号调到 18、语言选中文、点「刷新任务状态」就能看到。

## 二、根因

`task_admin_create_controls` 用**写死的基准像素**建控件：

```rust
create_control(hwnd, "STATIC", "", 0, 12, 14, 80, 20, ID_TASK_LABEL);   // ← 宽 80
```

而标签的内容在 `task_admin_reload` 里才写进去：`任务：{N} 个` / `Tasks: {N}`。

| 字号 | 文案 | 文字实测宽 | 控件宽 | 结果 |
|---|---|---|---|---|
| 14 号中文 | `任务：4 个` | 136 px | 160 px | 装得下 |
| **18 号中文** | `任务：4 个` | **176 px** | **160 px** | **切掉 16 px（8 基准像素）** |

判据原始输出：`w=160 text=176 slack=-16 CLIPPED relX=37`。

★ 这不是第一次：2.6.68 修过同一个标签的另一个形态 —— 零任务时文案是
「任务：0 个（尚无任务记录）」宽 156 px，被 80 px 的框切一半。那次的做法是**把文案改短**
（只留数字，说明挪到提示条）。**文案改短只解决那一次**；只要字号能变大，写死的宽度迟早再破。
这次把根因（固定宽度）修掉。

## 三、改法

标签宽度按**实测文本**算，下拉框跟着右移，**右边界保持 708 不变**：

```rust
let label_w = fit_width(&text, 80);          // 实测宽 + 12，下限 80
let combo_x = 12 + label_w + 4;
let combo_w = (708 - combo_x).max(320);      // 708 = 12 + 696，与详情框/提示条同一右边界
task_admin_place(label, 12, 14, label_w, 20);
task_admin_place(combo, combo_x, 10, combo_w, 240);
```

- `task_admin_place` 是新加的小工具：与 `create_control` 共用同一套 DPI 缩放
  （内部乘 `dpi::s()`），避免「一处乘了系数、一处没乘」的错位。用的是已有的 `MoveWindow`，
  没有新增 Win32 声明。
- 窗口自身尺寸不变（这个窗口刻意不可缩放）。
- 每次刷新（打开 / 点「刷新列表」）都会重算一次，任务数从 4 变成 100 也不会再切。

## 四、验证

| 项 | 2.7.2（修前） | 2.7.3（修后） |
|---|---|---|
| 18 号中文 标签宽 | 160 px（文字需 176） | **208 px**（文字 176，余 32） |
| 18 号中文 `SINGLE_LINE_CLIPPED` | **1** | **0**（`WORST_SLACK=32`） |
| 18 号中文 重叠 | 0（MIN_GAP=14） | 0（MIN_GAP=14） |
| 18 号中文 底边余 | 77 | 77 |
| 14 号中文 标签宽 | 160 px | 168 px（`fit_width` 的 +12 padding，+4 基准像素） |
| 14 号中文 裁切 / 重叠 | 0 / 0 | 0 / 0 |

部署：VM 内构建 `2.7.3`，`DEPLOYED SHA256=fb4e3e708a4ff3523d022cceaf61078650ac3d9f08f9c86956b955ca840597d0`，
四个文件逐个核对通过。`tools/gui-check/run.sh --quick` → `RESULT=PASS`（主窗口 + 4 个辅助窗口 + 错误码判据）。

## 五、这件事说明的

1. **判据的覆盖面本身就是判据的一部分**。同一份代码、同一套判据、只改了「量哪些窗口」，
   立刻多抓到一个用户可见的缺陷。此前的「全绿」没有任何问题——它只是**没量那里**。
2. **「文案改短」是治标**，写死的宽度才是根因。2.6.68 那次如果顺手把宽度改成实测，
   这次就不会有这份文档。
3. 辅助窗口只跑 12/18 两个极端档的判断是对的：14 号量不出来（装得下），18 号一量就红。

## 六、遗留

- 「任务与证据」窗口的其余控件（按钮 100/150/130/66 基准宽）**也是写死的**，
  目前 18 号中英文都装得下（余量 44~120），但同样是隐患；等哪天文案变长就会破。
  判据现在覆盖着它们，破了会立刻红，故本轮不改（避免无谓的重排与回归面）。
- PE 侧窗口（`BackupRestorePeDesktop` 等）仍未纳入矩阵。
