# 根因定位：克隆系统注册表里的绝对路径指向原卷，导致服务初始化崩溃

日期：2026-10-12 14:25
模型：GPT-5

## 结论

第二系统桌面起不来的根因：**镜像内注册表记录的绝对路径（`C:\...`）在还原到 E: 后仍然指向原卷 C:，
服务/组件去那些路径找文件时踩空，进程崩溃 → WerFault 循环 → 桌面无法加载。**

不是显示驱动问题，不是文件版本问题，不是 `dcdboot` 问题。

## 关键证据链

### 1. 崩溃的不只是图形进程（读 E: 的事件日志文件得到）

从 C: 上直接读 `E:\Windows\System32\winevt\Logs\Application.evtx`：

| 时间 | 崩溃进程 |
|---|---|
| 13:54:45 | `E:\Windows\system32\LogonUI.exe` |
| **13:55:45** | **`C:\ProgramData\Microsoft\Windows Defender\Platform\4.18.26080.4-0\MsMpEng.exe`** |
| **13:55:50** | **`E:\Windows\System32\svchost.exe`** |

**注意 `MsMpEng.exe` 的路径在 `C:\ProgramData\...`——C: 盘的路径，但进程跑在 E: 系统上。**

### 2. E: 的注册表里全是 C: 硬编码路径

挂载 E: 的 SOFTWARE hive 后：

```
HKLM\E_SOFT\Microsoft\Windows Defender
    LastKnownGoodPlatformLocation = C:\ProgramData\Microsoft\Windows Defender\Platform\4.18.26070.9-0
    SignatureLocation             = C:\ProgramData\Microsoft\Windows Defender\Definition Updates\{...}
    CacheFile                     = C:\ProgramData\...\CacheManager\{FD0A50CF-...}.bin
                                    ↑ FD0A50CF 正是 E: 自己的卷 GUID，
                                      说明这些路径是"从 C: 克隆来的"，本该随卷走却没走
```

### 3. 注册表状态与实际文件状态脱节

```
C:\ProgramData\...\Platform\  →  4.18.26070.9-0 / 4.18.26080.3-0 / 4.18.26080.4-0
E:\ProgramData\...\Platform\  →  4.18.26070.9-0 / 4.18.26080.3-0 / 4.18.26080.4-0
                                 ↑ 两边文件完全一致

E: 注册表 LastKnownGood = 4.18.26070.9-0   （旧的）
崩溃时实际加载         = 4.18.26080.4-0   （新的）
                                ↑ 对不上 → 初始化失败
```

## 为什么安全模式下也崩（推翻了"显示驱动"假设）

设`safeboot minimal` 后重启：**安全模式不加载图形子系统，`dwm.exe` 根本不启动，
但 WerFault 照样崩**。这直接证明崩溃源不在显示栈，而在系统服务/组件层。

（`safeboot` 标记已用 `bcdedit /deletevalue ... safeboot` 清除，BCD 已复原。）

## 已排除的错误方向（避免以后重走）

| 假设 | 排除依据 |
|---|---|
| 显示驱动没加载 | `Enum\ROOT` 16 项与 C: **完全一致**；DriverStore 两边都有 `prl_dd.inf_arm64_*`；服务配置 `Start=3` `Type=1` 正常 |
| `dwm.exe` 文件版本旧（26100.1 vs 8875） | **sha256 完全相同**（`9F48F96C…`）。版本号差异只是 26200 servicing 改写了版本资源，是红鲱鱼 |
| 设备枚举缺失 | 我第一次只 grep 出一项是**自己的过滤条件写窄了**，完整对比后两边 16 项全在 |
| 引导项错误 | `default`/`resume_object`/`displayorder` 三项经 `bcdedit` 独立核验正确，且能引导进内核 |

## 技术定性

这是 **sysprep 泛化（generalization）缺失**的典型症状。

微软的标准做法：把系统镜像部署到**新机器/新卷**后，跑 `sysprep /generalize` 清掉
机器身份（MachineGuid、SID、硬件枚举、注册表里的绝对路径），首次启动走 OOBE 重新生成。

我们的代码里 `sysprep` / `generalize` / `OOBE` **零命中**——STEP 4 只做了
`bcdboot` + 三行 BCD 设置，没有做任何克隆后的身份/路径处理。

## 修复方向（待用户拍板）

| 方案 | 做法 | 代价 |
|---|---|---|
| A. 还原后跑 `sysprep /generalize` | STEP 4 之后执行，让系统下次启动走 OOBE 重新生成身份 | 目标系统首次启动会进 OOBE（需用户手动设账号），不再自动继承原用户 |
| B. 还原后跑 `sysprep /oobe` | 只重置 OOBE 不泛化 | 同样要走 OOBE |
| C. 路径重写 | 扫描并修正注册表/服务里的 `C:\` 绝对路径 | 极其脆弱，服务众多，改不干净 |
| D. 保持现状 + 文档说明 | 明确"在线还原到第二卷后需手动处理身份" | 产品能力有缺口 |

**我的判断**：A 是微软认可的标准流程，但会改变"还原后能否直接用"的语义——
需要用户决定这个产品是否应该强制 OOBE。

## 附带确认：克隆身份重复

| 项 | 值（C: 与 E: 一致） |
|---|---|
| 计算机名 | `P8B6` |
| MachineGuid | `4fe3367d-c159-4294-95fa-6efd8da1b82c` |
| SID | `S-1-5-21-1971337861-2157081999-741701442-1000` |
| SetupType | `0x0`（两边都是已完成安装，E: 无泛化标记） |

两系统身份完全重复，这在 Windows 上是已知冲突源（DPAPI、证书存储、驱动绑定等）。
