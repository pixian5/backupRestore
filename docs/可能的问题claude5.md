## 零、先说结论

主干设计扎实：卷 GUID 身份而非盘符、载荷四件套哈希、原子写、阶段状态机、破坏性操作前先落可续跑状态、`boot_cleanup` 的"删完回读"。这些不需要再动。

问题集中在**三类**：

1. **分支条件取自"探测结果"而不是"任务意图"** —— 于是失败被吸收成另一种"正常情况"并判成功（第 1、2 条）。
2. **"损坏"被当成"缺失"** —— 于是本该硬失败的场景降级成"跳过校验继续"（第 3 条）。
3. **同一纪律只落在部分入口** —— 包括我上一轮自己留下的两处不一致：新建的进程树约束没接到 RE 路径，新建的格式化复验没接到核心还原路径（第 4、8 条）。

共 17 项，其中 3 项我判为 P0。

## 一、P0：PE 系统卷保护在"真的是系统卷"时失效

`native_gui.rs:7695,7701`（格式化）与 `:7734,7740`（引导修复）。两个缺陷叠加：

```rust
"cmd /c if exist {d}:\\Windows\\System32\\Config\\SYSTEM (echo SYS) else (echo NOSYS) > S:\\format-check.txt"
...
is_system = text.contains("SYS");
```

- **历史归因待核验：重定向的分支作用范围。** 原审计把它判为仅绑定 `else`，但未提供对应 Windows 版本的复现实录，不能当成已证实根因。当前另有静态可确认的输出写读路径不一致，详见第 16.1 节和已有 PE 路径方案；新实现取消这类命令解释器探测。
- **`"NOSYS".contains("SYS")` 为真**。子串判定对两种结果都成立，这个判据本身不具区分力。

以下是原报告在“读写同一文件、重定向按原假设工作”前提下的推断表，**不作为当前代码已复现的行为表**；实际路径不一致时应另行分析：

| 目标卷 | 文件状态 | `is_system` | 结果 |
|---|---|---|---|
| 系统卷 | 不生成（首次） | `false` | **无需 `--allow-system` 就格式化系统卷** |
| 系统卷 | 上一轮残留 | 取决于陈旧内容 | 行为由历史文件决定 |
| 非系统卷 | 写入 `NOSYS` | `true`（子串命中） | 过度拒绝，需要 `--allow-system` |

`bcdboot` 处同形，后果是**静默跳过引导修复**：还原完的系统卷不会被修引导，而任务不报错。

修法以 W01 为准：原生探测保留 I/O 错误并返回三态，路径同源、失败即停。仅改 `contains` 或改成 `Path::is_file()` 都不足以覆盖访问失败。

## 二、P0：还原"无 SYSTEM hive"被当成数据卷还原并判成功

`main.rs:2320-2409`。分支条件是**对结果的探测**：

```rust
if matches!(task.status, Stage::ImageApplied | Stage::BootRepaired)
    && target_root.join("Windows").join("System32\\config\\SYSTEM").is_file()
{ /* 修引导 */ } else if matches!(...) {
    append_log(log, "data-volume restore: target has no SYSTEM hive; skipping BCDBoot")?;
    store.write_transition(task, Stage::Success)?;   // ← 判成功
}
```

关键：`TargetRole` 只有两个取值（`lib.rs:346-349`），且**完全由操作类型决定**（`windows_prepare.rs:698-702`：`CreateSecondary → NewWindows`，其余 `→ ExistingWindows`），与"目标是不是数据卷"毫无关系。所以这条 `else` 分支不是在服务某个合法的"数据卷还原"任务类型，而是在吸收"apply 没产出 Windows"这件事。

叠加分流规则后影响面更大：GUI 把非当前活动系统的卷全部分流到在线路径（`native_gui.rs:4758-4772`），所以 **WinRE 还原路径基本只用于系统卷**。在这条路径上"目标没有 SYSTEM hive"几乎只有一个含义——系统还原没成。现在的处置是写 `Stage::Success` 并重启，用户看到"成功"，机器起不来。`create-secondary` 同样落进这条分支。

修法：需要一个"这个镜像本该含 Windows"的权威信号，而不是探测结果。可用的最低成本方案是在 `prepare` 阶段（此时目标卷上的旧 Windows 还在）探测一次并记进 `TargetSpec`，apply 后据此断言；镜像侧另一个可选信号是在捕获时把"源卷含 Windows"写进副档。

## 三、P0：副档"损坏"被当成"不存在"，连带跳过目标容量预检

两处：

- `windows_prepare.rs:1462`：`let metadata = crate::read_index_metadata(...).ok();`
- `main.rs:1969`：`if let Ok(metadata) = read_index_metadata(path, image.index) {`

`read_index_metadata` 的失败原因至少有三种：文件不存在、JSON 损坏、`wim_index` 与请求索引不符。这两处把三者压成一个 `None`。而 core 的 `load_sidecars`（`image_metadata.rs:41-62`）恰恰明确区分过"缺失跳过、损坏硬错"——纪律在，没落到这里。

"缺失即视为第三方 WIM 并跳过校验"是**有意设计**（注释写明），所以问题不在跳过本身，而在**损坏也走同一条路**。后果链条完整：

```
副档 JSON 损坏/索引错位
  → metadata = None
  → minimum = 0（windows_prepare.rs:1476-1486）
  → 目标容量预检等于不存在
  → 格式化目标卷（旧系统此刻已被擦除）
  → DISM apply 中途空间不足失败
  → 任务 Failed，但旧系统已经没了
```

容量预检存在的全部意义就是阻止这条链，吞掉损坏正好让它失效。

GUI 侧同一问题还多一层：`native_gui.rs:4563` 用 `metadata_check.is_err()` 统一判定，`:4584` 的文案写死"未在此镜像旁找到备份档案文件（可能被移动或删除）"。副档明明在、只是坏了的时候，这句话是**事实错误**，而对话框默认引导用户点"仍要继续"。

## 四、P1：格式化回读弱于项目自有标准（我上轮留下的不一致）

`main.rs:2472-2514` 的 `verify_partition_identity_after_format` 比对磁盘/分区 GUID、分区类型、磁盘号、分区号、偏移、大小——**不查文件系统，不查卷序列号是否变化**。

这组比对能证明"还是那个分区"，但证明不了"真的被擦了"。而 diskpart 脚本内单条命令失败时进程退出码仍可能为 0，项目已经有"mountvol 退出码会说谎"的教训（v1.8.0）。于是一次什么都没做的"格式化"可以完整通过。

更直接的问题是：上一轮我新建的 `operation_safety::verify_formatted_volume`（要求 NTFS + 卷序列号必须变化，`operation_safety.rs:29-45`）**只接到了 GUI 的 PE 安装路径**（`native_gui.rs:3826`），核心还原路径没用上。强校验写好了却没接到最需要它的地方，这是我的疏漏。

顺带一个佐证：`mount_env_volume` 在续跑时显式传 `reformatted_ok=true` 容忍序列号变化（`main.rs:868-874`），说明"格式化后序列号会变"是项目已知事实——那它就能当正向证据用。

## 五、P1：BCD 回滚的目标存储是隐式的

`main.rs:1846` 与 `:1859`。两处都已经算出并（在复制分支里）校验过 `efi_store`，但 `/import` 不带 `/store`：

```rust
Err(error) if error.raw_os_error() == Some(32) => {   // ESP BCD 被占用
    run_logged("bcdedit.exe", &["/import", &snapshot_arg], log)?;
    append_log(log, "Raw EFI BCD restore was locked; imported the saved BCD snapshot")?;
}
```

不带 `/store` 时 bcdedit 作用于默认存储。WinRE 里默认存储不保证就是刚校验过的那个 ESP BCD（这段代码自己要把 ESP 挂到 Z: 才能访问它）。锁定回退分支尤其可疑：ESP BCD 正被占用说明它打不开，若 import 落到另一个未被占用的存储，bcdedit 返回 0，日志照样写"imported the saved BCD snapshot"——**回滚伪报成功，而这是引导修复已经失败后的最后一道兜底**。

**设计校准：撤回“只需补 `/store`”的建议。** 微软文档说明 `/import` 仅适用于系统存储，不能作为任意离线存储的导入方式；正常 Windows 下也要证明目标确为系统存储。当前可确认的缺口是回退没有证明操作目标与快照匹配；具体是否导入了错误存储需环境证据，不能仅凭在 WinRE 运行就断言。正确方案见 W05。

## 六、P1：状态双写撕裂，续跑静默放弃

`lib.rs:1081-1090`：

```rust
let status = task.transition(next)?;
write_json_atomic(self.task_path(...)?, task)?;      // 第一次写
write_json_atomic(self.status_path(...)?, &status)?;  // 第二次写
```

两次各自原子，合起来不是事务。断电落在中间 → `task.status = next` 而 `status.stage = 上一阶段`。

- `resume_pending_boot_task`（`main.rs:375-380`）要求 `status.stage == task.status`，不等则 `if` 不成立 → **既不入 pending 也不写任何日志**，`pending.is_empty()` → `Ok(false)` → GUI 正常启动，用户什么也看不到。此时自建 BCD 对象和镜像卷上的载荷 WIM（约 700MB）无人清理。
- `recover_env`（`main.rs:809-815`）只放行 `Prepared → BootRequested` 这一种偏差，其余直接 `Err("status.json stage does not match task.json")`，任务卡死需人工介入。

最小改法：撕裂窗口消不掉，但"发现撕裂"必须留痕——续跑扫描里给这个分支补一条日志；进一步可让 stage 只存单一权威文件，status.json 退化为派生视图。

## 七、P1：准备失败不清理已建的 BCD 对象与载荷

`windows_prepare.rs:744-750`：

```rust
let result = prepare_payload(...);
if let Err(error) = result {
    if task_dir.exists() {
        let _ = store.write_failure(&mut task, 1, error.to_string());
        let _ = append_log(&prepare_log, &format!("Preparation failed: {error}"));
    }
    return Err(error);
}
```

`create_entry` 按设计跑在 DISM 注入**之前**（`windows_prepare.rs:946` 注释说明顺序要点）。因此注入、`refresh_payload_hash`、`arm_one_shot` 任一失败时，loader + devopts 两个 BCD 对象和镜像卷上的 `BackupRestoreRE\Winre.wim` 都已存在，而这里只写 failure，不 `disarm`。多次失败可能累积启动对象；同卷固定载荷路径还可能被另一任务覆盖，不应笼统说成每任务独立增加一份 WIM。

失败既可能发生在武装前，也可能发生在武装后；前者主要留下资源，后者还需对账一次性启动请求，不能统一判为“没有启动风险”。另外两处 `let _ =` 把 `write_failure` 和日志的错误也吞了：`write_failure` 失败时任务停在中间阶段，可能被续跑扫描捡起来。

## 八、P1：恢复与准备路径的外部命令没有超时，也没有进程树约束（我上轮留下的不一致）

`main.rs:2596-2630` 的 `run_logged` 用 `child.wait()`，无超时；`:2633-2650` 的 `capture_logged` 用 `.output()`，同样无超时。两者都不进作业对象。

DISM 挂载/提交、bcdedit、diskpart、shutdown、reagentc 任一挂住，准备或恢复就永久卡住。WinRE 里没有用户能介入，进度窗口停在某个阶段（它只读日志增量），只能硬复位。

上一轮新建的 `windows_command` 还未覆盖核心准备/恢复主链。需要补齐的是可管理的生命周期、取消、证据和按命令类别设置时限；**无输出不等于挂死，不能用静默时限自动误杀长写盘操作**。执行器迁移也不只是换一个函数名，详见 W08。

## 九、P1：`recover` 独立命令缺少 `recover_env` 的全部闸门

`main.rs:612-685`。与 `recover_env` 逐项对比，`recover` 不做：载荷清单校验（`validate_payload_files`）、运行中二进制自校验（`verify_running_recovery_binary`）、身份 env 核对（`verify_task_identity_env`）、payload task 与 workspace task 比对、`status.json` 与 `task.json` 一致性检查、终态 `finalize_boot_entry_after_task`。

却传 `finalize_success = true`，于是可以在**留着启动残留**的情况下把任务写成 `Success`。它是运维/开发命令（`usage()` 里有），但判成功的权力和 `recover_env` 一样大，闸门不该差这么多。

## 十、P1：`capture_logged` 绕过项目自有的控制台解码层

`main.rs:2641-2642` 直接 `String::from_utf8_lossy`，不走 `text_parsing::decode_windows_bytes` / `plan_console_bytes`——而项目正是为了中文 WinRE 的 GBK/UTF-16 输出才写了那一层（`recovery_progress.rs:261` 在用）。

两个后果：

1. 中文 WinRE 下 DISM/bcdedit 的中文输出在恢复日志里变乱码，可诊断性下降。
2. `verify_bcd_target`（`main.rs:2950`）通过它读 `bcdedit /enum`，其中匹配中文标签 `"设备"` / `"os 设备"`（`:2959-2960`）的分支在乱码下**不可能命中**。英文标签在已验证的镜像上可用，所以 v1.9.4 实机通过了——但本地化分支实际是死代码，这类"测试全绿掩盖半边失效"值得单独记一笔。

## 十二、不构成缺陷的几项（已核对，避免误修）

- **`ramdisk=[F:]\...` 用盘符**（`text_parsing.rs:896`、`boot_entry.rs:345`）：bcdedit 在 `/set` 时就把盘符解析成分区设备对象存入 BCD，存的不是字母，盘符重排不影响启动。回读比对也在同一上下文完成。**不是缺陷。**
- **`verify_hash=false` 时不比对副档哈希**（`main.rs:1970`）：`prepare` 在副档存在时直接把副档哈希抄进 `task.image.sha256`（`windows_prepare.rs:679-681`），所以这一行的比对本身是恒等式，**不是漏检**。
  但要注意同一机制的另一侧确实有缺口，已由并行复核记录：用户勾选严格哈希又选择"强制继续"时，`force_restore_hash` 只在准备阶段放行，任务里只存了 `verify_hash=true` 而没存这次例外，离线阶段用抄来的旧副档哈希再校验一次仍会拒绝（见 [可能的问题GPT6.md](可能的问题GPT6.md) 第 13 项）。本文不重复该项。
- **`/import` 的适用范围需重新限定**：系统存储导入是受支持功能，但“当前系统存储等于预期 ESP 存储”仍需证明；不能对正常 Windows 路径无条件否证风险，也不能对 WinRE 路径直接补 `/store`。见第 16.1 节和 W05。

## 十三、建议处理顺序

1. **第 1、2、3 条**：都是"失败被吸收成成功"或"保护在关键方向失效"，且改动面小、不涉及架构。
2. **第 4、8 条**：把上一轮已经写好并测过的 `verify_formatted_volume` 和 `windows_command` 接到核心还原/准备路径。基础机制可复用，但接口、取消/回读和恢复状态仍需按 W04/W08 补全，不能仅替换调用点。
3. **第 5、6、7、9 条**：异常与回滚分支，优先补"失败必须留痕"，再谈事务性。

### 16.3 每条入口共同遵守的六条约束

1. **先证实输入、目标和授权，再执行不可逆写入**；选择了一个盘符不等于确认了物理分区。
2. **先持久化操作意图，再执行外部动作，最后持久化回读证据**；“准备执行”与“已经完成”不可混用。
3. **外部命令退出、阶段完成、整轮完成、系统成功启动是四件不同的事**，分别记录。
4. **失败不可降级成别的任务类型**；未知、缺失、损坏、拒绝访问是不同状态。
5. **只能清理本任务拥有的对象**；既不删除其他任务的恢复载荷，也不覆盖用户后来修改的启动配置。
6. **恢复旧数据不是任何失败都能自动做到**。已经格式化的系统卷不能靠“回滚 BCD”恢复旧文件，日志和界面必须如实说明。

## 十七、共用契约与数据模型

以下名称是拟新增/调整的接口，不表示代码已经存在。先把协议放在核心库，Windows API（系统接口）留在平台层，三个入口只负责收集意图和展示结果。

### 17.1 任务意图与内容证据

| 字段/类型 | 内容 | 约束 |
|---|---|---|
| `RestoreIntent`（还原意图） | `SystemReplace` 系统替换、`SecondaryInstall` 第二系统、`DataOverlay` 数据覆盖、`PeInstall` 恢复环境安装 | 不由应用后的探测结果推断；未支持的模式明确拒绝 |
| `TargetMode`（目标处理方式） | 格式化后应用 / 不格式化覆盖 | 组合必须与意图一致；若以后支持数据卷清空还原，单独加模式与确认，不偷偷改变现有覆盖语义 |
| `ContentEvidence`（镜像内容证据） | 所选索引、源内容类型、关键路径、架构、证据来源及可信范围 | 有效副档可提供线索；第三方镜像必须实际检查，不能只凭镜像名称 |
| `DestructiveConsent`（破坏性确认） | 任务 ID、目标稳定身份、所选镜像/索引、操作模式、允许覆盖范围、确认时间 | 任一绑定条件改变，旧确认失效；授权覆盖系统不等于授权忽略身份或容量未知 |
| `ProtectedVolumes`（受保护卷集合） | 当前运行系统、任务定义的主系统、ESP（EFI 系统分区）、镜像卷、工作区、当前执行载荷所在卷等 | 是否允许目标与某个角色重合由操作矩阵决定，不能靠盘符黑名单 |

系统镜像的后置条件最少包含：所选索引应用完成、必要注册表配置单元和启动加载器可读取、架构与启动方式匹配、需要时引导修复已回读。可以检查 `SYSTEM`、`SOFTWARE`、`winload.efi`、内核等，但“几个文件存在”也不是完整可启动证明；启动确认另行记录。

第三方系统镜像在格式化前通过支持的只读镜像接口检查所选索引。优先使用现有 DISM（部署映像服务）能力；若需要只读挂载，使用任务私有挂载点并记录卸载责任。不能因为 `/Get-WimInfo` 返回 0 就断言所有系统文件都有效。未知架构、关键证据不足或挂载失败时停在预检，不先格式化。

### 17.2 稳定身份与现场地址分离

- `VolumeKey`（稳定卷身份）：磁盘 GUID、分区 GUID、分区偏移/大小及分区类型。卷 GUID 作为运行时解析线索，但格式化后可能需要重新取得；盘符、磁盘编号与分区编号均为现场地址。
- `ResolvedVolume`（现场卷）：稳定身份、此次解析的卷路径/设备路径、当前编号、文件系统与序列号、解析时间及证据。
- `resolve_unique_volume(key)`（唯一解析）：枚举后严格匹配；零匹配、多个匹配、GUID 克隆冲突、几何异常均拒绝。
- `authorize_write(plan, live_roles)`（写入授权检查）：返回短寿命的 `WritePermit`（写许可）。它不是永久豁免；每次格式化、应用、引导写入前都重验。
- 同一分区在多个角色中出现时共享同一解析结果；为工具临时分配盘符时登记所有权，收尾只撤销本任务创建且仍指向该卷的挂载点。

### 17.3 状态与结果不再挤在一个布尔值中

| 对象 | 设计 |
|---|---|
| `task.json` | 不可变任务计划；包括意图、卷身份、镜像策略和同意范围。载荷清单对它取摘要，执行中不反复改写 |
| `runtime.json` | 唯一运行事实：协议版本、任务 ID、计划摘要、递增修订号、当前阶段、阶段意图/结果、重试次数、已验证后置条件、资源清单、错误及待清理事项 |
| `status.json` | 可重建的界面投影，带权威修订号；比权威状态旧只触发重建，不阻断恢复，不成为第二裁判 |
| `StepResult`（步骤结果） | `Verified` 已验证 / `NotApplicable` 契约明确不适用 / `Failed` 失败 / `Indeterminate` 无法判定；不能把未知写成跳过成功 |
| `TaskOutcome`（任务结果） | 运行中、需要人工处理、可恢复中断、操作已验证待清理、完成、失败；取消单独记录，不伪装成普通退出 |
| `RebootReceipt`（重启记录） | 未请求 / 请求已接受 / 重启后已确认；`shutdown` 或 `wpeutil` 返回 0 不等于系统成功启动 |

`runtime.json` 仍用现有 `write_json_atomic`（临时文件落盘后替换）作为基础，但写前必须持有任务锁并检查修订号；错误后不能只修改内存阶段继续执行。权威状态损坏时从上一份已核验运行状态和现场证据进入人工处理，不以非原子镜像/启动修改反推一个“成功状态”。

### 17.4 副档与校验策略

`inspect_metadata(image, index)` 返回结构化结果：

| 状态 | 允许行为 |
|---|---|
| `Valid`（有效） | 使用已验证的索引、内容与容量信息；按所选校验策略核对镜像 |
| `Missing`（确实缺失） | 按第三方镜像做实际索引/容量/内容预检；不能把最小容量设为 0 |
| `Corrupt` / `IndexMismatch`（损坏/索引错位） | 硬错误；界面明确显示档案存在但不可用，不伪装成“未找到” |
| `Unreadable`（访问失败） | 保留系统错误、路径和卷身份；停止，不尝试绕过 |
| `LegacyAmbiguous`（旧目录级档案归属不明） | 不套用、不覆盖；可在独立的“按第三方导入”流程中显式处理 |

校验策略至少区分：

- `SizeOnly`（仅大小）：记录真实大小与索引；明确不能发现同大小损坏；不生成“64 个零”冒充 SHA-256。
- `StrictExpectedHash`（严格预期哈希）：与可信预期摘要比较，不自动接受变化。
- `AcceptCurrentImage`（用户接受当前镜像）：提示旧副档不再证明来源，重新计算当前实际摘要并绑定任务；重启后再验证它未变化。其授权不豁免容量、目标身份、内容角色和访问错误。

上述结构替代零散的 `verify_hash`/`force_restore_hash` 组合。历史布尔参数在入口适配层转换，不能只在 GUI（图形界面）或准备阶段生效。是否改变用户默认校验强度不在本次实施假设中：保持当前仅大小默认，并把能力边界说清楚。

4. 外部命令参数不夹带重定向脚本。输出文件由一个类型化 `CommandOutput`（命令输出路径）对象创建，同一个对象传给进程、解码器和回读者。
5. 中间输出放当前恢复环境的实际临时目录；持久控制文件放已核验的任务控制目录。`X:`/`S:` 只可作现场发现后的显示值，不再是身份或永久位置。
6. `pe-task*`、`pe-click*` 的生产者和消费者一起升级，携带协议版本、任务 ID、随机请求 ID、载荷摘要。旧控制文件不自动执行，诊断点击不能默认授权破坏性任务。
7. 写盘前现场推导 DiskPart（磁盘分区工具）编号。预检身份后又直接使用旧编号并不安全，因此这两项必须同一发布批次完成；不能把编号重解析留到以后，却声称保护已完整。

**失败处理：** 写输出失败、不认识动作、探测未知、目标解析不唯一，均返回结构化失败；保留日志，不执行下一条写盘命令。

**验收：** 三态探测分别覆盖权限、离线、缺失和非文件对象；`S:` 未分配/被其他卷占用、卷根与子目录路径差异、盘符重排、磁盘编号重排、克隆 GUID 多匹配、中文/空格/特殊字符路径全部测试。仅修子串而不修路径同源不算完成。

### W02：以任务意图定义系统还原成功

**覆盖：** 第 2 项，兼顾第二系统与在线数据覆盖。

**改动位置：** `TargetSpec`/`Task::validate`、`windows_prepare.rs::validate_operation_inputs`、`main.rs::recover_windows`、在线及 PE 任务构造处。

实施步骤：

1. 所有入口创建 `RestoreIntent`、`TargetMode` 和 `ContentEvidence`；第二系统目标为空是合法输入，不能因为原目标无系统文件就被设计成数据任务。
2. `SystemReplace` 和 `SecondaryInstall` 在格式化前验证镜像内的系统证据；`DataOverlay` 不要求系统文件，但也不能获得引导修复/自动格式化权限。

**失败处理：** 记录已执行到哪个不可逆阶段；不写总成功、不自动重启到已知不可用系统。可进入恢复工具，但不能声明旧系统已恢复。

**验收：** 空目标安装系统、旧系统缺注册表、镜像缺内核/加载器、数据卷合法覆盖、第二系统误选主系统、默认项后来变化分别覆盖；系统分支缺关键文件时后续成功/重启次数必须为零。

**改动位置：** 核心 `image_metadata.rs`、`windows_prepare.rs` 的输入检查/任务创建、`native_gui.rs` 的校验对话框、`recover_windows` 的镜像验证。

7. 按 17.4 持久化校验策略。接受当前镜像后绑定新摘要，不能继续抄旧副档摘要；重启后检查的是同一份获准镜像。

**验收：** 缺失、无权限、坏 JSON（数据格式）、索引不符、陈旧摘要、同大小不同内容、多个 WIM 共用旧档、接受当前后再改镜像、低容量目标。每种失败都必须发生在格式化之前；界面文案与实际错误类型一致。

### W04：格式化的意图、执行与完成证据分开

**覆盖：** 第 4 项；与 W01/W02/W06 同时解决安全重试。

**改动位置：** `format_target_partition`、`verify_partition_identity_after_format`、`operation_safety::verify_formatted_volume`，GUI PE 安装的格式化入口。

实施步骤：

1. 保留现有强校验思路，但先现场采集 `before`（本次操作前）身份和序列号，不直接拿几次重启以前的任务缓存作唯一参照。
2. 获得写许可，落 `FormatIntent`（格式化意图）及本次尝试 ID，再用现场磁盘号/分区号执行脚本。
3. 命令结束后回读稳定身份、几何、文件系统和序列号；检查卷根实际可用。退出码 0、卷根可见、序列号改变三者单独都不充分。
4. 若目标原本是未格式化分区，没有旧文件系统序列号，应进入显式的“无旧文件系统”分支；仍要有可靠物理分区身份和新的 NTFS（文件系统）证据。不能把空序列号当作通用豁免。
5. 在测试卷加入格式化前哨兵文件验证清空确实发生；生产不随意往未知用户卷写哨兵，也不把快速格式化宣传成安全擦除。
6. 续跑遇到只有 `FormatIntent`、没有完成证据时重新解析身份；允许重做的前提是同一获授权任务、同一目标、没有后续应用完成记录，也没有发现外部修改。否则转人工处理。

**验收：** 返回 0 但未格式化、格式化改到别卷、成功后序列号变化、未格式化目标、格式化中断、完成后落状态前中断、已进入应用后不得再无条件格式化。所有入口共用同一规则。

### W05：BCD 精确目标回滚与完整引导回读

**覆盖：** 第 5、15 项；不采用历史的“给 `/import` 补 `/store`”修法。

**改动位置：** `restore_bcd_snapshot`、`rollback_boot_request`、`verify_bcd_target`、`boot_entry.rs`。拟形成 `BcdStoreRef`（已核验启动存储引用）与 `BootSnapshot`（启动快照）。

快照必须记录：目标 ESP 稳定身份、卷内 BCD 路径、来源类型（系统逻辑导出/精确目标原始副本）、摘要、任务 ID、采集时间、默认项与显示顺序、任务创建/修改的对象集合。不能把逻辑导出文件和原始 BCD 文件无条件互换。

快照本身也必须一致：正在被系统修改的 BCD 配置单元不能靠一次并发文件复制就宣称可恢复。先验证取得一致副本的方式，并将相关事务日志的处理纳入受支持的恢复流程；不任意删除用户 BCD 日志文件，也不让旧事务日志重放覆盖新恢复的内容。无法取得并验证一致快照时，不开始需要该回滚保护的引导变更。

回滚策略：

1. 重新核验目标 ESP 与快照归属，检查目标在本任务之外是否发生过变更。
2. 针对离线精确存储，优先使用该目标的已验证原始副本恢复；使用同卷临时文件和经实际文件系统验证过的替换流程，保留当前副本及恢复日志，避免“先删后复制”。ESP 通常为 FAT32（文件系统），不可照搬 NTFS 上的原子/断电保证。
3. 目标被锁定时，只关闭/卸载本程序自己持有的对象；有限重试后仍锁定，返回 `RollbackBlocked`（回滚受阻），保留证据，**禁止悄悄转成系统 `/import`**。
4. `/import` 仅允许在另行验证“目标就是当前系统存储”、快照为对应逻辑导出、覆盖范围获授权的路径使用。若要支持这种路径，必须单独测试；本轮推荐离线恢复不走此回退。
5. 正常 Windows 下默认存储也不是天然可信的目标参数；特别是多 ESP、多磁盘场景，仍要绑定目标身份。
6. 恢复后分别给出原始内容校验和逻辑校验的证据。读取 BCD 可能更新内部元数据，不能把读取后字节变化一律说成回滚失败，也不能因这一点取消逻辑验证。

引导回读改成解析指定存储中的**明确加载器对象**：同时检查 `device`/`osdevice`、加载器路径、`systemroot`、预期目标卷和必要属性；完整系统与 PE 的属性分开。任何一条指向目标的散落字符串不再足以通过。

`partition=W:`、设备路径和卷路径均转换为现场稳定卷身份后比较。对不支持的启动设备类型明确报错，不猜盘符。第二系统还要验证原默认项和显示顺序没有被意外替换。

**验收：** 两个 BCD 存储内容不同、错误 ESP、锁定、快照损坏、错误快照类型、仅 `device` 正确而 `osdevice` 错误、旧加载器残留、外部修改、读取引起字节变化。测试一律操作隔离存储；真实启动变更另走快照保护轮次。

### W06：单一权威运行状态与可解释续跑

**覆盖：** 第 6 项；原恢复卷与目标重合时的重入问题。

**改动位置：** `TaskStore::write_transition`/`write_failure`、`resume_pending_boot_task`、`recover_env`、载荷清单生成和 GUI 状态读取。

拟定阶段序列：

| 场景 | 权威阶段顺序 | 崩溃后规则 |
|---|---|---|
| 准备 | 已验证计划 → 载荷准备意图 → 载荷已验证 → 武装意图 → 已武装 → 重启请求已接受 | 按实际资源和本次意图对账；请求接受不是重启完成 |
| 备份 | 捕获意图 → 候选捕获完成 → 保留策略完成 → 最终校验完成 → 发布意图 → 已发布 | 对账候选、正式镜像、旧镜像和副档，不重新猜索引、不盲目再追加 |
| 还原 | 预检完成 → 格式化意图 → 格式化已验证 → 应用意图 → 应用已验证 → 引导意图 → 引导已验证 | 每种意图有专门恢复器；不得简单按枚举大小跳过执行 |
| 收尾 | 操作已验证 → 清理中 → 清理已验证 → 完成 | 清理失败只重试清理，不重新捕获或格式化 |

执行规则：

1. 不变计划和权威运行状态分别存储。一次状态转移只需替换一个权威状态文件，派生视图写失败不能让两个权威互相争执。
2. 每次转移带 `expected_revision`（预期修订号）；持有跨进程任务锁，拒绝覆盖更新的状态。一次自动重试按任务、动作和证据计数，不能仅靠一个可能遗失的临时标记。
3. 状态先落意图再调用外部程序。外部动作完成、状态还没写入时，恢复器必须回读真实后置条件；有充分证据才补记完成，否则按该阶段安全策略重试或人工处理。
4. `Capturing`（捕获中）中断不能在已发布镜像上再追加一次；恢复器检查发布清单与生成代号。`ApplyVerified`（应用已验证）之后不再因为旧版本兼容注释而无条件重新应用镜像。
5. 清理异常、日志异常、命令失败分开记录；原始失败原因不被清理失败覆盖。运行状态无法持久化时停止新的不可逆动作，但仍尝试安全收敛本任务已持有的资源。
6. 对旧 `task.json`/`status.json` 阶段冲突，先备份两文件和载荷清单并报告差异。不得取“更晚阶段”继续，更不能随意把失败任务改回待执行。
7. 独立恢复载荷是本次执行的依据，不在还原目标被格式化后重新要求旧注册 WinRE 卷的文件系统序列号仍相同。需要该卷时按任务角色判断：作为镜像/工作区必须严格可达；仅作为先前模板来源则不能阻断已经验证的独立载荷。
8. 自动续跑需要真正可用的启动入口。系统卷被擦除后，不能假设会回 Windows 并启动 GUI 来重武装。推荐保留可选择的任务恢复入口和人工恢复说明；若要求无人值守自动再次进入恢复环境，必须另行验证持久启动方案，并明确批准是否改变默认启动策略。

**验收：** 在每一个权威写入前后、每个外部动作前后注入中断。检查状态缓存落后时能重建、权威文件损坏时拒绝冒进、重复启动不会重复发布/重格式化、恢复源与目标同分区时不会因旧序列号误拦、清理失败不会重跑业务动作。

### W07：启动准备资源隔离与统一清理

**覆盖：** 第 7 项；多任务共享固定载荷目录及准备期部分失败。

**改动位置：** `prepare_payload`、`boot_entry::{create_entry,copy_into_staging,arm_one_shot,rearm,disarm}`、`boot_cleanup`、启动恢复扫描。

实施步骤：

1. 任务私有目录建议为 `BackupRestoreRE/<task-id>/`，副档和清单引用该目录；卷根身份由 `VolumeKey` 定位。不再让两个任务覆盖同一个 `Winre.wim` 或 `boot.sdi`。
2. 每次准备获取“本机启动变更锁”及持久活动任务记录。运行时锁只负责防并发，跨重启是否可接管还要看持久任务状态，不能只看进程 ID 不存在或超时已过。
3. 完成输入、空间、镜像、工具可用性检查后才开始建立资源；在载荷内容允许的范围内尽可能先完成注入和校验，再创建/武装启动项。
4. 如果载荷需要启动对象 ID 而必须提前创建 BCD 对象，就先创建**不武装**的任务对象，每生成一个立即记入资源清单。采用创建前快照与本任务唯一标记补救“创建成功但记录未落盘”的窗口；无法证明归属的对象不自动删除。
5. 对创建目录、复制文件、挂载 WIM、创建 BCD 对象、设置一次性启动，每项都登记意图、实际资源引用、摘要/属性、回读证据及补偿动作。
6. 武装前要求资源清单和载荷清单可读、哈希匹配。落武装意图 → 写 BCD → 回读 → 落已武装状态；武装后的任何失败都进入统一对账，不只处理 `shutdown` 失败。
7. 清理按依赖反向执行：确认正在写入的进程已收敛 → 处理本任务挂载 → 去除本任务启动引用 → 删除本任务对象 → 清理本任务载荷 → 释放本任务挂载点与锁。
8. 一次性启动序列是集合/顺序而非永远只有一个 ID。只去除本任务 ID，保留其他条目及顺序；不覆盖他人后来改变的默认项或启动序列。资源仍被引用时，不继续删除它依赖的载荷。
9. 清理要检查路径归属、重解析点、文件实际摘要和未知文件；无法确认归属时报告 `CleanupBlocked`（清理受阻），不进行递归“扫干净”。未完成挂载卸载时禁止删除其底层 WIM。

**验收：** 每个创建点失败、挂载失败/提交失败、武装后状态写失败、关机请求失败、日志盘满、对象已被删除、其他任务同名资源、未知文件、启动顺序含他人 ID。要求只清理本任务资源；任何未清理项都出现在权威状态与最终报告中。

### W08：统一命令生命周期，不用静默超时误杀写盘

**覆盖：** 第 8、10 项及第 14 项的退出码读取；延伸既有 `windows_command`，不重新发明另一套执行器。

拟定接口：

| 接口 | 职责 |
|---|---|
| `CommandSpec`（命令描述） | 程序的可信解析路径、独立参数、任务/步骤 ID、读写类别、时限策略、输出目的地 |
| `CommandOutcome`（执行结果） | 真退出/未启动/等候失败/超时/已取消/无法确认结束，并携带原始错误码、进程树状态与耗时 |
| `CommandEvidence`（命令证据） | 原始输出文件、正确解码的正文、进度事件、输出完整性和回读结果 |
| `CancellationState`（取消状态） | 未请求、请求中、进程已收敛、现场已对账；不能在“请求中”就允许重试 |

实施步骤：

1. 运行前先建立必需的状态/日志接收端；失败不能在子进程已经开始写盘后直接返回，留下无人管理的进程。
2. 复用“挂起创建 → 加入作业对象 → 恢复”与句柄继承白名单。管理进程异常结束时关闭作业对象，后台写盘风险必须有明确错误状态。
3. `run_logged`、`capture_logged`、GUI 公用命令、PE 步骤逐批迁移到同一后端。用户路径与名称通过独立参数传递，不拼入命令解释器字符串；工具定位使用系统接口，不写死 `C:\Windows`。
4. 正常根进程退出不立即代表成功：等待必要后代退出。若必须强制结束未结束后代，结果应是中断/未知，而不是仍按根进程退出码 0 成功。
5. 作业对象活动进程数归零，只能证明受其管理的进程已结束。DISM 等如委派系统服务执行写入，还必须做操作特定的静止/锁/挂载状态检查；无法确认实际写入已停，维持禁止重试状态。
6. 短只读探针设置可配置总时限，初始测试值如 BCD 枚举 30 秒、WIM 元信息 120 秒，之后按实测调整。超时读失败必须阻止依赖它的写操作。
7. 捕获、应用、镜像提交不设十分钟上限，也不按固定速度估算后强杀。记录耗时、输出增量、进程活动和阶段心跳；无活动进入“疑似停滞”，默认仍不自动销毁业务数据。
8. 明确取消会结束受管进程并进行现场对账。候选备份可保留原件；已覆盖的还原只能报告部分还原/需要恢复，不能伪称取消后原数据仍在。
9. 日志保留原始字节供诊断，显示/解析共用 UTF-16、UTF-8 与系统代码页解码器；流式解码处理跨块字符及 `\r` 原地进度，不按每个碎片单独有损解码。
10. DISM 的文本解析命令统一带 `/English`，但不把此选项当作强制 UTF-8；BCDEdit 不假设存在 `/English`。数值与结构解析失败应报错，不能以空列表代替未知。

**验收：** 退出 0/非 0、启动失败、退出码读取失败、等待失败、超时、根进程先退但子进程继续、输出接收端失败、长时间静默但仍有 I/O、外部服务写入无法确认、GBK（中文代码页）/UTF-16/UTF-8 分块。每项同时核验界面结果与进程/产物实际状态。

### W09：三个入口汇入同一执行计划

**覆盖：** 第 9、16 项；PE 指定索引丢失、失败后继续和自动重启问题。

**改动位置：** `recover`、`recover_env`、`online_operation::execute`、PE 任务构造和 `execute_pe_task_line`。

实施步骤：

1. GUI、命令行和 PE 只产生 `ValidatedPlan`（已验证计划），都交给共用任务执行层；不能有一个入口绕过权限、身份、内容/容量、校验策略和终态判定。
2. PE 文本任务升级成类型化任务/步骤，必须携带镜像索引和目标身份；旧文本只允许只读诊断，或在验证后转换，不再默认把任何 restore 固定成索引 1。
3. 每一步返回 `StepResult`。只有 `Verified` 或计划允许的 `NotApplicable` 才进入下一步。空输出、未知命令、参数不足、取消、命令非零和后置校验失败都阻断。
4. `reboot`（重启）不是无条件的最后一行脚本，而是调度器在必要阶段、收尾和重启许可全部通过后才允许的动作。
5. `recover --dry-run`（只验证）保留只读；直接恢复必须加载同一不可变计划、权限和现场闸门。没有 WinRE 载荷的直接执行可跳过“不适用的载荷自校验”，但不能跳过目标身份或自己写总成功。
6. 系统替换/第二系统入口不能因为当前运行环境不是 WinRE 就直接格式化活动系统；选择环境与业务意图是两个独立字段。
7. 正常 Windows 下数据覆盖维持原有覆盖语义，但对占用卷做明确检查和警告。需要一致性备份或覆盖在用数据时，应选择离线执行；本轮不暗中新增 VSS（卷影复制）功能，也不将活跃文件集宣传成一致性快照。

**验收：** 同一任务从三个入口产生等价执行参数；索引 2/3 原样到达 DISM；任意一步失败后，引导修改及重启调用次数为零；直接命令不能绕过保留分区、活动系统与授权约束。

### W10：备份、保留策略和副档作为一笔可恢复事务

**覆盖：** 第 12、16 项；替换在线当前“有回滚但无持久发布对账”的不足。

**改动位置：** 命令行备份分支、`online_operation::capture`、PE 备份、`image_metadata.rs`。拟抽出 `backup_transaction.rs`（备份事务）。

事务算法：

1. 获取镜像写锁，解析最终路径/文件身份，读取真实索引集合，完整加载可归属的副档。锁键不能仅用原始路径字符串，必须处理盘符别名、规范路径及现有文件身份。
2. 创建同卷任务私有事务目录；保存持久发布清单，记录正式路径、旧镜像摘要/身份、候选路径、新代号、旧副档快照及当前阶段。没有落盘清单不开始正式文件替换。
3. 已有 WIM（Windows 映像格式）复制成候选再追加；新备份直接捕获到候选。原件绝不先删除。排除配置和日志不得落到捕获集合内，配置生成失败必须明确处理。
4. 捕获/追加后用 DISM 回读真实集合。首次只能产生预期初始索引；追加保留全部旧索引且只新增一项，不用副档枚举作为证据。
5. 保留策略仅作用于候选：每删除一次检查完整剩余集合；中途失败整笔停止，正式镜像和正式副档均不变。保留 0 明确表示不清理，不偷偷折成保留 1。
6. 副档全量读入后在内存重编号。缺失来源的历史索引仍标明未知，不能套用本次源卷身份；所有保留项写入同一最终 WIM 摘要、大小及生成代号。
7. 校验最终候选和副档，落盘“可发布”记录。发布前复核旧镜像未被替换/修改；跨进程锁与必要文件共享限制覆盖本项目入口，不能假设能约束任意管理员外部工具。
8. 落发布意图，保留旧 WIM 与旧副档，按清单执行重命名/替换；所有正式读入口遇到未完成发布标记，先对账或拒绝读取，不能拿“新 WIM + 旧副档”去还原。
9. 回读正式文件身份、大小与副档代号；候选在持有保护的情况下只做重命名时，可复用刚验证的摘要，不无意义地再读一遍大文件。无法证明未被修改时必须重验。
10. 所有正式后置条件通过后才落“已发布”。旧备份/候选的自动清理只能发生在发布确认之后，清理受阻仍显示待清理，不能破坏已有效发布的镜像。

**断电对账表：**

| 现场与权威记录 | 处理 |
|---|---|
| 捕获/删除候选中断，正式镜像仍是旧代 | 保留旧代可用；候选标为未完成，不重用它的副档证明成功 |
| 发布意图已落，旧镜像尚在正式路径 | 核验候选和旧代后继续发布或明确放弃候选 |
| 旧镜像已移到备份位置，新镜像尚未到正式路径 | 确认二者归属，恢复旧代或继续已验证候选；不报告镜像永久丢失，也不猜文件名 |
| 新镜像已在正式路径，副档只替换一部分 | 正式读取被阻断；根据持久清单补齐同代副档或整体回到旧代 |
| 全部文件已换，成功记录尚未落 | 逐项核验新代一致后补记发布完成，不再次追加或删索引 |
| 正式路径出现清单之外的文件/内容 | 停止自动修复，保留两个已知版本，不覆盖外部文件 |

多文件发布**不宣称底层天然原子**；保障来自持久清单、读入口门禁、旧代保留及可重复对账。外部程序绕过本应用直接读路径，可能看到发布窗口，文档必须提示。若未来选择不可变代目录加单一清单指针以缩短窗口，会改变外部文件使用习惯，另行评审，不在本方案默认切换。

**验收：** 新建、追加、保留全部/1/N/0、缺失历史副档、坏副档、复制失败、DISM 失败、每次副档写入失败、每个重命名窗口中断、发布后日志失败、外部修改、双实例同镜像。除已完成发布的新代外，失败不得让正式旧镜像失去可恢复副本。

### W11：容量与性能，避免靠降低校验强度提速

**覆盖：** 第 11、13、17 项；保持候选方案。

容量设计：

- 在首次写候选前分别计算镜像卷、工作区卷、恢复载荷卷、ESP 的峰值需求；角色在同卷时合并统计，避免分别通过后总量超限。
- 镜像卷保守需求为：本次额外候选副本需求 + 新捕获数据上界估计 + 工具临时空间 + 副档/日志 + 安全余量。旧镜像通过同卷改名保存不应再算一份复制空间；若实际策略要求再次复制，必须加进去。
- 当前空闲空间已经扣除了现有原镜像，公式不能再次把原文件当成可用空间，也不能假设压缩必然节省多少。
- NTFS 已用空间、稀疏/压缩文件展开和第三方镜像大小的关系要区分“已知下界、估计值、保守预留”。空间预检不保证永不遇到其他进程占用，运行中还要监测。
- 所有加法用检查/饱和运算，容量/身份缺失返回错误，清除业务 `unwrap()`。失败不自动清用户文件，也不自动切换到原件就地操作。

性能设计：

1. 只有确实需要检查旧目录级副档归属时才计算旧摘要；若本次本来就要复制原 WIM，可在同一读取流中同时计算摘要，避免另开一次读盘。
2. 保留策略执行完后计算一次最终候选摘要，结果共享给全部副档；不能每个索引重复全文件哈希。
3. 同一未变化的文件句柄/事务代内复用证据；跨重启或解除保护后，不用缓存的修改时间和大小冒充仍未改变。
4. 用户选择严格校验时，准备与恢复阶段各自承担明确证明义务；能省的是同一阶段重复计算，不是重启边界后的必要核验。
5. 记录复制字节、哈希字节、外部命令耗时、元数据耗时、峰值临时空间和 CPU/磁盘活动，先测再优化，不承诺未经测量的提速倍数。

**验收：** 三角色共卷、空间刚好不足、复制中磁盘满、稀疏/压缩大文件、慢盘、同大小内容修改、大整数溢出；检查一次最终副档同步只触发一次最终 WIM 摘要计算。

### W12：准备结果跟踪、结构化日志与用户反馈

**覆盖：** 第 14 项，及所有入口“日志有成功字样就显示成功”的风险。

**改动位置：** 提权准备启动、`WM_APP_*`（窗口消息）通知、进度窗口、任务状态读取、启动错误记录。

实施步骤：

1. 1.5 秒早退检查只作为快速反馈，不能决定准备后续是否成功。后台持续监听进程及任务状态，直到真实结束、明确重启请求或权威失败状态。
2. `GetExitCodeProcess` 等系统调用的返回值都检查；读取失败是未知，不是初始值 0。进程不可跟踪时通过任务 ID 查询权威状态，也不能直接报成功。
3. 以 `TaskOutcome` 驱动界面和重启动作，不搜索英文成功句或 `exit=0`。支持“备份已发布但清理未完成”“系统内容已应用但引导验证失败”等中间结论。
4. 每个结构化事件记录任务 ID、入口、步骤、修订号、时间、稳定卷身份、目标现场地址、索引、校验策略、命令结果、后置证据及下一步。敏感凭据不进日志；诊断命令参数按必要性脱敏。
5. 关键安全状态不能只写临时 RAM（内存）盘；控制和权威证据持久化到非目标卷，普通进度输出可临时缓存。日志接收失败不能让已启动的写进程失管，也不能阻止必要的收敛/回滚尝试。
6. 时间和活动显示独立于日志是否增长；哈希与复制阶段显示本阶段字节进度，不能借用上次 DISM 的 100%。最终完成标志只在该任务所有必需后置条件达成后产生。
7. 英文和中文界面共用错误码映射，区别缺失、损坏、未知、失败、取消和待人工处理；正常关闭/重启期间不允许绕开仍在执行的任务。

**验收：** 准备在 2 秒/数分钟后失败、读取退出码失败、后台线程异常、重复点击、消息投递失败、语言切换、日志增长暂停、复制/哈希无 DISM 输出、清理失败、重启请求被拒。界面结果必须与权威状态一致。

## 十九、总体流程、实施顺序与覆盖表

### 19.1 三条入口最终走的流程

**系统还原/第二系统：**

1. 选择意图、镜像索引及目标 → 现场身份检查 → 副档分类、内容与容量预检 → 绑定用户确认。
2. 保存不可变计划和初始运行状态 → 选择在线/恢复环境适配器；系统替换不得走活动系统在线覆盖。
3. 若需重启：任务私有载荷准备 → 验证载荷与资源清单 → 安全武装 → 请求重启。
4. 恢复环境重新核验计划、执行程序、镜像策略和现场卷身份 → 不重新依赖已被允许格式化的旧恢复卷序列号。
5. 格式化意图 → 实际格式化 → 回读证据 → 应用意图 → 应用所选索引 → 角色对应内容校验。
6. 需要引导修复的角色才进入指定 BCD 存储事务 → 对象/目标/默认项回读。
7. 操作已验证 → 按所有权清理 → 清理已验证 → 记录完成 → 若计划允许则请求重启；下一次启动证据单列。

**在线数据覆盖：** 计划/目标/索引/容量与占用检查 → 明确不格式化 → 应用及校验 → 目标身份复验 → 完成。数据模式不触及 BCD，不获得系统部署的成功标志。

**备份：** 计划/源身份/源一致性范围/空间预检 → 镜像写锁 → 候选复制或首次捕获 → 真实索引回读 → 候选上保留策略 → 最终摘要及副档 → 持久发布事务 → 正式读回 → 清理本任务临时资源 → 完成。

### 19.2 分批实施，不一次性大改后再排错

| 批次 | 内容 | 进入下一批的门槛 |
|---|---|---|
| A：契约冻结与复现夹具 | 17.1～17.4 数据契约；建立旧行为最小复现、动作记录器、故障注入点 | 17 项都能对应代码入口、修复目标与至少一条可判定测试；未验证前提单独标记 |
| B：写盘安全入口 | W01/W02/W03/W04；同时完成现场编号派生与统一拒绝闸 | 三入口的所有破坏性调用都通过统一许可；探测未知、镜像不符、容量未知均在第一次写盘前失败 |
| C：执行与状态基础 | W08、W06 基础、W12；先用只读命令适配后迁移写命令 | 命令故障可收敛，运行状态可恢复，GUI 不再猜成功；状态协议升级后旧任务不自动续跑 |
| D：入口与备份事务 | W09、W10、W11 | 所选索引端到端一致；失败不继续；保留策略失败不动正式镜像；每个发布窗口有恢复测试 |
| E：启动事务和完整闭环 | W05、W07，补齐 W06 的启动恢复对账 | 多 ESP、锁定、武装后失败、清理冲突测试通过；只处理任务拥有的资源 |
| F：环境验收 | Windows ARM64 原生测试 → 隔离测试卷 → PE/WinRE 启动测试 → 获明确授权后的系统卷测试 | 完整证据链齐全，且下一节发布门槛全部满足 |

批次 B/C 存在接口依赖，可先以接口与模拟实现并行设计；发布时不能上线“新格式任务 + 旧恢复程序”混合包。每批实际修改代码才递增一次届时版本，本方案不提前分配未来版本号。
