## 二、三个阻断缺陷

### ① 活动系统卷的探测失败被当致命错误（第一道坎）

**现象**：还原在 STEP 1 之后 45 毫秒失败，报 `I/O error: 另一个程序正在使用此文件`。

**定位过程**：逐层加 `eprintln!` 诊断（每次都重新构建+部署），最后缩到
`discover()` 的 for 循环：10 个卷里第 2 个是当前运行的 C:，进入后无声无息失败。

**根因**：`probe_file` 内部的 `fs::symlink_metadata(root)` 对**活动卷根**报共享违例，
而 `probe_file` 把它当 `Err` 往上抛（设计如此：它对"探测失败"和"不是 Windows 卷"
不加区分）。此前这段代码只在 WinRE 路径运行，候选卷里从来不含活动卷，所以没暴露。

**修法**：候选卷的**探测失败**（而非探测结果）一律跳过并记账，不让整个还原失败。
C: 本来就在启动菜单里，跳过它不影响功能；能读到的卷仍正常登记。

### ② DISM 读 WIM 的独占访问与紧邻调用冲突

**现象**：日志打出"引导菜单将使用镜像版本名：Professional 10.0.26100.9549"后
**2 毫秒**即 `I/O error`。

**根因**：我在 `read_image_version_name` 里自己跑了一次 `dism /Get-WimInfo` 读版本，
而调用方紧接着的 `indexes()` 又要对**同一个 WIM** 跑 DISM。DISM 读 WIM 需要独占访问，
前一个 DISM 主进程退出后句柄未必立刻释放。

**修法**：不再自己跑 DISM。`indexes_with_info()` 把已有的 DISM 输出一起返回，
版本名只做解析。一次调用服务两处，既消除竞争也少跑一次 DISM。

### ③ 不带 `/Index:` 的 DISM 输出里根本没有版本信息

**现象**：修完②后 `versioned_name = None`——白丢了一次拿到正确版本名的机会。

**根因**：不带 `/Index:N` 时，DISM 只输出**摘要**（Index/Name/Description/Size），
**没有 `Edition` 与 `Version` 行**。只有带 `/Index:N` 才输出完整信息。
我的 Windows 侧单测用的是带 `/Index:` 的真实夹具，所以通过了——**测的数据和实机跑的命令不一样**。

**修法**：`indexes_with_info` 带上 `/Index:{index}`。

顺带在①的排查中发现：DISM 输出最前面的 `Version: 10.0.26100.9549` 是
**dism.exe 这个程序自己的版本**，不是镜像版本。解析时必须从 `Details for image`
之后开始找，否则菜单名会写成 dism 的版本号。

## 四、第四个缺陷：验收断言自己不解析别名

上面那些全部通过之后，操作仍然报失败：

```
[ERROR] 原有启动菜单项丢失，拒绝报成功
```

**根因不在产品逻辑，在我的验收代码**：`bcdedit` 把默认项显示成 **`{current}`**
（别名），而我的断言拿它和快照里的 `{12e3701c-c361-11f1-90a2-c222b5348ef7}` 做字符串精确比对，
于是认为"默认项被改掉了"。实际两者是同一个 loader——实机核对
`bcdedit /enum {current}` 与 `bcdedit /enum {12e3701c...}` 的 `device` 都是 `partition=C:`、
`description` 都是 `Windows 11`。

`toolsdisplayorder` 同样从 `{b2721d73...}` 变成 `{memdiag}`（也是别名）。

**修法**：
- 默认项改用「指向哪个分区」判断，而不是比 GUID 文本——主系统在活动卷 `C:`，
  第二系统才是目标卷；`{current}` / `{default}` 别名直接认定为主系统。
- `display_order` 的比较前先把两边常见别名展开成真实 GUID 再比。

**教训**：验收判据本身也要经实机核对。一个把成功判成失败的断言，比没有断言更危险——
它会让人去"修"本来正确的东西。

## 五、方法论结论

**"测试用的数据"和"实机跑的命令"必须是同一个东西。** ③ 是最典型的：
我的夹具来自 `dism /Get-WimInfo /WimFile:... /Index:1`（手工跑的），
而产品代码跑的是不带 `/Index:` 的命令。夹具再真实，只要命令不同就测不到真问题。

**环境差异不会自己暴露。** ① 在 WinRE 路径永远不会发生（那里没有活动卷），
只有把同一段代码放到在线路径才会撞上。这类问题只能靠实机，或者靠
"主动问：这段代码在新的调用环境里，哪个假设不成立？"

**别名、本地化、权限这类"环境性状"要单独验。** ④ 的 `{current}`、⑤ 的中文标签，
都是"我以为 bcdedit 会输出 X，其实它输出 Y"。它们不影响正常路径，
只在你恰好命中时让整个功能失效。

**排查要逐层收敛，但每一层都要真重新构建。** 我最初把诊断加在 `run_capture`，
真正的失败点在它上游 5 层。中间有几次"改了却没生效"，
是因为改完只跑了 `cargo test`（macOS 侧，压根不编译 `online_operation`），
没跑 `build-win.sh`。**这个模块的改动必须在 Windows 侧验证**——macOS 的 138 项全绿
对它没有任何证明力。

## 六、补记：产品逻辑其实早就通了，是我的断言连错三次

上面四个缺陷修完后，实机日志已经明确记录：

```
[13:23:43] 引导修复完成：菜单 2 项，显示 10 秒；现有 PE 入口保留
```

也就是说 `boot_menu::apply` **完整执行并通过了自己的五项回读**。但操作仍然报失败，
因为我在在线路径后加的验收断言连错三次，把一次成功的还原判成失败：

| # | 断言的错误 | 实机真相 |
|---|---|---|
| 1 | `device` 被我转成小写 `partition=c:`，却用大写 `C:` 去 `starts_with` | 默认项一直是主系统（`partition=C:`），从没变过 |
| 2 | `displayorder` 第二项显示成 `{default}` 别名，展开逻辑漏了这一种形态 | 不带 `/store` 时 bcdedit 显示 `{current}`，带 `/store` 时显示完整 GUID，两种都会遇到 |
| 3 | 目标卷的旧 loader 被新 loader 取代，判成"原有菜单项丢失" | 还原到 E: 时 bcdboot 把 `{556b9391}` 换成 `{2f72105a}`（都指向 E:）——这正是"还原"该有的行为 |

**这一轮最贵的教训**：产品代码对了，验收代码错了，症状却完全一样（都是"操作失败"）。
如果当时没有去核对 BCD 实际状态，而是一直改产品逻辑去"适应"断言，
就会把一个本来正确的功能改坏。

**判断孰对孰错的方法**：不要看哪边报错，看**实机事实**——
`bcdedit /enum {current}` 与 `bcdedit /enum {12e3701c...}` 的 device 是否同一个分区？
旧 loader 与新 loader 是否都指向目标卷？事实站在哪边，哪边就是对的。
