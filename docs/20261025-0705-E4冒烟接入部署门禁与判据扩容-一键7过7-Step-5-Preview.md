## 1. 为什么串联点放在宿主侧

`build-windows.ps1 -Deploy` 在 VM 内跑、`br-smoke.sh` 在宿主跑（驱动 prlctl），两边天然跨边界；
VM 内的部署脚本没有也不适合有「回调宿主脚本」的能力。所以按设计文档「deploy 末尾 `--smoke` 开关」
的**语义**落在宿主封装器上：

```
tools/smoke/deploy-and-smoke.sh
  1) SYSTEM 通道 taskkill GUI（exe 占用会致部署失败）
  2) VM 内 build-windows.ps1 -Deploy -CargoTargetDir H:\br-target（构建日志落 .test-artifacts/）
  3) br-s1.sh start-gui.ps1 重启 GUI（顺带验证新二进制能起界面）
  4) exec br-smoke.sh "$@"（参数原样透传：--skip-backup/--drive/--keep/--vm…）
```

**默认不自动跑**：冒烟含一次 WinRE 重启，日常循环每次跑会拖慢；改了 apply 主链/判据层/发版时手动跑。

## 2. 判据扩容：失败必须带码

`br-smoke.sh` 的 C3 判据（任务 success/100）失败时，现在把两类结构化信息一并带进判据详情：

- `--json` 的 `error_code` 字段（程序自陈的码，v2.6.48 起有）；
- 任务日志里最后一条 `[BR-域-序号]` 码（回读日志 grep）。

门禁红了要能一眼看出是哪个码，不用回翻几百 KB 日志。判据本身仍只认 ASCII 结构化特征
（`success` 字段 + `STEP n/m` + DISM 英文成功行），不碰任何会被翻译的文案。

**范围外一项（如实记录）**：设计文档还写了「还原后回读 default 指向」——冒烟的作用卷是 T: **数据卷**，
整条链不碰引导（无 bcdboot、不动 default），该判据对数据卷冒烟无意义；系统卷还原的 default 回读
在程序内部本就是硬判据（`BR-BOOT-004` 拒绝报成功），且 E3 两轮实机已单独覆盖。故不引入。
