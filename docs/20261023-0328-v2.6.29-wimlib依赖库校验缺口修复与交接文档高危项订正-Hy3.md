## 1. 改动一（代码）：`locate_wimlib` 补校验 `libwim-15.dll`

### 1.1 缺口

`crates/backuprestore-cli/src/wimlib_apply.rs` 的 `locate_wimlib` **只检查
`wimlib-imagex.exe` 是否存在，没有检查同目录的 `libwim-15.dll`** —— 而模块注释明确写着
「`libwim-15.dll` 必须与 exe 同目录」，缺的正是把它落到代码里的那一步校验。

### 1.2 为什么这是真问题

`wimlib-imagex.exe` 与 `libwim-15.dll` 是**两个独立部署件**：

- 恢复环境载荷注入（`winre_payload.rs` 的 `OPTIONAL_RUNTIME_FILES`）分开拷这两个文件；
- 部署脚本也分开拷。

只拷了主程序、漏了动态库时，**Windows 加载器会在进程启动时直接终止 wimlib**——
报出来的错误既不点名缺哪个文件，也不会落进我们的日志；现场只能看到
`wimlib apply failed: …`，**无法归因到「部署清单漏拷」**，白白消耗一轮排查。

### 1.3 修复

`locate_wimlib` 改为分两步校验，缺依赖库时给**独立、可操作**的报错
（点名缺的文件名 + 保留「不会回退 DISM」语义，与既有主程序缺失报错风格一致）。

同步修正/新增单测：

- 修正 `locate_wimlib_accepts_present_binary`：原用例只写 exe，新逻辑下会失败 → 补写 dll；
- 新增 `locate_wimlib_rejects_exe_without_companion_dll`：只放主程序、不放依赖库，
  断言报错含 `libwim-15.dll` 且含「不会回退 DISM」。

## 2. 改动二（文档）：订正交接文档 §8.4 的两处误判

交接文档 `docs/20261023-0320` §8.4 把两条高危判为「**代码里未见修复标记**」。
按 `H1`/`H3` 修复标记与代码位置逐条核对后确认：**两条实际都已修（2026-10-18）**。

| 项 | 原文判断 | 复核结论 |
|---|---|---|
| 1. A 入口目标卷下拉框自动锁定失效且全链无硬闸 | 未见修复标记，仍是最高优先级风险 | **已修（H1，两层）**：界面层 `native_gui.rs:6599` 断言 `restore-existing` 目标必须 = `active_system_letter()`，不等即弹「还原已停止」并 `return`（中英双语文案 + 日志留痕）；准备层 `windows_prepare.rs:2521` 同判据第二层。风险已消除 |
| 2. `(RecoveryComplete, Failed)` 状态转移缺失 | 已修（H2） | 判断正确，维持 |
| 3. Esc 被转给编辑器专用的 `handle_key` | 未见修复标记，需实机复现后再动 | **已修（H3）**：`recovery_progress.rs:1906-1913` 在主进度窗家族里显式拦下 Esc 并 `continue`，不再落到 `boot_menu::handle_key` 的 `DestroyWindow`；日志弹窗 Esc 另有分支 `:1881-1895`（仅焦点在弹窗自身或子控件时收起） |

**若不订正的后果**：下一个接手 AI 会照着「最高优先级风险」去重新实现硬闸，
可能重复实现已有逻辑、或在已正确的代码上叠加改动而引入回归。

同节另补充说明：macOS 侧 `cargo clippy` 报的 15 条「未使用」告警是**假阳性，不要删**——
它们都是 Windows 专属辅助函数（`logs_dir`、`system_drive_letter`、`collect_orphan_tasks` 等），
macOS 上调用方被 `#[cfg(windows)]` 门控才显得无人调用；在 Windows 目标上均有大量调用点
（例如 `native_gui.rs` 十余处调 `logs_dir()`）。
