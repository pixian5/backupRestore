## 2. 嵌套模态：确认框在模态窗口里再开一个

点 `1404`（清理工作树）→ `MB_YESNO`（类 `#32770`）→ 选完才继续。处理要点：

- **找框按进程号过滤**（`GetWindowThreadProcessId`），别抓系统里其他 `#32770`；
  回调里引用外层变量必须走 `$script:`（委托从原生回调时跑在新作用域，本文件早前栽过）。
- **每次点完轮询它是否消失**，超时后 `WM_CLOSE` 兜底（MessageBox 收到关闭 = 取消），
  最后输出 `DIALOG_LEFT=0` 自证没把框留在屏幕上——模态框留着对用户等于程序卡死。
- 返回码分档：`1` 点完自然消失 / `2` 只在兜底关窗后消失 / `3` 仍在 / `0` 根本没有框。

**两轮设计**：

```
第 1 轮：点 1404 → 点「否」(IDNO=7) → 断言 stage/ 仍在   → T4_CANCEL_GUARDS
第 2 轮：点 1404 → 点「是」(IDYES=6) → 断言 stage/ payload/ 消失
                                    → 断言 task.json / status.json 仍在 → T4_CLEANUP_KEEPS_EVIDENCE
```

第二轮这条正是文档里写明的产品承诺——**证据是产品承诺，不在这里删**——现在它是一条判据。

## 3. 一个「凭空少一行」的仪器怪相

`Say ("DIALOG_LEFT=" + [int]((Find-Dialog) -ne [IntPtr]::Zero))` 这行**没有写进结果文件**，
而它后面的 `CLOSED=` / `MAIN_ALIVE=` / `DONE` 全都正常输出 → 冒烟因此报 1 条 FAIL（`DIALOG_LEFT=0` 找不到）。

诊断：把函数调用放在**方法实参位置**（`PostMessageW((Find-Dialog), …)`）时，这一句会整条被跳过，
且**不报错、不中断脚本**。改成「先赋给变量、再判断」后立刻恢复。

> 具体机制未查清，如实记录。可复用的经验是：**判据里不要在被测对象的参数位置直接调函数**，
> 先取值再使用；以及「少一行」这种症状要优先怀疑语句被跳过，而不是文件写入失败。
