# 未完成任务互斥与显式放弃

版本 **2.2.3**，开发测试版；模型：Opus 5（1M 上下文）。

## 设计结论

任务载荷必须按任务 ID 隔离，但这不意味着多个未完成任务可以并行执行。整台机器的 EFI BCD `bootsequence` 是单一资源，
同时还存在工作区、源卷、目标卷、镜像卷和恢复载荷的资源冲突。

因此采用两层策略：

1. **载荷目录按任务 ID 隔离**：避免任务 A/B 互相覆盖或清理误删。
2. **新任务准备入口拒绝所有未终结任务**：同一工作区只允许一个未终结启动事务。
   `TaskStore::incomplete_tasks()` 在任何新任务的 BCD 导出、任务创建、载荷注入之前扫描并校验所有任务。
   发现有效未终结任务就报出任务 ID、操作、阶段、目标分区 GUID，拒绝继续；任务/status 文件不一致或损坏也 fail-closed（安全失败）。

这正确处理了“任务 A 备份 C:、任务 B 还原 C:”的冲突：B 不会覆盖 A，且不会被允许在 A 未完成时启动。
即使 A/B 目标卷不同，也默认拒绝，因为它们仍竞争机器级一次性启动请求。

## GUI 交互

创建新任务前，GUI 现在显示未完成任务列表并提供三路选择：

- **是**：继续最早的旧任务，调用管理员 `resume <workspace> <task_id>`；不创建新任务。
- **否**：放弃并清理旧任务；只允许 `Prepared`、`BootRequested`、`RecoveryStarted`、`Preflight` 阶段，目标卷尚未写入。
  清理会把任务写成 `Failed` 保留诊断记录，再删除任务自己的 `mount/stage/original/payload` 工作树与任务隔离载荷。
- **取消**：不创建新任务、不修改 BCD、不请求重启。

如果任何待处理任务已进入 `TargetErased`、`ImageApplied` 或 `BootRepaired`，GUI 拒绝直接清理，必须先从原任务的恢复入口续跑或人工处理。
清理前会先预检所有任务，避免多个任务中前一个已经清理、后一个才发现不能清理的半完成结果。

CLI 也有对应的：

```text
resume <任务根目录> <任务ID>
abandon-task <任务根目录> <任务ID>
```

`abandon-task` 要求管理员权限、任务/status 一致，并只允许目标尚未写入的阶段；清理按稳定卷身份和任务 ID 定位，拒绝盘符漂移或分区身份不符。

## 阶段规则

- 可显式放弃：`Prepared`、`BootRequested`、`RecoveryStarted`、`Preflight`
- 不可从新任务对话框放弃：`Capturing`、`TargetErased`、`ImageApplied`、`BootRepaired`、`RecoveryComplete`
- 可显式续跑：`BootRequested` 到 `RecoveryComplete` 的持久阶段
- `Success` / `Failed`：终态；不再作为未完成任务阻止新任务
