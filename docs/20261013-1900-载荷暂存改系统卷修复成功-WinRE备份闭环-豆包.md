## 1. 根因回顾（为什么 2.4.4 永远进不了 WinRE）

`docs/20261012-1935-新启动通道盘符解析回归根因与修复方向-Step-5-Preview.md` 已完整定位：

> **bootmgr 只能解析「系统卷（C:）」的盘符；数据卷（H:/F:/T:/P:/E:）的盘符在 bootmgr 阶段解析不了。**

实验表（1935 文档）：

| 载荷卷 | BCD 盘符 | 结果 |
|---|---|---|
| H: / F: / T:（数据卷） | [H:]/[F:]/[T:] | 回落 C:（失败） |
| **C:（系统卷）** | **[C:]** | **✅ 进 WinRE** |

本会话 2.4.4 的 7 次实验（H:/F: 载荷）全部复现该根因。**00:52 那次 create-secondary"进 WinRE"的真相**
（`docs/20261013-0945`）：任务把 `{bootmgr} default` 改成了 P: 硬盘 RE 引导项（device=partition=P:），
bootsequence（F: 载荷）解析失败回落 default 时**恰好进的是 P: RE**——是 default 指向 RE 的巧合，不是载荷通道通了。

## 2. 代码改动（唯一改动点）

`crates/backuprestore-cli/src/windows_prepare.rs` 约 826 行：

```rust
// 新启动通道：载荷放到**系统卷**（re_staging），注册位只读。
// 2026-10-12 实测根因（docs/20261012-1935）：bootmgr 只解析系统卷（C:）的盘符，
// 镜像卷等数据卷的盘符在 bootmgr 阶段解析不了，ramdisk 载荷必然加载失败、回落默认项；
// 载荷放系统卷后 BCD 写 ramdisk=[C:] 即可正常进入 WinRE。
let re_staging = ReStaging {
    volume: recovery.clone(),   // ← 由 image_volume 改为 recovery（系统卷）
    ...
};
```

- `recovery` = `recovery_identity()`（注册 WinRE 的卷，即 C: 系统卷），在 prepare() 作用域内可直接用。
- `copy_into_staging` 用 `re_staging.volume` 构造 `{盘符}:\BackupRestoreRE\<任务ID>\Winre.wim` →
  改后落在 `C:\BackupRestoreRE\<任务ID>\`；BCD `ramdisk=[C:]`；`boot-entry.json` 的 wimVolume、清理路径同步一致。
- 载荷源 WIM 本就是系统卷的 `C:\Recovery\WindowsRE\Winre.wim`（722,034,583 B，dir /a 可见，完好），
  SDI 源 `C:\Recovery\WindowsRE\boot.sdi` 也同卷——注册 WinRE 全程只读的设计不变。
- 卷闸门不受影响：它管 workspace/镜像卷不能落在注册 WinRE 分区，暂存卷不在检查内（暂存的是载荷副本，非程序资产）。

## 5. 经验沉淀（本轮新增/强化）

1. **数据卷盘符解析不了 → 载荷必须放系统卷**。任何"载荷在非 C: 卷"的新启动通道设计都注定失败，
   除非改用"default 指向硬盘 RE"的副作用通道（create-secondary 特有，且会拖用户进 RE，观感是死循环）。
2. **`dir` 不加 `/a` 看不到隐藏/系统属性的目录和文件**（WinRE 相关目录全是隐藏属性）——
   法医判断必须先 `dir /a` 或 `if exist`，本次又复现一次"误判文件缺失"。
3. **"启动成功 ≠ 备份还原成功"**：本轮首次做到 backup 任务在 WinRE 内完整执行并产出 WIM；
   后续 restore（还原）闭环仍需单独验证。
4. macOS 交叉编译（rust-lld）LNK4099 警告为良性（文档已确认）；`build-win.sh --deploy` 部署
   会刷新 H:\brwork + 包目录的 BackupRestore.exe/Recovery.exe 并 4 处哈希核对，是可靠通道。
