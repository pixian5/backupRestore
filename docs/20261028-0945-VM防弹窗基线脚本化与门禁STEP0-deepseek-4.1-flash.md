# 测试 VM 的「防弹窗基线」脚本化 + 门禁 STEP 0

> 起因：「继续」时我挑了最贴近用户痛点的一件事——**今早那三条注册表改动只活在当前这台 VM 上**。
> 用户已经为同一个 V 盘弹窗报过两次；只要重建/换一台测试机，它就必然复发。
> 手工改的东西有两个毛病：**重建就丢**、**下一个人会以为是误改又改回去**。

* * *

## 一、基线是什么（三条，缺一条弹窗就会回来）

| 键 | 值 | 作用 |
| --- | --- | --- |
| `HKCU\...\Explorer\Advanced\PersistBrowsers` | `0` | 登录**不再还原**上次打开的文件夹窗口 —— 这一条是**掐掉复发机制**的关键（值不存在时 Windows 默认就是开） |
| `HKLM\...\Policies\Explorer\NoDriveTypeAutoRun` | `0xFF` | 所有驱动器类型禁用自动播放/自动打开 |
| `HKLM\...\Policies\Explorer\NoDriveAutoRun` | `0xFFFFFFFF` | 所有盘符禁用自动运行 |

后两条堵的是另一条同类路径：本机反复挂载/卸载 VHD，一旦「卷出现 → 自动开窗口」开着，
就又会留下一个停在临时盘符上的窗口。

## 二、`tools/vm/baseline.sh`：一条可执行、可校验、幂等的命令

```
tools/vm/baseline.sh check     # 只检查，输出结构化结果（门禁用这个）
tools/vm/baseline.sh ensure    # 检查并修复（手工用这个）
```

**四态输出**（与项目判据纪律一致，**不输出依赖中文文案的判断**）：

| 输出 | 退出码 | 含义 |
| --- | --- | --- |
| `BASELINE=pass` | 0 | 基线成立 |
| `BASELINE=fail key=<名> want=<值> got=<值>` | 1 | 不成立，且**点名是哪一条、现在是什么值**（`got=ABSENT` 表示键根本没有） |
| `BASELINE=skip reason=vm_not_running name=<VM>` | 3 | 机器没跑 —— 不是「不满足」 |
| `BASELINE=error reason=...` | 2 | 仪器故障（读不到注册表/找不到用户 SID）—— **也不是「不满足」** |

实现上刻意**不用 .ps1**：`prlctl exec` 里跑 PowerShell 要处理编码/引号/`-File` 不吃 UNC 一堆坑，
而这件事就是三次 `reg query` 加三次 `reg add`，用宿主 bash 直接发最稳。

用户 hive 必须走 `HKU\<SID>`（`prlctl exec` 的 `HKCU` 是盲区，本项目老坑）。

## 三、判据（三次变异，各自都能单独变红）

| 变异 | 期望 | 实测 |
| --- | --- | --- |
| 把 `PersistBrowsers` 改回 `1`（模拟「有人以为误改，给改回去」） | fail 且点名 | `BASELINE=fail key=PersistBrowsers want=0 got=1`，EXIT=1 |
| 删掉 `NoDriveAutoRun` | fail 且报 `ABSENT` | `BASELINE=fail key=NoDriveAutoRun want=4294967295 got=ABSENT`，EXIT=1 |
| `BR_VM_NAME` 指向不存在的机器 | **skip（不是 error）** | `BASELINE=skip reason=vm_not_running name=NoSuchVm`，EXIT=3 |
| 上面两条一起变异后 `ensure` | 复核通过才报 repaired | 两条 fail → `--- 复核 ---` → `BASELINE=repaired（复核通过）`，EXIT=0；再 check 为 `pass` |
| 连跑 5 次 `check`（抗偶发） | 5 次全 pass | 5/5 `BASELINE=pass` |

## 四、接进门禁 STEP 0（4 步 → 5 步）

```
STEP 0/5 检查测试 VM 基线（防弹窗：登录不还原窗口 + 关自动播放）
  BASELINE=pass
```

设计取舍：**只检查，不静默修复**。门禁跑着跑着偷偷改机器状态是很坏的习惯——
基线不成立就明确失败，并把修复命令打出来（`tools/vm/baseline.sh ensure`），
让「改环境」这件事永远是一个显式动作。

实测：`BASELINE=pass` → `pass=8 fail=0 skip=2`，`GATE_EXIT=0`。

## 五、这轮又踩到三个仪器坑（前两个是「同一类」，第三个是脚本自己的谎话）

1. **`vm "dir /b /o-d …" | head -1` 偶发返回空** → 门禁判「编译未完成」。
   而手工 `dir` 立刻就能列出产物：**空输出既可能是「真没有」，也可能是「命令没跑」**。
   —— 这正是我今早写进文档的那条：`prlctl exec` 约 1/8 调用根本不执行。
   新增 `vm_read()`：**输出可能合法为空的查询**，重试 3 次仍空才当成「真没有」。
   （`vm_launch_verified` 管「命令 + 探测是否生效」，`vm_read` 管「读一个查询」——两件事，别混。）
2. **我用 `| head -12` 跑门禁**，`head` 读够 12 行就退出 → 管道对写入端发 SIGPIPE →
   **门禁脚本被半路掐死**。正确做法：先重定向到文件（`> /tmp/gate.log 2>&1`），再从文件读想要的片段。
   ★ 这条和 1 是同一个根源的两面：**在「会产生长输出的仪器命令」前面接 `head` 是危险的**。
3. **我自己的基线检查器先把正确的机器判成了坏的，接着又谎报修好了。** 两个独立毛病：
   - **单值查询的空输出没法自证。** 原来用 `reg query <键> /v <名>`，返回空就记 `got=ABSENT`；
     而那次只是「命令没跑」——机器上 `NoDriveTypeAutoRun` 明明是 `0xff`。
     改：**查整个键**（键存在就一定有输出 → 空只可能是仪器没工作 → `error` 而不是 `fail`），
     再从输出里解析目标值。这样「值真不存在」和「命令没跑」才分得开。
   - **`ensure` 写完不复核就打印「已修复」。** 而 `reg add` 同样会被「命令没跑」吃掉 →
     用户看到 `BASELINE=repaired`，下次登录照样弹窗。改：写完**必须重新跑一遍检查**，
     复核通过才说 `repaired`，否则 `repair_failed` 并 exit 1。
     —— 这正是本项目反复记的那条：**「报告通过但什么都没验」的第三种形态**。

   ★ 连起来看很讽刺：我在同一个文件里，一边写着「空输出有歧义」，一边自己踩；一边要求
   「判据要能变红」，一边让 `ensure` 无条件报成功。**判据的纪律对写判据的人同样适用。**
