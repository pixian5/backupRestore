## 3. 顺手修：既有偶发测试失败（与本次改动无关）

**现象**：Windows 侧全量 `cargo test` 报 `windows_command::tests::timeout_terminates_nested_child`
FAILED（`windows_command.rs:496` panic：stream did not contain valid UTF-8）；单独跑该用例必过。

**对照实验**：`git worktree` 取 HEAD 干净副本（`.head-check`，无本轮改动）在同一 VM 跑同样全量命令
→ **同样 FAILED**。证明是既有问题，不是 A3/A4 引入。

**根因**：中文 Windows 上 `cmd /d /c` 在超时/负载场景会把 GBK 错误信息（如「系统找不到指定的路径。」）
写进 `run_shell` 的输出文件，而测试用 `std::fs::read_to_string` 解码 → 非 UTF-8 直接 panic。
**与用例意图（作业对象杀掉整棵进程树）无关**，纯属脆弱的读文件方式。22:41 那次全量通过是负载低的运气。

**修法**：按字节读 + `from_utf8_lossy`。`ORPHAN` 是 ASCII，存在性判断不受影响，GBK 噪声只会变成替换字符。

**教训**：VM 里凡是把子进程输出落盘再读回的测试/代码，都不能假设 UTF-8；GBK 是常态。

## 4. 另一个坑：PowerShell 5.1 脚本必须带 UTF-8 BOM

本轮写的部署核对脚本先炸了一轮：`Copy-Item` 到客体后 `powershell -File` 解析报「字符串缺少终止符」，
屏幕上是 mojibake。原因：**PS 5.1 把无 BOM 的 .ps1 按系统代码页（简体中文=GBK）解码**，
UTF-8 中文字面量全乱。处置：给 `.test-artifacts/*.ps1` 加 `EF BB BF` BOM。
（build-windows.ps1 本身全英文注释，所以一直没踩到。）
