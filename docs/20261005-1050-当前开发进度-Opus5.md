## 一、本轮要解决的问题

此前多轮（GPT-6 的 14 项、claude5 的 17 项、我自己的 PE 路径同源方案）全部停留在**静态代码分析**。文档里反复出现"仍存在""可能""静态结论，未实机复现"。用户要求实际测试，所以本轮把其中最关键的几条放进真实环境验证：

1. PE 里点「备份系统」能否产出有效镜像？
2. PE 里点「还原系统」是否真的格式化并还原？

4. ESP 定位、探测文件读写、盘符漂移在真实 PE 里到底什么表现？

## 三、测试用例与实际结果

### 3.1 用例一：真实界面备份 —— 通过

操作：点「备份系统」→ 产品弹出卷选择对话框 → 在产品自己的下拉里选 `V:` → 填镜像路径 → 点「执行」。

| 检查 | 结果 |
|---|---|
| 产出文件 | `r2-backup.wim` 存在，1,576 字节 |
| DISM 校验 | `Index : 1`，`Name : PE`，`Size : 24 bytes` |
| 内容对应 | 24 字节正是源盘 `payload.txt`（`PE-0845-original-content` 等长内容）的大小 |

**结论：备份功能本身有效。**

### 3.2 用例二：真实界面还原（正例）—— 通过

操作：先在 `V:` 上额外放一个 `old-only.txt`（镜像里没有这个文件），再点「还原系统」→ 选 `V:` → 填刚才的有效镜像 → 确认。

| 检查 | 结果 |
|---|---|
| 确认框文案 | `确认将 F:\BRPE-20261005-0804\r2-backup.wim 还原到卷 V:？此操作将格式化目标卷，数据不可恢复！` —— 正确点名镜像与目标 |
| 格式化 | `DiskPart 成功格式化该卷` |
| `payload.txt` | 内容 `PE-0804-original-content`，与源一致 |
| `old-only.txt` | **已消失** —— 证明格式化真的执行了，不是空操作 |
| 引导修复 | `bcdboot V: skipped (not a system volume)` |

**结论：格式化 + 应用镜像在正常路径上确实有效。**

### 3.3 用例三：真实界面还原（反例，镜像不存在）—— **失败，数据丢失**

操作：在 `V:` 上放 `sentinel.txt`（加上已有的 `payload.txt`，共两个文件），点「还原系统」→ 选 `V:` → 镜像路径填一个**确实不存在**的文件 `r2-definitely-missing.wim` → 确认。

| 步骤 | 证据文件 | 实际内容 |
|---|---|---|
| 1. 确认框 | `r2-missing-confirm.txt` | 正确点名了那个不存在的镜像 |
| 2. 格式化 | `r2-root-format-out.txt` | **`DiskPart 成功格式化该卷`** |
| 3. 应用镜像 | `r2-logs-restore-out.txt` | **`错误: 2` / `系统找不到指定的文件`** |
| 4. 结果弹窗 | `r2-missing-done.txt` | 标题 **`还原完成`** |
| 5. 重启询问 | `r2-missing-stay.txt` | **`还原完成，现在重启进入系统？`** |
| 6. 盘上实际 | `r2-negative.txt` | `sentinel_survived=false` `payload_survived=false` |

**净效果：目标卷被清空 → 镜像一个字节都没写进去 → 界面报"还原完成"并邀请重启。**

如果目标是用户的真实系统卷，数据已不可恢复，而用户不会收到任何失败提示。这是本轮最严重的发现，**从静态推测升级为实机复现**。

## 四、五项缺陷的详细证据

### 4.1 P0 — 失败后不阻断，先破坏再发现输入无效

**代码位置：**

- [`execute_pe_task_line`](../crates/backuprestore-cli/src/native_gui.rs#L7402) 返回 `()`，调用方拿不到任何成败信息。
- [`pe_restore_from_desktop`](../crates/backuprestore-cli/src/native_gui.rs#L6855) 无条件连跑三步：
  ```
  execute_pe_task_line("format {target} --allow-system")
  execute_pe_task_line("restore {wim} {target}")
  execute_pe_task_line("bcdboot {target} S")
  ```
  之后无条件 `show_message(..., "还原完成", ...)`。

**缺的两件事：** 第一次破坏性命令之前没有输入预检（镜像是否存在、索引是否存在、容量是否足够、镜像与目标是否同卷）；每一步之后没有成败判定与阻断。

### 4.2 P0 — 探测文件写入路径与读回路径不同源

**ESP 上的实际文件分布（实测）：**

| 文件 | 产品写入 | 产品读回 | 实际 |
|---|---|---|---|
| `find-system.txt` | `S:\find-system.txt`，8 字节，内容 `C \r\nX \r\n` | `S:\BackupRestore\logs\find-system.txt` | **不存在** |
| `format-check.txt` | `S:\format-check.txt`，7 字节，内容 `NOSYS\r\n` | `S:\BackupRestore\logs\format-check.txt` | **不存在** |
| `bcdboot-check.txt` | `S:\bcdboot-check.txt`，7 字节，`NOSYS\r\n` | `S:\BackupRestore\logs\bcdboot-check.txt` | **不存在** |
| `pe-drive.txt` | 产品用读回结果写出 | —— | **0 字节** |

**连锁后果（全部实测可见）：**

- `find-system-drive` 读不到 → `pe-drive.txt` 为空 → [`resolve_drive("AUTO")`](../crates/backuprestore-cli/src/native_gui.rs#L7249) 返回空字符串。
- `format` 的系统卷保护（保护 2）判据恒为"非系统卷"，等于保护不存在。
- `bcdboot` 判据恒为"非系统卷"：实测日志 `bcdboot V: skipped (not a system volume)`。本例目标确实不是系统卷，结论碰巧正确；**但真实系统还原走同一条路径会静默跳过引导修复，导致还原后系统不可启动。**

**来源：** v1.8.1 提交 `7613896`「ESP 日志迁出根目录」只改了 Rust 侧的读取路径，命令字符串里的 `> S:\x.txt` 重定向目标一个都没跟着改。

### 4.3 P0 — `mountvol` 的"无装入点"被当成英文固定串

**代码里两处注释明确声称该串不随本地化变：**

- `text_parsing.rs:1028`：``（`mountvol` 打 `*** NO MOUNT POINTS ***`，固定串不随本地化变）``
- `windows_prepare.rs:1206`：``*** NO MOUNT POINTS ***` 是固定串，不随本地化变``

**判据：** `text_parsing.rs:1168` —— `if current.is_some() && !trimmed.contains("NO MOUNT POINTS") { current = None; }`

**实测：** 中文 Windows 与中文 PE 下，`mountvol` 打的都是 **`*** 无装入点 ***`**。

**后果：** `esp_volume_from_listing` 永远匹配不到候选 → [`esp_volume_path_for_task()`](../crates/backuprestore-cli/src/windows_prepare.rs#L1190) 在中文系统上**必定返回 None**。PE 内两轮都打印：

```
[ESP] volume GUID not found; falling back to mountvol S: /S
```

**影响不止 PE：** Windows 侧的「重启进入 PE」[`pe_reboot_to_pe`](../crates/backuprestore-cli/src/native_gui.rs#L4147) 也靠这个函数写 `pe-task.txt`，返回 None 即 `write_ok=false`，该入口在中文系统上无法写入任务。这是 v1.8.2「方案 A」引入的回归。

### 4.4 P1 — 命令输出用 `read_to_string` 读，GBK 解码失败被当"无输出"

**实测对照：**

- `S:\BackupRestore\logs\backup-out.txt` **确实存在，142 字节**，内容是 DISM 的 GBK 成功文本（含 `操作成功完成。`）。
- 同一轮的 `pe-gui-backup.txt` 却记录：`backup V: -> F:\…\r2-backup.wim: no output`。

**原因：** `std::fs::read_to_string` 要求 UTF-8；中文控制台工具输出是系统代码页（GBK），解码失败返回 `Err`，分支落到"no output"。

**后果：** 在中文系统上产品看不到 DISM / DiskPart 的任何输出文本，因此**无法从输出识别失败**。项目本身已有解码层（`text_parsing::decode_code_page`、`decode_console_bytes`，软硬件信息页在用），但 PE 任务分支没用。

### 4.5 P1 — `mountvol` 退出码被当判据，实际已挂载却判失败

产品日志：`[ESP] mountvol S: /S FAILED with exit code 退出码 1`。

但同一轮里 `S:\format-check.txt`、`S:\find-system.txt` 等**写入全部成功**，说明 `S:` 实际已挂载。即 mountvol 返回 1 但操作成功。

项目自己的注释早已记录过这件事（"mountvol 返回码在实机上不可信：失败时返回 0、成功时反而返回 1"），但 [`esp_store_path_for_pe`](../crates/backuprestore-cli/src/native_gui.rs#L7352) 仍以退出码判定，非零即返回 `None`，导致 `pe_task_execute` 报 `no config`。

## 五、顺带实测确认的事实

### 5.1 PE 内盘符确实漂移

产品自己的卷下拉在 PE 里列出的内容，与 Windows 下对照：

| Windows 下 | PE 内 | 容量 |
|---|---|---|
| `T:` | `D:` | 5.0 GB |
| `P:` | `E:` | 64.0 GB |
| `H:` BRImages | `F:` | 192.0 GB |
| `F:` BRIMG | `G:` | 350.0 GB |
| `C:` | `C:` | 249.5 GB（未变） |

直接支持"任务里保存的盘符不能作为执行期身份"（历史文档第 2 项）。

### 5.2 还原确认框本身是合格的

文案点名了镜像全路径与目标卷，并明确警告"将格式化目标卷，数据不可恢复"。**问题不在确认环节**，而在确认之后缺少输入预检与失败阻断。这一点对修复方案有意义：不需要改交互设计，需要补执行层的闸门。

## 八、验收脚手架自身的两个问题（已记录，未改产品代码）

1. **第一轮驱动无法关闭模态框。** 向 MessageBox 投递 `WM_COMMAND(IDOK)` 未能关闭，驱动在第二个对话框上超时退出。第二轮改为「按控件 ID 取按钮句柄 → 投 `BM_CLICK` → 回读 `IsWindow` 确认消失 → 重试」，实测 6 次内必成。**这是脚手架缺陷，不是产品缺陷**，第一轮日志原样保留。
2. **PowerShell 包装器取不到原生进程退出码**，把已成功的 DISM 挂载误报为失败，随后重复挂载被 DISM 拒绝。改为直接调用原生命令并读 `$LASTEXITCODE`。失败与成功的原始日志都保留，不写成"一次跑通"。
