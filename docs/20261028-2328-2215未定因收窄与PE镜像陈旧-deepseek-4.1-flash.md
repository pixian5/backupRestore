## 2. 2215 当时为什么判成「回落」：缺的不是实验，是仪器

### 2.1 两种完全不同的因果，外观一模一样

| 因果 | 表现 |
| --- | --- |
| **(a) bootmgr 根本没加载 ramdisk** | 固件消费掉一次性启动项 → 回默认项 → 桌面；payload 目录仍在 |
| **(b) ramdisk 加载了、RE 起来了、Recovery.exe 失败 → 失败策略 auto-escape（清理 + `wpeutil reboot`）** | 屏幕闪一下 → 桌面；**payload 目录被清掉**；BCD 一次性项被消费 |

2215 记的是「**bootsequence 被消费、任务仍 boot-requested、无 WIM**」——
「无 WIM」当时被当成「没进 RE」的旁证，其实它正好是 (b) 里 cleanup 的**副作用**
（本轮日志里那两行 `staging directory … removed and verified` 就是它）。

而「任务仍 boot-requested」也不能排除 (b)：auto-escape 的收尾路径与成功路径在状态机上是两套，
2215 没有留下该任务的 `status.json` 快照，无法反推。

### 2.2 为什么当时分辨不了

`crates/backuprestore-cli/src/session_log.rs` 的**持久化镜像**（`<卷根>\BackupRestore-logs\<pid>-<纳秒>\`）
是 **2026-10-17** 才加的（文档头注释明写「修的是日志缺口 1/2：全部在重启瞬间消失」）。
2215 发生在 **10-13** —— 那一轮 RE 内写的一切都在 `X:` 上，`wpeutil reboot` 之后一个字节都不剩。

**所以：2.4.6 那次到底是 (a) 还是 (b)，已不可复核。** 本文件不给结论，只给方法。

## 3. 新的判定方法（可复用，以后查「进没进恢复环境」就照这个）

RE / PE 里程序从 `X:` 跑，但日志会**镜像一份到第一个可写的持久化卷**：

```
<卷根>\BackupRestore-logs\<pid>-<纳秒>\
    session.log                  ← 会话起点 + 镜像目录自身路径
    BackupRestore-init.log
    BackupRestore-escape.log     ← 失败策略：threshold=3 action=auto-escape consecutive_failures=N
    BackupRestore-Recovery-early.log
    Recovery-early.log           ← 各 role 的挂载过程（RECOVERY / SOURCE / IMAGE / WORKSPACE）
    Recovery.log                 ← 步骤 1/4 … 4/4
```

本机现存 4 个会话目录（`C:\BackupRestore-logs\`，F: 上另有 3 个同名目录）：

| 目录 | 时间 | 内容 | 说明 |
| --- | --- | --- | --- |
| `1544-1793197003262726800` | 10-28 22:16 | 6 文件，含完整 `Recovery.log` | **RE 真的跑完了**（§1.2） |
| `1512-1793112216333492500` | — | 读取时报 `PrlJob_GetRetCode: Invalid argument` | 通道抽风，未读到，**不代表空** |
| `1512-1793033093984541700` | 10-27 00:44 | 6 文件，`Recovery.log` 1,334 B | RE 起来了 |
| `1504-1793033976429390000` | 10-27 00:59 | `Recovery.log` 1,134,595 B | RE 起来了，跑了大活 |

**三态判据**：

| 观察 | 结论 |
| --- | --- |
| 会话目录**不存在** | RE/PE **没起来** → 查引导链（BCD `ramdisk=` 规格、固件是否消费一次性项） |
| 有目录但只有 `session.log` / `init` / `escape` | RE 起来了但**极早期就退出** → 看 `BackupRestore-escape.log` 的 `consecutive_failures` |
| 有 `Recovery.log` 的 `STEP n/4` | RE 真的在干活 → 问题在任务本身，不在引导 |

> ★ 从这条起，**不要再拿「重启后看到的画面」当判据**。本轮之前的教训（`经验/10 §A`「选 PE 后一闪回
> Windows」）和这条是同一个母题：**「看起来一样」的两种因果，只能靠持久化痕迹分开。**

## 4. 顺带钉死的三条 `winpeshl.ini` 字节级事实

三份镜像里的 `Windows\System32\winpeshl.ini`（`wimlib-imagex extract … --no-acls` 抽出后按字节核对）：

| 镜像 | 大小 | 内容 | 换行 |
| --- | --- | --- | --- |
| `C:\Users\Public\winre-src\Winre.wim`（**官方母本**） | **53 B** | `[LaunchApp]` / `AppPath=X:\sources\recovery\recenv.exe` | CRLF |
| `C:\Recovery\WindowsRE\Winre.wim`（注册位） | **99 B** | `[LaunchApps]` / `%SYSTEMROOT%\System32\Recovery.exe,recover-env %SYSTEMROOT%\System32\RecoveryTask.env` | **LF** |
| `H:\BRImages\pe-boot.wim`（PE 硬盘版源） | **89 B** | `[LaunchApps]` / `…RecoveryLauncher.cmd` / `…recenv.exe` | LF |

**推论 1（订正 2215 的一处误读）**：2215 §4 把「注入件与原版件的 `winpeshl.ini` 同 99 B / 同哈希
`743F193A`」当作异常线索，其实**是预期的** —— 那份「原版件」本身就是**早就注入过的注册位副本**
（真正的母本是 53 B 的 `[LaunchApp] AppPath=…recenv.exe`）。所以「shell 没被注入」这条从来不是变量。

**推论 2**：注入侧不存在「继承旧 shell」的可能 —— `winre_payload.rs:159`（`stage_static_payload_with_exe`）
无条件 `fs::write(...)` 写契约、`:200` 再按 `required_payload_names()` 拷进 WIM，`:220` 用完 `verify_payload_contract` 回验。
99 B 与代码里的 `EXPECTED_WINRE_SHELL`**逐字节相同**。

## 5. #140 的「PE 一闪回」不是产品缺陷：输入 WIM 陈旧

上一轮把「安装的 PE 起不来」归到「镜像里 `winpeshl.ini` 指向不存在的程序」是对的，
但**责任方判错了候选**。这一轮把三边都对上了：

| 环节 | 事实 |
| --- | --- |
| 镜像构建脚本 `poc/build-backuprestore-pe.ps1` | 会把 `windows/winpe-winpeshl.ini` 拷成 `winpeshl.ini`（`:80`），并按契约校验（`:87-90`），镜像内 `BackupRestorePE.txt` 也由它写（`:116`） |
| 产品安装链路 | 只往 PE WIM 的 `System32` 注入 `Recovery.exe`——本轮复核 `T:\Windows\System32\Recovery.exe` = **存在**；**不写** `winpeshl.ini` |
| 实际用的 `H:\BRImages\pe-boot.wim` | **2026-09-13** 的旧件，89 B 旧式 shell（`RecoveryLauncher.cmd` + `recenv.exe`），这两个程序都不在镜像里 → `winpeshl.log` 记 `[0x80070002]` → 无前台进程 → PE 自动重启 |

**结论**：产品没有「本该写 shell 却没写」的缺陷 —— PE 的 shell 属于**镜像构建**职责，构建脚本已经做了。
缺陷在**输入**：用的是 9 月的旧镜像。`windows/winpe-winpeshl.ini` 在 Rust 侧只出现在
「备份排除清单」（`backuprestore-core/src/lib.rs` 的 `SELF_DEPLOY_FILES`），这是对的，不是漏用。

**要重测 PE 可引导性**：先用当前脚本重出 `pe-boot.wim`，再走一次硬盘版安装 + 引导。

**唯一值得做的产品侧保险（待用户确认，本轮未改代码）**：安装前把待写入的 WIM 挂载（或直接读
`winpeshl.ini`）对比 PE 契约，不符就拒绝并说明原因 —— 与 WinRE 侧 `validate_winre_shell` 对齐。
否则「装成功了但里面什么都起不来」这种结果，用户只能靠重启才发现。

## 7. 教训

1. **「同形不同因」必须先用仪器分开，再谈定因**：(a) 没进 RE 与 (b) 进了 RE 又逃回 Windows，
   在用户眼里一模一样，甚至「payload 消失」也能被两种因果各自解释。本轮之所以能分开，
   只是因为**持久化日志镜像恰好早就存在**，而不是因为设计了新实验。
2. **先查现成仪器，再设计实验**：`session_log.rs` 的镜像机制写了 11 天，2215 之后的几轮都没人用它。
   查「进没进恢复环境」的成本从「再跑一轮重启」降到「`dir` 一个目录」。
3. **反例比新实验便宜**：推翻 10-13 的「必回落」，用的不是新实验，而是上一轮 lease 测试**顺手**跑出来的
   一次成功。★ 每次跑测试都值得回头看一眼它顺带证明了什么。
4. **别把「输入数据陈旧」记成产品缺陷**：PE 的 shell 该由镜像构建负责（脚本已校验），
   产品的职责边界是「按契约注入载荷」。判责任前先把三边（构建脚本 / 产品 / 实际用的件）对上。
5. **「已不可回溯」要明写**：2.4.6 那次是 (a) 还是 (b)，本文件不给结论。把不确定留在纸面上，
   比编一个自洽的因果便宜得多。
