## 1. 三层都是「仪器故障」伪装的

上一轮的结论是：`WINDOW=1` 首跑成功，之后稳定 `GUI_NOT_FOUND`，「疑窗口站/桌面差异」。

本轮用一份**只诊断不判判据**的探针（`_diag-enum-ctx.ps1`）先量读数侧：

```
PID=9356  PROC_SESSION=1
WINSTA=WinSta0  DESKTOP=Default   USER=P8B6\x   INTERACTIVE=True
PROC_COUNT=1  PROC pid=2188 session=1 mainwnd=262942
TOP_LEVEL=96
GUI_CLASS_MATCH=1   ← 主窗口找到了，类名可见、标题 v2.6.66
```

**通道是好的**。所以 `GUI_NOT_FOUND` 与窗口站无关，是驱动脚本自己坏了。三个原因叠在一起：

| # | 真因 | 表现 | 修法 |
|---|---|---|---|
| 1 | **钩子文件过期** | `H:\brwork\gui-token-body.txt` 还指向上一个脚本，于是安静地跑错的脚本、结果文件根本不生成 | 新增 `tools/smoke/run-body.sh`：写钩子→**回读核对**→删旧结果→启动→轮询 `DONE` |
| 2 | **C# 里写了 `[ref]`** | `Add-Type` 编译失败 → 类型没定义；PS 5.1 里这是**非终止错误**，脚本继续跑 → 回调抛异常被吞 → 枚举永远返回 0 | 改 `ref RECT`（合法 C#）；两处 `Add-Type` 各自 `try/catch` 落 `ADDTYPE_ERROR_*`，RS3 建不起来直接 **exit 4** |
| 3 | 失败信息太少 | 只写 `GUI_NOT_FOUND` 一个词，「读不到」与「没有」分不开 | 失败时先打会话/窗口站/桌面/进程/顶层窗口数，再给 `VERDICT=GUI_ENV_BAD｜GUI_WINDOW_MISSING` |

> 教训（与 `经验/05` 一致）：**判据红时先证明读数那一侧对**。这次读数侧连「自己在哪个窗口站」都答不出来，
> 却先被记成了被测对象的问题，白查两小时。

## 2. 修好仪器后抓到的真缺陷：客户区不是 720×480

第一份**真实**读数：

```
CLIENT_W=704 CLIENT_H=441 CHILDREN=8
  RECT id=1401 x=96  y=10  w=612 h=20    → 右边界 708 > 704
  RECT id=1402 x=12  y=44  w=696 h=336   → 右边界 708 > 704
  RECT id=1406 x=642 y=392 w=66  h=28    → 右边界 708 > 704
  RECT id=1407 x=12  y=428 w=696 h=20    → 右边界 708 > 704、下边界 448 > 441
OUTSIDE_COUNT=4
```

**根因**：`CreateWindowExW` 的 `nWidth/nHeight` 是**整窗**尺寸（含边框与标题栏），
而代码注释写的是「标题栏另算，故 height 是客户区高度」——正好写反。
于是 720×480 的窗口只有 704×441 的客户区，按 720×480 摆的控件右侧与底部被裁。

差 4 px，人眼在小屏上几乎看不出来；这正是几何判据存在的理由。

**修法**（`native_gui.rs`）：先用 `AdjustWindowRectEx` 由目标客户区反推整窗尺寸。

```rust
const CLIENT_W: i32 = 720;
const CLIENT_H: i32 = 480;
let style = WS_CAPTION | WS_SYSMENU | WS_VISIBLE;
let mut frame = Rect { left: 0, top: 0, right: CLIENT_W, bottom: CLIENT_H };
AdjustWindowRectEx(&mut frame, style, 0, 0);
let width = frame.right - frame.left;    // 整窗
let height = frame.bottom - frame.top;
```

修复后同一判据：`CLIENT_W=720 CLIENT_H=480 / OUTSIDE_COUNT=0 / OVERLAP_COUNT=0 / ZERO_SIZE=0`。
**判据两侧都红绿过**（修前 4、修后 0），不是自洽。

## 3. 三层判据（含每一项的变异证据）

| 层 | 判据 | 真值来源 | 变异验证 |
|---|---|---|---|
| 几何 | `OVERLAP/OUTSIDE/ZERO_SIZE = 0` | 枚举直接子窗口 + `GetClientRect` | 修前自然读到 `OUTSIDE_COUNT=4`；修后 0 |
| 存在性 | `MISSING_CONTROLS=0` / `BASELINE_STALE=0` / `CLASS_MISMATCH=0` | 签入的 `control-baseline-taskadmin.txt`（8 条 `id\|class`） | 基线多一条 → `MISSING=1`；少一条 → `STALE=1`；`1407` class 改 EDIT → `CLASS_MISMATCH=1`（三次各自单红） |
| 行为 T1 | `COMBO_ITEMS == TASK_DIRS` | 下拉 `CB_GETCOUNT` **与** 磁盘目录数（两条独立代码路径） | 实测 `COMBO_ITEMS=50 TASK_DIRS=50 → T1=1` |

★ 存在性判据的必要性：控件**根本没创建**时，重叠/越界/塌缩三条全是 0（没东西可重叠），
S2 的 `CB_GETCOUNT=50` 也照样绿——少一个「清理工作树」按钮不会有人发现。基线就是补这个洞。

## 5. 仪器基础设施的一处改造

`tools/smoke/gui-clicks.sh` 的 `run_case` 原来**固定 sleep 7 秒就读结果文件**，
读到「写了一半」的文件会让断言少几行 → 假红。改成**轮询到 `DONE` 或超时 20 秒**。
