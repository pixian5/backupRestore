## 1. 缺口的真实形态

`refresh_task_status`（`native_gui.rs:3335`）只解析 `last-task.json` 的五个字段：
`taskId` / `operation` / `taskRoot` / `prepareLog` / `recoveryLog`。

而 `status.json` 才是写 `stage` / `error` 的地方，**界面一次都没读过它**。
`last-task.json` 里其实早就备好了 `statusJson` 绝对路径（准备阶段写入），
只是没有消费方。

后果：任务在恢复环境里失败后，回到 Windows 点「刷新任务状态」，
界面只报「任务目录 / 日志路径」，**没有"失败"二字、没有失败原因**。

实机佐证（`H:\brwork\tasks` 里抄来的原文）：

```json
{
  "taskId": "02138f14-c938-460b-8b1f-d05c72e7a8af",
  "operation": "backup",
  "stage": "failed",
  "progress": 0,
  "updated": "2026-10-22T00:40:59.095332300Z",
  "errorCode": 2,
  "error": ""
}
```

★ 这份样本同时暴露第二件事：**`error` 是空串**。
也就是「失败但没记录原因」在真机上真实存在——界面若静默留空，
用户会以为"没事"。这条被写成硬规则（第 3 节规则 2）。

## 2. 一个连带发现：`status.json` 里根本没有稳定错误码

`write_failure(task, code: i32, error)` 的整型 `code` 装不下 `BR-域-序号`，
调用点传的是 `1` / `2` —— **不同调用点同一个数字含义不同，且无任何消费方**。

而真正的码在 `TaskError::code()` 里（`Io→BR-IO-001`、`Json→BR-IO-002`、
`InvalidTransition→BR-TSK-028`），**从未落盘**。

修法（core）：

- `StatusRecord` 新增 `error_code_text: Option<String>`（`serde(default, skip_serializing_if)`）
- 新增 `write_failure_coded(task, code_text, error, legacy_code)`，
  `write_failure` 委托调用（保持既有调用点不动）
- 新增 `write_recovery_error_coded`，`write_recovery_error` 委托
- 三处 CLI 调用点改传 `error.code()`：
  `windows_prepare.rs:1244`、`main.rs:1551`、`main.rs:2545`

★ **为什么不直接把 `error_code: Option<i32>` 改成 `Option<String>`**：
`H:\brwork\tasks` 里已有 status.json 的 `errorCode` 是整数，改类型会让这些
历史文件反序列化失败——而"读状态"恰恰是排查的第一步。加新字段、旧字段
留作只读，零风险；旧文件读进来 `error_code_text = None`，界面显示"无稳定错误码"。

## 3. 新模块 `status_receipt.rs`（362 行，无条件编译）

三条硬规则：

1. **四种结局分开表述**：`Missing` / `Unreadable` / `Malformed` / `Ok`。
   "读不到"与"读出来是失败"是两件事，混成一句"状态不可用"就无法定位哪侧坏了。
2. **失败但 `error` 为空 = 程序缺陷，必须说破**（实机确有 `error: ""`）。
3. **只要 `error` 有值就展示，不过滤阶段**：`StatusRecord.error` 只在两条失败
   路径写入，创建时恒为 `None`。按阶段过滤会把恢复环境里的**可重试失败**
   （stage 仍是 `capturing`，还要续跑）藏起来——那正是最需要看到的一类。

行数上限：状态框按 9 行设计，最坏情形 = 5 行任务信息 + 4 行状态 = 9 行，
故只在有信息量时才输出（进度仅在 `0 < p < 100` 时输出）。

### ★ 第一版写错了两次键名（最有价值的一条）

第一版用 `serde_json::Value` 手写取值，键名写成 snake_case（`task_id` /
`error_code`），阶段写成 `Failed` / `Capturing`。**全错**：

| 我写的 | 实际落盘 |
|---|---|
| `task_id` | `taskId`（`StatusRecord` 带 `rename_all = "camelCase"`） |
| `error_code` | `errorCode` |
| `Failed` | `failed`（`Stage` 带 `rename_all = "kebab-case"`） |
| `Capturing` | `capturing` |

暴露方式：core 单测报 `unknown variant 'Failed', expected one of …`。
**改成直接反序列化成 `StatusRecord`、按 `Stage` 枚举匹配**——键名与枚举只有
一处真源，这类漂移不可能再发生。教训与"判据红时先怀疑读数那一侧"同源：
这里是**取值那一侧先错了**，而且错得非常自信。

## 4. 实机验收：`tools/win-clicker/_t-refresh-status.ps1`（183 行）

用 GUI 自身令牌提权到会话 1，点 `ID_REFRESH_TASK(1004)`，读 `ID_STATUS(1300)`
真实文本 + `gui.log` 结构化行。四个用例：

| 用例 | 构造 | 实机结果 |
|---|---|---|
| S1 带码失败 | `stage=failed` + `errorCodeText=BR-PE-039` + `error="DISM timeout TEST123"` | 状态框出现码与原因，`LOG_OUTCOME=ok`，8 行 |
| S2 失败无原因 | `stage=failed` + `error=""` | 显示"未记录原因"，`LOG_CODE=none` |
| S3 文件缺失 | `statusJson` 指向不存在的文件 | `LOG_OUTCOME=missing`，6 行 |
| S4 解析失败 | 文件内容 `not json at all` | 显示"解析失败：expected ident at line 1 column 2"，`LOG_OUTCOME=malformed` |

副作用自证：脚本运行期间把 `H:\brwork\last-task.json` 换成测试版，
结尾还原并输出 `RESTORED=1`（还原失败会让这条判据变红，而不是静默留脏数据）。

### ★ 仪器本身也修过两次（"读数那一侧先坏"）

1. **日志取首个匹配 → 读到上一个用例的值**：`gui.log` 每次点击追加 2 行以上，
   `Tail 4` 里混着上一个用例的行。S3 显示 `ok` 就是这么来的。改为取**最后**一次匹配。
2. **`StringBuilder` 封送跨进程 `WM_GETTEXT` 只读回 3 个字符**：
   `TEXT_LEN_RAW=218` 而 `$t.Length=3` —— 状态框明明有 220 字符。
   改用 `Marshal.AllocHGlobal` + `PtrToStringUni` 后读回完整 218 字符。
   ★ 若不先证明读数那一侧对，就会得出"界面没显示"的**假结论**。
