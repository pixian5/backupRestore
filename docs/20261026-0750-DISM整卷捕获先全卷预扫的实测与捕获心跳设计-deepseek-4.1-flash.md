# DISM 整卷捕获「先全卷预扫再写」的实测与捕获心跳设计

- 时间：2026-10-26 07:50（+08）
- 模型：deepseek-4.1-flash
- 版本：v2.6.55
- 性质：**零代码观测课题结案 + 一项产品化改动**
- 前置文档：[P3-b wimlib 捕获 POC](20261026-0450-P3b-wimlib捕获POC-DISM与wimlib捕获侧实机对照-Step-5-Preview.md)

## 1. 为什么做这个观测

P3-b 那次大卷对照（DISM vs wimlib 捕获 `F:` 整卷）最终**两个引擎都卡住**：DISM 跑到 40 分钟只写出 208 字节，wimlib 先快后同样停滞。当时的归因是「`F:` 太满」，而那个归因是**错的**——上一轮把 `dir F:\` 末尾的「可用字节」当成了文件总大小，实际 `Get-Volume` 读数是总容量 349.98 GiB / 已用 78.56 GiB / 剩余 271.43 GiB。

归因错了，立项前提就悬空：到底是引擎有缺陷，还是我们对 DISM 的行为理解有误？这次观测就是为了把这个问题钉死，全部用外部脚本采样，**不改一行产品代码**。

## 2. 观测方法

外部脚本每 30 秒采样五个量（`tools/win-clicker/_probe-sample.ps1`）：

| 字段 | 含义 |
|---|---|
| `SIZE` | 最终镜像名 `probe-f-dism.wim` 的大小 |
| `CAND` | 候选镜像 `<镜像目录>\.br-online-<pid>-<ns>\candidate.wim` 的真实大小 |
| `DISMCPU` | `dism.exe` 累计 CPU 秒 |
| `DISMWSMB` | `dism.exe` 工作集 MB |
| `HFREE` | `H:` 卷剩余字节 |

★ **第一版采样只盯最终镜像名，读到 `SIZE=-1` 就误判成「没开工」**。真相是在线备份先写候选目录，成功后才改名发布——观测对象选错比没观测更危险。

## 3. 实测结论一：DISM 确实「先全卷预扫、后写数据」

捕获 `F:\Program Files`（8.7 GB / 32,732 文件）的逐 10 秒采样：

```
START=07:33:21
T=07:33:31 WIM=208          <- WIM 头，仅此而已
T=07:33:41 WIM=208
...（连续 10 次，100 秒恒为 208 字节）
T=07:35:11 WIM=143216153    <- 第 110 秒，开始写入
T=07:35:21 WIM=696046683
T=07:35:31 WIM=902019236
T=07:35:41 WIM=2279843430
T=07:35:51 WIM=2805631402
FINAL=07:36:01 WIM=3414782392   <- 60 秒内到 3.4 GB，约 68 MB/s
```

**预扫 100 秒，写入 60 秒。** 预扫期间三层同时静默：

1. 镜像文件恒等于 WIM 头（实测恰好 **208 字节**，一字节不涨）；
2. `C:\Windows\Logs\DISM\dism.log` 停在 `Executing command line` 之后**一行不写**；
3. 子进程 stdout 只有两行横幅。

也就是说：**「开头零字节」是正常行为，不是卡死。** 旧版界面上看就是「死了」，因为没有任何一层能说明它在动。

## 4. 实测结论二：排除表与 `/CheckIntegrity` 都不是元凶

原来的怀疑对象是那份 460 行、36,781 字节的排除表（`C:\Windows\SystemTemp\BackupRestore-exclusions.ini`）。做了一个四组合 A/B（`tools/win-clicker/_probe-ab.ps1`，每组硬超时 150 秒）：

| 组合 | 参数 | 结果 |
|---|---|---|
| a-plain | 小目录 | 1 秒内完成，WIM 1,846,638 B |
| b-integrity | + `/CheckIntegrity` | 1 秒内完成，WIM 1,846,264 B |
| c-config | + 同一份 `ConfigFile` | 1 秒内完成，WIM 1,846,286 B |
| d-both | + 两者 | 1 秒内完成，WIM 1,846,368 B |

**四组全部通过**，所以排除表（460 条）与 `/CheckIntegrity` 都排除嫌疑。唯一剩下的变量就是「捕获整卷 `F:\`」。

## 5. 实测结论三：整卷捕获的预扫极长，我上一轮是判早了

整卷 `F:` 那次（06:26:58 起）跑到 58 分钟仍是 208 字节，我把它判成「卡死」并杀掉。用子目录数据外推：`F:` 已用 78.56 GiB，预扫成本随文件数增长，构建卷（`br-target` / `BuildTools` / `BackupRestoreBuild`）里海量小文件会把这个时间放大到数十分钟量级。

**所以那次不是死，是预扫还没完。** 这也解释了 P3-b 里 wimlib「先快后停滞」的同款现象——写入前的遍历成本是共同的，只是 wimlib 会先吐一点数据、看起来更"活"。

★ 教训：**「零产出」在 DISM 捕获里没有判读价值**，必须同时看 CPU 与 I/O 计数，或者干脆等心跳行。

另外顺手记两条与本案相关的负面结论，省得以后重复走：

- `F:` 根上确实有一个自引用联接点 `Documents and Settings -> \\?\Volume{761230e8-...}\Users`，而生成的排除表里**没有**它（只有一条不存在的 `\Mac disk`）。虽然拿它做排除后仍 208 字节（说明它不是本次的主因），但**它应当在排除表里**——详见第 7 节遗留。
- 排除表把 `\Users\desktop.ini\AppData\Local\Temp` 当条目写进去了：`C:\Users` 下的枚举把 `desktop.ini` 当成了用户名。不影响正确性，但说明用户名枚举缺过滤。

## 6. 产品化改动：捕获心跳（v2.6.55）

### 6.1 设计

新模块 `crates/backuprestore-cli/src/capture_heartbeat.rs`：一个**旁路监控线程**，每 30 秒读一次候选镜像大小并写一行判据。

判据行（`text_parsing.rs` 里四个纯函数，**固定前缀 + 纯 ASCII + 不走 i18n**）：

```
CAPTURE_HEARTBEAT elapsed_secs=30 image_bytes=208 phase=pre_scan
CAPTURE_STALL elapsed_secs=600 image_bytes=208 silent_secs=420 phase=pre_scan note=dism_scans_whole_volume_before_first_write
CAPTURE_SUMMARY elapsed_secs=1234 image_bytes=3414782392 samples=41 phase=writing
```

阶段判据 `capture_phase()`：`image_bytes <= 1024` 判 `pre_scan`，否则 `writing`。这个 1024 是给 208 字节的 WIM 头留余量，来自实测而不是猜。

### 6.2 三条边界（都是刻意的）

1. **只观测、不干预**：绝不杀进程、绝不改超时。预扫时长随文件数增长，在这里杀进程会把正常备份一起杀掉。超时仍归用户显式配置的 `dism_timeout` 那个逃生阀管。
2. **不动 `windows_command::run_line`**：那里是「挂起创建 → 加入作业对象 → 恢复」的强一致序列（还带 `KILL_ON_JOB_CLOSE` 与 containment 失败域），为加心跳去改它风险远大于收益。心跳与子进程**没有任何句柄关系**，纯靠 `std::fs::metadata` 旁路读大小。
3. **判据不随语言漂移**：与 `RESTORE_SELFCHECK` 同理，2026-10-25 英文模式终态识别失效那次就是因为拿中文文案当判据。

Drop 时在**主线程**补 `CAPTURE_SUMMARY`（读的是捕获真正结束时刻的大小，而不是最后一次心跳可能已过期 30 秒的采样值）；Drop 的等待上限是一个 250 ms 切片，不会拖住捕获收尾。

### 6.3 埋点位置

| 链路 | 位置 |
|---|---|
| 在线捕获 | `online_operation::capture()`，`/Capture-Image` 与 `/Append-Image` 之前启动 |
| 恢复环境捕获 | `main.rs` 的 `/Append-Image` 与 `/Capture-Image` 两处，各自包一层 |

### 6.4 单测

- `capture_phase_splits_header_only_from_real_writing`：208 / 1024 / 1025 三个边界。
- `capture_heartbeat_lines_are_ascii_and_language_independent`：三行判据纯 ASCII、字段齐全，且停滞行**不得**出现 `failed` 字样（预扫慢 ≠ 失败）。
- `heartbeat_records_heartbeats_then_a_summary`：真实线程，40 ms 间隔，校验心跳行 + 总账 + `phase=pre_scan`。
- `heartbeat_turns_into_a_stall_line_when_the_image_stops_growing`：阈值 0 秒时第一拍就走停滞分支。

全仓 259 + 48 全绿。

## 7. 遗留与下一步

1. **排除表补根级自引用联接点 `\Documents and Settings`**（**已于 v2.6.56 修**）。本次实测它**不是**主因（排除后 58 分钟内仍 208 字节），但它是真的自引用联接点——不排除就等于把 `Users` 整棵树再遍历一遍，预扫时间翻倍。★ 只在**确认是重解析点**时才排除：数据卷上万一真有一个叫这个名字的普通目录，无脑排除会静默丢用户数据。Windows 侧判据必须看 `FILE_ATTRIBUTE_REPARSE_POINT`，**Rust 的 `FileType::is_symlink()` 对目录联接点返回 false**。
2. **用户名枚举过滤非目录项**（**已于 v2.6.56 修**）：排除表里出现过 `\Users\desktop.ini\AppData\Local\Temp`，因为 `C:\Users` 下确实有一个 `desktop.ini` 文件被当成了用户名。
3. **预扫时长不可预估**：目前只能事后看心跳。若要给用户「预计剩余时间」，得先有「已遍历多少」的信号，而 DISM 不提供。**结论：暂不做，先把「在动」说清楚就够了。**
4. **wimlib 是否提默认**：P3-b 的 34% 提速仍然成立，但那次大卷对照无效，如今归因也已订正。**建议维持 DISM 默认 + wimlib 失败兜底**，不再提「反转」。

## 8. 本次踩到的工具坑

- **`Start-Process -ArgumentList` 不会给含空格的参数加引号**：`/CaptureDir:F:\Program Files` 被拆成 `/CaptureDir:F:\Program` + `Files`，DISM 报 `doesn't recognize the command-line option "Files"`。必须自己写成 `'/CaptureDir:"' + $dir + '"'`。
- **`prlctl exec` 的 SYSTEM 通道看不到 `X:` 映射盘**，`--current-user` 才看得到；而 `--current-user` 是标准用户，`CreateFileW` 打不开 `\\.\F:`（Windows error 5）→ 读卷身份失败。**要管理员又要 `X:` 是矛盾的**，所以脚本用 `copy \\Mac\Home\... H:\brwork\` 搬进虚拟机后再带路径执行。
- **`Get-Process -Name dism` 的 `CPU`/`StartTime` 跨用户可能读不到**（`Access is denied`），`StartTime` 一读就抛异常会打断整条管道；判据要用 `Get-CimInstance Win32_Process` 的 `CreationDate` / `KernelModeTime`。
- **`dir /AL` 是找联接点的正确姿势**（`/AL` = 只列重解析点），`Get-ChildItem | Where Attributes -match "ReparsePoint"` 在 prlctl 单行命令里因为引号嵌套写不出来。
