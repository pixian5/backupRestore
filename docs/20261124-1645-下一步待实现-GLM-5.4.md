## 1. 等用户裁定：缺陷 1（离线数据卷还原走不通）的修法

**问题**：「还原数据到非 C 盘」选离线、进恢复环境，三道确认后报
`restore-existing target must be the active Windows volume`。复核成立，详见
[`20261124-1645-离线数据卷还原缺陷复核`](20261124-1645-离线数据卷还原缺陷复核与备份暂停问题-GLM-5.4.md)。

| 方向 | 做法 | 优点 | 代价 |
| --- | --- | --- | --- |
| **一（推荐）** | 准备期接受「数据镜像 → 数据卷」这一种组合 | 能力保留；A 入口（系统还原）的保护原样保留 | 中等：改判据、补单元测试与变异验证、一轮实机验证（要重启进恢复环境） |
| 二 | 界面对数据卷不再提供「进入 Windows RE」，只保留「进入 PE」 | —— | **按现在的代码走不通**：「进入 PE」对数据卷自己也是坏的——界面把它排成「系统替换」，PE 里会格式化数据卷、灌入镜像，然后校验系统文件失败、任务报失败（代码核实，见复核文档 §八）。选它等于把数据卷的离线还原整个砍掉 |

**推荐方案一，但有两个关键点：**

1. 区分「要拦的事故」和「要放行的场景」**必须看镜像**，只看目标卷分不开——
   - 要拦的事故：用户在 A 入口想还原系统盘，目标却落在数据盘上（**系统镜像** → 数据卷）。
   - 要放行的场景：B 入口的数据卷还原（**数据镜像** → 数据卷）。
   - 两种情况下目标都是数据卷。
2. **不能靠镜像的索引名判断，也不能直接用现成的探测函数当开关**——
   `image_admin.rs` 的 `wim_full_windows_probe` 先看索引名，含 `windows` 就直接通过；
   而在线备份写进镜像的默认索引名就是 `Windows Backup`（`online_operation.rs:1443`）。它的「通过」证明不了是系统镜像。
   可靠的做法：只认挂载之后的判定，并把「确认齐全 / 确认缺标记 / 无法判定」分成三种结果；
   或者备份时往副档里记一个「源卷是不是 Windows 卷」的标志，准备期直接读（详见复核文档 §六）。

**同一轮顺手做**：缺陷 2（目标卷默认选中光驱）、缺陷 3（选择框文案不随「格式化」变化）、给这类「非法任务」拒绝补上错误码
（现在 `error_code` 恒为 `null`）。

## 2. 修缺陷 5：「进入 PE」对数据卷也是坏的（代码核实，未实机）

「还原数据到非 C 盘 → 进入 PE」被界面排成 PE 的 `restore`（系统替换）：按镜像索引名放行（默认索引名就是 `Windows Backup`）→
**格式化数据卷** → 灌入镜像 → 校验系统文件失败 → 任务报失败。PE 链里专门为数据卷准备的 `data`（数据覆盖）分支，
产品里没有任何界面入口在用。基线测试没有测过这一条（测试机没装预安装环境）。

- **修法方向**：界面排队时，数据卷还原改用 PE 的 `data` 操作。**修缺陷 1 时不要顺手把界面改成「只留 PE」。**
- **实机验证**：装预安装环境 → 用数据卷镜像走「进入 PE」→ 看 `runtime.json` 停在哪个阶段。目标必须是可牺牲的测试卷。
- 详见 [`20261124-1645-离线数据卷还原缺陷复核`](20261124-1645-离线数据卷还原缺陷复核与备份暂停问题-GLM-5.4.md) §八。

## 3. 修缺陷 4：「备份时按暂停无效」（已坐实，修法二选一）

**现象**：备份进行中按「暂停(P)」或 P 键，按钮翻成「继续(P)」、日志写「将在下一个步骤边界挂起」，
但备份一路跑完并自动重启。实机证据与代码位置见
[`20261124-1645-离线数据卷还原缺陷复核`](20261124-1645-离线数据卷还原缺陷复核与备份暂停问题-GLM-5.4.md) §七。

| 修法 | 含义 | 评价 |
| --- | --- | --- |
| **备份时隐藏或禁用「暂停(P)」按钮，并注明「备份不支持暂停」** | 界面不再给出一个做不到的承诺 | **倾向这个**：改动小，也更诚实。捕获交给 DISM 子进程，本来就没法中途停 |
| 在备份链「捕获结束 → 校验」这个边界加一次暂停检查 | 点了暂停，备份会在捕获结束后停住，按「继续」再走 | 与用户对「暂停」的直觉不一致；恢复环境里的「继续」也要跟着验证 |

## 7. 测试设施与流程

1. **安全用例门禁第 0 步按用例区分前提**（现在两个夹具缺失会挡住不需要夹具的用例）。
2. **用户主动取消的任务记录原因**（现在错误是空串、错误码是 1）。
3. **不提权运行命令行时明确报「需要管理员」并返回非零**（现在是退出码 0 加误导性的结论）。
4. **副档里补系统版本信息**（现在 `windowsEdition` 等都是 `unknown`，界面显示「版本未知」）。
5. **根治部署前置检查的假红**：让构建清单记录源码指纹，检查改成比指纹而不是比时间
   （需要重新构建部署，二进制哈希会变，要配一轮实机冒烟——所以留到下次有产品改动时一起做）。

（「改动-复验对应表」脚本化已于 2026-11-24 晚完成：`tools/test/reverify-map.py`，见 `经验/06` §9。）

## 8. 建议的顺序

1. 你裁定缺陷 1 的修法 → 修（连带缺陷 2、3 与错误码）→ 实机验证。
2. 缺陷 4（备份时暂停无效）与缺陷 5（进入 PE 对数据卷是坏的）都是界面或排队处的小改动，可以和第 1 项合成一版；
   实机验证各用一轮备份 / 一次 PE 往返。
3. 你指定一个「可以抹系统盘」的时间，补上系统盘还原（§4）；在做第 1 项的实机验证时顺带做最省事。

5. 其余按 §6、§7 排。

## 9. 接手时必须知道的五条

1. **虚拟机设置一律不改**（[`README.md`](../README.md) §五第 9 条）。要用就自己开，用完休眠。
   在「已暂停」状态下休眠的，唤醒后仍然是「已暂停」，要再唤醒一次。
2. **`tools/vm/preflight.sh` 现在会报一项假红**（部署件早于提交），以哈希 `812ac52d…0292a` 为准；重新构建部署后自然恢复。
3. **备份校验一步如果很慢**，先看日志里有没有 `Image hash computed: backend=`：没有 = 跑的是旧版本；`software` = 快速路径没走到。
4. **要判断「有没有某行中文日志」，读原样拷出来的文件**。经 `vrun "type …"` 落盘的副本删光了非 ASCII 字符，
   搜不到不等于没有（2026-11-24 因此错降级过一条已坐实的缺陷）。
5. **改了产品代码，先跑 `python3 tools/test/reverify-map.py`** 看必须重跑哪些实机项；`UNMAPPED=` 的文件要人来判断。
