## 1. 五条判据（全部计数，全部必须为 0）

| 判据 | 含义 | 抓什么 |
|---|---|---|
| `OVERLAP_COUNT` | 两个可见兄弟控件占据同一像素 | 顶栏压入口（上轮，实测 36 对） |
| `OUTSIDE_COUNT` | 控件超出客户区 | 长文本/大窗口把控件顶出可视区 |
| `TEXT_CLIPPED` | BUTTON/STATIC 的文字比控件宽 | 按钮文字被裁 |
| `TEXT_OVERFLOW` | 多行 EDIT 装不下自己的行数 | **最后一行被切成半截** |
| `ZERO_SIZE` | 可见但宽或高为 0 | 控件塌缩（旧代码直接跳过，等于静默通过） |

伴随断言不可省：`PAGES_CHECKED=5`（防「只查一页」复活）、`CLIENT_W=`（防枚举到空集也算通过）、
`DONE`（防中途挂死但文件已写了几行）。

> `PARTIAL_LINE`（按行高取整余数）已被**撤掉**：装得下时余数只是底部留白，不是缺陷；
> 装不下已被 `TEXT_OVERFLOW` 覆盖。留着一个「永远 0 且不会红」的计数，比没有更糟。

## 2. 实现里踩到的四个坑（每个都让判据「看起来在工作」）

### 2.1 `SendMessageTimeout` 的返回值不是答案

```csharp
// 错：返回 1 = 调用成功，不是行数
public static int LineCountOf(IntPtr h) { IntPtr res; return (int)SendMsgL(h, 0x00BA, ...); }
```
症状：`EM_GETLINECOUNT` 恒返回 **1**、`WM_GETFONT` 恒返回 **1**（拿去 `SelectObject` 必然失败
→ 全程用 DC 默认字体量，宽度/行高全错）。改成读 `out res` 后，行数立刻变成真实的 9/10。

**判据红的时候先证明读数那一侧是对的**——这次是读数侧直接骗人。

### 2.2 `EM_POSFROMCHAR` 只被 RichEdit 支持

想「问控件最后一行画在哪」，用 `EM_POSFROMCHAR`（0x00D6）——标准 EDIT 返回 `(0,0)`。
换 `DrawTextW + DT_CALCRECT | DT_EDITCONTROL`，但它按 `tmHeight` 算，**也和真实渲染不一致**。

### 2.3 行距是 14 px，不是 12 px

实测 `SimSun 9pt`：`tmHeight = 12`、`tmExternalLeading = 2`。EDIT 排版用 **`tmHeight + extLead = 14`**。

用 12 算：9 行 = 108 px，而 `availH = 108` → 判「装得下」；**屏幕上最后一行明明被切成半截**
（截图确诊）。改成 14 后：9 行 = 126 > 108 → 红，与眼睛一致。

### 2.4 `Add-Type` 失败是**非终止错误**

给 `ref POINT` 加了个 P/Invoke 声明却忘了定义 `POINT` 结构 → `Add-Type` 编译失败
→ 但 PowerShell 继续往下跑 → `[Tf]` 不存在 → `EnumWindows` 没执行 → 报
`MAIN_WINDOW_NOT_FOUND`。而界面上窗口明明在。

**「找不到窗口」和「类没定义」在报告里长得一样**。正式脚本里把 `Add-Type` 包进
`try/catch` 并写 `ADDTYPE_ERROR=`，这个静默失败才算堵住。

### 2.5 还有第五个：我自己裁错了图

第一次判定「130 px 版本已修好」，依据是一张 2× 放大的裁剪图。后来复核发现那张图的
**裁剪下边界正好切在最后一行中间**——不是控件切了字，是我切了图。整图缩略一看就清楚了。

> 教训与「先证明读数那侧」同源：**截图也是仪器**。判定「字被切」必须让裁剪框的边界
> 落在控件边框之外。

## 3. 修法：高度按「最坏行数 × 行距」

```rust
// 详情框：最坏 = 「还原数据到非 C 盘」页的目标卷详情 10 行
// （该页设备详情有一行 954 px > 可用 950 px，软换行多出一行）→ 140 px
let details_height = 148;   // 140 + 4 文本区边距 + 4 余量

// 状态/提示框：最长 9 行（restore 页）→ 126 px
let status_height = 148;    // 实测 EM_GETRECT 比控件高少 14 px → availH 134，余 8
let image_y = status_y + 168;  // ★ 下方行距必须跟着改，否则新高度压住下一行
```

三条原则：

1. **按最坏的页算，不按当前页算**。五页的行数分别是 8/9/10 —— 按 backup 页的 8 行调，
   切到 restore 页就露馅。这与「两排控件共用 y 要按最坏宽度核算」是同一条。
2. **高度变化必须连带改下面的 `status_y + N`**。146 → 154 → 168 三次改动，
   每次都是「高度 + 20」的魔数在跟。
3. **宁可滚，也不要切半行**。内容超长时靠 `WS_VSCROLL` 滚动，不靠缩字/缩框。

## 4. 变异验证（每条判据都单独弄红一次）

| 变异 | 结果 |
|---|---|
| `details_height = 112` | `TEXT_OVERFLOW=5`（每页 1 个详情框；restore_nonC 的 10 行 need=140） |
| 状态框宽度 `client_width + 200` | `OUTSIDE_COUNT=5`（`x=20 w=1375 client=1175`） |
| `view_logs_w = 20` | `TEXT_CLIPPED=5`（`clientW=20 textW=48`） |
| `view_logs_w = 0` | `ZERO_SIZE=5`（`w=0 h=24`） |
| `TOP_BAR_Y = 60`（上轮） | `OVERLAP_COUNT=36` |

**一次只弄红一条、其余保持 0**——这样才能证明「这个计数是这条判据在驱动」，而不是
一堆东西一起响。

> 顺带一条反例：第一次把 `view_logs_w` 压到 **50** 时 `TEXT_CLIPPED=0`。
> 不是判据坏了，是中文 9pt 每字 12 px、「查看日志」4 字 = 48 px **刚好装得下**。
> 变异不够狠 = 假绿，得再压到 20 才见真章。

## 7. 可复用的钉子

1. **判据全绿时先证它会红**。今天四条判据四条都做了变异；不做的话，「全 0」可能只是
   「脚本根本没跑」——事实上本轮就出现过两次（`Add-Type` 静默失败、钩子指向旧脚本）。
2. **读数侧先自证**：`SendMessageTimeout` 返回 1、`EM_POSFROMCHAR` 返回 0、截图裁剪框切字
   ——三次都是仪器骗人，三次都长得像产品缺陷。
3. **「装得下」的判据必须用渲染行距（`tmHeight + extLead`）**，不能用 `tmHeight`。
   差 2 px/行 × 9 行 = 18 px，正好是一行半。
4. **高度写死就要写清依据**：注释里写「最坏 10 行 × 14 px + 边距」，下次加字段的人
   才知道要重算。
5. **`Add-Type` / `iex` 这类「加载即失败」的环节必须 try/catch 并落盘**，否则报出来的
   是下游症状（找不到窗口），不是真因（类没定义）。
6. **变异不够狠 = 假绿**：压到 50 px 时判据仍绿，因为 4 个汉字 48 px。判据的灵敏度
   要按「最坏内容」设计，不是按「当前内容」。
