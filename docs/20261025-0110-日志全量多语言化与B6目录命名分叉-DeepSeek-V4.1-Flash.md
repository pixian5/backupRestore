### 翻译前做的安全检查（这一步最关键）

先扫出**所有中文判据**（`contains`/`starts_with`/`ends_with`/`==` 用中文串），共 83 处，逐类核对「这条日志翻译了会不会打断判据」：

| 判据在哪 | 结论 |
|---|---|
| `text_parsing.rs` 的 STEP 解析 | **安全**：只认 `line.find("STEP ")` 与 `n/m` 数字，中文后缀只是给人看的阶段名 |
| `text_parsing.rs` 的 `bcdedit` 解析（`启动序列`/`设备`/`标识符`） | **不动**：那是**系统**的本地化输出，不是我们的文案；且已双语（`bootsequence`/`device`/`identifier`） |
| `failure_policy::classify_apply_failure` | **安全**：只认 DISM/wimlib 输出原文与 `CmdOutcome` 的 Display（`超时` 等），不读这些文案 |
| `online_operation` 的单测断言 | **安全**：断言的是 `step1_notice()` 的返回值，测试跑在默认中文下 |

★ 特意给 `cause_*` 的**英文措辞**定了纪律（写进表注释）：不能出现分类模式的整串（`access is denied` / `not enough space` / `disk is full` / `being used by another process` / `sharing violation`），否则 Busy 的文案会被认成 AccessDenied。语义本来就一致的（`corrupt` / `timed out`）保留。

## ② B6：备份任务目录不再叫 `online`

**旧问题**：备份走 `online_operation` 模块，目录名固定 `BackupRestore-online-<pid>-<nanos>`——名字看着像还原，翻日志时容易找错方向。一直挂着「改动面大、不紧急」。

**改法**：`online_log::resolve_dir(operation)`，目录标记按**白名单**分叉：

```rust
fn dir_tag(operation: &str) -> &'static str {
    match operation.trim().to_ascii_lowercase().as_str() {
        "backup" => "backup",
        "restore-existing" | "restore" => "restore",
        "create-secondary" => "secondary",
        "probe" => "probe",
        _ => "online",
    }
}
```

★ 白名单的理由：**绝不把外部字符串直接拼进路径**。若照抄 `operation` 原值，`--operation ../../evil` 就能把目录建到别处。不认识的一律回 `online`。

单测 3 条：标记映射（含大小写/空白/非法输入的回落）、备份目录名不含 `online`、`resolve_dir` 仍挂在统一日志根下。

## ③ CLI 也读界面选过的语言

**旧问题**：`i18n::init_from_env()` 只看 `BACKUPRESTORE_LANG`。用户在界面里选了 English，命令行日志照样中文——两套口径对不上。

**新优先级**：`BACKUPRESTORE_LANG` > `BackupRestore.settings.ini` 的 `ui_language` > 中文。

★ 环境变量仍然**最高**：自动化脚本要确定性，不能被某台机器上界面选过什么影响。值不认识（如 `fr`）不当作显式指定，继续往下看界面偏好。

键名做成**单一来源** `i18n::SETTINGS_UI_LANGUAGE_KEY`，`native_gui` 引用它（两处各写一份字面量迟早不同步）。

抽纯函数 `parse_settings_language(&str)` + 2 条单测（含「注释里出现同名字样不算数」——否则注释能改行为）。

## ④ 又一个门控坑：常量住在门控模块里

改完跑 `cargo check --workspace`，E0433：

```
error[E0433]: cannot find `failure_policy` in `crate`
  --> crates/backuprestore-cli/src/i18n.rs:100
```

**根因**：`i18n` 是**无条件编译**的（`text_parsing` 要用它的判据文案），而它读设置文件时引用了 `failure_policy::SETTINGS_FILE_NAME`——`failure_policy` 是 `cfg(any(windows, test))`。

**修法**（治本）：新建 `settings_file.rs`（无平台依赖、无条件编译），常量搬过去；`failure_policy` 用 `pub(crate) use` 重导出保持旧路径有效。

这是**同一天第二次**踩「门控模块里的东西被无条件模块引用」：
- 第一次：`MessageLanguage` 住在 `pe_safety`
- 第二次：`SETTINGS_FILE_NAME` 住在 `failure_policy`

**规则**：一个模块一旦要无条件编译，它引用的所有东西也必须是无条件可用的。

### 没做的：`err()` 的 244 处中文

日志清到 0 了，但 `crate::err("中文…")` 还有 **244 处**（含 26 处测试文件）。**本轮不动**，理由：

1. 这些是**维护者诊断信息**（进 `status.json`、弹窗、CLI stderr），不是流程状态行；
2. 26+ 处单测用中文断言错误文案（`unwrap_err().to_string().contains("…")`），改文案要连带改一堆断言，回归风险高于收益；
3. 真给自动化用的判据已经走 `--json`（结构化字段），不依赖任何文案；
4. 用户可见的**流程结论**已经在日志侧双语（本轮清的那 97 处就是这些）。

要真正解决，正确方向不是「翻译 244 条」，而是**给 TaskError 加错误码**，文案按码查表——那是独立一轮的活。
