## 3. 今天五次运行的成败归因（接手方必须理解，全部有证据）

| # | 时间 | 运行 | 结果 | 归因 |
| --- | --- | --- | --- | --- |
| 1 | 10:53 | `95ab0a7f` 原始阶段 3（GLM） | 失败 @ boot-repaired | **resumeobject 不对称**（真因，见下） |
| 2 | 15:35 | GLM 重试 | RE 未自动执行 | **未明**（勿轻信「快照嫌疑」，已被 #5 证伪） |
| 3 | 19:46 | resume 重试 | 失败（同一错误） | **载荷 WIM 是 08:03 暂存的旧二进制，修复没运行** |
| 4 | 20:38 | 全新 prepare 后首次进 RE | 未自动执行 + VM 停机一次 | **未明** |
| 5 | 20:47→12:53 | 同任务继续 | **成功** | **2.5.5 修复在新载荷里真实执行** |

### 3.1 失败 #1 的根因（证据链闭合）

1. 任务快照 `bcd-before-bootmgr.txt` 的 bootmgr 块**无 resumeobject 字段**（GBK 解码提取确认）→ `previous=None`；
2. **BCDBoot 为新系统凭空建一个 resumeobject**（与新 loader 是兄弟 GUID：`{66375ee0}` vs `{66375ee1}`；
   成功运行里同样复现 `{2ad660f2}` vs `{2ad660f3}`——**BCDBoot 固有行为**）；
3. 修复前代码 `if let Some(resume_object) = &previous.resume_object { 写回 }` **无 else 分支** → 新建的没人删；
4. 三项联合校验把 `(实时=Some, 快照=None)` 判失配 → 报
   `"Boot Manager default or secondary display order could not be preserved"`，**确定性失败**（条件不随时间变，重试必然同样失败）；
5. 同时证明 default/displayorder 当时都对：日志有 `/set {bootmgr} default {12e3701c}` 返回「操作成功完成」，回读一致——**唯一失配项就是 resumeobject**。

2.5.5 修法：补 else-if 分支，快照无而实时有 → `/deletevalue {bootmgr} resumeobject`（留着还会让休眠恢复走进第二系统）。
**成功运行的直接证据**：`[12:53:03.38] running bcdedit.exe /store Z:\…\BCD /deletevalue {bootmgr} resumeobject`。

**顺带证伪了 1904 文档的三个「实锤缺陷」**：
- 缺陷 A「assert 只报错不自愈」→ 不成立：`assert_boot_default_preserved` 是回读+自愈+再回读，#3 的日志有「BCDBoot /d 已生效：默认启动项仍指向原主系统」；
- 缺陷 B「失败后 default 留在半成品上」→ 不成立：日志/回读/实时 BCD 三证一致，default 从未离开主系统；
- 缺陷 C「bcdboot 后要主动回读」→ 就是缺陷 A 那个函数，已存在。

### 3.2 resume 的验证陷阱（最重要的新经验）

**resume 只重新武装启动项，复用 prepare 时暂存的载荷 WIM**（`H:\BackupRestoreRE\<任务>\Winre.wim`，
源码 `resume_task` 只 `rearm` + `shutdown`）。所以：

> **改了 RE 侧恢复代码后，用 resume 验证必然是旧代码假象——必须全新 prepare（才会重新暂存载荷）。**
> `build-win.sh --deploy` 只刷 `H:\brwork` 和包目录，不动已暂存载荷。

配套经验：
- 失败的 RE 运行会**重新武装一次性启动项形成 RE 循环**——快照回滚是唯一干净脱身（BCD 三行回滚覆盖不了循环状态）；
- `prepare` 默认武装+**立即重启**；只想验证参数/解除阻塞时必须带 `--no-reboot`（本轮忘带过一次，非破坏但白跑一趟 RE）。

## 5. 操作手册

### 构建部署

```bash
./build-win.sh --deploy   # 宿主交叉编译 + 部署（四处 SHA 校验）
# macOS 快速类型检查：RUSTFLAGS 照 build-win.sh，cargo check --all-targets --target aarch64-pc-windows-msvc -p backuprestore-cli
# 部署后必须 UTF-8 字符串比对确认二进制含新代码（Rust 字面量在二进制里是 UTF-8）
# 版本三处同步：VERSION + 两个 Cargo.toml；纯文档/验证轮不升版本
```

### VM 与通道

- **`prlctl` 用完整路径 `/usr/local/bin/prlctl`**（后台任务 shell 里 PATH 会丢）。
- prlctl exec 间歇抖动（`Unable to open new session`）：重试。**复合长脚本会神秘挂起且 0 字节输出——
  拆成单步命令、每步验证**（本轮反复验证此坑）。复杂命令写 .ps1 → UTF-16LE base64 → `-EncodedCommand`。
- RE 里 prlctl exec 不可用（无 Tools）；宿主侧判断 RE 是否真在干活 =
  看 `.pvm` 里快照层 `.hds` 的 mtime/size 是否变化（写入会持续更新）。
- **截图取证**：`prlctl capture`；**拿到图就立刻看**（本轮教训：只算哈希不看图，报错画面干等三分钟）。
  任务在 RE 里是无头执行，画面静止属正常；判断卡死用磁盘写入而不是画面。
- GUI 自动化（TCP agent、坐标表、控件 ID、坑）见 `docs/20261014-0126-…md`（权威）与 1904 文档 §6
  （1153×954 坐标；入口名**禁止改名**）。纯净 GUI 验收确认链：`tools/win-clicker/restart-gui-plain.ps1`。

### 任务/BCD 运维

- prepare 被非终态任务阻塞 → `Prepared/BootRequested/RecoveryStarted/Preflight` 可 `abandon-task`；
  **`BootRepaired` 及之后不可 abandon**（目标卷已改写），只能 resume 或人工：**备份任务目录 →
  status.json 的 `stage` 和 task.json 的 `status` 改 `failed`**（设计内逃生口，本轮实测有效）。
  ⚠️ abandon-task 的 BCD 快照回写（`bcdedit /import`）在联机态可能失败——失败就转人工路径。
- BCD 手术顺序：**先摘引用（`/deletevalue`）再删对象（`/delete {guid} /cleanup`）**；
  删前全量 `/enum all /v` 存证；`/cleanup` 会连带清从属对象（报「找不到指定文件」属正常）。
- 引导类改动前抄 `{bootmgr}` 三行（default/displayorder/resumeobject），改坏逐项 `/set` 写回；
  `bcdedit /export` 与 `/import` 在联机态不可靠。测试前拍快照（用户铁律，本轮救过场）；全程最多 1 个。
- 改 BCD / RE 卡住**绝不反复强停重启**（会触发系统还原挂起）——菜单关机或宿主侧救援。

### 日志/取证

- RE 主日志 `H:\BRImages\Recovery.log`（追加式）；任务目录 `H:\brwork\tasks\<id>\`；
  任务快照与 bcdedit 重定向文件是 **GBK**：`[IO.File]::ReadAllText($f, [Text.Encoding]::GetEncoding(936))`。
- **取证别用关键字过滤 bcdedit 输出**：`displayorder` 续行无字段名，一过滤就像「只剩一项」。看整块。
- 控制台 GBK 乱码不是文件坏了；`ConvertFrom-Json` 可能截断中文字段。
