# 对照实验：镜像卷载荷在当前环境确实进不了 WinRE（我的假设被否证）

> 模型：Claude Sonnet 5
> 日期：2026-10-13 19:36
> 实验版本：2.4.5 代码 + **临时把 `ReStaging.volume` 改回 `image_volume`**（即 2.4.4 行为），
> 构建哈希 `61e7fd62ac48083d7475892f05da7d613bf1d77e00fbf7f84fcc767b4365f69a`
> 起因：用户质疑豆包 2.4.5「载荷改放系统卷」的根因与代价——
> 「放 C: 污染了 C:」「我记得很早之前能直接修改 RE 的 WIM 创作副本进入 RE」

## 一、用户的质疑有硬证据，不是记错

| 证据 | 内容 |
|---|---|
| [09-29 PoC](./20260929-1300-pe-channel-poc-winre-wim-boots-from-image-volume.md) | 复制 `Winre.wim` → 注入载荷 → **放镜像卷** → 自建 BCD 条目 → **成功进 PE**；注册位字节未变、BCD diff 为空。**正是用户记的那件事** |
| [1935 文档](./20261012-1935-新启动通道盘符解析回归根因与修复方向-Step-5-Preview.md) 第三节 | 标题就是「这是今天发生的回归（不是一直如此）」：10-11 的 backup 任务 **success**，载荷在 `H:\BackupRestoreRE\...`（数据卷），同一盘符 10-11 可解析 |

所以「数据卷不行」**从来不是产品的固有设计限制**，而是某个时点出现的环境变化。1935 自己把诱因列为「待查」（Windows 更新或另一会话的 BCD 改动），并指出当天 bootmgr 的 `device` 从 `\Device\HarddiskVolume2` 变成了 `S:`。

## 二、我的假设：device 形态是诱因 —— **已被实验否证**

实验前实测 bootmgr 已自行恢复为 `device partition=\Device\HarddiskVolume2`（与 10-11 成功时同形态），
ESP 当前无盘符。我据此假设「把载荷放回镜像卷应当又能进 WinRE」。

### 实验设计（对标 1935 实验 #4）

- 代码：2.4.5 基础上仅把 `ReStaging.volume` 从 `recovery` 改回 `image_volume`
- 命令：`prepare --operation backup --source-drive T --image-path F:\BRImages\test-244-imagevol.wim --allow-destructive`
- 非破坏性：backup 不格式化任何卷；回滚材料（`default`/`displayorder`/`timeout`/`device`）已先行记录

### 实测记录（任务 `6d41ee94-6c2c-40a7-9a89-4bffb5c02fe0`）

载荷与 BCD 条目**都写对了**：

```
11:22:50  payload staged at F:\BackupRestoreRE\6d41ee94-…\Winre.wim sha256=cd16e994…
11:22:51  readback device=ramdisk=[F:]\BackupRestoreRE\6d41ee94-…\Winre.wim,{6c70c10b-…}
11:22:57  one-shot bootsequence armed at {6c70c10c-…}
```

`boot-entry.json` 的 `wimVolume` = disk2/part2、375GB NTFS、`driveLetter: F`，`wimPath` 为 F: 路径。

结果：

| 判据 | 实测 |
|---|---|
| 是否真重启 | ✅ `LastBootUpTime = 19:23:24`（prepare 19:22:57 武装） |
| bootsequence | **已被消费**（`NO_BOOTSEQUENCE`） |
| 任务 stage | **仍为 `boot-requested`、progress 2、updated 11:22:57Z**（= 武装时刻，重启后从未推进） |
| 备份 WIM | **未生成** |

**即 bootmgr 消费掉一次性启动却没加载 `[F:]` 的 ramdisk，直接回落进 Windows。**
与 1935 的失败签名一致。**结论：在当前环境下，数据卷载荷确实进不了 WinRE；
bootmgr 的 `device` 形态不是诱因（它已是设备路径形式，照样失败）。豆包 2.4.5 的修复方向成立。**

## 三、但用户的两点质疑仍然有效

1. **历史成功是事实，环境差异仍未查明**：09-29 PoC 与 10-11 实跑都成功过。本实验只证明
   「当前环境不行」，没能解释「当时为什么行」。可疑变量（已排除 device 形态）还剩：
   Parallels 版本（09-29 是 26.4.2，期间升过 27）、VM 固件设置、Windows 累积更新。
   **这条留作未解之谜记录，不要再把它当"原理限制"写进结论**——它只是当前环境的实测事实。
2. **放 C: 的代价是真的**，与根因对错无关：
   - 污染系统卷（用户明确反对）；
   - **单系统还原（restore-existing）的目标就是 C:，流程要格式化 C:** → 载荷与
     `C:\Recovery\WindowsRE\boot.sdi` 被抹掉 → **断电后 `resume` 续跑断链**
     （项目有状态机专门支持断电续跑）。`validate_volume_roles` **不覆盖 `re_staging`**，
     目前没有任何闸门拦这个冲突。
   - 09-29 PoC 当初选镜像卷的理由之一正是「载荷在镜像卷，不在 Windows servicing 管辖区」。

## 五、建议的下一步（需用户拍板）

载荷位置是「能进 WinRE」与「不污染 C: / 保住断电续跑」之间的取舍：

- **A. 维持 2.4.5（载荷放 C:）**，但补一道闸：prepare 检测到「载荷卷 == 还原目标卷」时
  明确告知「本次断电需重新开始」，并在 `resume` 路径检测载荷丢失后回退到注册位 WinRE。
- **B. 按操作分流**：backup / create-secondary 的目标不是系统卷，载荷可留镜像卷
  （但当前环境数据卷进不去，等于不可行）；仅 restore-existing 放 C:。
- **C. 继续查「当时为什么行」**：对比 Parallels 版本/固件/更新历史，若能恢复数据卷可解析，
  则回到 09-29 PoC 的无污染方案。成本高、不确定。

我的倾向是 **A**（立即可做、覆盖已知风险），同时把 C 作为后台待查项。
