- **时间**：2026-10-25 00:40
- **版本**：v2.6.42（基线 commit `06259b5`，上一版 `d5c9a34` = 文档订正）
- **模型**：DeepSeek-V4.1-Flash
- **性质**：改产品代码（GUI 行为 + 模块门控）

## 一句话结论

上一轮刚把「点一下切英文」打通，顺手发现它是**半截功能**——切完关掉再开又回中文。本轮把它持久化到 `BackupRestore.settings.ini`；做的时候又撞出 v2.6.41 留下的一个**编译缺陷**：`cargo test` 全绿，但 macOS 上不带 `test` 的 `cargo check` 直接挂。

## ① 语言偏好持久化

### 问题

`apply_language` 只改进程内的 `static Language` 和控件文本，**不落盘**。于是：

```
切到 English → 界面英文 → 关掉 → 再开 → 又是中文
```

同文件里 `failure_threshold` / `failure_action` / `dism_timeout_secs` 都是持久化的，唯独语言不是——开关看起来像"临时的"。

### 做法

- `BackupRestore.settings.ini` 新增一键：`ui_language=zh|en`
- 启动：`load_ui_language_pref()` 决定语言下拉框的初始索引（0=中文 / 1=English）
- 切换：**只在 `CBN_SELCHANGE` 分支**保存（初始化不写盘，避免每次启动都改文件时间戳）
- 文件缺失 / 读失败 / 值不认识 → 中文（GUI 必须能起来）

### 两个必须踩对的细节

**A. 只能合并写，不能整文件重写**

`BackupRestore.settings.ini` 是**共享文件**，`failure_policy` 与 `dism_timeout` 都往里写。整文件重写会把别人的键静默冲掉——用户切一次语言，失败策略和 DISM 上限一起回默认，事后极难归因。所以：只过滤掉 `ui_language=` 这一行，其余原样保留。

**B. 注释也不能整批丢**

同文件里 `failure_policy::save_to_dir` 的做法是「所有注释行整行丢弃再重写自己的」——那会顺手抹掉 `dism_timeout` 的说明，而且如果不重写就会每次保存多 3 行、文件线性膨胀（那里注释记着这个教训）。

本轮只剔除**自己那一条**（`# ui_language:` 前缀），别人的注释原样留着：

```rust
if trimmed.starts_with("# ui_language:") { return false; }      // 自己的，重写
if trimmed.starts_with('#') || trimmed.starts_with(';') { return true; }  // 别人的，留
```

### 实测（四条，逐条有输出）

| 验证 | 结果 |
|---|---|
| 切英文 → 重启 GUI | 界面**直接英文**（`Language: English` / `Refresh environment`），无需再点 |
| 切中文 → 重启 GUI | 界面**直接中文**（`语言：中文` / `刷新环境`） |
| 种子 ini 里放 `failure_threshold=7` / `failure_action=pause` / `dism_timeout_secs=300` 再切语言 | 三个键**全部保留**，只有 `ui_language` 从 zh 变 en |
| 连切两次 | 文件仍是 6 行，`# ui_language:` 注释只有一条——**不膨胀** |

## ② 顺带修的编译缺陷：`cargo test` 过 ≠ 构建过

改完语言持久化跑 `cargo check --workspace`，直接 5 个 E0433：

```
error[E0433]: cannot find `i18n` in `crate`
  --> crates/backuprestore-cli/src/text_parsing.rs:754
error[E0433]: cannot find `pe_safety` in `crate`
  --> crates/backuprestore-cli/src/text_parsing.rs:755
```

### 根因

| 模块 | 门控 |
|---|---|
| `mod text_parsing;` | **无条件**（只加了 `cfg_attr(not(windows), allow(dead_code))`） |
| `mod i18n;` | `#[cfg(any(windows, test))]` |
| `mod pe_safety;` | `#[cfg(any(windows, test))]` |

v2.6.41 为了让终态识别双语都认，在 `text_parsing` 里写了 `crate::i18n::msg_in(...)`。于是：

- `cargo test` → `test` cfg 成立 → `i18n` 编译 → **全绿**
- `cargo check`（不带 test）→ `i18n` 被 cfg 掉 → **E0433**

**教训**：`cargo test` 通过不代表构建通过。带 `test` 门控的模块被无条件模块引用时，这个缺口只在非 test 构建暴露。要么跑 `cargo check`，要么交叉编译（交叉编译是 windows target，门控成立，同样看不到——所以 mac 的 `cargo check` 是唯一能抓到的地方）。

### 修法（治本，不是给引用处打补丁）

第一版想把 `i18n` / `pe_safety` 都改成无条件编译，结果 `pe_safety` 又反过来依赖 `main.rs` 里同样门控的 `bcd_identifier_from_line` → 又挂。说明那个门控不是随手写的。

最终方案：**把语言枚举搬到语言层**。

- `MessageLanguage` 定义从 `pe_safety.rs` 移到 `i18n.rs`（语言维度本就属于语言层）
- `pe_safety.rs` 保留 `pub(crate) use crate::i18n::MessageLanguage;` —— 既有 `crate::pe_safety::MessageLanguage` 引用**一行都不用改**
- `mod i18n;` 改无条件编译（非 Windows/测试下没人用 → `allow(dead_code)`）
- `mod pe_safety;` 保持原门控
- `text_parsing.rs` 改用 `crate::i18n::MessageLanguage`

顺带清掉 `main.rs` 里两个「非 Windows 下未使用」警告（`command_name` / `operation_arg` 只在 `#[cfg(windows)]` 的 emit 块里用）。

## 工具补充

新增 `tools/win-clicker/start-gui.ps1`：部署脚本会杀掉运行中的 GUI，需要一条命令把它以提权身份重新拉起到 session 1 桌面：

```bash
./tools/win-clicker/br-s1.sh start-gui.ps1
```

（`br-s1.sh` 走 `run-in-session.ps1` + `br-gui-exec.ps1` 的既有链路：SYSTEM → session 1 → `ShellExecute runas` → High IL。脚本必须放在 `tools/win-clicker/` 下，`br-gui-exec.ps1` 从 `\\Mac\backupRestore\tools\win-clicker\` 取源。）
