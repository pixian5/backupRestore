# 200% 缩放下 GUI 底部按钮不可见：DPI 感知修复（v2.6.78）

> 模型：Qoder。时间：2026-10-30 01:40。
> 关联：本文件同时记录 R0（当前二进制全链复跑）的进行状态；R0 的 A/B 入口结果见文末。
> 版本：**2.6.78**（行为变更：进程声明 DPI 感知 + 界面字体钉在 96dpi 基准）。

---

## 1. 现象

测试虚拟机 `Windows 11` 的系统缩放是 **200%**（`HKCU\...\Control Panel\Desktop` 的
`LogPixels=0xc0`、`Win8DpiScaling=1`；分辨率 2350×1938）。在这个环境下：

- GUI 主窗口**底部四个按钮**（刷新环境 / 读取镜像 / 创建任务 / 刷新任务状态）
  **完全不可见**；截图只能看到上半部分（源卷行、详情框、说明区）。
- 控件枚举证明按钮**存在且在报告客户区内**：
  `ROOT client=1175x898`，`id=1003 (创建任务) rect=280,595,400,623`——按报告的客户区
  它明明在窗口里，屏幕上看不到。
- 「选择备份镜像保存位置」的系统文件对话框同样底部被裁，文件名框与「保存」按钮不可见。

这条不是「界面模糊」这种观感问题：**200% 下 GUI 根本无法完成「选路径 → 创建任务」**。

## 2. 根因

进程是 **DPI unaware**（`GetDpiForWindow` 对主窗口返回 96，而系统实际 192）：

1. Windows 把窗口位图整体放大 2 倍；
2. `GetClientRect` 对 unaware 进程返回**虚拟化后的逻辑坐标**（1175×898），
   而布局代码按 1020×760 写死；
3. 客户区被系统「撑大」后，控件按固定逻辑坐标绘制，再被整体放大——
   底部控件落在系统实际绘制的可视区之外（或与说明区重叠），
   于是「枚举得到在客户区内、屏幕上却看不到」。

这与 `docs/20261026-1418` 的读数一致：那次诊断输出 `DPI=96 AWARENESS=0`——
96 是 unaware 进程的虚拟化值，不是系统缩放。**问题当时就被量到过，只是没修**。

## 3. 修复（v2.6.78）

两处，都是小改动：

1. **进程级 DPI 感知**（新模块 `crates/backuprestore-cli/src/dpi.rs`）：
   `main()` 第一件事调用 `SetProcessDPIAware()`（Vista+，System aware）。
   失败无妨——保持 unaware，即改动前现状。
2. **界面字体钉在 96dpi 基准**（`native_gui.rs` 新增 `gui_font()`）：
   原先三处 `GetStockObject(DEFAULT_GUI_FONT)` 改为显式
   `CreateFontW(-12, …, GB2312_CHARSET, "SimSun")`。
   为什么要改：声明感知后**系统字体也跟着 DPI 变大**（200% 下约 18px），
   而布局坐标仍按 96dpi 写死，按钮文字互相重叠（实测顶栏按钮与入口按钮压在一起）。
   钉死 12px 后，布局恢复 100% 的样子。

**100% 缩放下本改动不改变任何窗口尺寸**（字体本来就是 12px 宋体）。

## 5. 遗留（必须交给 R2）

**只做感知、没做布局缩放**，所以 200% 下：

- 界面按 1020×760 **物理像素**绘制，在 2350×1938 屏幕上只占左上角约 43%，
  **文字与按钮偏小**；
- 顶栏按钮（查看日志 / 备份文件 / 取消待重启 / 设置 / 语言）在本次截图里**不可见**
  （入口按钮占了整行），需要在完整缩放里重新排布；
- 系统缩放改注册表**无效**：把 `LogPixels` 改 96 后重启，被 Windows 在登录时重写回 192；
  `PerMonitorSettings` 键不存在、`GraphicsDrivers\Configuration` 无 `DpiValue`。
  所以「临时改回 100%」这条路走不通，必须在产品侧适配。

→ R2 的完整方案（所有布局坐标 × DPI 系数、文本控件高度按实测行高、判据脚本先声明
DPI 感知）不变，本次只是把「GUI 在 200% 下不可用」这个阻塞先解除。

## 6. 顺带修的两个测试通道问题（不是产品代码）

1. **`br-gui-exec.ps1` 增加「预刷副本」回退**：提权会话读 `\\Mac\…` UNC 会间歇性
   报「系统找不到指定的文件」（同一脚本第一次能读、第二次失败），而 SYSTEM 通道同刻能读。
   现在宿主侧先用 SYSTEM 把脚本拷到 `H:\brwork`，`br-gui-exec` 在 UNC/X: 都失败时
   使用该本地副本（并改成「先读字节再删目标」，因为源可能就是目标本身）。
2. **`C:\Users\Public\pkg` 与 `X:` 映射重建**：2026-10-29 清理删掉了 `C:\Users\Public\pkg`，
   `br-s1.sh` 因此报 `MISSING_CMDFILE`；VM 重启后 `X:` 映射也会丢（经验/02 §4 已记）。
   两者都按原样重建，未改脚本默认路径。
