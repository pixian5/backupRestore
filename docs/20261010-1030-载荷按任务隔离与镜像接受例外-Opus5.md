# 载荷按任务隔离与镜像接受例外（问题 9、问题 13）

版本 **2.2.0**，开发测试版。日期：2026-10-10；模型：Opus 5（1M 上下文）。

本轮针对 [`可能的问题GPT6.md`](可能的问题GPT6.md) 里**最后两项确认未修**的缺陷：第 9 项（多任务共用固定载荷路径）与第 13 项（强制继续未贯穿执行）。
按用户要求不扩展平台。14 项清单的其余条目经本轮逐项复核已在 2.1.0～2.1.9 期间修复或改变机制，复核结论见下文第四节。

## 一、问题 9：多任务共用固定载荷路径

### 触发与后果

此前所有任务的恢复载荷都写在镜像卷的固定路径 `BackupRestoreRE\Winre.wim`：

1. 任务 A 准备完成（载荷已注入、哈希记进 `boot-entry.json`、BCD 条目指向该 WIM），尚未执行；
2. 用户回到界面再准备任务 B，`copy_into_staging` 用 `fs::copy` **覆盖同一个文件**；
3. 任务 A 随后续跑走 `rearm()`，它拿活载荷比对簿记哈希，必然不符，以
   `payload WIM hash differs from the prepared one; refusing to re-arm` **永久放弃续跑**；
4. 更严重的是清理：`remove_staging` 删除 `BackupRestoreRE\` 下的 `Winre.wim`/`boot.sdi` 和目录本身，
   **没有任何任务归属判断**，清理任一任务都会删掉另一个任务仍然需要的载荷。

不需要两个任务同时执行——只要旧任务未终结就存在冲突窗口。`cleanup_terminal_tasks` 只统计
`skipped_nonterminal` 并记日志，不拒绝新任务，因此准备流程不会拦住这个窗口。

### 修复

**载荷目录按任务 ID 隔离**，并把路径收敛到唯一构造点：

- `boot_cleanup::staging_relative_dir(task_id)` → `BackupRestoreRE\<任务ID>`（给 BCD 用的 Windows 形式）；
- `boot_cleanup::staging_task_path(root, task_id)` → 文件系统路径，逐段 `join`。
  刻意**不**复用上面那个字符串去 `join`：其中的 `\` 在本机（macOS）开发测试里不是路径分隔符，
  直接 `join` 会造出名字带反斜杠的单层目录，让按任务隔离在本机测试中静默失效。
- `staging_task_segment` 只接受规范 UUID（复用 `validate_task_id`）。被改过的任务 ID 不能把清理
  指向 `BackupRestoreRE\` 本身或卷上的其他目录（路径穿越）。

同源的消费点全部改为从上面两个函数取值，不再各自拼字符串：

| 位置 | 取值 |
|---|---|
| `boot_entry::copy_into_staging` | 写入 `{卷}:\BackupRestoreRE\<任务ID>\` |
| `boot_entry::create_entry` 的 `ramdisksdipath` | `staging_sdi_path(staging_relative_dir(id))` |
| `boot_entry::rearm` 载荷探测 | `probe_file(root, [RE_STAGING_DIR, segment, name])` |
| `resume_safety::payload_path` | 连任务 ID 一起核对，簿记只能指向**它自己**的子目录 |
| `resume_safety::verify_chain` | `ramdisksdipath` 期望值按任务生成 |
| `boot_cleanup::remove_staging(root, task_id)` | 只删本任务子目录下的两个载荷文件和该子目录 |

`ReBootEntry` 增加 `task_id` 字段，让簿记自带归属，续跑与清理都按它定位。

清理的父目录处理：本任务子目录删掉后由 `prune_empty_parent` 回收空的 `BackupRestoreRE\`；
里面还有别的任务载荷时**原样保留**——那不是残留，是另一个任务正在用的东西。竞态下别的任务
刚放进新载荷（`ENOTEMPTY` / `ERROR_DIR_NOT_EMPTY`=145）不算失败。

### 同时修掉的启动请求夺取

一次性 `bootsequence` 是整台机器只有一份的资源。续跑路径 `rearm()` 一直严格拒绝覆盖他人请求
（`allow_rearm`），但首次武装 `arm_one_shot` 此前**直接写、不看现状**：另一个未终结任务的请求、
或 Windows 自己设下的请求（`reagentc /boottore`、系统更新）都会被静默夺走，下一次开机进的不是
设置它的人期待的东西。现在两条路径一致，都先读 `{bootmgr}` 的 `bootsequence` 再经 `allow_rearm` 判断。

### 为什么选按任务隔离而不是"每台机器只允许一个未终结事务"

问题清单给了两个方案：载荷目录含任务 ID（本轮采用），或限制全机只允许一个未终结启动事务。
后者更简单，但会在旧任务卡在非终态时**把用户锁在门外**，且需要额外设计"不永久锁死、也不无条件抢占"
的恢复入口。按任务隔离从根上消除了互相覆盖与互相删除，不引入新的锁语义；整机唯一的那个资源
（一次性启动请求）则由上面的 `allow_rearm` 两路一致来保护。

## 二、问题 13：强制继续在重启后被静默撤销

### 触发与后果

用户勾选「严格对比哈希」，镜像与副档（`.index-N.metadata.json`）记录不符，界面弹窗
「备份档案与镜像不匹配…是否仍要还原？」，用户点「是」。此后：

1. 准备阶段 `--force-restore-hash` 放行大小与哈希判据；
2. 但任务里写入的 `image.sha256` 仍是**副档的旧值**，且 `verifyHash = true`，
   `force_restore_hash` **根本没有落盘**；
3. 机器重启进入 WinRE，离线预检 `verify_image_file` 读出镜像真实哈希与任务里的旧值比对，
   **必然不符**，任务在 Preflight 阶段失败。

即：用户点过的「仍要还原」在重启后被静默撤销，而且是在系统已经进入恢复环境之后才失败。

### 修复

把例外建模成**绑定具体镜像、索引与实际内容**的记录 `ImageAcceptance`：

```
accepted_sha256          用户接受时镜像文件的真实 SHA-256（不是副档记录的值）
accepted_size_bytes      用户接受时镜像文件的真实字节数
index                    被接受的 WIM 索引；换索引不复用这次例外
superseded_sidecar_sha256 接受时副档记录的哈希，仅留痕，不再作为判据
accepted_at              用户确认的时刻
```

- 准备阶段：只有**真正越过了副档判据**时才产生例外（正常通过校验的镜像不写例外，避免例外退化成默认状态）。
  严格哈希模式下复用本来就要付的那次读盘结果，**不额外再读一遍 58GB 镜像**；
  并把这个真实哈希写进 `ImageSpec::sha256` 作为本任务的权威值。
- 仅对比大小模式下的接受：`accepted_sha256` 留空，表示本次例外**不覆盖哈希判据**，离线侧也只走大小校验。
- `Task::validate()` 强制例外绑在本任务自己的镜像记录上：索引、大小、哈希任一对不上即**校验失败**，
  非法哈希文本同样拒绝。改 `task.json` 塞一条例外无法变成通用放行。
- 离线侧：旧副档退位的前提是 `ImageAcceptance::covers(索引, 实际哈希, 实际大小)` 成立，并写入日志
  说明"副档不再是本任务的来源真实性依据"。

关键性质：**例外放宽的是"和副档比"，不是"不比"**。镜像在用户确认之后又被改动时，实际哈希不等于
`accepted_sha256`，离线预检照样拒绝。

本轮新增/改写的测试：

- `boot_cleanup::staging_directory_is_per_task_and_rejects_unsafe_ids`：路径按任务生成；空串、`..`、
  `Winre.wim`、`..\..\Windows`、残缺 UUID、带 `/` 的 ID 全部拒绝。
- `boot_cleanup::cleanup_never_touches_another_tasks_payload`：**问题 9 的核心回归**。清理任务 A 后
  任务 B 的 `Winre.wim`/`boot.sdi` 逐字节不变，父目录因 B 仍在而保留；B 也清理后父目录才回收。
- `boot_cleanup::cleanup_rejects_an_invalid_task_id_instead_of_wiping_the_parent`：非法 ID 不会把清理
  扩大到父目录，已有载荷仍在。
- `resume_safety::cross_boot_path_and_full_chain_are_verified`（改写）：跨启动路径与完整启动链按任务核对；
  指向**别的任务**子目录、指向旧的共用路径、带 `..` 的路径均拒绝。
- `core::accepted_image_survives_the_reboot_and_still_detects_later_tampering`：同一份镜像放行；
  确认后内容或大小任一变化、或换索引，例外立即失效。
- `core::image_acceptance_must_match_the_task_image_record`：索引/大小/哈希对不上、非法哈希文本、
  无镜像任务携带例外，全部 `validate()` 失败；仅大小模式的空哈希接受合法且不覆盖哈希判据。

（链接期 `LNK4099` 缺 PDB 告警是既有现象，见 `20260925-0207-pitfalls-static-crt.md`）。

## 五、证据边界（重要）

**本轮只完成本机验证与交叉构建，未做实机验收。** 必须说清的是：

1. 本轮改动**改变了 BCD 元素的实际值**——`ramdisksdipath` 与 `device/osdevice` 里的 ramdisk 路径
   从 `\BackupRestoreRE\…` 变为 `\BackupRestoreRE\<任务ID>\…`。2.1.9 的断电续跑验收（11 个检查点）
   是在**旧的共用路径**下取得的，不能直接套用到新路径上。
2. 因此下列项目需要在新快照保护下重新实机验证：一次完整的准备→重启进 RE→捕获/应用→引导修复→清理→
   回正常 Windows；以及至少一次 `rearm()` 续跑（证明新路径的启动链回读与载荷探测在实机成立）。
3. Windows 侧 156 项常规回归未执行（需虚拟机）。本机 147 项不编译/执行全部 Windows 专属模块。
4. 未部署到客体包目录与 `H:\brwork\`，未核对部署后哈希。按 `AGENTS.md`，部署与任何启动项变更前
   必须先建并核验新的 Parallels 快照；当前虚拟机处于挂起状态，本轮未动它，也未新建快照。
5. **旧版遗留载荷**：从 2.1.9 或更早版本升级时，镜像卷上可能仍有旧的共用 `BackupRestoreRE\Winre.wim`
   与 `boot.sdi`。新代码不认它们，`prune_empty_parent` 会因父目录非空而保留（不报错、也不误删），
   需要人工确认后清理。这属于已知遗留物，不是失败。

构建通过只证明可构建，不证明备份还原、断电续跑或启动清理在实机成功。
