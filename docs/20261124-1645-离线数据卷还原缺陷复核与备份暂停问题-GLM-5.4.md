## 一、结论

1. **缺陷成立。**「还原数据到非 C 盘」选离线、点「进入 Windows RE」、连点三次「是」之后，任务准备失败，
   报 `restore-existing target must be the active Windows volume`（还原到原卷的目标必须是当前运行的系统卷）。
   图形界面通道、命令行通道各复现多次；失败是干净的（没有任务、没有写入、没有重启）。

2. **根因比原文写的「互相矛盾」更具体：同一个入口，在线和离线下发的是两条不同的命令，安全闸只装在其中一条上。**
   在线走 `online` 子命令（有自己的校验，通过）；离线走 `prepare` 子命令（被 10-18 加的闸拒绝）。

3. **它从 10-18 起就走不通，而且被它封死的那条路，是同一个函数往下二十行专门为之写了放行判据的。**
   准备期在 10-14 明确加过「数据卷还原必须放行」；四天后的安全闸是为了拦另一种事故，却把合法的数据卷还原一并拦了。
5. **顺带核实：缺陷 1 的另一个修法（只保留「进入 PE」）按现状走不通**——「进入 PE」对数据卷自己也是坏的
   （会被当成「系统替换」：格式化数据卷、灌入镜像，然后校验系统文件失败、任务报失败）。这是代码层面的结论，未实机（§八）。

4. **「备份过程中按暂停无效」——代码与实机都坐实**（§七）。这一条有一段波折：做哈希优化的会话记为「已坐实」；
   接手会话第一版复核把它降为「实机未验证」，**那是错的**（用一份被删光中文的日志副本去搜中文）；
   用原样拷出的原始日志重新核对后恢复为「已坐实」。修法二选一，留给用户。

## 二、缺陷是什么

- **现象**：「还原数据到非 C 盘」→ 通道选离线 → 点「进入 Windows RE」→ 选择框选「进入恢复环境」→ 确认框点「是」
  → 弹出「任务准备失败（退出码 1）：invalid task: restore-existing target must be the active Windows volume」。
- **影响**：数据卷的离线还原（经恢复环境）从 10-18 起是死路。数据卷还原的在线方式不受影响（基线测试 C5-1、C5-2 通过）。
- **失败是干净的**：没有创建任务（`TASK=NONE`）、没有写入、没有重启。
- **附带**：这个拒绝走的是「非法任务」一类的出口，`error_code` 是 `null`，用户无从按码查表。

## 四、根因：同一个入口，两条命令，闸只装在一条上

图形界面的入口分流在 `crates/backuprestore-cli/src/native_gui/task_executor.rs`：

| 通道 | 界面下发的命令 | 代码位置 | 经过准备期校验函数吗 | 结果 |
| --- | --- | --- | --- | --- |
| 在线 | `online --operation restore-existing …` | `task_executor.rs:1188` → `run_online_operation` → `online_operation.rs:424` 起 | **不经过**；它自己用「目标卷是不是 Windows 卷」分流（是 → 格式化、应用、修引导；不是 → 只铺数据） | 通过 |
| 离线（进 PE） | 排队一个 PE 任务 | `task_executor.rs:1223` → `schedule_pe_task` | 不经过 | 本缺陷无关 |
| 离线（进恢复环境） | `prepare --operation restore-existing …` 加数据卷目标 | `task_executor.rs:1204–1279`（选择框与确认框）→ `:1286` 起拼出 `prepare` 命令 | **经过**，在 `prepare_validation.rs:144` 被拒 | 失败 |

被拒的那一处（`crates/backuprestore-cli/src/prepare_validation.rs:144–148`）：

```rust
if options.operation == Operation::RestoreExisting && !target_is_active {
    return Err(err(
        "restore-existing target must be the active Windows volume",
    ));
}
```

它的注释写明了来意：2026-10-18「缺陷修复 H1 第二层」——图形界面 A 入口（系统还原到 C 盘）的目标下拉曾经会静默失效、
停在别的盘上，于是「源和目标都是某个数据盘」也能一路通到「格式化该盘并写入镜像」；界面修了之后，
这里再立一道**不依赖界面的最终防线**。防线本身是对的，问题是它拦得太宽。

**恢复环境那一侧其实是支持数据卷目标的**：恢复引擎按「目标卷当前是不是 Windows 卷」决定收尾时修不修引导
（`recovery_engine.rs:826–843`），对数据卷会跳过引导修复（日志 `recovery_engine.rs:1204`：
`data-volume restore: target has no SYSTEM hive; skipping BCDBoot`）。

## 六、修法（需要你裁定，未动代码）

两个方向，与基线文档一致：

### 方案一：让准备期接受「数据镜像 → 数据卷」这一种组合（保留这条能力）

把那道闸从「还原到原卷的目标必须是当前系统卷」收窄成「**目标是 Windows 镜像**时，还原到原卷的目标必须是当前系统卷」。

- **能力保留**：数据卷离线还原恢复可用；A 入口（系统还原）的保护原样保留。
- **关键提醒（接手会话核实后的补充）**：区分「要拦的事故」和「要放行的场景」，**判据必须看镜像，不能只看目标卷**。
  - 要拦的事故：用户在 A 入口想还原系统盘，目标却落在了数据盘上——此时**镜像是系统镜像**，目标是数据卷。
  - 要放行的场景：B 入口的数据卷还原——**镜像是数据镜像**，目标也是数据卷。
  - 两种情况下目标都是数据卷，所以现成的「目标卷是不是 Windows 卷」判据**分不开它们**（此前一个分析会话的
    修法评估里把这两个判据说成了一回事，这里订正）。
- **现成的探测函数不能直接当开关**（2026-11-24 19:20 读函数体后订正——本条第一版写的是「它对数据镜像直接返回错误」，不准确）：
  `image_admin.rs:508` 的 `wim_full_windows_probe` **先看镜像的索引名**：长度不小于 8、不含 `pe` / `preinstallation` / `recovery`、
  且含 `windows` 就直接返回通过（`prepare_plan.rs:291`）。而在线备份写进镜像的默认索引名就是 `Windows Backup`
  （`online_operation.rs:1443`）。所以**它的「通过」证明不了是系统镜像**（数据镜像照样通过）；只有挂载之后的结果才可信：
  标记齐全是系统镜像，缺标记才是数据镜像（或纯预安装环境镜像）。
- **可靠的判据有两条路**：① 只认挂载后的权威判定，并且把「确认缺标记」「确认齐全」「挂载失败、无法判定」分成三种结果，
  无法判定时保守拒绝；② 备份时往副档里记一个「源卷是不是 Windows 卷」的标志，准备期直接读；没有副档的第三方镜像
  按系统镜像处理。两条可以并用。
- **工作量估计**：中等。要改判据、补单元测试（系统镜像 + 数据卷目标 → 拒；数据镜像 + 数据卷目标 → 放行）、
  做变异验证，并且需要一轮实机验证（数据卷离线还原要重启进恢复环境）。

### 方案二：界面对数据卷不再提供「进入 Windows RE」，只保留「进入 PE」

- **按现在的代码，这条路走不通**（2026-11-24 19:20 只读代码核实，见下面 §八补）：「进入 PE」对数据卷**自己也是坏的**。
  选它等于把数据卷的离线还原整个砍掉，而且留下的那个按钮还会把人引向一条「格式化之后报失败」的路。
- 要让方案二成立，得先把界面排队改成 PE 的 `data`（数据覆盖）操作，再装预安装环境做实机验证——
  工作量不比方案一小，而当前测试机上没有装预安装环境。

### 推荐

**倾向方案一**（能力保留、事故照样拦得住），并顺带把这个拒绝出口补上 `error_code`
（现在这类「非法任务」错误用的是不带码的构造函数 `err()`，`main.rs:634`，所以 `error_code` 恒为 `null`）。
同一轮可以顺手修缺陷 2（目标下拉默认选中光驱）和缺陷 3（选择框文案不随「格式化」变化）。

## 七、备份时按「暂停」无效：代码与实机都坐实

做哈希优化的会话在测量时顺手发现了这个问题，并记为「已坐实」。**接手会话的第一版复核曾把它降为「代码坐实、实机未验证」，
那是错的**——错在读证据的方法（见下面「一次订正的订正」）。2026-11-24 18:50 用未经过滤的原始日志重新核对后，恢复为「已坐实」。

### 代码层面：确定

- 暂停等待函数 `wait_if_paused`（`recovery_progress.rs:299`）全仓**只有两个调用点**，都在还原链：
  `recovery_engine.rs:965`（第 2/4 步，应用镜像前）和 `recovery_engine.rs:1050`（第 3/4 步，修引导前）。
- 备份链 `recovery_backup.rs` 里**一处都没有**（全文搜不到任何暂停检查）。
- 备份时的进度窗（标题「备份进度」）与还原共用同一套窗口代码，照样有「暂停(P)」按钮和 P 键；
  按下后会翻转按钮文字、写一行日志「恢复将在下一个步骤边界挂起」（`recovery_progress.rs:1172`）。
- **推论**：备份时按下暂停，界面会显示成「已暂停」，但之后没有任何代码去读这个暂停标志，备份会一路跑完并重启。
  这个推论是从代码直接得出的，没有分支可以绕过。

### 实机层面：坐实（任务 `37eb3aa2`，2026-11-24 11:07，版本 2.10.6）

两条硬判据，出自虚拟机里**原样拷出**的 `H:\BRImages\Recovery.log`
（651,286 字节，SHA-256 `9ee7d1669b0c5126f2f9fd1f3ebefe0ef6b0a5346ead3fd69dc11206d4c5558e`）：

**① 暂停请求确实被登记了**——第 14991 行，捕获进行中：

```
[2026-11-24T03:07:17.391715600+00:00] 用户按 P 暂停：恢复将在下一个步骤边界挂起
```

**② 登记之后备份没有停**——其后的全部时间线（UTC；本地时间加 8 小时）：

| 时刻 | 事件 | 与上一行的间隔 |
| --- | --- | --- |
| 03:07:30.29 | 捕获心跳，阶段 `writing` | 照常推进 |
| 03:08:00.40 | 捕获心跳 | 照常推进 |
| 03:08:30.41 | 捕获心跳 | 照常推进 |
| 03:08:45.94 | 捕获完成（135 秒） | **距暂停请求 88.5 秒** |
| 03:08:45.94 | 第 3/4 步「校验」 | **边界处 0.000 秒** |
| 03:08:47.16 | 完成 | 校验 1.22 秒 |
| 03:08:47.90 | 重启回 Windows | 0.74 秒 |

全程没有任何一行表示「真的暂停了」或「继续了」；任务终态 `success` / 100。

**用户看到的现象**：按钮翻成了「继续(P)」、日志写着「将在下一个步骤边界挂起」，而备份一路跑完并自动重启——
**备份其实不支持暂停，但界面没有告诉用户。**

### 一次订正的订正：错在哪里（写给以后复核别人结论的人）

第一版复核说的「完整日志」是宿主上的 `perf/runC2-recovery.log`。它是经辅助函数 `vrun "type …"` 落盘的，
而 `vrun` 的输出管道里有一道「只保留 ASCII 字符」的过滤（`LC_ALL=C tr -cd '\11\12\40-176'`，用来保证哨兵和
结构化字段能被稳定判读）。于是：

- 上面那一行中文被删成了 `[2026-11-24T03:07:17.391715600+00:00]  P`；
- 整个文件的非 ASCII 字节数是 **0**；在里面搜「暂停」当然是 0 命中。

**搜不到 ≠ 没有。** 那道过滤对「有没有某行中文」这种问题零证明力，而第一版复核拿它的 0 命中当成了「没有这一行」的证据。

**教训**（已写进 `经验/05` 与本机 `AGENTS.md` 第四节）：**下否定性结论之前，先证明读数通道看得见要找的东西**——
先搜一个明知存在的同类行做对照，或者把文件原样拷出来再读。核对结果存档在 `pause-check/verdict.txt`。

### 修法方向（未动代码；二选一，留给用户）

- **备份时隐藏或禁用「暂停(P)」按钮，并注明「备份不支持暂停」**（倾向这个：改动小，也更诚实）。
  捕获是交给 DISM 子进程做的，本来就没法中途停；「暂停」最早也要等到捕获结束才可能生效，对备份意义不大。
- 或者在备份链「捕获结束 → 校验」这个边界加一次 `wait_if_paused`——含义是「点了暂停，备份会在捕获结束后停住」，
  这和用户对「暂停」的直觉不一致，而且恢复环境里的「继续」也要跟着验证。

## 八、顺带核实出的一条：「进入 PE」对数据卷也是坏的（代码核实，未实机）

核实方案二的前提时读出来的。**只读了代码，没有实机跑**——当前测试机没有装预安装环境，本轮也没有去装。
下面每一条都对应明文代码，不是「没搜到」。

### PE 链按「操作名」分流，而界面给数据卷排的是「系统替换」

| 环节 | 代码位置 | 事实 |
| --- | --- | --- |
| 界面排队 | `native_gui/task_executor.rs:1536–1552`（`schedule_pe_task`） | 除备份外**一律**排成 PE 的 `restore`：`let mode = if operation == "backup" { "backup" } else { "restore" };`。所以「还原数据到非 C 盘 → 进入 PE」发出去的是 `restore` |
| PE 链分流 | `pe_operation.rs:627–633`（`intent`） | `"secondary"` → 装第二系统；`"data"` → 数据覆盖；**其余（含 `restore`）→ 系统替换** |
| 系统替换的流程 | `pe_safety.rs:280–296`（`run_restore`） | 预检 → **格式化目标卷** → 应用镜像 → **校验系统文件** → 修引导 |
| 预检 | `pe_operation.rs:497`、`image_admin.rs:508`、`prepare_plan.rs:291` | 先看镜像索引名：长度不小于 8、不含 `pe` / `preinstallation` / `recovery`、且含 `windows` 就**直接放行**。在线备份写进镜像的默认索引名就是 `Windows Backup`（`online_operation.rs:1443–1446`），图形界面的默认命名「Windows 11 …」同理 |
| 校验系统文件 | `pe_operation.rs:762–776` | 要求目标卷上有 `Windows\System32\config\SYSTEM`、`winload.efi`、`ntoskrnl.exe`——数据卷上没有 |

**把这几条串起来**：数据卷的镜像 → 预检按名字放行 → **数据卷被格式化并灌入镜像** → 校验系统文件必然失败
（`SystemFileVerifyFailed`）→ 任务报「失败」。此时卷上的内容其实已经是镜像里的数据，但任务状态是失败；
镜像之外的文件已经被格式化清掉。校验在修引导之前，所以启动菜单不会被碰。

### PE 链里为数据卷准备的那条分支，产品里没有入口

`"data"`（数据覆盖）做的事正是数据卷需要的：不要求完整 Windows、**跳过格式化**、不校验系统文件、不修引导
（`pe_operation.rs:497、589、636、710、763、765`；`pe_safety.rs:283、292`）。
但把 `"data"` 这个操作名的全部出现位置列出来，只有三处「允许列表 / 分流映射」和**一处单元测试**
（`pe_operation.rs:1175`）；产品里两个构造请求的界面入口传的都是 `backup` / `restore` / `secondary`
（`task_executor.rs:1540`、`pe_desktop.rs:1084` 与 `:1156`）。**这条分支目前只有单元测试在用。**

### 这意味着什么

1. **缺陷 1 的方案二按现状不可行**（见 §六）。
2. **「还原数据到非 C 盘」的「进入 PE」选项本身是一条缺陷**（暂记为「缺陷 5」）：代码层面成立，实机未验证。
   基线测试 C5-3 只测了「进入 Windows RE」那一条，「进入 PE」那一条从来没有实机记录。
   风险：用户以为在用「覆盖式还原」，结果数据卷被格式化、任务还报失败。
3. **修方案一时不要顺手把界面改成「只留 PE」**。

### 怎么实机验证（本轮没有做）

装预安装环境 → 用数据卷镜像走「进入 PE」→ 看 `runtime.json` 的阶段是否停在 `failed: …SystemFileVerifyFailed`，
以及数据卷是否已被格式化（卷序列号变化、镜像之外的文件消失）。**目标必须是可牺牲的测试卷。**
