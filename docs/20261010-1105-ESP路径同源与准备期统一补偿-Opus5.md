# ESP 路径同源与准备期统一补偿（问题 10、问题 11）

版本 **2.2.1**，开发测试版。日期：2026-10-10；模型：Opus 5（1M 上下文）。

本轮处理 [`可能的问题GPT6.md`](可能的问题GPT6.md) 剩余两项：第 10 项（PE 辅助 ESP 定位与控制文件路径不一致）
与第 11 项（准备失败缺少覆盖所有副作用的统一回滚）。这是 14 项清单的最后两项。

## 一、问题 10：ESP 主体已修，残留是"固定 S: 假设 + 死代码"

### 复核结论与原文不同

问题清单（基线 2.0.4）描述了两处：`esp_volume_path_for_task` 直接返回第一个无挂载点卷、
`esp_log_path` 对控制文件返回固定 `S:\…`。本轮复核发现：

- **主体已修**：现在的统一入口是 [`windows_prepare::esp_identity_without_drive_letter()`](../crates/backuprestore-cli/src/windows_prepare.rs#L1201)，
  它原生枚举卷（含已挂载卷）、校验分区类型 GUID 为 EFI、**探测 `EFI\Microsoft\Boot\BCD` 可读**，
  多个候选或探测错误都明确拒绝猜测。`esp_volume_from_listing` 那条宽松路径已不存在。
- **残留比原文窄**：旧的 `pe-task.txt` / `.done` / `pe-task-result.txt` 控制通道已被
  [`pe_operation.rs`](../crates/backuprestore-cli/src/pe_operation.rs) 的请求队列取代
  （`pe-requests\<id>.json` + `.claimed` / `.result`，带写锁与单请求约束），
  现在只剩 `esp_log_path` 这一个消费者。

### 实际存在的两个问题

**1. 日志路径写死 `S:\BackupRestore\logs`。** 这等于假设 `S:` 就是 ESP。`S:` 被数据卷占用、
或 ESP 已挂在别的盘符时，本项目的日志会落到一个无关卷上，而且读日志的人无法分辨。

**2. 为该假设服务的死代码。** `ESP_CONTROL_FILES`（三个已废弃的控制文件名）、
`ESP_LOG_DIR`，以及 `rewrite_s_root` —— 后者靠字符串替换把命令里的 `S:` 换成卷路径。
问题清单的修复方案明确要求"不以字符串替换代替路径解析"，而且它带的一条不变量
（"控制通道必须留在 `S:\` 根"）随着控制通道被取代**已被证伪**，却仍在测试里被锁定。

### 修复

- `ESP_LOG_DIR` → `ESP_LOG_SUBDIR`（`BackupRestore\logs`，**不带盘符**）；
- `esp_log_path(name)` → `esp_log_path_on(volume_root, name)`：路径只从调用方传入的
  **已核验卷根**派生，接受 verbatim 卷路径（`\\?\Volume{GUID}\`）或盘符根（`Q:\`），
  缺尾部反斜杠时补齐。函数不猜、也不做盘符替换。
- 删除 `ESP_CONTROL_FILES`、`rewrite_s_root` 及其测试；
- `native_gui.rs::write_pe_exit_log` 不再盲写 `S:\…`，ESP 侧两份路径（卷根 + 同卷日志子目录）
  都从调用方传进来的卷根派生；卷根拿不到时只写 PE RAM 盘，不猜盘符。

测试改写为 `esp_log_path_is_built_from_the_caller_supplied_volume_root`：锁定
verbatim 卷根原样前缀且**不出现任何盘符**、盘符形态只用调用方给的盘符、缺反斜杠时补齐。

## 二、问题 11：准备期统一补偿

### 缺口

此前只有 `shutdown.exe` 失败那一步会回滚。`create_entry`（写 BCD 对象）、
DISM 挂载/注入、载荷覆盖到镜像卷、`refresh_payload_hash`、`arm_one_shot`、
`store.write_transition` 这几处失败都是直接 `?` 返回：

> 界面报告"准备失败"，而机器上可能留着本任务的 BCD 条目、一次性启动请求，
> 或镜像卷上的载荷文件，`boot-entry.json` 还指向它们。**下一次重启进的不是用户期待的东西。**

其中武装后状态落盘失败尤其危险：机器带着一个一次性启动请求重启，却没有任何持久状态
说明这是谁设的，等于把人推进一个没人负责的任务环境。

### 修复

**1. 半成品条目簿记**（新模块 [`boot_record.rs`](../crates/backuprestore-cli/src/boot_record.rs)）

`create_entry` 在字段写入全部重试失败后，本来就保留已建的两个 BCD 对象供诊断（KEEP 分支），
但那两个 GUID **只出现在日志文本里**，没有任何代码认得它们。现在落到 `boot-entry-residue.json`。

刻意与 `boot-entry.json` 分开：若两者共用，下一次 `create_entry` 的"复用已有条目"分支
会把这个 `device`/`osdevice` 从未写成功的条目当成可用条目，`arm_one_shot` 随后武装它，
机器下次开机会进一个指不到载荷的启动项。

**这个模块是跨平台的**——`boot_entry` 整个是 `#[cfg(windows)]`，其单测在 macOS 上
一次都不编译（代码注释里记着 2026-09-29 `ramdisk=` 值畸形就是这么漏过去的）。
簿记是纯数据 + 文件 I/O，所以放这里并配齐 5 项本机单测。

**2. 统一补偿 `compensate_prepare_failure`**

固定顺序，每步回读验证，任何一步失败都继续并汇总：

1. 先清一次性启动请求——反向保证机器不会重启进任务 RE；
2. 删 BCD 对象——只删本任务记录在案的那两个 GUID；
3. 删镜像卷上本任务那份载荷（按任务 ID 定位）；
4. 恢复 `create_entry` 之前导出的字节级 BCD 快照。

正式簿记走完整 `disarm`；**半成品簿记只走对象删除**——它的 `device`/`osdevice`
从未写成功、载荷也未必就位，走完整 `disarm` 会在载荷校验处报错，把"对象其实已经删掉了"
说成补偿失败。为此从 `disarm` 抽出 `remove_entry_objects`，让两条路径的安全边界逐字一致：
只按精确 GUID 删，绝不用描述字符串匹配；别人的 `bootsequence` 一律不碰。

**3. 接入点**：`create_entry` 之后的整段（建条目 → 载荷覆盖 → DISM 挂载/注入 → 卸载提交）
与 `refresh_payload_hash` 之后的整段（刷哈希 → 武装 → 状态落盘）各自收进闭包，
任一失败先补偿再返回**原错误**。`shutdown.exe` 失败分支也改为走同一个补偿函数，
消除两处清理逻辑各自漂移的可能。

补偿失败时一并报出，**绝不为了"看起来干净"而把补偿失败盖成成功**。

**4. 验收注入点**：新增 `acceptance:entry-fields:error`（加入 `recovery_fault::valid` 白名单），
在 `create_entry` 的字段写入块入口注入错误，让 KEEP 分支在实机夹具里可达。
夹具随后核验：建条目失败、残留簿记带上了两个精确 GUID、BCD 回到基线。

### 一个值得记住的工程教训

Windows 侧 clippy 抓到了本机看不到的两个问题（`unused_mut`、可折叠的嵌套 `if let`）——
本机 `cargo clippy` 不编译 `#[cfg(windows)]` 模块。**本机全绿不等于 Windows 侧全绿**，
交叉构建 + 交叉 clippy 必须单独跑。本轮第一版就是这么带着两个错误去构建、被 `E0308` 挡下的。

## 四、证据边界（重要）

**本轮同样未做实机验收。** 需说清的是：

1. 2.2.0 改变了 BCD 的 `ramdisksdipath` 与 ramdisk 路径实际值（载荷按任务隔离），
   2.1.9 的 11 点断电证据取自旧的共用路径，**不能套用**。2.2.1 又新增了补偿路径与
   `entry-fields` 注入点，同样需要在实机确认。
2. 因此实机验收需覆盖：部署并核哈希 → 一次完整链路 → 至少一次 `rearm()` 续跑 →
   两个未终结任务并存 → 注入 `acceptance:entry-fields:error` 走一次失败补偿 →
   Windows 侧常规回归。
3. 未部署到客体包目录与 `H:\brwork\`，未核对部署后哈希。按 `AGENTS.md`，部署与任何
   启动项变更前必须先建并核验新的 Parallels 快照；虚拟机本轮未动，仍为挂起状态。
4. 问题 10 的 ESP 定位在多 ESP、ESP 无挂载点、隐藏恢复卷排在 ESP 前等场景的实机行为
   仍待验证；本轮只把"固定盘符假设"这个明确的缺陷去掉。

构建通过只证明可构建，不证明备份还原、断电续跑或启动清理在实机成功。
