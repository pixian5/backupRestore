# 孤儿任务守卫误清「正在准备中的任务」的复现与修复（v2.10.9、v2.10.10）

> 时点：2026-11-25 00:25。模型：GLM-5.4。
> 起点：做 v2.10.8 的实机收尾时**撞到**的一个新缺陷；先在旧二进制上主动复现两种变体，再修复、再做实机对照。
> 提交与二进制：v2.10.9 = `49f0213` / `173b18a8…`；v2.10.10 = `6b47ec9` / `65a49489…`。
> 被误清的一方：v2.10.8 的最终二进制 `c9336473…`。

---

## 一、结论先行

**缺陷**：界面程序每次启动第一步是「孤儿任务守卫」（`collect_orphan_tasks`），它把「非终态 + 没写过目标卷 +
没有启动项记录」的任务当孤儿：标成失败、删任务产物。而**准备流程**（`prepare_payload`）是先把任务落盘
（阶段 = 已准备），要到最后建启动项时才写 `boot-entry.json`，中间约 20 秒（拷两遍恢复环境镜像、注入载荷、
一次刻意的 5 秒等待）。**这段时间里，在办任务与孤儿在守卫看来一模一样。**

**谁会在这个窗口里启动界面程序**：开机自启（每次登录都启动）；用户再点一次图标（界面没有单实例保护）。
只要有一个准备正在进行（命令行、计划任务、另一个界面实例派出的准备子进程），就可能被清掉。

**后果随时机而变**（两种都在实机上复现了）：

| 时机 | 后果 |
|---|---|
| 守卫早到（DISM 挂载前） | 删掉空的 `mount` 目录 → 85 毫秒后 DISM 挂载报 `0xc1420115`「用户尝试装入不存在的目录」，准备失败 |
| 守卫迟到几秒（挂载之后） | 删产物被原有的「镜像树还挂着」保护拦住，**但任务已被标失败** → 准备照常走完、一次性启动已武装 → 10 毫秒后状态推进被拒（`BR-CORE-074`）→ 再补偿，按字节回退启动配置被挡（`BR-TSK-035`，补偿未完成） |

同一个根因的另一条路：`abandon-task` 命令对在办任务照常执行——先把任务标成失败，最后一步清理产物被拒
（`BR-CORE-060`）才整体报错；在办的准备随后同样走到「武装后被拒」。

**修法**（v2.10.9）：准备流程从任务落盘起，**独占握住**任务目录里的 `preparing.lock`，直到准备结束。别人
（守卫、两条放弃入口）去碰它：共享冲突 = 有进程握着 = 在办，一律不动；打得开或文件不存在 = 没人在办。
文件带「所有句柄关闭即删除」标志，进程崩溃时系统关闭句柄、锁自动失效，**不会留下永远清不掉的僵尸**。

**实机对照**：

| | 旧二进制 `c9336473…`（v2.10.8） | 新二进制 `173b18a8…` / `65a49489…` |
|---|---|---|
| 准备进行中启动界面程序 | 守卫把任务标失败（`3c3aad44`、`6c49a5bd`） | 守卫日志 `… is still being prepared; left alone`（`9a562086`、`ce622a75`） |
| 准备进行中执行放弃命令 | 任务日志 `User explicitly abandoned … stage=Prepared`（`adb65d79`） | `success:false error_code:BR-TSK-036`，任务日志 `Abandon refused: …` |
| 准备结果 | 失败（补偿未完成） | 成功，随后备份 / 还原正常完成 |

**连带订正**（v2.10.10）：修的过程中发现一行诊断日志（「本操作是否兑现暂停」的声明）写进了恢复环境的临时
早期日志、随临时盘丢失。改为每切一次日志就补写一次。实机：三份落盘日志里 0 行 → 早期日志与正式日志各 1 行。

## 二、怎么发现的

22:56 做数据卷离线还原的脚本刚结束（虚拟机从恢复环境重启回来十几秒），我紧接着起了一个备份准备。准备失败：

```
invalid task: preparation failed: [BR-APL-009] dism.exe failed with exit code: 0xc1420115
```

输出尾部只有回滚时的启动配置枚举，看不到失败的是哪条命令。按「先证明读数通道看得见」的做法逐个取原始记录：

1. 任务目录 `6c49a5bd…\prepare.log`（原样取回）：22:56:16.53 准备开始 → 22:56:19.46 `dism /Mount-Image … /MountDir:…\mount`。
2. 系统 DISM 日志 `C:\Windows\Logs\DISM\dism.log`：`ImageCreate` 返回 `0xc1420115`，中文原文
   「用户尝试装入不存在的目录。不支持此操作。」——执行挂载那一刻 `mount` 目录不存在。
3. 界面日志 `H:\brwork\logs\gui.log`：

```
[14:56:19.377] orphan task guard: task 6c49a5bd-… stage=Prepared has no boot entry and cannot resume; marking Failed
[14:56:19.415] orphan task guard: collected 1 unresumable task(s)
[14:56:19.708] GUI started
```

三份记录互证：开机自启的界面程序在 19.377 把在办任务标失败并清理；85 毫秒后准备去挂载，目录已经没了。
事后任务目录里 `mount` 不在，`stage`、`original`、`payload` 都还在——因为清理 `stage` 时里面有正在拷贝的文件，
删除因占用失败，后面的没轮到。

## 四、修法

### 准备期在办锁（新模块 `prepare_lock.rs`）

- `hold(task_dir)`：以不与他人共享的方式打开 `<任务目录>\preparing.lock`，带 `FILE_FLAG_DELETE_ON_CLOSE`。
  返回的守卫活到 `prepare_payload` 返回（含三段失败补偿）。
- `probe(task_dir)`：四种读数分开报——有人握着（共享冲突）/ 没有锁文件 / 文件在但没人握着（断电留下的旧文件）/
  读不了。`in_flight()` = 只要拿不出「没人在办」的证据就当它在办。
- 锁文件不在 `cleanup_task_artifacts` 的白名单里（它只删 `mount/stage/original/payload`），清理产物不会碰它；
  也不在注入恢复环境的载荷目录里，不会进镜像。

### 三处入口

1. **守卫**（`pending_task.rs`）：动手前多一条——在办的不动，并留一行
   `orphan task guard: task <编号> stage=… is still being prepared; left alone`。工作区单列成参数
   （`collect_orphan_tasks_in`），便于写单元测试。
2. **`abandon-task` 命令**（`environment_admin.rs`）：在办则拒绝，新错误码 `BR-TSK-036`
   「任务 {0} 正在准备中，另一个程序正在写它的材料；现在不能放弃，请等它结束」，任务日志留一行 `Abandon refused: …`。
3. **新任务对话框里的「放弃并清理」**（`task_executor.rs`）：整体预检，有一个在办就一个都不清，并说明原因。

### 为什么用「操作系统持有的句柄」而不是记进程号或看时间

- 记进程号：进程号会被复用，还得比对进程创建时间，复杂且仍有缝。
- 看「多久没更新就算孤儿」：准备大镜像可以合法地跑很久，阈值定不准；定长了真孤儿要等，定短了照样误伤。
- 独占句柄：进程一死系统就关句柄，判断只有「握得住 / 握不住」两种，没有第三种状态。

### 适用前提与边界

- 只区分「有没有进程正在跑准备」。准备进程**卡死不退**时锁一直在，放弃命令会一直被拒——这时要先结束那个进程
  （任务管理器）才能放弃，这是有意的：它确实还在办。
- 新旧版本混用（旧版本的准备不握锁）不在保护范围内；部署位是同一套五件套，正常不会出现。
- 断电后可能留下没人握着的旧锁文件：读得出「没人握着」，照旧当孤儿收口；新的准备也可以直接接管它。

**命令行探测命令冒烟**：`list-volumes`、`inspect-environment`、`wim-info`、`list-images` 四条全过。

### 声明行为什么丢、怎么修（v2.10.10）

声明行原先在进度窗创建时写，进的是恢复环境的临时早期日志 `X:\BackupRestore-Recovery-early.log`；主链在窗口
建好之前就把早期日志拷进了任务目录，随后日志切到正式文件——这一行随临时盘丢失。读数通道自检过：同一份
恢复环境日志里明明存在的 6 行「Pause ignored」都读得到，而任务目录早期日志、`logs\recovery-early.log`、
`Recovery.log` 三份落盘日志里声明行都是 0。改法：`switch_log_path` 每切一次，就往新文件里补写一次。
实机：备份与还原两个操作的声明行都落在两处日志里，正式日志里那一行紧挨在「恢复程序启动」之前。

## 八、这一轮的教训（都已进经验库）

**产品层面**

1. 「清理 / 收口」类逻辑对「正在被别的进程使用的东西」必须能分辨。判断依据要来自操作系统持有的东西
   （句柄、共享冲突），不要来自自己记的状态。
2. 注释里的「判据极窄、不可能误伤」是需要证明的断言：守卫的注释这么写，事实是在办任务三条全中。
3. 状态机救了一次：准备在武装后被拒、随即撤销。如果那 10 毫秒里机器重启了，会进到一个任务已是失败的恢复环境。

**读数层面（这一轮踩得最多）**

4. 「输出里对不上号」不等于「没发生」：准备失败时命令行输出**不带任务编号**，守卫动的是哪个任务要从守卫自己的
   日志行里取，再拿那个任务准备日志的起始时间去对。
5. 证据要认「当时留下的那一份」：放弃命令先把任务标失败（文案「用户…明确放弃」），在办的准备随后又写一次
   失败把文案覆盖了——判据要认放弃命令写进任务 `recovery.log` 的那一行，不是事后任务状态里的文案。
6. 日志是累积的、声明行排在任务段之前：按「本任务第一行」起算的段落统计会把切换日志瞬间补写的行漏掉，
   要整份搜。
7. 证据文件名必须带版本号：两轮同名，后一轮覆盖了前一轮（靠虚拟机里的原始记录按新文件名补取回来）。
8. 变异验证的判读不能锚定行首（输出行有缩进），三次真红被记成了「未变红」；变异更不能拿模拟冒充。
9. 空参数会被命令行解析吃掉：`-Filter ""` 让 PowerShell 报「参数缺值」，测试根本没启动，而外层只看到「退出码 0」。
   长任务启动后要立刻核对「它真的在跑」（日志文件出现了）。
10. 常驻助手回传的控件文字是系统本地编码；按通用编码读会把「取消」认成别的控件。
11. 程序用标准输入传给解释器时，数据就不能再走标准输入；`tee` 漏了追加参数会盖掉前面的判定。

## 九、可以再优化的方向（需要用户决定，本轮都没做）

1. **界面程序加单实例保护**：现在用户再点一次图标会起第二个实例。加了以后「再点一次触发守卫」这类情况从根上
   消失，也不会有两个界面同时操作。改动不大，但会影响使用习惯（比如用户想开两个窗口对比），请裁定。
2. **把任务落盘时机挪到启动项记录写完之后**，或引入一个明确的「准备中」阶段：比加锁更彻底（守卫的判据自然
   成立），但改动面大、要动状态机与恢复环境读取方。目前加锁已够，建议先不动。
3. **无副档的大镜像做挂载探测很慢**（40 GB 镜像 189 秒）：可以改成不挂载、直接列镜像目录判断。普通备份都会
   写副档，只有副档丢了才会走到这一步。
4. **放弃命令的「半成功」**：任务已标失败、但清理产物被拒时命令整体报错。可以拆成两步分别报告，让用户知道
   「任务已经作废，只是材料没清掉」。
5. **自启的界面程序与登录时的自动备份会撞**：本版已不会误清，但建议在说明文档里提醒：需要登录即备份的话，
   用界面自己的计划功能，不要另外放脚本。
