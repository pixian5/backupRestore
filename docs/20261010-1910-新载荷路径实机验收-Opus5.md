## 二、新载荷路径的实机确证

`boot-entry.json` 记录的实际载荷位置与 BCD 对象：

```
wimPath = H:\BackupRestoreRE\10d65594-f7d3-4eb9-966c-83fdbe7af2d6\Winre.wim
taskId  = 10d65594-f7d3-4eb9-966c-83fdbe7af2d6
loader  = {b3bbe997-c499-11f1-8922-a44a0dbe1d02}
devopts = {b3bbe996-c499-11f1-8922-a44a0dbe1d02}
```

即 `BackupRestoreRE\<任务ID>\Winre.wim`。机器**凭这条路径真实启动进任务 WinRE 并完成恢复**，
说明 2.2.0 改动的 `ramdisksdipath` 与 ramdisk 路径在实机成立。

判读要点：若路径改动有误，表现会是 bootmgr 启动失败或 `payload WIM is missing`，
而不是能一路走到 `apply` 阶段。清理后两个 BCD 对象均已从终态 BCD 删除，
父目录 `BackupRestoreRE` 因无其他任务载荷而被 `prune_empty_parent` 回收
（`STAGING_PARENT_EXISTS=False`），这正是 2.2.0 设计的行为。清理日志逐字记录了按任务子目录删除：

    new boot channel: staging directory
      \\?\Volume{0e68475f-4890-43f3-ab85-75e8339116ac}\BackupRestoreRE\10d65594-f7d3-4eb9-966c-83fdbe7af2d6
      removed and verified

即删除走的是**卷 GUID 路径 + 任务 ID 子目录**，不信任跨重启的盘符，也不触碰父目录下其他内容。

## 三、两次恢复入口与真实写盘

`Recovery-early.log` 记录了同一任务的两次恢复入口：

- **11:00:30 首次**：各卷按卷 GUID 定位并核验稳定身份——RECOVERY→`C:`、SOURCE/TARGET→`D:`、
  IMAGE→`F:`（复用已挂载盘符）、EFI→`Z:`（`mountvol` 直接分配失败后经 `diskpart` 成功，4108ms）。
  日志明确记录「挂载稳定身份已核验：准备期 0/2，现场 Some(0)/Some(2)」。
  随后走到 `apply` 被注入错误拦下，`fault-apply.json`：
  `{"point":"apply","mode":"error-once","at":"2026-10-10T11:00:37.928Z"}`。
- **11:01:15 重试**：同一任务重新挂载、身份复核通过，完成格式化 → 应用 → 清理，
  `11:01:20` 写入 `success`。

真实格式化证据 `diskpart-format.txt`：

```
select disk 0
select partition 5
format fs=ntfs quick
```

### 次数的准确说明（复核更正）

初稿曾写「只发生了一次格式化」，**这是错的**。`images\Recovery.log` 显示：

| 时刻 | 动作 |
|---|---|
| `11:00:36.486` | diskpart 格式化（第 1 次），`DiskPart 成功格式化该卷` |
| `11:00:37.929` | `ACCEPTANCE_CHECKPOINT apply error-once` → `Recovery retry required at TargetErased`，保留启动项与载荷 |
| `11:01:18.119` | diskpart 格式化（**第 2 次**） |
| `11:01:19.547` | `dism /Apply-Image /Index:1 /ApplyDir:D:\` 跑到 100%，`The operation completed successfully.` |

准确表述是：**镜像应用只发生一次，格式化发生两次**——任务在 `TargetErased` 阶段失败，
重试时从该阶段重入，会再次格式化已擦除的目标。这是设计行为（目标本就已擦除且即将被覆盖），
不是缺陷；但不能说成「只格式化一次」。

### 本次运行**未**验证引导修复

`11:01:19.607` 日志明确：

    STEP 3/4 校验
    data-volume restore: target has no SYSTEM hive; skipping BCDBoot

本轮用的 `test.wim`（Index 1 / Name `RE213` / 32,505,896 字节）是**数据镜像**，

**默认按钮即"重试"**（代码判 `IDRETRY=4` 才继续循环）。宿主发送 Enter 后对话框消失、

恢复已完成的任务只重试清理，不会再次擦除目标」。

## 五、2.2.1 的 ImageAcceptance 实机行为

`task.json` 中 `verifyHash=true`、`imageAcceptance=None`。正常通过校验的镜像**不写例外**，
符合 2.2.1 的设计意图——例外只在真正越过副档判据时产生，不会退化成默认状态。

## 六、本轮踩的两个坑（已固化到验收说明）

1. **`--test-fault none` 不被接受**。[`windows_prepare.rs:436`](../crates/backuprestore-cli/src/windows_prepare.rs#L436)
   有白名单，只放行 6 个硬编码值或 `recovery_fault::valid()` 通过的 `acceptance:*` 值。
   要做到"失败一次后可重试"，正确值是 `acceptance:apply:error-once`。
2. **`prlctl send-key-event --key enter` 是无效键名**，退出码 255 且**静默无效**——
   前一轮按键没生效就是这个原因。必须用 `--scancode`：Enter=28、Tab=15。

另一条操作经验：**持续型故障（`acceptance:apply:error`）在 WinRE 内无法解除**。
WinRE 没有 Parallels Tools，`prlctl exec` 不可用（退出码 255），写不了 `H:` 上的
`fault-released`；而 `prlctl reset` 后一次性启动请求未被消费，会再次进入 WinRE。
此类用例应改用 `error-once`，或预先在正常 Windows 侧安排解除条件，
否则只能靠 `prlctl snapshot-switch` 回退。

## 八、仍未覆盖的边界

- **引导修复（BCDBoot）**：本轮目标无 SYSTEM 配置单元，按数据卷契约跳过该步，
  新载荷路径下的 BCDBoot 与启动项修复**完全未验证**。需用系统镜像在 C: 或第二系统分区另做。
- **两个未终结任务并存**：问题 9 的并发窗口。本机单测已覆盖清理隔离
  （`cleanup_never_touches_another_tasks_payload`），实机并发用例未做。
- **`acceptance:entry-fields:error` 失败补偿**：2.2.1 新增，需 `BR_ACCEPTANCE_ROOT` /
  `BR_ACCEPTANCE_SNAPSHOT` 夹具显式运行。
- **ESP 定位的多候选场景**：多 ESP、ESP 无挂载点、隐藏恢复卷排在 ESP 前。
- **真实断电矩阵在新路径下重跑**：2.1.9 的 11 点取自旧的共用载荷路径。
- 两个未终结任务并存（问题 9 的并发窗口）、`entry-fields` 失败补偿、ESP 多候选场景、
  真实断电矩阵在新路径下重跑。

**后续系统卷边界已在 2.2.2 的独立验收中补齐**：真实系统镜像还原到第二系统分区、
