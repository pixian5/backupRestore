# 多字节切片 panic：两处真缺陷（v2.6.72）

> 来源：`经验/07-墓碑与争议清单.md` §3「未决悬案/待修项」里的 H-GUI-1 / H-GUI-2。
> 两条都记着「待修，建议 `chars().take()`」，但一直没人动。这轮把它俩修了。

* * *

## 一、这两个缺陷为什么值得优先修

它们不是「可能有点问题」，而是**确定会崩溃**，而且崩在很糟的位置：

| 缺陷 | 位置 | 触发条件 | 后果 |
| --- | --- | --- | --- |
| **H-GUI-2** | `text_parsing::extract_timestamp_hms`（每天刷新进度都会走） | 日志行 `[...]` 里含中文，且 `字节长度-8` 落在字符中间 | 进度窗口 / 恢复流程**线程 panic** → GUI 直接 abort，可能停在半恢复状态 |
| **H-GUI-1** | `native_gui` 读 WIM 索引失败的**诊断分支** | WIM 的 `ImageName` 是中文，JSON 超 4096 字节 | **诊断代码自己成了崩溃源**：用户看到「解析失败后程序直接消失」 |

★ 第二条尤其讽刺：这段代码本来是用来**告诉你出了什么错**的，结果它先把你干掉了。
而 GUI 的窗口过程一 panic 就是**整个进程 abort**，没有栈回溯、没有提示。

## 二、先写用例，跑在未修的代码上（红）

纪律：**新判据要先证明它会红**。所以先只加用例、不改实现：

```rust
// inside 是 10 个三字节汉字（30 字节），30-8=22 落在第 8 个字符中间
assert_eq!(extract_timestamp_hms("[一二三四五六七八九十]"), None);
```

实跑输出（未修版本）：

```
thread '...timestamp_extraction_survives_multibyte_tail' panicked at text_parsing.rs:682:31:
start byte index 22 is not a char boundary; it is inside '八' (bytes 21..24 of string)
test result: FAILED. 1 passed; 1 failed
```

**这就是那个缺陷的现场**——不是我推理出来的，是它自己炸给我看的。

## 三、两处修法

### H-GUI-2：按字符定位尾部

```rust
// 旧：if inside.len() >= 8 { let tail = &inside[inside.len() - 8..]; ... }
//     len() 是**字节**数，偏移落进字符中间就 panic。
if let Some((start, _)) = inside.char_indices().rev().nth(7) {
    let tail = &inside[start..];
    ...
}
```

`char_indices().rev().nth(7)` 一次解决两件事：
- 不足 8 个**字符**时返回 `None` → 跳过（保持原来「太短就不认」的语义）；
- 够 8 个字符时给出的是**字符边界**上的字节下标，切片永远安全。

### H-GUI-1：按字符截断

在 `text_parsing`（**无条件编译**，本机可测）里加一个共享助手：

```rust
pub(crate) fn truncate_chars(value: &str, max_chars: usize) -> String
```

`native_gui` 的诊断分支改用它。顺带把「超长才加省略号」的语义也收进助手，
调用点不再自己判断长度。

## 四、顺手扫了一遍：其余「像字节切片」的地方为什么安全

改完一类缺陷后必须扫同类，但**扫描结论要写清楚理由**，否则下次有人会「凭感觉」去改一通：

| 位置 | 为什么安全 |
| --- | --- |
| `windows_prepare::image_path_info` 的 `&normalized[..2]` / `[..3]` | 前面先调 `validate_absolute_path`，它已保证 `len>=4` 且 `bytes[0]` 是 ASCII 字母、`[1]==':'`、`[2]=='\\'` → 前 3 个字节一定是字符边界 |
| `native_gui::trim_edition` 的 `words[..len-1]` | 是对 **Vec** 切片（不是 str），且有 `words.len() >= 3` 前置守卫，不会下溢 |
| `gui_text` / `i18n` 里的 `&rest[..open]`、`&after[..close]` | 下标来自 `str::find(字面量)`，`find` 返回的一定是字符边界 |
| `boot_entry` / `boot_menu_window` 的 `String::from_utf16_lossy(&buffer[..n])` | 切的是 `u16` 缓冲区（UTF-16 码元），与 UTF-8 字符边界无关 |
| `boot_menu` 的 `entries[..i]` | Vec 切片 |

结论：**真缺陷就是文档记的那两处**，其余属于「看起来像，实际安全」。
