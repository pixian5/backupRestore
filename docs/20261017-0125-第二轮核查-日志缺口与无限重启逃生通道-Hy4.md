## 二、新发现：日志缺口

### 高严重度

#### 1. RE 里「逃生决策」的唯一日志写在 RAM 盘 —— 重启即丢 ⭐ 本轮最有价值的一条
- **位置**：`main.rs:977`
  ```rust
  let escape_log = PathBuf::from(r"X:\BackupRestore-escape.log");
  ```
  `recover_env_interactive` 里**所有**关键决策都写这一个文件：策略与连败计数（1078）、
  达阈值的判断（1081）、`pause` 弹框还剩多少毫秒（1139）、用户选了「是/否/超时」（1169/1190）、
  `wpeinit` 失败原因（997）、`auto_escape` 的每一步（disarm 成功 / 标终态 / 失败原因）。
- **问题**：WinRE 里 `X:` 是**内存盘**。程序是从 `X:\Windows\System32\Recovery.exe` 起来的
  （`poc/build-backuprestore-pe.ps1:122`：`winpeshl.ini -> Recovery.exe --pe-desktop`），
  `X:\` 上的任何东西**重启后全部消失**。
- **后果**：机器自动逃出、回到 Windows 之后，用户想查「为什么逃出、连败了几次、当时选了什么」——
  **一个字都找不到**。任务目录里的 `Recovery.log` 只有恢复链自己的输出，不含这些逃生决策。
  连败 3 次这种最需要复盘的事件，证据恰好写在唯一会消失的盘上。
- 同类：`main.rs:1388` `X:\BackupRestore-Recovery-early.log`（早期日志，Recovery.log 可用之前的
  失败全靠它）—— 同样重启即丢。

#### 2. PE 会话内 GUI / 在线操作的日志全部写在 `X:\Windows\System32\logs`
- **位置**：`native_gui.rs:668` `state.executable_dir.join("logs").join("gui.log")`，
  即 `<exe 所在目录>\logs`；PE 里 exe 在 `X:\Windows\System32\` → `X:\Windows\System32\logs\gui.log`。
  同理 `panic.log`（`main.rs:433`）、`launcher-errors.log`（380）、在线日志
  `BackupRestore-online-*`（`online_log.rs:38`，exe 目录可写时优先它）。
- **后果**：PE 里做的任何操作（备份 / 还原 / 装第二系统 / 打开完整程序），
  只要 PE 一重启，gui.log / panic.log / 在线日志**全部归零**。而 PE 恰恰是最容易出事的环境。
  只有 `pe_operation` 的 `operation.log`（`pe_operation.rs:309`，写在任务目录 `self.dir`）能幸存，
  前提是任务目录不在 RAM 盘。
- 对比：PE 退出路径（`write_pe_exit_log`，`native_gui.rs:8191-8209`）**做对了**——
  优先写卷 GUID 路径（重启后仍在 ESP 上），最后才写 `X:\exit-pe.log` 当次排查用。这个思路应该推广。

#### 3. 三处「设 bootsequence + 重启进 PE」：bcdedit 输出不落盘，其中一处零日志
- **位置**：
  - `native_gui.rs:5675-5681`（主界面「重启进入 PE」）：`run_cmd_to_file(&command, None)`，
    前后各有一行 `append_gui_log`（命令 + 退出码），**bcdedit 的真实输出丢了**。
  - `native_gui.rs:7210-7218`（`schedule_pe_task`）：同上。
  - `native_gui.rs:5757-5772`（`--pe-reboot` 桌面快捷方式）：**连 `append_gui_log` 都没有**，
    失败只在弹框里显示退出码（`5759` 取 `code`，`5772` 拼进文案）。
- **后果**：这三处是**改引导 + 立刻重启**，是整条链上后果最重的动作之一，
  却连「bcdedit 到底说了什么」（元素未找到 / 拒绝访问 / 参数无效）都没留下。
  快捷方式那条更彻底：进程结束后没有任何痕迹表明这台机器被设置过一次性启动项。

## 三、卡死 / 无限重启：逃生通道盘点

### 3.1 已具备通道的（确认可用）

| 场景 | 通道 | 备注 |
|---|---|---|
| DISM 挂死（7 处） | 可配超时 + Job Object 杀进程树 | **默认 0 = 不限制**，必须先在设置里配 `dism_timeout_secs` 才生效 |
| RE「暂停」弹框无人应答 | `MessageBoxTimeoutW` 到期执行与「是」相同的清理 | 默认 0 = 无限等；**到期分支未在 RE 内实机触发过** |
| 进度窗「暂停」后无人继续 | `wait_if_paused` 总超时 + 关窗置 `pause_abandoned` | v2.6.10 才把配置值真正灌进 env，此前恒为 0 |
| 主进程被杀 | Job Object 句柄关闭 → 子进程树一起死 | **杀进程 ≠ 留下半截写盘**，这点是对的 |
| PE 里任务执行完卡住 | 「命令提示符(K)」开 cmd 跑 `wpeutil reboot` | PE 桌面仍可能残废（整窗禁用） |
| 引导改坏 | 进度窗「BCD 回退」按钮 | |

### 3.2 没有逃生通道的（本轮确认）

#### A. GUI 一启动就把机器重启走，用户无法在界面里叫停 ⭐
- **位置**：`native_gui.rs:9612`
  ```rust
  if super::resume_pending_boot_task()? { return Ok(()); }
  ```
  在 `run()` 里、创建主窗口**之前**执行。只要存在一个合法的待续跑任务，且 `rearm` + `shutdown` 成功，
  就 `shutdown /r /t 0`（`main.rs:695`）直接重启，然后 `return Ok(())` —— **用户只是想打开程序，
  窗口都没见着就被重启了**。
- **出口**：没有。GUI 里没有「取消待续跑任务 / 放弃 / 稍后再说」的任何控件。
  CLI 有 `abandon-task`，但它在任务已擦除目标卷之后**拒绝**清理（安全边界，正确），
  于是被擦除过的悬置任务在 GUI 侧完全无解。
- 唯一的间接出口：创建新任务时弹的「检测到尚未终结的任务」三选一（`5847-5915`，
  是 / 否=放弃并清理 / 取消）—— 但那要求用户**先去点创建任务**，而这一步之前机器可能已经被重启。

#### B. 自动重启只有「每阶段一次」的计数，没有跨阶段的全局上限
- **位置**：`main.rs:522-543` `claim_boot_resume_attempt`（marker `boot-resume-{stage}.attempted`），
  `546-553` `release_boot_resume_attempt`（失败路径会**删掉** marker）。
- **机制**：可续跑阶段共 8 个（`stage_resumable_after_interruption`，727-739）。
  marker 是 per-stage，所以**阶段一推进，计数就归零**。稳定性故障（每次都在 RE 里推进一小步然后死）
  可以让机器在「回 Windows → 启动 GUI → 再重启进 RE」之间走**最多 8 轮**，且每轮都重启用户的机器。
- 某种意义上 `auto_escape` 会把任务标成 `Failed` 从而终止循环，但那是**恢复链内**的保护；
  从 Windows 侧发起的自动续跑没有全局闸门。

#### C. PE 无限进：逃生依赖「PE 桌面能起来」这个前提
- 已知：`native_gui.rs:812/897` 注释写明「Parallels 等虚拟机的 bootsequence 可能不被固件消费」——
  不被消费 = **每次开机都进 PE**。
- 逃生：`pe-exit-*` 路径（`8360-8444`）会恢复 `default`、清 `bootsequence`、逐条校验，
  失败时 `show_diag_dialog` 停在 PE 里，**不重启**（8443-8447）——这段设计是对的。
- **但前提是 PE 桌面窗口能建起来**：`native_gui.rs:9568-9570`，`CreateWindowExW` 返回 null 就
  `return Err` → 进程退出 → PE 是 shell-free 的（`winpeshl.ini` 直接拉起本程序），
  **于是屏幕上什么都没有、没有任务栏、没有 cmd 快捷键**。此时只能硬断电，而重启又因为
  bootsequence 没清掉再次进 PE —— 真正的死循环。
- 同理：PE 里若 `wpeinit` 没让键盘就绪（RE 入口已经防了这条，PE 桌面没有对应的设备枚举），
  窗口建起来了但没法点。

#### D. `--pe-reboot` 快捷方式：设了就重启，GUI 里没有反向操作
- **位置**：`native_gui.rs:5757-5780`。设置成功 → 弹框告知 → 用户手动重启（或后续自动重启）。
- **缺口**：全仓搜 `/deletevalue {bootmgr} bootsequence` 的调用点只有四处
  （`boot_entry.rs:730` 任务内、`boot_menu.rs:1073`、`online_operation.rs:733`、`pe_operation.rs:773`、
  `native_gui.rs:8388` PE 退出）—— **没有一个是「Windows 桌面上的用户自救按钮」**。
  一旦快捷方式设了启动项而 PE 又起不来，用户在 Windows 里只能手敲 `bcdedit`
  （或者像项目历史那样挂 PE 光盘改 BCD）。

#### E. `close_and_wait` 的 join 仍然没有超时（上一轮卡死 5，未修）
- **位置**：`recovery_progress.rs:1446-1452`。窗口线程若卡在 `refresh_from_log`（日志增量巨大时
  一次性读全量）或 BCD 回退闭包（持锁跑 bcdedit），恢复链就永久阻塞在 `join()` 上，
  **连失败重试弹框都到不了** —— 也就是说 A/B/C 那些逃生阀全在它下游。

## 四、交叉结论（本轮的三条结构性观察）

1. **「写了日志」不等于「日志还在」。** 本轮最有价值的两条（1 和 2）都不是"没写"，
   而是**写在了会消失的盘上**——`X:` 是 WinRE/PE 的内存盘。上一轮审查的视角是"这段有没有
   `append_log`"，漏掉了"这个路径重启后还在不在"。**判据要加一条：日志落点是否跨重启存活。**
   对照组是 PE 退出路径（`write_pe_exit_log`），它按「卷 GUID → 同卷子目录 → X:」三级落盘，
   是唯一做对的地方，可以直接照抄。

2. **无限重启的两种形态，本仓防住了一种。** 防住的是「RE 内失败 → bootsequence 仍指向 RE」
   （`auto_escape` + 标终态 + per-stage marker）。没防住的是「Windows 侧发起的自动重启」：
   它无声（`return Ok(())`）、无界面出口（A）、无全局计数（B）。两者的差别在于
   **前者有用户可见的对话框，后者连窗口都没有**。

3. **最重的两个动作恰好日志最薄。** 「改 BCD + 重启」在本仓有 4 个入口
   （`resume_pending_boot_task` / 主界面重启进 PE / `schedule_pe_task` / `--pe-reboot`），
   其中 2 个零日志或只有退出码，而它们的效果是**立刻重启用户的机器**。
   相比之下，只读类的 mountvol 探测写得反而更细。日志密度与实际风险是**反相关**的。
