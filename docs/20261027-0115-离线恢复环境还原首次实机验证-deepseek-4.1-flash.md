## 1. 一个推翻原计划的发现

上一轮我判断「用小测试卷走离线通道就能低成本验证」，**错了**。

实测备份 C: 立刻失败（294 ms）：

```
[ERROR] invalid task: active Windows volume must be processed offline
```

★ 这条限制**同时管备份与还原**，不只是还原。我此前记成「只有在线还原拒活动系统盘」。
代码位置：`windows_prepare.rs:2563`（`restore-existing target must be the active Windows volume`）
与备份侧的同类检查。

后果：**离线通道只能用活动系统卷（C:）做目标**，小数据卷方案不成立。
所以只能走完整 C: 往返——那就先把空间账算清楚。

## 2. 空间账（本轮最关键的前置判断）

| 时点 | 宿主空闲 |
|---|---|
| 开工前 | 196 GiB |
| 离线备份完成（镜像 31.36 GB 落 H:） | 160 GiB |
| 还原过程中（写入 C:） | 152 GiB |
| 收尾 | 151 GiB |

C: 实际只用 **74 GB**（不是历史口口相传的 87 GB），fast 压缩后镜像 **31.36 GB**。
按「宿主 ≥ 镜像 × 2.5 ≈ 78 GB」核算，196 GiB 够用 → 才动手。
★ 若还按 87 GB 那个数去估，会得出「必须 220 GB、现在做不了」的错误结论。

## 4. 判据（三条，互相独立）

```
sentinel.sh verify --drive C
  SENTINEL_GONE=1
  SERIAL_BEFORE=0x569864f6  SERIAL_AFTER=0xf66a622e  SERIAL_CHANGED=1
  VERDICT=PASS
```

```
（镜像同目录 H:\BRImages\Recovery.log）
RESTORE_SELFCHECK target=C serial_before=569864F6 serial_after=F66A622E ntoskrnl=true
```

- **外部事实**：哨兵消失（卷被整体重写）+ 序列号变化
- **正向证据**：`ntoskrnl=true`（写进去的是完整系统，不是空卷）
- **交叉验证**：产品自报 `569864F6→F66A622E` 与 `fsutil` 外部读数 `0x569864f6→0xf66a622e`
  **逐位一致**——两条不同代码路径，不是仪器自洽

全机 `RESTORE_SELFCHECK` 计数：**TOTAL=2**（`workspace logs=1` 是在线 `target=T`，
`image dir=1` 是本次离线 `target=C`）。此前为 0。

## 5. 一个差点漏判的坑：RE 的日志不在 `H:\brwork\logs`

第一次搜索 `H:\brwork\logs` 只找到**在线**那条（`target=T`），差点得出
「离线分支还是没写自检」的错误结论。

原因是**恢复环境的主日志写在镜像同目录**：`H:\BRImages\Recovery.log`（91.9 MB）。
这是记忆里的既有结论（「RE 主日志 = 镜像同目录 `Recovery.log`」），但它离
「验证自检行」这个用途太远，实际搜索时容易漏。

★ 判据教训：**「搜不到」先想「是不是搜错地方了」**，再怀疑产品没写。
