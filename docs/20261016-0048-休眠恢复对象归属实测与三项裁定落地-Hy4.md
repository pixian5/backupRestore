## 1. 实测要回答的问题

还原完成后，`{bootmgr}`（启动管理器）上的两个字段指向不同系统：

- `default`（开机进哪套）→ 本次**新还原出来的系统**（2026-10-15 你定的规则）
- `resumeobject`（**休眠唤醒进哪套**）→ 被代码主动改回**原来那套系统**的快照值

要测的是：**Windows 会不会自己把这个字段改对？**

- 如果**会**：现状无害，两个字段不一致只是暂时的。
- 如果**不会**：不一致会长期存在，需要重新评估。

## 2. 实测方法

在 Parallels 的「Windows 11」虚拟机上实机操作（该机即日常验证机）。

| 步骤 | 操作 | 结果 |
|---|---|---|
| 0 | 记录原始状态 | `default {41326e72-…35fc}`、`resumeobject {41326e71-…35fc}`、`displayorder` 同上、`timeout 10` |
| 1 | `powercfg /a` 查休眠可用性 | **休眠未启用**（该机是 S0 现代待机） |
| 2 | `powercfg /h on` 开启休眠 | 成功，休眠与快速启动变为可用 |
| 3 | `bcdedit /deletevalue {bootmgr} resumeobject` | 操作成功完成 |
| 4 | 回读确认 | **`resumeobject` 字段已消失** |
| 5 | `shutdown /h` 休眠 | VM 状态 compressing → stopped |
| 6 | `prlctl start` 启动（从休眠恢复） | running |
| 7 | 回读 | **`resumeobject` 重新出现，且值 = 删除前的原值 `{41326e71-…35fc}`** |
| 8 | 确认是"真休眠恢复"而非冷启动 | 见下 |
| 9 | `powercfg /h off` 关闭休眠、删临时文件 | 机器恢复原状 |

### 第 8 步：如何确认是恢复而非冷启动

如果 VM 是冷启动，那么 `resumeobject` 被重建就可能另有解释（比如开机时的某个例行任务），
结论会不成立。所以必须排除。

用系统进程 `lsass`（开机即启动、不重启就不换）的启动时间来判断：

```
lsass 启动时间：2026-10-15 00:50:16     ← 昨天
当前时间：      2026-10-16 00:47:48     ← 今天
```

**`lsass` 已经连续运行一整天**——说明是**从休眠恢复**，不是冷启动。
若是冷启动，它的启动时间应该是本次开机时刻（00:45 左右）。

## 3. 结论：Windows 会自己维护这个字段，**现状安全**

**在一个完整的"休眠 → 唤醒"周期里，Windows 把被人为删掉的 `resumeobject`
重新写了回去，而且写的正是当前系统配对的那个恢复对象。**

这直接说明：`{bootmgr}.resumeobject` **不是**一个只在装系统 / 跑 bcdboot 时写一次的静态值，
而是 **Windows 在休眠时动态维护**的字段——它要在关机前告诉启动管理器「下次唤醒用哪个恢复对象」。

### 对还原流程意味着什么

还原完成后，`default`（新系统）与 `resumeobject`（旧系统）不一致，但：

1. 用户在新系统里**第一次休眠 / 快速启动时**，Windows 就会把 `resumeobject` 改写成**新系统**的配对恢复对象；
2. 因为是**先写后关机**，所以连"第一次休眠"本身也是正确的——不会出现唤醒走错系统的情况；
3. 只有在**没有任何待恢复的休眠镜像**时，`resumeobject` 才不起作用，那时开机走的是 `default`，本来就正确。

**→ 不一致是瞬时的、会自动修正的，不需要改代码。**

### 顺带印证的两件事

- **健康机器上 `default` 与 `resumeobject` 是成对的**：本次实测机 `default` 是 `…72`、
  `resumeobject` 是 `…71`——同一套系统的「启动加载器」与「休眠恢复对象」两个兄弟对象，
  由系统一起创建。我们还原后写回的是旧系统的兄弟对象，所以看起来"不成对"，这也正是
  之前觉得别扭的来源。
- **代码里「快照里没有该字段就删掉」的分支是安全的**：既然 Windows 会自己补回来，删掉不会
  造成功能缺失。（该分支是 2026-10-14 resumeobject 不对称事故的修复之一。）

### 现场已复原

- `powercfg /h off` 已执行，`powercfg /a` 显示「休眠：尚未启用休眠」——与测试前一致；
- `resumeobject` 回读为原值 `{41326e71-…35fc}`；
- 临时文件 `C:\br-proc.txt` 已删除。

## 4. 另外三项裁定的代码落地（commit `e2c57b0`，v2.6.4）

### 4.1 删除旧方案兼容分支

> 你的裁定：「既然已经更新了逻辑，删除是否可以？毕竟没人用旧程序了」

已删。具体做法与理由：

- 移除 `DefaultPolicy` 枚举与 `BootMenuPlan.default_policy` 字段；
  `decide_default` 从「策略 + 目标 + 原默认项 + 菜单列表」四个入参简化为**只吃目标加载器一个入参**，
  规则只剩一条。`DefaultDecision` 去掉了 `warning` 字段（不再有需要告警的分支）。
- 移除 `set_default_policy` 及 `main.rs`、`online_operation.rs` 两处调用。

**一个关键取舍（为什么是删字段而不是删枚举变体）**：

如果只删掉 `PreserveCurrentDefault` 这个枚举变体、保留 `default_policy` 字段，
那么旧方案 JSON 里残留的 `"default_policy":"PreserveCurrentDefault"` 在反序列化时会因为
**未知枚举值而读取失败**。
所以改为**把整个字段删掉**——这样旧 JSON 里残留的该字段会被 serde 当作未知字段忽略，
**旧方案文件照样能读**。已加单测
`legacy_plan_carrying_a_removed_default_policy_field_still_loads` 锁住这一点。

测试数 8 → 4（删掉 4 个只测被删分支的用例）。

### 4.2 盘符不再写死，改精确判定

> 你的裁定：「不要写死，你改代码精确判」

`install_pe_harddisk`（安装 PE 入口的目标校验）里原来的
`drive_char == 'C' || drive_char == 'S'` 已改为三条精确判定：

| 判什么 | 原来 | 现在 |
|---|---|---|
| 系统盘 | 盘符等于 `C` | 读环境变量 `%SystemDrive%`（新增 `system_drive_letter()`） |
| EFI 系统分区 | 盘符等于 `S` | 按**分区类型 GUID** `{c12a7328-…}` 判（复用 `windows_prepare::EFI_TYPE`，改为 `pub(crate)`） |
| 程序所在卷 | 取盘符首字母，取不到算空格 | `is_program_drive()`，取不到就判"不是" |

**"取不到就如实说不知道"**：`system_drive_letter()` 返回 `Option<char>`，
环境变量缺失时返回 `None`（此时不按"是系统盘"拒绝），**绝不退回字母 C**。

另外三处同类兜底也一并改掉：
- 目标盘符取不到 → 直接拒绝（原来 `unwrap_or('C')` 造出一个"合法目标"）；
- 备份索引名的「源卷是不是系统卷」判定 → 取不到就判"不是"，索引名降级成 `Windows (F:) 日期` 形式；
- 「默认 PE 目录」排除程序所在盘 → 取不到就不排除任何卷。

修掉的三种误判：系统盘不是 C 拦不住 / EFI 分区不在 S 拦不住 / C 或 S 其实是数据盘却被误拦。

## 5. 第五项（恢复环境注册降级）：你要的澄清 —— 到底发生在哪些流程里

> 你说："降级，但是你这个没说清楚是备份还原还是 PE，我不好决策"

我把调用链查清楚了。**这个检查只在「还原 Windows 系统」时才会触发**，其余流程根本走不到：

| 流程 | 会不会触发恢复环境注册 | 依据 |
|---|---|---|
| **备份**（任何通道） | **不会** | `pe_operation.rs:255` —— `operation == "backup"` 直接走 `backend.backup()`，不进还原链 |
| **还原数据卷** | **不会** | PE 通道：`pe_safety.rs:238-240` 意图为「数据覆盖」时 `boot()` 整个跳过；离线通道：`main.rs:2833-2846` 走另一分支，日志写「跳过 BCDBoot」 |
| **还原 Windows 系统（PE 通道）** | **会** | `pe_operation.rs:788` 调 `winre_registration::repair` |
| **还原 Windows 系统（离线通道）** | **会** | `main.rs:2794`（第二系统，走 `repair_secondary`）与 `main.rs:2796`（重建唯一系统，走 `repair`） |
| **还原 Windows 系统（在线通道）** | **不会** | `online_operation.rs:951` 注释明写：在线非 PE 环境不调用，该修复本身也拒绝非 PE；目标系统的恢复环境留到它自己首次启动后用 `reagentc` 完成 |

**触发时机很关键**：它发生在 `boot()` 的**末尾**——也就是**镜像已经铺完、引导已经修好之后**。
所以一旦因为缺组件而失败，前面所有工作都白做，而系统本身其实是好的。

**失败点**：`winre_registration.rs:314-321` 先检查目标卷有没有这两个东西，
缺任一个就直接返回错误「目标缺少离线注册组件」，**整个任务失败、无任何降级**：

- `Windows\System32\reagentc.exe`
- `Windows\System32\config\SYSTEM`

**代码里已有同类放行先例**：`windows_prepare.rs:2101-2108`（注释标着【P2】）处理过几乎同源的问题——
数据卷镜像本来就没有这两个文件，那里改成按「目标卷当前有没有 SYSTEM 注册表文件」分叉判定，不再一刀切硬拒。

### 需要你定的（现在信息应该够了）

**在「PE 通道还原 Windows 系统」和「离线通道还原 Windows 系统」这两种情况下，
目标卷里缺少上面两个文件时，要不要从"整个任务失败"改成"记警告 + 跳过注册 + 照常报成功"？**

- 选**降级**：代价是产出的系统没有恢复环境（以后想进恢复环境修系统会进不去），
  建议**必须**在最终结果里明确告知，不能静默跳过。
- 选**维持硬失败**：代价是"镜像铺完才失败、前面全白做"的场景继续存在。

**我建议先做一次实测再定**：确认「不注册恢复环境会不会导致系统进不了桌面」。
如果会导致进不了桌面，那就不是可选能力，不能降级。
