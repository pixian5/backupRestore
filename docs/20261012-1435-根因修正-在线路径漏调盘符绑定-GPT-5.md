# 根因修正：在线路径漏调 secondary_registry::repair 导致盘符未绑定

日期：2026-10-12 14:35
模型：GPT-5

> 🚫 **本文档修正同日 14:25 的 `20261012-1425-第二系统崩溃根因-克隆注册表绝对路径-GPT-5.md`。**
> 那份文档定性为"sysprep 泛化缺失"，**这是错的**。程序里早已有对应解法，只是在线路径没接上。

## 真正的根因（一句话）

离线路径在 `bcdboot` 前会调用 `secondary_registry::repair()` 做**系统盘符绑定**，
在线路径 `restore_to_windows_volume` **漏了这一步**，
导致第二系统启动时 `MountedDevices` 的 `C:` 仍绑定主系统分区，
注册表/service 里的 `C:\...` 绝对路径全部指向错误的卷 → 服务初始化失败 → 崩溃循环 → 桌面起不来。

## 证据链

### 1. 项目文档里记录过一模一样的故障（10-09）

`docs/20261009-0620-C盘断电自动续跑与第二系统完整验收-GPT-6.md` 第 38–44 行：

> ### 第二系统黑屏与系统盘符绑定
>
> **任务状态成功仍不能证明新系统能用。首次启动实际进入 `D:\Windows`，
> 离线事件日志记录 LogonUI（登录界面）与 dwm（桌面窗口管理器）反复崩溃。
> `MountedDevices` 的 C: 仍绑定主系统分区，第二系统自身被分配为 D:。**
>
> 新增 `secondary_registry.rs`，在镜像应用完成、首次启动前读取离线 SOFTWARE 中的原 `SystemRoot`，
> 备份 SYSTEM/SOFTWARE 及事务日志族，再按 GPT（GUID 分区表）`DMIO:ID:` 二进制身份
> **绑定原系统盘符至新分区，只清除该目标的重复盘符映射**，回读并成功卸载配置后才继续。

**症状与本次完全一致**：`LogonUI` + `dwm` 反复崩溃。

### 2. 上次成功那次，第二系统启动后是 C:

`docs/20261009-1955-失败恢复与断电边界验收-GPT-6.md`：

> **第二系统实际启动为 C:**，文件、核心服务、桌面、独立恢复注册通过

因为走的是离线路径，`secondary_registry::repair()` 已把盘符绑定好。

### 3. 代码层面确认

`main.rs:2643-2649`（离线路径，bcdboot **之前**）：

```rust
let windows_root = target_root.join("Windows");
let previous_boot_manager = if target.role == TargetRole::NewWindows {
    secondary_registry::repair(&target_root, &target.volume, log)?;   // ← 盘符绑定
    Some(boot_manager_state_from_task_snapshot(store, task, log)?)
} else {
    None
};
```

全项目对 `secondary_registry` 的引用只有两处：
- `main.rs:67` —— `mod secondary_registry;`
- `main.rs:2648` —— **唯一调用点，在离线路径里**

`online_operation.rs`（在线路径）中 `secondary_registry` **零命中**。

### 4. 现场数据吻合

E: 的注册表里全是 `C:\` 硬编码（含 `C:\ProgramData\Microsoft\Windows Defender\...`），
而 `MsMpEng.exe`（Defender 主引擎）崩溃时加载的正是 `C:\ProgramData\...\4.18.26080.4-0`——
**它在 E: 系统上跑，却去 C: 盘找文件**。这正是盘符未绑定的直接后果。

## 修复方向

**把 `secondary_registry::repair()` 接进在线路径**，位置在
`restore_to_windows_volume` 的 **DISM /Apply-Image 之后、bcdboot 之前**，
与离线路径 `main.rs:2648` 的时机一致。

需要评估的点：
- 在线路径的 `target_root` 是按 GUID 卷路径（`\\?\Volume{...}\`）拿到的，
  而 `repair()` 期望的是普通根路径——**路径形态可能需要转换**
- 在线路径没有 `TargetRole` 概念，需要显式判定"这是新建 Windows 场景"
  （`restore_to_windows_volume` 本身就已确认目标是 Windows 卷，可直接调用）

## 我犯的方法论错误

我拿到崩溃现象后，**直接推演根因并写文档+提交**，没有先查项目文档里是否已有同类问题的记录。
项目里 `20261009-0620` 白纸黑字写着同样的症状和同样的解法。
**正确顺序应是：先搜历史文档 → 再查代码有无对应实现 → 最后才提新假设。**

这与已记录的"照抄历史文档当当前事实"是**同一条教训的反面**：
那次是「历史文档不可信」，这次是「**历史文档不可跳过**」。两者都指向同一个动作：
**动手写代码前，先把相关历史记录读一遍。**
