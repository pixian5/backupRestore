## 一、为什么这一轮值得记

引导修复功能从 2.3.8 写到 2.3.9，自测一路全绿（134 单测 + Windows 侧编译 + 产物标记核对），
但复核查出 **10 项问题，其中 4 项会导致还原失败或改坏主系统**。
这说明"测试通过 + 编译通过 + 产物含新代码"**不足以**证明一个会写 BCD 的功能是对的——
它们只能证明"我写的代码按我想的方式运行"，证明不了"我想的方式是对的"。

更值得记的是：**有两项问题是我自己刚加的防护被我自己绕过**。

- 我加了 `restore_target_index()` 并写注释"调用方一律用本方法定位，不要硬编码 0"，
  结果唯一的调用方（编辑窗口）仍是 `cursor: 0`——而我同一轮刚把目标项从首位挪到末位。
  用户打开弹窗直接改名，改的是**主系统**的名字。
- 我新加的测试 `default_names_are_distinct_and_versioned` 自己编了两个不同的名字再断言它们不同，
  **永不失败**，而真正的重名约束（`validate`）压根没有。

## 二、10 项问题与处置

### P0（会失败或改坏数据）

| # | 问题 | 处置 |
|---|---|---|
| ① | `read_image_version_name` 会产出字面的 `unknown unknown`：`windows_edition`/`windows_build` 在本项目里**从来只被写成 `"unknown"`**（`WINDOWS_EDITION` 环境键只有读取者、无任何生产者），两个字段都非空所以 `is_empty()` 守卫全部通过 | 加 `usable()` 过滤占位值（`unknown`/`n/a`）；并新增 DISM `/Get-WimInfo` 直读 WIM 的 Edition/Version 作为后备——那是映像自带的，不依赖我们备份时写了什么 |
| ② | 取消勾选任一既有系统 → `apply` 把它从 `displayorder` 删除 → `selected` 不含旧默认项 → **默认启动项漂移到刚还原的系统**；随后在线路径的断言又判定失败，于是 BCD 已改坏却报失败且无回滚 | `BootMenuEntry` 新增 `is_current_default`，`discover` 按 loader id 比对 `{bootmgr}.default` 填充；`toggle` 与 `validate` 双重拒绝取消它 |
| ③ | PE 路径 `set_secondary_boot_menu` + `preserve_primary_boot_manager` 在 `apply` **之后**运行，用 `task.boot_menu_name` 覆盖用户改的名字、按快照顺序重写 `displayorder`，把排序和取消勾选一起丢掉——与弹窗"本列表就是最终顺序"的承诺直接矛盾 | 把 `apply` 移到这两步**之后**，使它成为最后一个写 BCD 的步骤 |
| ④ | 快照无 `resumeobject` 时，`/deletevalue` 分支被我删掉了：bcdboot 新写的值留在原地，预检与终检都判定"resume_object 变了"而报失败，且休眠恢复指向错误系统 | 在线路径与 `apply` 内部都补回 `else` 删除分支（删除失败是良性的） |

### P1（特定环境下全线失效）

| # | 问题 | 处置 |
|---|---|---|
| ⑤ | 我把 loader 判据从 OR 改成 **AND**（device 与 osdevice 都要有），同时猜中文 osdevice 标签是「操作系统设备」——而仓库里已实战验证的写法是 **`os 设备`（带空格）**。猜错 + AND = 中文机器上**所有 loader 都匹配不上**，引导修复全线失效 | 抽出 `block_is_loader_for`：恢复 OR 语义（猜错一个标签只少一项证据，仍能工作）、键名用 `starts_with` 兼容含空格的「os 设备」、列出已知拼法、改为显式排除 `ramdiskdevice`。**依据**：真实 resume 对象的 path 是 `winresume.efi` 而非 `winload.efi`，所以 path 检查本身就排除了它，OR 是安全的 |
| ⑥ | `existing_name` 在候选卷**挂载之前**读 BCD：无盘符的 Windows 卷在 bcdedit 里显示成 `\Device\HarddiskVolumeN`，按盘符查必然查不到 → 误判成"没有条目" → `apply` 覆盖掉用户起的名字（正是本轮要防的缺陷） | `discover` 改为两段：先把所有候选卷挂上盘符，再统一读 BCD |
| ⑦ | 编辑窗口 `cursor: 0`，而目标项已被挪到末位：用户打开窗口输入名字按保存，改的是主系统 | 光标初始化为 `restore_target_index()` |
| ⑧ | 重名无人拦：两个同补丁级别的未登记系统都得到同一个版本串，菜单出现两个一模一样的项 | `validate` 新增重名拒绝（只算已勾选项）；`discover` 返回前对撞名的默认名补盘符区分 |

## 三、测试变化

138 项（原 134）。关键的是**替换了假测试、补了真契约**：

- 删掉 `default_names_are_distinct_and_versioned`（自己编名字再断言不同，永不失败），
  换成 `versioned_names_satisfy_the_menu_constraints`：验证版本化名字能过 `validate` 全部约束、
  相同版本串**必须被拒绝**、加盘符后恢复合法。
- 新增 `current_default_entry_cannot_be_unselected`：toggle 拒绝 + validate 兜底。
- 新增 `duplicate_menu_names_are_rejected`：含"未勾选项不参与重名判定"。
- 新增 `loader_lookup_survives_a_missing_osdevice_label`：只有 device 时仍要认出 loader
  （这正是本地化标签未被识别时的观感，AND 语义会在这里失效）。
- 新增 `loader_lookup_accepts_chinese_os_device_with_space`：锁住「os 设备」带空格的真实写法。
- 改写 `loader_description_ignores_ramdisk_and_resume_objects`：夹具形态取自仓库里已验证的
  `main.rs::secondary_loader_selection_ignores_resume_object`，而不是我编的形态。

## 五、方法论结论

这一轮最该留下的不是修了什么，而是：

**写 BCD 这类"失败即破坏"的功能，自测通过只是起点。** 本轮 10 项里有 6 项是靠
"逆向追问每个假设的来源"发现的——`windows_edition` 真的有人写吗？中文标签真的是这么拼吗？
`apply` 真的是最后一个写 BCD 的吗？这些问题单测答不了，因为单测测的是我的假设本身。

**自己刚加的防护要回头检查有没有被自己绕过。** ⑦ 和 ⑧ 都是这一类：
我加了正确的工具（`restore_target_index`）和正确的意图（重名测试），
却没在唯一的调用点用上它、也没让测试真正驱动被测逻辑。
