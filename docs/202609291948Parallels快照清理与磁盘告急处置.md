# Parallels 快照清理与磁盘告急处置

## 背景
执行「只保留最近 3 个快照」时发现宿主磁盘已濒临写满：

- `/System/Volumes/Data` 可用 **646 MB**（容量占用 100%）
- `Windows 11.pvm` 体积 **350 GB**，其中快照链共 **39 个**，全部是 2026-09-29 当天的 PE 通道实验快照
- 三块虚拟盘（harddisk / harddisk1 / harddisk2）的基底 `be303189` 合计约 140 GB

磁盘只剩几百 MB 且虚拟机仍在运行（持续写入活动增量盘），属于随时可能写满导致 VM 崩溃/增量盘损坏的高危状态。

## 处置方案
按**由旧到新**的顺序逐个删除快照，而不是从新往旧删。原因：

Parallels 删除快照 X 时，是把 X 的**子快照增量合并进 X 的文件**再改名承接子快照身份。
从最旧端删时，被合并的子增量（几百 MB ~ 1.5 GB）写入的是已分配好的大基底文件，
绝大多数块是**原地覆盖已有块**，文件几乎不增长，合并完成后子增量文件即被释放 —— 每删一个都是净释放空间。
反向（从新往旧）删则会让小文件去吸收大增量，峰值占用高，在仅剩 646 MB 时极可能 ENOSPC 失败。

实际效果验证了这一点：删第一个（最旧的 `be303189`）后可用空间立刻从 646 MB 涨到 3.5 GB。

## 执行记录
- 共删除 **36 个**快照，保留最近 3 个：
  - `e9b6419a` 20260929-172221-newchan-v111-diag15
  - `8c011708` 20260929-173050-newchan-v111-diag16
  - `61adc34b` 20260929-184538-procmon-case-ab
- 脚本内置保护：每删一个前检查可用空间，低于 500 MB 立即中止
- 每步之间 `sleep 4`，给 Parallels 的异步合并留出时间
- 结果：可用空间 **646 MB → 186 GB**；`Windows 11.pvm` **350 GB → 169 GB**

## 经验教训

1. **zsh 不做单词切分**：`for id in $LIST` 在 zsh 下会把整个字符串当成一个元素传给 `prlctl`，
   首次批量删除因此整批失败（报 `Unable to find the snapshot ID`）。必须用数组 `LIST=(...)` + `"${LIST[@]}"`，
   或 `${=LIST}`。本机默认 shell 是 zsh，写批处理脚本时务必注意。
2. **快照链没有干净基线**：39 个快照全是当天实验快照，最旧的 `be303189` 本身已是 "pe-channel-poc-bcd-copy-test"，
   并非未改动过的正常 Windows 状态。清理后最早可回退点是 diag15（17:22），已经处在 PE 实验中段。
   后续做引导项变更实验前，应先建立一个明确命名的**干净基线快照**（如 `baseline-clean-windows`）并长期保留，
   不要让它混在按序号递增的实验快照里被当作普通旧快照清掉。
3. **实验快照要设上限**：本轮一天内积累 39 个快照、吃掉约 180 GB。建议约定实验快照数量上限，
   或在每轮 PE 通道实验收尾时顺手清理 diag 系列。
