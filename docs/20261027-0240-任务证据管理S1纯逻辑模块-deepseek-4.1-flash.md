## 1. 为什么先做这一层

`native_gui` 是 `cfg(windows)` 专属——写在里面的逻辑在 mac 上是**零信息**（编译器根本不打开那个文件），
而「任务怎么排序、坏记录怎么显示、失败原因怎么措辞」全是可测的纯函数。
先把它们剥到无条件编译的模块里，本机就能跑测试；即使 S2 的窗口设计要返工，这层逻辑仍然复用。

## 2. 模块接口（`crates/backuprestore-cli/src/task_admin.rs`，约 400 行含测试）

```rust
pub(crate) struct TaskRow {
    pub id: String,
    pub dir: String,            // 任务目录绝对路径，界面要显示给用户去翻
    pub operation: Operation,
    pub status: StatusRecord,   // 反序列化后的类型，不存 Value
}

pub(crate) enum RowDefect {                 // 分开报，不合并成「记录损坏」
    TaskMalformed(String),                  // task.json 坏
    StatusMalformed(String),                // status.json 坏
    IdMismatch { task: String, status: String },  // 两份 taskId 不一致
}

pub(crate) fn parse_row(task_json, status_json, dir) -> Result<TaskRow, RowDefect>;
pub(crate) fn sort_rows(rows: &mut [TaskRow]);       // 最新在前，同刻按 id 升序
pub(crate) fn combo_label(index, row, lang) -> String;   // `#1 10-27 01:15 备份 成功`
pub(crate) fn defect_combo_label(index, dir, lang) -> String;
pub(crate) fn defect_lines(defect, dir, lang) -> Vec<String>;
pub(crate) fn detail_lines(row, lang) -> Vec<String>;
```

### 三个刻意的设计决定

1. **`TaskRow` 直接持有 `StatusRecord`**，而不是把阶段/进度/错误拆成散字段。
   这样「阶段」「错误码」「失败原因」的措辞可以**完全复用 `status_receipt::render_status_lines`**——
   状态框和任务详情对同一个故障必须说同一句话。若各写一套，迟早出现「状态栏说有码、详情说没码」。
2. **不复用 `native_gui::operation_display`**：那个函数接受 `&str` 且覆盖 GUI 页签里的
   `install-pe-entry` / `restore-data` 等非枚举值；本模块要无条件编译，只能依赖 core 的 `Operation` 四值。
3. **坏记录仍然可选中**：`defect_*` 系列保证一个坏目录不会让整个列表打不开，
   且明确说清是 `task.json` 还是 `status.json` 坏了——两者的修法完全不同。

## 3. 9 条单测（`cargo test -p backuprestore-cli task_admin`）

| 用例 | 守什么 |
|---|---|
| `successful_task_has_no_error_lines` | 成功态不得出现「失败原因 / 错误码」两个字 |
| `failed_with_code_shows_the_code` | 失败带码 → 详情含 `BR-PE-039` 与原因原文 |
| `failed_with_empty_reason_is_called_out` | 实机存在的 `error: ""` → 必须说破「未记录原因」 |
| `broken_task_json_reports_defect_instead_of_panicking` | 非法 JSON 不 panic，报 `TaskMalformed` 并给路径 |
| `broken_status_json_reports_defect` | 阶段值是枚举外的字符串 → `StatusMalformed` |
| `id_mismatch_is_flagged_not_ignored` | 两份 taskId 不一致 → `IdMismatch`，不按其中一份行事 |
| `capturing_task_is_incomplete_and_warned_first` | `capturing` 判未完成，警示在**第一行**，进度 45% 可见 |
| `rows_sort_newest_first_and_stable_on_same_instant` | 最新在前；同一时刻按 id 升序（稳定） |
| `combo_label_carries_index_time_operation_and_stage` | 序号/时间/操作/阶段都在；英文界面不混中文 |

**结果 9/9 通过。**

## 4. 变异验证（判据必须能单独失败）

| 变异 | 期望 | 实测 |

| 排序降序 → 升序 | 只有排序用例红 | `8 passed; 1 failed` ✅ |
| 去掉 `is_incomplete()` 守卫 | 只有 capturing 用例红 | `8 passed; 1 failed` ✅ |
| 去掉 `taskId` 一致性检查 | 只有 IdMismatch 用例红 | `8 passed; 1 failed` ✅ |
| 三次 `diff` 还原后复跑 | 9/9 全绿 | ✅ 逐字节还原 |

三条变异**各自只让一条用例红**，说明判据互不覆盖——若多条同时红，就分不清是哪条判据在起作用。

## 5. 两个测试夹具坑（值钱的细节）

`Task` 的必填字段比想象的多，`#[serde(default)]` 只覆盖一半。构造测试夹具时连续撞了两次
`missing field`：

1. **`bootPlan`**（`BootPlan.mode` 无 default，枚举值 `return-existing` / `add-secondary`）
2. **`created` / `bootOnce` / `status`** —— 也是必填

最终可用夹具（与真机形状一致）：

```json
{"taskId":"…","version":1,"operation":"backup",
 "bootPlan":{"mode":"return-existing"},
 "created":"2026-10-27T01:00:00Z","bootOnce":false,"status":"success"}
```

★ 这条教训值得记：**写测试夹具前先去读一次结构的 serde 属性**，比一条条试 `missing field` 快得多。
