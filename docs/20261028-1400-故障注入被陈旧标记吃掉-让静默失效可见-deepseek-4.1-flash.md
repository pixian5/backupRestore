# 故障注入被"陈旧标记"吃掉：让静默失效变成可见（v2.6.74）

> `经验/07 §3` 未决清单最后一条真缺陷。清单给的建议是「改标记位置」，我读完代码后
> **没有照做**——理由在下面第二节。

* * *

## 一、这是个什么坑

故障注入（fault injection，故意制造崩溃来验证恢复流程）靠一个**一次性标记**防重放：

```
<任务目录>/.fault-<故障名>.triggered
```

第一次注入后写这个标记；重启回到同一阶段时看到标记就**不再注入**——否则会无限重启。

问题出在「任务目录会被复用」。我们的验收夹具就是**固定 task id**：

```
H:\br-accept\tasks\adb8700a-f29d-4219-9f32-7731079ff6e6
H:\br-accept2\tasks\49a99148-0036-498a-98d3-971a5f169e06
```

于是上一轮跑完留下的标记，会把**这一轮**的注入吃掉。后果不是报错，而是：

> 用例照样绿，**但那个故障根本没发生**——它什么都没验。

这正是本项目最贵的坑：**报告通过但什么都没验**。而且它极难发现，因为你看到的是一片绿。

## 二、为什么我没照清单的建议改「标记位置」

清单写的是「按日志路径定位 → 跨任务只触发一次」，暗示把标记挪个地方就好。

但换个位置要解决的核心矛盾是：**标记必须跨重启存活**（防重放），同时**不能跨任务存活**（防吃掉）。
这两个要求用同一个文件很难同时满足——挪到哪儿都还是「一个会被复用的路径」。

真正的问题是**测试侧复用了任务目录**，不是产品侧把标记放错了。所以：

- 改标记位置 → 会让「同一任务只触发一次」的语义失效（重启后无限重放，更糟）；
- 正确做法 → **两道保险**：
  1. **产品侧**：被陈旧标记抑制时**大声记日志**，再也别静默；
  2. **门禁侧**：跑前把夹具根下的陈旧标记清掉。

## 三、改动一：注入被抑制时留痕（产品）

`main.rs::interrupt_after_stage_if_requested` 原来是这样：

```rust
if marker.is_file() {
    return;          // ← 静默，什么都不说
}
```

现在：

```rust
if marker.is_file() {
    append_log(log, &format!(
        "TEST_FAULT={fault} injection=suppressed_by_stale_marker marker={}; \
         an earlier run left this marker, so NO fault was injected this time",
        marker.display()));
    return;
}
```

★ 关键在 `injection=suppressed_by_stale_marker` 这个**可 grep 的结构化痕迹**：
以后有人怀疑「这个故障到底注入了没有」，搜这一个词就能判断，不用去猜。

## 四、改动二：门禁跑前清标记（工具）

放在 `STEP 2`（准备夹具）之后、正式跑用例之前：

```
  FAULT_MARKERS_CLEARED=2
```

清完还要**再扫一遍**确认真的没了；没删干净就 `ERROR=stale_fault_marker_not_removed` 并退出。

★ 这里又踩了同一个老坑并当场处理了：`dir` 搜索没有匹配时输出为空，
而「空」既可能是「真的 0 个标记」也可能是「命令没跑」（`prlctl exec` 约 1/8 不执行）。
所以命令尾部加 `__END__` 哨兵：**连哨兵都没有 = 仪器故障**，不许当成「0 个」。

## 五、判据

| 项 | 做法 | 结果 |
| --- | --- | --- |
| 清理真的发生 | 往两个夹具根各埋一个 `.fault-*.triggered`，跑 `--only no_write_on_reject` | `FAULT_MARKERS_CLEARED=2`，用例 `PASS` |
| **副作用**（不是只看自陈数字） | 跑完直接 `dir /b /s …` 复扫 | 只剩 `SCAN_DONE`，两个标记都没了 |
| 第二次跑（没有标记时） | 完整门禁 | `FAULT_MARKERS_CLEARED=0`（不是 error，证明「0 个」与「读不到」分得开） |

## 六、顺带一条部署教训

这次部署我用 `Select-String -Pattern 'DEPLOYED|error'` 过滤输出，结果**整段是空的**。
差点当成「部署没跑」。真因是 PowerShell 把原生命令写到 **stderr** 的
`Finished \`release\` profile…` 当成 `NativeCommandError` 抛出，管道里的输出被吞了。

★ 幸好没有停在「没输出」上：改成直接比对 **部署件哈希 vs 产物哈希**，两边一致
（`f14f32c8…`）才算数。**「没输出」不能当「成功」，也不能当「失败」，要另找证据。**
