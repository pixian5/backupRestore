> 时间：2026-10-29 02:05　模型：deepseek-4.1-flash　版本：**不升版本**（本机这份镜像不含任何代码改动，代码仍是 2.6.76）
>
> 一句话：**仓库里那份 PE 镜像从「v2.6.75 载荷」换成了「v2.6.76 载荷」**，而且这次不是听构建脚本说「成功」，是把镜像重新挂起来、把里面的程序抠出来算哈希对上的。

## 一 为什么要重出，而不是直接把虚拟机里那份拷回来

PE 里的程序是**在构建镜像的时候烤进去的**（`poc/build-backuprestore-pe.ps1` 把
`BackupRestore.exe` / `Recovery.exe` / 两个 `VCRUNTIME140*.dll` / `winpe-winpeshl.ini`→`winpeshl.ini`
拷进挂载好的 ADK `winpe.wim`，再卸载提交、导出）。

所以：

- 虚拟机里那份 `93483be2…` 里的程序是 **2.6.75**（`build-result.txt` 记 `Package=…-v2.6.75`）；
- 当前代码是 **2.6.76**（本轮加的是「盘符时间线」观测）；
- 直接把 `93483be2…` 拷回仓库 → 下次重测 PE 又测一遍旧行为、而且拿不到 PE 环境里的盘符时间线
  （PE 恰恰是盘符最该被观测的地方）。

于是选**先重打包、再重出镜像、最后回写**。代价是十几分钟构建，收益是「仓库里的件和代码同一版」。

---

## 二 怎么把 v2.6.76 打成包（关键：不需要在虚拟机里跑 cargo）

`windows/build-windows.ps1` 产出的「包」其实就是一个**普通目录**，七个文件：

```
BackupRestore.exe / Recovery.exe     ← 同一个二进制拷两份
VCRUNTIME140.dll / VCRUNTIME140_1.dll
VERSION                              ← 一行 "2.6.76"
winpe-winpeshl.ini                   ← PE 桌面壳模板
build-manifest.json                  ← 版本 + binarySha256 + 其余元信息
```

而构建 PE 的脚本挑包的方式是：**在 `C:\BackupRestorePE\package\` 下按修改时间取最新的
`BackupRestore-windows-arm64-*` 目录**，只要求里面有 `Recovery.exe`。

所以不必为了更新包在虚拟机里再编译一次（`cargo build --locked` 还要 `C:\brtarget` 之类一堆前提），
**把上一版目录整个复制成 v2.6.76，换掉两份程序、改 VERSION 与清单里的版本号和哈希**即可，
产出的目录与脚本自己生成的完全同构。本轮就是这么做的，做完逐项核对：

- 目录 7 个文件齐全；
- `BackupRestore.exe` 与 `Recovery.exe` 都 = `2bf7234f…`（与部署到 `H:\brwork` 的 2.6.76 一致）；
- `VERSION` = `2.6.76`（8 字节，含 CRLF）；
- 清单里 `version` = `2.6.76`、`binarySha256` = `2bf7234f…`；
- 目录修改时间 01:55 晚于 v2.6.75 的 01:01 → 构建脚本会挑它。

> ⚠️ 本轮踩到的一个小坑：把清单文件先命名成 `.tmp-manifest.json` 再让虚拟机去共享盘上取，
> 报「系统找不到指定的文件。已复制 0 个文件」——**共享文件夹看不见以点开头的隐藏文件**。
> 改成普通文件名 `manifest-2676.json` 立刻成功。（同名现象上一次是 ACL，见 `经验/02 §11`；
> 这次是「不可见」，报错文案一模一样，别混。）

## 三 构建与验证：脚本说成功不等于镜像里有新程序

`build-backuprestore-pe.ps1` 的验证段做的是**存在性检查**——12 个文件在不在、壳是不是逐字等于预期。
它**不检查那两个 exe 是哪个版本**。这正是「报告通过但什么都没验」的那类情形：
拿上一版包去跑，它一样打印成功。

所以本轮多做了一步真正的判据：

1. 把新导出的 `C:\BackupRestorePE\BackupRestorePE.wim` **只读挂载**（`dism /Mount-Image … /ReadOnly`）；
2. 算 `Windows\System32\Recovery.exe` 和 `Windows\System32\BackupRestore.exe` 的 SHA-256；
3. 两个都 = `2bf7234f…` → **镜像里真的是 2.6.76**；
4. 顺手把 `winpeshl.ini` 打出来看，仍是 `[LaunchApps]` + `%SYSTEMROOT%\System32\Recovery.exe,--pe-desktop`；
5. 卸载（`/Discard`）。

构建结果（虚拟机 `C:\BackupRestorePE\build-result.txt`）：

```
Output=C:\BackupRestorePE\BackupRestorePE.wim
SHA256=6205569648623113e978b7253ce5cc4b738d82067692a4f1184b0c102bdb9283
Package=C:\BackupRestorePE\package\BackupRestore-windows-arm64-v2.6.76
Completed=2026-10-29T01:57:22.3904396+08:00
```

**构建前先把上一份镜像改名留底**（`ren … BackupRestorePE-v2.6.75.wim`）——脚本开头会
`Remove-Item` 输出文件，万一中途失败，改名前它已经是唯一一份 2.6.75 的件了。

## 四 回写仓库：判据只有大小和哈希

传输走「虚拟机 → 共享目录」写新文件名（`pe-boot.new.wim`），**不覆盖旧件**，因为宿主侧
`pe-assets/*.wim` 是只读权限（`-rwxr-xr-x`）时 SMB 会**假成功**（`copy` 退 0、`&& echo OK` 也打印 OK，
实际「已复制 0 个文件」）。落地后宿主侧核对：

```
412932733 字节                     ← 与虚拟机 dir 的大小一致
62055696…（SHA-256）               ← 与 build-result.txt 一致
```

两条都对上，才做轮换：旧件改名 → 新件改名成 `pe-boot.wim` → `chmod u+w`。

## 六 还剩什么

- **`pe-assets/` 不在版本控制里**（`git ls-files pe-assets/` 为空）。这 412 MB 的件
  **只有本机磁盘这一份**，删了就没了。要不要入库（或至少记个哈希清单进版本库）由用户定。
