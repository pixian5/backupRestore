# v2.6.10：两处「配置项配了却不生效」的静默失效修复 + 实机三组对照验证

- **日期**：2026-10-17 01:16
- **版本**：2.6.9 → **2.6.10**
- **起因**：用户一句「你来核查并修复错误」——对 v2.6.9（`docs/20261017-0100`）的改动做独立复核，而不是接受上一轮的自我结论。
- **结论**：查出**两个真实缺陷**，都属于「**界面上的配置项写进了磁盘，但消费它的那条路径根本读不到**」，且**失效完全静默**（无报错、无日志、无提示）。已修复、已实机证明（三组对照）。
- **性质**：不是新功能，是**修正文档与行为不符**。上一轮文档把这两个配置列在"已完成"里，实际只有一半路径真的生效。

## 1. 缺陷 A：`dism_timeout_secs` 对 2/3 的调用路径完全无效

### 1.1 现象（文档声称 vs 代码事实）

`dism_timeout.rs` 模块头明确写了三个入口：

```
① 进程环境变量 BACKUPRESTORE_DISM_TIMEOUT_SECS
② 任务级 RecoveryTask.env 的 DISM_TIMEOUT_SECS（恢复环境无人值守时用它）
③ 程序设置 BackupRestore.settings.ini 的 dism_timeout_secs
```

但 `wait_ms()`（唯一的取值函数）**只读进程环境变量**，而给这个变量赋值的**唯一位置**是 `recover_env`（`main.rs`，恢复环境入口）。于是三个消费方里：

| 消费方 | 所在进程 | 经过 `recover-env`？ | 实际取值 |
|---|---|---|---|
| `pe_operation::long_wait_ms` | PE / RE | **是** | ✅ 生效 |
| `online_operation::dism`（**在线还原**） | 普通 Windows 的 CLI/GUI | **否** | ❌ 恒为 `INFINITE` |
| `native_gui`「安装 PE」的 `dism /Apply-Image` | GUI 进程 | **否** | ❌ 恒为 `INFINITE` |

**即：用户在设置窗口把 `dism_timeout_secs` 设成 300，对「在线还原」和「GUI 安装 PE」这两条最常用的路径完全不生效。** 而这两条恰好是 `20261016-2250` 审查里点名的卡死 3 与卡死 6。

### 1.2 为什么上一轮没发现

上一轮的冒烟**只验了「设置窗口能写对并落盘」**（ini 四行值正确）——那是"写"的一端；"读"的一端从来没被触达过。这正是项目纪律里说的**弱信号**：写对了不等于生效了。

### 1.3 修法

在 `main()` **最早期**（任何子命令分派、任何子进程派生之前）加一次：

```rust
#[cfg(windows)]
crate::dism_timeout::init_process_env_from_settings();
```

新函数按两条规则决定是否灌值（抽成纯函数 `plan_env_value`，便于单测且不碰进程环境）：

1. **环境变量已被显式设置 → 绝不覆盖**。否则 `recover_env` 从任务读到的**任务级值**会被 ini 悄悄改掉，破坏"无人值守以任务为准"的契约。
2. **ini 为 0（默认）→ 不写**。保持"读不到 = 不限制"的单一语义，也不给每个进程多设一个没有信息量的 0。

`#[cfg(windows)]` 是必须的：`mod dism_timeout` 是 `cfg(any(windows, test))`，macOS 的非测试构建里没有这个模块（漏了会直接编译失败——核查时就是这样发现的）。

## 2. 缺陷 B：`failure_pause_max_wait_secs` 只覆盖了一种暂停，另一种读的是无人设置的变量

### 2.1 现象

`failure_policy.rs` 的 `pause_max_wait_secs` 是"暂停逃生阀"，它本该在**两种**暂停场景都生效：

| 暂停场景 | 实现 | 读的值 | 实际 |
|---|---|---|---|
| 失败达阈值 → 弹框等用户按「是/否」 | `MessageBoxTimeoutW`（`main.rs`） | `policy.pause_max_wait_secs`（来自 `RecoveryTask.env`） | ✅ 生效 |
| 用户点进度窗「暂停」→ 恢复链在步骤边界等待 | `recovery_progress::wait_if_paused` | 环境变量 `BACKUPRESTORE_PAUSE_TIMEOUT_SECS` | ❌ **全仓无写入方** |

全仓 grep 证实：`BACKUPRESTORE_PAUSE_TIMEOUT_SECS` **只有一处读取、零处写入**（`recovery_progress.rs` 里一枚裸字符串字面量）。`pause_total_timeout()` 因此**恒为 0 = 不限制**。

**后果**：没人值守时用户点了「暂停」就走人，恢复链会**永远停在那里**——而这正是该配置项存在的意义。上一轮文档把这条列成"`wait_if_paused` 加总超时 ✅"，实际是这个超时**永远不会到期**。

### 2.2 修法

1. 把键名提为**单一来源常量** `failure_policy::PAUSE_TIMEOUT_ENV_VAR`，`recovery_progress` 改用它——裸字符串各写各的正是本 bug 的成因。
2. 新增 `FailurePolicy::pause_timeout_env_value()`：`pause` 策略给配置值，auto-escape 给 0（它从不进入暂停态，给数字反而会误中断）。
3. 在 `recover_env` 里（与 DISM 上限同一个块）把该值**灌进进程环境变量**，0 也显式写一次（避免父进程遗留旧值）。

## 3. 实机三组对照验证（在线路径，Linux 宿主 + Parallels Windows 11）

### 3.1 方法

`online_operation::dism` 在**调用 DISM 之前**就会把等待上限写进 `Online.log`：

```
DISM 开始（等待上限 …）：["/English", "/Capture-Image", … /CaptureDir:S:\…]
```

所以只要让流程走到 DISM，无论 DISM 成功与否，**这一行就是"配置是否被读到"的直接证据**。用 `S:` 卷（310 MB）作源、镜像写到 `H:\brwork`——DISM Capture 在 S: 上必然失败（退出码 32），但**失败不影响取证**，且不触碰任何真实系统卷。

exe 位于 `H:\brwork\BackupRestore.exe`，故 ini 就在 `H:\brwork\BackupRestore.settings.ini`（**exe 所在目录**，与上一轮第 6 条坑一致）。

### 3.2 结果

| 组 | 条件 | 日志实测 | 判定 |
|---|---|---|---|
| **A** | 无 ini | `等待上限 不限制` | ✅ 默认零回归 |
| **B** | `dism_timeout_secs=300` | `等待上限 300000 毫秒` | ✅ **ini 生效** |
| **C** | `dism_timeout_secs=300` **+** env `BACKUPRESTORE_DISM_TIMEOUT_SECS=77` | `等待上限 77000 毫秒` | ✅ **显式优先，未被 ini 覆盖** |

三条规则（默认不限制 / ini 生效 / 显式优先）全部**实机钉死**。日志原文存 `.test-artifacts/online-A.txt`、`online-B.txt`。

### 3.3 顺带验证到的事

- **在线日志确实落在 `<exe>\logs`**（`H:\brwork\logs\BackupRestore-online-<pid>-<…>\Online.log`）——上一轮 `online_log.rs` 的改动在实机成立。
- 在线备份的中间产物目录 `.br-online-*` 在失败后**留在盘上**（三组留下三个）。已手工清理；**是否应自动收口，与 B2「非终态任务自动收口」同属一类问题**，记入待办。

## 5. 本轮教训（可复用）

1. **"写进去了"不等于"读出来了"。** 两个缺陷的共同形状：**写入方存在、读取方存在、但两边不是同一个键 / 不是同一个进程**。核查配置类功能时，必须**沿取值函数反查写入方**，而不是只验落盘。
2. **裸字符串键名是 bug 温床。** 缺陷 B 里，读取方写 `"BACKUPRESTORE_PAUSE_TIMEOUT_SECS"`、写入方写别的（甚至没有），编译器一声不响。键名应一律提为常量——这样"只有读取方、没有写入方"至少能在 grep 时暴露。
3. **单测锁纯判据、实机锁接线。** 单测能证明"判据对"，证明不了"这个进程真的调了它"。缺陷 A 只有跑一次真进程才能证伪——因此本轮把**"日志里读出实测值"**作为验收标准，而不是"ini 内容正确"。
4. **`cfg` 门控要跟着模块走。** `mod dism_timeout` 是 `cfg(any(windows, test))`；在 `main()` 里裸调用它，macOS 非测试构建立即编译失败。核查时正是靠这条错误才确认了模块门控关系（`pe_safety` 当年也是同一个坑）。
