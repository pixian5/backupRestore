**版本**：2.0.2 → 2.0.3  
**时间**：2026-10-01 00:29  
**模型**：Claude Sonnet 4.6 (Thinking)

## 背景与问题

### 问题 1：WinRE 进度窗口时钟停摆 / 呼吸箭头冻结

**根因**：`recovery_progress.rs::refresh_from_log` 函数开头有 `if size == *offset { return; }`。  
当底层正在进行大文件哈希计算、DISM 输出暂停等"日志无新字节写入"的间隙时，函数直接 `return`，导致：

- 右上角当前时钟**完全停摆**（可停数十秒甚至数分钟）
- 正在执行阶段的呼吸小箭头（`▶` 与全角空格交替）**直接冻结不动**
- 对用户产生"程序死锁/卡死"的错觉，直到 DISM 下一次打印进度时才突跳

### 问题 2：离线端无条件全量 SHA-256 哈希计算

**根因**：`main.rs::recover_windows` 在进入 DISM 之前，无论 GUI 前端是否勾选「严格对比哈希」，都调用 `verify_image_file` 对整个 WIM 文件执行流式 SHA-256 计算。  
对 60GB 镜像，这导致 WinRE 阶段 1 "挂载卷、校验"可白白等待 1~2 分钟，进度窗口完全无响应。

## 修改方案

### 优化 1：进度窗口 UI 与日志增量彻底解耦

**文件**：`crates/backuprestore-cli/src/recovery_progress.rs`

**策略**：
1. 拆分原来的 `refresh_from_log` 为两个独立函数：
   - `read_log_delta(shared)`：只负责读取日志增量并**更新缓存**（`cached_stage`, `cached_percent`, `cached_details`）；日志无新内容时直接 return，**不影响 UI**
   - `refresh_from_log(shared, hwnd)`：始终从缓存读取最新状态，并无条件完整驱动时钟、呼吸动画、进度条、详情区刷新，绝不假死

2. `ProgressShared` 结构体新增三个缓存字段：
   - `cached_stage: Mutex<Option<String>>` — 最近一次解析到的阶段名
   - `cached_percent: Mutex<Option<u32>>` — 最近一次解析到的百分比
   - `cached_details: Mutex<Vec<String>>` — 最近 4 条详情日志行

3. 每秒 `WM_TIMER` 触发时调用 `refresh_from_log`，无论日志是否有新内容，当前时钟精确每秒跳动，呼吸小箭头 `▶`/`　` 每秒平稳交替。

**效果**：消除时钟停摆与箭头冻结，界面始终保持活跃心跳。

### 优化 2：透传 verify_hash 标志，离线按需跳过全量哈希

**文件**：
- `crates/backuprestore-core/src/lib.rs` — `Task` 结构体
- `crates/backuprestore-cli/src/windows_prepare.rs` — `prepare_task`
- `crates/backuprestore-cli/src/main.rs` — `recover_windows`

**策略**：
1. `Task` 结构体新增 `verify_hash: Option<bool>` 字段（serde 默认为 None / false），与 GUI 校验选项框联动
2. `prepare_task` 中在 `RestoreExisting` / `CreateSecondary` 分支写入 `task.verify_hash = Some(options.verify_hash)`
3. 无 Sidecar 且未勾选哈希校验时，`sha256` 字段填充 `"0".repeat(64)` 合规占位，彻底跳过流式读盘
4. `recover_windows` 中根据 `task.verify_hash.unwrap_or(false)` 决策：
   - `false`（默认）：仅做文件大小核对（毫秒级），直接进入 DISM 还原
   - `true`（勾选严格对比）：执行完整 SHA-256 流式校验

**效果**：默认模式（不勾选哈希）下，阶段 1 校验从 1~2 分钟缩短到毫秒级，立即推进 DISM 还原。

## 已知限制

- 填充 `"0".repeat(64)` 作为无 Sidecar 时的占位哈希，Task 校验规则要求 64 位合规十六进制字符串，因此用 `0` 填充合规。此时离线端仅做大小校验，不影响安全性（大小已与 `image.size_bytes` 一致）。
- 若用户未勾选哈希且镜像无 Sidecar，离线端 `verify_hash && !sha256_eq` 判断短路，不会误报哈希不匹配。
