# 连续还原三轮同错根因：被删旧 loader 被误判为"原有启动菜单项丢失"

> 轮次：2.4.1（构建哈希 `27873c34…` 起）
> 模型：Claude Opus 5
> 日期：2026-10-13 01:52
> 前置：[引导修复实机验证阻断缺陷与验收误报](./20261012-2036-引导修复实机验证阻断缺陷与验收误报-Fable5.md)
> 证据：`.test-artifacts/boot-menu-verify/round4/`（round3-online.log / round3-gui.log / round3-bootmgr-blocks.txt）

## 一、现象：三轮还原，同一句报错

22:28（CLI 后台）、00:13（CLI 后台）、01:46（**GUI 前台**）三轮还原，DISM 应用、
BCD 五项写入全部成功，最终验收一律报：

```
[ERROR] 在线操作未完成：invalid task: 原有启动菜单项丢失，拒绝报成功
```

前两轮修复（`{default}` 自引用别名展开、GUID 大小写统一）都是真缺陷但都没治本。

## 二、实机数据（第三轮，GUI PID 10768）

`bcdedit /store S:\EFI\Microsoft\Boot\BCD` 的 bootmgr（{9dea862c}）状态：

| 时点 | default | displayorder | timeout |
|---|---|---|---|
| STEP 2 快照 | {12e3701c}（C: 主系统） | **{cdf9efe4}**（上一轮还原建的 E: 旧项）、{12e3701c} | 10 |
| 引导修复后 | {12e3701c} ✓ | **{d146fb01}**（本轮新建 E: 项）、{12e3701c} | 10 ✓ |

对象清单里只剩旧项的 resume 对象 {cdf9efe3}，**{cdf9efe4} 本体已被删除**——
这正是"还原"该有的行为：目标卷的旧 loader 被新 loader 取代并清掉。

## 三、根因：Err 分支把"被取代"判成"丢失"

验收逻辑对快照里有、还原后菜单里没有的项，逐个 `bcdedit /enum {id}` 查证：

```rust
match object {
    Err(_) => true,   // ← BUG：对象被删 = 被新 loader 取代，却返回"丢失外来项"
    Ok(text) => { /* 只排除主系统活动卷，指向 E: 的也算丢失 */ }
}
```

两个分支全错：连续第二次还原起，上一轮的旧 E: 项必然被删（走 Err → 误报）；
即使对象还在、device 指向 E:（目标卷），Ok 分支也只排除 C:、照样误报。
**这个门禁从建过第二系统的那台机器起就永远过不去**，与别名、大小写无关。

注释写的意图（"查不到该项（已被删）时，只要目标卷换了新 loader 就认它属于目标卷"）
与代码行为相反——又一例"注释正确、代码写反"。

## 三点五、第四轮修正被推翻：被删对象的 bcdedit 退出码是 0

第四轮把"对象被删（bcdedit 查不到）"改成按被取代处理（`Err(_) => false`），
并按 device 指向判存活对象——**仍然失败**。加门禁全量日志跑第五轮前，先在客体
实测了关键行为：

```
> bcdedit /store …\BCD /enum {d146fb01-…} /v   ← 第三轮建的、已被删的 loader
  没有匹配的对象或存储为空。
  EXITCODE=0                                    ← 关键！
```

**bcdedit 枚举已删除对象时退出码为 0**，只输出本地化文案（中文"没有匹配的对象
或存储为空"）。于是 `run_capture` 返回 `Ok("没有匹配的对象…")`——`Err` 分支
**根本不会触发**；空文案里没有 device 行，"读不到 device 按丢失"的保守分支接棒
误判。四轮报错由此全部闭环：

| 轮次 | 二进制 | 缺项的枚举结果 | 误判路径 |
|---|---|---|---|
| 1–2（CLI） | 旧 | Ok（空文案） | device=""≠partition=c: → 丢失 |
| 3（GUI） | 别名+大小写修复版 | Ok（空文案） | 同上 |
| 4（GUI） | Err→false 修复版 | **Ok（空文案）** | device 为空→保守判丢失 |
| 5（GUI） | 带门禁日志版 | Ok（空文案） | 同上（日志将现场证实） |

## 四、修复（构建哈希 `0dfade0a…`）

- 对象**被删** → 按"目标卷旧 loader 已被取代"处理，不算丢失（apply 只删目标卷
  的旧 loader；新 loader 在菜单里有独立断言兜底）。
- 对象**仍存在** → 看 device 指向：目标卷=被取代（正常）；其它任何卷（含主系统
  活动卷、ramdisk PE 项）或读不到 device=真丢失，拦截。
- device 字段名同时识别英文 `device` 与中文 `设备`（沿用 2026-10-12 的本地化教训）。
- **最终修复**（第三点五节的发现）：对象存在性改用**结构性判据**——全文没有任何
  BCD 标识符（{guid}）即视为对象不存在=被取代，不算丢失。退出码与本地化文案都
  不可靠，这是唯一稳的判法。对象确实存在时才看 device 指向；device 为空仍保守
  判丢失。
- 判定抽成纯函数 `missing_entry_is_foreign`，回归测试直接采用实机数据：中文
  "没有匹配的对象或存储为空。"与英文 "The element data store is not present."
  两种空文案、{8b55181a} 存活对象、{12e3701c} 主系统、中文 设备 标签。
  Windows 侧 `cargo test` 全过。门禁判定全程落日志（快照/现菜单/缺失清单、
  每个对象的枚举结果与判定值）。

## 六、方法论教训

1. **连续失败同一个报错 ≠ 同一个根因**。三轮里前两轮修的是真缺陷（别名、大小写），
   但都没有先用实机数据验证"缺的到底是哪个对象、它还在不在 store 里"。第二轮
   修复后如果直接枚举 store 对象清单，一轮就能定位 Err 分支。
2. **验收断言自己也要对账**。报错文案说"菜单项丢失"，但真正该问的是三个子问题：
   缺哪项、对象是否仍存在、指向哪个卷。断言粒度太粗时，修复只能靠猜。
3. gui.log / Online.log 的**全文**优先于截图肉眼读数。
