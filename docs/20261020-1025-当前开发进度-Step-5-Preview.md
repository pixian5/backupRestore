## 2. 重大发现：DISM 挂载门禁参数缺陷（**安全闸门形同虚设**）

### 2.1 症状与实证（三组实验，全部有落盘证据）

| 实验 | 命令要点 | 结果 | 证据文件 |
|---|---|---|---|
| ① 复现代码原样调用 | `dism /Mount-Wim /ImageFile:H:\BRImages\br-2619-cur.wim /Index:1 /ReadOnly /MountDir:C:\br-probe` | **EXIT_MOUNT=87**（「错误: 87 … /imagefile 选项」）；随后 `/Unmount-Wim` 也报 50 | `.test-artifacts/recon-20261020/dism-health-20261020.txt` |
| ② 换正确参数 | `dism /Mount-Wim /WimFile:… /Index:1 /ReadOnly /MountDir:C:\br-probe2` | **EXIT_MOUNT=0**；`MARKER_reagentc=YES`、`MARKER_SYSTEM=YES`；`/Unmount-Wim /Discard` **EXIT=0** | `…/dism-wimfile-test-20261020.txt` |
| ③ 清理遗留挂载 | `dism /Cleanup-Wim` | **EXIT=0**，之后 `Get-MountedWimInfo` 列表为空 | 同上 |

> 结论：`/ImageFile` 是 `/Apply-Image` 的选项；`/Mount-Wim` 只认 `/WimFile`。**不是环境问题，是参数写错**。

### 2.2 代码定位与影响面

- 缺陷点：`crates/backuprestore-cli/src/windows_prepare.rs` 的 `wim_mount_markers()`（约 1822–1875 行）
  ```rust
  let mounted = run(&[
      "/Mount-Wim",
      &format!("/ImageFile:{image_path}"),   // ← 错：应为 /WimFile:
      &format!("/Index:{index}"),
      "/ReadOnly",
      &format!("/MountDir:{}", mount_dir.display()),
  ])?;
  ```
- 后果链：`wim_mount_markers` 恒返回 `Err` → `wim_full_windows_probe()` 走 **Err 分支的「镜像名启发式」**（`windows_prepare.rs:1796–1806`）→ 只有名字含 `windows pe` / `winpe` 才拒绝，否则 `Ok(ProbeOutcome::HeuristicPass)` 放行。**「只读挂载 → 探 `reagentc.exe` + `SYSTEM` hive」这条权威判定从未真正执行过。**
- 受影响的两处调用（同一函数）：
  1. **准备期**：`windows_prepare.rs:2517-2519`，`operation == CreateSecondary || target_is_windows` 时无条件探测；
  2. **恢复期**：`pe_operation.rs:461-466`（`check_image()`，`intent != DataOverlay` 时探测），且随后 `share_mode(1)` 持句柄 + 全量哈希（:468-474），**「预检后替换镜像」被这条兜住**——所以换镜像作弊路线不通。
- **不受影响**：`/Apply-Image /ImageFile:`（`pe_operation.rs:666`）参数正确；P2 覆盖式硬拒（`pe_safety::overlay_restore_on_windows_volume_error`）、`verify()` 目标卷三文件校验（`pe_operation.rs:676-689`）都是独立判据。

### 2.3 缺陷溯源（git `-L` 逐行历史）

- `50ab69f`「2.4.2 待办五项全做：PE 擦除前预检…」**引入该函数时就是 `/ImageFile`**——**出生即错，不是回归**；
- `d3cc6a6`（v2.6.9 日志轮）只把内联 `Command` 换成 `run_output_logged`，参数原样保留。
- 因此：**从 v2.4.2 至今所有「权威探测」结论都不成立**，实际拦截全靠镜像名启发式。

### 2.4 连带纠正与影响分析

1. **10-13「有 VHD 附加时 `/Mount-Wim` 一律报 87」的归因不成立（至少证据被污染）**：参数错误本身就恒报 87，当时观察到的 87 无法证明与 VHD 有关。→ 已入经验库墓碑（`经验/07`）。
2. **纯 PE 镜像的保护一直在「碰运气」**：只要 WIM 显示名不含 `windows pe`/`winpe`（例如把 `boot.wim` 改名成 `backup.wim` 导出），准备期与恢复期都会放行 → 格式化目标卷 → 灌入 PE → `verify()` 查不到 `SYSTEM`/`winload.efi` → 任务失败、**目标卷已被擦除**。这正是 2.4.2 当初要防的「目标白毁」，实际上没防住。
3. **对 #39 的影响（关键顺序依赖）**：P5 降级路径（目标卷缺组件 → `Preflight::Skip`）只有在**门禁降级**时才能被真实触发。**修复门禁后，删件镜像会在准备期被正确硬拒，P5 端到端反而不可达**。所以顺序必须是：**先跑 #39 实机（用当前 2.6.21 降级门禁）→ 再修门禁（v2.6.22）并用同一份删件镜像验证「现在会硬拒」**——一份镜像同时给出两个方向的证据。
4. **修复本身很小**：`/ImageFile:` → `/WimFile:`，更新 1791–1806 的注释（VHD 归因改为「真实挂载失败才降级」），并把参数抽成小函数 + 单测锁死（防再漂）。**代价**：准备期会真的挂载一次（实测 32GB WIM 只读挂载约 60–90 秒 + 卸载约 60 秒），属可接受成本，但必须写进验收预期。

## 4. #39 P5 缺组件端到端（进行中）

### 4.1 原方案的两处坑（本轮代码核对后修正）

| 坑 | 依据 | 修正 |
|---|---|---|
| **删 `SYSTEM` 会让任务失败且系统不可启动** | `pe_operation.rs:676-689` `verify()` 在 apply 之后、注册之前校验目标卷 `SYSTEM`/`winload.efi`/`ntoskrnl.exe`，缺任一 → `系统文件验证失败`，根本到不了注册前置 | **只删 `reagentc.exe`**，`SYSTEM` 保留 |
| **`recovery_fault` 的 hold/error 注入在产物里不可用** | `configure()` 全仓只有 `boot_entry_fault_tests.rs` 两处调用；`--test-fault` 仅覆盖准备期（identity-env-mismatch / bcdboot-failure / power-loss-*） | 放弃「挂起后从 RE 控制台删文件」路线，改走删件镜像 |

### 4.2 为什么现在能走通（与 §2 的耦合）

- 准备期门禁因参数缺陷降级为「镜像名启发式」→ 副本名 `br-2619-noRE.wim` 不含 `pe` 字样 → `HeuristicPass`；
- 恢复期 `check_image()` 同一函数 → 同样放行；
- apply 后 `verify()` 只查 `SYSTEM`/`winload.efi`/`ntoskrnl.exe` → 全在（我们没删 `SYSTEM`）；
- `boot()` → `winre_registration::repair()`（`pe_operation.rs:828`）→ preflight 探目标卷 `reagentc.exe` → **不存在 → `Preflight::Skip`** → `checkpoint("registration-skipped")` → `RegistrationOutcome::Skipped(reason)` → 任务照常 `success`，日志两处留痕（preflight 原因 + 结尾复述）。
- **前提是门禁保持降级**——所以必须先跑 #39，再修门禁（见 §2.4）。
