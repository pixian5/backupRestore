## 2. 分维度分析

### 2.1 功能完整性（对照需求原文）

V1 范围一条没越界（增量/差异、网络备份、Legacy/MBR、动态磁盘、RAID、自研引擎——明确不做的都没做），
这条纪律保持得好。但需求原文中 **BackupRestore.exe 的职责描述**里有三项在 GUI 侧还只有 CLI 能力或没有：

1. **GUI 无「查看日志」入口**：完成对话框显示日志路径，但用户要自己进 `H:\brwork\logs`。
   报障第一步（「日志给我」）就卡住——这是错误码体系落地后最刺眼的一个体验断点。
2. **GUI 无「探测（probe）」入口**：需求 §7/§8 强调先自检再用；CLI 有 `--operation probe`，
   GUI 五个入口（备份/还原C/还原数据/第二系统/安装 PE）没有它，首次使用者缺少安全预检。
3. **「管理备份文件」缺口**：需求 §3 明确 BackupRestore.exe 负责「管理备份文件」。目前镜像管理只有
   `wim-info` 命令 + 手工删文件 + `--keep-indexes` 自动清理；镜像一多，用户没有可视化清单（有哪些镜像、几个索引、多大、能不能删）。

另有英文手册缺失（GUI 已双语，手册没跟上）。

### 2.2 代码健康度

- **`native_gui.rs` 10.7k 行单文件**是最大结构风险：合并冲突面、编译时间、新人导航都受影响。
  但它是 Win32 消息循环 + 五入口 + 多对话框的天然聚合体，拆分应按「对话框 / 入口 / 布局」切，
  收益是导航性而非正确性——**优先级低于体验缺口**，且拆错会引入回归，必须先出方案再动。
- **unwrap/expect ~537**：从未分类盘点。panic hook 已装（不会无声崩溃），但「有 hook」不等于
  「产品路径 panic 面可列举」。建议按「测试 / 锁 / IO 兜底 / 真风险」四类过一遍，把真风险压到个位数。
- clippy 真实告警 3 类，半天可清（mac 假阳性按既有结论忽略，别删 windows 专属代码）。

### 2.3 工程质量

已有：单测 + 交叉编译 + 冒烟门禁 + 错误码判据 + GUI 审计日志。
**缺 CI**：GitHub Actions（x64 Windows runner）可跑 `cargo check --target aarch64-pc-windows-msvc`
+ `backuprestore-core` 单测——正好把「`cargo test` 通过 ≠ 构建通过」（本项目反复踩：E0433/E0382 只在
非 test 构建或交叉编译暴露）变成每次 push 自动兜底。arm64 跑不了测试，但 check 级覆盖价值已足够高。

### 2.4 文档与知识管理

320 篇 + 经验库运转正常；部分历史文档结论被后续实机推翻，靠「墓碑与争议清单」治理——
随做随清即可，不建议单独开「文档大清仓」（动静大、收益低）。USER-GUIDE 英文版随 GUI 双语补齐。

### 2.5 现场与环境

大回归空间门槛（≥220 Gi）治理后基本够；跑前仍按纪律 `df -h /System/Volumes/Data` 确认。
验收环境是单 VM 单机——它本身是「验收单点」，任何环境级事故（VM 损坏）都会阻断验收，
属可接受成本（有 BCD 三行回滚 + 镜像可重灌），但要知道这个依赖存在。

## 3. 下一步开发建议（按优先级）

### P1-a　GUI「查看日志」入口（体验补缺）

- **做法**：顶栏加「查看日志…」按钮 → 打开日志根目录（`explorer H:\brwork\logs`）+ 弹窗列最近 N 个
  在线任务日志（点击用记事本打开）。复用 `log_root::logs_dir()`，不新造路径逻辑。
- **工作量**：0.5–1 天。**风险**：低（只读操作 + 一个对话框）。**验收**：GUI 点击能打开目录；
  任务完成后能从入口直达本轮日志；单测不涉及（GUI 层），冒烟 6/6 不回归。

### P1-b　GUI「探测」入口（体验补缺）

- **做法**：第五/第六个入口加「探测（仅检查）」→ 走已有 `prepare --operation probe` 同一条链
  （校验系统/WinRE/卷身份 + 生成任务文件 + 载荷校验，零破坏）。GUI 侧主要是入口 + 说明文案 +
  禁用无关字段（无镜像路径需求时置灰）。
- **工作量**：1 天。**风险**：低（复用 CLI 已验证路径，不碰破坏性分支）。
  **验收**：T: 空卷上点「探测」→ 创建任务 → success，零副作用（哨兵仍在、序列号不变）。

### P1-c　备份文件管理 UI（需求职责内）

- **做法**：新对话框列 `H:\BRImages\*.wim`（读 sidecar：索引数/各索引名/大小/捕获时间/源卷），
  支持「删除旧索引」（复用 `--keep-indexes` 同源逻辑，先备份 sidecar 再删）+「打开所在文件夹」。
  破坏性操作走程序原生确认框 + 二次确认。
- **工作量**：2–3 天。**风险**：中（删除是破坏性操作，判据要硬：删前 sidecar 备份、删后 wim-info 复核）。
  **验收**：T: 造 3 索引镜像 → 保留 1 → wim-info 复核索引数与 sidecar 一致；误删路径有确认框不误触。

### P2-a　CI：GitHub Actions

- **做法**：`.github/workflows/ci.yml`：push/PR 触发，x64 Windows runner 上
  `cargo check --workspace --target aarch64-pc-windows-msvc` + `cargo test -p backuprestore-core`。
  目标目录用 runner 本地盘（不碰共享目录）。
- **工作量**：0.5 天。**风险**：低（CI 失败不阻塞本地，只报警）。
  **验收**：故意提交一个 `cfg(windows)` 类型错误 → CI 红；修复 → 绿。

### P2-b　clippy 真实告警清零 + unwrap 四类盘点

- **做法**：清 3 类真实告警；`unwrap/expect` 按「测试 / 锁 / IO 兜底 / 真风险」分类，
  真风险逐条改错误传播或加注释论证。**工作量**：1 天。**风险**：低（行为不变，只改错误处理形态）。
  **验收**：clippy 真实告警 0；盘点表进文档，产品路径真风险可列举。

### P2-c　USER-GUIDE 英文版

- **做法**：照中文版译（GUI 已双语，术语一致）。**工作量**：1 天。**风险**：零（纯文档）。
  **验收**：与中文版结构一一对应；示例命令可原样执行。

### P3-a　`native_gui.rs` 拆分评估（先方案不动码）

- **做法**：按「对话框（settings/cancel/system_choice/invalid_path）/ 五入口布局 / 控件工具」
  出拆分方案 + 依赖方向图 + 回归风险评估，评审通过再排期。**工作量**：评估 1 天，实施另计。
  **风险**：中（Win32 消息路由对模块边界敏感）。**验收**：方案过评审 + 冒烟剧本覆盖五个入口。

### P3-b　wimlib capture POC（备份侧，不预设结论）

- **动机**：E3 只证明了 apply 侧打平；capture 目前 DISM 独占。若 wimlib capture 显著更快，
  备份体验收益直接。**做法**：T: 5G 卷同源对照（DISM capture vs wimlib capture）：
  耗时/退出码/sidecar 簿记/还原可用性四判据。**工作量**：1 天 POC。
  **验收**：对照表 + 「是否产品化」一句话结论。**不预设结论**——打平或更差就维持 DISM。

### 明确不做 / 等拍板（记录在案）

- **304 处用法错误发码**：维持 AI 建议「不发」（英文原文即标识；发 300 码淹没运行期码）——等用户最终确认。
- **需求范围外功能**（计划备份、镜像加密、任务证据管理 UI、网络备份）：需求原文明确不做或未提及，
  **等用户提需求再立项**，不自动进入排期。
- **B5 僵尸任务自动收口**：用户 10-23 已拍板「不自动终态」，不动。
