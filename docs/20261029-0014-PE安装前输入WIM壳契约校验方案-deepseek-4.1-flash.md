## 一、为什么现在提这件事

今天（10-29 凌晨）做完 PE 硬盘版重测，得到一条很硬的实测：

- **产品安装链路对输入 WIM 没有任何体检**：`install_pe_harddisk`（`native_gui.rs:4460`）只做
  「校验路径存在 → 格式化目标分区 → `dism /Apply-Image` → 建 9 条 BCD」，**一个文件的字节都不读**。
- 输入件是 2026-09-13 的旧镜像，其 `Windows\System32\winpeshl.ini` 是 89 B 的旧式壳：

  ```
  [LaunchApps]
  %SYSTEMROOT%\System32\RecoveryLauncher.cmd
  %SYSTEMROOT%\System32\recenv.exe
  ```

  第一行能启动（旧 POC 启动器），但它需要 `RecoveryTask.env`，没有就 `exit /b 87`；
  第二行的 `recenv.exe` **在镜像里根本不存在** → `0x80070002`。
- 结果：两个壳都退出 → WinPE 无前台进程 → **自重启**，`winpeshl.log` 记录了一个
  **间隔约 19 秒、连跳 9 次**的死循环。用户看到的就是「选了 PE，闪一下又回 Windows」。
- 装完之后产品侧**一切正常**：BCD 九条全 0，界面报「安装成功」。**失败只在重启后才暴露**，
  而且暴露出来的现象（闪回）与「产品 BCD 写错」完全同形，是被误判成产品缺陷的根源（#141/2215）。

一句话：**产品是纯铺设器，而「铺什么」这件事完全没有门禁。**

---

## 二、目标与非目标

**目标**：安装前就判断「这份 WIM 铺下去能不能起一个能用的 PE 桌面」，不能就**拒绝安装并说明怎么修**。

**非目标**（明确不做，避免范围膨胀）：

| 不做 | 理由 |
|---|---|
| 校验整镜像 SHA-256 / 与官方基线比对 | 用户 2026-10-28 已裁定「镜像哈希**不强制校验**」（仅比大小），翻案需用户重新拍板 |
| 校验 WIM 里其他 15000 个文件 | 与本类故障无关；今天两次事故都只出在壳那一个文件上 |
| 校验 PE 里的 `Recovery.exe` 版本是否与主程序一致 | 属「交付一致性」，另有部署 SHA 比对链负责（`build-win.sh --deploy`），不塞进安装路径 |
| 自动修复（把壳改对再装） | 静默改写用户输入件风险更高；宁可拒绝 |

## 三、判据（这一节是方案的核心，其余都是包装）

判据必须是**结构化、可复现、不依赖中文文案**的三条，全过才允许铺盘：

| # | 判据 | 通过条件 | 反例（今天真实存在过） |
|---|---|---|---|
| ① | 壳文件存在 | WIM 内 `Windows/System32/winpeshl.ini` 可提取 | 无壳的裸 ADK winpe.wim |
| ② | 壳内容**等于**正确件 | 规范化（`\r\n`→`\n`、`trim`）后**逐字等于** `[LaunchApps]\n%SYSTEMROOT%\System32\Recovery.exe,--pe-desktop` | 89 B 旧件（第一行合法、第二行指向不存在的 exe） |
| ③ | 壳指向的目标真实存在 | WIM 内 `Windows/System32/Recovery.exe` 存在 | 只有壳没有 exe 的半成品镜像 |

**★ 判据 ② 必须用「等于」而不是「包含」**——理由要说准，不要编（上一稿这里写错了，订正）：

- 89 B 旧件全文是 `[LaunchApps]` + `RecoveryLauncher.cmd` + `recenv.exe`，**不含** `Recovery.exe` 子串。
  所以「包含 `Recovery.exe`」这种判据**碰巧也能拒掉它** —— 但那是运气，不是判据表达了正确的语义。
- 真正的风险在别的口径上：「壳里至少有一个入口能启动」（旧件**满足**：`RecoveryLauncher.cmd` 的日志
  是 `Succeeded launching`）、「壳含 `Recovery`」（旧件**满足**）、「壳含 `[LaunchApps]`」（谁都满足）——
  这一类宽松判据**都会放过它**，而它装完就是 19 s 一轮自重启。
- 更普遍地：「包含」无法表达我们真正要的不变量 —— **winpeshl 拉起的前台进程必须唯一且是我们自己**。
  一个并列了 `Recovery.exe,--pe-desktop` 和另一个会先退出的入口的壳，用包含式判据照样过，
  但仍然会（在前者退出后）让 PE 失去前台进程。
- 只有「整份壳 == 产品期望的那一份」能表达这个不变量。这与 WinRE 侧
  `winre_payload.rs:53 validate_winre_shell` 的现有语义**完全一致**（也是 `!=` 直接拒），两侧口径统一。

## 四、校验点与实现手段

### 4.1 放在哪

**铺盘之前**（`dism /Apply-Image` 之前），位置在 `install_pe_harddisk` 的
「目标卷安全校验通过之后、破坏性确认之前」。

理由：
- 铺盘前拒绝 = 目标分区**毫发无损**（不格式化、不写 BCD），用户改个镜像路径就能重试；
- 若放在铺盘后，回滚要「删 BCD 项 + 清分区」，代价和风险都高一个量级。

### 4.2 怎么读镜像里的那个文件（不挂载、不解全量）

按代价从低到高三个候选：

| 方案 | 代价 | 备注 |
|---|---|---|
| **A. `wimlib-imagex extract` 单文件** | 读 WIM 目录 + 解一个几 KB 文件，亚秒级 | ★ 推荐。`wimlib-imagex.exe` **已随部署位分发**（`H:\brwork\wimlib-imagex.exe`，任务 #110），PE 内也在用，不引入新依赖；不需要管理员以外的额外权限，不占 2×WIM 空间 |
| B. `dism /Mount-Image /ReadOnly` | 分钟级、要临时目录、要 ~400 MB 可用空间 | 重；只在 A 不可用时兜底 |
| C. 先 `Apply-Image` 再查 `T:\Windows\System32\winpeshl.ini` | 已经铺完了，失败要回滚分区 + BCD | 不符合「铺盘前拒绝」 |

方案 A 的命令形态（与今天验证用的一致）：

```
wimlib-imagex.exe extract <wim> 1 /Windows/System32/winpeshl.ini --dest-dir=<临时目录>
```

★ 实测坑：该命令对**单文件**会把结果拍平到 `<临时目录>\winpeshl.ini`（不保留子目录结构），
所以取回路径是 `temp\winpeshl.ini`，不是 `temp\Windows\System32\winpeshl.ini`。
判据里要按拍平路径取，否则会「文件明明在、却报不存在」。
★ 第二个坑：`wimlib-imagex extract` 的成功判据不能用退出码单独判断（本项目 `prlctl` 通道另有静默失败史），
判据应落在**「临时文件存在且字节数 > 0」**这一副作用上。

### 4.3 错误码与文案

- 新增稳定错误码（`crates/backuprestore-core` 里的 `ErrCode`）：**`PeImageShellContract`**
  - 注意：`error_code` 整数是遗留死字段，稳定码走 `error_code_text`（本项目既定事实）。
- 文案必须给「下一步」，不能只说「校验失败」：

  > PE 镜像的启动壳不符合要求，已拒绝安装（目标分区未做任何改动）。
  > 期望的壳内容：`[LaunchApps]` + `%SYSTEMROOT%\System32\Recovery.exe,--pe-desktop`
  > 实测：<实际内容或「文件不存在」>
  > 请用 `poc/build-backuprestore-pe.ps1` 重新生成 PE 镜像后再安装。

- 同时落 `logs\pe-shell-contract-<时间戳>.txt`（原始内容 + 规范化后内容 + WIM 路径 + SHA256 前 16 位），
  便于事后判「是输入件旧」还是「我们的期望值改了」。

## 五、对现有测试与失败路径的影响

| 现有行为 | 变化 |
|---|---|
| 输入件是**正确件**（当前 `poc/build-backuprestore-pe.ps1` 的产物） | 无变化，正常安装 |
| 输入件是 09-13 旧件 | **从「装成功、重启闪回」变成「当场拒绝、分区不动」** |
| 输入件是无壳裸 ADK `winpe.wim` | 当场拒绝（此前会装完然后 winpeshl 走默认 `cmd.exe /k startnet.cmd`，停在命令行） |
| 输入件是 RAM 版（`install_pe_ramdisk`） | **建议同样适用**：RAM 版同样把 WIM 原样交给 bootmgr，壳坏了照样回落，只是现象不同（不占分区，但一样进不去桌面） |

**测试怎么写（若将来实现）**：
- 三个夹具：正确件 / 89 B 旧件 / 无壳裸件 → 三条用例，判据只认 `error_code_text` 与「目标分区未被格式化」；
- **89 B 旧件的真实镜像已留档**：`pe-assets/pe-boot.old-20260913-badshell.wim`（367,395,379 B，
  SHA-256 `d5f1515a…`，壳 89 B、双入口、`recenv.exe` 不存在）——不必自己造，直接用它当「真·负样本」
  （`pe-assets/` 被 `.gitignore:111` 忽略，属本机夹具，别的机器上需另行准备或自行构造）；
- **变异验收**（本项目铁律）：变异的目标是证明「判据真的在起作用，不是恒绿」。★ 这里有个**反直觉点**：
  旧件全文是 `RecoveryLauncher.cmd` + `recenv.exe`，**不含** `Recovery.exe` 子串——所以「包含 `Recovery.exe`」
  这种变异**测不出宽松判据的危险**（它照样会拒绝旧件）。真正该做的变异是两类：
  ① 把判据降级为 `contains("Recovery")`（旧件含，**必须变绿=坏判据被抓到**）；
  ② 把判据降级为 `contains("[LaunchApps]")`（谁都能过）。
  二者都必须让「89 B 旧件」用例 FAIL，而「61 B 正确件」用例仍 PASS。

## 六、成本与风险

- 代码量：约 60–100 行（提取 + 校验 + 落日志 + 错误码），集中在 `native_gui.rs` 一个函数前段。
- 版本：**属行为变更**（新增一条拒绝路径）→ 需 `+0.0.1`，三处 `VERSION` + 两个 `Cargo.toml` 同步。
- 风险：期望字符串与 `poc/build-backuprestore-pe.ps1`（`$expectedPeShell`）成为**两处**权威。
  必须在一处写清「改壳模板要同时改这两处」，否则将来改壳会自锁（产品拒绝自己新出的镜像）。
  建议：把期望值定义成 `poc/build-backuprestore-pe.ps1` 与 Rust 侧共同引用的**单一常量来源**
  （最省事的做法是在 `windows/winpe-winpeshl.ini` 作为唯一真源，Rust 侧读不到就退化成内置常量 + 注释指向它）。
