# 新增第二系统失败不改变默认启动项修复

> 版本：2.4.4
> 模型：Claude Opus 5
> 日期：2026-10-13 12:22
> 前置：[复核另一会话改动](./20261013-1036-复核另一会话改动-预检被放行致P卷被毁与恢复-Haiku4.5.md)

## 一、问题

新增第二系统（`create-secondary`）执行 `bcdboot` 时，Windows 默认行为可能把新建的第二系统 loader 写入 `{bootmgr}.default`。原代码只使用 `/addlast`，但 `/addlast` 只控制固件启动项顺序，**不保护 Windows Boot Manager 的 default**。

如果之后的 WinRE 注册、引导菜单应用、回读校验、断电续跑等任一步失败，原先的 `preserve_primary_boot_manager` 还没机会执行，机器可能每次开机进入未完成的第二系统。2026-10-13 的 WinRE 释放实机已经证明了这个后果：失败后 default 指向半成品 RE，只能进 WinPE 离线修 BCD。

## 二、修复

### 1. BCDBoot 源头加固

所有“新增第二系统”相关的 `bcdboot` 调用增加 `/d`：

- [main.rs](../crates/backuprestore-cli/src/main.rs)：WinRE `NewWindows` 分支；同时传入用户的 `boot_menu_name` 作为 `/description`，让中途失败时留下的条目仍可辨认。
- [online_operation.rs](../crates/backuprestore-cli/src/online_operation.rs)：在线还原 STEP 3.6 预建 loader。
- [boot_menu.rs](../crates/backuprestore-cli/src/boot_menu.rs)：方案中缺少 loader 时的兜底创建。
- [pe_operation.rs](../crates/backuprestore-cli/src/pe_operation.rs)：此前已加 `/d`，本轮复核确认继续保留。

`/d` 是 Windows BCDBoot 的“保留现有默认 Windows 启动项”选项；`/addlast` 不能替代它。

### 2. 立即回读与自愈

WinRE 主恢复链在 `bcdboot` 成功后立刻读取 `/enum {bootmgr} /v`：

- 与准备期快照的 default 相同：记录成功；
- 被改成新 loader：立即 `bcdedit /default <快照 default>` 写回，再回读确认；
- 回写仍失败：停止后续破坏性步骤并报错。

这样即使某个 Windows 版本忽略 `/d`，也不会静默进入后续注册步骤。

## 三、为什么不是只依赖失败清理

恢复失败可能发生在：

- BCDBoot 后、注册前；
- 注册过程中；
- 引导菜单最终应用过程中；
- 断电或进程崩溃之后。

事后清理无法覆盖断电/崩溃窗口，必须采用“`/d` 源头保护 + 立即回读自愈 + 终态快照回读”三层结构。

## 四、兼容边界

- 单系统还原（`restore-existing`）不加 `/d`：它的目标就是重建唯一系统，default 应指向新系统。
- 第二系统只加菜单项，不主动改 default；用户仍可在引导菜单里选择它。
- 纯 PE/WinRE 镜像仍在擦除前被拒绝，不能靠 `/d` 把不完整镜像变成合法第二系统。
- 镜像严格哈希 (`verifyHash`) 未在本轮改动，仍是后续独立待办。
