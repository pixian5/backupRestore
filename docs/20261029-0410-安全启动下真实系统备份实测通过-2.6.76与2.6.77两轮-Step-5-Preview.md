## 三、触发方式（可复现）

钩子配置 `C:\br-test.json`（`BackupRestore.exe --test-hook` 启动时读取）：

```json
{
  "tab": "backup",
  "channel": "offline",
  "source_volume": "C",
  "image": "H:\\BRImages\\c-secboot-2677.wim",
  "auto_install": true
}
```

脚本 `tools/win-clicker/br-backup-secboot-2677.ps1`（经 `br-s1.sh` 提权在会话 1 执行）：
杀旧 GUI → 写钩子 JSON → 启动 GUI → 弹窗「需要进入恢复环境处理」出现 →
`br-choose-pe-env.ps1` 按窗口类名 `BackupRestoreSystemDriveChoice` 点第一个含 `PE` 的按钮 →
产品排队 PE 请求（写在 **ESP** 的 `BackupRestore\pe-requests\<id>.json`）并设一次性启动序列 → 重启 →
PE 启动时自动领取并执行 → 完成后自动重启回 Windows。

注意：**请求队列在 ESP 上，不在镜像旁**。镜像旁的 `.br-pe-<id>` 目录是 PE 侧执行时才建的
（日志与运行时状态都在里面）；`request.json` 会被 PE 侧重写一遍，所以它的修改时间会刷新。

## 四、两个环境观察（非产品缺陷，记录待查）

1. **PE 会话期间客体时钟比真实时间快约 16 小时**：两轮 PE 实测都是如此。PE 里日志时间戳
   （程序按 UTC 记）与窗口时钟自洽，但比宿主快 16 小时；回 Windows 后时钟自动恢复正常
   （Windows 侧工具会重新同步）。影响：PE 会话内写的文件，其 NTFS 修改时间带着偏移值，
   在 Windows 里看会「超前」16 小时——本文件中的耗时/哈希不受影响，但引用客体时间戳时要留意。
2. **`bcdedit` 输出不要直读**：经 `prlctl exec` 直读会乱码甚至误导（曾看到 `default {default}`）；
   一律先 `> 文件` 再经 Base64 通道取回（`certutil -encode` + 宿主 `base64 -d`）。
