# TaskStore 搬离 C: 与证据目录保留边界（用户拍板 + 实机执行）

**2026-10-24 05:50 · v2.6.32 · 模型 Hy4**
交接来源：`docs/20261024-0350-接手AI交接说明-v2.6.32-Step-5-Preview.md` §5.1 两项待拍板。

## 1. 用户拍板（原文）

> 全留，只加一条例外——载荷副本（Winre.wim 的 stage/original 这类几百 MB、可从系统重新生成的过程产物）不算证据，应可清。
> TaskStore 搬离 C

即：①证据目录**全留**，例外是「载荷副本可清」；②**TaskStore 搬离 C:**。

## 2. 机制：任务目录在哪，由「从哪启动」决定

`TaskStore` 的根 = **可执行文件所在目录**，任务目录 = `<根>\tasks\<task_id>`：

- GUI：`TaskStore::new(&state.executable_dir)`（`native_gui.rs:6167` / `:6243`）
- CLI：`env::current_exe().parent()`（`main.rs:685` / `:745`）
- 核心：`self.root.join("tasks").join(canonical)`（`backuprestore-core/src/lib.rs:1283`）

所以「搬离 C:」本质不是改代码，而是**让权威运行目录不在 C:**。

**WinRE 交接不受影响**：`WORKSPACE_ROOT_REL` 存的是**卷内相对路径**
（`workspace_relative(executable_dir)\tasks\<task_id>`，`windows_prepare.rs:2757`），
恢复环境里按卷 GUID 定位卷再拼相对路径——换目录不破坏交接，盘符重排也能扛。
这也是**不改代码、只固化启动位置**路线成立的原因（改动面小、风险低）。

## 3. 调查发现（拍板前实测）

| 项 | 实测 |
|---|---|
| 两处部署 | `build-win.sh --deploy` 本来就同时部署 C: 包目录与 `H:\brwork` |
| 启动入口 | `tools/win-clicker/` 里**没有任何脚本**从 C: 包目录起 GUI；`restart-gui-h.ps1` 与各 `br-*-launch.ps1` 均指向 `H:\brwork\BackupRestore.exe`（`BRGUIC` 只是沿用旧任务名，不代表 C:） |
| 任务分布 | `H:\brwork\tasks` 21 个 / 41.8 MB；`C:\...\package\tasks` 4 个 / **1387.9 MB** |
| 大包袱 | `1aa188b1-…` 单任务 1.35 GB = `stage\Winre.wim` + `original\Winre.wim`（WinRE 载荷暂存的两份副本） |
| 备份排除表 | `build_capture_exclusions`（core/lib.rs:1631）**不含程序目录** → 备份 C: 会把包目录连任务一起打进镜像（旧任务「复活」的机理） |

结论：C: 上那 4 个是**老残留**（早期从包目录启动留下的），新任务早已落在 H:。
「搬离 C:」= 把这 4 个迁走 + 口径固化，不是大改。

## 6. 结论与遗留

**已结清**：TaskStore 搬离 C:（任务存储 100% 在 `H:\brwork\tasks`）；证据保留边界拍板
（全留 + 载荷副本可清）；顺带回收 C: 1.35 GB。

**未做（不需要做 / 留待评估）**：

1. **程序本体仍在 C: 包目录**——A 入口还原 C: 仍会把包目录二进制回滚成旧版，
   还原后仍需重署二进制。但**任务状态不再回滚**（这是本次修掉的部分）。
2. **备份排除表未改**（`build_capture_exclusions` 加程序目录）：任务已不在 C:，
   镜像不再带走任务状态；加排除只剩「不让旧 exe 进镜像」的收益，且会改变
   「还原后包目录还在」的现状，需单独评估 + 一次 A 入口回归。
3. 真正的权威安装迁到 H:（删掉 C: 包目录部署）——恢复环境载荷注入/预安装环境部署依赖它，风险较高。
