# 阶段 3 不重启诊断结论（v2.5.4）

> 模型：GLM-5｜用户选择方案 2：--no-reboot 重建任务做不重启诊断。**结论：代码链路无恙，快照嫌疑实锤级，已顺手清理 8 个 BCD 残留 loader。**

## 诊断过程与发现

1. CLI `prepare … --no-reboot` 重建任务 `e4b496b8`（create-secondary/F:/c-full 索引 1）→ 成功：
   - task.json 全部正确：`target=F:`、`isActiveSystem=false`、`formatTarget=true`、`bootPlan.mode=add-secondary`、菜单名落盘
   - BCD 新建 loader `{47b2f5d4…}` 正确指向 `H:\BackupRestoreRE\e4b496b8\Winre.wim`（设备路径形式）
   - **结论：prepare/载荷/loader 写入链路无任何问题**
2. **发现 8 个「BackupRestore task RE」历史残留 loader**（其中 5 个指向已空置的 F:、3 个旧 H: 任务）——历史任务终态清理只清了 displayorder 引用，loader 对象残留在 BCD store 里
3. 清理：`abandon-task` 正规放弃诊断任务（载荷删、loader 删、bootsequence 无）；剩余 7 个孤儿 loader 逐个 `bcdedit /delete {guid} /cleanup` 全部成功；最终 BCD 仅剩系统条目（default=`{12e3701c-…}` 基线）

## 根因结论（结合 1535 故障记录）

代码无恙 + 故障时序（拍快照 → 写 BCD/bootsequence → 重启 → 固件进了系统 WinRE 而非任务 RE）+ 对照实验（0200/0212 无快照时同链路全部成功）→ **头号嫌疑实锤级：Parallels 快照层与 UEFI/BCD 写入的视图不一致**——重启时固件读到快照基线的 ESP/BCD（不含新 loader），bootsequence 解析失败回落系统 WinRE 菜单。

次要发现：BCD 残留 loader 虽非直接原因，但会放大固件解析的不确定性，现已清零。
