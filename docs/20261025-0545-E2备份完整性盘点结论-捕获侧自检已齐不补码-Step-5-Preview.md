## 1. 盘点方法

读两条捕获链的收尾路径（不是猜）：

- **在线链**：`online_operation::capture`（`online_operation.rs`）。
- **RE/PE 链**：`pe_operation::Engine::backup`（`pe_operation.rs:435`）——**第 455 行直接委托
  `crate::online_operation::capture`**。所谓「RE 离线捕获链」不存在独立实现，
  它只是在恢复环境里挂载源卷后复用同一条 capture。

即：**全项目只有一条捕获实现**，在线与恢复环境共用。

## 2. capture 的完整收尾清单（逐条有行号）

| 自检 | 位置 | 挡住什么 |
|---|---|---|
| DISM 捕获带 `/CheckIntegrity` | `online_operation.rs:1354`（Capture/Append 都有） | 捕获过程中的结构损坏 |
| 捕获后**索引回读**（`indexes(&candidate)` + `verify_appended_index`） | :1365-1366 | 新索引没落上的静默失败 |
| 整档 sha256（写进 sidecar） | :1460 `write_sidecars(..., &hash, ...)` | 备份后被改/坏（还原预检时比对） |
| 发布前**重验原镜像**哈希（防并发修改） | :1439-1444 | 候选构建期间原镜像被换 |
| legacy 簿记写后**回读比对** | :1467-1469 | 副档写飞 |
| 发布后**尺寸核对** | :1474-1476 | 发布落空/截断 |
| 失败**回滚**（previous.wim + 原副档） | :1454-1457、:1312-1327、:1479 起 | 发布失败不留半成品 |

还原侧另有：sidecar sha256 预检（`pe_operation.rs:544`、`online_operation.rs` 还原路径）、
apply 时 DISM 参数带 `/CheckIntegrity /Verify`。

## 3. 唯一可争议点及「不做」的理由

**争议点**：发布（rename）后的成品路径没有再回读一次——capture 后的索引回读读的是 candidate，
发布是 `fs::rename(candidate, destination)`。

**不做的理由**：
1. candidate 与 destination 同目录同卷（`H:\BRImages\.br-online-*` 紧挨目标 wim），
   rename 是同卷原子操作，**内容逐字节不变**；对已完整读过（索引+整档哈希）的文件再读一遍是纯仪式。
2. 多一次只读 DISM 调用就多一个失败模式——「什么都成功了、最后礼仪性一步抽风」会把成功任务
   拖进回滚路径，属于负收益。
3. 真正可能漏的是「备份之后、还原之前」的介质级损坏，那由还原侧预检（sidecar 哈希 + apply 前
   `/CheckIntegrity`）负责，备份时再怎么自检也管不了未来。
