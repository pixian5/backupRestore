## 1. 背景与目标

程序已有状态机、`.partial`、WinRE/BCD 快照、阶段续跑与故障注入开关（`main.rs:2276` `interrupt_after_stage_if_requested`；`windows_prepare.rs:341-356` 的 `--test-fault`），并且历史上跑通过若干故障用例。但这些证据**分散在旧版本、旧快照、旧任务 ID**，且：

- `main.rs:54` 的 usage 只列了 3 个 fault（实际支持 6 个），文档与实现不一致；
- 逐阶段断电组合（Preflight、Capturing、格式化中、Apply 中、BCDBoot 前后）未全跑；
- BitLocker 拒绝、身份篡改拒绝的实机矩阵未跑全；
- 每个用例缺少统一的证据采集与判定脚本。

**目标**：把已有状态机与回滚代码**变成可复现的实机证据**——为每个用例定义前置、步骤、判定、证据与快照基线，补齐缺失的注入点与脚本，并在可回滚快照中逐项执行，记录任务 ID、阶段、恢复日志与最终状态。

## 3. 详细改动点

### 3.1 新增故障注入点（代码）

**拟新增** fault 名称（扩展 `windows_prepare.rs:345-350` 白名单与 `main.rs:54` usage）：

| 拟新增 fault | 注入位置 | 期望安全性质 |
|---|---|---|
| `power-loss-preflight` | `recover_windows` 进入 `Preflight` 后、**首次格式化/Capture 前** | 不擦除任何目标；重入可继续 |
| `power-loss-capturing` | Capture 已开始、`.partial` 写入中 | 恢复时删除本任务 `.partial` 并重新捕获（现有 `capturing` 续跑逻辑） |
| `power-loss-formatting` | `format_target_partition` 已发出 diskpart、`target-erased` 未持久化前 | 目标可能已格式化但状态未推进；重入按身份复核后重做 |
| `bcdboot-failure-before-boot-repaired` | `BootRepaired` 持久化**之前**、BCDBoot 调用前 | 与 `bcdboot-failure` 的“之后”形成前后对照；回滚判定需覆盖 `stage_before_failure` |
| `winre-register-failure` | Apply 后离线 WinRE 注册失败 | 不标 `success`、不清理恢复入口；可重试收尾 |

**拟新增**实现要点：
- 复用现有 `interrupt_after_stage_if_requested`（`main.rs:2276`）与 `TEST_FAULT` env（`windows_prepare.rs:1073-1075`）机制；
- 每个 fault 使用**一次性 marker**（现有 `log.with_file_name(format!(".fault-{fault}.triggered"))` `main.rs:2291`）防止循环注入；
- `power-loss-formatting` 需在 `diskpart` 调用前后都有明确的“意图/完成”记录，便于对账（与阶段 2 的 `boot-transaction.json` 对齐）。

**红线**：新增 fault 只允许 `--test-fault` 在开发 CLI 使用，普通 GUI 不暴露（与现有 `--test-efi-drive` 一致）。

### 3.2 修正 usage 与文档不一致

- `main.rs:54` 的 usage 补齐 6 个现有 fault + 拟新增 fault，或改为从白名单常量生成，避免再次漂移。
- `docs/testing-plan.md:105-116` 的 F 层表格与 `docs/verification-matrix.md` 同步新增用例 ID。

### 3.3 拟新增矩阵驱动与证据采集脚本

**拟新增** `scripts/fault-matrix.py`（或 `tools/fault-matrix.ps1`）：

职责：
1. 按用例清单逐个触发（`prepare ... --test-fault <name> --allow-destructive` 等）；
2. 采集证据：`task.json`/`status.json`/`manifest.json`、`prepare.log`/`recovery.log`/`Recovery-early.log`、fault marker 数量、前后 WinRE/BCD SHA-256、`reagentc /info`、`dism /Get-MountedWimInfo`；
3. 输出结构化结果（JSON/Markdown），含任务 ID、阶段、快照 ID、通过/失败、失败停留位置；
4. **只读采集**，不替用户恢复快照（快照恢复由人工/明确步骤执行）。

**拟新增** `scripts/verify-fault-evidence.py`：
- 校验“失败用例必须给出明确停留位置与人工恢复路径”；
- 校验 fault marker 恰好 1 个；
- 校验 WinRE 恢复 Enabled、无挂载镜像。

### 3.4 BitLocker 拒绝用例

现有实现：`assert_bitlocker_off`（`windows_prepare.rs:1278`）对源/镜像/目标只读检查；`ensure_bitlocker_accessible`（`core/lib.rs:1117`）在 core 层拒绝 `Protected/Unknown`。
**改动**：无需改代码（除非发现缺口）；补实机用例（见 7.2），验证：
- 开启 BitLocker 保护的源/镜像/目标任务在**任何写入前**拒绝；
- 拒绝后 BitLocker 状态不变（不自动 suspend/unlock）；
- 身份与容量拒绝不被 BitLocker 错误掩盖（现有 `windows_prepare.rs:465-472` 的顺序注释）。

### 3.5 身份篡改用例

现有实现：`verify_task_identity_env`（`main.rs:1151`）、`verify_live_volume_identity`（`:1474`）、`verify_mounted_volume`（`:1606`）。
**改动**：补实机用例，覆盖：
- 篡改 `task.json` 与 `RecoveryTask.env` 的卷序列号/分区 GUID/大小/偏移；
- 篡改 `RecoveryTask.env` 哈希（现有 `recovery_task_env_sha256` 二次校验，`core/lib.rs:254-255`）；
- 更换盘符后仍按 GUID 命中同卷（不得误拒）；
- 目标分区被替换/几何变化后拒绝。

## 6. 安全边界与回滚策略

1. **一用例一快照**：每个破坏性用例前建独立快照（如 `before-v<ver>-<scenario>`），结束恢复快照再开始下一项（`testing-plan.md:117-119`）。
2. **不复用旧快照**覆盖新操作；进入 PE 后手动动作另建快照（`AGENTS.md`）。
3. **失败即停**：快照创建/核验失败不得继续。
4. **不删除**用户文件、系统恢复原件、开发工具链或现有快照（`AGENTS.md`）。
5. **不把 failed 当修复**：故障实验成功标准是“预期安全状态与恢复能力”，不是“写了 failed”。
6. **`C:` 边界**：不把 `C:` 作为备份源或还原目标；破坏性用例在隔离 fixture/克隆中构造。
7. **回滚**：BCDBoot 失败用 `bcd-before-raw`/`bcd-before-export`（`main.rs:1657`）；WinRE 用原件哈希；阶段续跑用状态机合法边界。

### 7.3 通过标准

- 每个用例在**可回滚快照**中完成，记录任务 ID、阶段、恢复日志与最终状态；
- 失败用例必须给出**明确停留位置与人工恢复路径**；
- 正常链路落 `success`，异常注入落 `failed` 并恢复原始 WinRE/BCD；
- **不把 AST/单元测试/进程存活**当作 WinRE、DISM、格式化、BCDBoot 或真实重启成功的替代证据。

## 8. 风险与依赖

| 风险 | 说明 | 缓解 |
|---|---|---|
| 实机轮次成本高 | 每用例需快照 + 真实重启 | 复用阶段 1/2 的稳定包；批量编排但保持一用例一快照 |
| 断电注入点破坏其他分区 | `power-loss-formatting` 风险最高 | 只在隔离 fixture；身份复核后才格式化 |
| 历史证据被误当最新版 | 旧任务 ID 与 v1.7.4 不同 | 文档明确“历史证据，v1.7.4 未复验” |
| BitLocker fixture 构造 | 开启/暂停 BitLocker 有操作成本 | 在隔离克隆中做；只读 `manage-bde -status` |
| 快照膨胀 | 每用例一个快照 | 用例完成后清理仅限确认属于本项目的旧测试快照 |
| 与阶段 2 冲突 | 阶段 2 改动启动机制会重定义部分用例 | 阶段 3 排在阶段 1 或阶段 2 稳定之后；用例 ID 保持稳定 |

**依赖**：阶段 1（或阶段 2）启动机制稳定；VM 可回滚快照能力；隔离 fixture（非 `C:`）。
