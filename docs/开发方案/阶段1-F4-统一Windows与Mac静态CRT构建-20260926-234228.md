# 阶段 1 · F4 开发方案：统一 Windows 与 Mac 的静态 CRT 构建策略

> **文档性质声明（强制）**：本文件是**待实施的代码/构建改动方案**。当前状态：**Mac 脚本已修，Windows 入口未统一**（`development-roadmap-2026-09-26.md:31`）。所有“拟新增”均为设计意图。
> 本方案不触碰启动项，因此不强制快照；但一旦产出包用于实机，仍按 `AGENTS.md` 在实机操作前建快照。
> 基线：`VERSION=1.7.4`。上游：[winre-repair-implementation-plan-2026-09-25.md](../winre-repair-implementation-plan-2026-09-25.md) §9。

- 工作项：F4（P2，可与 P0 并行，但必须早于阶段 1 的 Release 产物验收）
- 依赖：无（可独立进行）
- 预估工作量：**M（1.5~3 人日，含 PE 审计工具与 CI 改动）**

## 1. 背景与目标

WinRE/PE 与精简版 Windows（tiny11）中**不存在** `VCRUNTIME140.dll`、`api-ms-win-crt-*.dll`。动态链接的产物在这些环境里连进程都起不来（退出码 `0xC0000135 / STATUS_DLL_NOT_FOUND`）。`build-win.sh:24-28` 已记录该踩坑并加上 `-C target-feature=+crt-static`，但 **Windows 构建入口 `windows/build-windows.ps1` 没有对应配置**，且仍强制从 `System32/SysWOW64` 拷贝 `VCRUNTIME140*.dll`（`windows/build-windows.ps1:152-156`），说明 Windows 入口当前仍产出动态包。

**目标**：
1. 让所有 Windows MSVC 产品构建入口**统一**采用静态 CRT；
2. 用**编译期硬约束**防止外部 `RUSTFLAGS/CARGO_ENCODED_RUSTFLAGS` 覆盖后静默产出动态包；
3. 用**最终 EXE 导入表审计**做最后把关，只拒绝 `VCRUNTIME*/MSVCP*/ucrtbase.dll/api-ms-win-crt-*`，**不宣称“零 DLL 依赖”**（仍依赖系统 Win32 DLL）。

## 3. 详细改动点

### 3.1 拟新增 `.cargo/config.toml`（仓库根）

```toml
# 拟新增：Windows MSVC 产品构建统一静态 CRT。
# 注意 Cargo 的 rustflags 优先级：RUSTFLAGS / CARGO_ENCODED_RUSTFLAGS
# 会覆盖本文件的 target rustflags；CARGO_TARGET_<TRIPLE>_RUSTFLAGS 亦会替换。
# 因此任何设置这些变量的脚本必须显式重复 +crt-static，并由编译期 compile_error! 兜底。

[target.'cfg(all(windows, target_env = "msvc"))']
rustflags = ["-C", "target-feature=+crt-static"]
```

**说明**：使用 `cfg(...)` 形式对 ARM64/x64 MSVC 同时生效；macOS/Linux 宿主不受影响。

### 3.2 拟新增编译期硬约束

在 `crates/backuprestore-cli/src/main.rs` 顶部（或 `lib.rs` 的产品入口模块）**拟新增**：

```rust
// 拟新增：Windows MSVC 产品构建必须启用静态 CRT。
// 若外部 RUSTFLAGS 覆盖导致未启用，构建必须失败，而不是静默产出动态包。
#[cfg(all(windows, target_env = "msvc", not(target_feature = "crt-static")))]
compile_error!("BackupRestore Windows MSVC build must enable +crt-static (see .cargo/config.toml)");
```

**注意**：`target_feature = "crt-static"` 是 Rust 支持的编译期 cfg，可在 `cfg` 中判定。该断言必须同时覆盖 `BackupRestore.exe` 与 `Recovery.exe`（同一二进制，天然覆盖）。

### 3.3 `build-win.sh` 改动

| 现状 | 拟改为 |
|---|---|
| `RUSTFLAGS="-C target-feature=+crt-static -C link-arg=/LIBPATH:..."`（`:30`） | 不再用裸 `RUSTFLAGS` 抹掉仓库 config；保留 linker 变量 `CARGO_TARGET_AARCH64_PC_WINDOWS_MSVC_LINKER="$RLLD"`（`:29`），并把 SDK 路径通过显式合并方式提供 |
| 未使用仓库 config | 在脚本开头 `cd "$(dirname "$0")"`（已有 `:9`）后显式确认仓库 `.cargo/config.toml` 存在；若不存在则报错退出 |
| 无产物审计 | 构建后调用 `python3 scripts/verify-pe-runtime.py <EXE>`，非零退出即失败 |

**关于 RUSTFLAGS 覆盖的诚实说明**：Cargo 中 `RUSTFLAGS` 环境变量**替换**（而非追加）config 的 `target.*.rustflags`。因此若脚本仍需传 LIBPATH，有两种可落地写法，实施时二选一并在脚本注释中写明原因：

- **写法 A（推荐）**：把 LIBPATH 放进 `CARGO_TARGET_AARCH64_PC_WINDOWS_MSVC_RUSTFLAGS`，并在该变量中**显式包含** `-C target-feature=+crt-static`，同时依赖 `compile_error!` 保证不会漏；
- **写法 B**：不在脚本设置任何 rustflags 变量，改为在**用户级** `~/.cargo/config.toml`（不入库，含本机 SDK 路径）中配置 linker 与 LIBPATH；仓库 config 提供 crt-static。

无论哪种写法，**`compile_error!` 与 PE 审计都是最终门槛**，脚本写法只是路径问题。

### 3.4 `windows/build-windows.ps1` 改动

| 位置 | 改动 |
|---|---|
| `Invoke-Cargo`（`:78-90`） | **拟新增**：在调用 cargo 前 `Push-Location $repoRoot`，并在 `finally` 中 `Pop-Location`；确保从任何 cwd 执行都能发现仓库 `.cargo/config.toml`。同时保留 `--manifest-path`（`:84`）用于定位 workspace |
| 环境恢复 | **拟新增** `try/finally` 恢复 `$env:RUSTFLAGS`/`$env:CARGO_ENCODED_RUSTFLAGS`/cwd 等临时状态，避免污染同进程后续架构构建 |
| 构建参数（`:134`） | 保持 `build --release --locked --target $target -p backuprestore-cli`；静态 CRT 由仓库 config 提供 |
| VC runtime 拷贝（`:145-156`） | **拟删除**强制拷贝 `VCRUNTIME140.dll`/`VCRUNTIME140_1.dll` 的步骤；改为调用 `scripts/verify-pe-runtime.py` 审计 `BackupRestore.exe`，确认无动态 CRT 依赖。若审计失败则构建失败 |
| `build-manifest.json`（`:166-179`） | **拟新增**字段：`crt: "static"`、`peAudit: "passed"`，明确静态策略，避免旧动态包伪装成新静态包 |
| 包内文件清单 | 静态包不再包含 `VCRUNTIME*.dll`；`Assert-ShellContracts`（`:14-31`）保持不变 |

**红线**：`--manifest-path` **不会**自动加载仓库 `.cargo/config.toml`；必须显式切换 cwd 或使用 `--config`。

### 3.5 拟新增 `scripts/verify-pe-runtime.py`

**拟新增**离线工具，解析 PE 普通导入与延迟导入，至少拒绝：

- `VCRUNTIME*.dll`、`MSVCP*.dll`；
- `ucrtbase.dll`、`api-ms-win-crt-*`；
- 架构与打包目录/`build-manifest.json` 不一致；
- 入口 EXE 与 `Recovery.exe` 内容不一致（同源应同哈希）。

输出：`PASS/FAIL` + 命中列表 + 架构；非零退出表示失败。
**边界声明**：该检查只证明**没有这些外部 CRT 依赖**，**不写成“零 DLL 依赖”**；程序仍依赖系统 Win32 DLL，API Set 不能按磁盘上是否有同名文件判断可用性。

### 3.6 `winre_payload.rs` 可选运行库逻辑分阶段处理

- 现状 `OPTIONAL_RUNTIME_FILES`（`:18`）与复制点（`:80,120`）保留用于**旧动态包的只读诊断兼容**；
- **拟新增**：新任务 `PayloadManifest` 明确记录静态策略字段（与 F1 的 manifest 扩展一并做），审计时若发现载荷携带动态 DLL 且策略为 `static`，直接失败；
- **禁止**让包里残留动态 DLL 成为“构建没静态化”的兜底。

### 3.7 编码与超时回归（计划 `:361-371`，与 F4 同批）

保留 `read_to_end + String::from_utf8_lossy`（计划 `:56`），并给 `crates/backuprestore-cli/src/text_parsing.rs` **拟新增**字节级入口与严格 GUID 行识别：

- 中文 OEM/GBK 错误字节不触发 UTF-8 异常；日志可替换解码；
- 成功但只有无关文本或空输出 → 返回 Unknown；**不得把任意首个非空行当卷 GUID**；
- 合法 ASCII 卷 GUID 周围存在本地化文本时仍能精确提取唯一匹配；
- 多个冲突 GUID、超时、子进程异常都拒绝挂载，**不得解释为“空盘符”**；
- 非零退出的“未挂载”判定需有明确规则和分配后的身份复核；对权限/未知错误保守处理。

### 3.8 CI 改动

`.github/workflows/ci.yml` **拟新增**：

- 新增 `windows-x64` job（`windows-latest`）：安装 rustup x64 target，执行 `windows/build-windows.ps1 -Architecture x64`，随后 `python scripts/verify-pe-runtime.py`；
- ARM64：若无 ARM64 runner，明确只完成**交叉构建 + 交叉 clippy**，并在 job 名/输出中写明“未在 ARM64 宿主实际链接”，**不得勾选 x64 或 ARM64 实机运行**；
- 版本一致性检查步骤（现有）保留；可增加“构建命令不得在未含 crt-static 的 RUSTFLAGS 下产出成功包”的静态检查（grep 脚本）。

## 6. 安全边界与回滚策略

1. **不影响运行时行为**：本方案只改构建配置与产物审计，不改 `prepare`/`recover-env` 业务逻辑（`text_parsing` 增强除外，需单测保护）。
2. **回滚**：若静态化导致构建失败，可临时移除 `.cargo/config.toml` 与 `compile_error!` 回退到动态构建，但**必须同时恢复 VCRUNTIME 拷贝**，且不得把动态包标为静态包。
3. **旧包只读诊断**：历史动态包保留用于诊断，不伪装成新静态包（计划 `:358`）。
4. **审计不夸大**：`verify-pe-runtime.py` 输出不得写成“零 DLL 依赖”。
5. **实机前置**：F4 产物用于实机前，仍按 `AGENTS.md` 建快照。
