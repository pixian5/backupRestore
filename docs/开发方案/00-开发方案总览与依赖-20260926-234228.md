## 2. 依赖与执行顺序（与路线图一致）

```text
阶段0 (设计冻结)
  └─> F1 + F3 (阶段1，P0，同一批交付)   ┐

              └─> 阶段4 (独立EFI闭环，仅开发测试)        ┘

  F4 统一构建   ── 可与阶段1并行，但必须早于阶段1的 Release 构建验收
```

因此 **F1 与 F3 必须同批交付**（`development-roadmap-2026-09-26.md:36`），F2 必须绑定阶段 2。

## 4. 统一口径（所有方案共用）

1. **版本规则**：每完成一个代码交付轮次按十进制进位 `+0.0.1`，同步 `VERSION`、两个 Cargo manifest、`Cargo.lock`、Windows 包目录名、`build-manifest.json`、GUI 标题（见 `.github/workflows/ci.yml` 版本一致性检查步骤）。
2. **离线门槛命令**（来自 `project-status.md:74-79`）：
   ```bash
   cargo fmt --all -- --check
   cargo test --workspace --all-targets --offline
   cargo clippy --workspace --all-targets --offline -- -D warnings
   git diff --check
   ```
   以及 `scripts/audit-runtime-boundaries.sh`。
3. **Windows 交叉类型检查**：`cargo clippy --workspace --all-targets --offline --target aarch64-pc-windows-msvc -- -D warnings`（CI 已有，见 `.github/workflows/ci.yml`）。
4. **快照规范**：任何手动修改 BCD、默认项、一次性启动序列、WinRE 注册、PE/任务引导部署前，创建并核验新快照，记录快照 ID、目的、变更范围（`AGENTS.md`、`winre-repair-implementation-plan-2026-09-25.md:466`）。
5. **证据目录**：原始证据留在已忽略的 `.test-artifacts/`；对外只传压缩后的必要内容。
6. **不得外推**：`cargo check/clippy --target` 只证明类型检查；ARM64 成功不能勾选 x64；静态检查不能替代 WinRE/DISM/格式化/BCDBoot/真实重启。
7. **`C:` 边界**：当前 VM 的 `C:` 是用户正常 Windows 基线，**不是格式化授权**；同卷还原用例优先在新建隔离克隆/fixture 中构造（`winre-repair-implementation-plan-2026-09-25.md:445`）。
