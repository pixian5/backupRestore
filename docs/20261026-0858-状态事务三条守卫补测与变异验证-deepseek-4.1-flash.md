## 二、为什么补这三条

`state_transaction.rs` 只有 73 行，却是整个存储层最关键的一段：**先写完整状态事务，再更新两个兼容视图**，
任何写入边界断电都要靠它重放。它守着三条错误码：

- `BR-CORE-073` 事务身份或阶段不一致（事务里 `task`/`status` 两半对不上，或与目录 id 对不上）
- `BR-CORE-074` 事务存在非法阶段跳转（不按阶段图走）
- `BR-CORE-075` 事务改变了任务身份或参数（换了目标/镜像/已授权参数）

补测前 `lib.rs` 里已有两个相关用例，但**只打到 075**：

- `interrupted_state_transaction_replays_at_each_write_boundary`（遍历 `written_views 0..=2`，验断电重放）
- `state_transaction_cannot_replace_authorized_target_or_skip_stages`（改 `partition_guid`，验 075）

→ **073、074、以及「盘符重排要被容忍」三条零覆盖**。前两条是安全闸门（一次文件损坏就能跳到终态或改写身份），
第三条是相反方向的闸门：**故意不报错**的容忍逻辑最容易被当成多余代码删掉。三处都是「只在断电残留的
事务文件里才会走到」的分支，正常流程 `commit_state` 写出来的两份永远自洽——这种分支在重构里天然不受保护。

## 三、三个用例怎么写的

### 3.1 `state_transaction_rejects_identity_mismatch`（073，四种变体）

一次循环四种不一致，每种都断言错误码 `Some("BR-CORE-073")`：

| 变体 | 动了什么 | 触发的是哪一条判据 |
| --- | --- | --- |
| `status_task_id` | 只改 `status.task_id` | `status.task_id != task.task_id` |
| `task_id` | `task.task_id` **和** `status.task_id` 一起换成新的 Uuid | `canonical_task_id(task) != canonical_task_id(目录 id)` |
| `operation` | `status.operation = RestoreExisting` | `status.operation != task.operation` |
| `stage` | `status.stage = Prepared` | `status.stage != task.status` |

★ **`task_id` 那一条必须两半一起换**——只换 `task.task_id` 的话两个判据会同时成立，测出来分不清是哪条守住的，
将来某条判据被重构掉也看不出来。

另外断言两件"拒绝之后该怎样"的事：

- **事务文件必须留在原地**（报错时顺手删事务 = 证据没了，用户再打开任务只会看到「莫名其妙停在旧阶段」）；
- **盘上的任务视图不能被这次非法重放改写**（`read_json(task_path) == 原 task`）。

### 3.2 `state_transaction_rejects_an_illegal_stage_jump`（074）

盘上 `create` 出来的任务停在 `Prepared`，事务却要求一步到 `Success`。
`Stage::can_transition_to` 里 `Prepared` 只有 `BootRequested / RecoveryStarted / Failed` 三条出边，
所以 `Prepared → Success` 必然被拒。`StatusRecord` 是普通 pub 结构体，直接构造（`Task::transition` 走不通——它自己就会先拒）。

同时断言**两个视图都没被改写**：`task_path` 仍是 `Prepared` 的任务、`status_path` 里的 `stage` 仍是 `Prepared`。
这条比"只断言返回 Err"更重要：074 分支如果在 `write_json_atomic` 之后才返回，光看 Err 是发现不了的。

### 3.3 `state_transaction_tolerates_drive_letter_reassignment`（盘符重排）

`replay_state_transaction` 里那段把五个 `drive_letter` 归零的循环：

```rust
for value in [&mut current, &mut expected] {
    // 盘符由已验证的 WinRE 挂载流程更新，不属于持久卷身份。
    if let Some(v) = value.source.as_mut() { v.drive_letter = None; }
    ...
}
```

**它存在的唯一理由就是让「盘符变了」不被判成身份篡改**（WinRE 挂载后盘符必然可能变）。没有用例的话，
这段看起来完全像"抄了两遍的冗余代码"。

两个方向都验（`disk_letter ∈ {None, Some('G')}`）：

- 盘上**没有**盘符（在线创建的形态）→ 事务里带 `F`/`H`/`W`；
- 盘上带着旧盘符 `G` → 事务里换成 `F`/`H`/`W`（换机器/重新挂载的形态）。

断言：`load` 成功、`status` 推进到 `RecoveryStarted`、**三个盘符都按事务里的新值落盘**、事务文件被清掉。

## 四、★ 变异验证：这一步才是验收

"补了测试而且变绿"证明不了任何事——尤其这种"原始代码本来就对"的分支：写个恒真断言也会绿。
所以把三处守卫逐个拆掉再跑一遍：

```bash
cp crates/backuprestore-core/src/state_transaction.rs /tmp/st.bak
# 1) 073 的 return Err(...)     → /*MUT073*/
# 2) 074 的 return Err(...)     → /*MUT074*/
# 3) 五处 drive_letter = None;  → let _ = &v;      （注意 v.volume.drive_letter 是不带 v 前缀的，正则要一起匹配）
cargo test -p backuprestore-core state_transaction
```

结果：

```
state_transaction_tolerates_drive_letter_reassignment ... FAILED
state_transaction_rejects_an_illegal_stage_jump       ... FAILED
state_transaction_rejects_identity_mismatch           ... FAILED
state_transaction_cannot_replace_authorized_target_or_skip_stages ... ok
interrupted_state_transaction_replays_at_each_write_boundary      ... ok
test result: FAILED. 2 passed; 3 failed
```

**三个新用例全部红、原有两个仍绿**——每个用例只盯自己那一条守卫，没有互相串味。验证完 `cp /tmp/st.bak` 还原，
`git diff --stat` 确认只剩 `lib.rs` 一处改动。

> 变异脚本第一版踩了两个坑：① 只匹配 `v.drive_letter = None;` 漏掉三处 `v.volume.drive_letter = None;`，
> 断言失败但**文件没写盘**，`cargo test` 于是跑在原版上、全绿——差一步就得出"用例根本不管用"的反向结论；
> ② 把 `drive_letter = None;` 直接替换成注释会留下悬空的 `v.volume.` 导致 E0308 编不过。
> 正确做法是整句替成 `let _ = &v;`，并**断言替换条数 = 5**。

## 五、为什么没升版本号

本仓库的惯例是每一步都升版本 + 三处同步，但这一轮的性质不同：**生产代码零改动**，测试代码不进 release 产物。
升到 2.6.58 会让已经打好的 `dist/BackupRestore-2.6.57-windows-arm64.zip`（包内 exe SHA256
`8d71ada5…9456`，与虚拟机 `H:\brwork\BackupRestore.exe` 一致）立刻变成"版本对不上 HEAD"，
而重打包、重新部署换来的功能收益是零。**判据：改没改会进二进制的东西**——改了才升。
