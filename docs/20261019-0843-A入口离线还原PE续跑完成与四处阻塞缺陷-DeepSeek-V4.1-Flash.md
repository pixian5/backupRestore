# A 入口离线还原在 PE 内续跑成功实机记录 + 四处阻塞缺陷（2026-10-19 08:43）

> 撰写时模型：DeepSeek-V4.1-Flash
> 现场：Parallels VM `Windows 11`，宿主 macOS；程序 `H:\brwork\BackupRestore.exe` v2.6.19

## 0. 一句话结论

A 入口（还原到活动系统盘 C:）那一轮在 RE 内被**宿主满盘**打断后，C: 停在「已格式化 + 只灌了 19GB」的半成品状态，机器陷入 `Preparing Automatic Repair` →
失败 → 重启的**无限重启**。本轮改用 **PE（BaseWinPE.iso）+ CLI `recover`** 把任务续跑完：镜像应用完成、`bcdboot` 完成、系统已实机启动。
但**最后一段 WinRE 重接在「WinRE 位于独立恢复分区」的布局下被拒**，任务被判 failed、WinRE 被禁用、`recoverysequence` 被清空，需要手工
`reagentc /enable` 补回（已补，Enabled @ partition6）。

## 1. 现场与故障链

**根因**：半灌的 C: 没有有效引导 → bootmgr 落到 `recoverysequence` 的 WinRE → WinRE 启动修复扫描失败 → 重启，循环。
期间我一度把 VM `memsize` 压到 512MB 腾空间，导致 WinRE 直接 `0xc0000017（not enough memory to create a ramdisk device）`——
`memsize` 已恢复为 **6144MB**（原配置值）。

## 2. 冲出现场的通道

1. VM 停 → `prlctl set "Windows 11" --device-bootorder "cdrom0 hdd0 hdd1 hdd2"`（config.pvs 里 CdRom 已指向 `artifacts/BaseWinPE.iso`）→ 开 VM；
2. `Press any key to boot from CD` 窗口只有几秒：用 `prlctl send-key-event --scancode 28`（Enter）**每 0.8s 连发 40 次**顶住；
3. 进 PE 后是 `X:\windows\system32\cmd.exe`，**无 Parallels Tools、无 prlctl exec**，只能靠 scancode 注入 + `prlctl capture` 截图回读。

> 按键注入的两个坑（本轮踩实）：
> - 单个字符走 `--scancode` 可靠；**Shift 必须在字符前 press、字符后 release，且两头各留 150ms**，
>   否则 `:` 退化成 `;`、大写退化成小写（我第一版就是 shift 用 tap 发 press+release，全部失效）。
> - `--key`（Parallels 虚拟键码）与 Windows VK 码**不是一套**，用 VK 会输出乱码（实测 `echo Test: 1` 变成 `o7brwork...`）。

## 3. 四处阻塞（按遇到顺序，均为实机复现）

### D1 `recover` 的 `<task-root>` 是**工作区根**，不是 `tasks` 目录

`TaskStore::task_dir = root.join("tasks").join(id)`。传 `H:\brwork\tasks` 时它去找 `...\tasks\tasks\<id>`，
报 **`invalid task: ... The system cannot find the path specified. (os error 3)`**——错误里**不含路径**，极难定位。
正确写法：`recover H:\brwork <task-id>`。

### D2 `recover` 不复原/不重解析镜像卷盘符 → 盘符一变就 os error 3

`resolve_volume_root()` 只用 `volume.drive_letter`（`PathBuf::from("{}:\\")`）。任务里记的是准备阶段的盘符，
而 PE 里同一卷是另一个字母（本轮 H: ↔ E:）。首次 `recover` 直接死在：
`failed to read image metadata: ... (os error 3)`。
RE 内同理：准备阶段记 H:、进 RE 后盘符重排 → 这条同样会炸。

**临时绕法**：在 PE 里用 `diskpart` 把任务记录的字母指派给镜像所在卷（本卷同时只允许一个字母，指派新字母会**顶掉**旧字母）。

### D3 `recover` 在 PE 里不会自动挂载 ESP

`find_efi_root()` 只认 `--efi-root`，否则在 **STEP 3/4 校验之后**才失败：
`invalid task: EFI root must be explicitly mounted before recovery`（此时镜像已灌完，等于白跑一趟 apply）。
必须 `diskpart` 挂 ESP（本轮 S:）后带 `--efi-root S:\` 重跑。

### D4 ★ WinRE 重接把「独立恢复分区」当成异常，直接拒接

`winre_registration.rs::reconnect()`：

```rust
if info.location.as_deref() != Some(self.location.as_str()) {
    return Err(crate::err("已启用 WinRE 不在目标分区，拒绝重接"));
}
```

`self.location` 期望 WinRE 位于**目标分区内**（`<target>\Recovery\WindowsRE`）。而本机 WinRE 在
`\\?\GLOBALROOT\device\harddisk0\partition6\Recovery\WindowsRE`（独立 840MB 恢复分区，Windows 默认布局之一），
于是：镜像灌完 → `bcdboot C:\Windows /s S:\ /f UEFI /v` 成功 → `reagentc /info` 成功（能读到 partition6）→ **拒绝重接**。

连锁后果：
- 任务被判 `failed`（progress 90 → 0，错误「恢复在恢复环境中连续失败，已自动逃出并标记为终态」）；
- 恢复控制台弹「恢复暂未完成」模态框，选「取消」→ 清一次性启动项 + 标记终态；
- **WinRE 被禁用**（`reagentc /info` → Disabled、位置空）、`{current}` 的 `recoverysequence` 被清空。

**手工补回（已执行）**：`reagentc /enable` → 状态 Enabled、位置回到 partition6、版本 10.0.26100.8031；
`bcdedit /enum {current}` 重新出现 `recoverysequence {264caa29-…}` + `recoveryenabled Yes`。

## 5. 教训（写进长期守则的部分）

1. **宿主满盘会以「VM 静默停机」的形式出现**，现象和"程序挂了"极像；先 `df -h` 再怀疑代码。
2. **不要用降 memsize 去腾空间**：512MB 直接让 WinRE 起不来（0xc0000017），故障叠故障。
3. PE 里**同一卷只能有一个盘符**（`diskpart assign` 是搬移不是追加）——想同时满足「程序路径 H:」和「任务记录 E:」是做不到的，
   必须以**任务记录的盘符**为准（D2 的正解是程序侧按卷 GUID 重解析，不是人工凑盘符）。
4. `recover` 在 PE 里跑之前，先确认三件事：`<task-root>` = 工作区根、镜像卷盘符 = 任务记录值、ESP 已挂并带 `--efi-root`。
5. 出现「Preparing Automatic Repair」无限重启 ≠ 还原还在跑；看 `hds` 是否增长、看 `status.json` 是否推进，别等。

## 6. 待办（本轮未做，按优先级）

- **P-A**：D2 修复——`resolve_volume_path` 优先按 `volume_guid` 解析（`\\?\Volume{…}\`），字母仅作兜底；PE/RE 里盘符必变，这条不修就等于"离线续跑不可用"。
- **P-B**：D4 判定——WinRE 在**独立恢复分区**时应视为合法（比较的是"是否指向本次还原的系统"而不是"是否在同一分区"），
  或至少在拒绝前把 `recoverysequence` 保留、不要把 WinRE 禁用。
- **P-C**：D3 在 PE 内自动挂载 ESP（或 STEP 3 之后再要求 --efi-root 属于顺序设计错误，应在 STEP 1 前校验）。
