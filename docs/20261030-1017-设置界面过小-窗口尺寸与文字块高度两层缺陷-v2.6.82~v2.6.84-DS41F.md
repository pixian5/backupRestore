# 设置界面过小：窗口尺寸与「文字块高度」三层缺陷（v2.6.82 ~ v2.6.84）

> 模型：DS41F。时间：2026-10-30 10:17（v2.6.84 补记 12:40）。
> 版本：**2.6.82**（七个窗口的尺寸改为随 DPI 缩放）→ **2.6.83**（文字块高度改为实测；操作模式页签按实测宽度排布）

## 1. 需求

用户发来设置窗口截图（`PixPin_2026-10-30_02-38-07.png`，窗口右侧与底部被切、文字互相压住）：

> 「设置界面过小，检修全部类似问题」

然后是：

> 「继续」

关键词是**「全部类似问题」**——不是只修设置窗口，而是把同一类缺陷在其它窗口里找齐。

## 2. 真因分三层，别混

### 2.1 第一层（2.6.82）：窗口尺寸没有跟着缩放

2.6.79 把**控件**坐标统一乘了 DPI 系数（`create_control` 一个入口全覆盖），
但**窗口本身**的尺寸是 `CreateWindowExW` 直接传的常量：

```rust
CreateWindowExW(..., (screen_w - 640) / 2, (screen_h - 560) / 2, 640, 560, ...)
```

控件按 1280×1120 摆，窗口只有 640×560 —— 右边和下边的控件画到窗口外。
这正是用户看到的「界面过小、右侧和底部被切」。

修法：把这 7 处窗口宽高包一层 `crate::dpi::s(...)`。涉及：

| 文件 | 窗口 |
|---|---|
| `native_gui/settings_dialog.rs` | 程序设置 |
| `native_gui/choice_dialogs.rs` | 系统盘处理选择、镜像路径无效提示 |
| `native_gui/image_admin_window.rs` | 备份文件管理 |
| `native_gui/logs_viewer.rs` | 查看日志 |
| `recovery_progress.rs` | 恢复进度窗（同时把该模块唯一的字体入口 `create_font()` 与 `layout_controls()` 里全部 `MoveWindow` 接上缩放） |

`recovery_progress.rs` 的做法与主窗口一致：客户区先 `unscale()` 换回 96dpi 基准空间，
常量一个不改，输出时统一 `s()`。

### 2.2 第二层（2.6.83）：文字块高度写死 → 字号一变大就溢出

窗口尺寸修好后，设置对话框仍然**文字互相压住**。原因是布局里每一块说明文字的高度、
以及下一个控件的 y，全是写死的：

```
40 / 56 / 44   ← 按 14 号字折「两行 / 三行」算出来的
```

2.6.81 允许用户把字号调到 16 / 18 之后，同一段文案在 18 号下折成**三行**，
第三行画到控件矩形**外面**，又被下一个控件的背景盖掉上半截。

**关键认识：一块文字折几行，由「字体 × 宽度 × 文案（随语言变）」三者共同决定，
人算不准，只能让 GDI 用同一套字体实测。**

实测证据（`.test-artifacts/dpi-2679/dlg-rects.ps1` 枚举子控件矩形，按 y 排序）：

| 控件 | 写死高度 | 18 号字实际需要 |
|---|---|---|
| `id=3106`（失败次数说明） | 80 | ≈120（三行） |
| `id=3107`（失败后动作说明） | 112 | ≈148 |
| `id=3109`（DISM 说明） | 112 | ≈148 |

### 2.3 第三层（2.6.84）：窗口**宽度**是常量，装不下最长的那一行

前两层修完，设置窗口在「英文界面 + 18 号字」下仍然有问题：窗口宽度是常量 560 基准，
而「Maximum wait when paused in the recovery environment」+ 编辑框 + 后缀这一行要 936 基准。
2.6.83 的应对是把标签宽度用 `clamp(80, 280)` 硬卡住——**把后缀保住了，代价是标签被切字**。

这属于同一类缺陷的第三个方向：第一层漏了窗口的**宽高**，第二层漏了文字的**高度**，
这一层漏的是「窗口宽度应当由内容决定」。

## 3. 改动清单（2.6.83）

### 3.1 新增文字度量（`native_gui.rs`）

```rust
pub(crate) unsafe fn measure_text(text: &str, width96: i32, wrap: bool) -> (i32, i32)
pub(crate) unsafe fn measure_text_width(text: &str) -> i32
pub(crate) unsafe fn measure_text_height(text: &str, width96: i32) -> i32
```

实现要点：
- `GetDC(NULL)` 拿屏幕 DC（**窗口创建前也能量**，设置对话框的排版就发生在 `WM_CREATE`）；
- `SelectObject` 挂上 `gui_font()`（当前字号 + 微软雅黑 + 字重 700）；
- `DrawTextW` + `DT_CALCRECT | DT_NOPREFIX`，需要折行时加 `DT_WORDBREAK`；
- 量完 `SelectObject` 还原、`ReleaseDC` 归还、`DeleteObject` 释放字体。
  **屏幕 DC 必须还**：每开一次对话框要量十几段文字，漏 DC 会一路累积到 GDI 对象上限。

### 3.2 设置对话框改成「从上往下按实测高度流水排」

`native_gui/settings_dialog.rs` 的 `WM_CREATE` 里，原先一排排写死的 `y` 换成：

```rust
let mut y = 20;
y += line + 10;
let height = measure_text_height(threshold_hint, content_width);
create_control(hwnd, "STATIC", threshold_hint, 0, left, y, content_width, height, ID_SETTINGS_HINT);
y += height + 12;
...
```

标签宽度也按实测：`measure_text_width(label).max(80)`。
（2.6.83 时「pause 最长等待」的标签还留了一个 `clamp(80, 280)` 上限——因为窗口宽度写死 560，
英文文案在 18 号下比 280 还长，放开就会把后缀挤到窗口外；**2.6.84 窗口宽度改成按内容算之后，
这个上限已删除**，见 §3.5。）

窗口高度不再写死 590，改成**按内容反推**：

```rust
let client_h = y + 30 + 18;                       // 最后一个控件底缘 + 余量
let mut frame = Rect { left: 0, top: 0, right: s(client_width), bottom: s(client_h) };
AdjustWindowRectEx(&mut frame, frame_style, 0, 0); // 客户区 → 整窗（含边框标题栏）
MoveWindow(hwnd, 居中x, 居中y, frame宽, frame高, 1);
```

（2.6.83 时这里 `right` 还是 `s(560)`；2.6.84 改成按内容算的 `client_width`，见 §3.5。）

### 3.3 顺手修掉的隐藏缺陷：字号下拉框展开后一条都看不到

`COMBOBOX` 的高度参数是**展开后列表的总高度**，不是闭合高度。旧值写死 24，比一行还矮。
改成 `(line + 6) * (档位数 + 1)`。

### 3.4 ★ 同类问题：「操作模式」那一排页签在 18 号字下互相挤压

五个 `BS_PUSHLIKE` 单选按钮的宽度在创建时写死（56 / 120 / 120 / 150 / 72，x 从 90 每隔 3px 排下去），
是按 14 号字中文文案估的。字号一变大：

1. 「新增非 C 盘第二系统」9 个字直接顶出按钮矩形，相邻两个的字贴在一起；
2. 左边「操作模式」标签固定 62px，18 号字下 4 个汉字要 70 多像素，末字被切；
3. 英文界面更严重——「Add 2nd system (non-C:)」比任何中文都长。

新增 `layout_operation_tabs()`：每个按钮宽度 = **实测文字宽度 + 左右各 9px 内边距**，
依次往右排，由 `layout_operation` 调用（所以**改字号也会重排**，`apply_font_size` 走的正是这条链）。

#### ★ 宽度为什么最终改用 `GetTextExtentPoint32W`（2.6.84 修正，别改回去）

2.6.83 用的是 `DrawTextW(DT_CALCRECT)` 量宽度，发现它比真实排版**窄**，于是加了固定补偿。
2.6.84 用判据把补偿量量了一遍，结论是**固定补偿这条路走不通**：

| 文案（18 号字，200% 缩放，基准像素） | `DT_CALCRECT` | 真实排版 | 差 |
|---|---|---|---|
| 还原数据到非 C 盘 | 298 | 316 | 18 |
| Maximum wait when paused in the recovery environment | 525 | 494 | −31 |
| seconds (0 = wait indefinitely) | 277 | 294 | 17 |
| Interface font size: | 170 | 190 | 20 |

差值从 −31 到 +20，**方向都不一致**，任何固定补偿都会在某些字符串上留下 3~12 像素的缺口。

所以宽度改用 `GetTextExtentPoint32W`（排版取字符串尺寸用的就是它），只留 4px 防 ClearType 取整：
18 号字、英文界面下把设置对话框每一行都量了一遍，应用内实测值与真实绘制墨迹**逐行吻合**
（详见 §4.4）。**高度仍然走 `DrawTextW(DT_CALCRECT|DT_WORDBREAK)`**——那个方向没观察到偏差，
而且折行只有 `DrawText` 会算。

### 3.5 ★ 2.6.84：设置窗口的**宽度**也改成按内容算

2.6.83 只把**高度**改成按内容反推，宽度仍是常量 560。后果是英文界面 + 18 号字下
「Maximum wait when paused in the recovery environment」这一行装不下，只能靠 `clamp(80, 280)`
把标签硬卡住，代价是**标签被切字**。

`WM_CREATE` 改成**两遍**：

1. **第一遍只定文案、算窗口要多宽**：把所有单行内容（标签 + 编辑框 + 后缀三件套、
   单选按钮的文字、字号行）各算一遍，取最大值 + 右边距，夹在 `[560, 屏幕宽−80]` 之间。
2. **第二遍用这个宽度去量每块说明文字的高度**（说明文字要折行，所以要用最终宽度）。

两遍不构成循环依赖：宽度只由单行内容决定，高度只由宽度决定。

配套改动：
- 三个后缀控件（`次后：` / `秒（0=不限制）` / `秒（0=一直等）`）的宽度原来是写死的 160/220/220，改成实测；
- `pause_wait_label_width` 去掉 `clamp(80, 280)`，标签按实测值给足，不再截断；
- 「取消 / 保存」按钮从写死 x=330/434 改成**贴着内容区右缘**；
- 窗口整宽用 `AdjustWindowRectEx` 从客户区反推（`CreateWindowExW` / `MoveWindow` 的宽高是**含边框标题栏**的整窗）。

中文界面在默认字号下算出来的客户区宽度正好还是 560，**窗口大小不变**；只有英文或大字号才变宽。

## 5. 过程坑（都踩了，记下来）

| 坑 | 现象 | 处理 |
|---|---|---|
| **提权程序收不到注入** | `PostMessage(BM_CLICK)` 返回成功、窗口毫无反应 | GUI 是 High IL（提权），中等完整性进程注入被 UIPI 丢弃。必须 `Start-Process -Verb RunAs` 起注入进程 |
| **`prlctl exec` 吃路径反斜杠** | `-File 'X:\test-artifacts\...'` 报「不是有效的 .ps1 文件路径」 | `\t`、`\r` 被当转义。改正斜杠 `X:/.test-artifacts/...` |
| **进 VM 的 PS 脚本必须纯 ASCII** | `ParserError: UnexpectedToken ')'`，且 `-Verb RunAs` 子进程 stderr 不进父管道 → 只表现为「没有输出文件」 | PowerShell 5 无 BOM 时按 ANSI 读文件，UTF-8 中文注释被逐字节拆开破坏引号配对。脚本头写死 `keep this file ASCII-only` |
| **`Get-Content` 读单行文件返回字符串** | `[0]` 取到的是第一个字符 `"B"` | 先 `@()` 包成数组 |
| **共享设置文件被写坏** | `BackupRestore.settings.ini` 只剩 `font_size=14` 一行 | 用「显式 `@()` 数组一次写全 6 行」的脚本恢复，写完立刻回读行数确认 |
| **截图全黑** | 灰度均值 < 2（正常 ≈235） | VM 屏幕休眠。注入鼠标移动 + 按键唤醒；`prlctl capture` 唤醒后仍可能抢不到帧，改用进程内 `CopyFromScreen` 截图（`snap.ps1`） |
| **`prlctl exec` 约 1/8 不执行** | 空输出 | 判据只认结构化特征（`OVERLAPS=` / `DEPLOYED SHA256=`），空输出重试 3 次 |
| **`FindWindow` 时序** | 进程已在但 `FindWindow` 返回 0 | 进程启动后要枚举磁盘，窗口晚于进程出现。先 `EnumWindows` 兜底 |
| **`WM_GETFONT` 取到的不是真实字体** | 同一控件在 14 号与 18 号下量出**完全相同**的字宽 | 该句柄不可用。判据改为在测试进程里按当前字号重建雅黑粗体再量 |
| **★ 判据量的是系统等宽字体（假红，最贵的一次）** | 2.6.84 第一版判据报 `SINGLE_LINE_CLIPPED=3`，可截图里一处都没被裁 | 判据的 `[DllImport("gdi32.dll")] CreateFontW(..., string face)` **少了 `CharSet=CharSet.Unicode`**，字体名按 ANSI 传进 W 接口变乱码 → GDI 回退到默认等宽字体。**识别特征极简单：`HHHHHHHHHH` 和 `iiiiiiiiii` 量出一样宽（都是 190）**。补上 `CharSet` 后 `tmHeight` 从 36 变 47、两者变成 280 / 100，数字立刻与真实墨迹吻合 |
| **`GetTextExtentPoint32W` 和 `DT_CALCRECT` 只在字体正确时才同值** | 判据里两者完全相等，应用里差 20 | 等宽字体下没有 kerning / 前缀处理差异，两个接口必然同值。**两者同值本身就是「字体选错了」的信号**，别当成「测量可靠」 |
| **`CreateWindowExW` 的宽高是整窗** | 客户区 704×441 而控件按 720×480 摆 | 要客户区尺寸必须 `AdjustWindowRectEx` 反推（2.6.67 踩过，本轮设置窗口沿用该结论） |

## 6. 遗留

1. **100% 缩放未实测**（改 VM 缩放要重登录，且 `LogPixels` 会在登录时被写回 192）。
   等价性是数学推理：系数 1.0 时 `s`/`unscale` 恒等。
2. **宽度测量依赖字体版本**：现在用的是 `GetTextExtentPoint32W`（真实排版宽度）+ 4px 余量，
   每侧实测余量 8~14 物理像素。若将来换字体族或字重，需要重跑 §4.4 的三方对照。
3. **窗口宽度有屏幕上限**：`client_width` 被夹在 `[560, 屏幕宽−80]`。英文 + 18 号字下
   算出来是 936 基准（1872 物理），离 1095 的上限还有距离，再加更长的文案仍有余量；
   但真到了上限会被截断，届时应当让过长的标签自己折行。
4. **中文界面下窗口宽度恒为 560**（因为算出来正好 ≤ 下限）。这不是「没生效」，
   是故意保留下限让默认字号下的窗口大小与旧版一致。
5. PE 恢复桌面 / 恢复进度窗仍未实机验证（与本轮改动无关，属历史遗留）。
