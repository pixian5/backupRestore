## 〇、怎么用这本账（防重复测试的操作步骤）

### 0.1 想测一件事之前，按这三步查

1. **在 §四 的主题表里找到它**，看「最后一次实测」和「实测时版本」。
2. **看 §九「改动-复验对应表」**：这次改动碰到的模块，是否落在那项测试的覆盖范围内。
   - 没碰到 → §五 里标了「✅ 免测」的，直接引用旧结论，**不要重跑**。
   - 碰到了 → 必须重跑，旧结论只作背景。
3. **跑之前先扫 §六「结论已作废」**：确认你要照着做的那份旧文档，结论没被推翻。

### 0.2 两条必须记住的判读规则

- **「测过」≠「当前二进制上测过」**。大量验收是在 2.6.1x ~ 2.6.3x 上做的，之后一路迭代到 2.6.77。
  严格按「当前二进制」口径，六项主流程里只有 C 入口做过全链复跑（`经验/05` §7 的诚实口径）。
  所以本账**分两级**（§五）：A 级 = 接近当前版本且对应代码未改，可免测；B 级 = 历史通过、版本已迭代，只证明「设计曾经工作」。
- **版本号是标签，不是文档 ID**。同一个版本号可能挂多篇验收文档（例如 2.2.2 同时挂数据卷
  `20261010-1910` 与系统卷 `20261010-2200`）。判定「某版本覆盖了什么」必须列全该号下所有文档。

### 0.3 状态标记

| 标记 | 含义 |
|---|---|
| ✅ | 已实机验证通过，结论仍成立 |
| ⚠️ | 测过，但**结论被后来推翻**、或只测了一部分、或判据已反转 → 引用前必读 §六 |
| ❌ | 明确还没测 / 是真缺口 → 见 §七 |
| 🔸 | 单一来源、未能交叉验证；或属静态审查而非实机 |

### 0.4 维护约定（写给下一轮）

- 每轮实测结束，**先更新 §四 对应行**（日期 + 结果 + 证据路径），再更新 §五 的免测清单，
  最后才写新的过程文档。顺序反了就会出现「代码往前走、账本没跟上」——这正是 2026-10-29
  全量审计抓到的最贵一类错误（6 处「把已修好的写成还没修」）。

  **空集也要能分辨「真没有」和「扫描没跑」**。
- 环境底数（盘符、空闲空间、界面坐标）**一律带时点**，跨轮照抄必错（§二的表就是时点快照）。

## 一、项目是什么（一页读懂）

### 1.1 一句话定位

BackupRestore 是**「Windows 自带恢复环境的自动化包装器」**：图形界面准备好任务和一次性启动项 →
重启进入恢复环境（WinRE，Windows 自带的修复系统）→ 自动运行 `Recovery.exe` 离线捕获/应用镜像 →
修好引导、清理临时启动项 → 重启回正常 Windows。

系统卷**必须离线**处理，这是被逼出来的：正在运行的 Windows 系统盘被系统自己占用，既不能整卷捕获、
也不能被格式化；而项目没有用卷影复制（VSS）。测试机的恢复环境恰好注册在 C 盘本身，更没有别的路。

技术栈：**纯 Rust**，两个 crate，自绘 Win32 图形界面 + 命令行，**零 .NET / C# 运行时依赖**。
构建目标 **Windows ARM64**，静态链接 C 运行库（`+crt-static` 是硬要求，漏了会依赖
`VCRUNTIME140.dll` 而进不了精简恢复环境，症状是零输出零副作用，退出码 `0xC0000135`）。

### 1.2 用户能看到的入口（入口名是用户拍板的全称，不要擅自改）

| 界面上的名字 | 内部代号 | 做什么 | 通道 |
|---|---|---|---|
| 备份 | `backup` | 从源卷用 DISM 捕获成镜像 | 智能分流（系统卷走恢复环境，小数据卷走在线） |
| **还原系统到 C 盘**（A） | `restore-existing` | 把系统还原回当前 C 盘，目标锁定为当前系统盘 | **必离线**（重启进恢复环境） |
| **还原数据到非 C 盘**（B） | `restore-data` | 还原数据卷，镜像不完整也放行 | 默认在线 |
| **还原系统到非 C 盘**（C） | `restore-system-other` | 把系统还原到另一块盘，做成双系统 | 默认在线，也可选离线 |
| 新增第二系统 | `create-secondary` | 旧入口，实质流程与 C 重复 | — |
| 安装预安装环境 | `install-pe-entry` | 部署 WinPE（Windows 预安装环境），分内存版/硬盘版 | — |

两条硬闸，测之前必须知道：

- **A 入口要求「目标 = 源 = 当前活动系统卷」**，所以它**不能用来验别的卷**。想验「目标非法被硬拒」
  只能用 C 入口的命令形式 `create-secondary --target-drive <非活动卷>`。
- **C 入口还原到另一块盘，不要求那块盘上已经装好 Windows**（2026-10-29 源码核实）：
  准入只有三条——目标 ≠ 源、目标 ≠ 当前运行的系统卷、镜像是完整 Windows。它本身就是
  「格式化目标卷 → 铺镜像 → 修引导」。所以**测试靶子可以是一块空 NTFS 卷**，不必养一套第二系统。
  这条推翻了 10-29 早上「删掉 F: 就没法测还原」的说法。
  源码落点（2026-10-29 核对，别指错模块）：目标 ≠ 活动系统卷在 `online_operation.rs:387`；
  「镜像是完整 Windows」由 `windows_prepare.rs:1863` 的 `wim_full_windows_probe`（调用点 `:2682`）把关；
  工作区/镜像落在注册 WinRE 分区由 `core/lib.rs:440` 的 `validate_volume_roles` 拒绝。
  ★ `windows_prepare.rs:2564` 的 `single-system restore target must equal source` 是 **A 入口**的硬闸，
  **不是** C 入口的准入——旧引用常把它错当成 C 入口的三条。

### 1.3 三条路径的能力差异（不随时间变，2026-10-29 从 `经验/01` 核对）

| 能力 | 恢复环境任务链 | 在线路径 | 预装预安装环境 |
|---|---|---|---|
| 11 个阶段的状态机 + 断电续跑 | ✅ | ❌ | ❌ |
| 载荷哈希五件套信任链 | ✅ | ❌ | ❌ |
| 多索引保留策略 | ✅ | ❌ | ❌ |
| 格式化 + 修复引导 + 恢复环境注册 | ✅ | ✅（有修复引导） | 简化（固定索引 1） |
| 副档（镜像旁的元数据）生产 | ✅ | ✅ | ❌ |

**在线还原是「覆盖式应用」**：默认不格式化、不动引导、没有卷影复制，镜像里没有的旧文件可能还留在目标上
（勾选「格式化」才清空）。所以「在线还原成功」和「恢复环境完整任务链成功」不是一回事，验收判据不同。

**三条纪律（项目灵魂，每个 bug 几乎都是违反它们的产物）**：
① 不信外部命令的退出码；② 写完必须回读；③ 元数据簿记必须与镜像实际内容同步。

### 1.4 代码地图（说人话，不写行数——行数会漂移）

```
crates/backuprestore-core/     任务模型、11 阶段状态机、载荷契约、副档、SHA-256、错误类型
crates/backuprestore-cli/src/
  main.rs                      入口与任务分发、恢复环境里跑的完整流程
  native_gui.rs                自绘 Win32 图形界面（最大的技术债，尚未拆分）
  windows_prepare.rs           正常 Windows 侧的准备：近百项校验、注入载荷、设一次性启动
  boot_entry.rs                自建启动项、ramdisk 规格、任务载荷隔离
  boot_menu.rs                 引导修复、启动菜单、默认项决策
  secondary_registry.rs        双系统的盘符绑定（读 Windows 的 MountedDevices 注册表）
  online_operation.rs          在线还原/备份事务与回读
  pe_operation.rs              预装 WinPE 的路径
  winre_registration.rs        系统还原后的恢复环境注册与关联核验
  windows_command.rs           作业对象约束下的命令与进程树管理
  recovery_progress.rs         恢复环境/PE 的进度上报（含后台控制台、B 键回退）
  wimlib_apply.rs              wimlib 应用通道（覆盖式还原）
  text_parsing.rs              解析 DISM/bcdedit/mountvol 的本地化输出 —— 纯逻辑，macOS 上也能单测
```

★ **纯逻辑必须下沉到 `text_parsing`**：`native_gui`、`windows_prepare`、`online_operation` 等 8 个模块
带 `#[cfg(windows)]`，在 macOS 上编译不到、单测一次都不会跑——「写了测试但永远不执行」等于没写。

### 1.5 范围边界（别擅自扩成 Ghost 工具）

**支持**：Windows 10/11、UEFI + GPT、NTFS 系统分区、镜像、Windows 自带恢复环境（或自定义 WinPE）、
DISM / wimlib 作为镜像引擎、BCDBoot 与启动配置数据（BCD）作为启动管理。

**明确不做**：分区布局重构、网络备份、增量/差异镜像、Legacy BIOS、自动改 BitLocker。

**两个硬边界（不是可降级的路径）**：
- 第二系统的盘符绑定只支持 GPT 盘；MBR 盘的注册表 blob 是 12 字节，解析不出 GUID，修复时报错。
- 程序**拒绝把当前活动系统盘当在线还原目标**（报 `active Windows volume must be processed offline`），
  系统卷还原必须走重启进恢复环境的离线路径。

### 2.2 唯一构建与部署路径

**发布路径只能走虚拟机内的 Windows 构建**：`windows/build-windows.ps1 -Architecture arm64 -Deploy`。
macOS 侧的 `./build-win.sh` **只作本地类型检查**，产物不得部署、不得当发布版——因为它对 8 个
`#[cfg(windows)]` 模块（约 59% 的代码）零证明力，历史上一批阻断缺陷全在 macOS 编译不到的文件里。
（用户 2026-10-15 拍板；实测对比见 `20261012-1640`。）

- 编译产物目录必须放本地盘（`H:\br-target` 或 `C:\brtarget`），**不能放共享盘 X:**——cargo 删临时目录会报 `os error 87`。
- 部署前先结束占着 `BackupRestore.exe` 的图形界面进程（SYSTEM 通道才杀得掉自启的实例）。
- 部署成功的唯一判据：**四个文件的 SHA-256 与刚构建的成品逐个相等**，复制成功不算数。

### 2.3 测试是怎么驱动起来的（固定脚手架，都在 `tools/win-clicker/`）

| 手段 | 用途 | 关键坑 |
|---|---|---|
| `C:\br-test.json` + `--test-hook` | 用 JSON 指定页签/模式/目标卷/自动安装，驱动**与按钮完全相同的函数** | **用完必须删**，否则下次启动重复安装；测试钩子会自动点「是」，**验真实确认链必须跑纯净图形界面** |
| `br-agent-tcp.sh`（端口 9124） | 首选的键鼠注入通道，Session 1 提权 | 消息级注入不可行（UIPI + 自绘按钮） |

| `br-focus-gui.ps1` / `br-enum-dlg.ps1` | 点击前聚焦并回读、弹窗现枚举 | 禁用 `SW_RESTORE=9`（会把最大化窗口打回默认尺寸） |

★ **两条通道不能混**：**编译必须用用户会话**（源码在共享盘 `X:`，SYSTEM 账户看不到它），
**运行必须用 SYSTEM**（建 VHD、跑 DISM、diskpart 都要管理员）。典型流程 =
「用户会话编译 → 复制 exe 到本地盘 → SYSTEM 运行」。复制夹具也要走用户会话。

★ **`prlctl exec` 约 1/8 的调用根本没执行命令**（不是失败，是没跑），症状是结果文件连创建都没有，
脚本白等到超时再把「仪器没工作」误判成用例失败。凡「发命令 → 等产出文件」的步骤一律走
`vm_launch_verified`（发 → 探测是否生效 → 最多重发 3 次）。**这是仪器层补救，绝不许把失败改判成通过。**

## 三、验收判据总纲（判定成败的那把尺子）

### 3.1 判据优先级

**持久任务状态 + 真实命令日志 + 文件/镜像回读 ＞ 退出码 ＞ 截图**。
空退出码不得记为成功；PowerShell 重定向图形界面程序常读到空 `$LASTEXITCODE`。
**DiskPart 脚本里单条命令失败时，进程退出码仍可能是 0**——格式化后必须回读 NTFS 类型、
卷序列号变化、分区身份，不能只看「格式化命令返回 0」。

### 3.2 「还原真的发生了吗」——两个卷级铁证

1. **卷序列号变化**（格式化路径）/ **不变**（覆盖式 `--skip-format` 路径，语义相反）。
2. **哨兵法**：还原前在目标卷根放一个 `BR-时分秒.txt`（精确到秒防同日重名）。
   - 格式化还原 → 哨兵**必须消失**；
   - 覆盖式还原 / 取消格式化 → 哨兵**必须存活**（这是「没有格式化」的铁证）。

★ DISM 应用镜像会**保留镜像内文件/目录的原始时间戳**，所以「目录时间是旧的」既证不实也证不虚，别用它。

### 3.3 「功能可用吗」——三项判据，缺一不可

① 截图看到完整桌面/完整任务栏；② 事件日志里 EventID 1000 零新增（无崩溃循环）；
③ WerFault 进程 ≤ 1。**「进程还在」是弱信号**——崩溃循环中的进程也会短暂存在
（`20261012-1350` 就是把「进程存在」误判成「第二系统可启动」，被下一份文档推翻）。

### 3.4 变异验证才算验收

补了测试/判据之后，验收方式**不是看它变绿**，而是**拆掉守卫或改回旧值重跑**：
新判据必须变红、老判据仍绿，恢复后再变绿。不变红的判据等于没有判据。

★ 变异本身也会做错：`Xremove letter=V` 里仍含 `remove letter=` 子串，判据照绿——
所以做变异时要确认**真的翻了语义**，而不是碰巧还匹配。

### 3.5 六个反复踩的判据坑（写新判据前必读）

| 坑 | 表现 | 防法 |
|---|---|---|
| **空输出有歧义** | 「真没有」与「命令没跑」分不清 | 判据查「不可能合法为空」的整体；或加 `__END__` 哨兵；或重试 3 次 |
| **判据红先证明读数侧** | 「读不到」被记成「被测对象失败」 | 先让仪器自证环境（打印进程/会话/窗口数），再怀疑产品 |
| **SKIP 掩盖用例不存在** | 用例丢了 `#[test]`，门禁在「环境缺失」那步跳过 | 门禁先核对 `--ignored --list` 里用例真存在 |
| **输入缺失静默通过** | 判据读外部文件，文件不在就 `return`（测试通过） | 夹具入库 + 缺失即 panic + 规模闸（如 `parsed>=100`） |
| **退出码不是判据** | `bcdedit /import` 报非 0 但值已还原；`copy` 退出码 0 但「已复制 0 个文件」 | 看副作用（值有没有回来、文件哈希），不看退出码 |
| **同源读数只证明自洽** | A 等不等于 B，两侧都由同一台仪器产生 | 叠加一条来自**不同代码路径**的绝对判据（如窗口内计数 vs 磁盘目录数） |
