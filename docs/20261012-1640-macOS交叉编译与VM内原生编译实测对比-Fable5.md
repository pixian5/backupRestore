# macOS 交叉编译 vs VM 内原生编译：实测对比

> 版本：2.3.9（`backuprestore-cli`，目标 `aarch64-pc-windows-msvc`）
> 模型：Claude Fable 5
> 日期：2026-10-12 16:40
> 同一份源码、同一个 rustc 1.98.1，两条路径各跑一遍的横向对比。

## 一、结论先说

**两条路径都能产出质量等同的可用产物**：都是 14 个 DLL、都零 CRT 外部依赖
（不含 `VCRUNTIME140.dll`、不含 `api-ms-win-crt-*`，因此都能进精简 WinRE/PE）、
大小只差 16KB（0.67%）、新代码标记全命中。

**真正的差别不在产物，在验证能力**：

- **VM 内编译的独特价值：编完能立刻在目标环境实机验证。** 本轮已实测
  （`inspect-environment` 输出正确 JSON、退出码 0）。macOS 侧编完无法验证，
  只能部署到客体后再验——而"部署后才发现问题"的成本高得多。
- **macOS 交叉编译的独特价值：快一倍，且不依赖客体在线。**
  8.16s vs 15.24s（Apple Silicon 原生运行 rustc vs Windows-on-ARM 虚拟化开销）。
  客体关机、共享掉线时照样能编。

## 三、差异来源分析

**为什么产物大小差 16KB**：两边链接器不同（LLVM lld vs MSVC link.exe），
对齐与节填充策略略有差异；PDB 引用方式也不同（两边二进制里都能找到 `.pdb`
字符串，但 macOS 侧那个 `D:\a\_work\1\s\binaries\arm64ret\lib\arm64\*.pdb`
路径在 macOS 上不存在，所以刷了一屏 LNK4099 警告——**纯噪音，不影响产物**）。

**为什么 DLL 列表一致**：两边都启用了 `+crt-static`，CRT 被静态链进产物，
只剩 Windows 系统 DLL 依赖。这是踩坑 25 的解决方案（见
`docs/20260925-0207-pitfalls-static-crt.md`），两条路径都保持了这个性质。

## 四、本轮我自己犯的一个错（值得记）

第一次在 VM 内编译时，我直接跑了裸 `cargo build`，**漏了 `+crt-static`**。
产物随后暴露出问题：含 `VCRUNTIME140.dll`、`VCRUNTIME140_1.dll` 和
五个 `api-ms-win-crt-*`，DLL 数从 14 涨到 20——这正是踩坑 25 描述的
"精简 Windows / WinRE 里连进程都起不来（0xC0000135）"的形态。

如果我当时没做 DLL 依赖核对，就会拿着一个**进不了 WinRE 的产物**得出
"VM 内编译没问题"的结论。核对二进制内容是唯一拦住它的手段。

**教训：VM 内编译不要手打 cargo 参数。** `build-win.sh` 已经把
`+crt-static` 和三条 `LIBPATH` 封装好了，VM 侧虽然不需要那三条 `LIBPATH`
（MSVC 环境自带），但 `+crt-static` 必须显式带。

## 五、各自的坑（本轮实测）

### macOS 侧
1. **依赖宿主 SDK 副本**。`~/win-sdk-arm64` 是从 VM 复制的快照，
   Windows 更新后不会自动同步，可能悄悄漂移。需要定期从 VM 重新复制。
2. **PDB 警告刷屏**。`LNK4099` 每条都指向一个 macOS 上不存在的 Windows 路径，
   看着吓人但完全无害（上面的 `rust-lld: Cannot use debug info` 都是它）。

### VM 侧
3. **共享目录会反复掉线**。本轮编译中途再次遇到：`X:\Cargo.toml` 突然
   "does not exist"，`net use` 里还列着 `X:` 但实际不通。
   **唯一解法：`net use X: \\Mac\backupRestore /persistent:no` 重挂。**
   （`--shf-host off/on` 无效，已实测两次。）
4. **共享不同步 `.` 开头的隐藏文件**。脚本别放成 `.tmp-xxx.ps1`，
   VM 侧 `dir` 直接看不到，且计划任务会静默不执行。
5. **`set VAR=value && …` 会带入尾随空格**，报
   `failed to create directory C:\…\target \release`（空格肉眼不可见）。
   必须写 `set "VAR=value"`。
6. **长任务不要用 `start /b`**（会被 `prlctl exec` 会话回收），
   **也不要上计划任务**（本轮试过，连踩两个坑）——直接前台跑，
   增量 15 秒内就完成。

## 六、建议

**两条路径都用，按场景选：**

- **日常迭代**：VM 内编译（编完立刻实机验证，问题当天发现）。
- **客体不可用 / 只想确认能编过**：macOS 交叉编译（快一倍，不依赖 VM）。
- **发布前**：两条都跑一遍，比对产物大小与 DLL 依赖列表是否一致
  （本轮两边 14 个 DLL 完全一致，是"两条路径都没退化"的有力证据）。

**一个可以做的改进（待你拍板）**：把 VM 内编译也封装成脚本
（如在 `windows/` 下加 `build-windows-vm.ps1`，或让 `build-windows.ps1`
检测到自己运行在 VM 内时自动跳过三条 `LIBPATH`），避免下次再手滑漏
`+crt-static`。本轮那个错误就是这么来的。
