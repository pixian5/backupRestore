## 当前主路径：VM 内一条命令

```powershell
# 在 VM 的 Windows 11 里执行（源码经共享目录 X: 可见）
& X:\windows\build-windows.ps1 -Architecture arm64 -Deploy
```

一条命令完成：**构建 → 打包 → 部署 → 逐个核对 4 个 SHA-256**。
`-Deploy` 可省（只构建打包）。常用参数：

| 参数 | 作用 |
|---|---|
| `-Architecture arm64\|x64\|all` | 目标架构，默认 arm64；`all` 会产出两个包，**不能与 `-Deploy` 同用** |
| `-Deploy` | 构建后部署到包目录与运行目录并核对哈希 |
| `-CargoTargetDir` | Cargo target 目录，默认仓库内 `target` |
| `-OutputRoot` | 打包输出根目录，默认 `artifacts\windows` |
| `-DeployPackageDir` | 部署包目录，默认 `C:\Users\Public\backupRestore-package` |
| `-DeployWorkDir` | 部署运行目录，默认 `H:\brwork` |

### 部署目标与判据

| 目标 | 文件 |
|---|---|
| 包目录 `C:\Users\Public\backupRestore-package\` | `BackupRestore.exe` + `Recovery.exe` + `winpe-winpeshl.ini` |
| 运行目录 `H:\brwork\` | `BackupRestore.exe` + `Recovery.exe` |

**判据只有一条：四个文件的 SHA-256 与刚构建的成品逐个相等。**
复制成功不算数——2026-09-30 踩过「只更新包目录、运行目录 `H:\brwork` 里的
`Recovery.exe` 还是旧件」的坑，于是 WinRE 载荷被烘进旧代码，
唯一症状是镜像元数据里的 `programVersion` 偏低，静态检查看不出来。

部署前会先 `Stop-Process` 掉可能在跑的 `BackupRestore.exe` / `Recovery.exe`
并等 500ms 让句柄释放（否则复制会撞"另一个程序正在使用此文件"）。

## 跑测试

```powershell
cargo test --manifest-path X:\Cargo.toml                      # 全量
cargo test --manifest-path X:\Cargo.toml -p backuprestore-cli
```

> ⚠️ **macOS 侧 `cargo test` 的绿灯不能作为这些代码的验证依据。**
> `online_operation`、`native_gui`、`windows_prepare`、`windows_command`、
> `recovery_progress`、`pe_operation`、`boot_entry`、`recovery_fault`
> 八个模块都是 `#[cfg(windows)]`，macOS 上静默跳过，共 15696 行（占 59%）。
> 改到它们必须在 Windows 侧跑测试——macOS 抓不到的错包括类型不匹配、
> borrow 检查错误、以及 2026-10-12 全部 7 个阻断缺陷。

## macOS 交叉编译（降级为快速 sanity check）

```bash
./build-win.sh              # 只构建
./build-win.sh --deploy     # 构建 + 部署 + 核对
```

只在改 `backuprestore-core` 这类**跨平台**代码、需要快速确认"没把公共库改崩"时用。
产物经 Parallels 共享文件夹进 VM：客体侧用 UNC 路径 `\\Mac\backupRestore`
（不用盘符 `X:`，因为 `prlctl exec` 默认走 SYSTEM 账户，看不到用户会话的盘符映射）。
产物质量与 Windows 侧等同（两边均 14 个 DLL、零 CRT 外部依赖、大小差 16KB），
对比数据见
[macOS 交叉编译与 VM 内原生编译实测对比](./20261012-1640-macOS交叉编译与VM内原生编译实测对比-Fable5.md)。
**它不能替代 Windows 侧测试。**

## 静态 CRT 是硬要求

无论哪条路径，`+crt-static` 都不能漏：漏了产物会依赖 `VCRUNTIME140.dll` 与
`api-ms-win-crt-*`，进不了精简 WinRE/PE（退出码 0xC0000135）。
`build-windows.ps1` 与 `build-win.sh` 都已内置，手打裸 `cargo build` 才会踩到
（2026-10-12 实测犯过，靠核对 DLL 依赖列表才发现）。

Windows 二进制不能做成同一个”通用 exe”。本项目采用两个独立产物，当前先开发
ARM64；x64 只保留构建配置，暂不作为默认目标：

| 产物 | Rust target | 运行环境 |
|---|---|---|
| x64 | `x86_64-pc-windows-msvc` | Windows 10/11 x64 |
| ARM64 | `aarch64-pc-windows-msvc` | Windows 10/11 ARM64 |

在 Win11 ARM64 开发机上默认运行（只构建 ARM64）：

```powershell
rustup target add aarch64-pc-windows-msvc
.\windows\build-windows.ps1
```

脚本不会自动下载工具链。缺少目标时会直接停止，避免在用户网络环境中
偷偷产生大流量。需要显式构建 x64 时再运行：

```powershell
.\windows\build-windows.ps1 -Architecture arm64
.\windows\build-windows.ps1 -Architecture x64
```

源码固定通过 Parallels 共享桌面同步到 `C:\Users\x\Desktop\BackupRestore`；不要再复制到旧的
`C:\BackupRestoreBuild\src`。共享目录不适合 Rust 的临时归档操作时，可把 Cargo 输出放到
Windows 虚拟磁盘：

```powershell
.\windows\build-windows.ps1 -Architecture arm64 -CargoTargetDir C:\BackupRestoreBuild\target
```

推荐在 VM 使用浅层目录，一次明确指定 target 和输出目录：

```powershell
.\windows\build-windows.ps1 -Architecture arm64 `
  -CargoTargetDir C:\BackupRestoreBuild\target `
  -OutputRoot C:\BackupRestoreBuild\package
```

输出位于 `C:\BackupRestoreBuild\package\BackupRestore-windows-<arch>-v<VERSION>`，每个包
包含同一架构的 `BackupRestore.exe`（启动 GUI）和 `Recovery.exe`（WinRE 恢复），
以及 Rust WinRE 启动载荷、所需 MSVC runtime 和 `build-manifest.json`。x64 与 ARM64 不可混用。

正常 Windows 的任务准备、卷枚举、WIM 读取、WinRE 注入、BCD 快照和重启请求均由
`BackupRestore.exe prepare` 直接完成，不依赖 PowerShell。Recovery.exe 是 WinRE
唯一执行入口；缺少它时不会回退到批处理执行备份或还原。

> 关于"源码同步到 VM"与"Cargo target 放 VM 本地磁盘"：这两条原本是为 VM 内编译写的，
> 在宿主机交叉编译模式下不适用——宿主机编译直接在 `target/` 下产出，
> 通过 `build-win.sh --deploy` 经 UNC 路径 `\\Mac\backupRestore` 送进客体。
> 若确实需要在 VM 内临时编译，下面关于 target 目录不要放共享盘的告诫仍然有效。
