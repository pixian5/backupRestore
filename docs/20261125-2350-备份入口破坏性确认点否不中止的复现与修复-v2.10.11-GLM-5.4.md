## 一、结论先行

1. **修了一处从 2026-10-13 起就存在的缺陷**：界面「备份」入口的「破坏性确认」框问的是「…确认继续？」，给了「是 / 否」
   两个按钮，但程序里**只有三个还原入口认「否」**。备份入口点「否」照样往下走：
   - 源卷是系统盘：继续弹「需要进入恢复环境处理」选择框（后面还有一道确认，所以不会真的开始备份，但「否」被无视了）；
   - 源卷不是系统盘：**直接开始在线备份、把镜像写出来**；镜像已存在时还会追加一个索引。
2. **两种分支都在 2.10.10 的最终二进制（`65a49489…`）上实机复现**，修复后的 2.10.11（`16db638b…`）上同一个用例两项通过。
   这就是「同一条判据在旧行为下变红、新行为下变绿」。
3. **界面上「创建任务 → 备份」这条下发路径第一次有了用例**：保留下来的界面日志里，备份页签的「创建任务」被点过 12 次，
   全部停在「镜像路径为空」的引导框上。新用例 `tools/vm/gui-backup.sh` 三种模式：`cancel`（点否必须停下）、
   `online`（界面在线备份全链）、`system`（界面系统盘备份经恢复环境，**写好了但没能上机**，见第六节）。
4. **工具侧这一晚又出了九处错**（第五节），全部实测抓到并修掉。最该记住的一条：**辅助脚本回报「点击已执行」，
   不等于点到了目标程序**——有两次点击落进了你开着的「设置」窗口。
5. 产品行为在修复之后的每一次运行里都是对的。

## 二、缺陷是什么

### 2.1 代码位置

`crates/backuprestore-cli/src/native_gui/task_executor.rs`，`create_task` 里弹出「破坏性确认」之后：

```rust
// 修复前
if is_image_restore_entry(&operation) && destructive_answer != IDYES { … return; }
// 修复后
if destructive_answer != IDYES { … return; }
```

`is_image_restore_entry` 只认 `restore-existing` / `restore-data` / `create-secondary`，所以 `backup` 点「否」时这个条件为假，
流程继续往下：系统盘走「处理方式选择框 → 最终确认 → 提权准备」，非系统盘走 `run_online_operation`。

### 2.2 沿革

| 时间 | 提交 | 当时的写法 | 说明 |
|---|---|---|---|
| 2026-10-13 02:20 | `f7824e6` | `matches!(operation, "restore-existing" \| "create-secondary") && destructive_answer != IDYES` | 能查到的最早版本，备份就已经不认「否」 |
| 2026-10-14 12:55 | `6f75215` | 改成 `is_image_restore_entry(&operation) && …` | 三入口拆分时只换了写法 |
| 2026-10-23 | — | 只修了**文案**（备份的确认框不再写「目标卷将被覆盖」） | 判据没动 |
| 2026-11-02 20:44 | `3e1aa6e` | 重构搬进 `task_executor.rs`，原样保留 | 不是重构引入的 |

文档与经验库里没有任何「备份点否也继续」的既定裁定；用户指南写的是「确认后」才继续。所以定性为缺陷，不是设计。

### 2.3 为什么一直没暴露

界面驱动的脚本只点「是」（要走到后面的流程），命令行下发的准备根本不经过这个框。
`tools/gui-check/restore-confirm.sh` 那条「最后点否」的取消路径验的是**还原**入口。

## 三、怎么复现的

`tools/vm/gui-backup.sh cancel`，约 2 分钟，不建任务、不写镜像（修复后的二进制上）：

| 轮次 | 源卷 | 镜像路径（不会被写出） | 动作 | 判据 |
|---|---|---|---|---|
| 系统盘分支 | 当前系统盘（备份页签的默认源卷） | `F:\br-gui-cancel-never.wim` | 创建任务 → 确认框点「否」 | 10 秒后：没有新窗口（尤其没有处理方式选择框）；界面日志有「已取消」那一行、没有「选择框返回」；任务目录不变；镜像不存在 |
| 在线分支 | 测试卷 F（用消息直选下拉框） | `H:\BRImages\gui-cancel-never.wim` | 同上 | 界面日志有「已取消」、没有 `online started`；没有新窗口；任务不变；镜像不存在 |

两处设计说明：

- **窗口清单比前后两份**（点「创建任务」之前一份、答完之后一份），判的是「之后多出了什么窗口类」，不是数窗口个数
  （输入法自己的窗口一直在，数个数会误判）。「之后一个窗口都没有」也不算通过——主窗口必须还在。
- **界面日志只数本次驱动之后的**（界线取虚拟机自己的时钟），第一版数整份文件时把两天前的记录数了进来（上一份文档 §五 第 1 条）。

### 3.1 实机复现（二进制 2.10.10，哈希 `65a49489…`）

证据文件前缀 `gui-backup-cancel-v2.10.11-20261125-232347-*`——**前缀里的版本号是宿主侧当时的 `VERSION`**
（我已经先升了版本号），被测的是哪个二进制以日志里的 `DEPLOYED_SHA256` 为准。

| 轮次 | 读数 | 结论 |
|---|---|---|
| 系统盘分支（第 3 次，前两次相同） | 点「否」之后 `NEW_WINDOW_CLASSES_AFTER=BackupRestoreSystemDriveChoice`（窗口标题「需要进入恢复环境处理」）；`GUI_LOG_CANCELLED=0`；`GUI_LOG_SYSTEM_CHOICE_ANY=0`（脚本读日志时选择框还挂着、没答） | **缺陷复现**：`GUI_BACKUP_CANCEL_SYSTEM=FAIL` |
| 在线分支 | `GUI_LOG_ONLINE_SPLIT=1`、`GUI_LOG_ONLINE_STARTED=1`、`GUI_LOG_CANCELLED=0`；10 秒内已弹出 `#32770`「执行完成」；`H:\BRImages\gui-cancel-never.wim` 被写出（104,859,962 字节） | **缺陷复现**：`GUI_BACKUP_CANCEL_ONLINE=FAIL` |

脚本在缺陷路径上做了收拾：系统盘分支核对「取消」按钮文字后点掉选择框；在线分支结束界面程序、删掉它写出来的镜像与副档、
删掉本轮新出现的候选目录。复现留下的那个镜像已删除并核对不在（`clean-never-image`）。

## 五、工具侧这一晚的九处错

全部是上机抓到的，没有一处是看代码看出来的。

| # | 现象 | 根因 | 修法 |
|---|---|---|---|
| 1 | 复现跑到「点完否」脚本突然死了，留着一个挂着的对话框 | 我在命令外层接了一个按通用编码工作的 `cut` 查看输出，它遇到助手回传的中文（系统本地编码）报「非法字节序列」退出，管道上游的脚本被连带弄断 | 输出只落文件，查看一律 `LC_ALL=C`；新的点击函数回显前先解码 |
| 2 | 「选下拉项」的辅助脚本什么都不返回，源卷停在 C 盘 | 经 `-Extra` 传给常驻助手的整串参数**末尾是冒号**（`-Text F:`）时被弄坏，外层脚本报「参数缺值」。对照实验：末尾带冒号 3 次全失败，不带冒号、或冒号在中间都正常 | 传盘符不带冒号（`gui_select_combo` 里去掉） |
| 3 | ★★ 两轮「点击已执行」的点击**落进了「设置」窗口**（页面从「Windows 更新」跳到了「帐户」） | 你开着「设置」，新启动的界面程序停在它后面；点击辅助脚本按屏幕坐标做真实鼠标点击，不看坐标下是谁。`CLICK=OK` 只表示动作执行了 | `uiclick.ps1`：点击前把目标窗口提到最上层，再核对「这个坐标下是不是目标窗口」，不是就回报 `CLICK=COVERED`、不点 |
| 4 | 加了守卫之后点击被拒绝（`under_the_point=… class=Windows.UI.Core.CoreWindow`），界面还在「设置」后面 | 普通的「提到最上层」对非前台进程被系统悄悄拒绝 | 改成「先置顶、再取消置顶」 |
| 5 | 在线备份全链：产品跑完了，脚本却把结果框留在桌上、判了「窗口残留」 | 我写死了结果框的「确定」按钮编号是 1，实际是 2 | 从清单里读出这个框唯一的那颗按钮再点；不是恰好一颗就不点 |
| 6 | 缺陷处置路径没删掉已经写出来的镜像 | 以为在线备份会跑一阵子，其实测试卷的镜像几秒就做完并发布了 | 处置路径里一并删掉镜像与副档 |
| 7 | 复现运行的证据文件名写着 v2.10.11，被测的却是 2.10.10 | 证据前缀用的是宿主侧 `VERSION`，我先升了版本号 | 用例打印 `DEPLOYED_GUI_VERSION`（界面标题里的版本号），与宿主侧不一致时点名；文档里写明以哈希为准 |
| 8 | 离线自检一条断言失败 | 是我写的期望值不对（判读程序的输出带着原因，更有用） | 改断言 |
| 9 | `gui-data-restore.sh` 不在自检的语法检查清单里 | 上一轮收脚本时漏了 | 补进清单 |

第 3 条里「设置项没有被改动」只是运气——那两次点击一次点中了左上角的账户头像（所以跳到了「帐户」页）、一次落在空白处。
新守卫本身在第 4 条的场景里**真实变红过一次**（界面还在「设置」后面时，点击被拒绝、点名了挡在上面的窗口类）。

## 六、界面系统盘备份：写好了，没能上机

`tools/vm/gui-backup.sh system`（界面 → 创建任务 → 是 → 处理方式选「进入 Windows RE」→ 是 → 界面自己派发准备 → 重启两次）
已经写完，但**没有在任何二进制上运行过**，文档与 README 里都按「未验证」标注。原因是空间：

- 测试卷 F 所在的虚拟磁盘（`harddisk2.hdd`）在宿主机上**按需增长**：客体里 20 GiB 的零文件只占约 300 MB，
  但往 F 盘写一个约 40 GB 的系统镜像，宿主上的磁盘文件就跟着涨约 37 GiB；
- 宿主数据卷 926 GiB 已用约 94%，空闲在 49–59 GiB 之间波动。项目空间纪律是「不够先清理，不要硬跑」，
  按「镜像 × 2.5」要约 100 GiB；
- 所以用例里加了前置检查：估算镜像大小（取测试机上基线系统镜像的字节数）× 2.5 对宿主空闲、× 1.5 对测试卷空闲，
  不够直接中止、不建任务。

宿主空间的大头都是用户的东西，我没有动：`Library` 约 147 GiB、`Parallels` 约 130 GiB（三块虚拟磁盘 82 + 48 + 0.3）、
`Documents` 约 100 GiB、`Pictures` 约 91 GiB、`code` 约 84 GiB（其中两个项目的构建目录 3.1 + 6.4 GiB）、`Downloads` 约 40 GiB、
`.npm` 缓存约 18 GiB。没有本机快照，废纸篓是空的。**清不清、清什么由你决定。**
