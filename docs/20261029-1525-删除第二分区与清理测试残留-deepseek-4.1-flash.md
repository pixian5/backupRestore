## 5. 三件要说清楚的事

### 5.1 「并入 H:」做不到——Windows 只能往后扩，不能往前并

用户选了「并入 H:」，我也照此执行了，但**系统拒绝了**：

- `Get-PartitionSupportedSize -DriveLetter H` 的 `SizeMax` = 206,141,636,096 B，
  而 H: 当前就是 206,140,604,416 B —— **只多 1 MB**。
- `Resize-Partition -Size $max` 报 `Size Not Supported / The size of the extent is less than the minimum of 1MB`。
- `Update-HostStorageCache` 刷新后数值不变；改走 `diskpart` 的 `select volume H` + `extend` 同样失败。

**原因**：`T:` 在磁盘 1 的**第 2 个**位置（偏移 16,777,216），`H:` 在第 3 个（偏移 68,736,253,952），
两者之间本来就有一块 56 GiB 的空洞。T: 删掉后，未分配空间连成 68.6 GB 一片，
**但它全部位于 H: 的前面**。Windows 的「扩展卷」只能把**卷尾之后**的连续未分配空间并进来，
不支持向左（向前）合并；要向左并只能用第三方分区工具移动分区，风险高。

**现状**：这块 68.6 GB 保持未分配、空着。H: 现在已有 184.7 GiB 空闲，并不缺空间。
如需用掉它，三条路：

1. **什么都不做**（推荐，零风险）；
2. 在这块空间上**新建一个分区**——代价是多一个盘符，产品的「备份目标」卷列表里会多出一个空卷；
3. **重建 H:**（把 H: 现有 7.3 GiB 数据拷到 `F:`，删卷后按整盘重建成一个 256 GiB 分区，再拷回）——
   能达到「H: 吃掉全盘」，但要动 `H:\brwork`（产品的执行目录），风险明显高于收益。

### 5.2 差点把宿主共享目录当成本地残留删掉

`C:\Mac` 按体积统计是 **2,724.9 MB / 46 项**，排在很前面。它其实是 Parallels 的共享文件夹入口：
里面有 `backupRestore`（就是宿主机的 `/Users/x/code/backupRestore` 仓库）、`Home`、`ReadMe.url`、
`desktop.ini`。**在这台虚拟机上删它，删的是宿主机仓库里的文件。**

**教训**：这台虚拟机的 `C:\Mac`（以及任何共享挂载路径）在按体积排序的清单里会伪装成本地大目录。
清理前必须逐项核对是不是挂载点，不能只看体积。本轮已把它列进「绝不动」并跳过。

### 5.3 还留着一件同类残留（1.37 GB），第一轮没动、后来删了

`H:\brwork\tasks\173c7ffa-489b-42ea-acfc-22ac7f8f9734` 与刚删掉的 `9221c945` 是**两份独立的**旧 WinRE

## 10. ⚠️ 重大失误：我把官方 WinRE 母本删掉了（已完整恢复）

### 10.1 发生了什么

`C:\Users\Public\winre-src\Winre.wim` 是微软官方原版的 Windows 恢复环境镜像，
`docs/20261014-0020-C盘残留镜像与垃圾清查-Opus5.md` 里明确标着「**必须保留、后续测试要从它复制**」，
`经验/04-WinRE与载荷.md` 也拿它作为「官方母本」的字节级基准（它的 `winpeshl.ini` 是 53 字节的
`[LaunchApp]` + `AppPath=X:\sources\recovery\recenv.exe`）。

我在第二轮脚本里对 `C:\Users\Public` 用的是「**不在白名单就删**」这种粗暴规则，结果是它连
`AccountPictures`、`logs`、`pkg`、`winre-src` 一起被删了。`AccountPictures` 已在第三轮重建，
`winre-src` 当时判定为丢失。

### 10.2 为什么不能拿「注册位的 Winre.wim」顶替

两个文件**不是同一个东西**：

| | 官方母本 | 注册位 / 注入件 |
|---|---|---|
| 路径 | `C:\Users\Public\winre-src\Winre.wim` | `C:\Recovery\WindowsRE\Winre.wim` |
| 大小 | **709,810,082 B** | **712,111,529 B** |
| `winpeshl.ini` | 53 B，`[LaunchApp]` + `recenv.exe` | 99 B，`[LaunchApps]` + `Recovery.exe,recover-env`（LF） |
| 用途 | 「原版」基准，测「注入前后差异」的对照组 | 程序已经改过的成品，装在本机恢复位里 |

拿 712 MB 那个去冒充母本，会让「注入前后对比」这个测试**永远通过**——因为对照组和实验组
本来就是同一份注入过的文件。所以我没有那么做。

### 10.3 母本没有丢：F: 里有一份完整副本

第二系统（`F:` 盘，即 BCD 里那个 Professional 项）的同一个位置也有这份母本：
`F:\Users\Public\winre-src\Winre.wim`，**709,810,082 B**。第二轮清理只扫了 `C:` 的
`Users\Public`，`F:` 的那份幸存。

已用它恢复：

```

SHA256 src = 0E09F47DC74F90AC65FE8412372A77B322831DA6E4D06BA087FF88DA1E792AC0
```

现在 `C:\` 与 `F:\` 各一份，字节数与哈希都一致。**这个哈希（`0E09F47D…`）以前没有记录过，
补在这里，以后判断母本真伪直接比它。**

### 10.4 教训

「白名单式删除」（不在名单里就删）在**公共目录**上是错的：`C:\Users\Public` 既放系统自带的
标准子目录，也放历年人为塞进去的东西，你不可能预先列全白名单。这种目录只能**逐个点名删**，
先 `Get-ChildItem` 列出来、看清每一项是什么、再一项一项删。

代码里 `enqueue()` 第一件事就是 `fs::create_dir_all(&dir)`，读队列时也容忍目录不存在
（`ErrorKind::NotFound` 直接返回「没有待办」）。所以删掉空目录无副作用，**下次入队会自己重建**。

清完 `S:\` 只剩 `EFI\` 与 `System Volume Information\`，BCD 复核：无 `BR PE secboot`、
无 `bootsequence`、`default {current}`。

## 14. 这一轮学到的三条（已同步进 `经验/`）

1. **公共目录不做白名单式删除**，只做逐项点名删除（§10.4）。
2. **「值班」的副本救命**：母本在 `C:` 与 `F:` 各一份，删了一份还有一份。重要的、不可再生的
   参照文件值得在第二块盘上放一份备份。
3. **`Test-Path` 说「不存在」不等于不存在**：`F:\+ $_.Target }`、`H:\brwork\tasks\173c7ffa-…`
   两次都是「明明在、偏报 False」。判「不存在」要用第二种方式（`Get-ChildItem` 枚举）复核，
   或者干脆不重建路径名、直接拿枚举到的对象去删（§11.3）。
