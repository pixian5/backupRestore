## 二、P0：还原失败后不阻断——先格式化、再发现镜像不存在、最后报"还原完成"

**这是本轮最严重的发现，是一条真实的数据丢失路径。**

### 复现步骤（全部通过真实界面）

1. 测试盘 `V:` 上放两个文件：`payload.txt`、`sentinel.txt`。
2. 点「还原系统」，在产品自己的卷下拉里选 `V:`，镜像路径填一个**确实不存在**的文件 `F:\BRPE-20261005-0804\r2-definitely-missing.wim`。
3. 产品弹出「还原确认」，文案正确点名了目标与镜像：
   `确认将 F:\BRPE-20261005-0804\r2-definitely-missing.wim 还原到卷 V:？此操作将格式化目标卷，数据不可恢复！`
4. 确认。

### 实际结果

| 证据文件 | 内容 |
|---|---|
| `r2-root-format-out.txt` | `DiskPart 成功格式化该卷` —— **格式化先执行并成功** |
| `r2-logs-restore-out.txt` | `错误: 2` / `系统找不到指定的文件` —— **应用镜像确实失败** |
| `r2-missing-done.txt` | 对话框标题 **`还原完成`** |
| `r2-missing-stay.txt` | 随后弹出 **`还原完成，现在重启进入系统？`** |
| `r2-negative.txt` | `sentinel_survived=false` `payload_survived=false` `reported_success=true` |

**净效果：目标卷被清空，镜像一个字节都没写进去，界面告诉用户"还原完成"并邀请重启。** 如果目标是用户的真实系统卷，数据已不可恢复，而用户不会知道出了问题。

根因在 [`execute_pe_task_line`](../crates/backuprestore-cli/src/native_gui.rs#L7402) 返回 `()`，[`pe_restore_from_desktop`](../crates/backuprestore-cli/src/native_gui.rs#L6855) 无条件连跑 `format` → `restore` → `bcdboot`，之后无条件弹「还原完成」。此前文档把它列为"第 4 项 仍存在"，**现在有了实机证据**。

### 对照：正例还原确实有效

同一轮先做的正例（镜像真实存在）：

| 检查 | 结果 |
|---|---|
| 备份产物 | `r2-backup.wim` 索引 1，24 字节，正是 `payload.txt` 内容大小 |
| 还原后 `payload.txt` | `PE-0804-original-content`，与源一致 |
| 还原前放置的 `old-only.txt` | **已被格式化清除**（证明格式化真的发生，不是空操作） |

所以格式化与应用在正常路径上是работ的；缺的是**失败判定与阻断**。

## 三、P0：探测文件写入路径与读回路径不同源（实机复现）

ESP 上的实际文件分布：

| 文件 | 产品写入位置 | 产品读回位置 | 实际 |
|---|---|---|---|
| `find-system.txt` | `S:\find-system.txt`（8 字节，内容 `C \r\nX \r\n`） | `S:\BackupRestore\logs\find-system.txt` | **读回路径不存在** |
| `format-check.txt` | `S:\format-check.txt`（7 字节，`NOSYS`） | `S:\BackupRestore\logs\format-check.txt` | **读回路径不存在** |
| `bcdboot-check.txt` | `S:\bcdboot-check.txt`（7 字节，`NOSYS`） | `S:\BackupRestore\logs\bcdboot-check.txt` | **读回路径不存在** |
| `pe-drive.txt` | 由产品用读回结果写出 | —— | **0 字节（空）** |

连锁后果，全部实测可见：

- `find-system-drive` 读不到结果 → `pe-drive.txt` 为空 → [`resolve_drive("AUTO")`](../crates/backuprestore-cli/src/native_gui.rs#L7249) 返回**空字符串**。
- `format` 的系统卷保护（保护 2）判据恒为"非系统卷"。
- `bcdboot` 判据恒为"非系统卷"：日志实测 `bcdboot V: skipped (not a system volume)`。本例中目标确实不是系统卷，结论碰巧正确；但**同一条路径在真实系统还原时会静默跳过引导修复**。

来源是 v1.8.1 提交 `7613896`「ESP 日志迁出根目录」只迁了读取侧，命令里的 `> S:\x.txt` 重定向目标一个都没改。

## 四、P0：`mountvol` 的"无装入点"标记被当成英文固定串，中文系统上 ESP 零盘符定位必定失败

代码里有两处注释明确写着这个串不随本地化变：

- `text_parsing.rs:1028`：``（`mountvol` 打 `*** NO MOUNT POINTS ***`，固定串不随本地化变）``
- `windows_prepare.rs:1206`：```*** NO MOUNT POINTS ***` 是固定串，不随本地化变``

判据在 `text_parsing.rs:1168`：`if current.is_some() && !trimmed.contains("NO MOUNT POINTS")`。

**实测：本机中文 Windows 与中文 PE 下，`mountvol` 打的是 `*** 无装入点 ***`。**（证据：`r2-mountvol-listing.out`，以及 Windows 侧 `mountvol | findstr "***"` 的同样输出。）

因此 `esp_volume_from_listing` 永远匹配不到任何候选，[`esp_volume_path_for_task()`](../crates/backuprestore-cli/src/windows_prepare.rs#L1190) 在中文系统上**必定返回 None**。PE 内两轮都打印了：

```
[ESP] volume GUID not found; falling back to mountvol S: /S
```

影响不限于 PE：Windows 侧的「重启进入 PE」[`pe_reboot_to_pe`](../crates/backuprestore-cli/src/native_gui.rs#L4147) 也靠这个函数写 `pe-task.txt`，返回 None 即 `write_ok=false`，该入口在中文系统上无法写入任务。这是 v1.8.2「方案 A」引入的回归。

## 五、P1：命令输出用 `read_to_string` 读取，中文输出解码失败被当成"无输出"

备份这一步实测：

- `S:\BackupRestore\logs\backup-out.txt` **确实存在，142 字节**，内容是 DISM 的 GBK 成功文本（`操作成功完成。`）。
- 但同一轮的 `pe-gui-backup.txt` 记录的是：`backup V: -> F:\…\r2-backup.wim: no output`。

原因：`std::fs::read_to_string` 要求 UTF-8，中文控制台工具输出是系统代码页（GBK），解码失败返回 `Err`，分支落到"no output"。

后果：**在中文系统上，产品看不到 DISM/DiskPart 的任何输出文本**，因此也无法从输出中识别失败。项目本身已经有解码层（`text_parsing::decode_code_page` / `decode_console_bytes`，用于软硬件信息页），但 PE 任务分支没有用它。

## 六、P1：`mountvol` 退出码被当作判据，实际已挂载却判为失败

产品日志：`[ESP] mountvol S: /S FAILED with exit code 退出码 1`。

但同一轮里 `S:\format-check.txt`、`S:\find-system.txt` 等**写入成功**，说明 `S:` 实际上已经挂载成功。即 mountvol 返回 1 但操作成功。

项目自己的注释已经记录过这件事（"mountvol 返回码在实机上不可信：失败时返回 0、成功时反而返回 1"），但 [`esp_store_path_for_pe`](../crates/backuprestore-cli/src/native_gui.rs#L7352) 仍以退出码判定，失败即返回 `None`。结果是：明明能访问 ESP，产品却认为没有 ESP，`pe_task_execute` 因此报 `no config`。

## 七、顺带实测确认的事实

**PE 内盘符确实漂移。** 产品自己的卷下拉在 PE 里列出的是：

| Windows 下 | PE 内 |
|---|---|
| `T:` 5 GB | `D:` |
| `P:` 64 GB | `E:` |
| `H:` BRImages 192 GB | `F:` |
| `F:` BRIMG 350 GB | `G:` |

这直接支持"任务里保存的盘符不能作为执行期身份"这一条（历史文档第 2 项）。

**还原确认框的文案是合格的**：点名了镜像全路径与目标卷，并明确警告将格式化。问题不在确认环节，而在确认之后缺少输入预检与失败阻断。
