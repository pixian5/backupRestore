## 二、我核实过的真实问题（按严重度排序）

### ★★★ P0-1：GUI 是唯一没有自动判据的主战场

- `native_gui.rs` **11,010 行**，占全项目 **22%**，里面只有 **3 个 `#[test]`**；
- 48 个源文件里 **20 个是 `cfg(windows)`**——macOS 上编译为零信息（`build-win.sh` 只做类型检查）；
- 最近五天修的 **8 类 GUI 缺陷**（雅黑字体、字重 700→400、18 号字裁切、控件重叠、气泡不折行、气泡缺失、
  DPI 换算、按钮行坐标连带）**全部是我临时写 PowerShell 判据量出来的**；
- 这些判据现在躺在 `.test-artifacts/dpi-2679/`（已 gitignore）：**不进仓库、不进 pre-push、下次没人跑**。

**这是最贵的问题**。改一处 GUI 代码，现在没有任何自动手段告诉你「有没有把别处挤坏」——
我这轮就自己踩了两次（按钮行改顺序排布 → 压住 PE 页按钮，重叠 208×56；字号测量窗口期拿旧字体）。
**每次都要重新造仪器，而仪器不落库就等于没造。**

### ★★ P0-2：非终态任务会被烘进备份镜像（10-18 缺陷的另一半，至今未修）

两处代码对照着看就清楚了：

1. 捕获排除表（`core/src/lib.rs` `build_capture_exclusions`）明确写着：
   > 同目录的 `tasks\`（任务证据）与 `logs\` **必须留在镜像里**（证据全留，2026-10-24 拍板）。

2. 续跑检测（`cli/src/main.rs` `find_pending_boot_task`）只扫 `<exe目录>\tasks` 里的
   `stage_resumable_after_interruption`（BootRequested / RecoveryStarted / Preflight / Capturing /
   TargetErased / ImageApplied …），**完全不校验 BCD 里有没有对应的一次性启动项**。

于是：备份时若 `tasks\` 里躺着一个**非终态**任务 → 它随镜像进 WIM → 还原到新系统后，
新系统的程序在 `tasks` 目录里看到它 → **弹「上次没跑完的还原任务」**，
而那个任务的原启动项根本不存在、卷身份也对不上，**续跑必然失败**。
用户看到的是一个"幽灵任务"，还不知道该点哪个按钮。

10-18 报过这个现象（`ef71fccc` 那轮，有截图实证），当时只修了死锁那半边
（`can_abandon_before_target_write` 已把 `Capturing` 收进去），**镜像污染这半边没动**。

### ★ P1-3：RE 离线捕获链的收尾自检没有证据

10-25 的 E2 结论是「自检已齐、不补码」，依据是**在线链**（`online_operation.rs` 捕获后整档 sha256 +
sidecar + 发布前重验）。但 **RE 离线捕获链（`main.rs` 的 capture 路径）收尾是否对成品镜像做
「只读重开 + 结构校验」**，我在 10-25 的文档里没找到明确证据。坏镜像只会在还原时才炸，
而那时用户的源盘可能已经没了。**建议花 1 小时盘点，不预设结论。**

### ★ P1-4：两条旧账仍「待裁定」（不是技术问题，是需要你拍板）

| 条目 | 现状 |
|---|---|

## 三、建议路线（按复利排序，不是按工作量）

### 第一步（P0，建议立刻做）：G1 把 GUI 判据收进仓库并接进门禁

**做什么**：把 `.test-artifacts/dpi-2679/` 那套脚本整理成 `tools/gui-check/`：

| 现有脚本 | 收编后 |
|---|---|
| `overlap-all.ps1` / `fit-bottom.ps1` | 控件两两重叠、底边是否出界 |
| `dlg-fit.ps1` | 单行文字裁切 / 多行块高度 |
| `tipquery.ps1` + `tipgrab.ps1` | 气泡最大宽度、气泡本体截图 |
| `setdpi.ps1` | DPI 感知读真实 dpi（区分 100%/200%） |
| `set-combo.ps1` / `launch-gui.ps1` | 字号 × 语言矩阵驱动 |

合并成**一条命令** `tools/gui-check/run.sh`，跑
「5 个页签 × 中英 × 14/18 号 × 当前缩放」，输出一行汇总：

```
GUI_CHECK tabs=5 langs=2 sizes=2 combos=20 clipped=0 overlaps=0 tooltip_untipped=0 -> PASS
```

**接门禁**：`build-win.sh --gui-check`（默认关，避免每次部署多等几分钟）；
或 pre-push 里用环境变量 `BR_GUI_GATE=1` 开启。

**为什么排第一**：这一周所有 GUI 缺陷都是"改完看不出来"，而且**每次都要重造仪器**。
仪器进仓库之后，「改完能不能自证」从"看我勤不勤快"变成"门禁替你问"。
这是本项目唯一一处还能产生**复利**的投入。

**成本**：中（整理 + 参数化 + 汇总行，约 1 轮）；**风险**：零（不动产品代码）。

### 第二步（P0）：G2 修「非终态任务被烘进镜像」

**方案 A（治标，让已有的脏镜像不再骚扰人）**
`find_pending_boot_task` 增加一条前提：**该任务的一次性启动项必须真的存在于 BCD**
（`boot-entry.json` 里的 `loaderGuid` 枚举得到）。不存在 → 跳过（记一行日志），不弹框。

**方案 B（治本，从源头不产生）**
捕获排除表里，`tasks\<id>` **只排非终态任务**（`status.json` 的 stage 不属于 success/failed），
终态的照旧留在镜像里做证据——这样既满足「证据全留」的拍板，又不会把"半截任务"带进新系统。

**建议 A+B 都做**：A 保证存量镜像不闹，B 保证不再产生。成本小-中，风险低（都是判定逻辑，可单测）。

**验收**：① 构造一个 `Capturing` 任务 → 备份 → 检查排除表里出现该目录、成品 WIM 里没有它；
② 手工在 `tasks\` 放一个伪造的非终态任务但 BCD 无对应项 → 启动不弹框，日志有一行 skip。

### 第三步（P1，产品化收尾）

- **G3 用户手册增补**（不重写）：10-25 的 `USER-GUIDE.md` 结清于 v2.6.50，
  之后新增了工具提示、任务与证据窗口、清理工作树、失败策略四项——补这三节即可。
- **G4 GUI 失败回执里错误码是否可见**：实测一次失败路径，确认 `[BR-xxx]` 出现在界面上
  而不是只在日志（10-25 的 E5 盘点一直没做）。
- **G5 RE 离线捕获链收尾自检盘点**（P1-3，1 小时，先看再决定补不补码）。

## 五、我的判断（一句话）

> 这个项目**不缺功能，缺的是「改动的可见性」和「跨代际的自证能力」**。
> 后面所有 GUI 工作都会被同一个问题卡住：**改完怎么知道没把别处挤坏？**
> 先把仪器落库（G1），再修那两条逻辑缺陷（G2/G5），比继续加功能划算得多。
