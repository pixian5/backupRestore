# WinRE 注册机制：多系统共存形态与误判复盘

日期：2026-10-12 15:20
模型：GPT-5

## 结论先行

**每个操作系统都必须注册自己的 WinRE，不能共用。** 独立恢复分区改变的是"文件放哪"，
不改变"每系统各注册一份"这个硬约束。

## 为什么不能共用（三层证据）

### 一、注册信息写在各自系统盘，不在共享区

每个系统一份 `ReAgent.xml`，跟随自己的系统卷。实测主系统：

```xml
<OsBuildVersion path="26100.1.arm64fre.ge_release.240331-1435"/>
<WinREStaged state="1"/>
<IsAutoRepairOn state="1"/>
```

`OsBuildVersion` 把 WinRE 与**该系统的具体版本**硬绑定。

### 二、BCD 恢复项按「分区身份 + 对象 GUID」定位

实测第二系统注册后，BCD 里的 ramdisk 项：

```
[E:]\Recovery\WindowsRE\Winre.wim,{f53cce29-c359-...}   ← 分区路径形式
[E:]\Recovery\WindowsRE\Winre.wim,{bf4adf4a-c4af-...}   ← 对象 GUID 形式
[F:]\Recovery\WindowsRE\Winre.wim,{eeca24dc-bb87-...}   ← 本项目载荷盘
[C:]\Recovery\WindowsRE\Winre.wim,{f530b9e1-bc2c-...}   ← 主系统
```

共用一个 wim 文件 ≠ 能共用一个注册对象。固件靠分区身份 + GUID 区分。

### 三、本项目的载荷宿主契约（致命约束）

项目 MEMORY 里已确立的硬约束：

> WinRE 强校验「启动 ramdisk 路径 == ReAgent 注册位置」

任务要注入 `winpeshl.ini` + `Recovery.exe` + 任务专属 env 到**该系统自己的注册位**。
两个系统共用一份 = 任务 A 与任务 B 的载荷互相覆盖，这正是 09-27、10-29 那几次
"注册位被 servicing 冲掉 / 载荷串台"故障的根源。

## 当前机器的恢复对象全景（实测）

| 恢复对象 | 指向 | 服务对象 | 是否该动 |
|---|---|---|---|
| `{eeca24db-bb87…}` | `[F:]\…\Winre.wim` | BackupRestoreRE 载荷盘 | **本项目需要** |
| `{f530b9e0-bc2c…}` | `[C:]\…\Winre.wim` | 主系统 | 正常 |
| `{bf4adf49-c4af…}` | `[E:]\…\Winre.wim` | 第二系统（今天 `reagentc /enable` 新建） | 正常 |
| `{f53cce28-c359…}` | `[E:]\…\Winre.wim` | **第二系统休眠恢复** | **正常，勿删** |

**`bcdedit /enum` 列出的数量本身没有异常**，不要按"看起来多了"就清理。

## 我犯的误判（重点复盘）

### 误判一：把正常对象当成"历史残留"

我看到 `{f53cce28-c359…}` 与新对象 `{bf4adf4a-c4af…}` 指向同一个 E: 分区的同一个文件，
**仅凭 GUID 时间戳新旧**就断言前者是"历史残留"，建议用户 `bcdedit /delete`。

**查清引用者后发现完全相反**：

```
1520: inherit            {resumeloadersettings}
1521: recoverysequence   {f53cce28-c359-...}
1522: recoveryenabled    Yes
1525: filedevice         partition=E:
1527: filepath           \hiberfil.sys
1535: path               \Windows\system32\winresume.efi
1536: description        Windows Resume Application
```

它是 **`Windows Resume Application`（休眠恢复加载器）** 的恢复入口，
引用者类型是 `resumeloadersettings`，配套 `hiberfil.sys`。
**删掉会破坏第二系统的休眠恢复能力。**

**如果当时直接执行，就会造成一个"我以为在清理垃圾、实际在删功能"的破坏。**

### 误判二：上一条回答里把注册对象数量解释错

我曾说"三个恢复对象 = 两个系统各一个 + 一个遗留"，实际是BCD 层面看到 4 个 ramdisk、
底下对应 3 个真实分区（F: / C: / E:）。**观察到了现象就外推结论，没把枚举完整做完。**

### 规律（与已有教训同源）

| ❌ 做法 | ✅ 做法 |
|---|---|
| 凭 GUID 时间戳新旧判断"新旧对象" | 查清引用者类型与用途再下结论 |
| 看到"数量异常"就建议清理 | 先把完整枚举读完，确认每个都有明确归属 |
| 观察到一个现象就外推解释 | 把枚举做完再解释 |

这与 MEMORY 里已记的两条同源：
- 「照抄历史文档当当前事实」（那次是文档不可信）
- 「提假设前先查历史文档」（那次是历史不可跳过）
- 这次是**第三种形态：凭局部证据下结论**——证据本身不假，但不足以支撑结论。

## 给后续操作的红线

**任何 `bcdedit /delete` 之前必须做三步**：

1. 记录回滚基线：`bcdedit /enum {bootmgr} /v` 的 `default` / `displayorder` / `resumeobject` 三行
2. 查清待删对象的**全部引用者**：
   ```cmd
   bcdedit /enum all > C:\Windows\Temp\full.txt
   findstr /n /c:"Windows Boot Manager" /c:"Windows Boot Loader" /c:"Windows Resume Application" /c:"<待删GUID>" C:\Windows\Temp\full.txt
   ```
   再按行号读上下文，确认它是 `loader` / `resumeloader` / `recoverysequence` / `ramdisk` 哪一类
3. 判断用途：本项目载荷宿主、系统恢复入口、休眠恢复入口——**这三类都不该随意删**
