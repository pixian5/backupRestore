## 先讲三件共同背景，后面五项都绕不开它们

### 背景一：BCD 是什么，以及 `{bootmgr}` 上那几个字段

BCD（启动配置数据库）是 Windows 存放「开机时启动谁」的数据库。里面有一个特殊对象叫
**启动管理器**（记法 `{bootmgr}`），它身上有三个关键字段：

| 字段 | 作用 |
|---|---|
| `default`（默认启动项） | 开机时用户不选、倒计时结束后**启动哪一个系统** |
| `displayorder`（菜单顺序） | 启动菜单里各项的排列顺序 |
| `resumeobject`（休眠恢复对象） | 指向一个「Windows 恢复应用程序」对象；**从休眠状态唤醒时，决定该唤醒哪一套系统** |

2026-10-15 你定的规则只动了第一个：`default` 一律指向本次新还原出来的系统。这条已经落地。

### 背景二：程序有三条还原通道，改一处往往要改三处

| 通道 | 什么时候用 | 代码文件 |
|---|---|---|
| 在线通道 | 就在当前系统里执行，不重启 | `online_operation.rs` |
| 离线通道 | 重启进恢复环境后执行 | `main.rs` → `boot_menu.rs` |
| 恢复环境通道 | 在 PE/RE 里执行 | `pe_operation.rs` |

### 背景三：程序风格是「宁可不报成功，也不留下说不清的状态」

代码里大量出现「……拒绝报成功」这类硬检查。这是本项目的既有取舍，五项决策里有三项
本质上都是在这个风格和一个具体代价之间做权衡。

## 事项一：还原完成后，「休眠恢复对象」仍指向原来那套系统，要不要改成指向新系统

> 待办总账里的编号是 **A1**，被标为「最高风险」。

### 现在代码里实际发生什么

**三条通道的行为完全一致**（我逐条核对）：

1. **在线通道**（`online_operation.rs` 第 660~692 行）
   bcdboot 会把 `{bootmgr}` 的 `resumeobject` 改写成**新系统**的恢复对象；
   代码紧接着**主动把它改回还原前快照里的值**（也就是原来那套系统的恢复对象）。
   第 937~941 行还有一道终检：

   ```rust
   if cur.resume_object != old.resume_object {
       return Err(crate::err("bootmgr resume_object 未恢复为主系统，拒绝报成功"));
   }
   ```

   即：**不等于快照值就直接判任务失败**。

2. **离线通道**（`boot_menu.rs` 第 1152~1172 行）：同样是「快照里有就写回快照值，快照里没有就删掉」。

3. **恢复环境通道**（`pe_operation.rs` 第 744~762 行）：同样写回快照值；
   第 779 行的终检同样要求等于快照值。

### 于是现在的状态是

- `default`（开机进哪套）→ 指向**本次新还原出来的系统** ✅（2026-10-15 你定的规则）
- `resumeobject`（休眠唤醒哪套）→ 指向**原来那套系统** ⚠️

**两个字段指向的不是同一套系统。这就是本事项的全部由来。**

### 为什么这个字段碰不得：2026-10-14 那次事故

记录在 `docs/20261014-2030-阶段3根因纠正-resumeobject不对称与skip-format漏接-Sonnet5.md`。

当时的现象是：任务停在「引导已修复」这一步**失败，而且重试必然以同样原因再次失败**（确定性失败）。
真实根因是——快照里没有 `resumeobject` 这个字段，而 bcdboot 凭空加了一个；
恢复代码只在快照「有」该字段时才写回、从不删除，可它自己的三项联合校验又把「实时有、快照没有」
判成失配，于是永远过不去。

那份文档还留下一句关键结论：

> 删掉它还有独立的正确性价值：留着会让**休眠恢复走进第二系统**。

这句话反过来印证了这个字段的语义——**它决定休眠唤醒进哪一套系统**。

### 三个选项

| 选项 | 怎么做 | 好处 | 代价 |
|---|---|---|---|
| **一（现状）** 继续指向原来那套系统 | 什么都不用改 | 保守；不破坏原系统可能存在的休眠状态；不动一个有真实事故史的字段；三处终检一字不用改 | `default` 与 `resumeobject` 指向不同系统。若新系统休眠后再唤醒，走的是旧系统那条恢复路径 |
| **二** 让它跟着 `default` 一起改指新系统 | 改三处写入逻辑 | 和「还原完开机进新系统」在语义上完全对齐，两个字段一致 | **风险最高**：还要把三条通道里「必须等于快照值否则拒绝报成功」这道终检**整个反过来**——而这道终检正是 10-14 事故之后专门加的护栏。反掉后，再没有任何检查能发现这个字段被意外改写 |
| **三** 还原后直接删掉这个字段 | 已有部分实现（快照无此值时就走删除分支） | 不留错误指向 | 若原系统正处于休眠状态，删掉后它的休眠恢复失效（通常表现为丢弃休眠镜像、改为正常启动） |

### 我的建议：**选一（维持现状）**

理由：这个字段的语义是「休眠唤醒进哪套系统」，而休眠是**跨重启的状态**。
真正最容易出事的是「删掉或改掉一个正在被使用的休眠引用」，而不是「两个字段指向不同系统」。
选项二的代价是拆掉一条事故后专门加的护栏，收益只是语义上好看。

### 还缺一个实测事实（我没做，需要实机）

**Windows 每次进入休眠时，会不会自己重写 `resumeobject`？**

- 如果**会**：现状其实无害——用户在新系统里休眠一次，Windows 自己就把字段改对了。
- 如果**不会**：现状就有真实影响，需要重新评估。

验证方法（一次实机即可回答）：在新还原出来的系统里执行一次休眠，唤醒后回读
`{bootmgr}` 的 `resumeobject`，看它有没有变成新系统的恢复对象。

## 事项二：读到旧版方案文件时，若「原来的默认启动项」不在最终菜单里，只警告还是直接报错拒绝

> 待办总账里的编号是 **A2**（对应历史文档 0725 的 S3 边界）。

### 先说清楚：这个决策现在的影响面已经很小

`boot_menu.rs` 第 957 行有个决策函数 `decide_default`，决定还原后 `default` 写谁。它有两种策略：

| 策略 | 含义 | 什么时候会用到 |
|---|---|---|
| 指向还原目标 | 写本次新还原出来的系统 | **正常流程**（2026-10-15 你定的规则） |
| 保留原默认项 | 写还原前那个默认项 | **只有读到旧版方案文件时** |

「保留原默认项」为什么只在读旧方案时才用？因为该字段（`default_policy`）是
**v2.6.1 才引入的**（提交 `7220303`），v2.6.0 及更早保存下来的方案文件里没有这个字段，
反序列化时只能落到一个保守默认值上，于是走进这条策略。

我核对了全部调用点，确认现在**只有这一条路**会用到「保留原默认项」：

- `main.rs` 第 2577 行（离线通道）：显式设为「指向还原目标」。
- `online_operation.rs` 第 494 行（在线通道）：显式设为「指向还原目标」。
- `pe_operation.rs`（恢复环境通道）：**根本不走这个决策函数**，直接用 bcdedit 命令把
  `default` 写成新系统的 loader（第 731~742 行）。

### 具体场景

走「保留原默认项」策略时，代码会检查：**还原前那个默认启动项的编号，是否还在用户最终勾选保留的菜单项里**。

- **在** → 保留它，正常。
- **不在** → 现在的行为：打一条 `WARN` 日志（「原默认项 xxx 不在最终菜单，default 将落到还原目标」），
  然后照样落到还原目标，任务继续、正常报成功。

「不在」什么时候会发生：还原前那个默认启动项对应的系统没有被探测进菜单列表，
或者落盘的方案文件被人手工改过。

### 两个选项

| 选项 | 好处 | 代价 |
|---|---|---|
| **一（现状）** 只警告，继续走完 | 不因为一个非致命的不一致，毁掉一次已经写到一半的还原（此时镜像往往已经铺完） | 异常只留在日志里，界面上看不到 |
| **二** 升级为直接报错拒绝 | 符合「宁可不报成功也不留说不清状态」的既有风格 | 会让**所有读到旧版方案文件的任务必然失败**；而用户很可能根本不知道自己手里那份是旧版存的 |

### 我的建议：**选一（维持现状）**

这条路现在只影响旧版方案文件，为了它去让一批历史任务必然失败，不划算。
真正值得做的是把那条 `WARN` 也在界面/结果里露出来，而不是改成报错。

## 事项三：界面里把 C 盘和 S 盘写死成「系统盘」和「EFI 系统分区」

> 待办总账里的编号是 **P4**，你 2026-10-15 已选进排期，待单开一轮。

### 事实

`native_gui.rs` 第 4367~4404 行，在**「安装 PE」这个入口**的目标分区校验里，有这条判断：

```rust
let drive_char = target_drive.chars().next().unwrap_or('C');
...
if drive_char == 'C' || drive_char == 'S' || drive_char == program_drive {
    // 弹窗：「目标分区不能是系统盘、ESP 或运行本程序的卷。」
}
```

也就是把**盘符 C 直接当成「系统盘」**、把**盘符 S 直接当成「EFI 系统分区」**（装引导文件的那个小分区）。

### 为什么这样不对

- **系统盘不一定是 C**。真正的判定方式是读环境变量 `%SystemDrive%`——代码里别处就是这么做的
  （例如 `native_gui.rs` 第 1251 行）。在恢复环境里 `%SystemDrive%` 是 X:，用户也可能把 Windows 装在 D:、E:。
- **EFI 分区不一定是 S**。盘符 S 只是本项目自己的约定，代码注释里也承认这是假设：
  `text_parsing.rs` 第 1011 行和第 2161 行都写着「这个假设在 S: 被别的卷占用、或 EFI 分区挂在别的盘符时成立不了」。
  而 `DriveInfo` 结构里**已经有** `partition_type_guid` 字段（第 905 行），
  EFI 系统分区有固定的分区类型 GUID，是**可以精确判出来的**，不需要靠盘符猜。

### 实际后果（三种误判）

1. 系统盘不是 C → 装 PE 到**真正的系统盘**时**拦不住**。
2. EFI 分区不在 S → 同样**拦不住**。
3. 用户的 C: 或 S: 其实是普通数据盘 → 被**误拦**，明明可以用却不让用。

### 选项

| 选项 | 说明 |
|---|---|
| **换**（你已选进排期） | 系统盘改读 `%SystemDrive%`；EFI 分区按分区类型 GUID 判。需动界面校验 + 补实机验证（尤其恢复环境里 `%SystemDrive%` 是 X: 这一支） |
| **不换** | 上述三种误判继续存在 |

### 补充：同类的兜底写法还有三处

`native_gui.rs` 第 1679、2617、4367 行都有 `.unwrap_or('C')`——取不到盘符时默认当成 C。
建议纳入同一轮一起处理。

### 影响面

只影响**「安装 PE」这一个入口**的目标校验，不影响备份/还原主流程。

## 事项四：目标系统里缺少恢复环境注册组件时，整个任务失败还是降级放行

> 待办总账里的编号是 **P5**。

### 事实

`winre_registration.rs` 第 314~321 行，在给还原出来的系统注册 Windows 恢复环境（WinRE）之前，
先检查目标卷里有没有这两个东西：

- `Windows\System32\reagentc.exe`（恢复环境配置工具）
- `Windows\System32\config\SYSTEM`（系统注册表配置单元）

**缺任一个 → 直接返回错误「目标缺少离线注册组件」，整个任务失败，没有任何降级。**

### 问题在哪

有些镜像**本来就没有这两样**（例如纯 WinPE 的镜像），但它们照样能正常还原、正常启动。
按现在的写法，这类镜像会在**镜像已经铺完、引导已经修好之后**才因为这一步失败——
前面所有工作白做，而系统本身其实是好的。

### 代码里已经有同类问题的放行先例

`windows_prepare.rs` 第 2101~2108 行（注释里标着【P2】）处理过几乎同源的问题：
数据卷镜像本来就没有 `reagentc.exe` 和 `SYSTEM` hive，那里改成按
「**目标卷当前有没有 SYSTEM hive**」来分叉判定，不再一刀切硬拒。

### 两个选项

| 选项 | 好处 | 代价 |
|---|---|---|
| **一** 降级：缺组件时记警告、跳过注册，任务照常报成功 | 不因为一个可选能力毁掉一次已经完成的还原 | 产出的系统**没有恢复环境**，用户以后想进恢复环境修系统会进不去。必须明确告知，不能静默跳过 |
| **二（现状）** 维持硬失败 | 绝不会交付一个缺恢复环境的系统，符合既有风格 | 「白做一遍」的场景继续存在 |

### 我的建议：**倾向降级，但有两个前提**

1. **必须**在最终结果里明确告知「本次未注册恢复环境」，不能静默跳过。
2. 先实测确认一件事：**WinRE 注册失败会不会导致系统进不了桌面？**
   如果会，就不能降级——那就不是可选能力，而是必需品。

## 事项五：「还原系统到非 C 盘」和「新增第二系统」两个界面入口，实际跑的是同一条代码路径

> 待办总账里写作「『新增第二系统』标签页与 C 入口目标重叠」。

### 事实

界面上一共有六个入口：

`备份` / `还原系统到 C 盘` / `还原数据到非 C 盘` / **`还原系统到非 C 盘`** / **`新增第二系统`** / `安装 PE`

后面加粗的那两个，在 `native_gui.rs` 里的映射：

- 第 1214 行：第 4 个入口 → `restore-system-other`
- 第 1215 行：第 5 个入口 → `create-secondary`
- **第 1228 行**：`restore-system-other` 又被归一成 `create-secondary`

**也就是说：这两个入口最终执行的是同一条命令，走的同一条代码路径。**

### 但它们的界面说明写的不一样

- 第 739 行「新增第二系统」的说明：
  > 格式化另一个卷并通过 BCDBoot 添加启动项。
- 第 748 行「还原系统到非 C 盘」的说明：
  > 把完整 Windows 镜像部署到另一个分区并新增启动菜单项，还原完成后默认启动项切换为这台新系统
  > （原系统仍保留在菜单中可选）。默认在线执行（格式化目标并修复引导，不重启）；
  > 离线则重启进恢复环境完成。目标不能是当前系统盘。

两条说明的侧重点不同：一个强调「加启动项」，一个强调「部署镜像 + 默认项翻转」。

### 问题

既然是同一条代码路径，界面上放两个入口，用户会以为它们是两种不同能力。

### 三个选项

| 选项 | 说明 |
|---|---|
| **一** 合并成一个 | 建议保留「还原系统到非 C 盘」这个名字，说明用较完整的那条 |
| **二** 保留两个，但让它们真的有区别 | 例如「新增第二系统」改为**从当前运行的系统克隆**，而不是从镜像还原——这是新功能，工作量大 |
| **三** 维持现状 | 两个入口、同一路径、两条不同说明 |

### 我的建议：**先选一或三**

如果选三，至少要把两条说明文字统一，避免用户误以为是两种能力。

| 事项 | 一句话问题 | 我的建议 |
|---|---|---|
| 一 | 休眠恢复对象仍指旧系统，要不要改成指新系统 | **维持现状**（选项一）；但建议先实机测一次「休眠会不会自己重写该字段」再定 |

| 三 | 界面把 C 盘 / S 盘写死成系统盘 / EFI 分区 | **换**（你已选进排期），改用 `%SystemDrive%` + 分区类型 GUID 判定 |
| 四 | 目标缺恢复环境注册组件时，失败还是降级 | **倾向降级**，但前提是实测确认「不注册不会导致进不了桌面」，且必须在结果里明确告知 |
| 五 | 两个界面入口实为同一条代码路径 | **合并成一个**，或保留两个但统一说明文字 |

**如果你只想先定最要紧的**：事项一风险最高（涉及一个有过事故史的字段），
但它其实可以先用一次实机验证（休眠会不会自己重写）来降低不确定性；
事项三你已经排期，是纯改造、没有语义分歧，可以直接开工。
