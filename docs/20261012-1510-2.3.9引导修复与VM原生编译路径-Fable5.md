> 轮次：2.3.8 → **2.3.9**（本轮修改：引导修复集成 + 中文 bcdedit 兼容修复 + 11 项单测）

## 一、本轮做了什么

### 1.1 【引导修复】功能从"写完"到"接上"

此前 `boot_menu.rs` / `boot_menu_window.rs` 只是两个孤立模块（能编译、无调用方）。
本轮把它接进了真实恢复链：

| 接入点 | 文件 | 行为 |
|---|---|---|
| 会话准备 | `main.rs` STEP 1 之前 | 目标卷是 Windows 系统卷时 `BootMenuSession::prepare`（探测候选 + 落盘 `boot-menu-plan.json`），并 `progress.set_boot_menu()` 把会话发布给进度窗 |
| 按钮出现 | `recovery_progress.rs` | 「引导修复」按钮随会话发布而显示；会话不存在（数据卷还原）时保持隐藏，不诱导误点 |
| 编辑器 | `recovery_progress.rs` WM_COMMAND | 点按钮 `open_editor(owner, session)`，非模态窗口与进度窗**共用消息循环**，恢复线程不等待关窗 |
| 键盘通路 | `recovery_progress.rs` 消息循环 | 在 `IsDialogMessageW` 之前沿父链尝试 `boot_menu::handle_key`：Esc 关窗、列表空格勾选、Shift+↑↓ 排序、F2 改名、编辑框 Enter 保存 |
| 落盘执行 | `main.rs` BCDBoot 之前 | `session.freeze()` 冻结用户最终选择 → `boot_menu::apply()` 一次性写入 BCD，然后才跑 `bcdboot` |

### 1.2 设计前提（用户 2026-10-12 拍板）

- **无倒计时**。恢复本身要几十分钟，任何倒计时都是逼用户在不了解候选的情况下做决定。
- **第二阶段出现按钮**（STEP 1 完成后）。此时候选已探测完、目标卷还没格式化，是信息最全、破坏最小的时刻。
- **本次还原的系统必选**，其它系统默认全选。用户可取消个别系统、调整顺序、改名、设菜单秒数。
- **还原链的设计前提是无人值守**，所以默认全选即可，不需要强制交互。

### 1.3 顺带修掉的真实缺陷：中文 bcdedit 字段名

`loader_identifier_for_partition()` 原先只认英文 `path` 字段名。中文 Windows 的
`bcdedit /enum` 输出是「**路径** \\Windows\\system32\\winload\\…」——只认英文会导致
**中文机器上所有加载器都匹配不上，引导修复永远找不到候选系统**。

修复：`matches!(*k, "path" | "路径")`。由新增单测
`loader_identifier_accepts_localized_device_labels` 拦住（该测试先失败、修复后通过，
是"测试抓出真 bug"而非照实现抄测试的案例）。

同类兼容此前已存在于 `device`/`osdevice`/`设备`，但 `path` 是漏的一个。

### 1.4 单测：11 项（替换原占位测试）

原 `boot_menu::tests` 只有一个 `boot_menu_module_compiles()` 占位断言。
本轮补齐 10 项实质单测：

| 测试 | 拦住的错误 |
|---|---|
| `restore_target_cannot_be_unselected` | 必选项被取消、越界下标 panic |
| `ordering_moves_entries_within_bounds` | 首项上移/末项下移越界 |
| `rename_trims_and_rejects_unusable_names` | 空名、控制字符、超 60 字 |
| `validate_requires_exactly_one_selected_target` | 还原目标缺失/取消/出现两个 |
| `validate_rejects_incomplete_identity_and_duplicates` | 卷身份不完整、同分区重复、timeout 超 999 |
| `loader_identifier_finds_the_unique_loader` | 正常匹配、非候选分区返回 None |
| `loader_identifier_accepts_localized_device_labels` | **中文「路径」标签** |
| `loader_identifier_refuses_to_guess_between_two_loaders` | 同卷两个加载器时报错而非按顺序猜 |
| `loader_identifier_ignores_ramdisk_and_incomplete_objects` | ramdisk 选项、缺 osdevice 的对象不冒充加载器 |
| `render_marks_cursor_target_and_selection` | 渲染格式：光标 `>`、勾选 `[√]`、必选标注、序号 |

**测试数据要点**：`bcd_identifier_from_line()` 只接受标准 GUID（8-4-4-4-12，38 字符）。
第一版测试用 `{loader-1}` 这种非标准形态，三个测试假失败——**测试数据必须符合
生产解析器的真实输入形态**，否则测的是自己编的童话。

## 二、Windows VM 原生编译：历史事实核实

用户 2026-10-12 问"之前都是在 macOS 还是虚拟机内编译"，结论：

**此前全部在 macOS 交叉编译**。证据：2.3.0 及更早的构建日志里有 `/Users/x/...`
路径、`rust-lld`（macOS 的 LLVM linker）与 `aarch64-pc-windows-msvc` target 组合，
这是 macOS 侧交叉编译的特征；VM 内原生编译此前**从未跑过**。

### 2.1 为什么 VM 内原生编译更好（用户判断，成立）

- Windows 自带 Windows SDK 的 arm64 import libs，链接 msvc 最干净，
  不依赖宿主维护的 `~/win-sdk-arm64` 副本。
- 交叉编译的 linker/library 路径漂移（历史上多次构建问题）天然消失。
- 编译产物直接在目标架构机器上产生，不存在"交叉编译漏了某个 cfg"的风险。

### 2.2 VM 内编译环境（2026-10-12 实测）

| 项 | 值 |
|---|---|
| 宿主机 | MacBook (Apple Silicon) + Parallels Desktop |
| 客体 | Windows 11，版本 10.0.26200.9550（arm64） |
| rustc / cargo | 1.98.1 stable，`aarch64-pc-windows-msvc` |
| MSVC | 14.44（`vswhere` 可用） |
| Windows SDK | 10.0.26100.0 |
| 源码通道 | 宿主共享 `\\Mac\backupRestore` → 客体 `X:` |
| 构建输出 | `C:\BackupRestoreBuild\{target,package}`（**本地盘**，不放共享、不放还原目标卷） |

### 2.3 编译命令（给后续 AI 直接照抄）

```bash
# 宿主侧：先确认共享可用（VM 重启后常掉，见下）
prlctl exec 'Windows 11' cmd /c 'dir X:\crates'
# 掉了就重挂
prlctl exec 'Windows 11' cmd /c 'net use X: \\Mac\backupRestore /persistent:no'
```

```powershell
# 客体侧：后台启动，避免 prlctl exec 被前台进程卡住
$env:CARGO_NET_OFFLINE = 'true'
& X:\windows\build-windows.ps1 -Architecture arm64 `
    -CargoTargetDir C:\BackupRestoreBuild\target `
    -OutputRoot C:\BackupRestoreBuild\package
```

**踩坑记录**：

1. **共享目录 VM 重启后必掉**。表现：`net use` 里还列着 `X:`，但
   `Test-Path X:\` 为 False；`net use X: /delete` 报"找不到网络连接"（2250）。
   `--shf-host off/on` 重开共享**无效**（本轮实测两次都 False）。
   **唯一有效手段：直接 `net use X: \\Mac\backupRestore /persistent:no` 重挂。**
2. **VM 内长时编译必须用计划任务，`start "" /b` 会被回收**。
   `prlctl exec ... start "" /b powershell -File build.ps1` 起来的 cargo 会在
   `prlctl exec` 会话结束时被一起杀掉：日志只写到开头几行，进程列表里
   cargo/rustc 全消失（只剩一个无关 powershell）。而且**不报错**，极易误判成编译失败。
   可用做法（XML 导入比 `New-ScheduledTaskAction/Trigger/Settings` 组合稳，
   后者本轮报 HRESULT 0x80070002）：

   ```powershell
   # XML 里必须带 <UserId>SYSTEM</UserId>，否则报"账户名与安全标识间无任何映射"
   Register-ScheduledTask -TaskName BRBuild -Xml (Get-Content 'X:\task.xml' -Raw) -Force
   Start-ScheduledTask -TaskName BRBuild
   # 之后在宿主侧轮询 C:\BackupRestoreBuild\build.log 找 "=== DONE ===" 标记
   ```
   脚本与 XML 放共享目录 `X:\` 下，日志写客体本地盘（`C:\BackupRestoreBuild\`）。
3. **PowerShell 把 cargo 的正常输出当 error 流**（`cargo.exe : Compiling ...`），
   判断成败要看脚本自己的退出码标记，不要被 `$ErrorActionPreference` 骗了。
4. **离线构建不保证成功**。缓存里 57 个锁依赖缺 7 个（cc-1.5.1、
   find-msvc-tools-0.1.14、js-sys、4×wasm-bindgen），`CARGO_NET_OFFLINE=true`
   失败就去掉该变量联网重试。

### 2.4 部署后必须核对二进制内含新代码

沿用 AGENTS.md 既有纪律：部署后用 `findstr` 或哈希比对确认客体上跑的是新产物，
**不要凭"复制成功了"就认定**。本轮新增的可检测标记：`boot-menu-plan.json`
文件名、`引导修复候选已准备` 日志文本。
