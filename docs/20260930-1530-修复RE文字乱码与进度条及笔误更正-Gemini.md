# 20260930-1530-修复RE文字乱码与进度条及笔误更正-Gemini

## 背景与问题清单

在 WinRE 备份实机闭环验证（C: → F:\6.wim）通过后，用户审阅执行过程及界面并提出了以下三个问题/改进项：

1. **re程序内，部分文字乱码**
2. **进度条应该显示当前阶段而非总进度**
3. **【必要时代原恢复环境】是否是笔误？**

## 根因分析与技术实现

### 一、【必要时代原恢复环境】笔误修正（问题 3）

- **确认结论**：确系笔误。
- **背景说明**：该提示属于方案 D 历史阶段文本，原意为在挂载卷并准备恢复环境时，若检测到注册恢复环境曾被改动，则在捕获前将其“还原”为微软官方纯净镜像。文字录入时输入法选词误写为“代原”。
- **修复措施**：
  - `crates/backuprestore-cli/src/main.rs`：将 `STEP 1/4 准备备份环境（挂载卷、校验、必要时代原恢复环境）` 全面更正为 `STEP 1/4 准备备份环境（挂载卷、校验、必要时还原恢复环境）`。
  - `crates/backuprestore-cli/src/text_parsing.rs`：同步更正测试用例中的硬编码断言。

### 二、RE 程序内文字乱码排查与根治（问题 1）

- **根因一：DISM 未指定语言开关导致 GBK 中文被损毁**
  - 在中文 Windows / WinRE 环境中，控制台子进程（如 `dism.exe`）默认采用系统的 OEM 代码页（CP936/GBK）输出本地化字符串（例如“操作成功完成。”）。
  - 主程序的 `stream_to_log` 和进度窗口的 `refresh_from_log` 原先直接调用 `String::from_utf8_lossy(line)` 将 GBK 字节强行当作 UTF-8 解析。由于 GBK 双字节在 UTF-8 中属于非法字节序列，字符被全部替换为 Unicode 替代符 `\u{FFFD}`（在 GBK 下回显即为经典的“锟斤拷”乱码），并被送入 RE 界面详情框展示。
  - 此外，`text_parsing.rs` 中仅匹配英文状态词（如 `"The operation completed successfully"`），DISM 输出中文甚至乱码时导致状态无法匹配。
- **根因二：GDI 字体字符集默认使用西欧回退**
  - `recovery_progress.rs` 的 `create_font` 传入了 `DEFAULT_CHARSET`（1）。在极简 WinRE/PE 环境中若缺少“微软雅黑”（Microsoft YaHei），GDI 字体回退机制若选用了西欧默认字体，在渲染扩展汉字与标点符号时可能出现方块（tofu）或乱码。
- **根因三：纯标签空行污染详情区**
  - 控制台刷新时吐出的只有 `[stdout]` / `[stderr]` 标签而无具体内容的空行未被过滤，导致详情区被空白标签刷屏。

- **修复措施**：
  1. **DISM 全量追加 `/English`**：在 `main.rs` 中为所有 DISM 子进程执行参数（`Append-Image`、`Capture-Image`、`Apply-Image`、`Delete-Image`、`Get-WimInfo` 等）增加 `/English` 参数，从源头确保 DISM 输出纯 ASCII 英文，规避任何代码页与解析错配。
  2. **跨平台 Windows 编码感知解码 `decode_windows_bytes`**：
     - 在 `text_parsing.rs` 实现 `decode_windows_bytes(bytes: &[u8]) -> String`。
     - 优先尝试 `std::str::from_utf8`；若失败且在 Windows 平台下，自动调用 Windows API `MultiByteToWideChar` 依次尝试 `CP_OEMCP`（控制台代码页 936）与 `CP_ACP`（ANSI 代码页），精准转换为 UTF-16 并转回 UTF-8，彻底根除乱码。
     - 在 `stream_to_log` 写入日志前与 `recovery_progress.rs` 读取日志时均采用该函数解码。
  3. **强制 GDI 中文字符集**：将 `DEFAULT_CHARSET`（1）改为 `GB2312_CHARSET`（134），确保即使在缺少微软雅黑的 WinRE 环境下，GDI 也必须回退到中文字体（如 SimSun 宋体）。
  4. **详情区空标签过滤**：在 `classify_log_line` 中过滤掉仅为 `[stdout]` 或 `[stderr]` 的纯空白行。

### 三、进度条显示当前阶段进度而非总进度（问题 2）

- **根因分析**：
  - `recovery_progress.rs` 原先计算了 4 个步骤的综合总进度 `overall_percent`（例如第 2 步 DISM 捕获跑满 100% 时，总进度仅折算为 50%）。用户在观察进度条时，容易误以为 DISM 已跑完但进度条滞后甚至卡死。
  - 步骤在推进时，`StepTracker` 未重置 `current_percent`，导致上一步的 100% 残留到后续步骤。
- **修复措施**：
  1. **进度条直观展示阶段进度**：
     - 将进度条 `PBM_SETPOS` 的位置绑定为 `progress.current_percent.or(latest_percent).unwrap_or(0)`。
     - 当 DISM 执行捕获或还原时，DISM 百分比（1%~100%）直接驱动进度条全幅填充，完成即满条。在无内部百分比的阶段（如挂载卷、校验写入元数据等），进度条重置为 0。
  2. **步骤切换重置机制**：在 `StepTracker::feed` 中增加检测，当 `self.inner.current != previous_current` 时清空残留百分比。
  3. **文本保留双维度信息**：界面文本行继续保留“当前进度”与“总进度”的数值显示，让全局进度与微观进度一目了然。
