# 环境基线第六项：`S:` 上必须真的摸得到引导存储

> 上一轮把基线扩到 5 项。这轮补第 6 项——它守的是一个**比弹窗更难查**的失败：
> 引导文件被写到了不相干的卷上。

* * *

## 一、为什么盯 `S:`

项目里有一批地方**硬编码盘符 `S:`**：

- `bcdedit /store S:\EFI\Microsoft\Boot\BCD …`（改引导存储）
- PE 交接脚本、冒烟脚本里的 `S:\` 路径
- 各种 `_bcd*.ps1` 探针

它们全都默认「`S:` 就是 ESP（EFI System Partition，EFI 系统分区）」。

一旦这个默认不成立——ESP 换了盘符，或者 `S:` 被别的卷占走——后果不是报错，
而是 **`bcdedit` 把某个不相干卷上的文件当成引导存储去改**。
症状是「引导被改坏了，但每一步都返回成功」，排查成本远高于一个弹窗。

## 二、先把事实核对清楚（不拿「我以为」当判据）

| 事实 | 读数 |
| --- | --- |
| `S:\EFI\Microsoft\Boot\BCD` 存在 | `if exist` → `YES` |
| `S:` 指向哪个卷 | `mountvol S: /L` → `\\?\Volume{d08d796f-f082-4402-bdbb-a4a6a09ac53f}\` |
| 该卷是不是 ESP | `Get-Partition` 全表里 `S: = {d08d796f-…}` = disk0 的第 2 分区（ESP） |
| 引导管理器用的是哪个设备 | `bcdedit /enum {bootmgr}` → `device partition=S:` |

四条互相印证，`S:` 当前确实是 ESP。

## 三、判据的选择：测「脚本需要的东西」，不测它的代理

最直觉的写法是「查 `S:` 的分区类型 GUID 是不是 `c12a7328-…`（ESP 类型）」。
我没这么做，两个理由：

1. **代理不等于需求。** 脚本真正需要的是「按 `S:\` 能摸到引导存储」；
   「分区类型是 ESP」只是它的一种实现。用代理当判据，将来换个等价的挂载方式就会误报。
2. **`if exist` 用 cmd 就能问完。** 查分区类型得请 PowerShell，
   而在 `prlctl exec` 里跑 PowerShell 要处理引号/编码/`-File` 不吃 UNC 一堆坑——
   今天已经在这上面栽过好几次。

所以判据是：

```
ITEM=esp_bcd_on_s|must_exist|S:\EFI\Microsoft\Boot\BCD
```

不成立时报 `want=present got=ABSENT path=… remanual=1`。

## 四、新原语 `path_exists`：这里**不需要**哨兵

上一轮为「数子目录」发明了 `BEGIN/dir/END` 哨兵，因为 `dir /b` 在空目录时**合法地**输出为空，
与「命令没跑」分不开。

`if exist X (echo YES) else (echo NO)` 不一样：**两个分支都会打印东西**。
所以「空输出」只可能是命令没跑 → 天然无歧义，不需要哨兵。

★ 这个区别值得记住：**要不要哨兵，取决于「合法为空」是否存在**，不是看心情加。

## 五、变异：不能真去卸 `S:`

卸掉 `S:` 会动到引导存储，代价太大。所以变异做在**一份改坏路径的副本**上
（脚本本身是自包含的，拷到 `/tmp` 照样能打真实 VM）：

```
把 S:\EFI\Microsoft\Boot\BCD 改成 S:\nope\nope\BCD
→ ITEM=esp_bcd_on_s status=fail want=present got=ABSENT path=S:\nope\nope\BCD remanual=1
→ BASELINE=fail，EXIT=1
→ 再跑 ensure：EXIT=1（拒绝写回，因为「把 ESP 重新挂到 S:」属于改机器挂载状态，
   该由人判断；产品侧走的是带租约的挂载入口，不该在这儿另开一条路）
```

「YES 分支」由真实项通过来证明，「NO 分支」由这次变异来证明——两条都覆盖到了。

## 七、顺手改掉的一处措辞

原来 `BASELINE=fail` 的提示写的是「目录类需人工」——现在清单里已经有「文件类」项了，
那句话会误导。改成「标了 `remanual=1` 的项需人工」，与数据本身对齐，而不是与某一类硬绑。
