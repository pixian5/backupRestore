## 2. R1 精确根因：确认（附「为什么没重跑 PE 对照」）

**主张**：`dism /Apply-Image` 覆盖式应用到**已含 Windows 的卷**时，在 `RestoreDirMetadata`
改写 `C:\Program Files\WindowsApps\*`（owner=`TrustedInstaller`）的目录元数据被拒 →
`0x80070005` → exit 5。

**我的复核**：证据链**四段闭合**，且互相独立：

| 段 | 证据 | 位置 |
|---|---|---|
| ① 现象级对照 | 同一 PE、同一镜像、同一 DISM `10.0.28000.1`：`/ApplyDir:F:\` **100% 成功**、`/ApplyDir:C:\` **秒退 Error 5** | `20261016-1413` §2.2 |
| ② DISM 自身日志 | `RestoreDirMetadata:(2418): Access is denied` → `WIMApplyImageInternal:(939)` | 同上 |
| ③ 旁证（排除"写不了盘"） | 同目录 `md` 建子目录**成功**、`rd` **成功**；只有**改写既有受保护目录元数据**被拒 | 同上 |
| ④ 解释力检验 | 「格式化能过」被同一根因解释：受保护目录被清空 → DISM 只需**新建**（允许）而非**改写**（被拒）→ 一次性解释了 v2.6.5 以前"格式化就好、不格式化就坏"的**全部**历史现象 | `20261016-1955` §1.5 |

**为什么我没有独立重跑 PE 对照**：进 PE 需要停 VM → 改启动顺序 → **立即连发空格抢 DVD 提示窗** →
diskpart 挂 ESP → 跑 DISM 对照 → 再退出；单次成本约 15–25 分钟，且中途失败会卡在 PE。
本条的**可证伪性**已经很强（④ 的解释力是"预测型"证据：一个假设解释了此前所有零散现象），
在时间预算下我判断**收益不抵成本**，改为记录"未独立复验"这一事实，供后续按需补做。
若用户要求硬证据，`20261016-1413` §2.2 的表已给出可逐字复制的命令。

## 4. 复核发现的出入（本轮最重要的产出）

### 4.1 修正一：「GUI 每次启动都重武装 `bootsequence`」**不成立**

`20261016-2005` §3.2 与 `20261016-1955` §5 都主张：**非终态任务会让 GUI 每次启动都重武装
`bootsequence`，把机器锁在 RE 里**。

**源码事实**（`main.rs:416-441`、`461-610`）：

```rust
fn claim_boot_resume_attempt(task_dir: &Path, stage: Stage) -> Result<bool, TaskError> {
    let marker = task_dir.join(format!("boot-resume-{stage:?}.attempted"));
    match OpenOptions::new().write(true).create_new(true).open(&marker) {   // ← create_new
        Ok(..) => Ok(true),
        Err(e) if e.kind() == AlreadyExists => Ok(false),                  // ← 第二次起直接拒绝
        ...
    }
}
```

`resume_pending_boot_task()` 在 `claim` 返回 `false` 时：

```rust
"Automatic WinRE resume suppressed: stage {:?} already had its one retry; manual inspection is required"
"自动续跑已暂停；任务阶段、启动对象和恢复载荷全部保留，可使用 resume 命令重试"
return Ok(false);   // 不重启
```

→ **每个 stage 只自动续跑一次**，第二次起打日志并保留一切，**不会无限武装**。

**现场实证**：`2f8f8efb` 的 marker 文件 `boot-resume-TargetErased.attempted`（19:23，31 字节）
存在；`prepare.log` 尾部只有**一次**续跑记录：

```
[2026-10-16T11:23:05.966] Detected durable interrupted task after normal Windows startup;
                          resuming task 2f8f8efb-… operation=RestoreExisting stage=TargetErased
[2026-10-16T11:23:07.892] new boot channel: one-shot bootsequence re-armed for resumption
[2026-10-16T11:23:07.940] Restart requested to resume pending task in Windows RE
```

**我做的两次冷启动（12:07、12:11 UTC）在 `prepare.log` 里没有留下任何新记录**——
说明 `resume_pending_boot_task()` 根本没走到 `claim`（否则会打 "suppressed"）。

**正确表述应为**：
> 未终态任务在**下一次从该任务所在 workspace 启动程序**时，会被**自动续跑一次**
> （rearm + 重启进 RE）。这一次是**设计行为**，不是缺陷。真正的缺陷是：
> **该次续跑若失败，任务仍停留在非终态**，而 `abandon-task` 在擦除后拒收 → 用户没有自救出口。

### 4.2 修正二（更关键）：**自动续跑只在"任务所在 workspace 的副本"里生效**

**现场实证**：冷启动后运行的 GUI 进程路径是

```
Id : 10084
Path : C:\Users\Public\backupRestore-package\BackupRestore.exe     ← 不是 H:\brwork
```

而 `resume_pending_boot_task()` 的工作区由 **exe 自身所在目录**决定：

```rust
let workspace = executable.parent()...;      // exe 所在目录
let tasks_root = workspace.join("tasks");    // → C:\Users\Public\backupRestore-package\tasks
if !tasks_root.is_dir() { return Ok(false); }
```

该目录里只有 2 个 **9 月**的旧任务（`launcher-errors.log` 最后一条是 `2026-09-13`），
**扫不到 `H:\brwork\tasks` 里的 `2f8f8efb`** → 直接 `Ok(false)`，**不打任何日志**。

→ **这两次冷启动"正常进桌面"的真实原因是"自启副本看不见任务"，
而不是"bootsequence 已清、任务已收口"。**

**推论（潜在陷阱，务必记住）**：
> 只要换一份副本启动（例如手动双击 `H:\brwork\BackupRestore.exe`），
> 就会**再触发一次**对 `2f8f8efb` 的自动续跑 → 又进 RE。
> 换句话说：**现场"看起来干净"，是因为侥幸没从正确的那份副本启动。**

这也解释了 11:23 那次续跑是谁触发的：**只能是从 `H:\brwork` 启动的那一份**。

### 4.3 结论：B2′ 的必要性**被确认**，但理由要改

原表述「GUI 每次都重武装 → 锁死」**不准确**；准确的是：

| 项 | 修正后 |
|---|---|
| 无限循环？ | ❌ 不成立（per-stage marker 保护，只续跑一次） |
| 用户会被锁在 RE 吗？ | ⚠️ 会——但机制是「**bootsequence 未清 + 续跑失败后无人清**」，在 RE 内 `recover_env_interactive` 的 RETRYCANCEL 循环里打转；PE 通道才能救 |
| 任务会永久悬置吗？ | ✅ **会**。`validate-task` 通过、`status` 正常，但 `abandon-task` 在 `target-erased` 后拒收 → 既不能续、也不能清 |
| 现场现在安全吗？ | ⚠️ **取决于从哪份副本启动**（§4.2），不是真安全 |

### 5.2 P0：非终态任务自动收口（B2′）——**必须做，但要先定语义**

基于 §4 的修正，实现要点应是：

1. **任务侧**：续跑失败（确定性失败）时，把任务写成**终态**（新增终态标记），
   使 `resume_pending_boot_task()` 不再认为它可续跑——**从根上消除"永久悬置"**。
2. **引导侧**：终态化时**同时清 `bootsequence`**（否则等于把锁留给下一次启动）。
3. **自救出口**：给 `abandon-task` 开一条「已擦除但确定性失败」的收口入口
   （**必须同时清 `bootsequence`**）。
4. **GUI 文案**：见到「已擦除且非终止」的任务时，给明确文案 + **可执行的**收口按钮。
5. **验收**：制造一次确定性失败 → 机器能自己回 Windows → **再冷启动一次仍回 Windows** →
   **且从 `H:\brwork` 那份副本启动也不再触发续跑**（这一条是本次修正新增的验收点）。

**需要用户拍板的两点**：

- **Q1**：确定性失败后，任务应标为哪种终态？①`Failed`（保留现场供诊断，但不再续跑）；
  ②直接走 `abandon` 清理（删任务目录 + 清引导，最干净但丢诊断材料）。我倾向 ① + 提供手动清理。
- **Q2**：自动收口要不要**自动重启回 Windows**？（`recover_env_interactive` 已有连败 3 次自动逃出，
  见 v2.6.6；但那是"回系统"，不是"终结任务"。）我倾向：**自动逃出 + 标终态**，不额外加重启。

### 5.3 顺带记录的现场卫生问题

- 多副本部署（`H:\brwork` 与 `C:\Users\Public\backupRestore-package`）导致
  **"任务可见性"依赖启动副本**（§4.2）。这不是本轮引入，但**会掩盖问题**，
  建议后续在 GUI 上明确显示"当前工作区路径 + 任务数"，避免再次误判。
