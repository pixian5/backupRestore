## 1. 精确根因（★ 用户点名要落档的那一条）

### 1.1 一句话

**覆盖式应用要改写 `C:\Program Files\WindowsApps\...` 这个 MSIX 包目录的 owner/ACL，
该目录受 `TrustedInstaller` 保护 → 改写被拒 → DISM 立即整体放弃（exit 5）。**

### 1.2 DISM 自身日志（PE 内 `X:\windows\Logs\DISM\dism.log` 逐字）

```
Warning  Directory metadata: C:\Program Files\WindowsApps\Microsoft.DesktopAppInstaller_1.29.289.0_arm64__8wekyb3d8bbwe (HRESULT=0x80070005)
Error    RestoreDirMetadata:(2418): Access is denied.
Error    WIMCreateDirectory:(3216): Access is denied.
Error    RestoreDirTree:(3468): Access is denied.
Error    WIMApplyImageInternal:(939): Access is denied.
```

失败点精确到函数：**`RestoreDirMetadata`**（还原**目录元数据**），不是写文件内容。

### 1.3 该目录为什么受保护

`C:\Program Files\WindowsApps\*` 是 MSIX/Store 应用的安装根：

- **owner = `NT SERVICE\TrustedInstaller`**（不是 Administrators，也不是 SYSTEM）；
- 带 **MSIX 专用 ACL**（app-package SID、`TrustedInstaller:(I)(F)`）；
- 操作系统**只允许 TrustedInstaller 改写其 owner / Security Descriptor / ACL**，
  即便是提权管理员、即便在 PE/WinRE 里（离线亦同）。

DISM 覆盖式应用时必须把镜像里该目录的**目录元数据（owner/SD/DACL）还原到卷上**——
这一步被 OS 拒绝，DISM 不做降级（不会"跳过元数据只写文件"），直接整体报错退出。

### 1.4 旁证：不是「写不了盘」，是「改不了元数据」

PE 内实测（同一 PE、同一镜像、DISM `10.0.28000.1`）：

| 操作 | 目标 | 结果 |
|---|---|---|
| `dism /Apply-Image ... /ApplyDir:F:\`（F: 是之前写过的系统） | 空/已写卷 | **100% 成功** |
| `dism /Apply-Image ... /ApplyDir:C:\`（C: 是完整旧系统） | 系统卷 | **秒退 `Error 5 Access is denied`** |
| 在 `C:\Program Files\WindowsApps\` 下 `md` 建目录 | 受保护目录内 | **成功**（`dir` 可见） |
| 在同目录 `rd` 删除刚建的目录 | 受保护目录内 | **成功** |
| **改写**既有受保护目录的 owner/ACL | 受保护目录本体 | **被拒** |

→ **变量只剩"改写既有受保护目录的元数据"这一步**。F: 上同路径的 `WindowsApps\...`（DISM 刚写入的）
**没有**这层 TrustedInstaller 保护，所以通过。

### 1.5 为什么「格式化」能过

格式化把 C: 清空 → `WindowsApps` 等受保护目录**一并消失** →
DISM 只需**新建**目录（`WIMCreateDirectory`，允许）而非**改写既有受保护目录元数据**
（`RestoreDirMetadata`，被拒）→ V1（先格式化）成功、V2（不格式化）确定性失败。
**这解释了 v2.6.5 以前"格式化就好、不格式化就坏"的全部现象。**

### 1.6 边界（务必记住）

| 判断 | 结论 |
|---|---|
| 与 RE / 在线 / PE 环境有关吗？ | **无关**。PE 里同镜像同样失败（此前误以为"RE 特有问题"） |
| 与 DISM 版本有关吗？ | **无关**。PE 用 `10.0.28000.1` 照样失败 |
| `--skip-format` 对数据卷有效吗？ | **有效**。数据卷没有 Windows，也就没有 `WindowsApps`（`20261014-2345` 已在 T: 验证） |
| `--skip-format` 对已含 Windows 的系统卷有效吗？ | **无效、且必然失败**（本次根因） |

→ 因此：**「已含 Windows 的目标卷 + 取消格式化」= 确定性失败组合，必须准备期硬拒。**

## 2. 准备期硬拒实现（v2.6.7）

### 2.1 判据抽成纯函数（`pe_safety.rs`）

放在 `pe_safety`（`cfg(any(windows, test))`）而非 `windows_prepare`（`cfg(windows)`），
使纯判据在 macOS 上可跑单测——与 `target_is_windows_volume` 同一处理方式。

```rust
pub(crate) fn overlay_restore_on_windows_volume_error(
    target_contains_windows: bool,
    format_target: bool,
) -> Option<&'static str> {
    if target_contains_windows && !format_target {
        Some("覆盖式应用（取消格式化）不能用于已含 Windows 的目标卷：DISM 在还原 \
              Program Files\\WindowsApps 等受 TrustedInstaller 保护的目录元数据时会被拒绝 \
              (RestoreDirMetadata 0x80070005)。请勾选「格式化目标分区」，或改还原到空的数据卷。")
    } else { None }
}
```

### 2.2 四处接线

| 位置 | 文件 | 作用 |
|---|---|---|
| ① 离线 prepare **权威闸门** | `windows_prepare.rs::validate_operation_inputs`（A/B/C 全走这里） | 最终防线，挡在擦除/重启之前 |
| ② 在线系统卷还原 | `online_operation.rs::restore_to_windows_volume` | 在线通道同源拦截（进入本函数即已确认目标是 Windows 卷，故恒传 `true`） |
| ③ GUI 早期预检 | `native_gui.rs`（restore 类入口，目标 `has_windows_installation` 且复选框未勾） | 不让用户白跑一趟提权 + 重启 |
| ④ 判据纯函数 + 4 项四象限单测 | `pe_safety.rs` | 行为固化、防回归 |

> ②③共用 ①的纯函数，**避免三处文案分叉**（项目内已有 P3「文案分叉」教训）。

### 2.3 判据为何用「是否含 Windows」而非「是否活动系统卷」

任何**已含 Windows 的卷**都带 `WindowsApps` 等 TrustedInstaller 保护目录，
都会命中同一根因；用「活动系统卷」会漏掉第二系统卷（C 入口 / 新增第二系统也可能打到旧系统卷）。

### 2.4 文案（用户可见）

> 覆盖式应用（取消格式化）不能用于已含 Windows 的目标卷：DISM 在还原
> `Program Files\WindowsApps` 等受 TrustedInstaller 保护的目录元数据时会被拒绝
> (RestoreDirMetadata 0x80070005)。请勾选「格式化目标分区」，或改还原到空的数据卷。

## 4. 现场救援（把 VM 弄回 Windows）

### 4.1 触发现象

进 RE 后产品原生框报 `恢复暂未完成：invalid task: dism.exe failed with exit code: 5`。
点「取消」→ **重启又回 RE**（`bootsequence` 仍指向 RE）。

### 4.2 救援步骤（PE 通道，`prlctl exec` 在 RE 内不可用）

1. 停 VM → `--device-bootorder "cdrom0 hdd0"` → **启动后立即连续发空格 ~20s**
   抓住「Press any key to boot from CD or DVD」窗口（窗口很短，晚了就过）。
2. PE 内 `diskpart` → `list volume` → **ESP = Volume 4（FAT32，300MB，Hidden）** →
   `select volume 4` → `assign letter Z` → `exit`。
3. **清 `bootsequence`**：因花括号 `{bootmgr}` 打字注入不可靠（见 §5 教训），
   采用「**写 bat + 回读校验 + 执行**」：
   ```
   echo bcdedit /store Z:\EFI\Microsoft\Boot\BCD /deletevalue {bootmgr} bootsequence > Z:\q.bat
   echo bcdedit /store Z:\EFI\Microsoft\Boot\BCD /enum {bootmgr} >> Z:\q.bat
   type Z:\q.bat        ← 必须先回读确认两行完整（花括号没被吞）
   call Z:\q.bat        ← 执行；再 /enum 确认已无 bootsequence 行
   ```
4. 停 VM → `--device-bootorder "hdd0"` → 启动 → **回桌面**。

### 4.3 收敛核验（全部通过）

| 项 | 值 |
|---|---|
| 哨兵 `C:\BR-102220.txt` | **仍在**（13 字节，2026/10/16 10:22） |
| `vol C:` 序列号 | **`5C93-0047` 未变** |
| `bcdedit /enum {bootmgr}` | **无 `bootsequence`**，`default {current}` → C: |
| {current} | `device partition=C:`，`description 本次还原的 Windows` |
| `reagentc /info` | `Windows RE 状态: Enabled`，版号 `10.0.26100.8031` |
| 桌面 | 30~60s 回桌面，**GUI v2.6.6 正常自启**（后升 v2.6.7 复核） |

## 5. 新发现：非终态任务让 GUI 每次都重武装 `bootsequence`（B2 实机复现）

救援完成、回 Windows 后，**再重启一次又进了 RE** —— 排查结论：

- `H:\brwork\tasks\2f8f8efb-…\status.json`：`stage=target-erased, progress=35,
  error="invalid task: dism.exe failed with exit code: 5"` → **非终态任务**。
- 该任务在失败**之前**已 `rearm()` 过（`main.rs` 擦除前重武装一次性启动项），
  失败后 `bootsequence` 未清 → **GUI 一启动看到未终结任务就再次武装 → 重启又进 RE**。
- 想手动收口也不行：`abandon-task` 只在 `Prepared/BootRequested/RecoveryStarted/Preflight`
  允许，**`target-erased` 之后主动拒绝**（实测 `error: invalid task: 任务已进入…`）。
  → 用户**没有**可用的自救出口，只能走 PE 通道。

**这正是待办 B2「非终态任务自动收口」的实机复现**，且证明了它**优先级很高**：
不加自动收口，任何一次确定性失败都会把机器锁在 RE 里。

> **临时处置**：本轮救援后已清 `bootsequence` 并确认重启不再进 RE（第三次重启验证通过）。
> **建议**（待用户拍板，与 v2.6.6 的 `auto_escape_to_windows` 配套）：
> ①`recover_env_interactive` 连败 N 次自动清 `bootsequence` + 回系统 + **把任务标记为终态**
> （否则下次 GUI 启动又会武装）；②或给 `abandon-task` 开一条「已擦除但确定性失败」的
> 明确收口入口（需同时清 `bootsequence`）。

## 6. 操作教训（本轮新增，务必记）

1. **`prlctl exec` 输出经过 `iconv` 仍可能夹杂乱码**——最可靠是**让 VM 侧把输出写到
   `\\Mac\backupRestore\…` 共享盘**，宿主直接读文件（本次 CLI 验证即用此法）。
   `& echo EXITCODE=%errorlevel%` 在 `cmd /d /c` 单行里会被展开成字面 `%0%`，
   要用 `setlocal` + `call echo %%errorlevel%%`。
2. **PE 内 scancode 打字对 `{ }` 花括号不可靠**：`type_text.sh` 会把 `{bootmgr}` 打错/粘连
   （实测出现 `/tore`、`ootsequence`、`select volume4`）。
   **可靠链 = 把整条命令 `echo` 进 `.bat` → `type` 回读校验 → `call` 执行**。
3. **PE/WinRE 的 DVD 引导提示窗口很短**：必须**启动后立即连续发键**（本次连发 40 次×0.5s），
   手动"等一下再发"必错过。
4. **`--device-bootorder "cdrom0 hdd0"` 对 UEFI 不必然生效**（v2.6.6 文档已记）：
   本次靠"立即连发按键"进 PE，而非靠 bootorder 生效。
5. **`prlctl exec` 启动的 GUI 落在 Session 0，屏幕上看不到**；要在用户会话里起，
   用计划任务（`Principal -LogonType Interactive -RunLevel Highest`）——项目脚本
   `tools/win-clicker/restart-gui-h.ps1`。**本轮该脚本因 VM 会话一度不可用而失败**，
   后续可直接 `prlctl stop --kill` + `start` 重启（自启项会拉 GUI）。
6. **救援后必须"再重启一次"才算验证**：只清 `bootsequence` 不清僵尸任务，
   下次启动 GUI 又会武装（见 §5）。**验收标准 = 连续两次冷启动都正常进桌面。**
