## 零、顺序为什么这样排

此前的排序依据是静态分析的推测严重度。本轮实测把一条"推测"变成了"已复现的数据丢失"，所以顺序必须改：

1. **先堵数据丢失**（第 1 步）—— 这是唯一一条已证明会真的毁掉用户数据的路径。
2. **再修让判据失效的基础设施**（第 2 步）—— 路径不同源、本地化假设、解码层，这三条让所有保护判据恒为假。不先修它们，第 3 步的判据改了也读不到值。
3. **然后才是判据本身**（第 3 步）—— 三态化与受保护卷集合。**顺序不能颠倒**：在第 2 步完成前把 `contains("SYS")` 改成精确匹配，会让 `NOSYS` 被判成系统卷，反而对非系统卷执行 `bcdboot`，比现状更坏。
4. **最后是身份与退出码**（第 4 步）—— 影响面大但触发条件较窄。

## 第 1 步：写盘前预检 + 失败即停（归 W02 / W04 / W09）

**这一步两半缺一不可。** 只做预检挡不住"格式化成功但应用失败"；只做阻断挡不住"镜像不存在仍先格式化"。

### 1.1 写盘前统一预检闸

在第一次破坏性命令之前，对所有破坏性入口（PE 桌面、WinRE 主链、硬盘安装 PE）共用一次检查，任一不满足即拒绝、不进入格式化：

| 检查项 | 拒绝条件 | 本轮实测依据 |
|---|---|---|
| 镜像存在性 | 文件不存在 | **反例正是这一条缺失导致数据全毁** |
| 镜像可读性 | DISM `/Get-WimInfo` 失败 | 2.0.9 轮已验证损坏镜像会让 CLI 退出 1 |
| 索引存在性 | 所选索引不在真实索引集合内 | 2.0.9 轮已验证 `/Index:999` 失败 |
| **镜像与目标同卷** | 镜像所在卷 == 目标卷 | PE 桌面目前完全没查，一次误选即同时毁掉镜像与数据 |
| 容量 | 目标 < `max(required_target_size, source.partition_size)` | —— |
| 角色冲突 | 目标是 ESP / 当前 PE 载荷卷 / 工作区卷 | 按分区类型 GUID 判定，不靠盘符 |

**改动位置：** `native_gui.rs::pe_restore_from_desktop`（:6855 交互分支、:6803 自动分支）、`pe_secondary_from_desktop`（:6954 / :6902）、`main.rs::recover_windows` 的 `RestoreExisting` 分支（:2250 一带）。

**验收：** 分别注入「镜像不存在」「镜像损坏」「索引不存在」「镜像与目标同卷」「容量不足」五种输入；每种都要求**格式化调用次数为零**（用动作记录器断言，不能只断言函数返回错误），且界面显示明确拒绝原因。

### 1.2 失败即停

`execute_pe_task_line` 从返回 `()` 改为返回结构化结果。不需要新造类型，`windows_command::CmdOutcome`（:17）已经区分 `Exited / TimedOut / SpawnFailed / ExitCodeUnavailable / WaitFailed / ContainmentFailed / Skipped` 并带 `is_success()`，目前只是在 PE 分支（:7555 捕获、:7648 应用）被丢弃。

```rust
struct StepOutcome {
    action: String,              // 原始动作行
    command: Option<CmdOutcome>, // 真实命令结果；纯探测步骤为 None
    postcheck: PostCheck,        // Verified / Failed(原因) / NotApplicable / Indeterminate
}
```

**后置检查不能只看退出码：**

- `format`：回读卷状态（文件系统为 NTFS、卷可访问、卷序列号已改变）。本轮实测 DiskPart 返回 0 且确实格式化了，但「返回 0 却没操作」是已知风险。
- `restore`：DISM 退出码 + 目标根存在 + 关键路径抽查。本轮实测 DISM 明确返回 `错误: 2`，产品却没看。

**三个调用方都要改：**

| 调用方 | 现状 | 改为 |
|---|---|---|
| `pe_restore_from_desktop` 交互分支 | 三步连跑后必弹「还原完成」 | 任一步失败即停，弹失败详情（含失败步骤与原始错误），**不提供重启** |
| 同上自动点击分支 | 同上 + `exit_pe_to_windows` | 失败则留在 PE、结果落盘、不自动回 Windows |
| `pe_task_execute`（:7928 循环） | 跑完全部行，失败也 `reboot`、也改名 `.done` | 首个失败即停；**不改名 `.done`**（保留现场可续跑）、不重启；结果写明第几行失败 |

**「完成」只能由一个统一成功判定函数产出**，不许各分支自行决定。

**验收：** 注入「格式化成功但应用失败」，确认不报完成、不重启、不改名 `.done`；注入「应用成功但引导修复失败」，确认同样不报完成。

## 第 2 步：路径同源 + 本地化判据 + 解码层（归 W01 / W08）

三条必须一起改，单改任何一条都不足以让判据恢复工作。

### 2.1 探测文件写读同源

本轮实测确认 `format-check` / `bcdboot-check` / `find-system` 三组不同源；静态分析列出的配对共 17 组。

**方案：** 探测动作改用 Rust 原生 API，不再经 cmd + 中转文件——这一步同时消灭"写读不同源"和"重定向绑定"两类问题。

```rust
/// 目标卷是否为 Windows 系统卷。三态；保留错误，不把 I/O 失败折叠成"不存在"。
fn probe_system_volume(drive: char) -> SystemProbe  // System / NotSystem / Unknown
```

**实现约束：** 禁用 `Path::is_file()` / `Path::exists()`（会把权限错误、卷离线折叠成 `false`）。改用 `fs::metadata()` 并匹配 `io::ErrorKind`：`NotFound` → `NotSystem`；`PermissionDenied` 及其余一律 `Unknown`，错误码与路径进日志。

**连带要修的第三处同类缺陷：** `discover_drives()`（`windows_prepare.rs:2418`）的输出正是用户挑目标盘时看到的那张表，其中 `:2444` 用 `.is_file()` 判 SYSTEM hive（权限错误会显示成"没有 Windows"），`:2420` 只枚举 `'C'..='Z'` 有盘符的卷（无盘符的 ESP、隐藏恢复分区完全不可见）。

**仍需外部工具的命令**（DiskPart / DISM / bcdedit / bcdboot），其输出文件由一个类型化对象产出路径，写入端、解码器、回读端共用同一个对象。

### 2.2 `NO MOUNT POINTS` 改为非文本判据

**删掉两处错误注释**（`text_parsing.rs:1028`、`windows_prepare.rs:1206` 声称"固定串不随本地化变"），并把判据从解析本地化字符串改为：

- 用卷枚举 API 判断是否有挂载点（`GetVolumePathNamesForVolumeNameW` 返回空即无挂载点），**或**
- 直接按分区类型 GUID `c12a7328-f81f-11d2-ba4b-00a0c93ec93b`（EFI System Partition）+ 卷内存在 `EFI\Microsoft\Boot\BCD` 两条判据认 ESP。

后者更可靠，且与 `esp_identity_without_drive_letter` 已有的判据一致——目前只有后者真的在验，`esp_volume_path_for_task` 直接取第一个无挂载点卷，两函数的文档却声称"同一套判据"。

**验收：** 中文系统上 `esp_volume_path_for_task()` 能定位到 ESP；隐藏恢复卷排在 ESP 前、ESP 已有挂载点、`S:` 被数据卷占用、存在多个 EFI 分区时，分别选对目标或明确拒绝。

### 2.3 命令输出统一走解码层

**禁止对工具输出使用 `std::fs::read_to_string`。** 改用项目已有的 `decode_console_bytes`（UTF-16LE → 严格 UTF-8 → 系统代码页三级回退），它已经在软硬件信息页使用。

**改动位置：** `execute_pe_task_line` 内全部 `std::fs::read_to_string(...)` 读取命令输出的地方（backup-out、restore-out、format-out、bcdboot-* 等），以及 `main.rs` 的 `capture_logged`。

**验收：** 中文系统上 DISM / DiskPart 的输出能被正确读出并进入判定；跨块汉字、`\r` 原地进度不破坏解析；解析失败必须报错，不能以空集合代替未知。

## 第 3 步：探测三态与受保护卷集合（归 W01 / W02，必须在第 2 步之后）

路径与解码修好后，探测才会真正返回值，此时同批完成：

### 3.1 三态与安全默认

| 调用点 | `System` | `NotSystem` | `Unknown` |
|---|---|---|---|
| `format`（:7700 一带） | 需授权，否则拒绝 | 放行 | **拒绝**，写明 `REFUSED: system probe inconclusive` |
| `bcdboot`（:7739 一带） | 执行 | 跳过，记 `skipped: not a system volume` | **跳过并标记步骤失败**（交第 1 步阻断后续） |

删掉两处 `text.contains("SYS")`（`NOSYS` 含 `SYS`），留回归锁单测 `nosys_is_never_treated_as_system`。

### 3.2 第二系统的判据升级

`pe_secondary_from_desktop` 的两个 `format` 构造点（:6902、:6954）故意不带 `--allow-system` 来拒绝系统卷，但该保护依赖已失效的探测，所以现在**安装第二系统可以格式化当前主系统卷**。

判据不能用"含 Windows hive"（主系统卷和第二系统卷都满足），也**不能只看 BCD 默认项**（装过第二系统后默认项可能指向第二系统，此时误选真正的主系统卷会被放行）。

**改为受保护卷集合：**

```
受保护集合 = { 目标 ESP 的 BCD 里每一个 osloader 对象的 device/osdevice 所指向的卷 }
           ∪ { ESP 自身 } ∪ { 本次镜像所在卷 } ∪ { 当前 PE 载荷所在卷 }
           ∪ { 当前运行系统卷（在线路径适用；PE 下运行卷是 X:，不在此列） }
```

`--allow-system` 全局布尔取消，换成绑定稳定身份的 `DestructiveConsent`：目标 ∈ 受保护集合时必须有确认，且确认绑定的身份与本次现场解析一致。「重装第二系统到另一个 Windows 卷」靠确认保住合法性，不靠放宽判据。

**未知态分两种：** 目标**物理身份**未知一律拒绝（确认无从绑定）；**受保护角色分类**未知在有身份绑定确认时放行并告警（角色分类只用于拦非预期目标）。

**验收：** 第二系统目标为空盘、为旧的第二系统卷、误选主系统卷三种情形分别为允许 / 需确认 / 拒绝；`SYS`、`NOSYS`、空输出、探测失败四种严格区分。

## 第 4 步：现场身份与退出码（归 W01 / W08）

### 4.1 盘符与编号不作执行期身份

本轮实测 PE 内四个卷的盘符全部漂移（`T:`→`D:`、`P:`→`E:`、`H:`→`F:`、`F:`→`G:`）。

同时 `format_target_partition`（`main.rs:2537`）把任务里持久化的 `disk_number` / `partition_number` 直接写进 DiskPart 脚本，而 `verify_partition_identity_after_format`（:2472）是按**盘符**查身份比 GUID——**两者认的不是同一个对象**，编号漂移导致格错分区时复验反而通过。

**改为以分区 GUID 为锚现场派生：** 枚举卷（含无盘符的）→ `volume_identity_at_path`（`windows_prepare.rs:1048`，返回含现场磁盘号与分区号的完整身份）→ 匹配 `partition_guid` → 用现场编号生成 DiskPart 脚本；零匹配 / 多匹配 / 几何不符一律拒绝。格式化后的复验用同一个解析结果，而不是重新按盘符查。

**这一项必须与第 1 步的预检闸同批发布**：闸在前面按 GUID 查了身份，真正下刀的命令却按旧编号选分区，等于闸没绑住写入动作。

### 4.2 退出码不可信时不作判据

`mountvol` 返回 1 但实际挂载成功（本轮实测）。`esp_store_path_for_pe`（:7352）改为**回读实际结果**（检查目标路径是否可访问），不以退出码判定。

同理，所有"退出码 0 即成功"的地方要补后置回读。
