## 1. 高危

### H1 · `select_drive` 漏了「无过滤视图」分支 → A 入口可把系统镜像写到任意非系统盘 ✅已验证

**位置**：`native_gui.rs:2472-2489`（`select_drive`）、调用点 `2067`、闸门 `6640`、combo 禁用 `1487`

**根因**：v2.6.13 引入 `target_combo_indices()` 视图后，`select_drive` 的 target 分支写成：

```rust
let position = if control == state.controls.target {
    target_combo_indices(state).as_deref().and_then(|view| { … })   // ← None 时整段短路
} else { …恒等映射… };
if let Some(position) = position { SendMessageW(…CB_SETCURSEL…) }   // None → 什么都不做
```

`target_combo_indices()` **只在 `create-secondary` 返回 Some**，其余入口（含 A）返回 `None`
→ `position` 恒为 `None` → **`CB_SETCURSEL` 从不发出**。基线 `e04fa92` 的 `select_drive`
是恒等映射、对所有控件有效，这是一次**静默回归**。

**失败场景**（完整链路，每步都已核对）：
1. 用户在 B／备份／安装PE tab 把目标选成 D: 或 F:（这些 tab 是**全量枚举**）；
2. 点「还原系统到 C 盘」→ `select_operation` 调 `select_drive(target, "C")` → **空转**；
3. 同处的重填校验 `target_combo_expected_count(state) != CB_GETCOUNT`：A 期望 `drives.len()`，
   实际也是 `drives.len()`（B 本就是全量）→ **相等，不重填**；
4. 目标 combo 停留在 D:/F:，并被 `EnableWindow(..., 0)` **禁用**，用户改不动；
   而标签写「目标卷（当前系统盘 C:）」、详情框写「锁定为当前正在运行的系统盘」——**界面在说谎**；
5. `create_task` 的 A 分支 `source_drive = target_drive`（都是 D:）；
6. 系统盘闸门（`6640`）只匹配 `restore-data | create-secondary`，**A（`restore-existing`）不在内**；
7. `windows_prepare` 对 `RestoreExisting` 只要求 `source == target`（满足），
   P0 安全闸只对 `CreateSecondary` 生效（不适用）；
8. → 提权 → 重启进 PE/RE → **diskpart 格式化 D:/F:** → 写入系统镜像 → 修引导。

**唯一残留拦截**：破坏性确认框里那行「目标卷：D:」。用户刚看到界面说"当前系统盘 C:"，
极可能直接点是。

**修法**（两层都要）：
- `select_drive` 的 target 分支补 None 分支，退回恒等映射；
- A 的 `create_task` 加硬闸：`target_drive != active_system_letter()` 即拒绝
  （不能只靠 UI 自动选中——本次正是 UI 自动选中失效）。

### H2 · 状态机缺 `(RecoveryComplete, Failed)` 边 → 自动逃出第②步必然失败，任务永久悬置 ✅已验证

**位置**：`core/src/lib.rs:111-139`（`can_transition_to`）、`1365-1376`（`write_failure`）、
`main.rs:1519-1538`（`auto_escape_to_windows` 第②步）、`874-886`（可续跑集）

**根因**：`can_transition_to` 里有 `(RecoveryComplete, Success)`，**没有 `(RecoveryComplete, Failed)`**。
而 `write_failure` 第一行就是 `if !task.status.can_transition_to(Stage::Failed) { return Err(…) }`。

**失败场景**：任务走到 `RecoveryComplete`（STEP 4 清理阶段）后失败 → 连败达阈值触发 auto-escape →
第①步 disarm 成功 → 第②步 `write_failure` 返回 `Err("cannot fail task from RecoveryComplete")`，
代码只 `append_log` 记一行 → **任务仍停在 `RecoveryComplete`**。而 `RecoveryComplete` 仍在
`stage_resumable_after_interruption()` 里 → 下次启动 `find_pending_boot_task` 再次发现它 →
再次提示重启 → 又失败 → 又逃不出。这正是 `main.rs:1512-1518` 注释声称要避免的
「任务永久悬置、用户仍无自救出口」，且日志里不会出现注释承诺的 `task marked terminal (Failed)`。

**修法**：在 `can_transition_to` 补 `(RecoveryComplete, Failed)` 边（RecoveryComplete 是清理阶段，
失败应允许收口成终态以保留现场）。

## 2. 中危

### M1 · 跨阶段总重试计数在重启前自增，准备工作失败不回滚 ✅已验证

**位置**：`main.rs::resume_pending_now()`

顺序：`allow_total_attempt` 检查 → `claim_boot_resume_attempt`（per-stage）→ 6 个产物存在性检查
→ **`bump_total_attempt()`（计数 +1 落盘）** → `boot_entry::read()` → `boot_entry::rearm()`
→ `shutdown.exe /r /t 0`。后三步失败时都只 `release_boot_resume_attempt` 释放 per-stage 标记，
**总计数不回滚**。

**后果**：`rearm`/`shutdown` 连续失败 3 次（ESP 临时不可达、BCD 被并发改、shutdown 被策略拒绝），
机器**一次都没重启**，但 `boot-resume-total.count` 已到 3 → 自动续跑被**永久关闭**。
总闸的设计目标是防「阶段推进式反复重启」，实际变成「尝试次数上限」，且日志只写"已达总上限"，
看不出从未重启过。

**修法**：把 `bump_total_attempt` 移到 `run_output_logged("shutdown.exe", …)` 成功**之后**；
或在两个失败分支里把计数减回去。

### M2 · combo 重填用「新视图」读「旧内容」，目标字母被静默移位 ✅已验证

**位置**：`native_gui.rs:2060` / `2090-2102`

`state.operation_index = index` 在函数**最前面**就更新了，而 `keep = selected_drive_letter(...)`
在后面才算——此时 combo 里装的还是**上一个入口**的内容，`selected_drive_letter` 却按**新入口**
的视图解释索引。

**场景**：C→A。C 视图（排除系统盘）= [D:, E:, F:]，用户选中 F:（combo idx 2）；
切到 A 后视图变恒等，`selected_drive_letter` 返回 `drives[2]` = **E:**（drives = [C:,D:,E:,F:]）
→ `set_drive_items([None,None,Some("E:"))` 把目标静默换成 E:。反向 A/B/PE→C 时选中项越界还会
落回 position 0。

**附带**：`set_drive_items([None, None, keep])` 的第一个 `None` 会把**备份 tab 的源卷选择**
重置为 index 0。

**修法**：在更新 `operation_index` **之前**用旧视图取 `keep`；或重填时显式传「保持源卷」。

### M3 · `loader_identifier_for_partition` 同分区多 loader 直接 Err，且发生在镜像已应用之后 ✅已验证

**位置**：`boot_menu.rs:538-540`，调用点 `main.rs:3529`（`assert_boot_default_points_at_target`）

```rust
if found.len() > 1 { return Err(crate::err("同一系统分区有多个引导项，拒绝猜测")); }
```

调用处是 `?` 直接中断。**场景**：BCD 里同一分区残留两个 loader（上次还原留下、或用户手动加过）
→ bcdboot 成功后、**镜像已应用、目标卷已格式化之后**才失败 → 任务停 `ImageApplied`，
重试同样失败，3 次后 auto-escape。旧实现 `assert_boot_default_preserved` 不做全枚举，没有这条失败路径——
这是 v2.6.1 起新增的失败面。

**修法**：降级——取 `default` 当前指向的那个 loader 并记 WARN，而不是拒绝。

### M4 · 「暂停总上限」名不副实：每次调用都新建 deadline ✅已验证

**位置**：`recovery_progress.rs:231-232`（`wait_if_paused`）

```rust
let deadline = (limit_secs > 0).then(|| Instant::now() + Duration::from_secs(limit_secs));
```

`wait_if_paused` 在 STEP 2/4、STEP 3/4 等多点被调用（`main.rs:3402`、`3439`），
**每次调用都新建一个完整时长的 deadline**。日志文案写的是「暂停**总**上限 N 秒」，
实际是「**每次暂停** N 秒」。反复「暂停→继续」可无限累积总暂停时间，与承诺的语义不符。

**修法**：把 deadline 存进 `ProgressShared`（首次暂停时设定、续跑不重置），或改名/改文案为「单次」。

### M5 · BCD 回退在窗口线程持锁跑 bcdedit，进度窗「未响应」✅已验证

**位置**：`recovery_progress.rs:1332-1333`

```rust
let guard = (*shared_ptr).bcd_rollback.lock().unwrap();
let log_path = (*shared_ptr).log_path.lock().unwrap().clone();
match guard.as_ref() { Some(action) => match action() { … } }   // ← 整段在锁内
```

`action()` 内部挂 ESP + 跑 bcdedit，可能数十秒。窗口消息循环停转 → 进度窗「未响应」、定时器停更；
同时主恢复线程若走到 `set_bcd_rollback`（`275`）会阻塞在同一把锁上。
**不是死锁**（无 AB-BA：`log_path` 锁只被窗口线程取，主线程 `append_log` 不走它），但双双停顿。

**修法**：把闭包丢到工作线程执行，按钮先置灰；或至少 `let action = guard.clone()` 后**释放锁**再执行。

## 4. 设计观察（非缺陷，做得对的地方）

1. **`decide_default` 纯函数化**（`boot_menu.rs:911`）：把 default 归属收敛成唯一纯函数、可在 macOS 单测——这正是 2026-10-13「default 静默漂移到半成品系统」事故的决策点，现在有回归护栏。
2. **`assert_boot_default_points_at_target`**（`main.rs:4078`）是「回读→自愈→再回读」的正确形状。
3. **`dism_timeout` 默认 0（不限制）** 而非固定秒数：58GB 镜像在机械盘上跑几十分钟是正常的，固定超时会「误杀合法还原」，比挂死更糟。且 `init_process_env_from_settings` 修掉了「ini 配置对在线/安装PE 两条路静默不生效」的真实缺口（`plan_env_value` 抽成纯函数：显式优先于文件、0 不写）。
4. **`online_log::resolve_dir`** 把现场从 `%TEMP%` 搬到 `<exe>\logs\`，且**刻意不做旧目录清理**（删文件可能误伤并发实例）——比「自动清理」稳妥。
5. **`boot_entry::delete_best_effort`** 给三处补偿删除补上日志，修好了「补偿路径无声失败 → 事后无法判断孤儿 BCD 对象是不是这里漏的」这个排查盲区。
6. **`pe_operation` 去掉 bcdboot 的 `/d`** 与 v2.6.1 起的 default 规则（指向本次还原的系统）一致，注释点明了冲突原因。
7. **`winre_registration` 降级边界划得准**：`Preflight::Skip` 在任何注册写入之前返回；身份不符、ESP 与活动 BCD 加载器不一致等安全闸门仍硬失败；`Skipped` 原因既进任务日志又在结尾复述。
8. **`failure_policy` 的阈值/action 容错解析**：坏值静默回退默认（绝不让恢复环境起不来），但 `parse_threshold` 对用户显式输入严格（拒绝 `+3`/`3.0`/全角）——两种口径分得清。

**根因建议**（子审 B 提出，主审认同）：`target_combo_indices` / `select_drive` / `set_drive_items`
三者的索引换算全是**可用假 `drives` 向量单测的纯逻辑**（只有 `SendMessageW` 是 unsafe），
但目前 `p4_precise_drive_tests` 完全没覆盖这条路径——这正是 H1、M2 能静默上线的原因。
补一组纯函数单测（构造假 drives + 假视图，断言「界面选中 X → 实际取到 X」）可以一次性锁住这类回归。
