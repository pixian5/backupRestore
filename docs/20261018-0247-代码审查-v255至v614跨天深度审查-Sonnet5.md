## 1. 中危

### M1 · 跨阶段总重试计数在重启前自增，准备工作失败不回滚

**位置**：`crates/backuprestore-cli/src/main.rs`，`resume_pending_now()`

**执行顺序**（按当前代码行号摘录）：

```
allow_total_attempt(attempts, MAX) 检查        ← 读计数
claim_boot_resume_attempt(per-stage)          ← 占 per-stage 标记
产物存在性检查（6 个文件）                     ← 缺则 release + return
bump_total_attempt()  ← 计数 +1 并落盘
boot_entry::read()   ← 无记录则 release + return（计数已 +1，未回退）
boot_entry::rearm()  ← 失败则 release + return（计数已 +1，未回退）
shutdown.exe /r /t 0 ← 失败则 release + return Err（计数已 +1，未回退）
```

**失败场景**：`rearm` 或 `shutdown` 连续失败 3 次（例如 ESP 临时不可达、BCD 条目被并发修改、
`shutdown.exe` 因权限/策略失败），机器**一次都没重启**，但 `boot-resume-total.count` 已到 3。
此后 `allow_total_attempt` 恒为 false，**自动续跑被永久关闭**，只能靠用户手动 `resume` 或
顶栏「取消待重启任务」。

**为什么是缺陷**：这道总闸的设计目标是防「阶段推进式地被反复重启」（每阶段推进计数归零，
8 个阶段最多重启 8 轮）。但准备工作失败并不产生重启，却消耗了重启预算——把「重启次数上限」
变成了「尝试次数上限」，且**静默**（日志只写"已达总上限"，看不出从未重启过）。

**修法**（二选一）：
- 把 `bump_total_attempt` 移到 `run_output_logged("shutdown.exe", ...)` 返回成功**之后**；
- 或在 `rearm` 失败 / `shutdown` 失败两个分支里，把计数减回去再 `release_boot_resume_attempt`。

## 2. 低危

### L1 · `resolve_menu_name_collision` 的兜底返回撞名值，与自身注释承诺相反

**位置**：`crates/backuprestore-cli/src/boot_menu.rs:186-200`

函数文档（第 170 行）写「**保证绝不返回重名**」。但 100 次尝试全部撞名后，第 199 行
`return trimmed.chars().take(NAME_MAX_CHARS).collect();` 返回的是**原始候选名本身**
——它正是撞名的那一个。

**后果**：`BootMenuPlan::validate()`（第 138-145 行）会因「启动菜单出现同名项」报错，
整条引导修复链失败。此时目标卷**已格式化、镜像已应用**，失败代价极高。

**触发条件**：需要 BCD 里同时存在 100 个与用户输入同名、或与生成的 `-年月日时分秒`/`-序号`
后缀同名的条目。实际概率极低（`attempt=2..99` 带 `-2`..`-99` 序号，正常环境不可能有 98 个同名），
但**兜底方向错了**：宁可返回一个必然唯一的名字（如追加 UUID 片段），也不该返回必然失败的名字。

**修法**：兜底改为追加一段稳定唯一串，例如
`format!("{}-{}", base, uuid::Uuid::new_v4().simple())` 截断到 `NAME_MAX_CHARS`。

### L2 · PE/RE 日志镜像探测在多块可写卷上留下空目录

**位置**：`crates/backuprestore-cli/src/session_log.rs`，`probe_mirror()`

循环 `for letter in 'C'..='Z'`，对每个 `root.is_dir()` 的盘符都执行
`fs::create_dir_all(&dir)`，再 `fs::write(dir.join(".write-probe"))` 判可写。
`pick_mirror_root` 只取**第一个**可写的，其余已创建的 `X:\BackupRestore-logs\<pid>-<纳秒>\`
**全部留在盘上**（只删了 `.write-probe` 文件）。

**后果**：一台有 C:/D:/E:/F:/H: 的机器，每次进 PE/RE 都会在 5 块盘各留一个空目录。
功能无影响、无数据风险，但排障时磁盘上多出一批来源不明的目录，观感差且会累积。

**修法**：先用根级探针文件（`{letter}:\.br-write-probe`）判断可写性，只对**最终选中**的卷
`create_dir_all`；或在 `pick_mirror_root` 之后把未选中的目录删掉。

### L3 · v2.6.13 新增 3 处 `position as usize` 无操作强转（clippy 净增 2）

**位置**：`crates/backuprestore-cli/src/native_gui.rs:2468`、`2487`、`4737`

`position` / `pos` 本身已是 `usize`，`as usize` 是 no-op。v2.6.12 基线 16 个 clippy 警告，
v2.6.13 起变 18 个，新增的全是这一类（另有一处是既有的）。

**后果**：不影响行为；但推高警告数，且项目若改用 `-D warnings` 会直接构建失败。

**修法**：删掉这三处 `as usize`。

### L4 · `require_administrator` 把「日志不可写」误报成「需要管理员权限」

**位置**：`crates/backuprestore-cli/src/windows_prepare.rs`，`require_administrator(log: &Path)`

新实现：
```rust
match capture_logged("fltmc.exe", &[], log) {
    Ok(_) => Ok(()),
    Err(error) => { let _ = append_log(...); Err(err("administrator elevation is required")) }
}
```
而 `capture_logged` 的第一步就是 `append_log(log, "capturing fltmc.exe ...")?`——
**日志写不进去时它也返回 `Err`**。于是「`<exe>\logs` 不可写」会被报成「需要管理员权限」，
把用户引向错误方向（实际要提权也解决不了目录不可写的问题）。

**后果**：错误信息误导。真实触发概率低（提权后通常能写程序目录），但方向错了。

**修法**：先 `fltmc` 跑完再写日志（或用 `run_output_logged` 把「日志失败」与「命令失败」分开），
只在 `fltmc` 真失败时提权报错。

### L5 · `CONTAINMENT_FAILED` 是进程级永久锁，GUI 长会话被一次失败永久污染

**位置**：`crates/backuprestore-cli/src/windows_command.rs:14`、`294-304`

`stop_tree()` 在 `TerminateJobObject` 后若无法确认进程数归零，就
`CONTAINMENT_FAILED.store(true)`；此后**本进程内所有** `run_line()` 立即返回
`ContainmentFailed`，永不重置。

**后果**：GUI 是长驻进程，一次 DISM 遏制失败（例如卷 I/O 挂起导致进程退不进内核）会让
**后续所有外部命令**（含与此无关的 `wim-info`、`bcdedit`）全部失败，用户必须重启程序。
文案是「请检查后台进程或重启**系统**」，实际重启程序即可，措辞也偏重。

**评价**：这是**有意的 fail-closed 设计**（注释明说「禁止本实例再次发起外部写操作」），
方向正确。列为低危只是因为影响面比注释描述的大（进程级而非操作级），且文案可更准确。

**建议**：文案改为「…请检查后台进程或重启本程序」；若希望缩小影响面，可考虑在
`Engine`/操作边界而非进程全局设锁。

## 3. 设计观察（非缺陷，但值得知道）

1. **`decide_default` 纯函数化做得对**。`boot_menu.rs:911` 把 default 归属收敛成唯一纯函数、
   可在 macOS 单测——这正是 2026-10-13「default 静默漂移到半成品系统」事故的决策点，
   现在有回归护栏了。`assert_boot_default_points_at_target`（`main.rs:4078`）也是
   「回读→自愈→再回读」的正确形状。
2. **`dism_timeout` 默认值是 0（不限制）而非某个固定秒数**——注释解释得清楚：
   58GB 镜像在机械盘上跑几十分钟是正常的，固定超时会「误杀合法还原」，比挂死更糟。
   这个取舍是对的。且 `init_process_env_from_settings` 修掉了「ini 配置对在线/安装PE 两条路
   静默不生效」的真实缺口（`plan_env_value` 抽成纯函数，显式优先于文件、0 不写）。
3. **`online_log::resolve_dir` 把现场从 `%TEMP%` 搬到 `<exe>\logs\`**，理由是磁盘清理或
   「还原掉含 TEMP 的卷」会连现场一起删。合理；且**刻意不做旧目录清理**的判断
   （删文件可能误伤并发实例）也比「自动清理」稳妥。
4. **`boot_entry::delete_best_effort`** 把三处 `let _ = bcd(&["/delete"...])` 换成带日志的版本，
   修好了「补偿路径无声失败 → 事后无法判断孤儿 BCD 对象是不是这里漏的」这个排查盲区。
5. **`pe_operation` 去掉 bcdboot 的 `/d`** 与 v2.6.1 起的 default 规则（指向本次还原的系统）
   一致，且注释点明了「`/d` 让 default 留在原主系统」与现规则的冲突。
6. **`winre_registration` 降级边界划得准**：`Preflight::Skip` 在**任何注册写入之前**返回；
   身份不符、ESP 与活动 BCD 加载器不一致等安全闸门仍硬失败；`Skipped` 原因既进任务日志、
   又在结尾复述。符合用户裁定范围。
