# 任务证据管理窗口（C 项）详细设计

**日期**：2026-10-27 02:20 ｜ **基线版本**：2.6.64（HEAD `ca6c1ab`）
**状态**：设计稿，**未改任何代码**
**一句话**：把 `H:\brwork\tasks` 下 50 个任务从「只能进资源管理器手翻」变成「GUI 里可列、可看、可安全清理」，
且不引入项目从未用过的控件类。

## 1. 先把缺口量化（实测，不是估）

| 项 | 实测值 | 怎么测的 |
|---|---|---|
| 任务目录数 | **50** | `dir /b /ad H:\brwork\tasks` |
| 文件总数 | **686** | `dir /s` |
| 总占用 | **89 MB**（93,293,805 字节） | `dir /s` 汇总行 |
| 单任务典型构成 | `task.json` / `status.json` / `manifest.json` / `boot-entry.json` / `prepare.log` / `recovery.log` / `bcd-before-*` / `status.env` | 抄自 `f785b473-…` |
| GUI 里的任务/证据入口 | **0 处** | `control-baseline.txt` 148 条里 grep `evidence\|task\|cleanup` 无命中 |

**★ 一个必须纠正的数字**：我一开始把 `dir` 末尾的 `158,126,981,120` 读成「任务占用 158 GB」，
差点把这件事说成「空间危机」。**那是 H: 的可用空间**（这条坑在项目记忆里写着，我还是先信了第一眼）。
真实占用 **89 MB**——所以 C 项的价值是**可追溯性**（50 个任务里哪个失败、为什么失败、日志在哪），
**不是** 省空间。

## 2. 能力盘点：后端已经齐了，缺的只有界面

`backuprestore_core::TaskStore` 已提供设计所需的全部接口：

| 接口 | 用途 |
|---|---|
| `TaskStore::new(root)` | 根 = exe 所在目录 → `<运行目录>\tasks` |
| `task_dir(id)` / `status_path(id)` | 定位证据 |
| `load(id) -> Task` | 读 `task.json`（**反序列化成类型**，不手写键名） |
| `cleanup_task_artifacts(id) -> bool` | 只删 `mount/stage/original/payload` 工作树，**保留** task/status/manifest/log/BCD 证据；未完成任务返回 `BR-CORE-059` |
| `cleanup_terminal_tasks(keep_latest) -> CleanupReport` | 批量清，保留最近 N 个 |
| `incomplete_tasks()` | 列出未完成（可续跑）任务 |

**结论**：本项不需要改 core，也不需要新错误码。改动全部落在 CLI 侧（新模块 + 一个窗口 + 入口改造 + 判据）。

## 3. 关键约束（决定方案选型）

1. **GUI 从没用过 ListView**：`grep SysListView32|WC_LISTVIEW|LVM_` → **0 处**。
   现有控件类只有 `BUTTON 67 / STATIC 24 / EDIT 17 / COMBOBOX 11`。
   引入 `SysListView32` 意味着：`comctl32` 的 `InitCommonControlsEx` + 列/项消息 + 新控件类进基线 + 几何判据要认新类。
   **风险与收益不成比例**（一次为了「好看的表头」引入整套新依赖）。
2. **主窗口 5 页已有 148 条控件基线**（`install_pe 32 / secondary 31 / restore_nonC 29 / backup 29 / restore_c 27`），
   几何判据 `PAGES_CHECKED=5` 只覆盖这 5 页。新窗口是**独立窗口**，不进这 5 页，因此
   **不破坏现有基线**——但它的控件要另立基线键（见 §7）。
3. **不可逆操作**：清理会删目录。必须走程序原生确认框（`MessageBoxW`），且只删工作树、不删证据。
4. **持久化格式的教训**（v2.6.64 栽过两次）：读 `status.json` **必须反序列化成 `StatusRecord`**，
   不许 `serde_json::Value` 手写键名。`StatusRecord` 是 camelCase、`Stage` 是 kebab-case。

## 4. 方案选型

### 方案 A（推荐）：COMBOBOX 选任务 + 只读 EDIT 看详情

```
┌─ 任务与证据 ────────────────────────────────────────────┐
│ 任务(50)： [ #1 10-27 01:15 restore-existing 成功   ▼ ]│  ← COMBOBOX
│ ┌─────────────────────────────────────────────────────┐│
│ │ 任务 ID：adb8700a-f29d-4219-9f32-7731079ff6e6       ││  ← 只读多行 EDIT
│ │ 操作：restore-existing    阶段：success             ││    (ES_MULTILINE|ES_READONLY|WS_VSCROLL)
│ │ 进度：100%                                          ││
│ │ 更新时间：2026-10-27 01:07                          ││
│ │ 任务目录：H:\brwork\tasks\adb8700a-…                ││
│ │ 准备日志：…\prepare.log    恢复日志：…\recovery.log ││
│ │ 工作树：无（已清理）                                 ││
│ └─────────────────────────────────────────────────────┘│
│ [刷新列表]  [清理本任务工作树]  [打开任务目录]  [关闭]  │
└─────────────────────────────────────────────────────────┘
```

**控件**（全部是已有类型）：`COMBOBOX ×1`、`STATIC ×2`、`EDIT ×1`（多行只读）、`BUTTON ×4`。

- 优点：零新控件类、零 comctl32 初始化；下拉框原生支持键盘选择与滚动；与项目风格一致。
- 缺点：没有多列对齐，靠等宽排版（`Consolas`/`宋体` 混排要试）；不能点列排序。

### 方案 B：SysListView32 表格

真表格（列、排序、多选），但首次引入 comctl32 新控件类，且要新增几何/存在性判据分支。
**结论：本轮不做。** 若将来任务数上百、需要按列排序，再单独评估。

**选 A。**

## 5. 数据流与模块设计

### 5.1 新增 `crates/backuprestore-cli/src/task_admin.rs`（**无条件编译**，本机可单测）

```rust
/// 一行任务摘要。字段全部来自已反序列化的类型，不从 JSON 里手抓键。
pub(crate) struct TaskRow {
    pub id: String,
    pub updated: String,        // status.updated 格式化后
    pub operation: String,      // operation_display()
    pub stage: Stage,           // 枚举，不是字符串
    pub progress: u32,
    pub error_code: Option<String>,   // error_code_text
    pub error: Option<String>,
    pub worktree_bytes: u64,    // 只统计 mount/stage/original/payload
    pub dir: String,
    pub prepare_log: String,
    pub recovery_log: String,
}

/// 从两个 JSON 文本解析一行；坏 JSON 不 panic，返回可展示的错误态。
pub(crate) fn parse_row(task_json: &str, status_json: &str) -> Result<TaskRow, RowDefect>;

pub(crate) enum RowDefect {
    TaskMalformed(String),
    StatusMalformed(String),
    IdMismatch { task: String, status: String },
}

/// 下拉框里的一行：`#3 10-27 01:15  restore-existing  成功`
pub(crate) fn combo_label(index: usize, row: &TaskRow, lang: Language) -> String;

/// 详情面板的多行文本（复用 status_receipt 的阶段/错误码措辞，保证两处口径一致）。
pub(crate) fn detail_lines(row: &TaskRow, lang: Language) -> Vec<String>;
```

**排序**：`updated` 降序（最新在前），同刻按 `id` 升序保证稳定。

**单测（本机可跑，至少 8 条）**：
1. 正常成功任务 → stage 成功、无错误码
2. `stage=failed` + `error_code_text=BR-PE-039` → 详情含码
3. `stage=failed` + `error=""` → 必须说破「未记录原因」（复用 2.6.64 的规则）
4. 坏 `task.json` → `RowDefect::TaskMalformed`，不 panic
5. 坏 `status.json` → `RowDefect::StatusMalformed`
6. `taskId` 与目录名不一致 → `IdMismatch`（防串目录）
7. 未完成（`stage=capturing`）→ 标记 incomplete，清理按钮应禁用
8. 50 行排序稳定性

### 5.2 GUI 侧（`native_gui.rs`）

新增常量与接线（**照 `2.6.61` 删入口的 8 类接线反向做**）：

| 类别 | 内容 |
|---|---|
| 常量 | `TASK_ADMIN_CLASS`、`ID_TASK_COMBO(1401)`、`ID_TASK_DETAIL(1402)`、`ID_TASK_REFRESH(1403)`、`ID_TASK_CLEANUP(1404)`、`ID_TASK_OPEN_DIR(1405)`、`ID_TASK_CLOSE(1406)` |
| 窗口过程 | `task_admin_wndproc`（`WM_CREATE` 建控件 / `WM_COMMAND` 分发 / `WM_SIZE` 重排） |
| 打开函数 | `show_task_admin(parent, state)`：模态循环，与现有「软硬件信息」窗口同构 |
| 刷新 | `reload_task_combo()`：枚举 `state.store.root/tasks/*` → `parse_row` → `CB_RESETCONTENT` + `CB_ADDSTRING` |
| 详情 | `CB_GETCURSEL` → `detail_lines` → `SetWindowTextW` |
| 清理 | 确认框 → `cleanup_task_artifacts(id)` → 结果写回详情 + `append_gui_log` |
| 打开目录 | `ShellExecuteW(open, dir)` |

### 5.3 入口：**改造现有按钮，不加新按钮**

现有顶栏有 `ID_REFRESH_TASK (1004)`「刷新任务状态」——它干的就是「看任务状态」。
**把这个按钮点开后从「往状态框贴五行文本」改成「打开任务与证据窗口」**，窗口里仍有「刷新列表」。

理由：
- 顶栏刚在 2.6.59 修过重叠（6 对控件压在一起），**再加按钮就要重算整行宽度**；
- 这个按钮的语义本来就覆盖新窗口，不需要两个入口；
- 主窗口控件数不变 → **148 条基线一条不动**，几何判据天然仍绿。

★ 但要保留原行为的一半：状态框（`ID_STATUS`）仍显示「最近任务的 4–9 行摘要」，
点按钮时先刷新状态框、再开窗口。这样 2.6.64 的实机用例（`_t-refresh-status.ps1` 四种结局）**仍然有效**。

## 6. 交互与错误处理（逐条定死）

| 场景 | 行为 |
|---|---|
| tasks 目录不存在 | 下拉框显示「（尚无任务记录）」，清理/打开按钮禁用，**不弹错误框** |
| 任务数 > 0 | 默认选中第 1 项（最新），详情立即填充 |
| 某任务 JSON 坏 | 该行标注「记录损坏」并**仍可选中**看目录路径；清理按钮禁用（不能对不认识的目录动手） |
| 未完成任务（`is_incomplete`） | 详情顶部加警示行；清理按钮禁用（core 也会返 `BR-CORE-059`，界面先拦） |
| 清理成功 | 详情刷新为「工作树：无」+ 状态栏提示；写 `gui.log` |
| 清理失败 | 弹框带 `[BR-…]` 码（复用 `failure_receipt`），不静默 |
| 列表刷新耗时 | 50 个任务读 100 个 JSON：预期 < 100 ms；若 > 500 ms 则改为「先只读 status.json，详情按需读 task.json」 |

## 7. 判据设计（三层，缺一层就是假绿）

### 7.1 存在性
`control-baseline.txt` 新增一段，page 键 **`task_admin`**，7 条：

```
task_admin|1401|COMBOBOX
task_admin|1402|EDIT
task_admin|1403|BUTTON
task_admin|1404|BUTTON
task_admin|1405|BUTTON
task_admin|1406|BUTTON
task_admin|1400|STATIC        ← "任务(50)：" 标签
```

主窗口 5 页的 148 条**一条不改**。基线脚本要能查独立窗口：现有 `_t-layout-rects.ps1` 只枚举主窗口子窗口，
需加一个 `-WindowClass` 参数（默认主窗口），新窗口用 `-WindowClass BackupRestoreTaskAdmin`。

### 7.2 几何（新窗口 5 条同样适用）
`OVERLAP / OUTSIDE / TEXT_CLIPPED / TEXT_OVERFLOW / ZERO_SIZE` 全部为 0。
★ 新窗口默认尺寸要按客户区算：`width ≥ 640`、`height ≥ 420`，且**`WS_CAPTION` 的 30 px 不算客户区**
（PE 对话框那次的教训：`height=312` 时底部按钮被裁）。

### 7.3 行为（`CASE_RESULT=` 逐用例，冒烟只认这行）

| 用例 | 构造 | 断言（ASCII） |
|---|---|---|
| T1 空列 | 临时把 tasks 改名 | `CASE_RESULT=T1_EMPTY=PASS`（下拉框项数 0 + 文案非空） |
| T2 排序 | 造 3 个任务，时间递增 | `CASE_RESULT=T2_ORDER=PASS`（第 1 项是最新的 id 前 8 位） |
| T3 带码失败 | status 写 `error_code_text=BR-PE-039` | `CASE_RESULT=T3_CODE=PASS`（详情文本含 `BR-PE-039`） |
| T4 拒清未完成 | status 写 `stage=capturing` | `CASE_RESULT=T4_REFUSE=PASS`（按钮 disabled 或返回码 `BR-CORE-059`） |
| T5 清理成功 | 造 worktree 目录 + 已成功 status | `CASE_RESULT=T5_CLEAN=PASS`（worktree 消失、task.json 仍在） |

★ 每条都要做**变异**：例如把排序改成升序 → T2 必须红；把清理前的 `is_incomplete` 判断去掉 → T4 必须红。

## 10. 风险与对策

| 风险 | 概率 | 对策 |
|---|---|---|
| COMBOBOX 跨进程读项数（`CB_GETCOUNT`）被 UIPI 拒 | 中 | 沿用 `run-gui-token.ps1` 借令牌到 session 1；实测过 `CB_GETCOUNT=0 + GetLastError=5` 就是 UIPI |
| 50 个任务枚举时某个目录权限异常导致卡住 | 中 | 逐条 `Result`，坏的标注「记录损坏」而不是整体失败 |
| 清理误删证据 | 低 | 只调 `cleanup_task_artifacts`（白名单只删 4 个 worktree 目录）；界面二次确认；T5 断言 `task.json` 仍在 |
| 入口改造破坏 2.6.64 的状态回执用例 | 中 | 保留「先刷新状态框再开窗」；现有 `_t-refresh-status.ps1` 四结局作为回归 |
| 中文等宽对齐在 EDIT 里错位 | 低 | 详情用「标签：值」两行式，不做列对齐；下拉标签只放 ASCII 与数字为主 |

## 11. 明确不做（避免扩散）

- 不做任务删除（只清工作树；证据保留是产品承诺）
- 不做跨磁盘/跨机器任务汇总
- 不做按时间/操作筛选与搜索
- 不改 `TaskStore` 任何语义
- 不引入 ListView（见 §4）

## 12. 建议的下一步

**直接开工 S1**。理由：纯逻辑模块无条件编译、本机可单测，没有任何 VM 依赖，也不动 GUI 布局；
即使 S2 设计要调整，S1 的解析与格式化逻辑仍然可复用。

若想先看到界面再定细节，也可先做 S2 的骨架（空窗口 + 静态控件 + 布局），但那会立刻牵动基线与几何判据，
返工成本更高。**推荐 S1 → S2 顺序**。
