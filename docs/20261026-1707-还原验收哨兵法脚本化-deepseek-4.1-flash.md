## 0. 为什么这条最难

还原验收一直是三条遗留里最后一条，因为它**必须重启真机**。而在此之前，判定靠人眼：

| 原做法 | 问题 |
|---|---|
| 看日志「还原成功」 | 日志可能来自上一次跑（本仓多次踩过读旧文件） |
| 看截图 | 本仓已明确「截图是弱信号，不算验收」 |
| 看 BCD 指向 | 改 BCD 是还原**之后**的一步，能过但不能证明卷被写了 |
| 跑 `RESTORE_SELFCHECK` | 那是**产品自己报的自检**——自证只能说明「它认为自己做了」 |

所以需要一个**外部可观测的物理事实**：目标卷被整体重写过。

## 1. 两条判据，三种结论

```bash
./tools/restore/sentinel.sh arm    --drive C    # 还原前
# … 进 WinRE → apply → BCDBoot → 重启回来 …
./tools/restore/sentinel.sh verify --drive C    # 还原后
```

`arm` 做三件事：在卷根写 `BR-<时分秒>.txt`、记下卷序列号（`fsutil` 输出里的 `0x…`）、
记下当前 BCD default。状态存 `.br-sentinel/<盘符>.state`（本机临时，已进 `.gitignore`）。

`verify` 只问两件事：

| 判据 | 含义 |
|---|---|
| 哨兵文件**不在了** | 目标卷的根目录被重写（不是「删了个文件」能解释的） |
| 卷序列号**变了** | 文件系统被重建 |

结论三态（外加一个 ERROR）：

| VERDICT | 条件 | 退出码 |
|---|---|---|
| `PASS` | 两条都满足 | 0 |
| `WARN` | 只满足一条（列明哪条没满足） | 1 |
| `FAIL` | 两条都没满足 | 1 |
| `ERROR` | 读不到（卷不存在 / 状态文件丢失 / 通道抽风） | 2 |

**单条弱信号不足以验收**——只删了文件、或只换了文件系统记录，都可能是别的动作造成的。
这就是 WARN 存在的理由，也是它和 FAIL 一样返回 1 的原因。

## 2. 实测：四个分支全部走过

在 `T:`（5 GB 测试卷）上用「格式化」模拟「卷被整体重写」——判定逻辑与还原无关，
它只关心「卷有没有被重写」。

| 场景 | 输出 | 退出码 |
|---|---|---|
| **负例**：布哨后什么都不做 | `SENTINEL_PRESENT=1` / `SERIAL_CHANGED=0` / `VERDICT=FAIL` | 1 |
| **正例**：`format T: /FS:NTFS /Q /Y` 之后 | `SENTINEL_PRESENT=0` / `0xea2fc666 → 0xc0338a4c` / `VERDICT=PASS` | 0 |
| **WARN**：只 `del` 哨兵、不动卷 | `SENTINEL_GONE=1` / `SERIAL_CHANGED=0` / `VERDICT=WARN` | 1 |
| **ERROR**：`--drive Q`（不存在的卷） | `VOLUME_NOT_FOUND=1` / 退出码 2 | 2 |
| **ERROR**：没布哨就 verify | `STATE_MISSING=1` / 退出码 2 | 2 |

正例的完整输出：

```
DRIVE=T
SENTINEL=BR-170457.txt
SENTINEL_PRESENT=0
SENTINEL_GONE=1
SERIAL_BEFORE=0xea2fc666
SERIAL_AFTER=0xc0338a4c
SERIAL_CHANGED=1
VERDICT=PASS
```

## 3. 通道上的两个坑（都会让判据「读不到」而不是「不满足」）

### 3.1 GBK 乱码让 `grep` 把整段当二进制

`fsutil fsinfo volumeinfo T:` 在中文 Windows 下输出 GBK。序列号本身是 ASCII 的
`0xea2fc666`，但**同一段输出里有非法 UTF-8 字节** → `grep` 判定为 binary file，
默认只打印 `Binary file (standard input) matches`，**一个字符都不给**。

现象极易误判：明明肉眼看到 `0x…`，脚本报「读不到序列号」。

解法是给通道加一层净化：

```bash
vm_run() { prlctl exec "$VM_NAME" cmd /d /c "$1" 2>/dev/null | LC_ALL=C tr -cd '\11\12\40-\176'; }
```

只保留可打印 ASCII 与换行——判据本来也只该在 ASCII 上做（中文标签是「数据」，不参与判定）。

### 3.2 不留 CR：行尾带 `\r` 会让 `grep -x` 永远不匹配

第一版净化保留了 `\15`。结果 `dir /b` 列出的文件名行尾是 `BR-xxx.txt\r`，
`grep -qxF "BR-xxx.txt"` **永远不匹配** → 刚写好的哨兵被判「读不回来」。

去掉 `\15`（统一成 LF）后正常。

### 3.3 `LC_ALL=C` 不是可选项

macOS 的 `tr` 在 UTF-8 locale 下遇到 GBK 字节会直接报
`tr: Illegal byte sequence` 并**放弃整条管道**（不是跳过那几个字节）。

下次做真实离线还原时，流程是：

```bash
./tools/restore/sentinel.sh arm --drive C

# 备份 → 进 WinRE → 还原 → BCDBoot → 重启
```

★ `verify` 的 PASS 与日志里的 `RESTORE_SELFCHECK` **是两条独立来源**：
前者是外部物理事实，后者是产品自报。两者都绿才算闭环——
只信其中一个，就是「A 等不等于 B 由同一台仪器产生」的老问题。

## 6. 可复用的钉子

1. **验收要用外部物理事实，不用产品自报的日志**。同一个进程说自己成功了，证明力很弱。
2. **「只满足一条」必须单独成一态**（WARN，且与 FAIL 同样返回非 0）。单条弱信号正是
   误判的来源：删文件很容易，重建文件系统不容易，两者混为一谈就会放过假阳性。
3. **通道输出先净化成 ASCII 再判定**。GBK 字节会让 `grep` 判二进制、让 `tr` 报错，
   两次都表现成「读不到」——而「读不到」绝不能被记成「判据不满足」。
4. **`grep -x` 与 CRLF 是天生不合**：要么先 `tr -d '\r'`，要么别用 `-x`。
5. **ERROR（退出码 2）与 FAIL（1）分开**：前者是仪器坏了，后者是被测对象没达到要求。
   混在一起就会「哪天通道抽风，被记成一次还原失败」。
