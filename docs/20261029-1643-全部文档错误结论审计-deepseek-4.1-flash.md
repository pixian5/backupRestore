## 三、`经验/` 内部互相矛盾（两条说法不可能同时成立）

### 3.1 PE 到底起没起，能不能看日志——同一份文件给了相反答案

- `经验/04` §1 第 14 行：「**判 PE 到底起没起，看 `T:\Windows\System32\winpeshl.log`，不要靠画面**」
- `经验/04` §9 第 135 行：「`T:\Windows\System32\winpeshl.log` 可能是 0 字节 —— **判「起没起」以截图为准，别拿这个 0 字节下结论**」

相隔 120 行，结论相反。**可调和的正确说法**（两处实测都支持）：日志**有内容时以日志为准**（只有一条 `Succeeded launching` = 驻留成功；多条且间隔约 19 秒 = 壳失败后自重启的死循环）；**只有 0 字节时才退回截图**——0 字节本身不能证明任何一方。

这条危险在于：违反「别把空输出当结论」这条最贵的纪律——§9 那句话是对的，但它没说「有内容时日志更强」，于是读者可能整体放弃日志判据。

### 3.2 `bcdedit /enum` 显示盘符形态——前一句少了前提

- `经验/03` 第 11 行：「`bcdedit /enum` **把两种形态都规范化显示成 `ramdisk=[X:]`**」
- `经验/03` 第 14–15 行（同一节，更晚的实测）：「写盘符形式**也会被渲染成设备路径**；把盘符摘掉，显示变成 `[\Device\HarddiskVolumeN]`；挂回又变 `[X:]`」

前者缺了「该卷当前有盘符」这个前提。正确写法：**有盘符时两种写入形式都显示成 `[X:]`；卷存在但无盘符时显示 `[\Device\HarddiskVolumeN]`；悬空引用显示 `[unknown]`**。所以 `[X:]` 对「当初写的是哪种形式」零区分力。

### 3.3 构建到底走哪条路——墓碑清单自己留了一句反转

- `经验/07` 第 21 行（第 11 号墓碑）括注：「用户 10-12 曾决定虚拟机内为主（**但当前实际又走回 macOS build-win.sh，见 06 §1 冲突**）」
- `经验/06` §1、`AGENTS.md` §三、`README.md` 第 210 行，三处一致：**发布唯一路径 = 虚拟机内**，macOS 的 `build-win.sh` 只做本地类型检查，**产物不得部署、不得作为发布版**

`经验/07` 那句括注是旧的。留着它的后果很具体：有人会照它去部署 macOS 交叉编译产物，而那批产物编译不到约 59% 的代码（8 个只在 Windows 下编译的模块，约 1.57 万行），历史上引导修复的每个阻断缺陷都在这批文件里。

### 4.1 `docs/20261012-1320-Parallels快照吃满磁盘根因与空间硬规则-GPT-5.md`

它的「一句话结论」是错的，而且是最要害的那句：

> Parallels 快照……**把这台 VM 当前所有虚拟盘的实际数据整份复制一份**……三层快照叠加 = 约 265GB
