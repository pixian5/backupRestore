## 0. 一句话结论

1. **规则翻转**：第二系统场景原本刻意「保留原主系统 default」（bcdboot `/d` + 三道回读自愈），
   用户指出这与 GUI 里「当前的默认启动项被钉住不可取消」的语义相反——**钉住的既然是「默认
   启动项」，那它就该是新还原出来的系统**。两个场景从此统一：**还原完成后 default 一律指向
   本次还原出来的系统**，原系统仍留在菜单里（仍钉住，理由改为「不能删掉原系统，否则启动不
   回去」）。
2. **备份索引名**：默认值由「程序启动时间 `YYYY-MM-DD HH:MM`」改为**「系统版本 + 年月日」**，
   如 `Windows 11 26200.9550 20261015`；源卷换成非系统盘时降级为 `Windows (F:) 20261015`；
   用户手改过则永不被自动值覆盖。

## 2. 改动一：default 归属翻转

### 2.1 旧规则为什么被推翻

`docs/20261015-0725` §1.3 记录的第二系统路径叠加了四道防线，全部为了「default 不许被劫持」
（2026-10-13 事故：`repair_secondary` 失败，default 留在半成品第二系统上，用户每次开机被拖
进去，只能进 PE 离线改 BCD）。防线本身没问题，问题是**产品语义**：

- GUI 引导方案弹窗里，「当前的默认启动项」这一项被**钉住、不可取消勾选**；
- 用户看到的行为却是「还原完成后，开机进的还是旧系统」；
- → 钉住一个「不是最终默认项」的条目，语义自相矛盾。

旧规则用 bcdboot `/d` 换来的「半成品保护」实际收益也有限：`/d` 只在**镜像已应用完成**、
bcdboot 即将执行时起作用，而那一刻目标卷已经是完整的 Windows；此后失败（WinRE 注册等）
不会让系统启动不了。故不再为它牺牲 default 语义。

### 2.2 新规则（唯一权威表述）

`boot_menu.rs::DefaultPolicy` 的文档注释即规则原文：

- 还原本系统（目标 = 活动系统分区）→ default 指向还原后的自己；
- 新增第二系统（目标 = 其它分区）→ **default 同样指向本次新还原出来的系统**。

`PreserveCurrentDefault` **不再被任何调用方显式设定**，降级为「方案里没有该字段时的保守兜底」
（旧版本落盘的 `boot-menu-plan.json`），此时对场景一无所知，不动 default 更安全。

### 2.3 代码改动清单

| 文件 | 改动 |
|---|---|
| `boot_menu.rs` | `DefaultPolicy` 文档改写为修订后规则；标注 `PreserveCurrentDefault` 已无调用方；`validate` 里「默认项不可取消」的理由改写为「原系统必须留在菜单里」；`discover` 里 `is_current_default` 注释同步；apply 的 `Preserve` 分支加「仅旧方案兜底」说明 |
| `main.rs` | ① `set_default_policy` 去掉 `target_is_secondary` 分支，统一 `PointAtRestoreTarget`；② 第二系统 bcdboot **去掉 `/d`**（保留 `/addlast`）；③ `assert_boot_default_preserved` **删除**，新增 `assert_boot_default_points_at_target(efi, target_letter, log)`——按分区找目标 loader，回读 default，不符就写一次，仍不符则报错拒绝继续；④ `preserve_primary_boot_manager` **不再写 default**，验收去掉 default 比较，日志改为 "default left to the boot-menu plan"；⑤ 路由日志文案同步 |
| `online_operation.rs` | ① 策略改 `PointAtRestoreTarget`；② STEP 3.6 bcdboot **去掉 `/d`**；③ 不再把 default 恢复成快照值（只恢复 `resumeobject`）；④ STEP 4 预检由「default == 快照」改为「`resume_object` 未变」；⑤ **终检反转**：`default_is_primary`（default 指向活动卷）→ `target_is_default`（default 指向**目标卷**），别名 `{current}`/`{default}` 一律判 false |
| `pe_operation.rs` | ① bcdboot **去掉 `/d`**；② `SecondaryInstall` 分支的 `/set {bootmgr} default` 由 `old.default` 改为 `loader`；③ 终检 `default: loader` |
| `native_gui.rs` | 中英六处帮助/提示文案：「默认启动项保持不变」→「还原完成后默认启动项切换为这台新系统（原系统仍保留在菜单中可选）」 |

### 2.4 顺带修正的一处自相矛盾

`preserve_primary_boot_manager` 原先在 bcdboot 之后把 default 写回 `previous.default`，而
`boot_menu::apply`（最后一步）又按策略覆盖——同一流程里两处对 default 拉锯。现在删除前者，
default 归属只由 apply 一个决策点负责（符合 0725 文档 S1 的「单一权威」设计意图）。

## 3. 改动二：备份索引名默认值

### 3.1 实现

`native_gui.rs` 新增：

- `reg_read_string` / `reg_read_dword`：`RegGetValueW` 手写 FFI 直读 HKLM（不 spawn `reg.exe`
  ——GUI 里开子进程会闪控制台），读 `HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion`；
- `current_windows_version_tag()`：拼 `Windows 11 26200.9550`；
- `default_backup_index_name(source_is_system, letter)`：拼 `… 20261015`；
- `set_index_name` + `index_name_auto` / `index_name_touched`：与 S5 的菜单名同一套
  「程序预填 vs 用户手改」机制（**先记 auto 再写文本**，理由见 §6）；
- 触发点：建窗时按「源盘 = 系统盘」预填；`refresh_environment` 后与源卷 `CBN_SELCHANGE` 时
  各重算一次（用户手改则跳过）。

### 3.2 两个必须记住的判据坑

1. **主版本不能只信 `ProductName`**：本机实测是 Windows 11 25H2（build 26200.9550、
   `DisplayVersion=25H2`），注册表 `ProductName` 却仍写着 **`Windows 10 Pro`**——
   跨版本升级/预览通道常见。所以桌面版按 **build 号**判定（≥22000 = Windows 11，
   ≥10240 = Windows 10），这也是通行做法。若只读 ProductName，本机会输出
   `Windows 10 26200.9550`，与用户给的示例不符。
   Server 分支不受影响：`ProductName` 含 "Server" 时优先用 ProductName（其 build 号与桌面版
   不同源，套桌面阈值会误判）。
2. **版本只安在「确实备份的是当前系统」时**：源卷换成别的卷时，那个卷的版本要挂离线 hive
   才读得到；把当前系统的版本写上去是**误导，而且索引名写进 WIM 就改不了**。故降级为
   `Windows (F:) 20261015`——信息少但不假。

### 3.3 CLI 侧刻意不动

`main.rs` 备份分支的 `image_name` 兜底仍是 `Windows Backup`：CLI 可能跑在 RE 里，读到的
「当前系统」是被还原的环境而不是被备份的源卷，照搬 GUI 算法会写错名字。

### 4.3 遗留观察点：`{bootmgr}.resumeobject` 与 new default 不同源

验收时发现一个**语义上的不一致**（不是失败，行为符合代码）：

- `{bootmgr}.default` = 新系统 `{baf4e768}`（F:）；
- `{bootmgr}.resumeobject` = `{41326e71}`，即**原主系统**的 resume 对象（按 apply 的「恢复为快照值」
  逻辑写入），而新 loader 的配对 resume 对象是 `{baf4e767}`。

旧规则下两者天然一致（default 也是主系统）；规则翻转后这个组合是新出现的。潜在影响：**快速启动
（hiberboot）关机后开机的路径是「固件 → bootmgr → resumeobject 指向的 resume app」**，如果此刻
主系统的 `hiberfil.sys` 仍带「从休眠恢复」标志，用户可能被带回旧系统，而不是按 default 进新系统。
需要说明的是 Windows 在**每次关机上会自行把 `{bootmgr}.resumeobject` 改写为当前系统的**，所以
该不一致是短暂的、会自愈；但它恰好覆盖「还原完成后的第一次开机」这个用户最关心的时刻。

处置建议（**未实施，待用户裁定**）：default 指向还原目标时，把 `{bootmgr}.resumeobject` 一并设为
**目标 loader 的 resume 对象**（`bcdedit /enum <target_loader> /v` 取 `resumeobject` 字段）。
风险点是 2026-10-14 有过 resumeobject 相关的血泪修复（不对称导致任务永久失败），贸然改动需配套
改回读校验，故本轮只记录不动手。

### 4.4 现场清理时踩的新坑：删掉 default 项会把 `{bootmgr}.default` 一并清空

按守则清理时依次执行 `displayorder /remove` → `delete {baf4e768} /f`，然后回读发现
**`{bootmgr}` 里 `default` 那一行整个消失了**——`bcdedit /delete` 删除的正是当时的 default 项，
BCD 不会自动补一个，`default` 变成空值（开机时 bootmgr 退化用 displayorder 首项，看似正常，
但状态已不干净）。

**正确顺序（已写入 MEMORY.md 守则）**：
```
bcdedit /default {主系统 loader}          # ← 先切走，再删；否则 default 被清空
bcdedit /displayorder {待删} /remove
bcdedit /delete {待删} /f
format X: /FS:NTFS /Q /Y
```
本轮已用 `bcdedit /default {41326e72…}` 恢复，回读确认 `{bootmgr}` 与主 loader 全部回到
E2E 前的干净基线（default/resumeobject/displayorder 三项一致）。

> 这条坑之所以此前没暴露：上一轮 E2E 的新项**不是** default（那时 default 保持主系统），
> 删它自然不影响 `default`。**规则翻转后新项成了 default，清理顺序就必须调整**——
> 与 §6 第 4 条「flip 规则要检查派生处」是同一类问题的第二次现身。

## 6. 教训（下次别再犯）

1. **EDIT 的 `WM_SETTEXT` 会同步重入 `EN_CHANGE`**：`SetWindowText` 在**同一调用栈**上向父窗
   发 `EN_CHANGE`。凡是「程序预填 + 用户手改」双轨的文本框，必须**先记录自动值、再写文本**，
   否则重入时读到旧 auto 值 → 把程序自己的预填误判成用户输入 → 此后再也不预填。
   v2.6.0 的 S5 就栽在这里（菜单框永远停在语言默认值），v2.6.1 的索引名沿用同一套机制时
   已按正确顺序写。
2. **跨进程读控件文本只有 UIA 可靠**：`GetWindowTextW` / `WM_GETTEXT` 在 GUI 自动化里都不可信。
3. **截图 ≠ 全屏**：agent `shot` 是屏幕左上 1153×954 的 1:1 捕获，最大化窗口（2306 宽）右侧
   的弹窗根本不在图里。要坐标就用 UIA 的 `BoundingRectangle`（`br-enum-dlg.ps1`），
   或 `GetWindowRect`——不要凭截图目测。
4. **规则类改动要顺带清理「同义的第二处实现」**：`preserve_primary_boot_manager` 与
   `boot_menu::apply` 都写 default，翻规则时漏一处就会互相打架。**同理要检查「派生字段」**——
   `{bootmgr}.resumeobject` 就是跟着 default 走的派生值（见 §4.3），flip default 时容易漏。
5. **版本判据优先用 build 号**：`ProductName` 在升级/预览路径上会撒谎（本机实测）。

## 7. 遗留 / 待裁定

- **`{bootmgr}.resumeobject` 与 default 不同源**（§4.3）：default 已指向新系统，但 resumeobject 仍
  是主系统的快照值。Windows 每次关机自查自愈，但「还原后第一次开机」这一档存在被快速启动带回
  旧系统的理论风险。是否改成「default 指向目标时 resumeobject 也指向目标 loader 的配对对象」，
  待用户裁定。
- **S3（0725 文档）**：`PreserveCurrentDefault` 分支里「原 default 的 loader 还在 BCD 只是没被
  勾选 → 是否报错拒绝」，边界仍待用户裁定；本次修订后该分支只服务旧方案兜底，优先级下降。
- **V1/V2/V5/V6 未按新规则重跑**：A 入口（还原本系统到 C:）本来就指向还原目标，新规则下
  终态不变，但「还原前默认项是另一套系统」的边角用例值得重跑一次。
- **`boot_entry.rs` 模块头设计原则注释（S4）** 待补。
- **默认启动项钉住的 UI 文案**：现在「当前的默认启动项」这一项在改动后仍会被钉住（理由变了），
  但列表里没有任何文字说明它「还原后不再默认」。若用户希望界面直说，需要另设计一行提示。
