# 下一步待实现

版本 **2.2.1**；模型：Opus 5（1M 上下文）。

14 项清单已全部处理完毕，剩下的都是**实机验收**与验证加固，没有已知未修缺陷。

## 一、必须先做：2.2.0 / 2.2.1 的实机验收

这两轮改了 BCD 元素的实际值并新增了补偿路径，2.1.9 的 11 点断电证据不能套用。
按 `AGENTS.md`，下列操作前必须先建并核验新的 Parallels 快照（最多保留最近 2 个）：

1. 部署 2.2.1 到客体包目录与 `H:\brwork\`，逐一核对 SHA-256；
2. 一次完整链路：准备 → 重启进 RE → 捕获/应用 → 引导修复 → 清理 → 回正常 Windows；
3. 至少一次 `rearm()` 续跑，证明新路径的启动链回读与载荷探测在实机成立；
4. 两个未终结任务并存：准备 A 后再准备 B，核对 A 的载荷哈希不变、清理 B 不影响 A、
   第二次武装被 `allow_rearm` 拒绝；
5. **失败补偿用例**：注入 `acceptance:entry-fields:error`，确认建条目失败后
   残留簿记落盘、BCD 与镜像卷都回到基线、`boot-entry.json` 未被污染；
6. Windows 侧常规回归（2.1.9 为 156 项，新增测试后应更多）。

另需人工确认并清理镜像卷上旧版遗留的共用 `BackupRestoreRE\Winre.wim` / `boot.sdi`——
新代码不认它们，也不会误删。

## 二、验证加固建议

- **把交叉 clippy 纳入常规流程**：本轮 Windows 侧 clippy 抓到本机看不到的两个问题，
  而第一版是带着它们去构建、被 `E0308` 挡下的。本机 `cargo clippy` 不编译
  `#[cfg(windows)]` 模块，所以双侧必须分别跑。
- **继续把可测逻辑移出 `#[cfg(windows)]` 模块**：`boot_record` 就是这么做的，
  效果直接（5 项本机测试兜住簿记语义）。`boot_entry` 里还有纯数据/纯路径逻辑可以照做。
- ESP 定位在多 ESP、ESP 无挂载点、隐藏恢复卷排在 ESP 前等场景的实机行为仍待覆盖。

## 三、仍然保留的既有边界

- BCDBoot 完成后断电目前支持进入系统并显式 `resume`；要做到完全自动需重新设计持久恢复入口，
  会改变当前仅用一次性启动请求的设计。
- 状态事务的三个内部文件边界由真实文件重放测试覆盖；要增加存储介质级证明需另做定点断电。
- 按用户要求不扩展平台（Windows 10、x64、实体设备均不在范围内）。
