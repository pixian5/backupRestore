## 本轮（2.3.0）做了什么

1. **复核外部 AI 的 2.2.9 验收报告，推翻其根因判断**
   - 它称失败原因是 PowerShell 把 `FindWindowW` 的 `$null` 绑成空字符串。
   - 实测：`$null` / `[NullString]::Value`（真 NULL 指针）/ `''` 三种传参**全部返回 0x0**，
     所以"空字符串绑定"不成立。
   - 真因是**窗口站隔离**：`prlctl exec` 通道在 Session 0 的 `Service-0x0-3e7$\Default`，
     GUI 在 Session 1 的 `WinSta0\Default`；`FindWindow` / `EnumWindows` /
     `Get-Process.MainWindowHandle` 都只看调用方自身窗口站，跨站结构性不可见。
   - 因此它提议的 `EnumWindows` 修复**同样会失败**。
2. **修掉它没能测出的真缺陷**：详细日志弹窗的编辑框既无 `WS_TABSTOP`，
   整个 `recovery_progress.rs` 也没有任何 `SetFocus` 调用 → 编辑框永远拿不到键盘焦点。
   在 WinRE（可能无鼠标，而这正是当初加热键的全部理由）下，用户能打开日志但**完全滚不动**。
   修复：弹窗编辑框加 `WS_TABSTOP`，首次创建与复显两条分支都
   `SetFocus(GetDlgItem(window, ID_LOG_EDIT))`。
3. **用宿主侧方法完成 2.2.9 + 2.3.0 三项 GUI 实机验收**
   （`prlctl send-key-event` + `prlctl capture` + macOS Vision OCR，不受窗口站限制）。

## 本轮经验

1. **客体内窗口枚举在 `prlctl exec` 下结构性不可用**，GUI 验收一律走宿主侧
   `send-key-event` + `capture` + OCR。
2. **`WS_TABSTOP` 与 `SetFocus` 缺一不可**：只加热键打开窗口不够，
   窗口里的控件拿不到焦点，纯键盘环境下依然是死的。
3. **哈希必须在最终构建之后采集**：1830 收口文档里记的 `e7fa8c21…` 是 15:40 的构建，
   早于 18:10 的 2.2.9 GUI 改动，属于错配，已在该文档内更正。
4. **截图 SHA-256 比对是 UI 行为的可靠判据**："看起来没变"主观，
   逐像素哈希能区分"根本没响应"与"响应后恰好相同"。
