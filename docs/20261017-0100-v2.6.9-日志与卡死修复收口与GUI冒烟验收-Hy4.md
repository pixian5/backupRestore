## 3. ★ 本轮新发现的 5 条脚本级坑（全部会「静默失败」）

> 共性：**不报错、退出码 0、日志看起来正常**，但结果是错的。写自动化注入时必须逐条对照。

### 3.1 `SendMessage` 必须显式声明 `CharSet=Unicode`，否则 `WM_SETTEXT` 被截成首字符

**现象**：注入 `1200` → ini 里存成 `1`；注入 `600` → 存成 `6`；注入 `4`（单字符）→ 正常。
**根因**：`[DllImport("user32.dll")]` 不写 CharSet 时默认 **Ansi** → 实际调用 `SendMessageA`，跨进程时系统按 **ANSI** 编组 `WM_SETTEXT` 的 UTF-16 指针：`'1','\0','2','\0'…` 在第一个字符后即遇 NUL 终止 → 只传过去一个字符。
**修法**：
```powershell
[DllImport("user32.dll", CharSet=CharSet.Unicode)] public static extern IntPtr SendMessage(...);
```
**教训**：**单字符测试值会漏掉这个 bug**——用 `4` 验证通过不代表 `1200` 也对。多位数测试值必须带 readback 校验。

### 3.2 不要用同步 `SendMessage(BM_CLICK)` 去点开模态窗口 → 脚本会卡住

**现象**：脚本 transcript 停在 `settings-button=…` 之后无任何输出，而设置窗口其实**已经弹出来了**（截图可见、后续手动操作正常）。
**根因**：GUI 线程处理 `BM_CLICK` 时进入**嵌套模态消息循环**，跨线程 `SendMessage` 的等待被一路拖到模态窗口关闭才返回。
**修法**：按钮/单选的点击一律用 **`PostMessage`**（异步，立即返回），再 `Start-Sleep` 等界面就绪。

### 3.3 借令牌起的子进程**看不到 `X:`**（每用户网络驱动器映射）

**现象**：`Test-Path X:\` = False → `Start-Transcript -Path X:\...` 抛错 → **全部输出丢失**，表现为「脚本好像没执行」。上一 AI 的脚本正是把日志与 marker 写在 `X:` 上。
**根因**：`DuplicateTokenEx` 产生的令牌属于**新的登录会话**，每用户网络驱动器映射（`X:`）不随之而来。
**修法**：借令牌的子进程**日志与 marker 一律写本地路径**（如 `<exe>\logs\`），宿主再用 **SYSTEM 通道**读回共享盘。UNCID 兜底亦可，但本地 + SYSTEM 回读最稳。

### 3.4 `GetWindowText` 跨进程读 EDIT 返回空 → 要用 `WM_GETTEXT`

**现象**：脚本里 readback 打印 `(readback=)`，看起来像「值没写进去」，其实值已正确写入（UI 截图与 ini 都是对的）。
**根因**：`GetWindowText` 对**其他进程**的窗口不发送 `WM_GETTEXT`（只对同进程窗口有效）。
**修法**：
```powershell
$ptr = [Runtime.InteropServices.Marshal]::AllocHGlobal(256)
$n = [SW]::SendMessage($h, 0x000D, [IntPtr]256, $ptr)   # WM_GETTEXT
$s = [Runtime.InteropServices.Marshal]::PtrToStringUni($ptr, [int]$n)
```
**注意**：同一条规则解释了为什么 `GetDlgItem` 能拿到句柄（纯查询、不受 UIPI 限）而 `BM_CLICK` 不行（要执行）。

### 3.5 SYSTEM 会话枚举不到会话 1 的窗口

**现象**：在 SYSTEM 通道跑 `EnumWindows` 找设置窗口 → 报 `no settings window`，而窗口明明开着。
**根因**：`EnumWindows` 只枚举**调用进程所在窗口站/桌面**的窗口；SYSTEM 在 session 0，GUI 在 session 1。
**修法**：任何需要「找 GUI 窗口 / 操作 GUI 窗口」的动作，都必须**借令牌到会话 1** 执行。**推论**：SYSTEM 通道只适合查文件/注册表/进程/事件日志这类不涉及窗口站的操作。
