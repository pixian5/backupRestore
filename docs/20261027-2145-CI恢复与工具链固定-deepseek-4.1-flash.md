# CI 恢复：只搬「云端也验得了」的 4 步 + 工具链固定到 1.98.1

> 撰写：2026-10-27 21:45。前序：`docs/20261027-2108-外部命令失败带码与启动菜单修复拒绝用例`。
> 本轮是 N4：把门禁从「只在本机 hook」变成「换机器/交接后依然存在」。
> **未升版本**：只动 CI 配置、工具链文件、一处纯重构与一条用例，无产品行为变化。

## 1. 先看上一版 CI 是怎么死的

`gh run list` 里躺着 9-28 的一串 `failure`，而 `.github/` 已从仓库消失：

| 提交 | 动作 |
|---|---|
| `9b96f52`（工程整治） | 引入 CI，跑 `scripts/audit-runtime-boundaries.sh` |
| `8dcfe88`（v1.7.10） | 删除 `.github/`（提交说明没写理由） |

那套 CI 跑的是 `fmt --check` + **cli 的 clippy `-D warnings`** + 交叉编译 —— 恰好是本机
pre-push **刻意不做**的三件事（仓库从未 fmt-clean、cli 那 40 条告警几乎都是
`cfg(windows)` 假阳性、交叉编译需要 Windows SDK libs）。连红 5 次后被删，
**一个长期红的 CI 比没有 CI 更坏：它训练所有人忽略红色。**

所以这次的第一条设计约束是：**第一轮就必须全绿**，宁可少覆盖。

## 2. 覆盖对照（本机 6 步 → 云端）

| pre-push 步骤 | 云端 | 说明 |
|---|---|---|
| 1 单测 | gate: `cargo test --workspace` | ubuntu-latest，依赖全是纯 Rust，与 mac 等价且便宜 |
| 2 core clippy `-D` | gate: 同 | 只对 core（cli 的告警是假阳性，开成阻塞会逼人 `--no-verify`） |
| 3 错误码同步 | gate: `gen-error-codes.py` + `git diff --quiet` | 同步即绿，脏了报 `::error` 并打印 diff |
| 4 交叉编译 release | windows: `cargo check --target aarch64-pc-windows-msvc` | 不链接（runner 没有 ARM64 CRT），类型检查足够 |
| 5 Windows 测试目标 | windows: **`cargo test --workspace` 原生跑** | 比「只编译」更强：这一半以前从没被执行过 |
| 6 文档链接入库 | gate: `check-doc-links.py --strict` | 分级语义不变（1 阻塞 / 2 判据故障） |

## 3. 第一轮就红了两个——都是真问题

### 3.1 gate 红：clippy 新 lint + 工具链漂移

`core clippy -D warnings` 报 `for loop over a single element` → `core/lib.rs:1790`：

```rust
for junction in ["Documents and Settings"] { … }
```

这是**故意写成单元素循环的列表**（每发现一个根级自引用联接点就加一条），本机 clippy 1.98
根本不知道这条 lint；runner 的 `stable` 已经 1.99，`-D warnings` 下直接判 error。
**本质是「本机 1.98 / CI 1.99」的版本漂移**，修法两层：

1. 新增 `rust-toolchain.toml`：`channel = "1.98.1"` + `components = ["clippy"]` +
   `targets = ["aarch64-pc-windows-msvc"]`；CI 显式装同版本，并加一步断言
   `rustc --version` 与文件一致，**漂移即红**。升级工具链从此是主动动作。
2. 那处列表改成具名常量 `ROOT_JUNCTIONS`：既表达「这是会增长的列表」，
   又不受 1.98/1.99 任一版本影响（内联字面量才会触发该 lint）。

⚠️ 顺手踩到：固定工具链等于新装一份，**忘了写 `targets` 时交叉编译报
`can't find crate for 'core'`**——与代码无关，极易误判成代码坏了。

### 3.2 windows 红：用例依赖具体硬件布局

`recovery_object_accepts_only_the_registered_partition` 失败。用例硬编码
`harddisk0\partition6`，而校验会真去 `CreateFileW("\\.\HarddiskVolume6")` 打开那个卷——
runner 上没有这个分区，于是「必须通过」的断言必然红。**这不是产品缺陷，是用例的假设过期**。

改法：用**本机系统卷的真实设备路径**构造规格——
`volume_identity(系统盘)` 取 `disk_number`/`partition_number`，
`boot_entry::dos_device_of(系统盘)` 取 `\Device\HarddiskVolumeN`（该函数放开到 `pub(crate)`）。
于是任何 Windows 机器上都成立，并且**比原来更强**：

- 正向：真实设备 + 真实分区号 → 必须通过（原来只是「常量恰好对得上」）；
- 反向：同一真实设备，但规格声称的分区号不符 → 必须拒绝（新加的，验的是真链路）。

## 5. 结论与边界

- **本地钩子与 CI 是分工，不是替代**：钩子负责「推之前 30 秒知道」，CI 负责
  「换机器、交接、多人协作时判据仍然存在」。README 里原来那句「选本地钩子而非
  GitHub Actions」已订正。
- **CI 不覆盖的**：真机部署、VM 冒烟、`#[ignore]` 的 10 条破坏性用例（那是
  `tools/test/ignored-acceptance.sh` 的活儿，需要 VM + 管理员 + 真实卷）。
- **判据仍是「结构化」的**：CI 只认 `test result:` / `git diff --quiet` / 脚本退出码，
  不 grep 中文文案——换 locale 也不该变红。
