## 0. 结论速览

| 维度 | DISM（当前唯一捕获引擎） | wimlib（POC） | 判定 |
|---|---|---|---|
| 4.94 GB / 15,359 文件捕获耗时 | **133.8 s**（纯 DISM 阶段，不含产品收尾 5 s） | **100 s** | wimlib 快 **34%** |
| 产物体积（同源同载荷） | 2,054,642,315 B | 2,018,848,685 B | wimlib 小 **1.7%** |

| 进度可观测性 | **无**（只打版本横幅，全程 0 进度行） | 有（百分比 + 绝对 MiB，逐段刷新） | wimlib 明显更优 |

**一句话结论：捕获侧建议引入 wimlib，但方式是「DISM 默认 + wimlib 失败/超时兜底」，而不是直接反转默认。**
理由见 §5。是否需要产品化，**等用户拍板**（本轮不改码）。

## 1. 为什么做这个 POC

- 还原侧（apply）在 [E3](20261025-0700-E3主备反转评估-DISM与wimlib实机对照结论不反转-Step-5-Preview.md) 已做过实机对照，结论是 DISM 与 wimlib 打平（28.1 min vs 26.7 min、ACL 双 6/6），故**不反转**。
- 但**捕获侧（capture）从未做过对照**：产品备份链从 v2.6.x 起一直是 DISM `/Capture-Image` 独占，wimlib 只作为 apply 失败时的降级通道。
- 10-25 整体分析把它列为 P3-b，明确「不预设结论」。

## 2. 实验设计

### 2.1 载荷（T: 小卷，可控规模）

`T:`（5 GB 测试卷）构造真实载荷，**刻意不用全零文件**（全零会被压缩器瞬间吃掉，测不出真实开销）：

```
robocopy C:\Windows\System32 T:\poc\sys32 /E /MAX:8000000 /R:0 /W:0 /NFL /NDL /MT:8
```

结果：**15,359 个文件 / 4,942.3 MiB**，真实系统文件（DLL/MUI/MAN/ETL 混合），另有 100 MiB `big.bin` 与哨兵 `T:\poc\seed.txt`（内容 `POC-SENTINEL-20261025`）。

> ⚠️ 踩坑：第一次不加 `/MAX` 直接拷 `System32`，T: 容量不够，robocopy 报 **错误 112（磁盘空间不足）**。
> 改用 `/MAX:8000000`（单文件上限 ~8 MB）截断后才装下。**小卷造载荷必须先估容量再定筛选条件。**

### 2.2 捕获命令

| 通道 | 命令 |
|---|---|
| DISM（产品） | `BackupRestore.exe online --operation backup --source-drive T: --image-path H:\BRImages\poc-dism-t.wim --json`（内部 = `dism /Capture-Image /Compress:fast /CheckIntegrity`） |
| wimlib | `wimlib-imagex.exe capture T:\ H:\BRImages\poc-wimlib-t.wim "POC wimlib T" --compress=fast --check` |

### 2.3 规模对照（85 GB 系统卷 F:）

同一卷上各跑一次在线捕获，验证「大卷场景下 DISM 是否仍然可用」。

## 3. 实测数据

### 3.1 4.94 GB 载荷（T:）

| 项 | DISM | wimlib |
|---|---|---|
| 墙钟总耗时（含产品收尾） | 139 s | 100 s |
| **纯捕获耗时** | **133.8 s**（日志 `20:32:34.807` → `20:34:48.587`） | **100 s**（归档 + 完整性表一次完成） |
| 产物字节 | 2,054,642,315 | 2,018,848,685 |
| 退出/结论 | `--json success=true` | 正常退出到 100% |

**口径说明（重要）**：DISM 那 139 s 里有 ~5 s 是产品自己的收尾
（`dism /Get-WimInfo` 索引回读 → 整档 sha256 → 发布前重验 → 发布后尺寸核对，
见 `online_operation.rs:1438-1476`），不是 DISM 捕获本身。
**对比必须用 133.8 s 这个纯捕获数**，否则会低估 DISM。

### 3.2 互操作性往返（关键）

用产品把 **wimlib 捕获的镜像** 还原回 T:：

```
online --operation restore-existing --target-drive T: --image-path H:\BRImages\poc-wimlib-t.wim --index 1 --format-target --json
→ success:true
```

还原后核验：

- 文件数/体积 **15,359 / 4,942.3 MB**，与源**逐一相符**；
- 哨兵 `T:\poc\seed.txt` 内容仍为 `POC-SENTINEL-20261025`；
- 目录结构 `big.bin / seed.txt / sub1 / sys32` 完整。

另：`wim-info H:\BRImages\poc-wimlib-t.wim --skip-hash --json` → `success:true`，
说明 **DISM 侧能正常读 wimlib 产出的镜像元数据**。

### 3.3 85 GB 系统卷（F:）—— 决定性差异

| 通道 | 现象 | 产物 |
|---|---|---|
| DISM（第一次） | 挂起 **12 小时以上**；`tasklist` 里 dism.exe 已消失、CLI 仍在无限等待 | 候选 `candidate.wim` **0 字节** |
| DISM（第二次，装 40 min 逃生阀 `BACKUPRESTORE_DISM_TIMEOUT_SECS=2400`） | 满 2400 s 撞阀终止；日志 `DISM 结果：等待 2400000 毫秒超时；进程树确认结束=true`；期间 CPU 仅 **2.5%**（阻塞在 I/O，不是扫描） | 候选 `candidate.wim` **208 字节**（只有 WIM 头） |
| **wimlib** | 先快后停：4 min **7.37 GB** → 13 min **11.47 GB** → 23 min **18.04 GB** → 33 min **18.15 GB**（此后 ~0.011 GB/min，等同停滞）；进程 CPU 同样只有 **2.5%** | 中途终止（实验判定无效） |

**§3.3 结论：这个大卷对照实验不成立，不能用来判优劣。** 三条理由：

1. **两引擎最终都卡在同一处 I/O 阻塞**：DISM 与 wimlib 的 CPU 占用**都是 2.5%**
   （阻塞，不是计算），且 F: 小文件读取 1 秒正常、大块读停滞 ——
   **是 F: 这个卷在当前 VM/宿主状态下的大规模顺序读问题，与引擎无关**。
2. **卷的规模被我先前估错了**：`dir F:\` 实测根目录合计 **291,441,258,496 B ≈ 271 GiB**
   （不是我一直以为的 85 GB；F: 是长期堆满的测试卷，含 `Mac`/`Users`/`Windows`/`WinRE-PoC` 等 16 个目录）。
   按 fast 压缩比推算产物约 130 GB，而 H: 当时只剩 **123 GB** ——
   **就算读得动，也会撞「磁盘空间不足」，实验无法跑完**。
3. wimlib 已写入的 18 GB 产物已删除，H: 回到 141.5 GB。

**唯一仍然成立的差异**：在**同一个卡死发生前的窗口**里，
DISM 只产出 **208 字节**，wimlib 产出 **18 GB**（相差 8 个数量级）。
一个合理的解释（未证实）：DISM `/Capture-Image` 先做全卷枚举/安全描述符预扫，
扫完才开始写；wimlib 是流式边扫边写。**若属实，这就是 DISM 在大卷上「长时间零字节」的根因**，
值得作为独立课题去证实。

> 教训：**POC 的卷规模必须先实测 `dir`/`Get-Volume`，不能沿用记忆里的旧数字。**
> 我按「F: 85 GB」设计了实验，实际是 271 GiB，直接导致实验无效。

> 逃生阀复算：第二次能自动终止，全靠 v2.6.44 的 `dism_timeout`
> （默认 `0` = 不限制，正是本轮「无限等 12 小时」的成因）。
> **这同时又是一次捕获链上的超时兜底端到端验证。**

## 4. 两个顺带发现（值得单独记）

### 4.1 超时路径不带错误码 —— **已修（v2.6.51）**

> ✅ **本项不再是待办**：排查中发现根因不只在超时点，而是 `online` 主路径**整体吞码**
> （`main` 用无码 `err()` 替换了内部所有带码错误）。已在 v2.6.51 修复并实机验证：
> 超时场景 `error_code` 由 `null` 变为 `BR-APL-001`。
> 详见 [20261026-0520 online 主路径错误码被吞修复](20261026-0520-online主路径错误码被吞修复-error_code不再恒null-Step-5-Preview.md)。

当时的现象（DISM 超时终止后 `--json` 输出）：

```json
{"command":"online","error":"invalid task: online operation did not complete successfully",
 "error_code":null,"operation":"backup","success":false}
```

`error_code` 为 **null**。按项目错误码纪律（`errc`/`errc_with` = 带码运行期失败），
DISM 等待超时属于运行期失败，理应带码。**已修，见上。**

### 4.2 捕获阶段零进度输出

DISM 捕获 40 分钟期间，日志只有「DISM 开始（等待上限 …）」+ 版本横幅，**没有任何进度行**。
GUI 侧同理——用户看到的是一个静止的窗口。
wimlib 则输出 `Archiving file data: 3132 MiB of 5043 MiB (62%) done`。
**进度可观测性是 wimlib 的显著优势**，且与「开发测试版要详细日志」的项目要求直接契合。

## 5. 建议与方案对比

### 5.1 三种方案

| 方案 | 做法 | 收益 | 代价/风险 |
|---|---|---|---|
| **A（建议）** DISM 默认 + wimlib 兜底 | 捕获失败或超时后自动切 wimlib 重捕获 | F: 那类挂死可被自动救回；**不动默认路径，零回归面** | 需新增一条降级链（含排除表在 wimlib 格式的等价实现、产物一致性判据） |
| B 直接反转默认 | 捕获默认走 wimlib，DISM 作兜底 | 快 34%、体积小 1.7%、有进度 | 捕获是「造数据」侧，换默认等于换掉全部历史镜像的产出引擎；wimlib 的 ACL/安全描述符语义需重新验收（还原侧已验过 apply，捕获侧未验） |
| C 维持现状 | 不动 | 零成本 | 85 GB 系统卷在线捕获实测不可用；无进度；超时无码 |

### 5.2 推荐 A 的理由（**置信度：中，比做实验前低**）

1. **大卷对照实验无效（§3.3）**，所以「DISM 在大卷上不可用」这条**最有力的论据已被削弱**——
   实测两引擎最终都卡在同一 I/O 阻塞上。剩下的理由是次要的：快 34%、小 1.7%、有进度输出。
2. **证据只支持「wimlib 稍快且可观测」，不支持「wimlib 全面更优」**——
   E3 在还原侧已证明两者打平；为 34% 换掉默认引擎，收益/风险不成比例。
3. **兜底架构已在 apply 侧跑通**（DISM 失败自动降级 wimlib，v2.6.37 起），
   捕获侧照抄同一形态，概念与判据都可复用。
4. 兜底只在「本来就会失败」的路径上生效，**对成功路径零影响**。

**⚠️ 采纳 A 之前建议先做一件事**：证实 §3.3 末尾的假设——
DISM `/Capture-Image` 是否「先全卷预扫、扫完才写」。
若成立，那么「长时间零字节」是**可解释的正常行为**而非挂死，
此时 A 的收益就只剩「快 34%+有进度」，优先级应下调；
若不成立（真挂死），A 就是高优先级缺陷修复。**这个课题本身不需要改码，只需计时观测。**

### 5.3 若采纳 A，落地清单（供后续排期）

1. `online_operation::capture` 增加降级分支：DISM 失败/超时 → `wimlib-imagex capture`；
2. 排除表：DISM 用 `/ConfigFile`（`[ExclusionList]`），wimlib 配置格式不同，**需转换或双写**；
3. 降级产物必须走同一套收尾（索引回读、整档 sha256、发布前重验）——**不能因为是降级就跳过**；
4. 日志明确标注实际使用的引擎（便于报障归因）；
5. 判据：T: 小卷双向跑通 + F: 挂死场景能自动救回。

## 7. 附：本轮新增经验（已同步 MEMORY.md）

- **小卷造载荷先估容量**：`robocopy` 装满卷才报 **错误 112**，且已拷的部分会留下——
  用 `/MAX:<bytes>` 按单文件上限截断，比事后删更省事。
- **DISM 与 wimlib 的耗时对比必须剥掉产品收尾**：产品 online 备份的墙钟里含索引回读+整档 sha256+发布重验（本轮 ~5 s / 4.94 GB），
  直接比墙钟会低估 DISM。
- **验收「另一引擎产出的镜像」要跑真还原**，不能只 `wim-info`：
  本轮 wimlib 镜像经产品 DISM apply 还原后文件数/体积/哨兵全对，才算互操作性成立。
- **后台长任务的进度文件比回读 stdout 稳**：wimlib 的进度行是同一行 `\r` 刷新，
  直接抓 stdout 会得到一大坨互相覆盖的文本；重定向到文件再取尾部更可控。
