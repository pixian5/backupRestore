# 完整 DPI 布局缩放：200% 下界面与字体恢复正常大小（v2.6.79）

> 模型：Hy4。时间：2026-10-30 01:53。
> 版本：**2.6.79**（行为变更：布局坐标与字号随系统 DPI 缩放）。
> 关联：`docs/20261030-0140-200%缩放下GUI底部按钮不可见-DPI感知修复-v2.6.78-Qoder.md`（上一轮，只做了一半）。

---

## 1. 用户反馈的现象

「整个 GUI 字体非常非常小」。测试虚拟机系统缩放 **200%**（用户会话实测
`HKCU\Control Panel\Desktop` 的 `LogPixels=192`、`Win8DpiScaling=1`；物理分辨率 2350×1938）。

## 2. 真因：上一轮是"半程修复"，代价就是整体缩水

上一轮（2.6.78）为了修「200% 下底部四个按钮完全看不见」这个阻塞缺陷，做了两件事：

1. 进程声明 **DPI 感知**（`SetProcessDPIAware()`）—— 窗口不再被系统位图拉伸；
2. 界面字体**钉死在 96dpi 基准的 12 像素**（防止 200% 下系统字体变大后压住按钮）。

第 1 条是解药也是毒药：**一旦不再被系统拉伸，界面就按代码里写死的 96dpi 坐标原样绘制**。
在 200% 缩放下，本该画 24 像素高的字只画了 12 物理像素，窗口也只占屏幕左上角约 43%
——这就是「字体非常非常小」的直接来源。**不是显示器或系统设置的问题，是产品行为。**

三个字号的钉死位置（都在 `native_gui.rs`）：界面字体 `-12`、恢复桌面大字号 `-44 / -30 / -18`。

## 3. 修复：一处取系数，两处总闸，其余全部不动

### 3.1 核心设计——「在 96dpi 空间里算完，最后统一乘」

布局坐标有两个来源，混在一起会算错：

- **静态创建**：71 个控件，坐标全是 96dpi 字面量；
- **动态重排**（`layout_operation`，约 530 行）：用「实际客户宽 − 常量」做右对齐，
  客户宽是**放大后的真实值**，常量却是 96dpi 的。

若直接在物理量上乘系数，右对齐会算出 `(2040 − 20 − 241) × 2` 这种**翻倍的错误位置**。
所以约定：

| 环节 | 处理 |
|---|---|
| 读客户区 | 先 `unscale()` 换算回 96dpi 基准空间 |
| 中间 530 行常量 | **一个都不改**，仍按 96dpi 书写 |
| 输出（`reposition` 闭包） | 统一 `s()` 换算成物理像素 |
| 静态创建（`create_control`） | 入参直接 `s()` |
| 字号（`gui_font()` 与大字号） | `s()` |

由此得到一条硬性质：**100% 缩放下系数为 1.0，`s(v) == v`、`unscale(v) == v`，
所有窗口尺寸与改动前逐像素等价**——这既是安全网，也是回归判据。

### 3.2 改动清单（共 4 个文件）

- `crates/backuprestore-cli/src/dpi.rs`：**新增** `scale()` / `s()` / `unscale()`。
  系数取自 `GetDeviceCaps(GetDC(NULL), LOGPIXELSY) / 96`，用 `OnceLock` 缓存；
  取不到 DC 或数值越界（合理区间 48–480 dpi）时**退化为 1.0**（宁可偏小，也不要因为
  读到荒谬的 DPI 把界面画到屏幕外）。
- `native_gui.rs`：
  - `gui_font()`：`-12` → `-s(12)`（200% 下 = 24）；
  - `create_control`：x/y/width/height → `s()`（**一处覆盖 71 个控件**）；
  - `layout_operation`：客户区 `unscale()` + `reposition` 内 `s()`（一处覆盖 530 行重排）；
  - 主窗口初始尺寸 1020×760 → `s()`；任务窗口目标客户区 720×480 → `s()`；
    PE 对话框 440 / 324 / 312 → `s()`；恢复桌面大字号 → `s()`；
    下拉宽度与文本区内边距 → `s()`。
- 版本三处同步：`VERSION` + 两个 `Cargo.toml` → 2.6.79。

### 3.3 顺带修的构建脚本缺陷（不是产品代码）

`windows/build-windows.ps1` 的 `Invoke-Cargo` 原先直接 `& cargo ...`，而脚本全局是
`$ErrorActionPreference = 'Stop'`。cargo 把编译进度写到 **stderr**，PowerShell 5 会把它包装成
ErrorRecord → **第一条 "Compiling …" 就让脚本终止**。增量构建没有输出时相安无事，
一旦全量编译（换新 target 目录）就暴露：现象是构建"自己退出"、日志停在 Compiling 上。

改为临时切 `Continue` 并**显式检查退出码**——真正的失败照样抛出，只是不再把正常进度误判为错误。

## 5. 遗留 / 未做

- **100% 缩放下未实测**。改 VM 缩放需要重登录（且改注册表 `LogPixels` 会被 Windows 登录时
  重写回 192，文档已记）。等价性由「系数为 1.0 时 `s`/`unscale` 是恒等函数」保证，
  **结论是数学推理而非实测**，记为待验证项。
- **PE 恢复桌面与恢复进度窗未实机验证**：它们的大字号同样改成了 `s()`，但本轮只看了主界面。
- 完整缩放只覆盖坐标与字号；**文本行高**（`details_height = 148`，按 96dpi 行距 14 × 10 行算出）
  是随坐标一起线性缩放的，比例不变，但**未在 200% 下逐行数验证行数**。

## 6. 一句话总结

2.6.78 用「不再被系统拉伸」换来了底部按钮可见，代价是界面整体缩水一半；
2.6.79 把这一半补回来——坐标与字号一起按 DPI 缩放，字体恢复到与系统标题栏一致的大小，
且 100% 下逐像素不变。
