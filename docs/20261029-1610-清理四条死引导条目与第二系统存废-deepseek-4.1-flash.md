# 清理四条死引导条目，以及「F: 那块第二系统盘要不要删」

> 模型：deepseek-4.1-flash｜用户指令：「可以拍快照啊；清掉那 4 条死条目」
>
> 前半（§1–§6）是执行记录；后半（§7–§9）是关于 `F:` 那块盘的存废分析，
> 结论是**我没有删**，理由在 §8，需要用户拍板。

## 1. 为什么会有 4 条死条目

引导配置（BCD）里每个「启动项」都是独立对象。产品每做一次 WinRE 任务，会在 BCD 里建一条
临时启动项（描述写着 `BackupRestore task RE`），指向上一步铺到 `H:\BackupRestoreRE\<任务号>\Winre.wim`
的镜像；任务做完应当删掉。

历史上有两轮任务没清干净，加上 Windows 自己升级恢复环境时留下的两条旧壳子，一共 4 条：

| 描述 | 指向 | 为什么是死的 |
|---|---|---|
| `BackupRestore task RE` | `H:\BackupRestoreRE\173c7ffa-489b-…\Winre.wim` | 镜像已在本次清理的第三轮删掉（`H:\BackupRestoreRE` 整个目录 685.2 MB） |
| `BackupRestore task RE` | `H:\BackupRestoreRE\9221c945-4c80-…\Winre.wim` | 同上，镜像第一轮就删了（1.43 GB） |
| `Windows Recovery Environment` | `[unknown]\Recovery\WindowsRE\Winre.wim` | 设备卷已不存在，路径解析不出来 |
| `Windows Recovery Environment` | `[unknown]\Recovery\WindowsRE\Winre.wim` | 同上 |

它们都**不在启动菜单的显示顺序里**（`{bootmgr}` 的 `displayorder` 只有 `{current}` 和
`{b28feb7c-…}` 两项），所以看不见、也不影响选系统。但它们是残留，且指向不存在的文件。

## 2. ★ 踩到一个必须记住的坑：条目和它的「设备子对象」GUID 只差最后一位

第一次动手时我按 `bcdedit /enum all` 里 `device` 行尾部那个 `,{GUID}` 去删，结果删掉的是
**设备选项子对象**，不是启动条目本身。证据：

```
标识符                  {472f272f-cfce-11f1-a501-b5edaeceab66}      ← 条目
device                  ramdisk=[unknown]\Recovery\WindowsRE\Winre.wim,{472f2730-…}   ← 子对象
                                                                       ↑ 只差最后一位 2f / 30
```

后果很隐蔽：

- 删子对象**会报「操作成功完成」**，条目仍然在，只是它的 `device` 行从
  `ramdisk=[H:]\…\Winre.wim,{GUID}` 变成了残缺的 `ramdisk=[H:]\…\Winre.wim`（尾部子对象引用被抹掉）。
- 直接对子对象 `/delete`、`/set device`、`/deletevalue device` 三种方式**全部报
  「系统找不到指定的文件」**，因为它们不是可独立操作的条目。
- 正解：删**条目**的 GUID（末位上一号的那个）。四条删完，四个子对象**自动消失**，不用单独处理。

★ 另一条老规矩再次应验：`prlctl exec` 里 `%errorlevel%` **恒为 0**，失败时也是 0。
判据只能是「GUID 的引用数变成 0」「配置总行数变少」这类结构化事实。

## 3. 删除前做了什么

1. `reagentc /info` 确认**系统当前登记在用的恢复环境**是 `35457f54-…`（对应条目 `35457f55-…`，
   镜像 `[C:]\Recovery\WindowsRE\Winre.wim`，文件在，712,111,529 B）——**这条绝不动**。
2. 对四条候选取证：每条 GUID 在整份配置里只被引用 2 次（自己的 `device` 与 `osdevice`），
   **没有任何别的对象引用它们**（不在 `displayorder`、不是任何条目的 `recoverysequence`）。
3. `bcdedit /export C:\bcd-20261029-before-deadentry.bcd` → 106,496 字节，
   再用 `/store` 读回确认 `displayorder` 两项都在（**判据是「能读出关键项」，不是字节数**）。
4. 备份拷回宿主机 `.test-artifacts/cleanup-20261029/bcd-20261029-before-deadentry.bcd`
   （同样 106,496 字节，逐字节一致），客体里也保留了一份。

## 6. 回滚方法

坏了就用备份导回去：

```
bcdedit /import C:\bcd-20261029-before-deadentry.bcd
```

★ 回导的判据**不能**拿整份 `bcdedit /enum all` 相等来比——`{fwbootmgr}` 段（UEFI 固件项）会被
每次开机重排顺序、`description` 也会重写，与回导无关。要比就比**除 `{fwbootmgr}` 之外**的部分。

## 7. 关于 `F:`：它到底是什么

先把三个容易混的东西分开：

| 名称 | 实体 | 现状 |
|---|---|---|
| 「第二分区」（8 GB，装预安装环境那块） | `T:` 分区 | 已删（2026-10-29 15:25） |
| `F:` | 一块**独立的虚拟硬盘**（磁盘 2，标称 350 GB），装了第二套完整 Windows | 完好 |
| 磁盘 1 上的 64 GiB | 删 `T:` 留下的未分配空间 | 空着（在 `H:` 前面，并不进去） |

`F:` 在启动菜单里是「Professional 10.0.26200」，与 `C:` 那个并列。

它的用途分三层：① 当「**非活动的系统卷**」靶子——产品代码明确拒绝把当前运行的系统盘当在线还原目标，
要测「还原到另一块系统卷」就必须有第二个系统卷；② 10 月 27 日为解锁一批被跳过的测试用例专门建的；
③ 顺带持有官方 WinRE 母本的第二份副本（今天救回 `C:` 那份就靠它）。

## 8. ★ 关于「可以拍快照啊」——快照解决不了空间，而且这个靶子是消耗品

用户提出「可以拍快照」。这句话在两个层面都成立、但都不解决核心问题，必须讲清楚：

### 8.1 拍快照**不会**释放宿主空间

Parallels 快照是写时复制：拍下快照后，**被删除/被覆盖的数据块会继续被快照保留**。
所以「先拍快照，再删 F: 那块盘」的结果是——**宿主磁盘一个字节都没省**，反而因为多了一层快照索引更占。
只有把快照也删掉，空间才真的回来；而快照一删，回滚能力也就没了。二者不可兼得。

### 8.2 `F:` 本来就是「用完就毁」的靶子

还原测试做的事就是**格式化目标卷再把镜像铺上去**。也就是说 `F:` 上那套 Windows
**每做一次还原测试就被抹掉一次**，它存在的意义是「被还原覆盖之后能启动，用来证明还原成功」。

既然如此，它的「永久保留」价值就不高——下次要测，本来就要往里铺镜像。

### 8.3 宿主空间现状（这是真正的约束）

| 项 | 数值 |
|---|---|
| 宿主可用 | **153 GiB** |
| `harddisk.hdd`（磁盘 0 = `C:`） | 82 GiB |
| `harddisk1.hdd`（磁盘 1 = `H:`） | 3.9 GiB（精简置备：内部 192 GiB，实际只占 3.9） |
| `harddisk2.hdd`（磁盘 2 = **`F:`**） | **70 GiB** |
| 跑一次 87 GB 级整机还原所需 | 镜像 × 2.5 ≈ **220 GiB** |

也就是说：宿主现在 **153 GiB，还差 67 GiB 才够跑一次整机还原**；删掉 `F:` 恰好能回到 **223 GiB**，
刚好越线。这比「省 350 GB」这种虚数实在得多——**实际能省 70 GiB，而缺的正是 67 GiB**。

★ 注意标称 350 GB 与实际占用 70 GiB 的差别：虚拟盘是精简置备的，`du` 才是真实占用。

## 9. 我的建议（等用户拍板）

**建议删 `F:`，但先做一件事**：把 `F:\Users\Public\winre-src\Winre.wim` 这份母本备份挪到 `H:`
（`H:` 内部 192 GiB、宿主只占 3.9 GiB，几乎不花钱），然后再删盘。

这样：

- 宿主空闲 153 → **约 223 GiB**，够跑整机还原
- 母本仍有 `C:` 与 `H:` 两份，不依赖 `F:`
- 失去的只是「现成能启动的第二套 Windows」，下次要测时按测试本身的需要重建（或直接从镜像还原）

**另一种选择**：不删。理由是重建一套系统要几小时（装系统 + 修引导 + 重新登记恢复环境），
而 153 GiB 只要不去跑 87 GB 整机还原就够用。

两条路都合理，取决于近期要不要跑整机还原测试——这个只有用户知道，所以我没有擅自动手。
