# v2.0.4 - start_time 毫秒级重置对齐与全新备份还原端到端闭环

> **日期**：2026-10-01 01:30  
> **模型**：gemini-3.8-flash  
> **版本**：v2.0.4  
> **验证目标**：彻底解决 WinRE 恢复进度窗口初始「已用时间」相比阶段 1 时间戳存在 5 秒偏差问题，完成全新备份与系统还原端到端实机闭环验证。

---

## 一、问题根因深度分析

在前期测试中，用户指出反推法计算的开始时间为 `00:59:41`，而恢复窗口显示的阶段 1 时间戳为 `00:59:46`，两者存在约 5 秒的初始偏差。

### 根因剖析：
1. **计时起点过早**：在 WinRE 模式下拉起 `Recovery.exe` 时，UI 进度窗口在 `spawn_gui` 阶段便初始化了 `start_time = Instant::now()`。
2. **前期初始化开销**：在实际业务逻辑执行前，程序需要执行：
   - 卷枚举与匹配（`mount_matching_volume`）；
   - Manifest 文件与任务配置解析（`tasks/{task_id}/task.json`）；
   - UI 窗口的 Win32 API 消息循环预热。
   这些步骤在 WinRE 低频/单核虚拟机环境下耗时约 4.9 秒。
3. **首个时间戳记录时点**：业务日志正式记录 `1/4 挂载卷、校验 [HH:MM:SS]` 是在上述初始化全部完成、开始进入阶段 1 循环的那一刻。由于界面右上角的「已用时间」一直基于最开始的 `Instant::now()` 累加，导致在阶段 1 刚渲染出来时，已用时间就已经显示为 `00:04` 或 `00:05`，造成直观上的“偷跑 5 秒”体验。

---

## 二、架构设计与代码优化

为了让用户界面右上角的「已用时间」与各阶段时间戳（特别是第一步 `1/4 挂载卷、校验`）做到分秒不差的严格对齐，实施了如下改进：

1. **`ProgressShared` 增加原子对齐控制**：
   - 新增 `start_time_aligned: AtomicBool`；
   - 增加 `reset_start_time()` 方法：重置 `start_time = Instant::now()`，将 `start_time_aligned` 置为 true。
2. **多重安全对齐机制**：
   - **显式调用**：CLI 主流程在进入 `STEP 1/4` 时，显式调用 `progress.reset_start_time()`；
   - **日志增量自动对齐兜底**：在 `read_log_delta` 解析到第一行包含 `STEP 1/` 时，若未对齐则自动触发 `reset_start_time()`，防止任何异步时序引起的脱节。
3. **跨平台兼容与编译隔离**：
   - 保证 non-Windows（macOS 单元测试）下编译桩函数签名一致（`_progress: Option<&()>`），避免 `E0433`。
