# V 盘「无法访问」弹窗：根因与彻底修复（v2.6.70）

> 用户报：「经常会弹出这个 V 盘无法访问这个对话框，你彻底修复」。
> 结论：**幽灵盘符 + 未设进程错误模式**两个独立缺陷叠加。前者制造不存在的 `V:`，
> 后者让任何一次对它的访问都变成一次弹窗。两层都已修。

* * *

## 一、现象与定位

| 步骤 | 读数 | 结论 |
| --- | --- | --- |
| 1 | `fsutil fsinfo drives` → `C: D: F: H: S: Y:` | **当前没有 V: 这个盘** |
| 2 | `mountvol V: /L` / `dir V:\` → 「系统找不到指定的路径」 | V: 连坏链接都不是，**根本没挂上** |
| 3 | `HKLM\SYSTEM\MountedDevices` 有 `\DosDevices\V:` | 盘符**记录**还在，只是没有对应的卷 |
| 4 | 把记录解成 GPT 分区 GUID，与 `Get-Partition` 全表（3 盘 9 分区）逐条比对 | **无一命中** → 纯幽灵 |

解码结果（`DMIO:ID:` + 16 字节 PARTUUID，小端）：

```

\DosDevices\B:  ->  236e3729-3f8d-4ac1-a107-5278864d07ab   ← 全机不存在
```

配套的排除：计划任务、快捷方式、开机 Run 项、**没有一处**引用 `V:\`；
近三天系统事件里也没有磁盘类错误。所以弹窗不是「某程序主动去开 V:」，
而是「系统为一个记录里存在、物理上不存在的盘符报严重错误」。

## 二、根因

### 1. 幽灵盘符是怎么留下的

`mountvol <letter>: <卷>` 与 diskpart `assign letter=` 写的都是**持久**记录——
它就落在 `HKLM\SYSTEM\MountedDevices\`。用完不撤销，盘符就永久属于那个分区；
等分区后来被删（本机 10-27 删过 T: 与第二系统分区、清理过 VHD），
记录留在原地，Windows 每次碰它都为「一个不存在的卷」报错。

本项目里这件事**早就知道**：`efi_bcd_store_path` 的注释原话是
「调用方用完必须把盘符卸掉，否则『临时盘符』会变成新的污染源——那正是 S 盘反复出现的原因」，
`docs/20260929-2014-S盘自动打开问题定位与修复方案.md` 也整篇在讲它。
但**约定靠人记**，于是总有调用点漏掉，而且漏了没有任何信号。

最可能的污染链（解释了为什么偏偏是 `V:`）：
RE 里 `mount_letter_candidates` 的备用盘符表含 `V`（`['J'..'Q','U','V','Y']`）→
方案把 `drive_letter='V'` 存进 `SavedPlan` → 在线续跑时
`ensure_volume_mounted(&entry.volume, 'V', log)` 在**真实系统**里挂了一次 →
写进 C: 系统自己的 hive → 分区删除后成为幽灵。
**RE/PE 盘符不落盘（hive 是内存盘），只有在线路径会污染真实系统**——所以在线调用点是唯一要盯的地方。

### 2. 为什么会弹窗而不是静默失败

Windows 对「设备未就绪」这类严重错误默认弹系统对话框。进程只要没设
`SEM_FAILCRITICALERRORS`，一次 `GetFileAttributesW("V:\\")` 就足以弹一次框。
**弹的是谁的框，用户只看到「又是这个程序」**——这就是修一层不够的原因。

## 三、修复（三层）

| 层 | 改动 | 作用 |
| --- | --- | --- |
| 环境 | 删除 6 条幽灵记录 | 立刻消掉弹窗源 |
| 进程 | `SetErrorMode(SEM_FAILCRITICALERRORS \| SEM_NOOPENFILEERRORBOX)` | 从此**任何**残留盘符都只产生错误码，不产生弹窗 |
| 代码 | `MountLease` 盘符租约 | 让「忘记 /D」这件事不可能发生 |

### 1. 环境侧（已执行）

```
reg delete HKLM\SYSTEM\MountedDevices /v "\DosDevices\V:" /f
（同法删 B: G: I: Q: Z:）
```
复核：`MountedDevices` 现剩 `C: D: F: H: S: Y:`，与 `fsutil fsinfo drives` 完全一致。

### 2. 进程侧：`main()` 第一件事

```rust
#[cfg(windows)]
fn suppress_system_error_dialogs() {
    const SEM_FAILCRITICALERRORS: u32 = 0x0001;
    const SEM_NOOPENFILEERRORBOX: u32 = 0x8000;
    unsafe {
        unsafe extern "system" { fn GetErrorMode() -> u32; fn SetErrorMode(mode: u32) -> u32; }
        let current = GetErrorMode();
        SetErrorMode(current | SEM_FAILCRITICALERRORS | SEM_NOOPENFILEERRORBOX);
    }
}
```

两个刻意的选择：

- **放在 `main()` 最前**：设的是**进程**错误模式，之后派生的线程与 `launch_gui`
  起来的同一 exe 都继承，一条语句覆盖 CLI + GUI 两条形态。
- **不设 `SEM_NOGPFAULTERRORBOX` / `SEM_NOALIGNMENTFAULTEXCEPT`**：那两个是关
  **崩溃报告**，会把真正的程序缺陷藏起来。本次只关「设备/文件不在」这类环境噪音。

### 3. 代码侧：`MountLease`

约定靠人记 → 改成**类型系统**记。`windows_prepare.rs`：

- `release_mounted_letter(letter, log)`：`mountvol <letter>: /D`，结果落日志，失败不打断任务。
- `ensure_volume_mounted_tracked(...)`：内部函数，返回 `(盘符, 本次是否新分配)`。
- `ensure_volume_mounted(...)`：旧签名不变（`tracked` 的 `.0`）。
- `ensure_volume_mounted_leased(...)`：返回 `(盘符, MountLease)`，租约 drop 时自动撤销。

★ **只有新分配的盘符才进租约**：走 `identity.drive_letter` / `mounted_letter_for_identity`
命中时盘符本来就是用户的，撤掉会把用户正在用的盘符弄丢——这是本设计唯一要守的红线。

已改为租约的 5 处在线挂载（都是「读/刷一下就走」）：

| 位置 | 场景 |
| --- | --- |
| `boot_menu::existing_boot_menu_names` | 挂 ESP 读一次 BCD |
| `boot_menu` 候选卷枚举（原 `'U'`） | 枚举候选系统卷 |
| `boot_menu::apply` | 挂各方案条目写 BCD |
| `windows_prepare` 重启前刷新（载荷卷 `'R'`） | flush 后紧接着 `shutdown /r` |
| `windows_prepare` 重启前刷新（ESP `'S'`） | 同上 |

**刻意不改** `boot_menu` 里生成方案的那处（`ensure_volume_mounted(&entry.volume, entry.drive_letter, …)`）：
那里的盘符会写进持久化的 `SavedPlan` 并被后续步骤使用，此时撤销会直接断掉流程。
代码里留了注释说明「为什么不改」——**不写理由的例外，下一次就会被当成疏漏删掉**。

## 四、判据与复核

| 项 | 读数 |
| --- | --- |
| 交叉编译（Windows ARM64） | `Finished release`，产物 3,349,504 字节 |
| 宿主单测 | cli **307 passed / 1 ignored**、core **57 passed**，0 failed |
| 幽灵清理前/后 | 12 条 DosDevices → 6 条，且与 `fsutil fsinfo drives` 逐字一致 |
| 现存盘符未被误伤 | C/D/F/H/S/Y 六条记录的 GUID 与 `Get-Partition` 全表逐条命中 |

变异思路（本次未自动化，留给后续）：把 `created` 恒改成 `true`，
`ensure_volume_mounted_leased` 会在命中既有盘符时也去 `/D`——能验证「只撤新分配的」
这条红线真的被判据守住。**红线没有判据 = 红线不存在**，这条属于已知缺口，不掩饰。

## 五、坑（下次直接抄）

1. **`bcdedit` 在中文系统把 `identifier` 输出成「标识」**，按 `identifier` 匹配一条都取不到
   （`docs/20261027-0035` 里记的是「标识符」，实机是「标识」——两种都别依赖）。
   正确做法：按**结构化特征**取，例如「最后一个『键 + GUID』行的 GUID」。
2. **`Get-Content` 读 `bcdedit` 重定向出来的文件会因编码失配**，`findstr` 对同一文件
   部分命中更迷惑人。要解析就**让 PowerShell 直接捕获命令输出**，不要先重定向到文件。
3. 判幽灵必须**双向比对**：光看「盘符不在 `fsutil` 里」不够（可能是离线盘），
   要把记录的 GUID 拿去和**所有磁盘的所有分区**比（`Get-Partition` 三盘九分区全表）。
4. 删之前先分清**持久记录**（`MountedDevices`）与**运行时链接**（`\GLOBAL??\X:`）：
   本例根本没有链接，所以 `mountvol V: /D` 必然失败，只能改注册表。
5. `extern "system"` 在 edition 2024 必须写成 `unsafe extern "system"`（本机编译第一发就撞上）。

## 补记：真凶是**测试夹具**，上面第二节的推断错了（2026-10-27 23:5x 订正）

清理完 6 条幽灵后又跑了一轮门禁，然后顺手复查——**`V:` 又回来了**，
而且它指向的分区 GUID 是一个**已销毁的 VHD 分区**（`{00f7514e-…}`，不在任何磁盘的分区表里）。
再跑一轮，GUID 又不一样。所以「RE → 方案存 `drive_letter='V'` → 在线续跑」只是我按代码
推的**合理故事，不是事实**；真正每次制造它的，是本机反复跑的这条测试：

```
pe_operation.rs: create_disposable_vhd_fixture()
    diskpart: create vdisk / attach vdisk / convert gpt / create partition primary
              / format fs=ntfs quick / assign letter=V      ← 持久写入
    teardown: select vdisk / detach vdisk                   ← 只摘运行时链接
```

`detach vdisk` **不会**删 `HKLM\SYSTEM\MountedDevices` 里的 `\DosDevices\V:`。
于是每跑一次就多一个指向「已经随 VHD 一起消失的分区」的记录。

**为什么之前没人发现**：收尾那条断言是 `GetLogicalDrives() & (1<<'V'-'A') == 0`，
而 `GetLogicalDrives` 根本**看不见**幽灵盘符（它只有注册表记录、没有符号链接）。
**「判据看不到它」被当成了「它不存在」**——这正是本项目判据纪律里最贵的那条坑。

### 修法

1. 夹具开跑前先 `reg delete … /v "\DosDevices\V:" /f`（自愈：把历史遗留清掉，
   不然幽灵只增不减）。
2. 收尾脚本加 `select partition 1 / remove letter=V`，**在 detach 之前**撤掉持久指派。
3. 判据升级：收尾后直接 `reg query HKLM\SYSTEM\MountedDevices /v "\DosDevices\V:"`，
   **查不到才算干净**——这是唯一能看见幽灵的读数（`fsutil` / `mountvol` /
   `GetLogicalDrives` 全都看不见）。

### 验收（前后对照，同一台机器同一套仪器）

| 时点 | `\DosDevices\V:` |
| --- | --- |
| 手工清理后 | 无 |
| 跑完一轮完整门禁（修复前） | **又出现**，指向已销毁的 VHD 分区 |
| 单跑 `no_write_on_reject`（修复后，且故意不预清理） | **消失，且跑完未再生成** |

（这本身就是一次天然变异：修复前同一条用例必然留下记录，修复后必不留下；
新断言在修复前的状态下必然变红。）

### 教训（比这条 bug 本身值钱）

- **推断不是证据。** 我按代码逻辑写出了一个自洽的污染链，它错得很有道理。
  真正的判据是「跑一轮 → 复查 → 看 GUID 变没变」。
- **「清理完了」要复查，不能一次了事。** 本次正是清理之后的复查才钓出真凶。
- 产品代码里那 5 处租约和进程错误模式**仍然是对的**：前者防的是同类问题在产品里
  发生，后者保证即便再有残留也不会弹框。但**它们没有修到这次的弹窗源**——
  这个区别必须写清楚，不能因为改了就说修好了。
