# GUI 失败回执接入稳定错误码（v2.6.63）

> 时点：2026-10-26 22:30 · 模型：deepseek-4.1-flash · 版本：**2.6.63**（升版本：改了用户可见行为）

## 1. 起因

用户让「整体分析项目并给出下一步建议」。分析里把 `E5（GUI 侧错误码可见性）` 列为待办——
这是 10-25 就挂上的项，一直没有实证。本轮先把它查清，结论比预期更具体：

**不是「界面可能没显示码」，而是「有一条真实路径的码永远显示不出来」。**

## 2. 实证链条（先证明读数那一侧，再改）

| 环节 | 事实 | 证据 |
|---|---|---|
| 弹窗正文来自哪 | `OnlineResult.detail` = `online_failed_prefix` + `TaskError` 的 `Display` + 后缀 | `online_operation.rs:127` |
| `Coded` 的 Display | `[{code}] {rendered}` —— **自带码** | `lib.rs:85` |
| `Io` / `Json` / `InvalidTransition` | `code()` 有值（`BR-IO-001` / `BR-IO-002` / `BR-TSK-028`），但 **Display 故意不加前缀**（文案是 OS 本地化串或 serde 原文） | `lib.rs:98-111` |
| `error_code` 字段 | 2.6.51 专门把它从 `main` 的 `err()` 覆盖里救出来，注释写着「码必须由结果结构体带出来」 | `online_operation.rs:31-38` |
| 界面消费了吗 | **没有**：`native_gui.rs` 里 `error_code` 只出现 1 次，是 panic 分支的 `error_code: None` | grep 实测 |
| 状态栏写什么 | 恒为固定串「在线任务失败，请检查日志；不要将部分产物视为成功」——**没有码** | `native_gui.rs:7516` |

所以失效形状是：业务失败（`Coded`）看起来有码 → 掩盖了「磁盘满 / 句柄占用 / JSON 损坏」
这类最常见、最需要查码的失败**一个码都看不到**。用户手册第 4 章教人「按码查表」，
而界面不给人码。

## 3. 改法：`failure_receipt.rs`（新增 103 行，无条件编译）

纯字符串逻辑，三条规则，**必须幂等**：

1. 没有码 → 原样返回（panic 与「故意无码的用法错误」不能伪造码）
2. 文字里**已出现任何 `[BR-`** → 原样返回（真码已在内层，再拼一个会让用户报两个号）
3. 其余 → `[码] ` 前置

另有两条防御：
- 码不以 `BR-` 开头 → 原样（不把任意字符串当前缀贴到用户面前）
- `detail` 为空 → 只返回 `[码]`

**为什么幂等是硬要求**：同一段文字要同时进弹窗、状态栏和 `gui.log`，若两次处理结果不同，
界面与日志就对不上——而日志是事后唯一现场。

## 4. 接线（`native_gui.rs` 的 `WM_APP_ONLINE_DONE`）

```rust
let receipt = crate::failure_receipt::with_code(&result.detail, result.error_code);
append_gui_log(…, &format!("online completed: success={}\n{receipt}", result.success));
set_text(status, &status_text);   // 失败时 = with_code("在线任务失败，请检查日志…", code)
show_message(root, &receipt, …);
```

三处同源：**弹窗正文 / 状态栏 / gui.log 用同一份 receipt**，不会出现「界面有码、日志没码」。

## 5. 验收

### 5.1 单测（7 条，全绿）

| 用例 | 钉住的规则 |
|---|---|
| `no_code_keeps_text_untouched` | 无码不得造码 |
| `code_is_prepended_for_plain_text` | Io 类失败的典型形状 |
| `existing_code_is_not_duplicated` | ★ `Coded` 已有码不叠加 |
| `any_br_code_in_text_suppresses_prefixing` | 文字里是**另一个**码时也不加 |
| `idempotent_under_repeated_application` | 两次处理逐字相同 |
| `empty_detail_yields_bare_code` | 空详情只给码 |
| `non_br_strings_are_not_treated_as_codes` | `"2"` / `""` / `"   "` 都不当码 |

### 5.2 变异验证（拆守卫看红，不是「变绿就算」）

| 变异 | 结果 |
|---|---|
| A：`if detail.contains("[BR-")` → `if false && …` | **3 红 4 绿**（幂等相关三条全红） |

两次变异后都 `diff` 确认文件逐字节还原，再复跑 7 绿。

## 6. 遗留（如实记录，不拿编译过去凑）

1. **界面回执未实机触发一次失败**：唯一的零副作用入口是「读取镜像」的文件对话框（模态），
   自动化成本高于本轮收益。已验证的是「纯逻辑 7 条 + 2 次变异共 4 条用例变红」+「接线是单点替换」，
   不等于「屏幕上亲眼看到码」。下一轮跑真实还原时会自然带上这条。
2. **GUI 完全不读 `StatusRecord`**：`native_gui.rs` 里 grep 不到 `StatusRecord` / `load_status`。
   这意味着 **RE 里失败的任务，回 Windows 后界面无法显示它的 `status.error`（含码）**——
   用户只能去翻日志。这是比本轮更大的缺口，需要单独一轮（读状态 + 渲染 + 判据分级）。
3. **`StatusRecord.error_code: Option<i32>` 是遗留整数码**，与 `BR-域-序号` 字符串体系并行；
   消费方目前为零（GUI 不读、CLI 只写）。改它要动 serde 契约，须单独评估。
