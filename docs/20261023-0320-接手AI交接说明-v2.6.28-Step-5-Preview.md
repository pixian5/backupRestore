## 1. 这个项目是干什么的

Windows 下的「整机备份 / 还原」工具，三条还原入口 + 一条备份：

- **A 还原系统到 C 盘**（本位还原，`restore-existing`）
- **B 数据到非 C 盘**（在线执行，不动启动配置数据）
- **C 系统到非 C 盘**（`create-secondary`，还原到 F: 之类的第二块卷，双系统并存）
- **备份**：系统分区 → 镜像（DISM `/Capture-Image`）

两条「应用镜像」通道并存，**这是当前最需要先分清的事**：

| 通道 | 触发条件 | 用什么 | 说明 |
|---|---|---|---|
| 格式化还原 | 目标卷要格式化（默认） | DISM `/Apply-Image` | 老路径，稳定 |
| **覆盖式还原** | `--skip-format` **且**目标卷已含 Windows | **wimlib `apply`** | 不删卷上既有文件；**不带 `--no-acls`**，属主/访问控制列表随镜像完整还原 |

判据只认一个文件：目标卷上 `Windows\System32\config\SYSTEM` 是否存在（`pe_safety::target_is_windows_volume`）。
存在 + 不格式化 → 置 `overlayNoAcl: true` → 恢复环境里走 wimlib；否则走 DISM。
**为什么换 wimlib**：DISM 覆盖式应用到已含 Windows 的卷，还原微软商店应用包目录
（`Program Files\WindowsApps`，属主 `TrustedInstaller` + 专用访问控制列表）的安全描述符时
报 `RestoreDirMetadata 0x80070005` 并整体放弃；wimlib 自行取得 `SeRestore`/`SeBackup` 提权，
写入与安全描述符还原都能做。根因与两次概念验证见 `docs/20261022-2308`、`docs/20261022-1427`。

## 6. 环境坑（血泪，按类分组）

### 6.1 prlctl 通道

- `/usr/local/bin/prlctl` 与 `prlsrvctl` 是**坏的 bash 包装器**（报 `Failed to initialize Parallels Desktop
  in unattended mode`）。真二进制在 `/Applications/Parallels Desktop.app/Contents/MacOS/prlctl`。
  **所有调用（含后台任务）先 `export PATH="/tmp/prlbin:$PATH"`**（`/tmp/prlbin/prlctl` 已建软链）。
- **`--current-user` 是两种权限，别混**：不加 = `nt authority\system`，能 `bcdedit`、能用 UNC 写共享盘，
  但**看不到 `X:`**；加 = 交互用户，能用 `X:`，但**未提权**（`bcdedit` 拒绝访问、读卷身份 `error 5`、
  `taskkill` 拒绝访问）。→ **启动配置数据/卷身份/全量测试走 SYSTEM + UNC；读写仓库文件走 `--current-user`。**
- `prlctl exec` 返回 **137/SIGTERM 是常态**（包装层被 kill，脚本通常已跑完）；**输出文件常比命令返回晚
  5–10 秒落盘**，读之前先 `sleep 5–10`。
- 瞬时故障 `PrlJob_GetRetCode/GetResult: Invalid argument` —— 直接重试即可。
- 输出是 **GBK 与 UTF-8 混合**（cmd 内建命令 GBK、Rust 程序 UTF-8），单独 `iconv` 会报错；
  最可靠是**虚拟机侧写共享盘 → 宿主 Read**，或 `open(...,'rb').read().decode('gbk', errors='replace')`。
- **投进虚拟机的 `.cmd` 一律纯 ASCII**：中文（UTF-8）会被 cmd 按 GBK 解析、破坏引号配对，
  **整个脚本静默不执行**（现象＝输出文件根本没生成）。
- `cmd /d /c '...'` 单行内 `%VAR%` 会在解析时提前展开 → 用完整路径，或写成 `.cmd` 再
  `pushd \\Mac\backupRestore\.test-artifacts && x.cmd`（SYSTEM 会话无 `X:`）。
- **★ 铁律：还原/灌镜像执行期间绝不 `prlctl restart`。** `Unable to open new session in this virtual machine`
  的真意是「**已经在恢复环境里**」而不是"还没启动完"；先 `prlctl capture` 看屏。

### 6.2 文件与编码

- BSD `grep` 不支持 `\|` 交替与 `\b`（会**静默零匹配**，害人多次）→ 用 Grep 工具或 Python 正则。
- PowerShell 5.1 脚本必须带 UTF-8 BOM；否则按系统代码页（GBK）解码，中文字面量全乱。
- 子进程输出别假设 UTF-8：一律 `fs::read` + `from_utf8_lossy`。

### 6.3 启动链与对话框

- **`bcdedit` 的 `{current}` / `{default}` 是显示别名，不是存储损坏**：默认项等于本次引导条目时显示
  `{current}`，显式设过默认项后显示 `{default}`。
- 每个 stage 只自动续跑一次（`boot-resume-{stage}.attempted` marker）；第二次起保留现场不重启。
- **自动续跑只在「任务所在工作区副本」里生效**：workspace = exe 自身所在目录。本机自启的图形界面在
  `C:\Users\Public\backupRestore-package\`，**看不见** `H:\brwork\tasks\` 里的任务。
- **还原系统首次启动会弹「持续跑的还原任务」**（镜像内置的旧备份任务停在 Capturing）：
  按钮 `是(Y)` / `否(N)` / `取消`，**`否(N)` 是 Alt+N 加速键**——`vmkey.sh n` 单按无效，
  `vmkey.sh alt+n` 一次命中；**绝不能用 `enter`**（默认按钮是「是」，会重启续跑历史任务）。
- 恢复环境内没有 `prlctl exec`（无 Parallels Tools）：唯一交互通道 = `prlctl capture` 截图判状态 +
  `tools/win-clicker/vmkey.sh`（`prlctl send-key-event`，用 Parallels 键码）。

### 6.4 wimlib 与进度条

- wimlib 用 `\r` 原地刷新，一次 apply 是**三段**（`Creating files` → `Extracting file data` →
  `Applying metadata to files`），**每段各报 0–100**；进度窗按 `\r`/`\n` 拆行后由
  `parse_wimlib_progress` + `wimlib_overall_percent` 折成一条 0–100（权重 10/80/10）。
  **不要用 DISM 的 `parse_percent` 解析 wimlib 行**——行首是计数，拼出来必然越界 → 进度条恒 0。
- 日志落点三层：任务目录 `recovery.log`（只有 resume 三行）/ 镜像卷 `H:\BRImages\Recovery.log`
  （**跨重启的主日志**）/ `H:\brwork\Recovery.log`（常被运行中的图形界面占用）。
- `H:\brwork\Recovery.log` 被占用时 `findstr`/`copy` 都会失败 → 以 `H:\BRImages\Recovery.log` 为准。

### 6.5 部署

- **`-Deploy` 前必须先杀掉自启的图形用户界面**（它占着 `BackupRestore.exe`）：`--current-user` 的
  `taskkill` 报「拒绝访问」→ `Copy-Item` 失败 → `DEPLOY_EXIT=1`。必须走 SYSTEM 通道杀。
- 两路径产物**大小不同**，判断"部署的是不是刚编的"只能按 SHA-256，不能按大小。
  `artifacts/windows/BackupRestore-windows-arm64-v<版本>/` 里是**虚拟机原生产物**
  （`build-manifest.json` 的 `nativeMachine: ARM64` 可辨）。
