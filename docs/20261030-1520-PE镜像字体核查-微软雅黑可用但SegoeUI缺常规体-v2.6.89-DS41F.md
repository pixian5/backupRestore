# PE / RE 里的字体核查：微软雅黑可用，但 Segoe UI 缺常规体（v2.6.89）

> 模型：DS41F。时间：2026-10-30 15:20。
> 版本：**2.6.89**（改行为 +0.0.1）。
> 关联：`docs/20261030-1510-界面字体去掉加粗改常规字重-v2.6.88-DS41F.md`（本轮的起因）。

---

## 1. 问题

用户问：

> 「re/pe 下微软雅黑也能正常吗」

这个必须查，不能猜。原因：`CreateFontW` 请求一个不存在的字体**不会失败**，
Windows 会静默挑一个最接近的替代字体，程序拿到的句柄照样有效。
所以「代码里写了微软雅黑」和「屏幕上真的是微软雅黑」是两件事。

## 2. 查了哪三样

### 2.1 镜像里有没有字体文件

`wimlib-imagex dir C:\BackupRestorePE\BackupRestorePE.wim 1 --path=/Windows/Fonts`，
152 个文件里：

| 字体文件 | 在不在 |
|---|---|
| `msyh.ttc`（微软雅黑 常规 + 雅黑 UI） | **在** |
| `msyhl.ttc`（雅黑 细体） | **在** |
| `msyhbd.ttc`（雅黑 **粗体**） | **不在** |
| `simsun.ttc`、`mingliu.ttc` | 在 |
| `segoeui.ttf`（Segoe UI **常规**） | **不在** |
| `segoeuib / ii / l / sl / z .ttf` | 在 |

### 2.2 注册表有没有登记它

**字体文件躺在 `\Windows\Fonts` 目录里不等于能用**——Windows 的字体驱动是按
`HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion\Fonts` 这条键登记的字体启动的，
目录里有、注册表没登记就调不出来。

从镜像里把 `\Windows\System32\config\SOFTWARE` 单独抽出来（`wimlib-imagex extract`，
不挂载、只读），按 UTF-16LE 搜字体名：

| 名字 | 出现次数 | 含义 |
|---|---|---|
| `Microsoft YaHei` | 114 | **已登记** |
| `Microsoft YaHei UI` | 101 | 已登记 |
| `msyh.ttc` | 1 | 字体文件已登记 |
| `msyhbd.ttc` / `msyhsb.ttc` | 0 | 粗体/半粗**没有** |
| `segoeui.ttf`（常规） | 0 | **没有登记** |
| `segoeuib.ttf`（粗体） | 1 | 已登记 |

### 2.3 实机画面对不对

历史证据：`.test-artifacts/secboot-pe/19-pe-progress-2677.png`（2.6.77 在 PE 里跑的
恢复进度窗）。画面里的中文是无衬线黑体、笔画是雅黑的样子，**不是宋体、也没有豆腐块**。
说明当时就已经在用雅黑。

## 3. 结论

**微软雅黑在 PE / RE 里可用。** 依据三条同时成立：文件在、注册表登记了、实机画面是雅黑。

但有两个附带发现，都很重要：

### 3.1 PE 里的「加粗」是算法合成的

镜像里没有 `msyhbd.ttc`（雅黑粗体文件）。2.6.88 之前进度窗用的是字重 700 →
Windows 拿常规体**算法加粗**（把笔画描粗一圈）。这也解释了 2.6.77 那张截图里
中文为什么偏重、笔画有点糊。

**所以 2.6.88 把字重改成 400，对 PE 不是"变淡了"，而是从"假的粗体"换成"真的常规体"，
反而更清晰。**

### 3.2 PE 恢复桌面的三级字重全部错位（本轮修掉）

`BackupRestorePeDesktop`（PE 里的恢复桌面）原来请求 `Segoe UI` + 字重 **700 / 600 / 500**
做三级层次。但这套镜像里 Segoe UI **只登记了 Bold(700) / Light(300) / Semilight(350) /
Italic，没有常规体 400**。GDI 按"最接近"挑：

| 代码写的 | 实际画出来的 | 为什么 |
|---|---|---|
| 700（标题 44px） | Segoe UI Bold | 正好命中 |
| 600（卡片 30px） | **Segoe UI Bold** | 600 离 700 比离 350 近 |
| 500（底栏 18px） | **Segoe UI Semilight(350)** | 500 离 350 比离 700 近 |

也就是**一个写着三级的层次，实际只有"粗"和"很细"两种**，而且和代码写的不是一回事。

改法：换成 `Microsoft YaHei` + 统一字重 400，字符集与主界面一致用 134。
层次改由**字号**（44 / 30 / 18）承担——不靠字重，就不存在"挑不到对应字重"的问题。

## 4. 验证到什么程度

| 项 | 结果 |
|---|---|
| PE 镜像里雅黑文件在、注册表已登记 | ✅ 见 §2.1 / §2.2 |
| 雅黑在 PE 里实际画得出来 | ✅ 2.6.77 实机截图（当时是算法加粗的雅黑） |
| 2.6.88 的常规字重（400）在 PE 里可用 | ✅ 逻辑上必然（`msyh.ttc` 就是常规体文件，已登记）；**但没在 PE 里目视确认** |
| 2.6.89 的 PE 恢复桌面换成雅黑 | ⚠️ **完全没在 PE 里看过**——要重启进 PE 才能看 |
| 宿主机类型检查 | ✅ 0 新警告 |

**诚实口径**：前两条是硬证据（文件 + 注册表 + 历史截图），后两条是**推断 + 待验证**。
PE 恢复桌面这次改动只有外观影响，不会影响任何备份/还原逻辑，但"看着对不对"必须进 PE 才知道。

## 5. ⚠️ 一个跨版本的风险（值得单独记）

`CreateFontW` 的静默回退意味着：**将来只要有人改 PE 镜像、把 `msyh.ttc` 精简掉，
整个界面会在不报任何错的情况下换成别的字体**（中文大概率变豆腐块），
而所有自动化判据都察觉不到——它们不检查"画出来的字形"。

建议（尚未实现）：启动时用 `GetTextFaceW` 把 GDI **实际选中**的字体名写进 GUI 日志一次。
这样"字体到底生效没有"就从不可见变成可查，代价只有一行日志。

## 6. 遗留

1. PE 内恢复进度窗（2.6.88 改字重）与 PE 恢复桌面（2.6.89 换字体）都**没有实机目视**。
   下次进 PE 时一并看：进度窗中文是否清晰、恢复桌面标题/卡片/底栏三级字号是否协调。
2. 开机菜单（`boot_menu_window.rs`）仍用系统字体 `GetStockObject(17)`，未跟随；
   它在 `bootmgr` 阶段由 Windows 侧绘制，与 PE 不是同一条渲染路径，本轮未动。
3. 上面那条「启动时打一行实际字体名」的日志，未实现。

## 7. 2026-10-30 15:40 补记：真机进 PE 实测完成（本节取代 §4 的「未验证」口径）

用户当场要求「实测」，于是**真的重启进 PE 三次**做了验证。结论：**全部成立**，并且发现了一个
比字体重要得多的事实。

### 7.1 先说那个更重要的事实：PE 里的程序是镜像内的副本

PE 的启动链是：

```
boot.wim → \Windows\System32\winpeshl.ini
         → [LaunchApps] %SYSTEMROOT%\System32\Recovery.exe,--pe-desktop
```

也就是恢复桌面是 **`Recovery.exe`** 画的，而它**在镜像里**，不是 `H:\brwork\BackupRestore.exe`。
推论（此前被我漏掉）：

> **改代码不会自动改变 PE 里看到的东西。必须用新包重建 `boot.wim` 并重新安装，PE 才会变。**

第一次进 PE 时标题是 `v2.6.77`。我还试过直接把新的 `BackupRestore.exe` 用 `wimlib update`
塞进 `sources\boot.wim`——重启后标题**仍然是 v2.6.77**，因为我改的是 `BackupRestore.exe`，
而启动跑的是 `Recovery.exe`。**改错了文件。**

### 7.2 正确的做法（已跑通）

1. 把 `dist/BackupRestore-2.6.89-windows-arm64.zip` 解到
   `C:\BackupRestorePE\package\BackupRestore-windows-arm64-v2.6.89\`；
2. 跑 `poc/build-backuprestore-pe.ps1 -SkipIso -Package <上面那个目录>`（DISM 挂载 + 拷贝 + 压缩，
   约 40 秒），产出 `C:\BackupRestorePE\BackupRestorePE.wim`；
3. 用测试钩子（`C:\br-test.json` + `--test-hook`，`tab=pe / mode=ram / auto_install=true`）
   自动安装：把 wim 拷到 `sources\boot.wim` 并建 BCD 项；
4. `bcdedit /set {bootmgr} bootsequence <项GUID>` + 重启 → 进 PE 看。

**判据不是脚本自报**：从新 wim 里抽出 `\Windows\System32\Recovery.exe` 算 SHA-256 =
`b7d24189…`，与 2.6.89 包里的 `Recovery.exe` 完全一致；PE 界面标题显示 `v2.6.89`。

### 7.4 环境状态

不过它和桌面用的是**同一个字体文件、同一个字重常量**（`FW_NORMAL = 400`），桌面已证实渲染正常，

## 8. 2026-10-30 16:12 补记：恢复进度窗也看到了（§7.5 作废）

§7.5 说「PE 内恢复进度窗没看到」。用户要求继续实测，于是**腾出空间真跑了一次备份**，
进度窗拿到了。

### 8.1 先纠正上一节的判断：那张图不是进度窗

第一次用 `--test-fault identity-env-mismatch` 进恢复环境，看到的窗口是
「BackupRestore 恢复需要处理」+ 重试/取消。**它是 `MessageBoxW` 弹的**
（`failure_policy.rs`），用**系统字体**，不是我们的控件 —— 拿它证明字体改动是错的。
查源码确认：那段文案在 `failure_policy.rs` 里，`MessageBoxW` 需要 NUL 结尾标题的注释就在同一处。

**教训**：截图里有中文，不等于「验到了自己的字体」。先确认那个窗口是谁画的。

### 8.2 怎么才看得到真进度窗

- `power-loss-window` 这个故障注入名不副实：它只是「写完 boot-requested 状态就停住、
  不关机」（日志原话 `stopped after durable boot-requested state; no shutdown requested`），
  任务根本没进恢复环境；
- 而 `identity-env-mismatch` 在开工前就失败，进度窗不会出现。

真进度窗只在**复制阶段**出现，所以必须真跑。空间判据是「已用字节 + 保留量」：
C: 已用 68.6 GiB，把 `H:\BRImages\r0-c-2677.wim`（30,284,953,404 字节 = 28.2 GB）
移到宿主 `.test-artifacts/wims/` 后 H: 空出 83.5 GB，够用。
**移之前做了 SHA-256 两侧比对：`8e38c478…` 一致**，是「移动」不是「删除」，可回退。

### 8.4 顺带验证到的

- 恢复环境的**自动回退**正常：第一次失败后按 Esc 取消，机器自行重启回 Windows；
- `prepare` 会自己把恢复环境写进 `H:\BackupRestoreRE\<task>\Winre.wim` 并设一次性引导

  但恢复流程不走它。
