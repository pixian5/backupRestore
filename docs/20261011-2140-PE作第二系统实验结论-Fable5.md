# PE 作第二系统实验结论：create-secondary 拒绝纯 WinPE（Fable 5）

时间：2026-10-11 21:00–21:40。回答用户早先的问题：
**「新增第二系统」+ Windows PE boot.wim，能否把 PE 直接做成第二个系统（双系统）？**

## 一、结论（一句话）

**不能。** 「新增第二系统」(`create-secondary`) 期望一个**完整 Windows 映像**
（含 `SYSTEM` 注册表 hive 与 `reagentc.exe`），因为它要对目标卷做
**离线 WinRE 注册 + BCDBoot** 才能把它变成真正可引导的第二 Windows。
纯 WinPE 的 `boot.wim` 缺这些组件，在恢复阶段的注册前置检查就被拒。

## 二、实验设计

- 产物：2.3.0 `BackupRestore.exe`（`bfdb77c7…96808`），客体部署三处哈希一致。
- 隔离目录 `F:\PE2OS\{app,images}`（避开其它任务），镜像用客体内现成的
  ARM64 PE `C:\BackupRestorePE\media\media\sources\boot.wim`
  （SHA-256 `C06FA2D2…A4DE`，纯 WinPE，无完整 Windows）。
- 命令：
  ```
  BackupRestore.exe prepare --operation create-secondary \
    --source-drive C --target-drive E \
    --image-path F:\PE2OS\images\boot.wim \
    --boot-menu-name "BackupRestore PE Lab" --allow-destructive
  ```
- 启动事务前已建快照 `{86c4da7b}`（`20261011-2135-pe-create-secondary`）。

## 三、实机结果

1. **prepare 成功**：创建任务 `71d7bc04-ee5c-4363-bcdf-46a150c4c777`，
   武装一次性启动，重启进 WinRE。
2. **恢复阶段失败并弹对话框**（截图
   `pe-secondary-registration-failed.png`）：

   > 恢复暂未完成：invalid task: **目标缺少离线注册组件**
   > 已保存的任务与恢复材料会保留。排除磁盘、镜像或空间问题后选择"重试"，
   > 继续同一任务；选择"取消"进入系统恢复工具。
   > 恢复已完成的任务只重试清理，不会再次擦除目标。

   报错点在 [winre_registration.rs:306](../crates/backuprestore-cli/src/winre_registration.rs#L306)
   的 `preflight`：注册前要求目标卷存在
   `Windows\System32\reagentc.exe` 与 `Windows\System32\config\SYSTEM`，
   纯 WinPE 两者皆无，于是报「目标缺少离线注册组件」。

## 四、为什么这是正确行为

「新增第二系统」的语义是**造一个真正的、可持久引导的第二 Windows**：
格式化目标卷 → DISM 应用完整 Windows 映像 → BCDBoot 写引导 →
离线注册该系统自己的 WinRE。纯 WinPE 不是完整 Windows——没有 SYSTEM hive、
没有 reagentc，无法被注册，也不该被当成常驻系统。产品在**擦除目标后、
写引导前**的注册前置检查里拦住，是合理的失败边界，不是缺陷。

> ⚠️ 代价提示：失败发生在**目标卷 E: 已被格式化、PE 已被应用之后**。
> 也就是说，纯 PE 走 create-secondary 会先擦掉目标卷才失败。产品靠
> 「失败对话框 + 保留任务 + 不再二次擦除」把损失封在目标卷内（本就是用户
> 指定要重写的卷），但用户若误选 create-secondary 装 PE，目标卷数据已没了。
> **这是一个值得提给用户的 UX 风险**（见第六节）。

## 五、正确做法：PE 用 ramdisk 路径，不是 create-secondary

要引导 PE，产品另有一条独立功能——「PE 恢复」(`install-pe-entry`)，
**有两种启动方式**：

- **ramdisk（内存）**：`ramdisk=[X:]\...\boot.wim,{ramdiskoptions}`，把整个 WIM
  读进内存运行，不格式化、不写磁盘系统；
- **硬盘版（独立分区）**：和 create-secondary 一样**格式化分区 + DISM 应用 +
  分区直启**（`device partition=X:` + `path \Windows\system32\winload.efi`），
  但 BCD 用 `bcdedit /create` 手工建项并**显式打上 `winpe yes` + `detecthal yes`**，
  **且不做离线 WinRE 注册**。

> **更正（2026-10-11 22:xx）**：本文初稿把 PE 恢复说成"只能走 ramdisk / 内存临时"，
> 是错的。硬盘版 PE 同样是分区直启、同样用 bcdedit 建项落在独立分区上。
> 真正让 create-secondary 对纯 PE 失败的，**不是"分区 vs 内存"**，而是收尾时
> 产品"拿它当什么对待"：

| | 新增第二系统 (create-secondary) | PE 恢复·硬盘版 | PE 恢复·ramdisk |
|---|---|---|---|
| 格式化 + DISM 应用到分区 | ✅ | ✅（完全一样） | ❌（复制到目录） |
| 分区直启 `partition + winload.efi` | ✅ | ✅（一样） | ❌（ramdisk） |
| BCD 建项 | `bcdboot`（**无 `winpe yes`**） | `bcdedit /create`（**手打 `winpe yes`**） | `bcdedit /create`（ramdisk + `winpe`） |
| 离线 WinRE 注册 | **要**（reagentc + SYSTEM hive） | 不做 | 不做 |
| 纯 PE 能否成功 | ❌ 卡在注册前置检查 | ✅ | ✅ |

关键在那个 **`winpe yes`** 标志：它告诉 winload"这是临时 PE，按内存驻留启动，
别指望磁盘上有完整系统注册表状态"。create-secondary 用 `bcdboot` 生成的是
**常规 Windows 启动项（无 `winpe yes`）**，并假定目标是完整安装的 Windows，
还要对它做离线 WinRE 注册——注册要 `reagentc.exe` + `SYSTEM` hive，纯 PE 没有，
于是失败。硬盘版 PE 把它当 PE 对待（`winpe yes`、不注册），所以同样是
"格式化 + 应用到分区"，一个成一个败。

硬盘版 PE 的 BCD 项用 `bcdedit /displayorder /addlast` 加成**永久启动菜单项**
（不是一次性 `bootsequence`），因此是**持久**的——详见第八节实测。

## 六、建议优化（提给用户拍板）

create-secondary 在**格式化目标卷之前**就能知道镜像是不是完整 Windows
（prepare 阶段 DISM `/Get-WimInfo` 已读过 WIM，或可加一次离线挂载探测
`reagentc.exe`/`SYSTEM` 是否存在）。**建议把"目标缺少离线注册组件"这个检查
从恢复阶段（擦除后）前移到 prepare 阶段（擦除前）**，纯 PE 直接在准备期拒绝，
给出"请改用 PE 恢复·硬盘版/内存版"的提示，避免先擦目标卷才失败。这与现有要求
（增加详细日志帮助发现问题、主动提示优化方向）一致，但属产品行为改动，
按规矩由用户决定是否做。

## 七、清理

实验是破坏性的（格式化 E:），**用启动事务前的快照 `{86c4da7b}` 回滚**，
E: 恢复到实验前内容（`BRRE213` + `testdata`），BCD 与任务一并还原。
符合 AGENTS.md：启动变更事务触发前已建专用快照，失败后用它回滚。

## 八、硬盘版 PE 实测：持久化 + 备份还原后仍在

用户追问：硬盘版 PE 是不是持久的？做完一次备份/还原后它还在吗？实测如下
（经 GUI 测试钩子 `--test-hook` + `C:\br-test.json` 的真实产品路径安装，
不是手搓命令；证据见 `F:\BR\logs\gui.log`）。

### 1. 持久化：是，而且是设计使然

硬盘版 PE 装到独立分区 E:（格式化 + DISM 应用 PE WIM），BCD 项
`{7c41385a-c575-11f1-8940-b2a8069664aa}` 的几个关键字段实测回读：

```text
device    partition=E:
path      \Windows\system32\winload.efi
winpe     Yes          ← 关键：当 PE 启动
detecthal Yes
```

且该项用 `bcdedit /displayorder /addlast` 加成**永久启动菜单项**，实测确实
进了 `{bootmgr}` 的 `displayorder`（续行里）——**不是**一次性 `bootsequence`。
所以它跨重启持久存在，和产品恢复用的「一次性 WinRE 启动通道」完全相反
（后者 `bootsequence` 自清、用完即弃）。

### 2. 备份还原后：仍在

装好硬盘版 PE 后，用产品对**另一个分区 T:** 跑了一次完整 restore-existing：
prepare → 进 WinRE（`wpeinit`、挂载 RECOVERY/SOURCE/IMAGE/TARGET/EFI、
diskpart、改 ESP 上的 BCD）→ 还原 → 清理 → 回到 Windows，任务终态 `success`。

还原**全程 PE 不受影响**，逐步实测：

| 时点 | PE BCD 项 `{7c41385a}` | `E:\Windows\...\winload.efi` |
|---|---|---|
| prepare 后（已武装一次性启动） | ✅ 仍在 displayorder | ✅ 在 |
| 还原 success 后（已清理、回到 Windows） | ✅ 仍在 displayorder | ✅ 在 |

原因：还原走的是**独立的一次性 `bootsequence` 通道**，清理只撤销它自己这次任务
建的 BCD 对象并把 `{bootmgr}` 恢复到**准备期快照**；而准备期快照是在 PE 装好
**之后**导出的，`displayorder` 里本就含 `{7c41385a}`，恢复快照自然把它留住。
孤儿 resume 清理也只删「loader 已不存在」的对象，PE 的 loader 还在，不算孤儿。

> ⚠️ 边界：本次测的是**数据卷 T:** 还原（跳过 BCDBoot）。**系统卷**还原会多跑
> 一次 BCDBoot（重写 `{bootmgr}` default/displayorder/resumeobject）。按代码，
> `preserve_primary_boot_manager` 同样把 displayorder 恢复成准备期快照值（含 PE 项），
> BCDBoot 的 `/addlast` 只追加不删除，所以系统卷还原也应保住 PE——但这一条
> **尚未单独实机验证**（需 35GB 系统镜像 + 完整 BCDBoot），仅代码推断。

### 3. 清理

硬盘版 PE 实验同样破坏性（格式化 E:），用 PE 安装前快照
`{faca0ab1}` 回滚：E: 恢复 `BRRE213`+`testdata`、PE BCD 项消失、
`C:\br-test.json` 清除。只保留该一个干净基线快照。
