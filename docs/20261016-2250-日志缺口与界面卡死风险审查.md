## 一、日志不够完整甚至没有的环节

### 高严重度

#### 1. DISM 预检输出全丢 —— GUI「创建任务」后第一道失败点
- **位置**：`windows_prepare.rs:1660-1662`（`mount failed`）、`1675-1676`（`unmount failed`）、`1696-1697`（`Get-WimInfo failed for image name`）
- **缺什么**：`run()` 走 `.output()` 但**只取 `status`**，DISM 的 stdout/stderr 全部丢弃。
- **后果**：用户在 GUI 点「创建任务」→ 镜像探测失败 → `prepare.log` 只有一句无原因的错误。DISM 真实原因（错误 87 / 镜像被占用 / 路径不可访问 / 挂载点残留）**一个字都没留下**。事后只能盲猜重试，无法定位。
- 这是**用户交互之后最常见的第一道失败**，因此排在第一。

#### 2. GUI 线程 panic 载荷丢失 + 全仓无 panic hook
- **位置**：`native_gui.rs:6962-6969`
  ```rust
  let result = std::panic::catch_unwind(|| crate::online_operation::execute(&params))
      .unwrap_or_else(|_| OnlineResult {
          success: false,
          detail: "在线执行线程异常退出，请检查本轮日志和候选目录；不能判定为成功。".into(),
      });
  ```
  `unwrap_or_else` 的 `|_|` **把 panic 载荷（含断言消息、文件行号）整个丢掉**。
- **补充核实**：全仓 `grep -rn "set_hook|panic::set"` **无任何命中** —— 没有 `std::panic::set_hook`。
- **后果**：windows subsystem 程序没有控制台，panic 消息既不打屏也不进 `gui.log`。在线备份/还原线程 panic 后，日志只有上面那句通用文案，**不知道是哪个 `expect`/`unwrap`/断言炸的**。

#### 3. RE 入口 `reg.exe` 探测静默跳过 `wpeinit`
- **位置**：`main.rs:845-852`
  ```rust
  if std::process::Command::new("reg.exe")
      .args(["query", r"HKLM\SYSTEM\CurrentControlSet\Control\MiniNT"])
      .output()?
      .status.success()
  { run_logged("wpeinit.exe", &[], &init_log)?; }
  ```
  `reg query` 非零退出 → **静默跳过 wpeinit，不留任何痕迹**（此刻除 `init_log` 外的日志都还没开）。
- **后果**：WinRE 内键盘/设备未初始化类故障，事后**无法区分**是否走了这条分支，也无法知道 `reg query` 自己失败的原因。

#### 4. `recover` CLI 路径：`?` 用写盘错误**替换**原始错误
- **位置**：`main.rs:816-818`
  ```rust
  if let Err(error) = &result {
      store.write_recovery_error(&task, error.to_string())?;
  }
  ```
  若 `write_recovery_error` 自身失败，`?` 会用**写盘错误**替换掉原始恢复错误向上传播。
- **另一处割裂**：同一条 `recover_windows` 失败，RE 内路径（`main.rs:1412-1428`）会 `append_log` 到 `Recovery.log`；`recover` 命令路径只写 `status.json`，**不写 `Recovery.log`**。
- **后果**：GUI 文案引导用户「查看 Recovery.log」，但这条路径下日志里**没有错误内容**。

## 二、可能卡死且无补救 / 补救不可靠的界面

### 高严重度

#### 1. RE「暂停在恢复环境」弹框 —— 无超时、无自动逃生
- **位置**：`main.rs:916-955`（弹框在 930 行 `MessageBoxW(..., 0x10034)`）
- **卡死条件**：用户选 `pause` 策略、连败达阈值 → 弹「是/否」模态框停在恢复环境。无人值守 VM / 键盘未就绪 → **永久等待**。注释原文：「弹框是模态的：不点就一直等，这就是『暂停在恢复环境里』的语义」。
- **补救**：**无**。`auto-escape` 分支（899-912 行）有自动逃出；`pause` 分支**刻意去掉自动逃出且无任何超时兜底**。选「否」只是 `continue` 重试，确定性故障时反复弹同一个框。
- **逃生只能靠人按键。**

#### 2. PE 桌面执行期间整窗禁用 + DISM INFINITE
- **位置**：`native_gui.rs:8850-8852`
  ```rust
  EnableWindow(hwnd, 0);
  let result = crate::pe_operation::execute(&request);
  EnableWindow(hwnd, 1);
  ```
  INFINITE 等待在 `pe_operation.rs:329 / 928 / 944 / 1007`（四处 DISM）。
- **卡死条件**：PE 桌面点「备份/还原系统」→ DISM 挂死（I/O 挂起等）→ `execute` 永不返回 → **`EnableWindow(hwnd, 1)` 永不到达**，PE 桌面窗口永久禁用（不能点、不能关）。
- **补救**：**有但有限**。进度窗是独立线程的顶层窗，可用「命令提示符(K)」开 cmd 跑 `wpeutil reboot`、或走 BCD 回退；但 **PE 桌面本身残废**，且依赖用户知道这条键路。

#### 3. 主 GUI「安装 PE 到硬盘」在 GUI 线程同步等 DISM
- **位置**：`native_gui.rs:5041`（`run_cmd_to_file_timeout(..., INFINITE)`），调用链 `4367 install_pe_entry` → `4779 install_pe_harddisk`，**从 WM_COMMAND 同步调用，不开线程**。
- **卡死条件**：`dism /Apply-Image` 挂死 → 主窗口消息循环被阻塞，整窗「未响应」、无进度、无取消。
- **补救**：**无窗口内手段**，只能任务管理器杀进程。正常情况冻结数分钟。

### 中-高严重度

#### 4. 暂停中 + 关闭进度窗口 = 恢复线程永久空转
- **位置**：`recovery_progress.rs:178-188`（`wait_if_paused` 无超时自旋）+ 主进度窗 `window_proc`（1000-1308 行）
- **核实要点**：主进度窗口 `window_proc` **没有 `WM_CLOSE` 分支** → 落到 `_ => DefWindowProcW` → 默认 `DestroyWindow`。（`recovery_progress.rs:982` 那个 `WM_CLOSE` 属于**日志子窗口**，只做 `ShowWindow(SW_HIDE)`，别搞混。）
- **卡死条件**：用户按 P 暂停 → 关闭进度窗口 → 恢复线程永远在 `while paused { sleep(200ms) }` 自旋。进程存活但**无任何 UI、无超时、无出口**。
- **WM_DESTROY 分支（1292）只做**：`KillTimer` + 销毁日志弹窗 + `PostQuitMessage(0)` —— **没有通知恢复线程停止**。
- **补救**：无自动机制。杀进程后 `bootsequence` 仍武装，重启回 RE 重来。

### 中严重度

#### 5. `close_and_wait` join 无超时
- **位置**：`recovery_progress.rs:1347-1353`，调用点 `main.rs:1130`
- **卡死条件**：窗口线程卡在 `refresh_from_log`（376-454 行，日志增量巨大时一次性读全量进内存）或 BCD 回退闭包（1257-1260 行持锁执行 bcdedit）→ 恢复链 `join` 永久阻塞，连失败重试弹框都到不了。

#### 6. 在线操作 DISM INFINITE + 「创建任务」按钮永久禁用
- **位置**：`online_operation.rs:111`（`run_program("dism.exe", args, Some(log_path), INFINITE)`）、`1043`（`long` 分支）；按钮禁用 `native_gui.rs:6959`，恢复在 `7608`
- **卡死条件**：在线备份/还原 DISM 挂死 → 工作线程永久等待，按钮与状态永远停在「执行中」。
- **补救**：主窗口仍可关闭程序 → 杀进程即可。**不算永久**。
- （好在在线路径前后各有一条日志：`log(... "DISM 开始（等待至退出，无固定超时）")` / `"DISM 结果：..."`，这是在线路径比 prepare 路径强的地方。）

#### 7. `recover_env` 入口前置 `?` 不经 `auto_escape` → 重启打转
- **位置**：`main.rs:845-852`（`reg query` 与 `wpeinit` 的 `?`，都在恢复循环**之外**）
- **卡死条件**：入口步骤失败 → 直接 `return Err` → 进程 `exit(1)`；`auto_escape_to_windows` 只在 `recover_env` 失败**之后**才跑 → 一次性启动项仍武装 → 每次重启进 RE 同样退出，**无限循环**。
- **补救**：有但**不可靠** —— 只有跨出宿主改 BCD（正是仓库文档记载的历史事故模式）。

#### 8. `boot-resume` 一次性标记用尽后 GUI 无续跑入口
- **位置**：`main.rs:525-539`
- **失效条件**：自动续跑一次仍失败 → 任务停在可续跑阶段但不再自动重启；GUI **无任何出口**（仅 CLI `resume`），用户面对挂起任务无从下手。

### 低严重度

| # | 位置 | 说明 |
|---|---|---|
| 9 | `native_gui.rs:8182-8343` | PE 任务对话框无 ESC（有 X/取消可退，仅 ESC 无效） |
| 10 | `boot_menu_window.rs:130-132 / 211-218` | 引导修复编辑器控件锁定，靠 500ms 定时器重绘探测解锁；若永不解锁只剩 Esc/关闭（有出口） |

### 已核实「无问题」的项（防误报）
- **四个模态弹窗的 `EnableWindow` 配对可靠**：`native_gui.rs:3041/3065`、`3212/3230`、`3578/3596`、`8684/8710`。窗口被外部销毁时 `IsWindow` 短路退出循环，`EnableWindow(hwnd,1)` 仍执行；ESC/取消/X 齐全。唯一缺口是第 2 条（`execute` 不返回）。
- 全仓 `WaitForSingleObject` **均有超时**（1500ms/10s/60s）；INFINITE 只出现在 DISM 等待（`pe_operation.rs`×4、`online_operation.rs`×2、`native_gui.rs`×1，共 7 处）。
- `boot_menu_window.rs` 编辑器为**非模态**（未禁用父窗），不构成残废路径。

## 三、交叉观察：卡死与无日志往往是同一处

本次审查最有价值的发现不是单点，而是**重叠**：

| 重叠点 | 日志缺口 | 卡死风险 |
|---|---|---|
| `main.rs:845-852` | 静默跳过 wpeinit，不留痕 | `?` 不经 `auto_escape` → **重启打转** |
| `windows_prepare.rs` DISM 预检 | stdout/stderr 全丢 | GUI「创建任务」后最常见失败点，事后无法定位 |
| `native_gui.rs:6962-6969` | panic 载荷丢弃、无 hook | 界面无响应后**连排查线索都没有** |

三个结构性结论：

1. **INFINITE 等待共 7 处，全部用于 DISM。** DISM 是唯一可能长时间挂住的外部依赖，而它的挂起会**同时**触发「窗口禁用/阻塞」和「无进度可见」。这是最大的单一风险面——一处改动（给 DISM 加超时 + 保留现场）能同时缓解 3 个高严重度卡死点。

2. **`pause` 与 `auto-escape` 存在设计不对称。** `auto-escape` 有自动逃出兜底，`pause` 刻意没有。这在「有人值守」语义下是对的，但在**无人值守**场景下等于放弃这台机器。若 `pause` 加一个「最大等待时长后自动逃出」的选项，可同时消掉第 1 条高严重度与「用户不点就永久挂」的隐患。

3. **日志缺口集中在「GUI 用户操作之后」和「RE 无人值守时」两端**，恰好是**没有人盯着屏幕**的两个时刻——也就是最需要日志的时刻。反过来，`write_transition` / `run_logged` / `capture_logged` 这些有意识封装的路径反而覆盖良好。缺口几乎都来自**手写 `.output()` / `Stdio::null()` 的散点**，收敛方式明确。
