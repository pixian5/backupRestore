## 一、这项目是什么

**一句话**：Windows 桌面程序，用户在正常 Windows 点「备份/还原」→ 程序自己准备任务 → 重启进系统自带 WinRE → 离线跑 DISM → 修好引导 → 自动回到 Windows。**全程不需要 U 盘、BIOS、命令行。**

需求原文（根目录 `Windows 一键系统备份还原 V1——完整开发需求.md`，1449 行 / 33 节）首句即约束：

> 先做 V1，不要擅自扩展成完整 Ghost/PE 工具。

**明确不做**：增量/差异备份、网络备份、自研镜像格式、自研 bootloader、自带完整 WinPE、Legacy BIOS/MBR、动态磁盘、Storage Spaces、分区重构、自动处理 BitLocker。

这个"不做清单"解释了后面几乎所有设计取舍——项目不是 Ghost 竞品，是**"系统自带 WinRE 的自动化包装器"**。

### 为什么必须离线走 WinRE（不是可选优化，是被逼的）

1. 系统卷在线被占用，不能 Capture、更不能格式化；在线热备要 VSS，而 VSS 不在 V1 范围。
2. 测试机就是最坏场景：WinRE 注册在 **C: 本身**（`C:\Recovery\WindowsRE`），无独立 Recovery 分区。而"备份/还原系统盘"恰恰是主场景。
3. 需求 §16 明令：**不许降级成"用户自己开命令提示符"**。证明不了自动入口就必须标为阻塞。

## 二、三条入口与能力差异（理解全项目的钥匙）

GUI 按「受影响卷 == `%SystemDrive%`」分流（注意：判定基准是 %SystemDrive%，**不是"含 Windows 的卷"**——双系统里另一个 Windows 卷可在线处理）。

| | **WinRE 任务链**（主线） | 预装 PE 恢复 | 在线执行 |
|---|---|---|---|
| 触发 | 受影响卷 == 系统盘 | 同上，用户选 PE | 受影响卷 ≠ 系统盘 |
| 重启 | 是 | 是 | **否** |
| 任务状态机 | **有**（11 Stage） | 无 | 无 |
| 格式化 | 会 | 部分形态会 | **不会** |
| 引导修复 / bcdboot | 会 | **不会** | **不会** |
| 断电续跑 | **会** | 无 | 无 |
| 还原索引 | 用户指定 | **固定 Index 1** | 用户指定 |
| 镜像副档 | 生成并同步 | **不生成** | 生成并同步 |

**PE 为什么是"简化路径"**：根子在一条用户硬要求——**PE 内零点击**。为免用户在 PE 里手敲命令，早期用 ESP 上的配置文本驱动，绕开了任务契约，代价是上表 8 项能力全丢。统一三条入口是清单里的 **W09，至今未做完**。

⚠️ **术语陷阱**：v1.8 之后主 WinRE 链也改走 ramdisk + 自建 BCD（文档俗称"PE 式通道"），但它是**完整任务链**；与"预装 PE 简化通道"**同名不同物**。

## 四、核心机制：任务状态机 + 断电续跑（产品的灵魂）

**11 个 Stage**：`Prepared → BootRequested → RecoveryStarted → Preflight → Capturing → TargetErased → ImageApplied → BootRepaired → RecoveryComplete → Success / Failed`
用 `can_transition_to` 白名单控跳转；`is_destructive_boundary()` 标出三个不可逆点（擦除 / 应用 / 修引导）。

**断电续跑靠四层叠加**：

1. **载荷按任务 ID 隔离在镜像卷** —— `BackupRestoreRE\<task-id>\Winre.wim`。不在注册位、不在 servicing 管辖区。这是 2.2.0 的核心改动，一次性解掉 F1/F2/F3/F4。
2. **状态事务** —— `commit_state()` 先写 `state-transaction.json` 再重放拆落到 `task.json` + `status.json`；每次 `load()` 前都重放 → 任意写入边界断电自愈。
3. **原子写** —— `MoveFileExW(REPLACE_EXISTING|WRITE_THROUGH)` 后再 `FlushFileBuffers` 才返回成功。
4. **`rearm()` 重武装** 自己的 `bootsequence` + `claim_boot_resume_attempt()` 给**每 Stage 一次**重试额度（防无限重启循环）。续跑入口：`main.rs::resume_pending_boot_task()`，已在 `native_gui.rs:7616` 接线。

**实测成绩**：25 个真实断电点（`prlctl stop --kill` 硬断电）。核心断言反复成立——`FORMAT_COUNT=1`、`APPLY_COUNT=1`（35.6 GB 系统镜像 6 次断电只应用一次）、BCD 逐字节回基线 diff=0。

## 五、启动链硬约束（最难、最危险）

### 5.1 WinRE 注册的硬约束（结论经过一次修正，**勿按旧结论操作**）

- **2026-09-27 原始结论**：WinRE 强校验「启动 ramdisk 路径 == ReAgent 注册位置」，四条绕法全证伪。
- **2026-09-29 修正（当前产品依据）**：被校验的其实是 **ReAgent 登记的那个 BCD 对象** + `reagentc /boottore` 写下的 bootstatus，**不是任意 BCD 条目的路径**。自建条目指向镜像卷副本 → **成功进 PE 并拉起载荷**。早期失败是因为改的都是"被登记的那个对象"。
- **路径不一致的代价**：`reagentc /boottore` 返回 **RC=2**，bootstatus 不设 → WinRE 被拉起也**静默自退**。

### 5.2 注册位只能时间分片

`R:\Recovery\WindowsRE\Winre.wim` 一个文件要扮演两个互斥角色：

| 角色 | 要求 | 谁要求 |
|---|---|---|
| **P 载荷宿主** | 注入件（自动拉起 Recovery.exe） | 断电续跑 |
| **C 捕获纯净** | 微软原版 | DISM 捕获瞬间 |

**三条不变量**：A 任务存活期必须是注入件 / B 捕获瞬间必须干净且**硬失败** / C 终态必须干净。

**servicing 会静默替换它**：2026-09-27 部署的载荷当天就被累积更新冲成官方原版（714,409,997 B → 709,810,082 B，内部 `Recovery.exe` 消失）。所以**注册 WinRE 不是可靠的载荷宿主**——这直接推动了载荷搬到镜像卷。

### 5.3 卷身份与路径规则

- **卷身份 = `disk_guid + partition_guid`**，不是盘符、不是磁盘序号。
- `volume_path()` 产出 `\\?\Volume{GUID}\`，**零盘符直接读写 ESP**。
- **盘符会重排**：桌面 `T:/P:/H:` → WinRE 里是 `D:/F:/G:`。WinRE 内 `SYSTEMDRIVE=X:`。**绝不硬编码盘符**。
- 卷 API 吃 `\\?\Volume{GUID}\`，设备 API 吃 `\\.\Volume{GUID}\` —— 必须 `volume_path_to_device_path()` 转换，否则 161 BAD_PATHNAME。

### 5.4 绝对禁止的操作（踩错就是机器起不来）

| 禁止 | 后果 |
|---|---|
| 对**真实 ESP** 跑 `bcdboot X:\Windows /s S: /f UEFI` | bootmgr 的 default/displayorder 被改写 → **下次启动进错系统**（已发生过一次）。要试只能在"假 ESP"上做 |
| 在 WinRE **入口**立即把注册位翻干净 | 违反不变量 A → 续跑落进原版 WinRE 起不来，还白烧重试额度 |
| 复用/改写 ReAgent **已登记**的 BCD 对象 | 无 `/boottore` 时 8 秒内被 bootmgr 丢弃 |
| `ramdisk=` 值拼错（`]` 位置） | 两种错法报不同的错，曾把排查带偏一整轮 |
| 载荷注入完成**前**武装 `bootsequence` | `--no-reboot` 也会改 bootmgr → 下次重启直接进 PE |
| 先删 BCD 对象再清 `bootsequence` | 中途断电留下指向已删对象的启动请求 |
| `bcdedit /delete` 后**立即重启** | **对象复活**（需等 60–90 秒） |
| 夺走不属于本任务的 `bootsequence` | 开进的不是设置它的人期待的环境 |
| WinRE/PE 里直接用 `reagentc` | **不存在**（rc=9009）；必须全路径调目标 OS 的 `<目标>:\Windows\System32\reagentc.exe` |
| PE 里 `reagentc /disable` | rc=50「Windows PE 中不支持此命令」；顺序只能是 setreimage → enable |
| `prlctl send-key-event --key enter` | 无效键名，退出码 255 且**静默无效**；必须用 `--scancode`（Enter=28、Tab=15） |
| WinRE 里用持续型故障注入 | WinRE 无 Parallels Tools，`prlctl exec` 不可用，解除不了；改用 `error-once` |
| 本机 `cargo clippy` 全绿就认为 Windows 侧也绿 | `#[cfg(windows)]` 模块在 macOS 上一条都不编译 |

正确形态：`ramdisk=[F:]\BackupRestoreRE\<task-id>\Winre.wim,{devopts}` —— **方括号只包"卷"，`]` 紧跟卷后闭合，结尾没有 `]`**。
