# 下一步待实现

版本 **2.2.0**；模型 Opus 5（1M 上下文）。

## 一、必须先做：新载荷路径的实机验收

本轮把载荷目录改成按任务隔离，**改变了 BCD 元素的实际值**（`ramdisksdipath` 与 `device/osdevice`
里的 ramdisk 路径）。2.1.9 的 11 点断电续跑证据取自旧的共用路径，不能直接套用。按 `AGENTS.md`，
下列操作前必须先建并核验新的 Parallels 快照（最多保留最近 2 个）：

1. 部署 2.2.0 到客体包目录与 `H:\brwork\`，逐一核对 SHA-256；
2. 一次完整链路：准备 → 重启进 RE → 捕获/应用 → 引导修复 → 清理 → 回正常 Windows；
3. 至少一次 `rearm()` 续跑，证明新路径的启动链回读（`verify_chain`）与载荷探测在实机成立；
4. 一次「两个未终结任务并存」的实机用例：准备 A 后再准备 B，核对 A 的载荷哈希不变、
   清理 B 不影响 A，以及第二次武装被 `allow_rearm` 拒绝；
5. Windows 侧常规回归（2.1.9 为 156 项，本轮新增测试后应更多）。

另需人工确认并清理镜像卷上旧版遗留的共用 `BackupRestoreRE\Winre.wim` / `boot.sdi`——
新代码不认它们，也不会误删。

## 二、问题清单剩余两项

- **第 10 项**：`text_parsing::esp_log_path` 与 `ESP_LOG_DIR` 仍返回固定 `S:\…`，
  而主链已有 `esp_identity_without_drive_letter()` 统一入口。应让控制文件与 BCD 操作
  使用同一个已验证的 ESP 对象；兼容盘符通道时要核验盘符确实映射该分区，不用字符串替换代替路径解析。
- **第 11 项**：准备期缺少覆盖所有副作用的统一回滚。目前只有重启失败分支会撤销启动序列与条目；
  建条目、注入、复制、哈希刷新、状态落盘各点失败仍可直接返回，可能留下本任务的条目或载荷。
  应记录每个已完成副作用及其所有权，用统一清理路径撤销，并为掉电后的遗留事务提供恢复入口。

## 三、仍然保留的既有边界

- BCDBoot 完成后断电目前支持进入系统并显式 `resume`；要做到完全自动需重新设计持久恢复入口，
  会改变当前仅用一次性启动请求的设计。
- 状态事务的三个内部文件边界由真实文件重放测试覆盖；要增加存储介质级证明需另做定点断电。
- 按用户要求不扩展平台（Windows 10、x64、实体设备均不在范围内）。
