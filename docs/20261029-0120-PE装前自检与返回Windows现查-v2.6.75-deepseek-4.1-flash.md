## 一、第一件：装前自检（只警告）

### 1.1 判的是什么

镜像里 `Windows\System32\winpeshl.ini` 决定「WinPE 启动后运行哪个程序」。产品期望它**逐字等于**：

```
[LaunchApps]
%SYSTEMROOT%\System32\Recovery.exe,--pe-desktop
```

三条判据（任一不过即提示）：

1. 这个文件在镜像里**存在**（没有它，WinPE 会退到 `startnet.cmd`，停在黑命令行）；
2. 内容**逐字等于**上面那份（不是「包含 `Recovery.exe`」——宽松判据在别的坏法上会漏，
   论证见 `docs/20261029-0014` §三，那里也订正了我先前写错的一处事实）；
3. 它指向的 `Recovery.exe` **在镜像里存在**（防「配置对、程序没打进去」的半成品）。

### 1.2 怎么实现

| 部分 | 位置 | 说明 |
| --- | --- | --- |
| 判定（纯逻辑） | `crates/backuprestore-cli/src/text_parsing.rs` | `EXPECTED_PE_SHELL` / `normalize_shell_text` / `PeShellFacts` / `judge_pe_shell` / `PeShellProblem` |
| 从镜像里取事实 | `crates/backuprestore-cli/src/wimlib_apply.rs` | `probe_pe_image_shell`（`#[cfg(windows)]`），`wimlib-imagex dir` + `extract` |
| 对话框与接线 | `crates/backuprestore-cli/src/native_gui.rs` | `confirm_pe_image_shell`，在硬盘版与内存版**各自**的破坏性确认之前调用 |

**为什么用 wimlib 不用 DISM**：只需读一个几百字节的文件，DISM 要先挂载整个镜像（400 MB 起、
要临时目录、要清理），代价与收益不成比例。

**两个实测坑写进了代码注释**：

- `wimlib-imagex extract` 取**单个文件**会把它**拍平**到 `--dest-dir` 根下（实测落点是
  `<dest>\winpeshl.ini`，不是 `<dest>\Windows\System32\winpeshl.ini`）→ 两处路径都找；
- 文件不存在时 `extract` 的退出码是 **49**（不是 0/1）→ 所以先用 `dir` 判存在性，再决定提不提取，
  避免把「镜像损坏」误报成「缺这个文件」。

**三条刻意的设计选择**：

- **探测失败一律不拦**（缺 wimlib、镜像被占用、wimlib 报错）：这是附加保护，不是安装前置条件；
  做成硬门禁会让「装 PE」在缺 wimlib 的机器上整体不可用，而那些机器本来也能正常装 PE。
  失败时日志写 `PE image shell check skipped (probe failed): …`。
- **默认按钮放在「否」**（`MB_DEFBUTTON2`）：让人看见，但别让一个回车把坏镜像装上去。
- **只警告不拦**：警告框点「是」照装，日志记 `PE image shell warning acknowledged; continuing by user choice`。

### 1.3 变异验收（本项目铁律：验收是变异，不是变绿）

纯逻辑 14 条用例（`text_parsing::pe_shell_and_loader`）先在 macOS 跑绿，然后**故意拆判据**：

| 变异 | 结果 | 抓住它的用例 |
| --- | --- | --- |
| 判据从「逐字等于」降级为 `contains("Recovery")` | 🔴 3 条红 | `old_two_entry_shell_is_rejected…`、`shell_with_an_extra_second_entry_is_rejected`、`shell_without_the_desktop_argument_is_rejected` |
| 去掉「排除 winpe 条目」这一层过滤 | 🔴 2 条红 | `pe_only_store_yields_nothing_instead_of_the_pe_entry`、`candidate_needs_the_loader_file_to_exist…` |

★ **诚实的观察**：变异二下 `windows_loader_is_picked_and_the_pe_entry_is_skipped` **仍然绿**——
因为真机那份 `displayorder` 里 Windows 排在 PE 前面，等于被顺序救了。**真正抓住这个变异的是
「只有 PE 条目时必须返回 None」那条**。这条记下来是为了下次别再拿「主用例绿了」当判据有效的证据。

### 1.4 实机验证（同一台机、同一个 8 GiB 分区）

| 输入镜像 | 日志 | 装完 `T:\…\winpeshl.ini` |
| --- | --- | --- |
| `H:\BRImages\pe-boot.wim`（09-13 旧件，367,395,379 B） | `PE image shell check: PE image winpeshl.ini is not the expected shell (89 bytes): [LaunchApps] \| %SYSTEMROOT%\System32\RecoveryLauncher.cmd \| %SYSTEMROOT%\System32\recenv.exe` → `test hook: PE image shell warning auto-continued` | **89 字节**（日期 2026/08/19） |
| 新件（412,928,209 B） | `PE image shell check passed` | **61 字节** |

两行合起来就把用户裁决验完了：**发现不对 → 提示 → 仍按用户意愿装完**，
并且「装完真的是 89 字节」证明这不是空转（garbage in / garbage out 依旧成立）。

★ **警告框本身没有截到图**：验收走的是 `--test-hook` + `auto_install`，而该钩子按设计会
自动跳过确认框（`test hook: PE image shell warning auto-continued`）。对话框文案与
`MB_YESNO | MB_ICONWARNING | MB_DEFBUTTON2` 只经过代码审查，**没有人眼证据**。这是本轮的一个缺口。

## 二、第三件：「返回 Windows」改为现查

### 2.1 改成什么样

`exit_pe_to_windows`（`native_gui.rs`）不再读 ESP 上的 `S:\pe-exit-guid.txt`，而是：

1. `bcdedit /store <S:\EFI\Microsoft\Boot\BCD> /enum all /v` 拉全量；
2. 纯逻辑 `text_parsing::pick_windows_loader` 认候选：
   **非 winpe** + `path` 含 `winload.efi` + `device` 是 `partition=X:` + 该盘符上
   `Windows\System32\winload.efi` **真的存在**（盘符是 PE 视角的，只有 PE 自己能判，
   所以这个谓词由调用方注入）；
3. 多条候选时**按启动菜单顺序**（`displayorder`，多行值）取第一条；
4. 认出来才 `set {bootmgr} default <guid>` + 清 `bootsequence` + 复核枚举；
5. **认不出来就绝不编一个 GUID 写进去**（那正是上一版把 default 写成悬空值的原因），而是分两种：
   - 当前 `default` 指着**某个 PE 条目** → 只清 `bootsequence`、**不重启**，留在 PE 并弹诊断，
     让人自己从启动菜单选 Windows；
   - `default` 不是 PE 条目 → 清 `bootsequence`、**不动 default**、照现状重启
     （bootmgr 会回落到 `displayorder` 第一项）。
   两种结局用两个布尔分开记（`found_bcd` / `reboot_without_target`），不混成一个。
6. 过程全部进 `S:\exit-pe.log`：每条候选的 `identifier/winpe/device/path`、最终选中的
   `live Windows loader: …`、每一步退出码。

### 2.2 `winpe` 字段的判据为什么是「字段存在」而不是「值等于 Yes」

**安全偏向**：值读错最多让候选集变空（于是「不动 default」），而把 PE 条目误认成 Windows
会直接把人送回 PE——两种错的代价差一个数量级。实测确认 `bcdedit` 中文环境里这个字段名
**不翻译**（就是 `winpe`，值 `Yes`），但判据仍按「存在即排除」写，不问值。

### 2.3 实机验证：一次负向对照 + 一次正向

都先**故意把 `S:\pe-exit-guid.txt` 写成假 GUID `{11111111-1111-1111-1111-111111111111}`**，
这样「有没有读那个文件」一眼可辨。

**负向对照（旧代码，PE 桌面显示 v2.6.74）**

```
S:\exit-pe.log:  deploy GUID: {11111111-1111-1111-1111-111111111111}
bcdedit:         default  {11111111-1111-1111-1111-111111111111}
```

→ 盲信文件、把 `default` 写成**不存在**的条目。机器还能进 Windows，靠 bootmgr 回落第一项。
**这就是用户拍板要改掉的那个行为，现场复现成功。**

**正向（v2.6.75，PE 桌面显示 v2.6.75）**

```
S:\exit-pe.log:  enum all exit code: 退出码 0
                 enum candidate: … 534 条（其中 13 条 winpe=true 全部被排除，含我们自己历次装过的 4 条 PE 项）
                 live Windows loader: {a6273652-d15f-11f1-aa4b-ff70ff0b7794}
                 set default exit code: 退出码 0
bcdedit:         default  {a6273652-d15f-11f1-aa4b-ff70ff0b7794}   ← 真实 Windows 项
```

文件里明明是假 GUID，写进去的却是真的 → **现查生效**，且 534 条杂项条目里没有选错。

**为什么必须重出镜像才能测**：PE 里的 `Recovery.exe` 是**构建镜像时烤进去**的，装 PE 只是把 WIM
原样铺开。所以这一轮先用 2.6.75 的载荷重出了 `pe-boot.wim`（412,928,209 B，
SHA-256 `93483be2d0a24b68c110fee3630c24cf13358b2a1229a7603f65ae32ef65dba1`），
PE 桌面标题才从 v2.6.74 变成 v2.6.75。

## 三、版本与构建

- 三处同步：`VERSION` / `backuprestore-cli/Cargo.toml` / `backuprestore-core/Cargo.toml` → **2.6.75**；
- ★ 踩到的构建坑：只改 `Cargo.toml` 不改 `Cargo.lock` 时，虚拟机内构建脚本带 `--locked` →
  `error: cannot update the lock file X:\Cargo.lock because --locked was passed`。先在本机
  `cargo check --workspace` 刷新 lock 再进虚拟机；
- ★ 第二个坑：**不能把 target 目录放在共享盘**（`X:\target`）→
  `failed to build archive … failed to remove temporary directory: 参数错误`。
  用 `-CargoTargetDir C:\brtarget` 指到本地盘即可；源码仍可留在共享盘。

构建命令（虚拟机内，用户会话）：

```powershell
& X:\windows\build-windows.ps1 -Architecture arm64 -Deploy -CargoTargetDir C:\brtarget
# → 2.6.75 / SHA256 118d14385d69e5a750e3b49751e8af9544d9128752ae4a514a83afb9c1c49042 / H:\brwork
```

## 四、第四件：安全启动侦察（未做真机验证）

- 本机（Parallels）`Confirm-SecureBootUEFI` = **False**：安全启动**关闭**。
  ⇒ **这台虚拟机能跑通 PE，完全不能说明开着安全启动的真机也能跑通。**
- 但把「会不会被签名挡死」这个风险点查清了：Secure Boot 真正会验证的三个文件全部 **Valid 且签发给
  Microsoft**：

  | 文件 | 状态 | 签署者 |
  | --- | --- | --- |
  | `T:\Windows\System32\winload.efi`（来自我们的 PE 镜像） | Valid | CN=Microsoft Windows |
  | `T:\Windows\System32\ntoskrnl.exe`（同上） | Valid | CN=Microsoft Windows |
  | `S:\EFI\Microsoft\Boot\bootmgfw.efi`（ESP 上的启动管理器） | Valid | CN=Microsoft Windows |

  我们自己的 `Recovery.exe` 是**用户态程序**，安全启动不校验它。

⇒ 结论：签名链这一关**大概率不是问题**（WinPE 本身就是微软签名的，这也是业界用 PE 装机的前提）。
剩下的真机不确定项变成：固件是否消费「一次性启动序列」、ARM64 与 x64 的固件差异、
真机的分区/盘符布局。**真机验证仍待安排**（用户裁决「暂不验证」）。

## 五、第二件为什么本轮没做（如实交代）

用户裁决是「要观测，把事实钉死」。这一轮**没有做**，原因是顺序问题而不是改变主意：

- 前两件事都已进入产品代码并需要实机验证，而验证要重出 PE 镜像、反复重启进出 PE；
  观测盘符同样要跑一次真实的「准备恢复环境」流程，两者抢同一台机器、同一轮时间；
- 本轮已经用掉两次完整构建 + 三次进/出 PE，继续叠加观测会让这一轮变成「什么都做了一半」。

**下一轮第一件事**（已想清楚做法，不需要再拍板）：

1. 在 `windows_prepare::identity_from_diskpart` 的 `diskpart assign letter=` **前后各一行日志**
   （记：盘符字母、分配前该卷是否已有盘符、分配后结果、`\DosDevices\*` 条数）；
2. 在准备恢复环境期间以 **100–250 ms** 采样一次「当前有哪些盘符」，落成一条时间线；
3. 跑一次真实的准备流程（挑测试盘），读时间线回答三个问题：
   **谁分配的、什么时候分配的、有没有被收回**；
4. 只有观测到之后才决定 `windows_prepare.rs:1228` 那段「收回」代码是删、是改、还是保留
   （本轮仍只保留 `debug_assert!`，不改变行为）。
