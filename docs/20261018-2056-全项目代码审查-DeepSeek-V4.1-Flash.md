## 1. 高危

### H1 · A 入口「目标锁定当前系统盘」失效，且全链无硬闸 → 界面显示的卷 ≠ 实际格式化的卷 ✅源码核对

**位置**：`native_gui.rs:2498-2515`（`select_drive`）、`2172-2175`（`target_combo_indices`）、`2089-2094`（`select_operation` 对 A 调 `select_drive`）、`1510-1515`（A 页 `EnableWindow(target,0)` 禁用）、`6562-6588`（`create_task` 取目标/源）、`6651-6652`（GUI 目标闸门）、`windows_prepare.rs:2381-2383` 与 `2398-2404`（prepare 侧闸门）。

**机制**：
1. `select_drive` 对「目标卷」分支写作 `target_combo_indices(state).as_deref().and_then(|view| …)`；而 `target_combo_indices` 在**非 `create-secondary` 入口返回 `None`** → `and_then` 得 `None` → `position=None` → **`CB_SETCURSEL` 从不发出**。同文件的 `drive_combo_position`（`2200-2208`）对 `None` 是恒等映射，`select_drive` 独缺这一回退，**两者不对称**。
2. A 入口文案写「目标卷（当前系统盘 C:）」（`2051`）且把下拉 **`EnableWindow(...,0)` 禁用**（`1512-1515`），意图是「`select_operation` 会自动选中 `%SystemDrive%`」——但 `select_drive` 空转，**这个意图落空**。
3. 于是目标 combo 停在**上一个入口选中的盘**。`create_task` 又令 `source_drive = target_drive.clone()`（`6587`，A/B 统一），prepare 仅要求 `source==target`（`2381-2383`）即放行。
4. GUI 目标闸门（`6651`）只匹配 `restore-data | create-secondary`，**A（`restore-existing`）不在内**；prepare 的 P0 闸（`2400`）只对 `CreateSecondary` 生效，且注释明确写「restore-existing **不加**这条」（`2398-2399`）——**无任何一处**断言「A 的目标＝活动系统卷」。

**后果**：A 页下拉若停在 D:/E:/F:，则源＝目标＝该盘，链路直通「格式化该盘 → 灌回 Windows 镜像 → 修引导」。界面文案却写「当前系统盘 C:」——**显示卷 ≠ 操作卷**，非系统盘数据全丢。唯一残留拦截是破坏性确认框里的「目标卷：D:」一行。

**与既有审查的关系**：即 `20261018-0247` 的 **H1**，**未被后续任何提交修复**（`f4136a9` 只改了 tooltip 与非法路径弹窗，未动 `select_drive`）。

**修法**（两层缺一不可）：
- `select_drive` 目标分支：视图为 `None` 时退回恒等映射（或直接复用 `drive_combo_position`）；
- **A 的 `create_task` 加硬闸**：`restore-existing` 时断言 `target_drive == active_system_letter()`，否则报错中止（不能只靠 UI 自动选中——本次正是 UI 自动选中失效）；prepare 侧同步加同判据。
- 建议补一组**纯逻辑单测**（构造假 `drives` + 假视图，断言「界面选中 X → 实际取到 X」），一次性锁死 `target_combo_indices`/`select_drive`/`set_drive_items`/`selected_drive_letter` 四者的索引换算。

### H2 · 状态机缺 `(RecoveryComplete, Failed)` 边 → RecoveryComplete 阶段失败后任务永久悬置 ✅源码核对

**位置**：`backuprestore-core/src/lib.rs:113-138`（`can_transition_to`）、`1377`（`write_failure` 首行守卫）、`160`（`can_resume_after_interruption` 仍含 `RecoveryComplete`）、`main.rs:1519-1549`（`auto_escape_to_windows` 第②步）、`main.rs:1041-1042`（`complete_recovery_cleanup`）。

**机制**：`can_transition_to` 里 `RecoveryComplete` **只有一条出边 `(RecoveryComplete, Success)`**，没有 `(RecoveryComplete, Failed)`；而 `write_failure` 第一行就是 `if !task.status.can_transition_to(Stage::Failed) { return Err(…) }`。

**后果**：任务走到 `RecoveryComplete`（STEP 4 清理阶段）后确定性失败 → 自动逃出第②步 `write_failure` 返回 `Err("cannot fail task from RecoveryComplete")`，代码只 `append_log` 记一行 → 任务仍停在 `RecoveryComplete`。而 `RecoveryComplete` 仍在 `can_resume_after_interruption` 里 → 下次启动 `find_pending_boot_task` 再次发现它 → 再次提示重启 → 又失败 → 又逃不出；`abandon-task` 在该阶段也被拒 → **用户无自救出口**，且日志里不会出现注释承诺的「任务已标终态」。

**与既有审查的关系**：即 `20261018-0247` 的 **H2**，**仍在**（`lib.rs:137` 至今仍只有 `(RecoveryComplete, Success)`）。

**修法**：`can_transition_to` 增加 `| (RecoveryComplete, Failed)`（此时磁盘/引导/恢复注册均已验完，标失败只影响清理）；或让 `write_failure` 对 `RecoveryComplete` 特判放行。

### H3 ·（新）进度窗消息循环把 `Esc` 交给编辑器专用的 `handle_key` → 销毁焦点控件/主进度窗，且绕过「暂停中关窗」防卡死处理 ⚠️需实机复现

**位置**：`recovery_progress.rs:1716-1728`（`key_target` 循环）、`boot_menu_window.rs:343-356`（`handle_key`，`Esc` → `DestroyWindow(hwnd)`）、`recovery_progress.rs:1432-1461`（主窗 `WM_CLOSE` 的 `pause_abandoned` 置位，2026-10-16「卡死 4」修复）、`1624`（主窗 `WS_OVERLAPPEDWINDOW | WS_VISIBLE`）。

**机制**：
```rust
let mut key_target = msg_hwnd;                       // ← 从「消息目标」本身起调
while !key_target.is_null() {
    if crate::boot_menu::handle_key(key_target, &*msg.as_ptr()) { break; }
    ...
}
```
`handle_key` 的入口守卫是 `(msg.hwnd != hwnd && IsChild(hwnd, msg.hwnd) == 0)`（`343-350`）。当以 `key_target = msg_hwnd` 调用时，`msg.hwnd == hwnd` 成立 → 守卫**恒放行**，随即命中 `if key == 0x1b { DestroyWindow(hwnd); }`。也就是说：**焦点落在哪个窗口上，Esc 就销毁哪个窗口**——而 `handle_key` 本是「引导修复编辑器」（类名 `BackupRestoreBootMenuClass`）专用处理函数。

**后果**：
- 焦点在主进度窗的**子控件**（按钮/日志尾部/详情框等 `WS_TABSTOP` 控件）→ `DestroyWindow(子控件)`，该控件凭空消失；
- 焦点在**主进度窗自身**（点窗口空白/详情区可取得焦点）→ **整个进度窗被销毁**，且 `DestroyWindow` **不走 `WM_CLOSE`**，`1432-1461` 的 `pause_abandoned` 置位被跳过 → 若当时处于暂停，恢复主线程在 `wait_if_paused` 里无超时自旋：**进程活着、无 UI、无出口**（正是「卡死 4」要根治的场景）；
- 反向地，在**引导修复编辑器内**按 `Esc` 也只会销毁焦点子控件、而不会关闭编辑器（UI 文案却写「Esc 关闭」）。

**性质**：该循环与 `handle_key` 的这段调用在 v2.6.17 改动**之前就存在**（是 diff 的上下文行），故属**先于本轮的历史遗漏**，上一份审查未记录。

**修法**：在调用前加窗口类校验——仅 `GetClassName == BackupRestoreBootMenuClass` 的窗口才调 `handle_key`；或在主窗家族里显式吞掉 `Esc`。这样既修「误销毁」，也修「编辑器 Esc 不关窗」。

## 2. 中危

### M1 · 跨阶段总重试计数在重启前自增、失败不回滚 ✅源码核对

**位置**：`main.rs:776`（`bump_total_attempt`）、`809`（`shutdown.exe /r`）、`824`（失败分支只 `release_boot_resume_attempt`）。
**机制/后果**：`bump_total_attempt` 在 `shutdown` **之前**落盘（+1）；`shutdown` 失败只释放 **per-stage** 标记，**总计数不回滚**。于是 `rearm`/`shutdown` 连续失败 3 次（机器一次都没重启）也会把总闸烧到上限 → 自动续跑被**永久关闭**，且日志只写「已达总上限」，看不出从未重启过。
**修法**：把 `bump_total_attempt` 移到 `shutdown.status.success()` **之后**，或失败分支把计数减回。

### M2 · combo 重填用「新视图」读「旧内容」，且把源卷重置为第 0 项 ✅源码核对

**位置**：`native_gui.rs:2086`（`state.operation_index = index` 在最前）、`2119`（`keep = selected_drive_letter(...)`）、`2127`（`set_drive_items([None, None, keep])`）、`2486-2495`。
**机制/后果**：`operation_index` 已更新后，`selected_drive_letter` 按**新入口视图**解释 combo 里**旧入口填充**的索引 → 切换入口时选中项被静默移位（如 C→A 时把用户选的 F: 读成 E:）；`desired[1]=None` 又把**源卷（备份页）静默重置为第 0 项**——切走再切回后可能**备份到错误的分区**。
**修法**：在更新 `operation_index` **之前**用旧视图取 `keep`；重填时把当前源卷盘符一并传入。

### M3 · `loader_identifier_for_partition` 同分区多 loader 直接 Err，且发生在镜像已应用之后 ✅源码核对

**位置**：`boot_menu.rs:538-540`，调用点 `main.rs`（`assert_boot_default_points_at_target` 等）以 `?` 中断。
**机制/后果**：BCD 里同一分区残留两个 loader（上次还原留下/用户手动加过）→ **bcdboot 成功后、镜像已应用、目标卷已格式化之后**才失败 → 任务停 `ImageApplied`，重试同样失败，3 次后 auto-escape。旧实现不做全枚举，**没有这条失败面**——是 v2.6.1 起新增的。
**修法**：降级——取 `{default}` 当前指向的那个 loader 并记 WARN，而不是拒绝。

### M4 · 「暂停总上限」名不副实：每次调用都新建 deadline ✅源码核对

**位置**：`recovery_progress.rs:243-245`（`wait_if_paused`）。
**机制/后果**：`let deadline = (limit_secs > 0).then(|| Instant::now() + Duration::from_secs(limit_secs));` 每次进入等待都新建完整时长 deadline；日志文案写的是「暂停**总**上限」，实际是「**每次暂停** N 秒」，反复「暂停→继续」可无限累积，与承诺语义不符。
**修法**：deadline 存进 `ProgressShared`（首次暂停设定、续跑不重置）；或改名/改文案为「单次」。

### M5 · BCD 回退在窗口线程持锁跑 `bcdedit`，进度窗「未响应」 ✅源码核对

**位置**：`recovery_progress.rs:1162-1166`（`trigger_bcd_rollback` 整段在 `bcd_rollback` 锁内执行 `action()`）。
**机制/后果**：`action()` 内部挂 ESP + 跑 `bcdedit`，可能数十秒；窗口消息循环停转 → 进度窗「未响应」、定时器停更。**不是死锁**（无 AB-BA：`log_path` 锁只被窗口线程取；`set_bcd_rollback` 在准备期一次性调用），但界面冻结。
**修法**：`let action = guard.as_ref().cloned();` 后**释放锁**再执行；或丢工作线程、按钮先置灰。
**附带（新）**：BCD 回退的成败只 `append_log` 写日志文件，**界面零反馈**（不改按钮态、不弹提示）——用户点完只能瞟一眼日志尾部，失败也无法确认，属「静默结果」。

### M6 ·（新）在线 `restore-existing` 数据卷分支用「格式化前的旧盘符」做 `/ApplyDir`，盘符↔分区再校验在 Apply 之后 ✅源码核对

**位置**：`online_operation.rs:322`（`let root = PathBuf::from(format!("{affected}:\\"))` 在格式化前取定）、`356-391`（格式化 → `refresh_identity(&identity)` 校验同分区）、`406`（`/ApplyDir:{root}`）、`416-423`（Apply **之后**才 `volume_identity(affected)` 复核）。
**机制/后果**：`root` 是**盘符路径**，格式化后若 mountmgr 把该盘符重排到别的卷，DISM 会**写到错误卷**；同文件的 `restore_to_windows_volume` 却已改用 `after.volume_path()`（GUID verbatim 路径）——两处不一致。事后校验（`416-423`）只能「写完后发现」，破坏性写入已完成。
**修法**：Apply 改用 `formatted.volume_path()`（卷 GUID 路径）；或在 Apply 前用 `pe_safety::verify_binding` 复核盘符↔分区绑定。

### M7 ·（新）CLI `recover` 手动路径 `metadata_context=None` → 跳过「擦除前 rearm」与「载荷卷≠目标卷」两道闸 ✅源码核对

**位置**：`main.rs:1045-1053`（`recover_windows(&store, …, None, false, None)`）、闸门 `main.rs:3329-3346`（`if metadata_context.is_some() { … 校验载荷卷 … boot_entry::rearm(&entry, log)?; }`）。
**机制/后果**：`metadata_context` 为 `None` 时，**擦除前不重新武装一次性启动项**（中断后落回原版 WinRE、无法续跑），且**不校验「续跑载荷卷 ≠ 擦除目标卷」**——存在误擦载荷卷的可能。
**修法**：让 `recover` 同样加载 env 并传入 `metadata_context`，或把这两条闸改为**无条件执行**。

### M8 ·（新）BCD / 工具输出的「字段名本地化」盲区（多处硬编码英文/中文）⚠️需实机复现

同一类问题散落多处：解析器对**对象标识符**已双语（`identifier`/`标识符`），但对**字段名**只认 ASCII 或中英双写：
- `winre_registration.rs:95-105`（`field`：`device`/`osdevice`/`path`/`winpe`/`recoverysequence`/…全 ASCII；同文件 `object()`（`112-120`）却已同时认 `identifier`/`标识符`——**认识到了本地化却只补了对象键**）→ 缺/重即硬失败「BCD 字段缺失或重复」；
- `resume_safety.rs:6-31`（`field`：同样只认 ASCII）→ 断电续跑时本地化即 `verify_chain` 硬失败「续跑启动链字段不符」；
- `text_parsing.rs:961-971`（`ramdisk_device_options_guid`：`starts_with("device ")||("osdevice ")`）→ 建启动项取不到设备选项对象 GUID；
- `text_parsing.rs:322-328`（`bcd_output_has_bootsequence`：只认 `bootsequence`/`启动序列`）；
- `pe_safety.rs:30-60`（`target_loader`：只认 `device`/`osdevice`/`path` + `\windows\system32\winload.efi`；在线链已改用容忍中文的 `boot_menu::loader_identifier_for_partition`，**PE 未跟进**）→ PE 在「格式化+应用之后」的 boot 步报「目标引导加载器不唯一」的**假失败**；
- `winre_registration.rs:40-54`（`parse_info` 状态值须等于 ASCII `enabled`/`disabled`）。
**后果**：非英文/非中文 Windows 上，这些解析会在**破坏性写入之后**硬失败。**注**：仓库内实机抓样显示字段名是英文（仅对象头/`标识符` 中文化），故**当前多半不触发**，属韧性短板而非现网缺陷。
**修法**：抽一份「本地化感知的 BCD 字段读取」，或改为「按对象块 + 值形态」匹配。

### M9 · `CONTAINMENT_FAILED` 是进程级永久锁，且成功路径也参与置位 ✅源码核对

**位置**：`windows_command.rs:14`（`static CONTAINMENT_FAILED: AtomicBool`）、`301`（`stop_tree` 未确认归零即置位）、`399`（`AssignProcessToJobObject` 失败也置位）、`306-308`（置位后**所有**外部命令立即 `ContainmentFailed`）、`419-421`（`Exited(0)` 成功路径也 `stop_tree`，失败即**丢弃真实退出码**）。
**机制/后果**：一次瞬时的 `QueryInformationJobObject`/作业对象未归零（如 DISM 退出后残留 worker >10s）→ 本进程**此后所有外部命令永久失败**，且不可复位。若发生在 RE 链「格式化之后」，DISM/bcdboot 全灭 → 目标卷已清空却无法写入；GUI 长驻进程里还会污染后续无关命令，须重启程序。属**有意的 fail-closed**，但失败域被放大到「进程级」远超需要。
**性质**：上一份审查列为 **L5**（低危）；本轮据「成功路径也置位 + 格式化后触发即全链报废」**上调为中危**。
**修法**：失败域缩到「本次操作」（操作边界复位）；或引入「遏制待复核」态（确认作业对象已空可放行）。至少把「本命令失败」与「整进程禁用」用独立分支区分，并附真实退出码。

### M10 · `require_administrator` 把「日志不可写」误报成「需要管理员」 ✅源码核对

**位置**：`windows_prepare.rs:2803-2811`（`require_administrator` 用 `capture_logged`）、`main.rs:3836`（`capture_logged` 第一行即 `append_log(log, …)?`）。
**机制/后果**：`capture_logged` **先写日志**再跑 `fltmc`；若日志不可写（目录满/ACL 限/`logs_dir` 回退到不可写目录），`?` 在 `fltmc` **之前**就失败 → 被 `require_administrator` 一律翻成「administrator elevation is required」。用户反复提权仍失败，**真正原因被带偏**。
**修法**：先做真正的权限判据（`fltmc` 退出码），日志写入单独 try 并记录；或加一个不写日志的 `capture()` 变体。

## 4. 设计观察（做得对的地方，非缺陷）

1. **身份以 GUID/分区号为准、不以盘符为准**：`diskpart_format_script`（`main.rs:3708-3725`）按已验证的 disk/partition 号选目标，`verify_formatted_volume`（`operation_safety.rs:29-63`）校验「同分区 + 几何 + 序列号已变」，多数 apply 走卷 GUID 路径——M6 是本组里唯一的漏网点。
2. **在线路径「候选副本 + 回读 + 失败回滚」**：`online_operation` / `pe_operation` 对系统卷还原既做预检又做事后身份复核，失败保留候选与日志。
3. **`decide_default` 纯函数化 + 单测护栏**（`boot_menu.rs`）：把 default 归属收敛为唯一纯函数、可在 macOS 单测，锁住「default 静默漂移」的决策点。
4. **`assert_boot_default_points_at_target`** 是「回读→自愈→再回读」的正确形状。
5. **`dism_timeout` 默认 0（不限制）** 而非固定秒数：避免误杀机械盘上的合法长还原；`plan_env_value` 修掉「ini 配置对在线/安装 PE 静默不生效」的真实缺口，纯函数可单测。
6. **`failure_policy` 容器解析的两种口径**：坏值静默回退默认（绝不让恢复环境起不来），但对用户显式输入严格（拒 `+3`/`3.0`/全角）——两种口径分得清。
7. **`pe_safety::overlay_restore_on_windows_volume_error` 抽成纯函数**（`MessageLanguage` 维度）供离线/在线/GUI/单测四处共用，杜绝文案分叉重演——但**在线 create-secondary 无条件进 `restore_to_windows_volume` 且把 `target_contains_windows` 硬编码为 `true`**（`online_operation.rs:452` + `487-488`）：目标为**空分区**（C 入口常态）而用户取消格式化时，会以**事实错误的文案**「已含 Windows」拒绝一个合法组合。修法：传真实探测结果（同 `execute_inner:347` 的 `target_is_windows_volume(&target_root)`）。🔶新发现
8. **`winre_registration` 降级边界划得准**：`Preflight::Skip` 在任何注册写入之前返回；身份不符、ESP 与活动 BCD 加载器不一致等安全闸门仍硬失败；`Skipped` 原因既进任务日志又在结尾复述。
9. **`log_root` / `session_log` fail-safe**：`OnceLock`、`current_exe().ok()`、`unwrap_or_else` 兜底，只读/无盘时不 panic（问题在 L2/L3：不识别目标卷、留空目录）。
10. **`secondary_registry::gpt_mapping` 对 MBR 不 panic**：`Uuid::parse_str` 失败返回硬 `Err`（非崩溃、非误写）；`DMIO:ID:` 混合端序经测试向量确认正确——但错误文案「分区 GUID 无效」与「不支持 MBR」混同，建议区分。
